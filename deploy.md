## 1. Что именно мы деплоим

| Часть | Что это | Нагрузка |
|---|---|---|
| Фронтенд | React + Vite, статические файлы после `npm run build` | раздаёт CDN/nginx, почти бесплатно |
| API | FastAPI (`backend/app`), один процесс uvicorn | чтение контента, запись прогресса, постановка проверок в очередь |
| БД | SQLite, `backend/data/say.db`, **18 МБ**, режим журнала сейчас `delete` (не WAL) | см. раздел 3 |
| Проверка кода | очередь `exec_jobs` в той же БД + воркеры с Docker (`local` — потоки внутри API, `remote` — `backend/worker.py` на другой машине) | самая тяжёлая часть, раздел 2 |
| Лаборатории (книги 14, 15, 17, 18) | симуляторы целиком **в браузере**, на сервер уходит только «решено» | нагрузки на сервер почти нет |
| Озвучка | сейчас не используется (см. правило в AGENTS.md); потом — статические wav | статика |

Контент (учебники, слайды, квизы, задачи) меняется только при выкладке новой версии — это данные «только для чтения»
во время работы. Меняется только то, что пишут пользователи: прогресс, черновики, попытки, задания в очереди.

Целевая схема на будущее (из прошлого обсуждения): основной бэкенд на VPS, отдельная VM на домашнем сервере с Docker забирает
задания сама (исходящий HTTPS, входящих портов нет). **Для первого запуска** — всё на одной машине (раздел 7, «Этап 1»);
схема собирается так, чтобы потом воркер можно было вынести на другую машину переносом одного сервиса.

## 2. Узкое место — выполнение кода, а не FastAPI

### 2.1 FastAPI не узкое место

Что делает API на запрос: проверяет сессию, читает/пишет несколько строк в SQLite, отдаёт JSON. Тяжёлого вычисления
внутри нет — самое дорогое (запуск чужого кода) вынесено за пределы процесса. Грубая оценка на одном ядре: порядка
1–2 тысяч таких запросов в секунду; реальных запросов у нас будет на порядок меньше.

Прикидка нагрузки на 1000 одновременно занимающихся (**[измерить]** на реальном трафике):

- просмотр слайда — 1 запрос на слайд раз в 30–60 с → ≈ 20 запросов/с;
- автосохранение черновика кода (с задержкой) — пока ученик печатает, ≈ 1 запрос/с на печатающего; допустим 100 печатающих → 100/с;
- проверка кода: сама постановка — единицы в секунду, но **опрос результата** `GET /run/{id}` каждые 0,7 с за каждую идущую проверку;
  50 идущих проверок → ≈ 70 запросов/с;
- итого сотни запросов в секунду на пике — одного процесса uvicorn хватает; при росте добавляем процессы
  (`--workers N`) или машины.

Переписывать на Rust (или Go) не имеет смысла: выигрыш в скорости ответа на нашей доле времени запроса не заметен,
а стоимость — переписанный бэкенд, потеря скорости разработки, раздвоение кода задач/сидера на Python. Если API
когда-нибудь упрётся в CPU, это решается числом процессов и кэшированием, а не языком.

Что реально стоит сделать для API раньше, чем думать о языке:

- включить WAL и `busy_timeout` в SQLite (раздел 3) — сейчас каждый запрос открывает новое соединение с журналом `delete`;
- HTTP-кэш и `ETag` для неизменяемого контента (учебники, список задач без ответов), `Cache-Control: immutable` для статики
  с хешами в имени (Vite делает сам);
- gzip/brotli на уровне nginx/CDN;
- вынести ограничение скорости (rate limit) на вход/регистрацию/`run` по IP в nginx или в приложение (см. раздел 6).

### 2.2 Почему узкое место — песочница

Каждая проверка = запуск контейнера Docker: создание, монтирование tmpfs, старт интерпретатора/компилятора, прогон тестов,
уничтожение. Это секунды CPU и десятки/сотни МБ памяти на одну проверку, а не миллисекунды.

Ориентиры (**[измерить]** на домашнем сервере; сейчас в `exec_jobs` есть только 30 лёгких запусков):

| Полоса | Режимы | Что происходит | Время одной проверки |
|---|---|---|---|
| `light` | python, js, sql, func/stdout-задачи на питоне | старт контейнера + интерпретатор | **измерено: в среднем 0,35 с, максимум 0,63 с** (30 заданий, разработческая машина) |
| `heavy` | rust, c | компиляция (`rustc`, `gcc` с санитайзерами) | оценка 3–30 с; у Rust с крейтами (tokio, axum, sqlx) и PostgreSQL — больше |

Пропускная способность воркера ≈ число слотов / время одной проверки:

- `light`, 4 слота при 0,35 с → ≈ 11 проверок/с (≈ 680 в минуту);
- `heavy`, 2 слота при 15 с (оценка) → ≈ 8 проверок в минуту.

Самый опасный сценарий — не среднее, а **синхронный пик**: преподаватель просит класс из 30 человек нажать «Проверить»
на задаче по Rust. 30 заданий × 15 с / 2 слота ≈ 4 минуты ожидания у последнего. Поэтому масштабируется именно
`heavy`-полоса, и именно под неё нужны кэш и ограничения.

Рычаги, от дешёвых к дорогим:

1. **Кэш результатов** (есть, `exec_cache`): одинаковое решение одной версии задачи не выполняется повторно. Для типовых
   задач у многих учеников совпадают «пустая заготовка» и «эталон из учебника» — реальный выигрыш. Что кэшируется — раздел 5
   (в кэш идёт всё, что вернулось со `status == "ok"`, включая ошибки компиляции; таймаут всего контейнера, ошибки Docker — нет).
2. **Квоты и честность очереди**: одна проверка на пользователя (есть), потолок очереди 300 (есть); добавить приоритет
   «лёгкое впереди тяжёлого» (полосы уже разделены) и лимит `run` на IP/сутки.
3. **Горизонталь на воркерах**: воркер без состояния — добавить ещё одну VM/машину и `--light N --heavy M`; очередь
   в API общая. Это самый прямой путь масштабирования.
4. **Дешёвый запуск вместо контейнера на каждую проверку** (когда лёгкая полоса станет дорогой): пул заранее запущенных
   изолированных процессов (gVisor/Firecracker microVM/`nsjail`), переиспользование контейнера между проверками
   (одной задачи, одного пользователя) со сбросом `tmpfs`. Даёт ×5–10 по `light`, но сложнее и опаснее — изоляция
   между проверками должна быть доказана. Делать, когда измерения покажут, что это упёрлось.
5. **Предварительная компиляция**: для Rust/C с неизменным «каркасом» (драйвер задачи) кэшировать артефакты сборки
   зависимостей (у образа `say-rust-crates:1` уже собран `--extern`). Остаётся компиляция кода ученика.
6. **Исполнение SQL-задач без контейнера**: SQL-режим уже выполняется внутри SQLite `:memory:` — теоретически его можно
   проверять в процессе воркера (изоляцию даёт сам SQLite с запретом `ATTACH`, загрузки расширений и лимитом времени
   через `progress_handler`). Это убирает самый частый вид проверок из Docker. Пока не делаем: безопасность дороже выигрыша.

Безопасность тоже определяет архитектуру: код исполняется в контейнере **на отдельной VM с изолированной сетью**, API
с БД к нему доступа не имеет, воркер к БД тоже (подробнее — `docs/code-runner.md`).

## 3. SQLite или Postgres

### 3.1 Что и как мы пишем в БД

| Данные | Читаются | Пишутся | Размер/частота |
|---|---|---|---|
| Контент: книги, главы, уроки, слайд-метаданные, задачи (`tasks`), квизы | на каждый просмотр | только при сиде | ≈ 15 МБ, не растёт во время работы |
| Прогресс: `slide_views`, `quiz_picks`, `answer_solved`, `code_status` | на каждый заход | редко (раз в слайд/ответ) | строка на действие |
| Черновики кода (`code_drafts`) | при открытии задачи | **часто** — автосохранение | одна строка на (пользователь, задача), перезапись |
| Попытки (`code_attempts`) | история задачи | на каждую проверку | до 50 на задачу |
| Очередь (`exec_jobs`, `exec_cache`, `exec_workers`) | опрос воркеров и клиентов | на каждую проверку: постановка, аренда, продление, итог | десятки записей на проверку |

Читать приходится много, но читать **один** общий набор (контент) — он идеально кэшируется. Писать приходится мелкими
транзакциями; доминируют автосохранение черновиков и жизненный цикл заданий.

### 3.2 Узкое место ли SQLite

SQLite — **не** узкое место на ближайшем этапе, если выполнить два условия:

- включить `PRAGMA journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout` (сейчас режим `delete`: писатель блокирует
  читателей, а каждый запрос открывает новое соединение с `timeout=10` — на пике это дадут «database is locked»);
- держать один процесс-писатель на одну БД (или несколько процессов API, но короткие транзакции).

SQLite в WAL выдерживает порядка тысяч коротких записей в секунду с одним писателем. Наша запись — единицы–сотни в
секунду. Сама БД маленькая (18 МБ) и целиком живёт в кэше страниц ОС.

Где SQLite **начнёт мешать**:

1. **Больше одного сервера API** (HA, горизонтальное масштабирование): файл БД нельзя безопасно делить по сети (NFS и т. п.).
2. **Бэкапы и репликация онлайн**: у SQLite — `.backup`/Litestream, у Postgres — потоковая репликация и PITR «из коробки».
3. **Очередь заданий под нагрузкой**: сейчас захват задания — транзакция в SQLite; при сотнях заданий в секунду
   конкуренция воркеров и API за единственного писателя станет заметной. В Postgres захват делается `FOR UPDATE SKIP LOCKED`
   без блокировок между воркерами.
4. **Аналитика** по прогрессу (отчёты, когорты) — тяжёлые чтения будут конкурировать с записью.
5. **Миграции схемы без остановки**: в SQLite ограниченный `ALTER TABLE`.

### 3.3 Рекомендация

Двухступенчато, без спешки:

1. **Сейчас (до первых реальных пользователей):** остаёмся на SQLite, включаем WAL/`busy_timeout`, делаем ежедневный
   `sqlite3 .backup` (или Litestream в объектное хранилище). Один процесс API.
2. **Переезд на Postgres — по триггерам**, а не «на всякий случай»: нужен второй экземпляр API, или p95 записей > 50 мс,
   или появились ошибки «database is locked» в логах, или нужны онлайн-реплики/аналитика. К этому моменту:
   - Postgres держит данные пользователей и очередь (`SKIP LOCKED`), в том числе `LISTEN/NOTIFY` вместо опроса;
   - **Valkey** (по прошлому обсуждению) берёт то, что дёшево терять и часто читать: кэш прогресса пользователя,
     rate limit, статус воркеров; не нужен, пока одна машина;
   - контент (`books`, `chapters`, `lessons`, `tasks`, квизы) остаётся «сидируемым» — его можно хранить файлами/в Postgres и
     читать с локальным кэшем в процессе.

Что нужно подготовить заранее, чтобы переезд был недорогим:

- держать SQL в одном слое (сейчас `db()` в `books/service.py` + модули `accounts`, `exercises`, `quizzes`, `jobs`) и не
  размазывать диалектные особенности SQLite (`INSERT OR REPLACE`, `PRAGMA`, типы);
- у задач/квизов SQL-файлы инициализации (`backend/data/sql/*`) уже есть — их придётся сделать диалект-нейтральными или завести два набора;
- тесты бэкенда ходят во временную SQLite-базу (`SAY_DB`) — для Postgres понадобится тестовая БД (контейнер).

Вывод: «**Postgres лучше**» — да, но это инвестиция под рост до нескольких серверов и под HA, а не лекарство от текущей
нагрузки. Раньше, чем нужны эти свойства, он добавляет работу (операции, бэкапы, пул соединений) без заметной выгоды.

## 4. Нужна ли очередь

**Да, очередь нужна, и она уже есть.** Причины:

- **Выравнивание пиков.** Проверка занимает секунды, а нажимают одновременно; без очереди либо отказываем, либо запускаем
  десятки контейнеров сразу и перегружаем машину.
- **Отделение API от выполнения.** API на VPS, воркер дома: API ничего не знает о Docker, воркеру не нужна БД.
- **Обратное давление.** Потолок очереди (300) и «одна проверка на пользователя» не дают одному человеку занять всех.
- **Устойчивость.** Воркер упал — задание по истечении аренды вернётся в очередь (две попытки), пользователь увидит ошибку, а не вечную загрузку.
- **Разные полосы.** Тяжёлая компиляция не блокирует быстрые проверки.

Как устроена очередь сегодня — таблица `exec_jobs` в SQLite, воркеры забирают задания длинным опросом (`/internal/worker/*`).
Это правильный выбор на старте: без нового компонента в инфраструктуре, видна в обычном SQL, переживает перезапуск API.

Альтернативы и когда о них думать:

| Вариант | Плюсы | Минусы | Когда |
|---|---|---|---|
| Таблица в БД (сейчас) | ничего нового, транзакционность вместе с попытками/статусами | захват = запись; опрос; один писатель | до ~десятков заданий/с |
| Postgres + `SKIP LOCKED` + `LISTEN/NOTIFY` | то же, но без блокировок между воркерами, мгновенная выдача | нужен Postgres | вместе с переездом на Postgres |
| Valkey (Redis) Streams / списки | быстро, есть группы потребителей | вторая система правды, надо согласовывать с БД; потеря при сбое без AOF | если очередь станет сотнями заданий/с |
| RabbitMQ/NATS | зрелые очереди, приоритеты, DLQ | ещё один сервис, воркер за NAT нужно подключать к брокеру (против нашей схемы «воркер сам ходит по HTTPS») | не нужно: у нас схема «воркер тянет по HTTPS» |

Модель «воркер сам приходит за заданием» (pull) осознанно выбрана: дом за NAT, ни одного входящего порта, при компрометации
воркера у злоумышленника нет доступа к БД и нет маршрута в домашнюю сеть.

## 5. Результат проверки зависит только от присланного кода?

Да, **почти**. Сформулируем точно: результат проверки — это функция

```
result = f(версия задачи [spec], код ученика, версия окружения [образ + лимиты])
```

и не зависит от того, **кто** прислал. Попытка и статус «решено» записываются отдельно для пользователя, а вычисление — общее.
Поэтому кэш по `sha256(spec_hash \0 code)` корректен, и именно это даёт общий кэш для всех.

Где «почти» — это важно для правильности кэша:

1. **Версия окружения не входит в ключ.** Ключ учитывает определение задачи, но не образ: обновили `rust:1.97-slim` /
   `python:3.13-slim` / `gcc` — старые результаты в кэше остаются. TTL 7 дней смягчает, но правильнее добавить в ключ
   «версию раннера» (digest образа или константу `RUNNER_VERSION`), либо чистить кэш при выкладке. **[сделать]**
2. **Недетерминированный код.** `random`, `time`, порядок итерации `set`/`dict` с рандомизацией хеша строк, потоки, `sleep`
   в тестах Tokio, зависимость от `/proc`, архитектуры (x86_64/aarch64 — мы это уже ловили в задачах Linux). Результат такого
   кода на повторном запуске может отличаться, а кэш закрепит **первый**. Для обычного ученического кода это редкость, для задач
   на параллелизм/время — риск; такие задачи должны быть написаны детерминированно (так мы и делаем: драйвер печатает только
   стабильное).
3. **Зависимость от загрузки машины.** Тесты эффективности используют лимит 25 с/память: решение, которое «еле успевает», на
   занятой машине упадёт по таймауту, на свободной пройдёт. **Таймауты, нехватку памяти и ошибки инфраструктуры нельзя
   кэшировать.** Что сейчас (проверено по `runner.py` и `jobs.py`): кэшируется результат со `status == "ok"`; таймаут всего контейнера
   (`status: "timeout"`) и ошибки Docker в кэш не попадают — это правильно. **Но** для `rust`/`c`/`js` таймаут и OOM *самой программы*
   (`timeout 10` внутри контейнера, код выхода 124, убийство по памяти — 137) возвращаются как `status: "ok"` с проваленным результатом
   («Программа завершилась с кодом 124») — значит, **они кэшируются на 7 дней**. На загруженной машине один неудачный запуск закрепится
   для всех, кто пришлёт тот же код. Нужно не класть в кэш результаты с кодами 124/137/143. **[сделать]**
   И «ok»-результат у граничного решения может быть случайным; для таких задач нужен запас по лимиту (мы так и делаем:
   наивное решение должно падать с большим запасом).
4. **Ошибки компиляции уже кэшируются** (для `rust`/`c` они приходят как `status: "ok"` с `ok: false` и текстом «Ошибка компиляции»).
   Это безопасно и выгодно: компилятор детерминирован, а ученик часто присылает одно и то же. Для Python/JS синтаксические ошибки —
   то же самое.
5. **Побочные каналы.** Мгновенный ответ из кэша выдаёт, что точно такой код уже присылали раньше. Утечка мала (мы не показываем
   чужие решения), но её стоит помнить, если когда-нибудь появятся соревнования или антиплагиат. И наоборот — совпадающие
   хеши решений дают дешёвый сигнал для антиплагиата.
6. **Вывод проверки не должен раскрывать скрытые тесты.** Раз результат общий и логи видны, в `stdout`/`stderr` не должно быть
   ожидаемых значений скрытых тестов; в задачах с драйвером ожидание обычно печатается в сравнении — это сознательное решение
   для обучения; для «экзаменов» следует отдельно решать, что показывать.
7. **Лаборатории режима `lab`** (книги 14, 15, 17, 18) вообще не проходят через песочницу: проверка идёт в браузере, а сервер
   принимает «решено» на веру (`PUT .../solved`). Это нормально для учебного прогресса, но решение не доказано; если когда-нибудь
   понадобятся достоверные результаты (сертификаты, соревнования), движок проверок надо перенести на сервер (он на чистом TS —
   можно исполнять в Node воркером) или проверять решение повторно на бэкенде.

Итого: ваше утверждение верно в части «не зависит от пользователя» — это и есть основание для общего кэша; к ключу стоит добавить
версию окружения и не кэшировать нестабильные исходы (таймаут/OOM самой программы).

## 6. Безопасность перед публичным запуском

Все пункты — из `docs/code-runner.md` и прошлых обсуждений, сведены сюда как чек-лист:

- [ ] HTTPS (nginx/Caddy), cookie `secure`, `SameSite`, заголовки безопасности;
- [ ] лимиты на регистрацию, вход и `POST /run` по IP (иначе открытая регистрация обходит лимит «одна проверка на пользователя»);
- [ ] убрать временных пользователей `student/programmer` и `DEFAULT_USERS`;
- [ ] квоты на размер кода и черновиков, на число попыток;
- [ ] WAL и бэкапы БД (раздел 3);
- [ ] воркер: отдельная VM, исходящий трафик только к API, снимок для отката, gVisor как следующий шаг;
- [ ] журналирование и метрики: длина очереди, время ожидания, время выполнения по полосам, доля кэша, число контейнеров,
      отказы воркеров, коды ответов API;
- [ ] алерты: очередь > N, нет живых воркеров, диск воркера, свободная память.

## 7. Варианты размещения

### Вариант A — «всё на одной машине, только docker-compose» — **ВЫБРАНО для первого запуска** (этап 1)

На машине установлен только Docker с compose-плагином. Всё остальное — контейнеры. Тот же compose-файл подходит и для проверки
дома, и для небольшого VPS. Это сознательно «простой старт»: мало движущихся частей, всё воспроизводимо одной командой, а
потом переносится по частям (воркер → другая машина, SQLite → Postgres).

#### Состав сервисов

| Сервис | Образ | Что делает | Сети |
|---|---|---|---|
| `proxy` | Caddy (или nginx) | HTTPS (автосертификат), раздаёт собранный фронтенд, `/api` → `api:8000`, gzip/brotli, лимиты по IP | `front` |
| `api` | свой образ: Python + `uv` + код `backend/` | FastAPI; `SAY_RUNNER=remote` (см. ниже), том `data` с `say.db` | `front`, `back` |
| `worker` | свой образ: Python + `docker` CLI + `backend/worker.py` и `app/exercises` | забирает задания у `api` по HTTP (`http://api:8000`), запускает песочницы в `dind` | `back`, `sandbox` |
| `dind` | `docker:dind` | **отдельный Docker-демон только для песочниц**; образы `python:3.13-slim`, `rust:1.97-slim`, `node:22-alpine`, `say-rust-crates:1` лежат в его томе | `sandbox` |
| `web-build` (разовый) | `node:22` | `npm ci && npm run build` → том со статикой для `proxy` (multi-stage сборка проще: статика копируется в образ `proxy`) | — |
| `backup` (по расписанию) | образ с `sqlite3` | `sqlite3 say.db ".backup …"` раз в сутки, копия в том/внешнее хранилище | `back` |

Сети: `front` (интернет → `proxy` → `api`), `back` (`api` ↔ `worker`), `sandbox` (`worker` ↔ `dind`). Контейнеры песочниц запускаются
с `--network none`, и вообще не видят ни одну из этих сетей.

#### Почему воркер — отдельный сервис, а не `SAY_RUNNER=local` внутри `api`

- `local`-режим запускает Docker из процесса API: тогда в контейнере API нужен доступ к Docker-демону, а значит, компрометация API =
  доступ к демону. Отдельный `worker` ограничивает этот доступ одним контейнером без БД и без публичной сети.
- Это **ровно та же схема**, что и целевая: потом `worker` переезжает на другую машину, меняется только `--server https://…`.
- Воркер использует тот же `runner.py` и `worker.py` (в образе воркера лежит `backend/app/exercises`, но не база).

#### Главная техническая сложность: Docker внутри compose

Песочницы запускает `runner.py` командой `docker run …` и **монтирует каталог с кодом ученика** (`-v {tmpdir}:/sandbox:ro`).
Из контейнера `worker` есть три способа добраться до Docker:

| Способ | Плюсы | Минусы |
|---|---|---|
| Смонтировать `/var/run/docker.sock` хоста | просто, образы уже есть, нет вложенности | **песочницы — соседи на хосте**; сокет = root на хосте; ошибка в воркере или побег из контейнера = полный захват машины. Не рекомендуется для пользовательского кода |
| `docker-socket-proxy` перед сокетом (разрешает только `containers create/start/rm`, `images`) | уже лучше сокета | всё равно демон хоста; `docker run --cap-add` и монтирования нужно разрешать — прокси мало что ограничит |
| **`docker:dind` (privileged) отдельным сервисом** — рекомендую | свой демон, свои образы и сети; `rm -f` по префиксу не заденет хост; можно жёстко лимитировать cgroup'ом (`cpus`, `mem_limit`) всё сразу; потом заменяется на другую машину | `privileged` контейнер сам по себе — риск побега ядра (изолируем сетью и отсутствием томов с данными; следующий шаг — gVisor/sysbox, раздел 2.2); образы нужно один раз залить в том `dind` |

Выбор по умолчанию — **dind**. Нужны две вещи:

1. **Общий каталог для песочниц.** Каталог с кодом создаётся в контейнере `worker`, а `docker run -v` разворачивается на стороне демона
   `dind`. Поэтому нужен общий том, смонтированный по **одному и тому же пути** в `worker` и `dind` (например `/sandboxes`), и
   `TMPDIR=/sandboxes` у воркера (`tempfile` берёт его). Без этого bind-mount увидит пустую директорию.
2. **`DOCKER_HOST=tcp://dind:2375`** у воркера (сеть `sandbox` недоступна снаружи, TLS можно опустить, но держать порт закрытым).

#### Лимиты, чтобы код учеников не ронял сайт

На одной машине код учеников и API делят CPU/память/диск, поэтому:

- у `dind` — `cpus` и `mem_limit` (например 60–70% машины): это потолок суммарной нагрузки **всех** песочниц; API и `proxy` остаются живыми, даже если всё сожрали;
- у `api` — свой `mem_limit`, у `worker` — небольшой; `restart: unless-stopped` у всех;
- слоты воркера соответствуют ядрам: `--light` и `--heavy` не больше числа ядер у `dind` (см. раздел 2.2);
- диск: том `dind` ограничить (отдельный раздел/квота) — переполнение слоёв и логов Docker не должно остановить БД;
- свап лучше выключить: OOM-killer быстрее и предсказуемее, чем «залипший» сервер;
- логи контейнеров — `json-file` с `max-size`.

#### Подготовка образов (разово)

Образы песочниц нужны внутри `dind`, а не на хосте: сервис `init` (или `docker compose run`) делает `docker pull`/`docker build -t say-rust-crates:1 …` с
`DOCKER_HOST=tcp://dind:2375`. Том `dind-data` сохраняет их между перезапусками. `rust` с крейтами собирается долго (скачивание tokio/axum/sqlx и сборка) —
делать заранее, не при первой проверке.

#### Данные

- `say.db` лежит в томе `data` (только `api` пишет; `worker` базы не видит); бэкап — сервис `backup` и ежедневная копия вне машины;
- пользовательские данные — только в этом томе, контент пересоздаётся сидером: `docker compose run --rm api uv run seed_textbook.py --no-audio`;
- до включения публичной регистрации — WAL/`busy_timeout` (раздел 3) и лимиты (раздел 6).

#### Что было доделано в репозитории (этап 1) — сделано 2026-10-22, файлы в `deploy/`

1. `Dockerfile` для `api` (multi-stage: `uv sync`, копия `backend/`), `Dockerfile` для `worker` (Python + docker CLI), `Dockerfile`/`Caddyfile` для `proxy` со сборкой фронтенда.
2. `docker-compose.yml` со всем выше (сети, тома, лимиты, healthcheck, `depends_on`).
3. Скрипт `init` для заливки образов песочниц в `dind`.
4. Переменные окружения: `SAY_DB`, `SAY_RUNNER=remote`, `SAY_WORKER_TOKEN` (из секрета), `DOCKER_HOST`, `TMPDIR` — в `.env`/`secrets`, не в git.
5. Проверка конца в конец: сид, вход, проверка кода python/js/sql/c/rust, остановка воркера → корректное «проверка временно недоступна», перезапуск контейнеров → данные на месте.
6. Замеры времени проверки на этой машине (раздел 9, п. 1) — они определяют `--light/--heavy`.

#### Чем этот вариант хуже целевого

- Код учеников и БД на одной физической машине: изоляция держится на `dind` и сетях, а не на отдельной VM. Для закрытой группы пользователей это приемлемо; перед
  открытой регистрацией — gVisor/sysbox или перенос воркера (этап 2).
- Нет запаса мощности: пик проверок отнимает ядра у API (смягчается лимитами у `dind`).
- Одна точка отказа: упала машина — упало всё. Бэкапы и быстрое восстановление из `docker compose up` важнее, чем «высокая доступность» на этом этапе.

#### Переход на этап 2

Когда измерения покажут, что `heavy`-полоса или CPU упираются, или перед открытием регистрации: поднять `worker`+`dind` на другой машине (VM), в `api`
оставить `SAY_RUNNER=remote`, у воркера поменять `--server` на публичный HTTPS-адрес API. Остальное не меняется — поэтому воркер сразу отдельный сервис.

### Вариант B — «API на VPS, воркер дома» (целевой, этап 2)
VPS: nginx + uvicorn (1–2 процесса) + SQLite (WAL) или Postgres + статика фронтенда. Дом: VM с Docker и воркером
(`SAY_RUNNER=remote`). Минимум движущихся частей, пользовательский код изолирован на отдельной сети/VM. Узкое место — домашний
канал и мощность сервера; даёт запас по `heavy`-полосе.

### Вариант C — рост
Несколько воркеров (дом + арендованные «dedicated»-машины под компиляцию), Postgres + Valkey, два экземпляра API за балансировщиком,
CDN для статики/wav, отдельный пул `heavy`. Переходим по триггерам из раздела 3.3 и по метрикам очереди.

## 8. Решения (зафиксировано)

- Язык/фреймворк бэкенда не меняем: FastAPI остаётся.
- **Первый запуск — всё на одной машине, на которой есть только `docker-compose`** (вариант A, этап 1). Целевая схема с отдельной VM — этап 2.
- Воркер — отдельный compose-сервис (`worker.py`, `SAY_RUNNER=remote`) с **собственным Docker-демоном `dind`** для песочниц; сокет хоста в контейнеры не монтируем.
- Выполнение кода — в Docker, очередь — в БД, воркер забирает задания сам (pull) — это не меняется между этапами.
- Результаты проверки кэшируем по `(версия задачи, код)`; результат не зависит от пользователя.
- Ближайший шаг по БД — WAL + `busy_timeout` + бэкапы, не переезд.
