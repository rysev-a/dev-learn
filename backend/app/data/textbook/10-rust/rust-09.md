#SECTION Язык глубже
#CHAPTER 9 | Модули, тесты и карго
Изучаем Раст. Глава 9. Модули, тесты и карго. До сих пор мы писали небольшие программы в одном файле. Настоящий проект состоит из десятков и сотен файлов, подключает чужие библиотеки, покрыт тестами и собирается одной командой. Сегодня мы разберём, как Раст организует код: пакеты, крейты и модули, видимость имён, пути и подключение, раскладку по файлам. Узнаем, что хранится в манифесте карго и какие команды нужны каждый день. Научимся писать модульные и интеграционные тесты, документацию, которая сама превращается в тесты, и несколько идиом для библиотек: сборщики, преобразования из строки и значения по умолчанию.\n\nНачнём с терминов. Крейт — это единица компиляции: либо исполняемая программа, либо библиотека. Пакет — это один или несколько крейтов с общим файлом манифеста; именно им управляет карго. Модуль — единица организации кода внутри крейта: у него своё пространство имён, а вложенные модули образуют дерево. Корень дерева — главный файл крейта: «мейн-рс» для программы или «либ-рс» для библиотеки. Всё остальное подключается из него объявлением «мод». Такая трёхуровневая схема позволяет и держать код аккуратным, и открывать наружу только то, что действительно нужно.\n\nПо умолчанию всё внутри модуля приватно: снаружи не видны ни функции, ни структуры, ни поля. Чтобы что-то открыть, перед ним ставится слово «паб». Структура может быть публичной, а её поля — приватными, и тогда создать её можно только через публичную функцию внутри модуля. Это основа инкапсуляции: банковский счёт с приватным балансом, который меняется лишь методами, проверяющими правила. Есть и промежуточные уровни, например видимость в пределах крейта, когда нужно показать имя соседним модулям, но не внешним пользователям библиотеки.\n\nЧтобы не писать длинные пути каждый раз, их подключают ключевым словом «юз». Путь может быть абсолютным от корня крейта, относительным от текущего модуля или идти вверх через слово «супер», родительский модуль. Слово «ас» задаёт псевдоним, когда два имени конфликтуют, а фигурные скобки позволяют подключить несколько имён из одного места. Особая конструкция «паб юз» делает реэкспорт: библиотека может держать внутри сложную структуру модулей, а пользователям предложить короткий и красивый путь к главным типам.\n\nМодули можно писать прямо в файле в фигурных скобках, но обычно каждый модуль живёт в своём файле. Объявление «мод» с точкой с запятой говорит компилятору найти модуль в файле с тем же именем рядом или в одноимённой папке с файлом «мод-рс» внутри. Вложенные модули выкладываются в подпапки. Эта раскладка полностью определяется структурой дерева модулей, а не наоборот: сначала вы объявляете модуль в коде, а потом файл подтягивается. Забытое объявление «мод» — частая ошибка новичков: файл существует, но компилятор о нём не знает.\n\nМанифест карго называется «карго-томл». В нём имя пакета, версия, издание языка и список зависимостей с версиями. Версии записываются по соглашению семантического версионирования, и по умолчанию карго берёт совместимые обновления. Дополнительные секции описывают профили сборки, например оптимизации для релиза, и необязательные возможности, которые включаются флагами. Ежедневные команды короткие: «карго ран» собирает и запускает, «карго билд» только собирает, «карго чек» быстро проверяет типы без генерации кода, «карго тест» запускает тесты, «карго фмт» форматирует, «карго клиппи» подсказывает улучшения. Файл блокировки фиксирует точные версии, чтобы сборка была воспроизводимой.\n\nТесты в Расте живут рядом с кодом. Функция помечается атрибутом «тест», внутри вызываются макросы проверок: равенство, неравенство, истинность. Обычно в конце файла создают модуль «тестс» с атрибутом условной компиляции, чтобы тестовый код не попадал в рабочую сборку, и подключают в него всё из родительского модуля. Команда запуска собирает отдельный исполняемый файл, прогоняет все тесты параллельно и печатает список с результатами. Если проверка не выполнилась, тест падает с сообщением, где показаны обе стороны сравнения, и это сильно ускоряет поиск ошибки.\n\nВидов тестов несколько. Модульные тесты проверяют отдельные функции, в том числе приватные, потому что находятся внутри того же модуля. Тест, который обязан завершиться паникой, помечается дополнительным атрибутом с ожидаемым сообщением. Тест может возвращать резалт, и тогда вопросительный знак работает прямо внутри него. Интеграционные тесты лежат в папке «тестс» рядом с «срс» и используют библиотеку как внешний пользователь, видя только публичный интерфейс. А примеры в документации тоже выполняются как тесты, так что устаревший пример сразу ломает сборку проверок.\n\nДокументация пишется тройным слэшем над элементом и поддерживает разметку маркдаун. Двойной слэш с восклицательным знаком описывает сам модуль или крейт. Команда «карго док» собирает из этого сайт, а блоки кода внутри комментариев запускаются как тесты. Над элементами ставят и другие атрибуты: «дерайв» для автоматической реализации трейтов, «аллоу» для отключения предупреждений, «инлайн» как подсказку оптимизатору, «сфг» для условной компиляции под платформу или режим. Макрос «сфг» возвращает значение времени компиляции, например разрядность платформы, и условия вычисляются без накладных расходов.\n\nБиблиотеку и программу обычно разделяют: логика живёт в «либ-рс» и проверяется тестами, а «мейн-рс» тонкий и только разбирает аргументы, вызывает библиотеку и обрабатывает итог. Главная функция может возвращать резалт, тогда ошибка из неё печатается и процесс завершается с ненулевым кодом. Для ошибок разных типов удобна коробка с динамическим трейтом ошибки: оператор вопросительный знак превращает любую ошибку в неё автоматически. В библиотеках лучше описывать собственный тип ошибок, а коробку оставлять для приложения, где важна простота, а не точная классификация.\n\nЕсть несколько идиом, без которых не обходится ни одна библиотека. Значения по умолчанию задаёт трейт «дефолт», и вместе с синтаксисом обновления структуры позволяет создавать конфигурации, меняя только нужные поля. Паттерн «строитель» собирает сложный объект цепочкой методов. Трейт «фром-стр» учит тип разбирать себя из строки, после чего работает метод «парс» с указанием типа. А трейты «фром» и «инто» описывают безопасные преобразования между типами: реализуете одно, второе получаете даром. Все эти приёмы делают API предсказуемым, потому что пользователь встречает знакомые слова из стандартной библиотеки.\n\nНа уровне модуля можно объявлять константы и статические значения. Константа подставляется в место использования, у неё нет адреса, а тип обязательно указывается явно. Статическая переменная живёт всю программу по одному адресу; изменяемую статику без «небезопасного» не тронуть, поэтому общие счётчики делают атомарными. Когда проект растёт, несколько пакетов объединяют в рабочее пространство с общим файлом блокировки и общей папкой сборки. Инструменты вроде форматера и линтера включают в процесс разработки с первого дня, и код всех участников выглядит одинаково.\n\nПодведём итоги. Крейт — единица компиляции, пакет — набор крейтов с манифестом, модуль — пространство имён внутри крейта. Всё приватно по умолчанию, а «паб» открывает наружу, «юз» подключает, «паб юз» реэкспортирует. Карго собирает, запускает, проверяет, форматирует и тестирует, а манифест описывает зависимости и профили. Тесты бывают модульные, интеграционные и документационные, и все они запускаются одной командой. Библиотеку отделяют от тонкой программы, а API делают привычным с помощью дефолта, строителя, фром-стр и фром. В следующей главе мы займёмся многопоточностью и общим состоянием.
