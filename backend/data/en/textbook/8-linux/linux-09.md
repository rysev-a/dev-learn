#CHAPTER 9 | Memory: Pages, Zones and the Address Space
Diving into Unix. Chapter 9. Memory: pages, zones and the address space. When a program asks the system for memory, it does not get RAM directly, it gets a promise. Between the word "allocate" and the actual chips lies a whole floor of the kernel: it divides memory into pages, hands them out by rules, builds each process its own virtual address space, and when memory runs short it pushes the excess out to disk or, as a last resort, kills a process. In this chapter we will walk this path, building on what you already know about virtual memory from the architecture book.\n\nLet's start with the unit of accounting. The kernel divides physical memory into pages of four kilobytes, and all decisions are made in these pieces. For every page there is a record: whose it is, how many references point to it, whether it is free, whether it is in a file cache. This record used to be called simply a page. Now the kernel increasingly works with folios: a folio is one page or a group of adjacent ones managed as a single unit. That makes it simpler to cache files in big chunks and to spend less time on bookkeeping.\n\nNot all memory is the same. Some devices can only reach low addresses, so the kernel divides memory into zones. The lowest one is for ancient devices, then there is a zone for devices with thirty-two-bit addresses, and finally the normal zone, where almost everything lives. On machines with several processor sockets there is also a division into nodes: each socket has its own fast memory, and someone else's is slower. When allocating a page, the kernel tries to take it from the nearest node and a suitable zone. You can watch this in the file proc zoneinfo.\n\nHow does the kernel hand out pages? With an algorithm called the buddy system. Free memory is kept in blocks of two to the power of the order pages: one, two, four, and so on up to one thousand twenty-four. You need a block of eight pages, but only a block of sixteen is free? The kernel splits it into two buddies of eight, gives one away and keeps the other. When blocks are freed, buddies are merged back together if both are free. This is how the kernel fights fragmentation and quickly finds large contiguous pieces.\n\nBut the kernel often needs small objects: a task descriptor, an inode, a directory entry. Allocating a whole page for each would be wasteful. So on top of the buddy system works the slab allocator. It receives pages and cuts them into identical cells for a specific object type, keeps lists of free and used cells, and hands out a cell within a few cycles. General-purpose allocation, kmalloc, is also built on a set of such caches of different sizes. Of the earlier implementations, one is left in the kernel, SLUB, and the others were removed. The statistics are shown by the slabtop utility.\n\nNow the address space of a process. Every process has its own set of virtual addresses, and the kernel describes it as a list of regions: program code, data, heap, stack, mapped files and libraries. Each region has boundaries and permissions, and they are all kept in a special tree, which in version six point one replaced the red-black tree. You can look at the regions in the file proc, process number, maps. The addresses are random every time, so that it is harder for an attacker to guess what lies where. This is called randomization.\n\nThe key point: when a program calls malloc and gets a pointer, there is no physical memory yet. The kernel merely records a region. The page appears later, on first access: the processor will not find it in the table, and a page fault occurs. The kernel will see that the region is legitimate, find a free frame, zero it, put it into the table and repeat the instruction. This is lazily allocated memory. If the page is already in the file cache, the fault is called minor, and if it has to be read from disk, major, and then the delay is noticeable.\n\nEvery memory access requires translating a virtual address into a physical one. In page tables there are four levels, and on new processors five, and nine bits of the address select an entry at each level. To avoid walking the tables on every access, the processor keeps a cache of translations, the TLB. A miss in it noticeably slows a program down. That is why huge pages of two megabytes are used for large regions: one entry in the cache covers five hundred twelve times more. The kernel can do this transparently, but databases sometimes turn it off.\n\nWhat happens when free memory is about to run out? The reclaim thread wakes up. It looks for pages that have not been touched for a long time and evicts them: clean file caches it simply throws away, and modified anonymous pages it writes to swap. The kernel keeps pages by age. The classic active and inactive lists were supplemented by a multi-generational algorithm, MGLRU, which appeared in version six point one and is enabled in many distributions: pages are grouped into generations, and the oldest go first. Swap can be kept on disk or in compressed memory.\n\nAnd what if there is nothing left to free? Then the out-of-memory killer kicks in. It scores every process: the more memory it holds, the higher the score, and the oom score adjust tunable lets you protect something important. The winner gets a kill signal. To keep this from happening to the whole machine, memory is limited by groups: a control group has a limit, and when it is exceeded, a process is killed inside the group. And daemons like systemd-oomd watch memory pressure ahead of time and terminate the offenders before everything suffocates.
