#CHAPTER 16 | I/O: Non-Blocking Mode, epoll, io_uring, and Terminals
Diving into Unix. Chapter sixteen. I/O: non-blocking mode, epoll, io uring, and terminals. A server accepts thousands of connections, and almost all of them are silent. If you start a thread for each one, memory and the scheduler will not hold out. If you read them one by one with a blocking call, a single quiet client stops everybody. That is why Unix has worked out four approaches: a thread per connection, non-blocking I/O, multiplexing, and asynchronous operations. This chapter shows how the kernel helps us wait on many descriptors at once, and along the way explains how the terminal we started this book with actually works.\n\nLet us begin with non-blocking mode. The O-nonblock flag on a descriptor changes the behavior: if there is no data, the read call does not go to sleep, it immediately returns the error EAGAIN. That is not a failure, it is a message that says come back later. This lets you walk over many descriptors in a loop, but you must not spin such a loop idly: the processor would be busy doing nothing. We need a way to sleep until something happens on at least one descriptor. For that the kernel provides multiplexing calls, and the oldest of them are select and poll.\n\nSelect takes a set of descriptors as a bit mask and waits until one of them becomes ready. It has two drawbacks: the largest descriptor number is limited to one thousand twenty-four, and the masks have to be filled in again on every call. Poll fixes the first problem: you pass an array of structures, where each descriptor has the events you care about, and there is no limit. But both calls copy the whole list into the kernel on every invocation and scan it from start to finish. With ten thousand descriptors, of which two are ready, the work is wasted.\n\nEpoll is built differently. You create a kernel object, add descriptors to it once with the epoll ctl call, and then call epoll wait. The kernel keeps the interest list in a red-black tree, and when something happens on a descriptor, it moves that descriptor to a ready list. The wait call returns only the ready descriptors, so the cost depends on the number of events, not on the number of connections. That is exactly why a single thread can serve hundreds of thousands of sockets. Other systems have counterparts: kqueue on BSD and completion ports on Windows.\n\nEpoll has two notification modes. Level-triggered mode reports readiness as long as data remains in the buffer, so you can read part of it and come back. Edge-triggered mode, the EPOLLET flag, reports only a change of state: new data has arrived. Then you must read until you get EAGAIN, or the remainder is lost for good. The one-shot flag disables a descriptor after a single event, so that only one thread handles it. If several threads wait on the same socket, all of them wake up, and this is called the thundering herd; the exclusive flag wakes only one.\n\nThere is an important caveat. Readiness is not the completion of an operation, it is a promise that the call will not block. For sockets and pipes this works. For ordinary files on disk, epoll always says ready, and yet a read may still sleep until the disk answers. That is why servers move disk operations into a thread pool. Another way is asynchronous operations: you put a request in a queue and keep working, and the kernel tells you when it is finished. The old AIO interface was limited and awkward, and that is what led to a new one.\n\nThe new interface is called io uring, and it appeared in version five point one. The application and the kernel share two rings in common memory. Into the submission ring the program puts entries: read, write, accept a connection. Into the completion ring the kernel puts the results. Dozens of operations can be submitted with a single system call, and in polling mode the kernel picks up entries by itself, so there are no calls at all. There are fixed buffers and linked chains of operations. Io uring works with files and with sockets, and we come back to the idea from the chapter on system calls: the fewer transitions, the faster.\n\nNow let us return to the terminal. It is not just a window: behind it stands a device driver with a line discipline. In canonical mode it collects a line, handles backspace and echo, and gives the program the whole line after you press Enter. It turns special characters into signals: Control-C sends the interrupt signal, Control-Z sends stop, and Control-D means end of file. Editors and pagers switch the terminal into raw mode and read every key themselves. Everything is configured with the termios structure and the tcsetattr call.\n\nA modern terminal is virtual. A pseudoterminal is a pair: the master end, driven by an emulator or an SSH server, and the slave end, which looks to the program like a real terminal. SSH, tmux, and terminal windows are all built exactly this way. Processes are gathered into groups, and groups into sessions. A session has a controlling terminal, and one group is its foreground group: it is the one that receives keyboard signals. The background command moves a group to the background, and when the terminal is closed, the session receives the hangup signal. That is where nohup comes from, and daemons that call setsid and detach from the terminal.\n\nLet us sum up. Blocking I/O is the simplest, but one thread per connection lasts only for a while. Non-blocking mode plus epoll gives you an event loop: one thread waits for everyone and handles whatever is ready. Io uring removes extra system calls and suits files as well. The typical traps are partial writes that you have to finish, calls interrupted with the EINTR error, forgetting to read until EAGAIN in edge-triggered mode, and a blocking call inside the event loop. Now you know how a program waits, how the terminal talks to it, and how the whole system works.
