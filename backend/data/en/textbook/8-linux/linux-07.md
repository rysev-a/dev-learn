#CHAPTER 7 | Interrupts, deferred work, and time
Diving into Unix. Chapter 7. Interrupts, deferred work, and time. The processor runs a program step by step, but the world around it doesn't wait: a network packet arrives, a key is pressed, a disk read finishes, a timer ticks. If the processor kept polling all the devices, that's all it would ever do. So the device signals by itself, and the processor drops what it's doing to serve it. That's an interrupt. In this chapter we'll see how the kernel copes with them, how it postpones long work, and how it keeps track of time.\n\nFirst, a classification, familiar from the architecture book. Hardware interrupts come from devices asynchronously, at any moment. Exceptions arise inside the processor itself, in the middle of an instruction: division by zero, access to someone else's memory, a page fault. Those are synchronous events. And finally, a system call is also an entry into the kernel, but at the program's own will. For all three, the processor looks into a vector table, where the address of the handler is stored by number, and the kernel fills in these addresses itself at boot.\n\nNow the most important rule: an interrupt handler must be fast. While it runs, the device waits, and on this core some events are muted. So the work is split in two. The top half runs immediately: it acknowledges the interrupt to the device, grabs the most urgent data, and postpones the rest. The bottom half runs later, when interrupts are enabled again, and it may take a long time. Take a network card: the top half merely notes that packets have arrived, and parsing headers and protocols happens afterwards. The interrupt counters are visible in the file proc interrupts.\n\nThe kernel has several mechanisms for deferred work, and the fastest is called softirq. It's a fixed set of ten software interrupts: timers, network receive and transmit, block devices, the scheduler, data updates, and others. A softirq runs on the way out of an interrupt handler and executes with interrupts enabled, but it cannot sleep. If there's too much work, the kernel hands the remainder to a special per-core thread called ksoftirqd. You can see it in the top utility as the column labeled S-I.\n\nTasklets used to live on top of softirqs, and many drivers used them as a convenient wrapper. But they accumulated drawbacks: they are hard to cancel and wait for, and a bug in them can lead to touching memory that's already been freed. So tasklets were declared deprecated, and in kernel version 6.9 a replacement was added: bottom halves on workqueues. They run in the same context as tasklets but have a proper interface. Drivers are being moved over one by one, and in time there won't be any tasklets left in the kernel.\n\nWhat if deferred work needs to sleep, for example to wait for a disk or take a sleeping lock? You can't sleep in interrupt context. That's what workqueues are for: the kernel keeps a pool of worker threads, called kworkers, which take jobs from a queue. The work runs in ordinary process context, so it can sleep, allocate memory with waiting, and access files. The rule of thumb is simple: if you need speed and don't need to sleep, use a softirq or its replacement; if you need to sleep, use a workqueue; and there's one more option, making the second half a thread of its own.\n\nThat kind of thread is called a threaded interrupt. The driver registers its handler in two parts: a short function in interrupt context just checks and wakes the thread, and all the serious work happens in a kernel thread, which the scheduler handles like any ordinary task. The advantage is that interrupt latency can be bounded, and the thread can be given a priority. That's exactly why real-time mode forces interrupts to be threaded. Networking has its own trick too, NAPI: under a heavy stream of packets, the kernel turns interrupts off and polls the card in batches.\n\nNow, time. The kernel counts it in ticks: a timer interrupts the processor a few hundred times a second, usually two hundred fifty or a thousand, and each tick increments the jiffies counter. On a tick, the scheduler checks whether it's time to switch tasks, and the kernel updates statistics. But a tick wakes the processor even when it's idle and drains the battery. So there's a tickless mode: on idle cores the timer is switched off altogether, and on cores running just one task it can be switched off completely. Precise time comes from the processor's counter, not from ticks.\n\nTimers live in two worlds. Ordinary kernel timers are for timeouts: the connection didn't answer, so give up. They're coarse, they live in a hierarchical wheel, and they're almost always cancelled before they expire, so they must be cheap. High-resolution timers are for when precision matters: sleep exactly one hundred microseconds, not "around that". They're kept in a tree ordered by time, and the processor is programmed precisely for the nearest event. From a user program, you see both worlds through the sleep calls and timer descriptors.\n\nWhat do you do with all this in practice? If networking is bottlenecked on one core, look at where the interrupts are directed: the smp affinity file in the proc directory lets you pin each device to its own core, and the irqbalance service does it automatically. If top shows a lot of time in softirq, the load comes from the network or the block layer. To check latency in real-time mode, people use the cyclictest utility: it repeatedly asks to sleep for an exact time and measures how late the kernel was in waking up.
