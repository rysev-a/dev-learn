#CHAPTER 12 | Boot, systemd and packages
Diving into Unix. Chapter twelve. Boot, systemd and packages. You press the power button, and a few seconds later you have a running system with a network, a database and a web server. Who started all of that, and in what order? In this chapter we will walk the path from power-on to ready services: firmware, bootloader, kernel, initial image, first process. Then we will look at how systemd describes services, dependencies, restarts and logs, and finally we will talk about where the programs themselves come from, that is, packages.\n\nThe first steps are taken by the firmware, which on modern machines is UEFI. It initializes the hardware, finds the system partition with the bootloader and starts it. The bootloader, that is GRUB or systemd-boot, shows a menu, picks a kernel and loads two files into memory: the kernel itself and the initial filesystem image, initramfs. It also hands the kernel a command line with parameters: where the root partition is, whether to boot quietly, and so on. From this moment control belongs to the kernel, and everything else is done by it.\n\nThe kernel unpacks itself, sets up memory, processors and interrupts, and then mounts the initial image in RAM. Why is it needed? So that the kernel can find the real root: the disk driver, encryption, RAID and LVM are sometimes built as modules, and they can only be loaded from here. The image's scripts unlock the disk, assemble the volumes and mount the root filesystem. After that comes the root switch, and the kernel starts the first user program, process number one. Usually that is systemd.\n\nsystemd manages not programs but units: that is the name for any item it knows about. A service starts a process, a socket opens a port, a timer fires on a schedule, a mount attaches a disk, and a target is a meeting point, like multi-user mode. Each unit is described by a text file with three sections. The Unit section holds the description and the dependencies, the Service section says what to run, as which user and how to restart it, and the Install section says which target to attach it to when autostart is enabled.\n\nDependencies determine the boot order. Requires says that the service cannot work without this unit: if the unit fails to start, so does the service. Wants is softer: it would be good to start it, but we can live without it. After and Before set only the order and do not pull in other units. Thanks to this graph, systemd starts everything that does not depend on each other in parallel. On a server with a hundred services, startup takes seconds rather than minutes. The systemd-analyze command shows who waited, and for how long, at every step.\n\nSocket activation makes startup even smarter. systemd itself opens the port and listens on it, and starts the real service only on the first connection, handing it the ready descriptor. While nobody connects, the service takes no memory. As a bonus, the startup order stops mattering: clients can connect even before the server starts, and the kernel will accumulate the connections in a queue. Timers replace cron in a similar way: a timer unit has a schedule, and the unit it triggers is a separate service with its own log.\n\nWhat should happen when a service crashes? In the Service section, the Restart setting defines when to restart: always, on failure, or never. The pause between attempts is set separately. But if a service crashes instantly and endlessly, the restarts will eat the processor. That is why there is a limit: no more than a given number of starts within a given interval, after which the unit is marked as failed and waits for a human. The status shows the cause of the crash, the exit code and the last lines of the log.\n\nEach service runs in its own control group, and this gives systemd power over resources. You can limit memory, processor share and the number of processes right in the unit file, and the kernel will enforce it, and when the service stops it will kill all of its descendants to the last one. There are also protective settings: make the system read-only for the service, give it its own temporary directory, take away its network. The systemd-analyze security command even gives a service a security score. And since version two hundred fifty-eight, support for the old version one control groups has been removed entirely.\n\nFor logs, systemd keeps its own service, the journal. It collects the output of all services and the kernel messages into one structured binary journal, where every entry has fields: unit, priority, process, time. The journalctl command can filter by unit, by severity and by time, for example errors of a service over the last hour. The journal can be kept across reboots, and if you wish, forwarded to a central server. A habit of starting diagnostics with the status and the journal saves a lot of time.\n\nThat leaves the question of where programs come from. They are installed by a package manager. A package is an archive with files, metadata and a list of dependencies. In the Debian family, apt works on top of dpkg, and in the Red Hat family, dnf works on top of RPM. The manager picks versions so that all requirements are met at once, and installs dependencies before the packages that need them. Versions are compared not as strings but by special rules. Unneeded dependencies are removed by autoremove, and ldd helps in finding missing libraries.
