#CHAPTER 5 | The scheduler: from a queue to EEVDF
Diving into Unix. Chapter 5. The scheduler: from a queue to EEVDF. A machine has hundreds of processes, but only a handful of CPU cores. So somebody has to decide who runs right now, for how long, and who goes next. That job belongs to the scheduler, and it determines how responsive your computer feels, how quickly a server answers, and whether resources are shared fairly. In this chapter we will see how the scheduler is built today, why the new algorithm beats the old one, and how it copes with several processors and with real-time tasks.\n\nA little history, because the logic shows in it. Old kernels had a scheduler with constant-time selection; it split tasks into classes by priority and tried to guess which of them were interactive. The heuristics got confused. In two thousand seven it was replaced by the Completely Fair Scheduler, CFS: it stopped guessing and started counting how much CPU time each task had received. And in kernel version six point six, in two thousand twenty-three, EEVDF took its place, which handles latency better. More on that below.\n\nFirst, the big picture. The scheduler consists of classes that are polled in order of importance. At the top is the stop class, which the kernel needs for housekeeping. Next comes the deadline class, then real time, then the ordinary fair class, where almost everything you run lives. The newer extensible scheduler class sits below the ordinary one, and the very last is idle, for when there is no work. The scheduler simply takes a task from the first non-empty class. That is why a real-time task will always overtake an ordinary one.\n\nIn the ordinary class the key word is fairness. Each task is assigned a weight, and it depends on its nice value. A value of zero gives a weight of one thousand twenty-four, and each step up or down changes the weight by roughly a factor of one and a quarter. If two ready tasks have weights in a ratio of two to one, they will get CPU time in the same proportion. For bookkeeping, the kernel keeps virtual time: for a heavy task it flows more slowly, for a light one faster. The idea is simple: everybody should live through the same amount of virtual time.\n\nNow, how EEVDF picks the next task. It compares the time a task has received with the time it is fairly owed: the difference is called lag. Positive lag means the task has been shortchanged, and it is eligible to be picked. Negative lag means it has already taken extra and will wait. For each eligible task a virtual deadline is computed: the start time plus its slice divided by its weight. The scheduler takes the eligible task with the earliest deadline. This combines fairness on average with a predictable order at every moment.\n\nThe main win of EEVDF is that latency can now be requested directly. Before, for a responsive program to get the CPU ahead of others, you had to raise its priority, and that changed its share of time as well. Now a task can ask for a short slice through the sched set attr call. Its deadline comes earlier, it gets the CPU sooner, but its share of time does not change: its slices are simply shorter and more frequent. That is very convenient for interactive programs, audio and games, while heavy computations happily run with long slices.\n\nNow, about sleep. A task often waits: for the disk, the network, the user. What happens to its lag? While it sleeps, the lag must not simply be erased, otherwise you could keep refreshing your entitlement by dozing off for a moment. The scheduler stores the lag of a sleeping task and then gradually brings it down to zero. A task that wakes up comes back with its honest remainder, and if it was shortchanged, it gets the CPU quickly. That is why interactive tasks, which sleep a lot, usually win, while compute-bound ones, which never give up the CPU, wait their turn.\n\nBut a modern machine has many cores. Each core has its own queue of ready tasks, so the cores do not get in each other's way with locks. In return, the queues must be balanced: if one core is idle while another has a long queue, the idle core takes tasks for itself. The scheduler knows the topology: sibling threads of one core, a shared cache, memory nodes. So it is cheaper to move a task between nearby cores. You can pin a process to certain cores with the taskset command, and limit a group's share of CPU with control groups. Both mechanisms are used in containers.\n\nFor tasks with strict requirements there are the real-time classes. In the first, with fixed priorities from one to ninety-nine, a task holds the CPU until it yields or a more important one preempts it. The deadline class takes three numbers from a task: how much time it needs, by what deadline, and with what period, and it promises to meet them, or else it refuses. To make the kernel itself preemptible, version six point twelve merged the real-time mode into the mainline, which turns locks into sleeping ones, and six point thirteen added lazy preemption.\n\nAnd the last novelty. The extensible scheduler, sched-ext, appeared in version six point twelve: you can write task-selection rules in the BPF language, load them into a running kernel and apply them at once. The kernel verifies the program, and if it hangs or breaks, it hands control back to the ordinary scheduler, so experiments are safe. Schedulers for games and servers are built on it. And version seven point zero added slice extension: a program can briefly ask not to be preempted inside a critical section. So the scheduler turns from kernel code into a configurable platform.
