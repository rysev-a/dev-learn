#CHAPTER 4 | Processes: how a program becomes a task
Diving into Unix. Chapter 4. Processes: how a program becomes a task. A program on disk is just a file with code. A process is a program at the moment of execution: code in memory, data, a stack, open files and a current state. We have already seen that the shell starts processes with the fork and exec calls. Now let's look inside the kernel and see how it describes a process, how a thread differs from a process, how tasks are born and die, and how we talk to them with signals.\n\nFor every process the kernel creates a structure called the task descriptor, in the source code task_struct. It is a big record that gathers everything about a process: the identifier, the state, the parent and children, a pointer to the description of the address space, the table of open files, the user's credentials, signal handlers and the data for the scheduler. When you read the proc directory, you are really browsing these records. Everything the kernel does with a process is reading and editing its descriptor.\n\nSo what counts as a thread? In Linux the difference is subtler than in other systems. The kernel knows only tasks, and they are all created by a single call, clone. The flags of the call say what the tasks share: if the new one gets its own copy of memory and of the file table, it is an ordinary process; if they are shared, you get a thread. So a thread is simply a task that shares memory with its neighbors. Every task has its own number for the kernel, while a group of threads has one common number, and that is what the get-pid call returns.\n\nHow can a copy of a process be created so quickly? The kernel does not copy the memory, it copies only the page tables, and both tables point to the same physical pages, marked read-only. As long as both processes only read, nothing is duplicated. As soon as one of them tries to write, a page-fault exception occurs, the kernel makes a copy of that one page, and the write continues. This is copy-on-write. It makes fork fast even for huge processes, and we met the very same idea in virtual memory.\n\nNext, exec. It does not create a process, it remakes an existing one: the old address space is thrown away, a new program is loaded into it, the stack is built from scratch, and the process identifier stays the same. Open files are kept too, unless they carry the close-on-exec flag. Thanks to this, the shell can swap descriptors between fork and exec. For the rare cases when a full copy is not needed, there is a special fast call, and modern libraries use a one-step process spawner.\n\nProcesses form a tree. Each one has a parent, and the root is process number one, that is, systemd or another init system. With the pstree command you can see the whole tree at once. What happens if a parent dies before its children? The kernel does not leave orphans unattended: it hands them to the nearest adopter, a subreaper, and if there is none, to process number one. That is why the parent of daemons that detached from the terminal is often process one. And containers need adopters too.\n\nAt any moment a process is in some state. It is running on a processor or ready to run, that is R. It is sleeping, waiting for an event, and can be woken by a signal, that is S. It is sleeping briefly, waiting for a disk reply, and cannot be interrupted, that is D, and it is exactly such processes that inflate the load average. It is stopped by a signal, that is T. And finally the zombie, Z: it has already finished, but the parent has not collected its exit code. The STAT column in the ps command shows exactly these letters, and they tell you what is going on in the system.\n\nNow, about death. A process ends with the exit call and leaves an exit code behind. But the kernel cannot delete the entry right away: the parent has the right to learn how the child's life ended. Until it calls wait, the child stays a zombie: it has no memory, it only occupies a row in the process table. The parent receives a signal about the child's death. Many zombies mean that the parent does not call wait: that is its bug. You cannot kill a zombie, it is already dead; the only help is to terminate the parent.\n\nNow signals. These are short asynchronous notifications to a process: the kernel or another process sends a number, and the recipient reacts. The most common are: terminate, number fifteen, a polite request to finish; interrupt, number two, which is what pressing control-C sends; and kill, number nine, unconditional termination. For most signals you can install a handler, and the process has time to clean up. But kill and stop cannot be caught: the kernel carries them out itself. A signal is delivered on the way back into user mode.\n\nIn practice, you most often send terminate first and wait a few seconds so the program can close its files properly, and only then kill. A signal can go not just to one process but, when needed, to a whole group: the shell's processes are organized into groups, and the groups into sessions tied to a terminal. Pressing control-C goes to the entire foreground group, so the whole pipeline stops together with the program. The jobs, fg and bg commands move tasks between the background and the foreground. The details of a process always live in the proc directory, under its number.
