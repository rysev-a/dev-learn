#CHAPTER 14 | Modules, drivers, and observability
Diving into Unix. Chapter fourteen. Modules, drivers, and observability. We have come all the way from the command line to the insides of the kernel, and what is left is to understand how the kernel grows, adapts to hardware, and how to watch it at work. The kernel is not a monolithic lump: a lot of it is plugged in at runtime as modules, devices show up as files, and parameters change on the fly. And when something goes wrong, the kernel has its own logs, counters, and tracing tools. This is the final chapter, and at the end we will look back over the whole course.\n\nLet's start with devices. The dev directory holds files that stand for devices. Each one has a pair of numbers: the major number picks the driver, and the minor number picks a particular instance. Character devices, like a terminal, hand out bytes as a stream; block devices, like a disk, work in blocks with random access. But nobody writes this directory by hand: that is the job of the udev service. When the kernel finds a new device, it announces it, and udev creates the file, sets permissions, and runs the rules. Information about devices is exposed through the sysfs filesystem.\n\nHow does a device find its driver? The kernel keeps a device model: there are buses, for example PCI or USB, there are devices on them, and there are drivers. When a bus discovers a device, it reports its identifier: the vendor and the model. Drivers declare in advance which identifiers they can handle. The kernel matches one against the other and calls the binding function of the suitable driver. If the driver is not loaded, udev uses the identifier to find the right module and loads it. That is exactly why a new flash drive works the moment you plug it in.\n\nA module is a kernel object file that can be loaded and unloaded without a reboot. The lsmod utility shows what is loaded, and modprobe loads a module with its dependencies in mind: if one module uses functions from another, the second one is loaded first. The file with dependencies is built ahead of time. A module can be unloaded only if nobody is using it. Modules are signed, and the kernel may refuse to load an unsigned one; in version seven point zero a post-quantum algorithm was added for signatures, and the outdated SHA-1 signatures were removed.\n\nNow, about the language. The kernel has always been written in C, but since version six point one it has support for Rust, and you know from the book about it why it is attractive: the ownership system keeps you from making mistakes with memory and data races. Real drivers are already written in Rust: Binder for Android, which replaces the C version, and a driver for graphics cards on Mali chips. Work on a driver for NVIDIA graphics cards is still going on. The experimental status has been lifted: in version seven point zero, Rust support is considered a permanent part of the kernel, not an experiment.\n\nThe kernel has many settings, and the most common ones change without a reboot. The proc sys directory is a tree of parameters, and the sysctl utility reads and writes them: queue sizes, network behavior, dirty page thresholds, limits. A value you write holds until the reboot, and to make it permanent, you put it in a file in the etc sysctl dot d directory. Some parameters are passed at boot on the kernel command line. Always look at the current value and at what has been changed: tuning without understanding is the most common cause of strange behavior.\n\nWhen something goes wrong, the kernel writes about it to its ring buffer log. The dmesg command shows it, and each message has a severity level, from informational to emergency. A serious error in the kernel leads to an oops: the kernel prints the register state and the call stack, and then kills the culprit. If the error is unrecoverable, the kernel declares a panic and stops. To investigate afterwards, servers are set up with kdump: on a panic, a second kernel is loaded and saves a memory dump of the first. Filtering dmesg by level is the main technique for a first look.\n\nHow do you tell that a machine is overloaded? The first indicator is the load average, over one, five, and fifteen minutes. It is the averaged number of tasks that are running or waiting for the processor or the disk. If there are four cores and the load is twelve, the queue is three times longer than the capacity. But the number does not say what exactly is lacking. The vmstat utility breaks it down: the process queue, swapping, input and output, and time in user space, in the kernel, and waiting for the disk. And the pressure stall information, PSI, directly tells you how much time tasks stood idle for lack of processor, memory, or disk.\n\nIf you need to find out where the processor spends its time, perf comes to help. It takes stack samples at a given frequency and builds a report: which functions the program spends its time in, including inside the kernel. For a detailed picture there is ftrace: built-in tracing that records function calls and events. The kernel has tracepoints placed in it, stable places where you can attach, and dynamic kprobes can be hung on almost any function. All of this works without recompiling and with small overhead.\n\nAnd the most powerful observation tool is eBPF. The bpftrace and bcc utilities let you hang a small program on a system call, a function, or a tracepoint with a single line, and collect histograms: disk latency by request size, who opens files, where packets get lost. The kernel verifies the program, so it will not crash the system. New versions come out roughly every two to three months, while long-term support versions live for years. You have gone through the course from the shell to the kernel: now the kernel is not a black box for you, but a system you can read, measure, and understand.
