#CHAPTER 6 | System calls: the only door into the kernel
Diving into Unix. Chapter 6. System calls: the only door into the kernel. On its own, a program can do almost nothing: it can't read a disk, open a network connection, create processes, or allocate physical memory. Only the kernel does all that, and the program merely asks. The request is called a system call, and it is the one permitted way to get from ordinary code into the kernel. Today we'll see what happens at the processor level, how to watch the calls of any program, what they cost, and how to restrict them.\n\nLet's start with modes. A processor works in two main modes, and we know this from the computer architecture book. User mode is restricted: you can't touch devices, change page tables, or disable interrupts, and you can only reach your own memory. Kernel mode, also called privileged mode, allows everything. The kernel runs in it and guards the border. If an ordinary program tries to execute a privileged instruction, the processor raises an exception, and the kernel terminates the offender. That way one faulty program can't break the whole machine.\n\nNow the transition itself. The program puts the number of the call it wants into the RAX register, and the arguments into RDI, RSI, RDX and other registers, by convention. Then it executes a special instruction, syscall. The processor switches to kernel mode and jumps to a pre-configured address, and the kernel uses the number to look up the handler in the system call table. When the work is done, the result is placed in RAX, and a return instruction takes the processor back to user mode, to the next instruction of the program. All of this takes a few hundred cycles.\n\nBut nobody wants to write assembly, so the standard library provides wrappers. When you call the function write, the library puts the arguments into registers and executes the syscall. On failure the kernel returns a negative code, and the wrapper turns it into minus one and saves the reason in a variable called errno. That's why the rule of good code is simple: after every call, check the result and look at errno. No such file, no permission, disk full: the reasons differ, and only this number tells them apart.\n\nYou can watch the calls of any program with the strace utility: it shows every call with its arguments and result, including the failed ones. It's the best way to understand what a program really does: which files it opens, where it connects, which call it hung on. The dash c option prints a summary: how many times each call was made and how much time it took. If a program reads one byte at a time thousands of times, you see it immediately. Strace slows the program down, so in production people use lighter observation tools.\n\nWhat does this cost in time? The switch itself is cheap, on the order of hundreds of nanoseconds, but it became more expensive after the mitigations for processor vulnerabilities, and every call also flushes part of the cache. That's why programs try to call the kernel less often and in larger batches. For the most frequent harmless calls, like getting the time, the vDSO was invented: a small library that the kernel maps into every process by itself. It reads the time from a shared page without entering the kernel, and the call costs just a few nanoseconds.\n\nNow, what you get back when you open a file. It's a file descriptor: an index into the process's table, and the table entry holds a pointer to an open file in the kernel. Two descriptors can point to the same open file, for example after the dup call, and then they share the read position. The table is limited: the ulimit utility shows the limit, and running out of descriptors gives the error "too many open files". And the close-on-exec flag keeps a descriptor from leaking into a program you launch.\n\nLet's look at reading. The read call asks for at most a given number of bytes and returns how many it actually got. That number can be smaller than requested, even without an error, and zero means end of file. A signal can also interrupt it, in which case you get an interrupted error and the call must be repeated. The kernel copies the data from its page cache into the program's buffer, and we'll come back to that in the chapter on file systems. For reliability, a write needs a synchronization call, otherwise the data may stay in memory.\n\nSince system calls are a trust boundary, the kernel checks everything on it. A pointer from a program can't be dereferenced directly: the kernel copies data with special functions that return an error for a bad address. Beyond that, a process can be forbidden unneeded calls. A seccomp filter written in BPF receives the call number and arguments and decides: allow it, return an error, or kill the process. Browsers and containers greatly shrink their attack surface this way, because a call that doesn't exist can't be abused.\n\nOrdinary calls have a drawback, though: each one is a separate transition, and for thousands of simultaneous operations that's a lot. So kernel version 5.1 introduced io_uring. The program and the kernel share two ring buffers in memory: the program puts requests into one and takes results from the other. A single call can submit a whole batch of operations, and with kernel polling, no calls are needed at all. Io_uring handles files, networking, and timers, and today it is developing faster than other interfaces, including filters on BPF.
