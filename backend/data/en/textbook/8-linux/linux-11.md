#CHAPTER 11 | Networking: sockets, the stack and eBPF
Diving into Unix. Chapter eleven. Networking: sockets, the stack and eBPF. Linux owes a great deal to networking: most of the internet runs on it. The network stack is one of the biggest and most finely tuned parts of the kernel, and almost everything we have already covered meets in it: file descriptors, interrupts, queues, memory. In this chapter we will follow the path from a call in a program to the wire: sockets, addresses and routes, the packet's path through the kernel, the TCP protocol, the firewall, names and, finally, a programmable network built on eBPF.\n\nA program works with the network through sockets. A socket is a file descriptor that, instead of a file on disk, has one end of a network connection behind it. The server creates a socket, binds it to an address and a port, announces that it is ready to accept connections, and waits. The client creates its own socket and connects. After that both sides read and write with ordinary calls. The pair of an address and a port, plus the protocol, uniquely identifies the end of a connection, and a port is a number from zero to sixty-five thousand, by which the kernel picks the right program.\n\nNow addresses. An IP version four address is thirty-two bits, written as four numbers, and part of them identifies the network while the rest identifies the machine within it. Where the boundary lies is told by the mask: the notation ten dot zero dot zero dot zero slash twenty-four means that the first twenty-four bits describe the network. Two machines in the same network talk directly, and in different networks they send packets to a gateway. For version six the addresses are four times longer, but the principle is the same. Computing boundaries and ranges is a typical task, and we will solve it.\n\nHow does the kernel decide where to send a packet? By the routing table. Each row holds a destination network, an interface and a gateway. When several rows match, the most specific one wins, that is, the one with the longest prefix. The default row, zero dot zero dot zero dot zero slash zero, matches everything and works as a fallback: everything with no better route goes there. The table is shown by the ip route command, and it can be changed on the fly, so a mistake in a route turns into a lost connection.\n\nWhat happens to a packet inside the kernel? It arrives at the network card, and the card writes it into a ring in memory by direct memory access, without distracting the processor. Then the card raises an interrupt, and the kernel switches to NAPI polling and picks up packets in a batch. Each packet is wrapped in an sk_buff structure, which goes up the stack: the link layer, IP, then TCP or UDP. In the end the data lands in the socket's receive buffer, and a process that fell asleep waiting wakes up. Sending goes along the same path in the opposite direction.\n\nTCP promises reliable, ordered delivery, and all of this works inside the kernel. A connection begins with a three-way handshake: the client sends a request, the server answers, the client confirms. After that every piece sent must be acknowledged, and anything that doesn't arrive is sent again. The window shows how much data can be sent without an acknowledgment, and the congestion control algorithm makes sure the network isn't clogged. Usually this is CUBIC, but there is also BBR, which goes not by losses but by bandwidth. The parameters are visible in the ss command with the dash t i option.\n\nNow protection. Inside the kernel, at several points on a packet's path, there are hooks: before routing, on input to the machine, on forwarding, on output, and before sending. The netfilter subsystem lets you hang rules on them: accept, drop, or rewrite an address. The modern interface is called nftables, and it replaced the old iptables. Alongside it works the connection tracker: it remembers which flows are open so that replies to your requests are let through automatically. Firewalls and address translation, that is NAT, are built on this.\n\nBut users work not with addresses but with names. Before sending a packet, a program asks for name resolution. The order of sources is set by the nsswitch dot conf file: first the hosts file, then DNS. The addresses of name servers are kept in the resolv dot conf file, but in many distributions it points to a local intermediary, systemd-resolved, which caches answers and can work with several networks. If a name can't be found but the address works, look for the problem here: the network and name resolution often break independently.\n\nAnd now the most modern part. eBPF lets you load small programs into the kernel that run at certain points: when a packet is received, when a function is called, on a timer. The kernel first checks the program with the verifier, proving that it will terminate and won't go outside its memory, and then compiles it to machine code. The fastest point is XDP, the earliest place of reception in the driver: a packet can be dropped or redirected even before a structure is allocated for it. This is how attack protection and load balancers are made.\n\nWhat do you do when the network doesn't work? Go through the floors from the bottom up. Is there a link at the link layer? Is an address assigned? Is the route right? Does the gateway answer? Does the name resolve? Is the program listening on the right port? There is the familiar toolkit for this: ip for addresses, ip route for routes, ss for sockets, and tcpdump shows the packets on the wire. A classic of its own is packet size: if it is larger than the link limit, it gets fragmented or lost, and big requests hang while small ones work fine.
