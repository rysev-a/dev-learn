#CHAPTER 3 | Permissions, Users and Privileges
Diving into Unix. Chapter three. Permissions, Users and Privileges. Linux was designed from the very beginning as a multi-user system: dozens of people and services can work on one machine, and none of them should read what belongs to others or break what is shared. The kernel does this job: on every access to a file it checks who is asking and what they are allowed to do. Today we will look at how the kernel learns who the user is, what the nine access bits mean, why we need special bits, access control lists, sudo and capabilities, and how protection is built in layers.\n\nTo the kernel, a user is a number. The user ID, UID, and the group ID, GID, are recorded in every process and in every inode. Names exist for people: the mapping between numbers and names is kept in the passwd file in the etc directory, while password hashes are stored separately, in the shadow file, which only the administrator can read. The superuser, root, has ID zero, and the kernel gives it almost everything. The id command shows your numbers and groups. Service accounts exist too, but without a password and without login.\n\nNow the permissions themselves. Every inode has three sets of three bits: for the owner, for the group and for everyone else. Each set holds three permissions: read, write and execute. That is why you see a string like r-w-x, r-x, r-dash-dash. For a file everything is clear, but for a directory the meaning is different: read means seeing the list of names, write means creating and deleting names inside, and execute means passing through the directory. Without the execute permission you simply cannot reach a file inside.\n\nThree sets of three bits are conveniently written as an octal number: read is four, write is two, execute is one, and the sum gives a digit from zero to seven. Permissions six-four-four mean read and write for the owner, read for everyone else. They are changed by the chmod command, either with a number or with letters. New files are not created with arbitrary permissions: the system takes six-six-six for a file and seven-seven-seven for a directory and subtracts the mask, umask. With the mask zero-two-two you get the familiar six-four-four and seven-five-five.\n\nHow exactly does the kernel decide whether to let you in? It compares the effective ID of the process with the owner of the inode. If they match, the owner's set applies, and the check ends there. Otherwise it checks the process's group and supplementary groups; if one matches, the group's set applies. Otherwise the set for everyone else is used. Notice: the sets are not added together, the first one that fits wins, even if it is stricter. And to reach a file, you need the execute permission on every directory along the path. Root walks past these checks: it has a special privilege.\n\nSometimes an ordinary user needs to temporarily get someone else's rights. The passwd command changes a password, that is, it writes to a file closed to everyone except root. For this there is a special bit: if an executable file has setuid set, then at launch the effective ID of the process becomes equal to the file's owner. The real ID stays the same, so the program knows who called it. Such programs are dangerous, because a bug in them hands out someone else's rights, so they are hunted down and kept on a strict list. The setgid bit works the same way for a group.\n\nThere is also the sticky bit on shared directories like tmp. In an ordinary directory with write permission you can delete someone else's file, because deleting is an edit of the directory. The sticky bit forbids that: only the owner of the file or of the directory can delete a name. But three sets of bits are sometimes not enough: you need to give access to one more person without creating a group. Access control lists were invented for this. The setfacl command adds an entry for a specific user or group, and the mask limits the maximum for all entries except the owner.\n\nAnd how does an ordinary user do administrative work? Through sudo. It runs a single command as another user, usually root, if the sudoers file allows it. That file describes who can do what and where: a whole shell, or just restarting one service. Sudo asks for your password, not root's, and writes every command to a log. The main security principle is least privilege: give exactly what the task needs. Being logged in as root around the clock is a bad habit, and in sudoers never allow everything to everyone.\n\nIn the modern kernel, root's might is divided into small pieces called capabilities. There are about forty of them: binding ports below one thousand twenty-four, changing the time, loading modules, administering the system, and so on. A process can hold only the ones it needs. A web server needs only the capability to take a privileged port, and does not need root at all. Capabilities can be written into the executable file itself instead of setuid. Containers rely on this too: at launch most capabilities are dropped, and the process inside is left almost powerless.\n\nThe scheme described so far is called discretionary access control: the owner decides who gets what. On top of it the kernel supports mandatory access control, implemented by security modules: SELinux and AppArmor. They follow the administrator's rules, and even root cannot bypass them. Another layer is seccomp, a system call filter, and Landlock, which lets a process give up access to part of the file system. Each layer can only deny. So access is allowed only when every layer has approved it, and this principle is worth keeping in mind.
