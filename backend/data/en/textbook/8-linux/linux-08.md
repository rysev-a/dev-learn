#CHAPTER 8 | Synchronization: Races, Locks and RCU
Diving into Unix. Chapter 8. Synchronization: races, locks and RCU. The kernel is the most parallel program on the machine. All the processor cores run its code at the same time, any device can interrupt it, and the scheduler can preempt it right in the middle of a function. If two threads of execution touch the same data without agreeing on who goes first, the result is unpredictable, and this kind of bug is called a race. Today we will look at where parallelism comes from, what kinds of locks there are, how to pick the right one, and how to read data with no lock at all.\n\nLet's show a race on the simplest possible example. A counter goes up by one, and in the program that is a single line, but in reality it is three steps: read the value, add one, write it back. Say two cores do this at the same moment. Both read five, both add one, both write six. We should have gotten seven, and we got six: one update was lost. Worst of all, the bug shows up rarely, depends on timing, and does not reproduce under a debugger. That is why you must always protect shared data, not just when you notice a problem.\n\nThe simplest tool is atomic operations. The processor can do a read, a modify and a write as one indivisible step: for that, the instruction gets a bus lock or cache line lock prefix. In the kernel these are the atomic types and functions like atomic add. For counters and flags they are enough, and they are very fast. But they are not free: while one core is modifying a cache line, the others have to wait, because the line travels between them. You have already seen this effect in the MESI protocol: the more cores fight over a single line, the slower it gets.\n\nWhen you need to protect not a single number but a whole piece of code, you need a lock. The simplest one is the spinlock. A core that wants to get in spins in a loop and checks the flag again and again until it becomes free. While the lock is held, preemption on that core is disabled. So you can stay inside only for a very short time, and you must never sleep: the holder would fall asleep while its neighbors spin uselessly. A modern spinlock builds a queue, so that waiters enter in order instead of shoving each other.\n\nIf the section is long, or you need to sleep inside it, you take a mutex. It works differently: a core that fails to get the lock goes to sleep, and the scheduler hands the processor to someone else. If the holder is about to release the lock, the core spins for a little while before going to sleep. A mutex costs more, but it does not waste processor time. It has restrictions: you cannot take it in an interrupt handler, because sleeping is not allowed there, and it must be released by the same task. In real-time mode a mutex can pass its priority on to the holder, to avoid priority inversion.\n\nHow do you choose? Start by asking which context you are entering from. If an interrupt handler touches the data, you need a spinlock that also disables interrupts on that core, otherwise the handler will interrupt the holder and hang, waiting for it. If the code runs only in process context and may sleep, use a mutex. If the data belongs to a single core, it is better to avoid locking altogether and use per-CPU variables. The shorter the critical section and the less shared data, the better the kernel scales to hundreds of processors.\n\nOften data is read much more often than it is changed. A reader-writer lock lets in any number of readers at once, but only one writer, and only with no readers present. A sequence lock goes further: readers take nothing at all. They read a version counter before and after reading, and if it changed, they retry. This is how the kernel reads the time, because it is written rarely and read constantly. But an ordinary reader lock still modifies a shared cache line, and on many cores that is expensive.\n\nThe radical solution is RCU: read, copy, update. Readers take no locks at all and write nothing to memory: they simply follow pointers. A writer makes a new copy of the structure, edits it, and swaps the pointer in one atomic step. But the old version cannot be freed right away: readers might still be looking at it. The kernel waits out a grace period, until every core has passed through a safe point at least once, and only then frees the old version. Routing tables, directory entries and much more are built on RCU.\n\nLocks bring a new trouble: deadlock. The first thread holds lock A and waits for B, the second holds B and waits for A, and both stand still forever. The defense is a single locking order: always A first, then B. But the kernel has hundreds of thousands of locks, and tracking the order by hand is impossible. That is why there is lockdep, which checks on the fly: it remembers the order in which locks are taken, and at the first hint of a cycle it prints a warning, even if no hang has happened yet. It is switched on in debug builds.\n\nAnd one last thing. All these rules, take the lock, don't forget to release it, don't touch the data without it, rest on discipline in the C language. In Rust code, the kernel has gone further: the mutex owns the data itself, and you can reach the data only by getting a guard that releases the lock when it goes out of scope. Forgetting to take the lock is impossible, and a data race in safe code does not compile. Since version seven point zero, Rust support is no longer experimental, and guarantees like these are the main reason it was added to the kernel.
