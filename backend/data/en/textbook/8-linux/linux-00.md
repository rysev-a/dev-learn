#CHAPTER 0 | What an operating system is and where Unix came from
Diving into Unix. Introduction. What an operating system is and where Unix came from. Picture a computer with no operating system: every program talks to the disk, the keyboard and the network card on its own, divides memory with its neighbors on its own, and makes sure nobody breaks anything on its own. No program could survive that load. So between the programs and the hardware sits a go-between. It does three things: it hides the hardware behind simple concepts, it shares resources between programs, and it protects them from each other. This whole book is about how exactly it does that.\n\nLet's start with the first job, abstractions. A disk is made of sectors, but you work with files and directories. There is one processor and dozens of programs, and each program feels as if the processor belongs to it alone: that's a process. Memory is shared, but every program has its own set of addresses: that's virtual memory. A network card transmits frames, while you open a socket and write bytes into it. Every abstraction makes a promise: use the simple thing, and we'll handle the complicated part for you.\n\nThe second job is sharing, and the third is protecting. Processor time is cut into time slices, memory into pages, the disk into blocks, and the network into queues of packets. One program must not read another's memory, and an ordinary user must not read other people's files. Agreements alone are not enough for that; it takes hardware support. The processor works in two modes: in the privileged one everything is allowed, and in the ordinary one you can't touch devices or other programs' memory. The kernel lives in the first mode, your programs in the second.\n\nThat gives us a split into two halves. The kernel is the code that runs in privileged mode, is loaded first, and stays in memory as long as the machine is on. Everything else is called user space: the shell, editors, browsers, services and the standard library. A program talks to the kernel only through system calls: open a file, create a process, allocate memory. It's a narrow door with a check at the entrance. The kernel is not a separate program that keeps running alongside everything else: it runs when someone calls it, or when an interrupt arrives from a device.\n\nInside, the kernel is divided into subsystems, and this book is organized around them. The scheduler decides who runs on the processor, and when. Memory management hands out pages and takes them back. The file system and the block layer take care of data on disks, the network stack talks over the network, and drivers hide the differences between specific devices. In Linux they all run in a single address space: such a kernel is called monolithic, and extra code is loaded as modules. A microkernel keeps only a minimum in privileged mode, and everything else is moved out into ordinary processes.\n\nNow, where did all this come from? In the nineteen sixties, a big shared system called Multics was built jointly by MIT, General Electric and Bell Labs. The project turned out unwieldy, and Bell Labs pulled out. In nineteen sixty-nine Ken Thompson and Dennis Ritchie wrote a modest system for themselves on a small machine. Their colleagues jokingly called it Unix: one, as opposed to many. And in nineteen seventy-three it was rewritten in the C language, which Ritchie had invented for exactly this kind of work.\n\nRewriting it in C turned out to be decisive: to move the system to another machine, you only had to rewrite a small piece. Bell Labs was not allowed by law to sell software, so the system was handed out to universities along with the source code. That's how the Berkeley branch, BSD, appeared, where sockets and the TCP/IP stack were born. Commercial companies shipped their own versions, and so that programs could move between them, a standard was devised: POSIX. It describes system calls, utilities and the behavior of the command line.\n\nIn the nineteen eighties Richard Stallman started the GNU project: free replacements for all the Unix utilities, but without a kernel of its own. In nineteen ninety-one a Finnish student, Linus Torvalds, wrote a kernel and released it to everyone. Free utilities plus a new kernel made a complete system. Strictly speaking, Linux is only the kernel, and what you install is called a distribution: the kernel, utilities, libraries and a package manager. The Linux kernel underlies Android, cloud servers and supercomputers, while Berkeley's descendants run in macOS and FreeBSD.\n\nUnix is remembered not only for its code, but for its philosophy. Write small programs, each of which does one thing and does it well. Make the output of one program usable as the input of another, which is why the common format is plain text. Make everything available as a file: disks, terminals, pipes. Write so that a tool can be used in unexpected ways. As a result, instead of one big program you assemble a solution from little bricks through a pipeline. That's exactly how we'll look at the system.\n\nLet's finish with the big picture. You type a command, the terminal passes the characters to the shell, the shell calls fork, and the kernel creates a copy of the process. Then the exec call loads the right program into that copy. The program opens a file: the kernel walks the path, checks permissions, takes pages from the cache, and on a miss asks the disk. The result goes back to the terminal. Processes, memory, files, permissions, interrupts and the scheduler all took part in that chain. From here we'll go through them one by one, from the shell down to the kernel.
