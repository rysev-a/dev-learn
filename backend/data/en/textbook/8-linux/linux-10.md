#CHAPTER 10 | File systems, the page cache and disks
Diving into Unix. Chapter ten. File systems, the page cache and disks. In the first chapter we looked at files through the eyes of a user, and now we will follow the whole path of a written byte from top to bottom. The program calls write, the kernel deals with the file system, the data settles in the page cache, then it goes to the block layer, from there to the driver and, finally, to the device. Each step solves its own problems: a single interface, speed, ordering of operations, reliability. We will go through the steps one by one and see why a write returns so fast and what "data on disk" really means.\n\nLet's begin with the virtual file system. Its job is to give one common interface to all file systems at once. It works with four objects. The superblock describes a whole mounted file system. The inode is a single file. The directory entry, or dentry, links a name to an inode; it lives in a cache and speeds up path lookup. And the open file is what a process gets together with a file descriptor. These objects are the same for ext4, XFS, Btrfs and even for procfs and network file systems. What differs is only what stands behind them.\n\nHow are these layers connected? Through operation tables, that is, sets of function pointers. Every object has its own table: a file has read and write operations, an inode has create and delete, a superblock has sync and statistics. When you call read, the virtual file system finds the open file and calls a function from its table, and which function that is was decided by the particular file system when the file was opened. In essence, this is object-oriented programming written in C long before it became fashionable.\n\nReading from a disk is slow, so the kernel keeps what it has read in memory. This is the page cache: file data lives in pages grouped by file. The first read goes to the disk, the second one comes from memory. What is more, the kernel notices that you are reading a file sequentially and starts loading the next chunks in advance: this is readahead. Almost all the free memory on a Linux machine is occupied by exactly this cache, and that is a good thing: when memory runs short, the cache is released instantly. That is why the free command shows little "free" memory but a lot of "available" memory.\n\nWriting is more interesting. A write call only copies the data into the page cache and marks the pages dirty. The program gets its answer immediately, and the data goes to the disk later. This is handled by the writeback threads: they wake up every few seconds and flush whatever has been sitting for more than thirty seconds. If too many dirty pages pile up, say more than ten percent of memory, writing starts earlier, and at twenty percent the writing process is slowed down. These thresholds are visible in the vm dirty settings.\n\nBut this raises a question: what if the power goes out before the data gets written out? It will be lost. That is why programs that care about reliability call a sync: fsync tells the kernel to write the file and wait for confirmation from the device itself. Databases call it at every transaction commit. Extra protection comes from the file system journal: changes are first written to the journal, and after a crash the structure is restored. But the journal protects metadata, while the contents are protected only by your fsync. This is one of the most common causes of data loss.\n\nBelow the file system lies the block layer. It accepts requests in the form of a bio structure, which means "write these pages to these sectors", merges neighboring requests and hands them to the driver. The modern block layer is multi-queue: every core has its own software queue so that cores don't fight over a lock, and then requests are distributed across the device's hardware queues. NVMe supports tens of thousands of queues, and that is what unlocks its speed. The old single shared queue was removed from the kernel back in version five point zero.\n\nBetween the queues stands the I/O scheduler. It comes in four flavors. The do-nothing one, called none, suits fast NVMe drives: there is nothing to sort, and extra work only slows things down. The mq-deadline scheduler sorts requests and guarantees a deadline; it is usually used for spinning disks. Kyber watches latency. And BFQ divides bandwidth fairly between processes and is good for desktops. The current choice lives in the scheduler file under sys, block, your device, queue, and it can be changed on the fly.\n\nNow let's go above the block layer but below the file system. Between them lies the storage layer. A disk is divided into partitions, and partitions can be assembled into more flexible constructions. LVM combines partitions into a common pool and cuts logical volumes out of it, which are easy to grow. RAID, also known as md, combines several disks into an array: a mirror survives the failure of a disk, while levels four, five and six store parity. Disk encryption, that is dm-crypt, works here too. All of them are built on a single mechanism called device mapper.\n\nFinally, the most down-to-earth topic: disks die, and data must be protected. RAID is not a backup: it saves you from a disk breaking, but not from a deleted file or ransomware. The three-two-one rule calls for three copies on two different media, one of them offsite. Rsync copies only the changes, and a retention policy decides how many daily and weekly copies to keep. And a disk's SMART attributes warn about an approaching failure: a growing count of reallocated sectors is a reason to replace the disk before disaster strikes.
