#CHAPTER 2 | The Command Line: Shell, Pipelines and Scripts
Diving into Unix. Chapter two. The Command Line: Shell, Pipelines and Scripts. You type a line, press enter, and a moment later you get a result. What happens between those two events? The shell reads the line, splits it into words, substitutes values, starts a program and waits for the answer. Today we will walk through this path step by step: how a line turns into a process, how redirections and pipelines work, how a program reports success, and how to put all of it into a script.\n\nThe first thing to understand: the shell is an ordinary program, not a part of the kernel. Bash, zsh, dash are just executable files that read lines in a loop. When it gets a line, the shell splits it into words at spaces, respecting quotes. Then it expands substitutions: an asterisk turns into a list of matching files, a dollar sign with a name turns into the value of a variable. Only after that do we get a finished array of arguments: element zero is the program name, the rest are its parameters. The kernel plays no part in this.\n\nNow the launch. The shell calls fork: the kernel makes an exact copy of the current process, and now there are two, a parent and a child. The child calls exec, and the kernel replaces its contents with a new program: the process ID stays the same, but the code and data are different. Meanwhile the parent calls wait and sleeps until the child finishes. This pair of calls, fork and exec, is the foundation of starting any program on Linux. We will talk about it in detail in the chapter on processes.\n\nEvery program has three standard streams, and each has its own descriptor number. Zero is standard input, where the program reads from by default. One is standard output, where it writes its result. Two is the error stream, where messages about problems go. If you change nothing, all three are connected to the terminal, which, as we remember, is also a file. Thanks to this, a program does not know where its data came from or where its answer will go: it simply reads from zero and writes to one.\n\nRedirection is replacing what a descriptor points to. The greater-than sign sends output to a file, a double sign appends to the end, and the less-than sign takes input from a file. The shell does this in the child, between fork and exec, with the dup2 call, and the program does not even find out. The notation two, greater-than, ampersand, one means: send the error stream to wherever the output currently points. Order matters: if you swap the redirection to a file and the merging of the streams, the result will be different.\n\nA pipeline connects programs through a pipe. This is a buffer inside the kernel, usually sixty-four kilobytes: one program writes into one end, another reads from the other. All the programs in a pipeline start at the same time. If the buffer is full, the writer goes to sleep; if it is empty, the reader goes to sleep. This way the kernel balances the speeds on its own, and the data does not have to be stored on disk in full. When the writer closes its end, the reader gets end of file and finishes. That is exactly why pipelines are so economical with memory.\n\nA program reports its result with an exit code: zero means success, any other number means an error. The shell stores it in the variable called question mark. Double ampersand runs the next command only if the previous one succeeded, and double vertical bar only if it did not. But in a pipeline, by default only the code of the last command is visible, and a failure at the start is easy to miss. That is why scripts turn on the pipefail mode, so that any failed stage makes the whole pipeline fail.\n\nEnvironment variables are another way to pass data to a child process. An ordinary shell variable lives only inside the shell, but after the export command it goes into the environment, which the kernel copies to the child at launch. The most important variable is PATH, the list of directories where the shell looks for a program when you type only its name. The search goes from left to right until the first match. Remember the reverse too: the child gets a copy, so changes made there do not affect the parent.\n\nThe strength of the command line is in small filters that read text line by line. Grep selects lines, sort orders them, uniq with the dash c option counts repeats, sed replaces, and awk picks out and sums columns. Each does one thing, and the pipeline joins them into a solution to the task. For example: from a web server log, take the lines with an error, pull out the addresses, sort them, count the repeats and show the ten most frequent. One line replaces a small program, and the data flows through a pipe, not through the disk.\n\nWhen commands repeat, you write them into a script. The first line starts with a hash and an exclamation mark, followed by the path to the interpreter: the kernel itself reads this line at launch and substitutes the interpreter. The file needs the execute permission. A good script starts with setup: stop at the first error, reject undeclared variables, and take pipeline errors into account. And always put variables in quotes: otherwise a space in a file name will split it into two words, and an empty variable will simply vanish.
