#CHAPTER 1 | The file system: tree, inode and links
Diving into Unix. Chapter one. The file system: tree, inode and links. This book goes from the top down: from the familiar terminal to the kernel itself. At the top are programs and the command line, below them system calls, then the kernel, and under it the hardware we've already studied in Computer Architecture. The first stop is files, because in Linux almost everything is built like a file. We'll look at the single tree, the inode, names and links, mounting, and at the end we'll peek into the kernel and see how it finds a file by its path.\n\nLet's start with the tree. Linux has no drive letters: there is one root, written as a slash, and everything else grows out of it. In etc live the settings, in home the home directories, in var the changing data such as logs, and in usr the programs and libraries. Need another disk or a flash drive? It doesn't get a letter of its own; it's attached to some directory and becomes a branch of the common tree. A path is always read from the root to a leaf, and every slash means a step deeper.\n\nThis tree also has places that don't exist on disk. The proc directory shows processes and kernel state, the sys directory shows devices and parameters, and the dev directory shows devices as files. When you read such files, you are really asking the kernel questions, and it answers on the fly. That's why people say that in Linux everything is a file: the same calls, open, read, write and close, work for a document, for a terminal and for a network socket. This is one of the main ideas the system owes its simplicity to.\n\nNow, what a file really is. The name of a file isn't stored in it. A file is an inode: a record on disk with the owner, permissions, size, modification times and pointers to the blocks with the data. The name lives in a directory: a directory is also a file, and it holds a table of pairs, a name and an inode number. So renaming doesn't touch the data; it only changes a row in the table. The ls command with the dash i option shows inode numbers, and the stat command shows the whole record.\n\nThis design immediately implies that one inode can have several names. That's a hard link: a second row in a directory table pointing to the same inode. The inode holds a count of names, and the data is freed only when that count drops to zero. A symbolic link works differently: it's a separate small file with a path to the target written inside. Delete the target, and the link is left hanging in the air. Hard links live within a single file system, while symbolic links can point anywhere.\n\nThere's a second counter that people forget. When a program opens a file, the kernel creates an open-file record, and the program gets a small number, a file descriptor, which is simply an index into its own table. As long as the descriptor is open, the inode stays alive, even if all the names have been deleted. That's how it happens that you erased a giant log, but the disk space didn't come back: a program is still holding the file. You need to close the descriptor or restart the program. We'll need those same descriptors in the chapter about the shell.\n\nSo how does a new disk get into the tree? This is called mounting. The kernel keeps a table of mount points: this partition is attached here, and that in-memory file system over there. As you walk along a path, the kernel looks for the longest matching mount point and moves into another file system in such a way that you don't notice. Permanent mounts are described by the etc fstab file, and the current picture is shown by the findmnt command. A disk can be unmounted only if nobody is using it.\n\nWhat kinds of file systems are there? The classics are ext4 and XFS, and they keep a journal: first they record in a special area what they're about to do, then they do it. If the power goes out halfway, at startup the kernel replays or rolls back the write using the journal. Btrfs and its relatives take a different path, copy-on-write: new data is written to free space, and then a pointer is switched in a single move. The old version stays intact, which is why snapshots are cheap. In kernel version seven, XFS even learned to heal itself on the fly.\n\nNow about space. A disk is divided into blocks, usually four kilobytes each, and a file takes a whole number of blocks. A one-byte file still eats a whole block, and on the tail of every file about half a block is lost on average. Besides space, the number of inodes on a disk is limited too: they are created in advance. Millions of tiny files will exhaust the inodes before the space, and then the system will say there's no space left, even though the df command shows free gigabytes. Check both numbers: df with the dash h option, and with the dash i option.\n\nOne main question remains: how does the kernel find a file by its path? For that it has a layer called the virtual file system. It breaks the path into pieces and looks up a directory entry for each one, and it keeps the entries it found in a cache so it doesn't go to disk again. Then it calls the code of the specific file system, be it ext4 or a network one. In the end you get a descriptor. The four objects, the superblock, the inode, the directory entry and the open file, we'll examine in detail in chapter ten.
