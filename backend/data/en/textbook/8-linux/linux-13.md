#SECTION Isolation and the kernel
#CHAPTER 13 | Containers: namespaces and cgroups
Diving into Unix. Chapter thirteen. Containers: namespaces and cgroups. The word container sounds as if the kernel had such an entity inside. In fact it doesn't. A container is an ordinary process, or several, whose view and appetite the kernel has limited: it sees only its own processes, its own files and its own network, and it cannot take more than a set amount of memory and processor time. We have already covered everything needed for this piece by piece, and now we will put the picture together: namespaces, control groups, layered filesystems and protection.\n\nLet's start with how it differs from a virtual machine. A virtual machine runs a whole guest system with its own kernel on top of a hypervisor. A container uses the host's shared kernel, and the isolation is built from the kernel's own mechanisms. That is why a container starts in a fraction of a second and costs almost nothing in memory, but its protection is weaker too: a bug in the kernel affects everyone. The main idea of isolation is the namespace: a mechanism that replaces a process's picture of the world. Each namespace is responsible for one type of resource, and a process can be in any combination of them.\n\nThere are eight kinds of namespaces. Mount, which is its own filesystem tree. Process IDs, which are its own numbers. Network, which means its own interfaces and ports. Then the host and domain name, inter-process communication, users, control groups and time. You can create them with the flags of the clone call or with the unshare call, and the utility of the same name runs a program in a new namespace right from the shell. The setns call lets you enter someone else's. The list of a process's namespaces is visible in the proc directory, under its number, in the ns subdirectory.\n\nLet's try it on the example of process IDs. In a new namespace the first process gets number one, as if it were the only one on the machine. It sees nothing outside: the ps command shows only its descendants. But on the host this same process has a completely different number, say twenty-three thousand. So one task carries two names in two worlds. The process with number one inside is responsible for adopting orphans and reaping zombies, which is why containers often include a tiny init program; otherwise zombies pile up.\n\nNow files. The mount namespace gives a process its own table of mount points. The container's program replaces the root in it with the pivot root call, and then the host's real root filesystem disappears from view, and the process sees the image directory as slash. In addition, proc, dev and tmp are mounted, and needed directories from the host can be attached as volumes. The old chroot trick, which changes only the way paths look, is not enough for isolation, because there are known ways out of it, while pivot root together with a mount namespace closes them.\n\nThe network is isolated too. In a new network namespace there is not a single interface except loopback. To give the container connectivity, a pair of virtual interfaces, veth, is created: one end stays with the host and the other is moved inside. The host end is plugged into a bridge, and address translation is set up on the host. To publish a port, a netfilter rule redirects incoming connections from the host's port to the container's address. So when you write publish port eight thousand to internal eighty, the system creates exactly such a rule.\n\nThe user namespace solves an unpleasant problem: root inside a container must not be root outside. The kernel lets you map a range of numbers: for example, inside zero corresponds to outside one hundred thousand. Inside, the process sees itself as the superuser and can mount and change owners, while on the host it is an ordinary unprivileged user. This is how rootless containers work, for example in Podman. Breaking out of such a container gives no power over the host, because you can only escape into an account that can do almost nothing.\n\nNow resources. Namespaces limit visibility, while version two control groups limit consumption. It is a single directory tree in a special filesystem: in each group, files control different resources. The memory limit is set in the memory max file, and when it is exceeded, the out-of-memory killer fires, but only inside the group. The cpu max file sets a time quota: for example, fifty thousand microseconds out of every hundred thousand is half a core. There is also a weight for fair sharing, a limit on the number of processes, and disk limits.\n\nWhere does a container's filesystem come from? From an image, and it consists of layers, each layer being a set of changes. The overlay filesystem stacks the layers into a single view: the lower ones are read-only, the top one is writable. When a container changes a file from a lower layer, it is first copied to the top layer, and further edits happen there. A deleted file is recorded as a marker, a whiteout. Thanks to this, a hundred containers from one image share one set of layers on disk, and each has only its own thin writable addition.\n\nAnd finally, protection. Since the kernel is shared, everything unneeded must be taken away from the process: most capabilities are dropped, and a seccomp filter forbids dozens of dangerous system calls. On top of that, SELinux or AppArmor work. But remember that this is not a wall, like with a virtual machine, so for untrusted code there are stricter options: micro virtual machines and sandboxes with their own kernel in user space. All of this is launched by a runtime that reads a standard description, and above it stand Docker, Podman and Kubernetes with health checks.
