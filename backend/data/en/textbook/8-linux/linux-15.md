#CHAPTER 15 | Inter-process communication: pipes, memory, and sockets
Diving into Unix. Chapter fifteen. Inter-process communication: pipes, memory, and sockets. Every process lives in its own address space, and that is a good thing: someone else's bug will not corrupt your memory. But real systems are made of many processes, and they need to talk to each other. There are several ways, and each one is a trade-off. Byte streams: pipes and sockets. Shared memory: the fastest, but you have to synchronize it yourself. Message queues, signals, and file locks. When choosing, ask yourself: how much data, in which direction does it flow, are the processes related, and what matters more, speed or simplicity.\n\nThe oldest way is the anonymous pipe. The pipe call returns two descriptors: you write into one and read from the other. Inside the kernel it is a ring buffer of about sixty-four kilobytes. If the buffer is empty, the reader goes to sleep; if it is full, the writer goes to sleep, and that is natural rate control. When all write ends are closed, the reader gets end of file. When all read ends are closed, the writer gets a SIGPIPE signal and an error. Writes no larger than PIPE_BUF, usually four kilobytes, are atomic: nobody else's data will get wedged into them.\n\nAn anonymous pipe connects only relatives, because descriptors are passed along at fork. A named pipe, a FIFO, removes that limitation: the mkfifo command creates a special file of type p in the filesystem, and any process with permission can open it by name. The mechanism is the same: a buffer in the kernel, not a single byte on disk. Opening blocks until someone is at the other end, so the reader and the writer meet at that point. Named pipes are good for simple links between scripts and services.\n\nWhen you need two-way exchange, you reach for Unix domain sockets. The socketpair call gives you two connected ends at once, and a server's address is either a path in the filesystem or a name in the abstract namespace. A socket can work as a stream or as datagrams with message boundaries. The main advantage is that you can pass open descriptors over it: you send a file or a connection, and the receiver gets its own descriptor for the same open file description. The kernel also tells you which process connected. That is why Docker, systemd, and graphical servers run on such sockets.\n\nIf you need to move a lot of data, copying through the kernel becomes the bottleneck. Then processes map the same memory. The mmap call with the shared flag exposes a common file or an anonymous region; object names live in the dev shm directory, which is a filesystem in memory. There is just one physical page, and in the page tables of the two processes two entries point to it. There is no copying at all, and the exchange runs at memory speed. But the kernel no longer enforces order: who writes, who reads, and when the data is ready are for you to decide.\n\nThis is why shared memory needs synchronization. The foundation is the futex. The fast path lies entirely in user space: an atomic operation on a memory word. When the lock is free, there is no system call. The kernel gets involved only when there is contention: the futex puts the process to sleep on that word and wakes it on a signal. Mutexes and semaphores of the pthread library are built on futexes; for shared memory they need the process-shared attribute. For files there are advisory locks: flock for the whole file and fcntl for a byte range.\n\nThere are message queues too. The POSIX version is opened with the mq_open call: messages have boundaries and priorities, and the reader gets exactly what was sent. The old System V queues, along with semaphores and memory segments of the same family, still work, but they are rarely chosen in new code. A queue is valuable when you need message boundaries without parsing a stream, and different priorities. If messages are long and frequent, it is simpler to use a datagram socket or shared memory with a ring buffer.\n\nSignals are a separate kind of communication, but their capabilities are modest: just a number and a little auxiliary data. A signal handler interrupts the program at any point, so inside it you may call only async-signal-safe functions, for example write a byte into a pipe. Hence the well-known trick: the handler writes to a pipe, and the main loop reads from it along with the other descriptors. The modern options are signalfd, a descriptor for signals, and pidfd, a descriptor for a process: both fit into an ordinary event-wait loop.\n\nIn real systems, processes connect in a client and server pattern. A service creates a socket, hangs it in the filesystem, and clients connect and send requests. The permissions on the socket file decide who can connect; the kernel adds information about the sender to the connection. On top of such a socket the D-Bus bus is built: graphical environments, the network manager, and the logging service use it. That is why one of the main problems is agreeing on a protocol: message format, versions, errors, and timeouts, so that a hung server does not hang its clients.\n\nLet's sum up. You need a simple stream between relatives: a pipe. You need an address by name: a named pipe or a Unix domain socket. You need descriptor passing or two-way exchange: a socket. You need maximum speed: shared memory with a futex. You need boundaries and priorities: a message queue. Signals are fine for notification, but not for data. Typical traps: unclosed pipe ends that make a reader wait forever, races in shared memory, hung clients, and forgotten zombie processes.
