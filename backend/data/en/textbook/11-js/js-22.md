#CHAPTER 22 | Inside the Browser: Engine, Rendering and the Event Loop
Modern Frontend. Chapter 22. Inside the Browser: Engine, Rendering and the Event Loop. So far we have studied the language by itself, and now we move to the environment where it lives most often. A browser is a huge program: it downloads pages, parses markup, computes styles, paints pixels, handles input and runs JavaScript. To write fast and predictable interfaces, you need to understand what happens between your line of code and the picture on the screen. In this chapter we will walk the path from an address to pixels, and take a close look at the event loop, which decides when your code runs and when the screen updates.\n\nA modern browser is not one process but a whole family. The main process is responsible for the window, the tabs and the address bar. Each page runs in a separate renderer process, so a hung tab does not bring down the others. The network, graphics and plugins live in their own processes. Site isolation places pages of different sites in different processes, so a vulnerability in one does not give access to the data of another. Inside the renderer process, the main thread does a great deal: it parses markup, runs scripts, computes styles and layout, and prepares paint commands. This means a heavy script blocks both repainting and the reaction to a click.\n\nJavaScript is run by an engine. Chrome's V8 first turns code into bytecode with the Ignition interpreter, then compiles frequently called functions with fast compilers, and the hottest ones with the optimizing compiler called TurboFan. Optimization relies on guesses: if a function always received numbers, code for numbers will be generated, and when an unexpected type shows up, deoptimization happens. Objects with the same order of fields get a shared hidden shape, and access to a field becomes cheap. So it is useful to create objects in the same way, not to add fields in different orders, and not to change the types of values. The garbage collector splits memory into young and old generations and works mostly in parallel.\n\nNow the path of a page. The browser finds the server address, sets up a secure connection, gets the response, and starts parsing bytes into tokens, and tokens into a tree of nodes, the DOM. In parallel, the preload scanner looks through the markup ahead of time and requests images, styles and scripts early. A regular script stops parsing: it has to be downloaded and run, because it may change the document. The defer and async attributes solve the problem: a deferred script runs after parsing, in order, and an async script runs as soon as it has downloaded. A module script behaves like a deferred one. Styles are collected into a parallel tree, the CSSOM, and painting will not begin until it is ready.\n\nFrom the DOM and the CSSOM the render tree is built: only visible nodes get into it, so, for example, an element with display none will not be there. Then come the stages. Style calculation determines the final values for each element. Layout computes sizes and positions. Paint turns elements into a list of drawing commands, and compositing assembles the layers on the graphics processor into the final picture. Changing a color affects only paint, changing a width affects layout and paint, while transform and opacity often need just compositing, so those are the best ones to animate. The whole path is called the critical rendering path.\n\nBack to JavaScript. It has one call stack: it holds the frames of running functions, and at any moment only the top one is working. When a function calls another, a new frame is put on the stack, and on return it is removed. If there are too many calls, for example with infinite recursion, a stack overflow happens. While the stack is not empty, nothing else can run: not a click, not a timer, not a repaint. That is why a loop of a hundred million iterations freezes the page. Asynchrony does not create parallel execution of code, it only moves its execution to later.\n\nThe event loop is the mechanism that decides what to run next. It has a task queue: timer callbacks, user events, messages from other windows and responses to network requests all land here. The loop takes one task and runs it to the end on the stack, then checks the microtask queue and runs it completely, and after that the browser decides whether the page needs to be repainted. Then comes the next task. Tasks run one at a time and are never interrupted, so inside one task you will never see other code interfering. This simplifies reasoning: there are no races, as in multithreaded programs.\n\nMicrotasks are promise handlers, queueMicrotask calls and mutation observer callbacks. They run right after the current task, until the queue is empty, and a microtask added by a microtask will also run before the next task. That is why an endless chain of microtasks blocks everything else just like an infinite loop. From this follows the famous order: first all the synchronous code, then the microtasks, then the next task, for example a timer with zero delay. If you create a promise inside a timer, its handler will run right after that timer, before the next one.\n\nRepainting is built into the loop. The browser updates the screen at the display's refresh rate, for example sixty times a second, which is about once every sixteen and a half milliseconds. If a task takes longer, the frame is skipped and the user sees stutter. Before painting, the browser calls the requestAnimationFrame callbacks: this is the right place to change an animation, because the calculations are synchronized with frames. For secondary work there is requestIdleCallback, which runs when the browser is free. Tasks longer than fifty milliseconds are called long tasks: they hurt responsiveness, and they are split into pieces, handing control back to the loop through a scheduler.\n\nTimers are not as precise as they seem. A setTimeout call promises to call the function no sooner than the given time, but in fact it goes into the queue and waits until the stack is free. In nested calls the browser adds a minimum delay of four milliseconds, and hidden tabs get timers less often, up to once a second. A setInterval call can accumulate drift, while a recursive setTimeout guarantees a pause between runs. For animations you need not timers but requestAnimationFrame, and for handing control back immediately you need a message channel or a scheduler method. The choice of tool determines how smooth the interface is.\n\nA lot happens outside the stack. Requests, timers, file reads and DOM events are Web APIs: the browser executes them, and your code gets a callback through the queue when the result is ready. For real parallelism there are web workers: separate threads with their own event loop and no access to the DOM. You talk to them with messages through postMessage, and the data is copied by the structured clone algorithm, while large buffers can be transferred without copying or shared through shared memory. This way heavy computations leave the main thread, and the interface stays smooth.\n\nHow do you look at all this? In the developer tools, the Performance tab shows a flame chart: the stack, tasks, layouts and paints. Long tasks are marked with a red corner. The Rendering tab highlights repainted areas, the Memory tab takes heap snapshots and looks for leaks, and Coverage shows unused code. In code there are marks and measurements, the performance mark and performance measure functions, and the performance observer receives long tasks and metrics. You should measure on real devices and before optimizing, otherwise you will improve something that is not the slow part.\n\nLet us sum up. The browser is multiprocess, and in the renderer's main thread sit JavaScript, styles, layout and paint. V8 optimizes code by guessing, so it is better not to change the shape of objects. A page goes from bytes to the DOM, the CSSOM, the render tree, layout, paint and compositing. The event loop runs tasks one at a time, drains the microtasks after each one, and paints a frame when needed. Long tasks should be split, animations tied to frames, and heavy work handed to workers. In the next chapters we will deal with the DOM itself, the tree of elements, and learn to change it.
