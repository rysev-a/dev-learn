#CHAPTER 33 | Registries: the npm registry, JSR, publishing and supply chain security
Modern Frontend. Chapter 33. Registries: the npm registry, JSR, publishing and supply chain security. When you install a package, the manager goes to a server called a registry. The registry stores metadata: the list of versions, tags, dependencies, checksums. And it stores the code archives themselves. The conversation runs over plain HTTP: a request by package name returns a document describing all versions, and the archive address is taken from that document. Since we are running somebody else's code, understanding the registry and its risks is part of a developer's professional literacy.\n\nThe main public registry is registry dot npmjs dot org. A request by package name returns a document with a versions field, where each version has its manifest, and a dist-tags field. Tags are movable labels: the latest tag points to the version that gets installed by default, and the next tag points to a prerelease. For every version, the dist section gives the archive address and a checksum. For scoped packages the name is encoded, and the archive address is built from the name and the version. Registry copies, mirrors and caches work over the same protocol.\n\nJSR is a newer registry, created by the authors of Deno and compatible with Node through a special layer. Its idea: publish TypeScript source, not built code. The registry itself generates types, documentation, and versions for different environments. Only ES modules are accepted, and only semver. Every package gets a score from a checklist: is there a description, documentation, runtime support, types, build provenance. Publishing from continuous integration is signed without secrets, using certificates. For older packages and for Node, npm is still the foundation.\n\nA company's internal code is published to a private registry. To do that, a scope, for example at company, is bound in the npmrc file to the address of your own registry: all packages with that scope are fetched from there, and everything else from the public one. The access token goes in the same file, but its value is taken from an environment variable so that the secret never lands in the repository. Ready-made options are Verdaccio, GitHub Packages, Artifactory and Nexus. They also cache public packages, which speeds up installs and protects you if a package disappears from the public registry.\n\nPublishing starts with the version: the npm version command bumps the number and creates a commit and a tag. Then npm publish builds an archive from the files listed in the manifest and sends it to the registry. The version has to be new: you can't overwrite what has been published. Prerelease builds are published with the next tag so that they don't become the default version. For public scoped packages you have to explicitly allow public access. Two-factor authentication is required, and even better is publishing from continuous integration with build provenance.\n\nA published version can't be changed. If it has a bug, you release a new one. An outdated version is marked with the deprecate command and a message: the manager will show a warning on install, but won't break the project. Deletion, unpublish, is heavily restricted after the left-pad story, when the disappearance of a tiny package broke thousands of projects: seventy-two hours after publishing, a version can be deleted only if nobody depends on it and it has few downloads. So you can't count on being able to pull a package back; you react to mistakes with new versions.\n\nHow do you make sure the archive you downloaded is exactly the right one? For that, the metadata and the lockfile store an integrity value: an algorithm, a hyphen, and a hash in base64 encoding, for example SHA-512. After downloading, the manager computes the archive's hash and compares. If the values differ, the install is aborted. This protects against the archive being swapped on a mirror or on the network, but not against the author themselves publishing malicious code: a hash confirms that it's the same file, not that the file is safe. That's why other protective measures are needed too.\n\nThe supply chain is the weakest spot of modern development. Typosquatting: a package whose name differs by one letter from a popular one waits for typos. Dependency confusion: an internal package exists only in the private registry, and an attacker publishes a package with the same name and a higher version in the public one. A hijacked author account and a malicious release. Install scripts that run right at installation. Protestware releases, where the author sabotages their own package. Each attack has its own countermeasures, and we'll go through them one by one.\n\nBasic hygiene includes several habits. A lockfile in the repository and installs from it with the ci command, so that a new malicious version doesn't get into your build without your knowing. Disabling install scripts where they aren't needed. Binding internal scopes to your own registry and reserving the names in the public one. A minimum of dependencies: every package adds risk. Vetting new dependencies: age, number of maintainers, activity. Regular audits and automatic update requests that you read rather than blindly accept.\n\nProvenance answers the question of which commit and which build produced the package. When you publish from continuous integration, the registry stores a signed record: the repository, the commit, the workflow. That record is built on Sigstore, and it can be verified. The second tool is the software bill of materials, SBOM: a machine-readable list of all components with versions and licenses, in the CycloneDX or SPDX formats. When a new vulnerability comes out, such a list tells you within minutes whether you are affected and which products to check.\n\nEvery package has a license, and it imposes obligations. Identifiers are standardized in SPDX: MIT, Apache two, BSD, GPL. An expression can be compound: MIT or Apache means you choose one, while "and" requires you to comply with both. A company usually defines a policy: which licenses are acceptable, which are forbidden, which need approval from lawyers. Checking the licenses of the whole dependency tree is automated in continuous integration. A package without a license legally means that you can't use it.\n\nBefore you add a dependency, ask yourself a few questions. Do you need it at all: ten lines of your own code are sometimes more reliable than a package. Who maintains it and for how long, are there fresh releases, how quickly are issues closed. How many dependencies does it have and how big is it. What is the license, and are there types. How many users does it have, and is there an alternative. One good package with a clear API is better than three small ones, each made by one person. The decision to add a dependency is worth recording, so that later you understand why it's here.\n\nLet's sum up. A registry stores metadata and archives; the package document contains versions, tags and checksums. npm is the main registry, and JSR is the new one, oriented toward TypeScript. Private registries are bound by scope in the npmrc file. You publish by semver with tags, and you don't rewrite versions. Integrity confirms that the file is the same, but not that it is safe. Typosquatting, name confusion and malicious scripts are real attacks. The defenses are a lockfile, disabled scripts, provenance, a bill of materials and a license policy.
