Modern Frontend. Chapter 6. Functions, Scope and Closures. In JavaScript, a function is a value just like a number or a string. You can put it in a variable, pass it to another function, return it from a function and store it in an object field. These are called first-class functions, and almost everything is built on them: event handlers in the browser, callbacks, promises, array methods and interface components. In this chapter we will look at how functions are declared, how parameters are passed, where variables live, and why closures, which seem like magic, are really just a consequence of a simple rule about the visibility of names.\n\nThe most familiar way is a function declaration: the keyword function, a name, parameters in parentheses and a body. Such a declaration is hoisted to the top of its scope, so you can call the function earlier than it is written in the file. Another way is a function expression: the function is written to the right of an equals sign and assigned to a variable; it is not hoisted as a whole, and a call before the assignment gives an error. If a function returns nothing with the return keyword, the result is undefined. Notice that return followed by an expression on the next line does not work, because the engine inserts a semicolon right after the word return.\n\nArrow functions are a short notation: parameters, an arrow and an expression. If the body is a single expression, return is not needed and the value is returned implicitly. If you need a block with several statements, you put in curly braces and write return explicitly. A single parameter can go without parentheses, and to return an object literal you wrap it in parentheses, otherwise the curly braces will be taken for the body. The main difference of an arrow is not the syntax: it has no this of its own, and takes it from the environment where it was created. Arrows are ideal for short callbacks, but object methods and constructors are written as regular functions.\n\nParameters in JavaScript are not checked: you can call a function with extra arguments, which are ignored, and missing ones will be undefined. Default values are set with an equals sign right in the parameter list: they are used only when undefined arrives, while null and zero stay as they are. A rest parameter with three dots collects all the extra arguments into a real array, and it replaces the old arguments object. Arguments are passed by value, but for objects the value is a reference, so a function can change a passed array from the inside. This is one of the common causes of unexpected side effects, and pure functions that change nothing are easier to test.\n\nParameters can be destructured, that is, taken apart right in the header: curly braces pull out object fields, square brackets pull out array elements. The technique is very popular for named arguments: instead of five positional parameters, the function takes one object with settings, defaults are set right there, and the order no longer matters. The spread operator with three dots works in a call too: it unpacks an array into separate arguments, so the maximum of an array is computed as Math dot max, three dots, and the array. Copying arrays and objects with the same operator is the basis of the immutable style that modern libraries love.\n\nNow scope. It can be global, function or block. Variables declared with let and const are visible only inside the nearest curly braces, whether that is a condition block, a loop, or just a pair of braces. A var is visible throughout the whole function, and that is its weakness. Before the line of its declaration, let and const are in the temporal dead zone: touching them gives a reference error, even though the engine already knows the name. This is useful: an uninitialized variable no longer quietly returns undefined. Global variables in the browser are fields of the window object, and you should not clutter them: any extra global variable can collide with the code of another script on the page.\n\nThe visibility rule in JavaScript is called lexical: a function looks for names where it is written, not where it is called. Every call has its own environment, a table of variables with a reference to the outer environment. The search goes up the chain: first local names, then the environment where the function was created, then the global one. If the name is not found anywhere, we get a reference error. An inner variable with the same name as an outer one shadows it, and this is a common source of bugs. Remember the picture: an environment is not a stack of frames, as in C, but linked tables that can outlive the call if somebody still refers to them.\n\nThis is exactly why closures work. If a function returns an inner function, the inner one keeps a reference to the environment where it was created and remembers the variables even long after the outer call has finished. In the classic example, a counter factory creates a variable and returns a function that increments it; every call of the factory produces its own independent counter. The variable is not accessible from outside, which means a closure is a way to create private state without classes. In C you had to pass a structure and a function pointer for that; here both data and code are packed into one function. The garbage collector keeps the environment alive as long as at least one function refers to it.\n\nThe classic trap is a closure in a loop. If you declare the loop counter with var, all the functions created inside the loop refer to the same variable, and after the loop it equals the last value: five callbacks will print the same number five times. Let creates a new variable on every iteration, so each function gets its own value. It used to be necessary to wrap the loop body in an immediately invoked function, called an IIFE. Now it is enough to write let, and the rule is simple: in loops, declare variables only with let or const, and closures will behave as expected.\n\nHigher-order functions take or return other functions. The array methods map, filter and reduce take a callback: map transforms every element, filter keeps the suitable ones, and reduce folds the array into a single value, and you give it the starting value of the accumulator. Chains of such calls read like a description of data, not a loop. Composition builds a new function from two. Currying turns a function of two arguments into a chain of functions with one argument each. Partial application remembers some of the arguments in a closure. All these techniques are just functions returning functions, and they made the functional style the norm in modern frontend.\n\nThe keyword this is especially tangled. For a regular function it depends on how it is called: for an object method it is the object itself, and for a plain call in strict mode it is undefined. So if you pull a method out into a variable or pass it as a callback, this is lost. The call and apply methods call a function with a given this, and bind returns a new function with this fixed. Arrow functions take this from the outer environment, and in callbacks inside methods that is exactly what you need. To be safe, people more often pass the needed data as explicit arguments or through a closure, and do not rely on this where they can do without it.\n\nA few more techniques. Recursion is a function calling itself; the stack depth is finite, and thousands of nested calls will lead to an overflow error, so a deep traversal is rewritten as a loop. Memoization saves results in an object inside a closure, and a repeated call with the same arguments returns the ready value. An immediately invoked expression used to create a private scope before modules appeared. Functions in JavaScript are objects too: they have a name and a count of declared parameters. We will cover generators and iterators in the chapter on classes, and now let us sum up.\n\nLet us sum up. Functions are values: they are passed, returned and stored. Arrows are short and take this from the environment. Parameters can have defaults, be gathered by rest and be destructured. Scope is block-level for let and const and lexical: names are looked up where the function is written. A closure is a function together with the environment where it was created; counters, memoization, partial application and private data are built on it. In loops, use let, and for array methods, use callbacks. In the next chapter we will deal with objects, arrays and collections: Map, Set and immutable updates.
