#CHAPTER 12 | Libraries and techniques of FP: Ramda, lodash/fp, Immer, RxJS, Maybe and Either, lenses
Modern Frontend. Chapter 12. Libraries and techniques of functional programming: Ramda, lodash FP, Immer, RxJS, Maybe and Either, lenses. We covered the basics in the previous chapter, and now it is handy to look at what grew out of them in the ecosystem. JavaScript has a great many libraries for functional style, and they have different goals: sets of utilities, immutable updates, sum types, event streams. We will go through their ideas and write scaled-down versions, so that you understand what is hidden under the hood. Then no library is magic anymore, and choosing between them becomes a conscious decision.\n\nLodash is the best-known utility library: grouping, deep copying, access by path, sorting by several keys, debounce. Much of it is already built into the language, so today people take it selectively, importing individual functions. The lodash FP variant redesigns the same functions in a functional style: they are curried, they do not change their arguments, and the data comes as the last parameter, so the functions fit together in a chain. Two conventions are worth knowing. First: the iteratee goes before the collection. Second: the functions have fixed arity, so map does not pass extra arguments, as in the well-known trap with parseInt.\n\nRamda is a library designed to be functional from the very first line. All functions are curried, the data always comes last, and none of them changes anything. Pipe and compose glue steps together, map works not only on arrays but also on objects and functions, assoc and assocPath return a copy with a changed field, path pulls out a value by path, and evolve transforms fields. There is also a placeholder that lets you skip an argument in partial application. The code comes out short and point-free, and that is both a strength and a trap: for a newcomer, a chain of ten Ramda functions is harder to read than a single loop. The value of Ramda lies in its consistency and in the well-thought-out order of arguments.\n\nImmer solves the most unpleasant part of immutable data, updating nested structures. You call produce and pass it the original state and a function that receives a draft and simply changes it in the familiar way: assigns fields, calls push. Under the hood the draft is a proxy that records the changes, and then the library builds the new state, copying only the touched nodes while the rest stays shared. If nothing changed, the original reference comes back. Immer can freeze the result and report patches, that is, a list of changes that can be sent to a server or applied in reverse. It is built into Redux Toolkit and made immutable state pleasant to work with.\n\nSome data structures are immutable by their very nature, and they are called persistent. A new version of a list or a map keeps the shared parts of the old one and copies only the path to the changed cell. The classic example is a tree with a high branching factor, where appending to the end costs almost constant time. The Immutable.js library implements such structures, but it has its own set of methods, and you have to convert data back and forth. That is why plain objects and Immer are chosen more often today. But the idea matters: immutable does not mean «always copy everything», it means «share what did not change between versions».\n\nSum types are also found in libraries. Fp-ts, purify-ts and neverthrow provide Maybe, Either and Result with a rich set of operations. Effect-TS goes further: it is a whole system for describing programs with errors, dependencies and asynchrony, where the type tells you what can go wrong. The main idea is the same everywhere: an operation that may fail returns a value instead of throwing an exception, and the compiler makes you handle both outcomes. For checks that must collect all the errors at once instead of stopping at the first one, people use validation, a variant of Either that accumulates errors in a list.\n\nA lens is a pair of a getter and a setter focused on a part of a structure. The view operation reads the part, set returns a new structure with the part replaced, and over applies a function to the part. The main benefit is composition: a lens on the address field and a lens on the city field glue together into a lens on the city inside the address, and you can use it just like a simple one. Ramda offers lensProp, lensIndex and lensPath. Lenses obey laws, for example: if you write into a part what you have just read from it, the structure does not change. More general optics, prisms and traversals, work with variants and with many parts at once.\n\nWe have already seen the problem of intermediate arrays: a chain of map and filter creates a new array at every step. A transducer solves this differently. Instead of transforming a collection, it transforms the reducer itself: a map transducer takes a reducer and returns a reducer that applies a function before accumulating. Such transformations glue together with ordinary composition and are applied in a single pass to any collection: an array, a string, a stream. The transduce function takes a transformation, a reducer and an initial value. Ramda has ready-made transducers. The idea is worth understanding, although in practice iterators with lazy methods are enough.\n\nRxJS is a reactive programming library. Its main abstraction is the observable: a stream of values over time that you subscribe to and can unsubscribe from. Unlike a promise, it emits many values, can be infinite, and can be cancelled. Operators transform streams: map, filter, scan accumulates state, debounceTime waits for a pause, distinctUntilChanged drops repeats. A subject is a stream into which you can push values by hand, and any subscriber will receive them. Streams are easy to get from events: mouse clicks, typing, a web socket. A subscription must be closed, or memory will leak.\n\nThe main strength of RxJS is combining streams. For every value of the outer stream, switchMap starts an inner one and discards the previous one: this is the ideal model for search as you type, when the answer to the old query is no longer needed. MergeMap runs all the inner streams in parallel, concatMap runs them one after another, and exhaustMap ignores new ones until the old one has finished. CombineLatest joins the latest values of several streams, and merge mixes them into one. The retry and catchError operators handle errors, and takeUntil stops a stream on a signal. It is a powerful language, but the entry threshold is high, so use it where you really have streams of events.\n\nEffects can also be described as data. A Task is a lazy promise: it is a function that starts nothing until it is asked to. You can map it, chain it and combine it, and execution happens in a single place at the edge of the program. This gives repeatability and easy tests: instead of mocks, you check the description. A Reader describes dependencies: a function receives an environment, and the environment is supplied at the edge. Such techniques underlie Effect-TS and similar systems. In ordinary code a simple idea is enough: functions return a description of an action, and the shell carries it out.\n\nWhen should you apply all this? Functional style is not free. Copying data puts load on the garbage collector, thousands of tiny functions are harder to profile, and point-free chains are hard for a team without experience to read. A sensible path looks like this. Keep a pure core and a thin shell. For state, use Immer or reducers. For collections, the built-in methods are enough, and you reach for a library when it makes the code shorter. Use sum types at the boundaries, where explicit error handling matters. Reactive streams are for events. The rest is a matter of taste. What matters most is the habit of separating computation from effects, which pays off in any style.\n\nLet's sum up. Lodash FP and Ramda give curried functions with the data last, Immer lets you change a draft and get an immutable result, and persistent structures share the unchanged parts between versions. Maybe, Either and validation turn errors into data, lenses assemble access to nested fields, and transducers join transformations without intermediate arrays. RxJS describes event streams and their combinations, while Task and Reader describe effects and dependencies. Apply them where they simplify the code.
