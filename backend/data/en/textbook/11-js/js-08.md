#CHAPTER 8 | Classes, Prototypes and Iterators
Modern Frontend. Chapter 8. Classes, Prototypes and Iterators. So far we have created objects with literals, but now we need objects with shared behavior: users, shopping carts, connections, components. JavaScript has classes for this, and they look familiar if you have written in Python or Java. But underneath them lies a model of their own: prototypes. Understanding this model helps you see where methods come from, how inheritance works, and why "this" sometimes gets lost. At the end of the chapter we will meet iterators and generators: the protocol on which the for of loop, the spread operator and all the collections of the language are built.\n\nEvery object has a hidden link to another object, its prototype. When you access a field, the engine looks for it in the object itself, and if it does not find it, it follows the link further, up the prototype chain to the very end, where null lies. That is why any ordinary object has a toString method: it is found in the Object prototype object, the common ancestor. You get an object's prototype through Object getPrototypeOf, and you create an object with a given prototype with the Object create function. Writing to a field always goes to the object itself, not to the prototype, so an inherited value can be shadowed.\n\nBefore classes appeared, objects were created with constructor functions. Calling such a function with the new keyword does four things: it creates an empty object, links its prototype to the prototype field of the constructor, calls the function with this object as "this", and returns it. Methods were put into the prototype of the constructor so that they were shared by all instances and not copied into each one. The instanceof operator checks whether the constructor's prototype is in the object's chain. A forgotten new is a common mistake: then "this" turns out to be undefined, and the function either spoils global names or crashes.\n\nThe class keyword is a convenient notation for the same mechanism. Inside a class you write a constructor, which initializes the fields, and methods, which go into the prototype. An instance is created with the new operator, and you cannot call a class without it: you will get an error. The typeof of a class returns "function", because a class really is a constructor function. Unlike a function declaration, a class is not hoisted: it must be declared before use. The body of a class always runs in strict mode. Methods are made non-enumerable so that they do not show up in a loop over properties, and this is one of the differences from working with a prototype by hand.\n\nModern classes can do more. Class fields are declared right in the body: a name, an equals sign and a value, and each instance gets its own copy. Names with a hash sign, for example hash balance, are truly private fields: they cannot be accessed from outside, even through square brackets, and an attempt causes a syntax error. The static keyword creates methods and fields of the class itself, not of its instances, and suits factories and counters. Getters and setters, with the get and set keywords, look like ordinary fields but run code: they are handy for computed properties and for checking values on write.\n\nInheritance is written with the word extends. A child class gets the methods and statics of its parent, can override them, and can call the parent version through the word super. If a child class has its own constructor, it must call super before the first use of "this", otherwise you get a reference error: the object is created by the parent. The prototype chain then consists of the child class prototype, then the parent one, and on up to the base. This is how custom user errors are made: they extend the built-in Error class, set a name and a message, and then instanceof and the call stack work just like for standard errors.\n\nClasses do not remove the problem of "this". If you pull a method out and pass it as a callback, for example an event handler, it loses the object, and accessing a field will fail. There are three solutions. The first is to bind the method in the constructor with the bind method. The second is to declare the method as an arrow field: an arrow remembers the "this" of the instance being created, but you get a copy of the function for every object instead of one shared method. The third is to call the method as part of an expression, for example by wrapping it in an arrow when passing it. In libraries like React, classes have almost been replaced by functions, where there is no "this" at all, but in server code and in browser APIs you will meet it all the time.\n\nInheritance is not always the best way to reuse code. Deep hierarchies are fragile: a change in the parent breaks the descendants. Composition is often better: an object gets abilities by containing other objects or a set of functions. So instead of a class "bird, inherited from an animal that can fly", you create separate functions "can fly" and "can swim" and mix them into the objects that need them. Mixing in is done with Object assign or the spread operator. JavaScript follows the duck approach: what matters is whether a value has the needed methods, not what it inherits from, and the instanceof check is needed less often than in strictly typed languages.\n\nEvery property has a descriptor, a set of flags. The writable flag allows writing, enumerable makes the property visible in loops and in Object keys, and configurable allows deleting and changing it. The Object defineProperty method sets them by hand, and Object getOwnPropertyDescriptors shows them. Object freeze forbids writing and deleting for all fields, Object seal seals the set of properties, and preventExtensions only forbids adding. Properties can also be symbols, unique values created by calling Symbol: they do not conflict with any string names and are needed for the service protocols of the language.\n\nSymbols define protocols. Well-known symbols are built into the language: the iterator symbol defines how a value is iterated in a loop, the toPrimitive symbol controls conversion, and the toStringTag symbol changes the label in the output. A protocol is an agreement about having a method with a special key. If an object has a method under the iterator symbol key, it can be plugged into the for of loop, the spread operator, destructuring, Array from, and the Map and Set constructors. That is exactly why the same loop works for arrays, strings, maps, sets and your own collections, and from the client's point of view they all look the same.\n\nThe iterator protocol is simple. An iterable object has a method with the iterator symbol, which returns an iterator. An iterator is an object with a next method that returns a pair of a value and an end flag: when the done field is true, iteration is over. The for of loop calls next again and again until it gets done. You can write your own iterator by hand, but it is inconvenient: you have to keep state. On the other hand, an iterator is lazy: the next element is computed only on request, so it can even describe an infinite sequence, and the loop can be stopped with the word break. The break itself calls the return method of the iterator to release resources.\n\nGenerators are the most convenient way to write iterators. A function with a star, function star, does not run when called but returns a generator object. Each yield pauses execution and hands a value outward, and the next call of next continues from the same place, keeping the local variables. This is how a tree traversal, Fibonacci numbers or an infinite counter is written in a few lines. The yield star construct delegates the work to another iterable object. Generators also underlie async functions, which we will discuss in the next part, so it is useful to get used to the idea that a function can be stopped and resumed.\n\nLet us sum up. Every object refers to a prototype, and field lookup goes along the chain. A class is a notation for a constructor and a prototype; fields, private names with a hash sign, statics, getters and setters make it convenient. Inheritance is extends and super, but composition is often more reliable. Descriptors control writing and enumeration, symbols are needed for protocols, and iterators, defined by the iterator symbol, feed the for of loop and the spread operator. Generators with yield write iterators briefly and lazily. In the following chapters we will talk about modules and errors, and then about asynchrony: promises and async await.
