#CHAPTER 37 | Templates and the virtual DOM: the h function, diffing and updating
Modern Frontend. Chapter 37. Templates and the virtual DOM: the h function, diffing and updating. The reactivity from the previous chapter tells us when to update the interface. Now we have to decide how. You can change nodes by hand, or you can describe the desired result as a whole and let the framework find the difference. That is what the virtual DOM is for: a tree of lightweight objects that describe elements. Every state produces a new tree, the framework compares it with the old one, and applies only the changes to the real DOM. This is the declarative approach: you write what should be, not how to get there.\n\nA node description is just an object with a type, props and children. The h function, short for hyperscript, creates such objects: the element type, a props object, and the children. Children are normalized: nested arrays are flattened, nulls and booleans are dropped, and strings and numbers become text nodes. The key is pulled out of the props separately. JSX is just a convenient notation: a transpiler turns angle brackets into calls to h. Virtual nodes are cheap to create and to compare, because they are plain objects, not heavy browser elements.\n\nThe first display is the render. The function takes a virtual node and builds a real one: it creates an element by its type, sets attributes, subscribes the event handlers from props that start with "on", and recursively creates the children. For text nodes it creates a text node. On the server side, the same tree is turned into a markup string: names and values are escaped, and void elements have no closing tag. One description, two ways of output, and this simplicity is the main thing the virtual DOM gives you, besides speed.\n\nNow the interesting part: what to do when the state has changed and we have a new tree. The diffing algorithm walks both trees from the top down. No old node: create. No new node: remove. Different type: replace it whole, together with its children, since digging inside makes no sense. Same type: keep the same element, update the changed props, and move on to the children. Text: replace the content. The result is a list of patches, lightweight instructions like replace, update a prop, remove. Applying the patches is a separate step, so the diffing can be tested without a browser.\n\nProps are compared by keys. A key that is gone must be removed, and a key with a new value must be set. There are some subtleties. A handler prop starting with "on" has to be unsubscribed from the old function and subscribed to the new one, otherwise listeners pile up. Class and style need normalization: a class can be a string, an array or an object, and a style is an object with names in camel case, which are turned into kebab case. Boolean attributes like disabled are either present or absent. All of this hides inside the function that applies props.\n\nThe simplest way to compare lists of children is by index: the first against the old first, the second against the second. For static trees that is enough. But imagine a list of five items with a new one inserted at the start. By index, all five items end up "changed": each of them gets the content of its neighbor. That is extra work, and worse, state gets lost: if the user typed text into an element, it stays in place while the data shifts. To tell list items apart, we need something that identifies them regardless of position.\n\nA key is a stable identifier of an item in a list, for example a record number from the database. It lets us match items by meaning. The algorithm builds a map of the old children by key. For each new child it looks up the old one by key and updates it, and if there is none, it creates one. Old children left without a pair are removed. Order is fixed with moves. Thanks to this, an insertion at the start gives one insertion instead of five updates, and the state of the items is preserved. A key must be unique among siblings and must not be the index, otherwise the whole point is lost.\n\nMoving elements is expensive, so we want to move as few as possible. Say the old order was A, B, C, D, and the new one is C, A, B, D. We can move C to the front, and the rest stay where they are. Mathematically, this is the longest increasing subsequence problem: find the largest set of elements that follow in the same order in both the old and the new list. They stay, and all the others are moved. This algorithm is used by Vue 3 and Inferno, while React uses a simpler rule based on the index of the last placed element.\n\nA component is a function that takes props and returns a virtual node. The node type can be not only a string but also a function: during render and diffing it is called, and its result is handled like an ordinary subtree. Props are passed as they are, and children go in a special field. Components can be nested and reused. To skip unnecessary work, they are wrapped in memo: if the props are shallowly equal to the previous ones, the result is taken from the cache. State inside a component is kept by hooks, which we'll talk about in the next chapter, together with the lifecycle.\n\nPatches are applied to the real DOM in a strict order. Each patch is addressed by a path: child indices from the root. A simple safety rule is that child removals go from the larger index to the smaller one, so the indices of the rest don't shift. Insertions and moves come after removals. Updating props doesn't affect the structure and is safe at any moment. The browser repaints the page once after the whole batch of changes, so grouping operations into a single synchronous block is cheap. Insertions into the document are best collected in a fragment and added all at once.\n\nThe virtual DOM is not the only way. At build time, Svelte turns a template into code that directly updates the right nodes when a particular variable changes. Solid builds the DOM once, and after that targeted effects on signals update only the nodes that depend on the changed values: components run once. The upside is no cost for diffing trees. The downside is more complex compilers and a more complex mental model. The virtual DOM stays simple and universal, while targeted updates win in very dynamic interfaces. The right choice depends on the task, not on fashion.\n\nThe virtual DOM is not "faster" than working with the real one by hand: it adds the cost of diffing. The gain is that it saves you from needless changes and lets you write declaratively. In practice the bottlenecks are elsewhere: components that re-render for no reason, huge lists without virtualization, expensive computations inside render. What helps against them is memoization, keys, splitting into small components, and moving heavy work into computed values. Measure with a profiler instead of guessing: often the problem isn't in the tree diffing at all.\n\nLet's sum up. The virtual DOM is a tree of lightweight descriptions of the interface. The h function creates nodes and normalizes children. Render builds the real DOM or a markup string. Diffing produces a list of patches: create, replace, update props, remove. Props are compared by keys, and handlers are resubscribed. Children without keys are compared by index, and with keys, by meaning, with a minimum of moves thanks to the longest increasing subsequence. Components are functions that return nodes. Svelte and Solid show that there are other paths too. In the next chapter we'll put together components and a router.
