#CHAPTER 2 | Node.js and io.js: the fork that changed open source
Modern Frontend. Chapter 2. Node.js and io.js: the fork that changed open source. In the previous chapter the language stayed locked inside the browser. This chapter is about how it got out onto the server, and how a quarrel around that server project became one of the best-known and most instructive examples of a revolution in the world of open source. We will look at why Node.js was needed, how the npm ecosystem grew, why in twenty fourteen developers split off and created io.js, how it all ended, and what became of the creator of Node.js afterwards. It is a story about people and money no less than about technology.\n\nIt all started with pain. In two thousand nine Ryan Dahl, an independent developer, was trying to build a file upload progress bar on the server, so the user could see how far along it was. Classic servers like Apache created a separate thread for every connection, and while a thread waited for the disk or the network, it simply slept, taking up memory. Thousands of slow clients ate up resources while the processor sat idle. Dahl noticed that the nginx server coped better: it waits for nothing and reacts to events instead. And he decided to build a platform where non-blocking input and output is the default rule, not a trick for experts.\n\nIn November of two thousand nine, at the JSConf conference in Berlin, Dahl showed Node.js. The idea is simple. The V8 engine runs JavaScript, while a layer written in C plus plus takes over network and file operations and uses the operating system's tools for waiting on events: epoll on Linux and kqueue on the Mac. Later this layer was split out into a separate library called libuv. The program stays single-threaded: it starts an operation, registers a callback and hands control back to the event loop, and when the data is ready, the loop calls the callback. One process serves tens of thousands of connections while waiting on the network, because nothing blocks.\n\nWhy did JavaScript fit such a task in particular? First, it had no libraries with blocking input and output, so there was nothing to fight against: everything was written from scratch, right away in an asynchronous style. Second, the language had closures and functions as values, which means callbacks were short to write. Third, browser developers were already used to the event model: a click, a load, the response to a request. And finally, V8 was the fastest engine in the world. The first Node.js program was a web server in six lines: create a server, pass in a handler function, listen on a port. That is exactly the picture shown at every conference.\n\nA platform without packages is impossible. In twenty ten Isaac Schlueter released the npm package manager, and with it came modules in the CommonJS format: the require function loads a file, and the module exports object hands out whatever is needed. Every package lived in a node_modules folder, and dependencies were installed recursively. It was incredibly convenient, and the ecosystem exploded: hundreds of thousands of packages within a few years, more than for any other language. Later the flip side showed up too: huge trees of tiny dependencies and fragile supply chains. We will talk about that in the chapter on registries.\n\nThe project grew, but its fate depended on a single company. Ryan Dahl was backed by the firm Joyent, which held the trademark rights, hired the lead developers and made the decisions. In twenty twelve Dahl stepped away from development and handed leadership to Schlueter, and later the leaders were TJ Fontaine and others. By twenty fourteen discontent had piled up in the community. Releases had become rare: almost two years passed between versions zero point ten and zero point twelve. The V8 version lagged behind, and new language features that were already appearing did not make it into the platform. Contributors complained that their fixes sat unanswered for weeks and that decisions were made behind closed doors.\n\nIn December of twenty fourteen a group of core developers, among them Fedor Indutny, did what open source calls a fork: they copied the repository and continued development separately under the name io.js. The principles were different: open governance, where decisions are made by a technical committee rather than a company; anyone who has made a notable contribution can get commit rights; fast releases under semantic versioning; and a fresh V8 with new language features. It felt as if the project had finally been returned to the community. The first version of io.js came out in January of twenty fifteen, and after that new versions appeared every few weeks.\n\nThe community split. Some feared the schism: two incompatible servers, double work for package authors, lost trust from companies. Others welcomed the pressure on Joyent. And the pressure worked. As early as February of twenty fifteen Joyent, together with sponsoring companies including IBM, Microsoft, PayPal and others, announced the creation of the Node.js Foundation under the wing of the Linux Foundation: governance was becoming open. Meanwhile io.js stayed compatible with npm packages and quickly gained users. It became clear that the split suited neither side and that it was time to find a way back to a single project.\n\nIn May of twenty fifteen the io.js technical committee voted to merge with Node.js under the foundation. The work took several months, and in September Node.js four point zero came out. It is built on the io.js codebase, uses its semantic versioning and the new V8, and the project kept the name Node.js. The numbers jumped straight from zero point twelve to four: the threes were already taken by io.js. The paradox is that the fork lost in the name but won in the ideas: open governance, regular releases and a fresh engine became the basis of Node.js for the next ten years.\n\nWhat lessons did the community take from this? First: a fork is not a war, it is a tool. When a project does not meet contributors' needs, the ability to copy the code and go your own way forces the owner to change. Second: governance is part of the product; without open rules and regular releases a project loses developers. Third: a neutral foundation helps companies trust a project. The same scenario played out with LibreOffice and OpenOffice, MariaDB and MySQL, Jenkins and Hudson. In twenty nineteen the Node.js Foundation and the JS Foundation merged into the OpenJS Foundation, which now includes dozens of projects.\n\nAfter the merger releases became strict. A new major version comes out twice a year, even-numbered versions get long-term support, and odd-numbered ones are short-lived. Step by step, Node.js absorbed things that used to require packages: built-in standard modules, a built-in fetch, a built-in test runner, file watching, and support for Web Streams and Web Crypto. Modern Node.js can already run some typed code without a separate build step. The core has moved closer to the browser, and the same code increasingly runs in both environments, which we will cover in more detail in the chapters on Node.js.\n\nWhat became of Ryan Dahl? In twenty eighteen he gave a talk called Ten Things I Regret About Node.js: unsafe access to disk and network by default, a tangled module system, the package file as the only source of truth, and the node_modules folder. In that same talk he showed a new runtime, Deno, written in Rust and TypeScript. The first stable version came out in twenty twenty. Alongside it appeared Bun by Jarred Sumner, written in Zig and built on the Safari engine. In December of twenty twenty-five Anthropic announced it was acquiring Bun, which stays open source, and in October of twenty twenty-six Cloudflare announced it was acquiring the Deno company. The runtime will keep getting fixes for another year, and the team will move to the Cloudflare Workers platform.\n\nLet's sum up. Node.js appeared in two thousand nine because servers needed non-blocking input and output, and JavaScript already had an event model. npm and require created the ecosystem. Closed governance and slow releases led to the io.js fork in twenty fourteen, and nine months later the projects merged into Node.js four point zero on io.js terms. The fork became an example of how open source changes a project. Next we will tell how the language sped up after its stagnation: Babel, transpilers, bundlers and preprocessors, from which modern frontend grew.
