#CHAPTER 1 | The birth of JavaScript: ten days, the browser wars and ECMAScript
Modern Frontend. Chapter 1. The birth of JavaScript: ten days, the browser wars and ECMAScript. Before you write code, it helps to know where it came from. JavaScript is a language with quirks, and almost every quirk has a historical reason: haste, rivalry between companies, a demand never to break anything. This book is laid out like this: first history, then the language itself without a browser, then the browser, Node.js, bundlers and package managers, and at the end we will write our own mini-framework. In this chapter we will travel from the first pages on the web to the two-thousands, when the language got ready to become the foundation of the whole modern web.\n\nIn the early nineties the web consisted of static pages: you asked for a document, and the server handed back ready-made text. The Mosaic browser, and then Netscape Navigator, made the web mainstream, but the pages stayed dead. You could not validate a form without sending it to the server, and you could not calculate anything on the page. Netscape was looking for a way to bring pages to life, and in April of nineteen ninety-five it hired Brendan Eich to build a language into the browser. At first they planned to use Scheme, but management wanted the language to look like Java, which had just come out and was the talk of the town.\n\nAccording to the well-known story, Brendan Eich wrote the first working prototype in about ten days in May of ninety-five. The language was first called Mocha, then LiveScript, and in December, when Netscape struck a deal with Sun, it got the name JavaScript. The name turned out to be a marketing trick: the language has nothing to do with Java, just as ham has nothing to do with a hamster. It sounds similar, but there is almost nothing in common. The confusion lives on to this day. What matters is something else: the foundation you work with now was invented in a matter of weeks, and then refined for many years, but breaking something that had once been released onto the web turned out to be almost impossible.\n\nThe language mixes three sources. The syntax, with curly braces, loops and keywords, was taken from C and Java so that it would look familiar. Functions as values and closures came from Scheme, the functional language Eich originally wanted. And prototypes instead of classes, along with dynamic objects, were borrowed from a language called Self. That is why JavaScript has no classic classes, but functions can be passed anywhere. This is also where the roots of the quirks lie: typeof null, double equals, and automatic semicolon insertion all came from the wish to make the language forgiving for beginners, and then stayed forever for the sake of backward compatibility.\n\nSoon a competitor appeared. Microsoft released Internet Explorer and in ninety-six made its own version of the language, called JScript, essentially by reverse engineering. The browser wars began: each side added its own extensions, and different browsers showed the very same page differently. Netscape had layers, Microsoft had its own document collections, and the same script worked in only one of the browsers. Developers wrote a check for which browser it was and two branches of code. That era left the language its main lesson: without a standard, the web falls apart into several incompatible networks.\n\nTo stop the chaos, Netscape handed the language over to the organization Ecma International, and in June of ninety-seven the ECMA-262 standard appeared. The language itself is legally called ECMAScript, while JavaScript is a trademark and the best-known implementation. The standard is developed by technical committee thirty-nine, TC39, which includes representatives of browsers, big companies and the community. The second edition came out in ninety-eight, and the third, in ninety-nine, brought regular expressions and the try-catch block. For almost ten years the third edition remained the basis of everything that ran in browsers, and it was a very long stagnation.\n\nAlong with the language, the browser changed too. The document standard, the DOM, gave scripts a single way to read and change the tree of page elements. Style sheets, CSS, separated presentation from markup. The combination of the three technologies produced what was called dynamic HTML: menus, tooltips, form validation. It was fun, but hard to maintain: code was edited on the fly in Notepad, debugging was done through the alert dialog, and in tricky cases values were printed right onto the page. The page still reloaded completely on every request to the server, and the user saw the screen flicker.\n\nThe turning point came when someone figured out how to request data without reloading the page. The XMLHttpRequest object appeared in Internet Explorer in ninety-nine as an ActiveX component, and the other browsers copied it later. It got its real fame in two thousand four and five: Gmail and Google Maps showed that a page can behave like a desktop program, loading data in the background. In two thousand five this approach was named Ajax. The XML format quickly lost to JSON: JSON could be parsed directly with the language's built-in tools, was shorter, and fit JavaScript objects like a glove.\n\nBut writing for several browsers was still torture, and the community built layers on top. The libraries Prototype and MooTools extended the built-in objects. In two thousand six John Resig released jQuery. The dollar sign became a universal function: you used it to find elements by CSS selectors, change them, subscribe to events and send Ajax requests, and it all worked the same in every browser. jQuery became so popular that many sites still include it today, and the habit of finding an element and doing something with it made its way into textbooks for a long time.\n\nThe language was not ready for big programs. There were no modules: files were included with script tags, and the order of inclusion mattered. All variables became global and collided with each other. To isolate code, people used an immediately invoked function: the body sits inside a function that is called right away, and only what is needed is exposed outside. The module pattern built on closures became the standard way of organizing code. In two thousand eight Douglas Crockford wrote the book JavaScript: The Good Parts, showing that an elegant language hides behind the quirks, and suggested checking code with a linter. It was Crockford who popularized JSON.\n\nThere was one more barrier: performance. Browsers interpreted code line by line, and the language was considered good only for decoration. Everything changed in September of two thousand eight with the release of the Chrome browser. A Google team led by Lars Bak created the V8 engine, which compiled JavaScript into machine code on the fly. Code ran several times faster, and after Chrome the competitors sped up too: SpiderMonkey in Firefox, JavaScriptCore in Safari, and a performance race began. Suddenly it became clear that you could write big and fast programs in JavaScript, not just highlight a menu. On top of that came the iPhone of two thousand seven, which did not support Flash, and HTML5: JavaScript remained the only language you could use to build interactive things in all browsers at once.\n\nNow picture development in two thousand eight. There is no package manager: you download a library from a website and copy it into a folder. There is no build step: you upload files to the server over FTP. No modules, no classes, no arrow functions, no promises, and debugging goes through alert and the Firebug browser console. The language was weak, but it now had a fast engine, a huge audience and a feeling that things could only get better. One thing was missing: a way to run JavaScript outside the browser, on a server. That is exactly what we will talk about in the next chapter: the birth of Node.js and the war that flared up around it.\n\nLet's sum up. JavaScript was created by Brendan Eich at Netscape in ninety-five in a matter of days and combines C-like syntax, functions from Scheme and prototypes from Self. The browser wars showed the price of nonstandard extensions, and the language was standardized as ECMAScript, which is developed by the TC39 committee. Ajax made pages come alive, jQuery smoothed over the differences between browsers, and the module pattern built on closures replaced the missing modules. Chrome and V8 proved in two thousand eight that the language can be fast. Next comes the move to the server: the story of Node.js and io.js.
