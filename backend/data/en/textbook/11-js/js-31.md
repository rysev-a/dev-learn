#CHAPTER 31 | Runtimes: Deno, Bun and built-in tests
Modern Frontend. Chapter 31. Runtimes: Deno, Bun and built-in tests. For a long time Node was the only way to run JavaScript outside the browser, but now there are three runtimes. Deno was written by the creator of Node to fix earlier decisions: security by default, JavaScript and TypeScript with no setup, and web standards instead of custom interfaces. Bun was built for speed and convenience: a runtime, a bundler, a package manager and a test runner in a single executable. We will compare them on the main points and learn to write code that is not tied to one runtime.\n\nDeno runs TypeScript right away, with no separate compile step and no build configuration. Modules are imported by address or from the JSR registry, and the standard library is built on web standards: fetch, Request, Response, URL, Web Streams. The main difference is security. By default a program has no access to files, the network or environment variables: every permission has to be granted explicitly with a flag. Because of that, a script you downloaded cannot quietly read your files, and this changes how you think about dependencies.\n\nIn Deno, permissions are granted with flags, and they can be narrow. The allow-read flag with no value permits reading everything, but with a value it permits only the listed paths: a directory allows everything inside it. For the network you list hosts and ports, for the environment you list variable names. The deny flags take priority over the allow flags. If a program asks for a permission it does not have, it gets an error or, in interactive mode, a prompt. Good practice is to grant the minimum: not the whole disk but one directory, not the whole network but one host.\n\nBun is built around speed. It uses JavaScriptCore, the engine from Apple, starts up fast, and can do by itself what Node needs separate tools for: installing packages, building a bundle, running tests, executing TypeScript. The built-in server, Bun dot serve, gives high performance without external libraries. At the same time Bun aims to stay compatible with Node: most packages and built-in modules work unchanged. The price of the convenience is less maturity and rare differences in behavior, which you have to check against your own scenarios.\n\nWhat brings all these runtimes together is a set of web standards. Fetch, Request and Response, URL, TextEncoder, AbortController, Web Streams, binary data and EventTarget exist in the browser, in Node, in Deno and in Bun. If you write code against them rather than against runtime-specific interfaces, it will run anywhere, including cloud functions at the network edge. A good example is a handler that takes a Request and returns a Response: it can be plugged into any server. Platform features, such as the file system, are hidden behind a small adapter, so you can swap it when the runtime changes.\n\nYou can test code without third-party libraries: Node has the node test module, and Deno and Bun have similar built-in runners. The test function takes a name and a function with the checks, describe groups tests, and the assert module provides comparisons. Running the node test command finds files by a pattern, runs them in separate processes and prints a report. Watch mode reruns the tests whenever the code changes. A test that throws an exception counts as failed, and a test that finishes quietly has passed. Nothing more is needed to get started.\n\nA good test has three parts: arrange, act, assert. One test checks one idea, so its name tells you what broke. Tests are independent: the order they run in must not affect the result, and shared data is created fresh for every test. An asynchronous test returns a promise or uses await, otherwise the runner will finish the test before the check has run. For expected errors there are assert throws and assert rejects. And one last rule: a test must fail when the code is broken, so it helps to confirm at least once that it really can fail.\n\nTo test code that depends on the outside world, you replace its dependencies. The mock function helper creates a stub that records calls and arguments and can return set values. The mock method helper replaces a method on an object and can restore the original. For time there are fake timers: the test calls tick with the number of milliseconds it wants, and all the timers fire without any real waiting. This is how debounce, retries and timeouts are tested in a fraction of a second. Use mocks in moderation: the more replacements you make, the more your test is tied to the implementation.\n\nWhen you need to check a function against many inputs, you don't write ten tests, you write a table: an array of cases, each an input and an expected result, and a loop that creates a test for each row. Build the test name from the case data, so the report shows which row failed. Adding a new case means adding one row. This works well for parsing, validation, formatting and boundary values. It is also useful to keep a few cases meant to break things: empty input, very large numbers, unexpected types.\n\nCoverage shows which lines, branches and functions were executed while the tests ran. The runner can collect it out of the box. It is a useful indicator of blind spots: an uncovered branch is certainly not tested. But a hundred percent coverage does not guarantee that the tests check anything: you can execute a line and never compare the result. So coverage is used as a guide, with a threshold below which the build fails in continuous integration, and the quality of tests is judged by other signs: do they catch real bugs, and are they clear to the reader?\n\nIt is tempting to compare runtimes and implementations by speed, but you have to measure honestly. The first run is slower than the rest: the engine has not optimized the code yet, so you do a warm-up and throw away the first measurements. A single measurement is random, so you take many repetitions and look at the median and the spread, not the average. Time is measured with a monotonic clock, not with the date. The result depends on the computer, the load and the runtime version, so only runs under the same conditions can be compared. And most important: measure what matters for your task, not an abstract example.\n\nWhich runtime should you choose? Node is the most mature and widespread: it has the best support for packages and hosting. Deno fits if security by default and built-in TypeScript matter to you. Bun fits if you need speed and a single tool. The decision depends on the team, the infrastructure and the dependencies. To avoid the trap, write portable code: rely on web standards, hide platform calls behind adapters, and check the project in several runtimes in continuous integration. Then changing the runtime becomes a configuration change, not a rewrite.\n\nLet's sum up. Node, Deno and Bun are different runtimes for one language. Deno gives security by default and TypeScript with no setup, Bun gives speed and a set of tools in one file, and Node gives maturity and compatibility. A shared layer of web standards makes code portable. Built-in test runners let you write tests without libraries: a test, a group, asserts, mocks, fake timers, tables of cases and coverage. Benchmarks need warm-up, repetitions and the median. In the next chapter we move on to packages: how managers work, the manifest file and versions.
