#CHAPTER 27 | Workers, Service Workers and PWAs: An App That Works Without a Network
Modern Frontend. Chapter 27. Workers, service workers and PWAs. So far all of our code has run on the page's single main thread and has depended on the network. Workers move heavy work into separate threads, while a service worker sits between the page and the network and lets an app open without internet, receive notifications and update by clear rules. Put together, these make a progressive web app. In this chapter we will cover ordinary workers, the service worker lifecycle, caching strategies, offline mode, push, the manifest and installation, and in the exercises we will write small models of every one of these mechanisms.\n\nThere is only one main thread, and it runs page scripts, style calculation, layout and painting. Start a long computation there, and the interface freezes. The way out is a web worker: a separate thread with its own global object and its own event queue, and with no access to the document. You create a worker from a separate file and talk to it with messages through postMessage, and the data is copied along the way by an algorithm called structured cloning. It handles dates, maps, sets and circular references, but not functions and not page elements.\n\nCopying large data is expensive, so there is transfer of ownership: a buffer listed as transferable is not copied, it moves to the other thread, and for the sender it becomes empty. For direct communication there is a message channel with two ports, and a worker shared between tabs is called a shared worker. Shared memory with atomic operations is provided by SharedArrayBuffer, but it requires the page to be isolated. In practice, workers are wrapped in remote procedure calls, as the Comlink library does, and you keep a pool of threads so you don't create a new one for every task.\n\nA service worker is a special script that the browser runs separately from the page. It works as a proxy between the page and the network: it sees every request within its scope and can answer it from the cache, from the network, or with a response of its own. It has no access to the document, it lives for a short time, and it wakes up on events. It works only over a secure connection, with localhost as the exception for development. The scope is the path under which the worker controls pages; by default it is the folder where its script lives.\n\nA service worker has a lifecycle. After registration the browser downloads the script and fires the install event, where you usually put files into the cache. If an old version still controls open tabs, the new one waits in the waiting state until those tabs are closed. Then comes activation, which is the time to clean up old caches. The skipWaiting method and clients claim speed up the transition, but they can mix versions on one page. On every update check the browser compares the script byte by byte and treats any difference as a change.\n\nThe main event of a service worker is intercepting requests. The handler receives the request and calls the respondWith method with a promise, into which you can put a response from the cache or from the network. If no response is set, the request simply goes to the network as usual. Don't forget about extending the worker's life: background work, such as refreshing the cache, is wrapped in waitUntil, otherwise the browser will put the worker to sleep too early. Requests should be told apart by method, address and destination, and only safe GET requests are worth caching.\n\nCaching is built from a few strategies. Cache first, then network, is for immutable files with a hash in the name. Network first, then cache, is for data that should be fresh, but where it is better to show at least something when there is no connection. Serve stale and update in the background is for images and avatars. Cache only and network only are the extremes. The interface is called the Cache API: open a store by name, put in a request and response pair, look up by request with the Vary header taken into account, and delete. A response with an error is never put into the cache.\n\nCaches need versions. The store name includes the version, and on activation you delete every cache with the same prefix and a different version, otherwise the disk fills up. The core files of the app are put into the cache ahead of time from a list in which every file has a revision: on an update you download only what changed and delete what has disappeared. The bundler generates this list, and ready-made strategies, routing rules and plugins for entry lifetimes are provided by the Workbox library. And don't forget the limits: the number of entries and the age of the cache.\n\nFor an app to open without a network, it needs a shell: the minimal markup, styles and script from which the interface is built. For navigation requests the worker serves this shell from the cache, and the page's router decides what to show; the exceptions are API addresses and files with extensions. When nothing else worked, the worker returns a fallback page: an offline page for a document, a placeholder for an image. If the worker is slow to wake up, navigation preload helps: the network request goes out in parallel with the worker starting.\n\nThe page and the worker talk to each other with messages. A worker can write to all open tabs: it goes through the clients and sends each of them an event. That is how the notification "a new version is available" works: the page notices a waiting worker, shows a button, and on click sends a message asking it to skip waiting, and reloads exactly once when the controlling worker changes. For communication between tabs there is BroadcastChannel: every participant except the sender receives the message. The same channel can be used to elect a leader tab, which holds the single connection.\n\nNotifications arrive through push: the server sends a message to the browser's push service, which wakes the service worker with a push event, and that is where the notification is shown. The subscription is created with the app's public key, and the server signs its requests using a scheme called VAPID. You need the user's permission and some restraint, because notifications without a reason are annoying. Background sync helps send accumulated requests once the connection returns: the queue is kept in IndexedDB and processed on the sync event. Periodic sync and some other features are not available in every browser.\n\nA progressive web app consists of a secure connection, a service worker and a manifest. The manifest is a file with a name, a start address, a scope, a display mode, colors and icons; you need icons in two sizes, including a maskable one. When the conditions are met, the browser offers installation, and the before-install-prompt event lets you show your own button. An installed app runs in its own window, and it is worth remembering storage quotas: they are measured per origin, and persistent storage has to be requested separately, otherwise the data may be evicted.\n\nLet's sum up. Web workers move computation out of the main thread and communicate by copying or by transferring ownership. A service worker acts as a proxy with a lifecycle: install, waiting, activate, and an update is detected by a byte-by-byte comparison. Caching strategies are chosen by the type of resource, caches are versioned, and the app shell and fallback pages give you offline mode. Push and background sync extend what is possible, and the manifest turns a site into an installable app. In the next chapter we will deal with performance: what to measure and how to speed things up.
