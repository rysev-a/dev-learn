#CHAPTER 29 | Node.js Internals: V8, libuv, the Event Loop and Modules
Modern Frontend. Chapter 29. Node.js Internals. Node is JavaScript outside the browser: on the server, on the command line, in the bundlers and tools we use every day. To write reliable code in it, you need to understand what it is made of and how its event loop works. In this chapter we will look at how the runtime is put together, the V8 engine, the libuv library, the order of the loop phases, the thread pool, modules, parallel processes, exit codes and graceful shutdown. In the exercises we will build models of the event loop, the module loader, the garbage collector and a restart manager.\n\nNode consists of several layers. At the bottom is V8: the engine that parses and runs code. Next to it is libuv: a cross-platform library for input and output and for the event loop, written in C. Between them sit C++ bindings and a set of built-in modules: files, network, streams, processes, cryptography. There is no window or document here; instead there is the process object and the global object called globalThis. Node is deliberately single-threaded for your code: one main thread runs JavaScript, and it hands blocking work off to someone else.\n\nThe V8 engine does not simply interpret code. First it parses the source into a tree, then the Ignition interpreter turns it into bytecode and runs it while collecting statistics. Hot functions are compiled to machine code by optimizing compilers; if a guess turns out to be wrong, deoptimization happens. Objects with the same property order get a shared hidden shape, and call sites remember those shapes in inline caches, so stable shapes are faster. Memory is cleaned up by a generational garbage collector: the young generation is cleaned often and quickly, survivors move to the old generation, which is visited less often.\n\nThe event loop is the heart of Node. It goes through its phases in a circle. First come timers: expired timer callbacks run. Then pending system callbacks, the preparation phases and the poll phase, where the loop receives I/O events and waits for them if necessary. After that comes the check phase, where callbacks from the immediate queue run, and the close phase, where closed handles are processed. As long as there is something in the queues, the loop keeps spinning; when all active handles are finished, the process exits by itself.\n\nBetween every two callbacks of the loop, Node drains two special queues. First the next-tick queue is processed, then the promise microtask queue, and this repeats until both are empty. That is why next-tick callbacks and promises always get in ahead of any timer. A setImmediate call fires in the check phase, and inside an I/O handler it is guaranteed to run before a timer set to zero. Because of this, endless recursion through next tick can starve the loop: I/O simply never gets a word in.\n\nNot everything in Node is asynchronous at the operating system level. Network sockets use kernel mechanisms such as epoll and kqueue, but file operations, name lookup through the system call, compression and part of the cryptography run in the libuv thread pool. By default it has four threads, and the size is set with an environment variable. If you start many heavy tasks at once, they line up in a queue. The main rule is: never block the main thread with long synchronous calls or computations, because that freezes all requests at once.\n\nHistorically, modules in Node are CommonJS. The require function finds a file by a set of rules: a relative path, file extensions, a directory with a main file, and then a search through the dependency folders going up the tree. The file's code is wrapped in a function with the parameters exports, require and module, and the result goes into a cache, so a second call does not run the file again. With a circular dependency, a module gets whatever the other one has managed to export by that moment. Built-in modules take priority over packages with the same name and are loaded with the node colon prefix.\n\nModern modules are standard ES modules. The mode is switched on by the M J S file extension or by the type field in the package description file. In a package, the exports field defines the public entry points by conditions: node, import, require, default; everything that is not listed is closed. The imports field describes internal aliases that start with a hash sign. Top-level await is allowed, and in version twenty-two you can load synchronous ES modules with require. The danger of dual packages is when one library is loaded both as CommonJS and as an ES module and behaves like two different libraries.\n\nNode has three tools for parallelism. Worker threads start separate threads inside the process: each has its own engine and its own memory, and they exchange messages and shared memory with atomic operations; they suit computation. Child processes run other programs and scripts: spawn, fork and exec; they suit isolation and external utilities. The cluster module starts several processes that listen on one port and distributes the connections among them; in modern deployments an orchestrator often replaces it by running many copies of the application.\n\nA process talks to the world through arguments, environment variables, standard streams and exit codes. A zero code means success, a non-zero code means an error; when a process is terminated by a signal, the convention is to count the code as one hundred twenty-eight plus the signal number. An unhandled exception and an unhandled promise rejection terminate the process by default, and that is the right thing to do: the state of the program is already unknown. The before-exit and exit events let you tidy up, but in the exit event you can only do synchronous work.\n\nGraceful shutdown is a sign of a mature service. When the orchestrator or the system sends a termination signal, the application stops accepting new connections, waits for the current requests, closes its pools and database connections, and only then exits; the whole thing gets a limited amount of time, and a second signal means exit immediately. Next to it you need a supervisor: it restarts a crashed process with a growing delay and gives up if failures come one after another, while liveness and readiness probes tell the orchestrator whether traffic can be sent.\n\nFor diagnostics, Node has an inspector that you can attach from the browser's developer tools, a CPU profiler, heap snapshots and tracing of loop events. The async hooks module and the async local storage let you carry a request identifier through all the awaits without passing parameters. A loop lag monitor shows how much the main thread is slowing down. An error stack is parsed into frames; an error can have a cause, which helps you build chains. Good logs and metrics are often more useful than a debugger.\n\nLet's sum up. Node is V8, libuv and built-in modules around one main thread. The event loop goes through phases, and next tick and microtasks are drained between callbacks. The thread pool takes over blocking operations, but the main thread must never be blocked. Modules come as CommonJS and ES modules, and packages have an exports map. For parallelism there are workers, child processes and the cluster, and a mature service shuts down gracefully. In the next chapter we will deal with files, streams and events.
