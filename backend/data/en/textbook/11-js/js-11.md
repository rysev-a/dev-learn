#CHAPTER 11 | Functional programming: pure functions, immutability, composition
Modern Frontend. Chapter 11. Functional programming: pure functions, immutability, composition. In JavaScript, functional style is not exotic, it is the main way to write reliable code. Functions are values here, the language has closures, the methods map, filter and reduce, and whole libraries have grown around the style: Ramda, lodash in its functional flavor, Immer, RxJS. Redux and React are built on the same ideas. This chapter covers the basics: how a pure function differs from an impure one, how to work with immutable data, and how to build a program out of small pieces using composition and currying. The next chapter will show the libraries and some more advanced techniques.\n\nA pure function returns the same result for the same arguments and changes nothing outside itself. It does not read global state, does not write to the console, does not touch the network, and does not modify its own arguments. From this follows referential transparency: you can replace a call with its result and the program will not change. Impure things include math random, the current time, changing an array that was passed in, touching the DOM, and reading a file. Pure functions are easy to test: values go in, a value comes out, and you need no mocks. They are safe to cache, to reorder, and to run in parallel, because they do not interfere with each other.\n\nThat does not mean a program should have no side effects. Without them it would be useless: you need to read input and show a result. The point is to separate effects from computation. The core of the program consists of pure functions, and a shell at the edges does the input and output. If a function needs the current time or a random number, you pass it in as a parameter, and then a test can supply a fixed value. This gives you a familiar architecture: a layer of logic you can test instantly, and a thin layer that talks to the world. This very split is the foundation of Redux, where the logic that updates the state is a pure function.\n\nImmutability is the second pillar. Const does not make data immutable: it only forbids replacing the binding. Real immutability means that instead of editing a value we create a new one. For objects you copy with spread, and for arrays you use methods that return a new array: map, filter, slice, and the recently added toSorted, toReversed, toSpliced and with. The dangerous ones are the methods that change an array in place: push, pop, splice, reverse and sort. They return the same value, but with changed contents, and when one array is passed to two functions, things start to behave unexpectedly. Object freeze helps catch such mistakes during development. Copying every time sounds expensive, but structural sharing comes to the rescue: when you update a nested object, only the nodes on the path from the root to the changed field are copied, and everything else is shared with the old version. Old and new data live side by side, which gives you undo and redo for free, and the check «did anything change» comes down to comparing references.\n\nHigher-order functions take and return functions. Map transforms every element, filter keeps the matching ones, and reduce folds a collection into a single value. FlatMap combines a transformation with flattening, some and every answer questions about a collection, and find looks for an element. Reduce is the most universal: you can express map, filter, grouping, counting and unique values through it. The habit of thinking «what do I want to get» instead of «how do I walk through it» makes code declarative: instead of a loop with mutable counters, you describe the data transformation as a chain of steps, and each step can be read, tested and replaced on its own.\n\nComposition means gluing functions together into a new one. Composing two functions applies the second one first and then the first, as in mathematics. Pipe does the same thing left to right, the way we read text: data moves from step to step. A pipe function takes any number of steps and returns a function that runs a value through all of them. To debug a chain, you insert a probe step that prints the value and returns it unchanged. This style is called point-free: the data is never named, and only the operations on it remain. It is elegant, but do not overuse it: if the code becomes a riddle without names, put the names back.\n\nComposition requires functions to take one argument. That is what currying and partial application are for. Currying turns a function of several arguments into a chain of functions that take one argument each. Partial application fixes some of the arguments and returns a function for the rest. It is important to put the data last: then a partially applied function can be used right away as a step in a chain. For example, a «multiply by» function with a fixed factor can be passed straight into map. The Ramda library makes every function curried, while in plain JavaScript you get the same effect from closures and arrow functions that return arrow functions, and the bind method fixes the first arguments.\n\nRecursion replaces loops where there are no mutable counters: walking a tree, going through subsets, parsing nested structures. But JavaScript has a limit on stack depth, and most engines have no tail call optimization, so a recursion thousands of steps deep fails with an error. The way out is a trampoline. Instead of making a recursive call, the function returns a step function, and a loop outside calls the steps one after another without growing the stack. Often recursion can be expressed with reduce or plain iteration. Memoization, which we discussed in the chapter on functions, is especially useful when the function is pure and is called with repeating arguments.\n\nFunctional style likes sum types: a value is one of several variants, marked with a tag. In JavaScript these are objects with a type field. The best-known examples are Maybe and Either. Maybe represents a value that may be missing: either «there is a value» or «nothing». Either is the result of a computation: either «success with a value» or «failure with a reason». They replace null and exceptions with explicit data and force you to handle both cases. A switch on the tag works like pattern matching, and a check that all variants are covered catches forgotten branches. The optional chaining operator, a question mark followed by a dot, is a tiny Maybe built into the language.\n\nContainers that have a map are called functors. An array is a functor: map applies a function to every element and keeps the shape. Maybe and Either are too: map works inside the value and skips the empty cases. The functor law is simple: mapping the identity function changes nothing, and mapping a composition equals composing the maps. If a container also has an operation that takes a function returning a container and flattens the result, it is called a monad: for an array that is flatMap, and for a promise it is then. Don't worry if the terms are still foggy. What matters is that a chain of steps, each of which may fail, can be written flat, without nested checks.\n\nLaziness saves work. Generators produce values one at a time and compute the next one only when it is asked for, so you can take the first ten elements of an infinite sequence. A pipeline of map and filter like this creates no intermediate arrays: each element goes through all the steps in full. Transducers develop this idea: transformations that do not depend on the kind of collection. Newer engine versions add helper methods to iterators, map, filter, take and others, so lazy chains are available without libraries. But laziness is not free: it makes debugging harder, so use it where the data is large or infinite.\n\nHow does all this look in an application? The state is described by a single object, and changes are described by actions. A reducer is a pure function of the old state and an action that returns the new state. At any moment the state equals the fold of all actions since the start, so the history can be replayed, rolled back and recorded. Selectors are pure functions that compute from the state what needs to be shown; they can be memoized. Side effects, such as requests, live separately and only dispatch actions. Redux and the Elm architecture are built on this scheme. Testing a pure function is just a call with a check of the result, with no setup and no cleanup.\n\nLet's sum up. A pure function depends only on its arguments and changes nothing, and effects are pushed to the edges of the program. Immutability means creating new values instead of editing old ones, and structural sharing makes it cheap. Map, filter and reduce describe data transformations, composition and pipe glue the steps together, and currying with data as the last argument helps them fit. The trampoline rescues recursion, Maybe and Either replace emptiness and errors, and lazy iterators handle large streams. Application state is a fold of actions. In the next chapter we will meet these ideas in ready-made libraries.
