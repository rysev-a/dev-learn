#CHAPTER 25 | Forms, Validation and Storage: localStorage, Cookies, IndexedDB, History API
Modern Frontend. Chapter 25. Forms, Validation and Storage: localStorage, cookies, IndexedDB and the History API. Through forms, the user hands data to the application, and storage lets that data survive a page reload. These two topics are connected: whatever was typed has to be checked, sent, saved as a draft, and then the state has to be restored from the address in the browser bar. In this chapter we will follow the path of the data: form fields and how they are submitted, built-in validation, cookies and web storage, the database inside the browser, and working with the address. In the exercises we will write small versions of these mechanisms, so that we understand what happens inside.\n\nA form is made of input elements. The input element comes in many types: text, email, number, date, password, checkbox, radio button, and file. There is also the multi-line textarea, the drop-down select, buttons, and the fieldset for grouping. Every field needs a name, because the name is exactly what ends up in the data, and a label with the for attribute. That makes the field accessible and enlarges the click area. A button inside a form submits it by default, so all the other buttons are marked with the type button. The autocomplete attribute tells the browser and the password manager what exactly is being asked for in the field, and makes signing in easier for people.\n\nWhen a form is submitted, the browser collects name and value pairs. Only fields that have a name and are not disabled make it into the set, and checkboxes and radio buttons only if they are checked; the selected options of a list give one pair for each. A button goes into the data only if it was exactly the one that was pressed. For scripts there is the FormData object: you can create it from a form and send it with fetch, and it has the methods append, get, getAll, set and delete. The encoding type defines the shape of the body: urlencoded is a string of key equals value pairs joined with ampersands, with percent encoding, while multipart is needed for files. The GET method puts the data into the address, and POST puts it into the body.\n\nValidation of data starts in the markup. The attributes required, pattern, min, max, minlength, maxlength and step set the rules, and the email and URL types are checked automatically. The programmatic interface is called the Constraint Validation API. A field has a validity object with the flags valueMissing, typeMismatch, patternMismatch, tooLong, tooShort, rangeUnderflow, rangeOverflow and stepMismatch, the methods checkValidity and reportValidity, and the method setCustomValidity for your own message. The invalid selector styles the faulty fields. The novalidate attribute turns off the built-in validation if you show your own.\n\nClient-side validation is a convenience, not protection. Any user can send a request bypassing your form, so the server is obliged to check everything again. But client-side validation saves time and nerves: the error must be clear and placed next to the field. It is usual to show it when the user leaves the field or tries to submit, but not at the moment of the first typed letter. Connect the message to the field with the aria-describedby attribute and set aria-invalid, and when submission fails, move the focus to the first wrong field. Input masks for phones and cards are useful, but they must not get in the way of pasting and editing.\n\nThe state of a form is a topic of its own. An uncontrolled form keeps values in the DOM itself, and you read them on submit. A controlled one keeps values in the application state and redraws the field on every change, as frameworks do. The value property holds the current value, defaultValue holds the initial one, and by comparing them you can tell whether the user changed the data. The beforeunload event lets you warn about unsaved changes when the page is being closed. It is worth saving drafts automatically, with a pause after typing, so that accidentally closing the tab does not destroy the user's work.\n\nCookies are the oldest way to keep data between requests. The server sets them with the Set-Cookie header, and the browser sends them back with every request to the same site. Cookies have attributes: Path and Domain define the scope, Max-Age and Expires define the lifetime, Secure means only over a secure connection, HttpOnly hides the value from scripts, and SameSite limits sending on requests from other sites and protects against request forgery. From JavaScript cookies are visible through document dot cookie, but each one is limited to about four kilobytes, and they make every request heavier. The session identifier should be stored exactly in a cookie with HttpOnly.\n\nWeb storage is simpler. localStorage and sessionStorage keep pairs of string to string; the first lives until the user clears the data, the second until the tab is closed. The methods setItem, getItem, removeItem and clear are synchronous, so large volumes slow the page down; the quota is around five megabytes, and an exception is thrown when it is exceeded. Objects are stored through JSON, and the format version is put into the key so that you can migrate later. The storage event tells other tabs about a change, and this is how themes and sign-out are synchronized. Secrets must not be kept there: any script on the page can read them.\n\nWhen there is a lot of data or you need queries, you use IndexedDB, a database inside the browser. It stores objects, keys can be paths inside an object, and indexes let you search by fields. All operations happen inside transactions and are asynchronous: you open a request, and the result arrives in a handler. The schema changes when the version is increased, in the upgrade-needed event. It is inconvenient to work with directly, so people use thin wrappers, for example idb. Nearby there are the Cache API for network responses, the origin private file system, and the storage manager, which reports the volume used and asks the browser not to evict your data.\n\nThe address is also part of the state. The URL object parses an address into parts, and URLSearchParams works with query parameters: it adds, reads and removes them and encodes characters correctly. The browser history is available through the History API: pushState adds an entry without a reload, replaceState replaces the current one, and the popstate event fires when the user presses back or forward. In the past, people used the part of the address after the hash sign for this, and that approach works without any server setup. The new Navigation API promises to simplify this even further, but the basics stay the same.\n\nA single-page application router is built from these pieces. It matches a path to a screen, takes parameters out of the address, intercepts clicks on internal links, and calls pushState instead of navigating. Not every click should be intercepted: you let through presses with modifier keys, the middle button, links with a target or a download, and addresses of other sites. You also need to restore the scroll position on going back and show a not-found page. Meanwhile the server must return the main page for any path, otherwise refreshing the page will give an error. In the last part of the book we will write such a router ourselves.\n\nStorage security is a concern of its own. Everything that lies in localStorage and IndexedDB is available to any script on the page, so injected code can steal a token. HttpOnly cookies are not available to scripts, but they bring the risk of request forgery, and SameSite and tokens protect against it. A content security policy reduces the risk of code injection. For encryption there is Web Crypto, but the key still has to be stored somewhere. Do not forget privacy laws either: consent for non-essential cookies, the ability to delete data, and a minimal set of what is stored.\n\nLet us sum up. A form sends name and value pairs, and FormData assembles them programmatically. Built-in validation is set by attributes and read through validity, but the real validation is on the server. Cookies carry the session and go out with every request, web storage keeps strings synchronously, and IndexedDB keeps objects with indexes and transactions. The address and the history are part of the application state, and a router maps them to screens. Secrets do not belong in storage that scripts can reach. In the next chapter we move on to the network: fetch, cross-origin requests and WebSockets.
