Modern Frontend. Chapter 34. Bundlers: webpack, Rollup, esbuild, Vite — bundling, tree shaking and code splitting. The browser can load ES modules on its own, but you can't ship a project with a thousand modules that way: hundreds of requests, code in TypeScript and JSX, styles, images, dependencies from node modules. A bundler takes an entry point, walks all the imports, transforms every file, throws away what's unused, compresses, and produces a small set of files. It also gives you a development server with instant updates. In this chapter we'll look at how a bundler works on the inside.\n\nIt all starts with the entry point. The bundler reads a file, finds the imports in it, and for each one finds the next file. That's how it walks all the modules and builds a dependency graph: the nodes are files, the edges are imports. Static imports are visible right away, and so are dynamic import calls with a literal. Paths are resolved by rules: relative ones from the current file, bare names in node modules, with extensions and index files filled in. Imports that can't be understood without running the code are invisible to the bundler, so in a bundled project it's better to write static paths.\n\nA bundle is a single file that holds all the modules. Each one is wrapped in a function so that it has its own scope, and is put into a table by identifier. A tiny loader is added at the start: a function that, given an identifier, runs the module once, caches the result and returns its exports. The imports inside modules turn into calls of this function. For ES modules, modern bundlers can skip the wrapping and instead merge everything into one shared scope, producing smaller and faster code, but the principle stays the same.\n\nA bundler only understands JavaScript, so everything else has to be transformed. In webpack there are loaders for that: TypeScript becomes JavaScript, styles become an includable module, an image becomes an address or an inline string. Plugins are broader: they step into any stage, add files, substitute variables, optimize the output. In Rollup and Vite, plugins work through hooks: path resolution, loading, transforming, generating. The good news is that most plugins boil down to a function with text in and text out.\n\nTree shaking is the removal of code that nobody uses. It works because imports and exports in ES modules are static: from them the bundler knows which names are needed. If one function out of a hundred is imported from a library, the rest don't end up in the bundle. Side effects get in the way: if a module does something when it loads, for example changes a global object, it can't be removed. The sideEffects field in the manifest, set to false, promises that the package's modules are safe to remove. CommonJS modules are dynamic, so they don't respond well to this optimization.\n\nMinification reduces the file size without changing its behavior. Comments and whitespace are removed, local variable names are shortened to one or two letters, expressions are simplified, dead branches are deleted. This is done by Terser, esbuild and the bundlers' built-in tools. To debug such code, the bundler creates a source map: a file that maps positions in the minified code to positions in the original. The browser console uses it and shows you your own lines instead of a mess. The map isn't handed out to everyone if the sources are closed, but a developer needs it.\n\nOne giant bundle makes the user download everything, even what they don't need. Code splitting divides the code. A dynamic import call returns a promise and creates a separate file, which is loaded on first use: for example, a settings page or a heavy editor. Code that several parts need is moved into a shared chunk so that it isn't duplicated. A sensible rule: for the first load, serve only what the first screen needs, load the rest as you go, and preload what will most likely be needed.\n\nIt's good for the browser to cache files for a long time, but then, when you update, the user would get old code. The solution is to put a hash of the content into the file name: app, dot, hash, dot, js. If the code changed, the hash and the name changed, and the browser downloads the new file. If it didn't change, it takes the file from the cache for a year. The page that references the files must update too: it is either not cached or generated anew. The map from logical names to hashed ones is called the build manifest, and the addresses are filled in from it.\n\nWebpack is the most powerful and flexible: thousands of plugins, support for any kind of asset, but a complex setup. Rollup was born for libraries: clean ES module output and the best tree shaking. Esbuild is written in Go and runs tens of times faster: it builds in a fraction of a second, but it has fewer plugins. Vite uses esbuild to prepare dependencies and Rollup for the final build, and provides ready-made settings for typical projects. Parcel and Rust-based builds like Turbopack and Rolldown are other directions. The choice depends on the task, the team and inherited configuration.\n\nIn development, what matters most is the speed of feedback. Older bundlers rebuilt the whole bundle. Vite serves ES modules to the browser as they are and transforms each file on request, so startup is instant, and dependencies from node modules are prebuilt by esbuild. Hot module replacement, HMR, updates the changed module in the running page, keeping the state. If a module can't accept the update, it bubbles up to the parent, and in the worst case the page reloads. A good HMR experience makes edits visible within a fraction of a second.\n\nA bundler is set up with a configuration file. Environment variables are substituted as constants at build time, which means secrets must not end up in browser code. Aliases shorten paths: at-slash instead of long relative ones. The external option excludes a package from the bundle: when you build a library, dependencies usually stay external. Target browsers determine which language features need to be transformed and which left as they are: the newer the target, the smaller and faster the code. Environment conditions let you cut debug branches out of the production build.\n\nA bundle grows unnoticed: you added a library, and instead of ten kilobytes it's a hundred. That's why you need to analyze it. Visualizers show which modules and packages take up space, and find duplicate versions and libraries that couldn't be shaken. A size budget sets a limit for each chunk, and continuous integration fails if the limit is exceeded. Comparison with the previous build shows which change added how many bytes. Often the gain comes from replacing a heavy library with a light one, lazy-loading rarely used code, and carefully importing only the functions you need.\n\nLet's sum up. A bundler builds a module graph from the entry point, transforms files with loaders and plugins, and joins them into bundles. Tree shaking removes unused code thanks to static ES modules. Minification reduces the size, and the source map keeps debugging possible. Dynamic import creates chunks on demand, and shared parts are moved out separately. Hashes in names give a reliable long-lived cache. Webpack, Rollup, esbuild and Vite solve one task in different ways. Analysis and budgets keep the size under control.
