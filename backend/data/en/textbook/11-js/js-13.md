Modern Frontend. Chapter 13. HTML: document, semantics and accessibility. We are starting the section on markup, the foundation of every web page. HTML is a markup language, not a programming language: it has no conditions and no loops, it only describes what kind of content we are looking at. Here is a heading, here is a paragraph, here is a list, and here is a link. The key word is meaning. Styles set the appearance, while markup answers the question of what something is, and search, screen reading and maintainability all depend on that answer.\n\nEvery document begins with the document type declaration, the doctype. It switches on modern parsing, and without it the browser behaves like it is the nineties. Next comes the root html element with a language attribute, which translators, search engines and text to speech programs use to pick the right pronunciation. Inside the root there are two sections, in strictly this order: the head, which holds information about the page, and the body, which holds everything a person sees. The root has no other children, and each part appears exactly once.\n\nThe head of a page is invisible, but very important. The title element is shown in the browser tab, in history and in search results, so the name should be meaningful and unique. The meta tag with the encoding comes right at the start and tells the browser to read the file as Unicode, otherwise instead of accented letters you get garbled characters. The viewport meta tag tells a mobile browser that the page is designed for the width of a phone screen. The link element attaches style sheets and the site icon, and scripts are attached with a separate element, usually with deferred loading.\n\nA page is made of elements. An element is an opening tag, the content and a closing tag: for example, a whole paragraph. Tags are written in angle brackets, and the closing one differs by a slash. Inside the opening tag there may be attributes, pairs of a name, an equals sign and a value in quotes: a link stores an address, an image stores a path to the file and a description. There are empty elements with no content and no closing tag: a line break, a horizontal rule, an image and an input field. Elements nest inside one another like matryoshka dolls: whichever opened last is the first to close.\n\nBy default, elements have two main kinds of display. Block elements, like a paragraph, a heading or a list, take the full width and line up one under another, each starting on a new line. Inline elements, like a link, an emphasis or a span, live inside a line of text and take exactly as much room as their content needs. An inline element inside a block is normal, but the other way around is usually not allowed: a paragraph inside an emphasis is already an error. These modes are only defaults: styles can change them later however you like, but the meaning of the markup stays the same.\n\nHeadings, from H1 to H6, are the outline of the page. There is usually exactly one H1: the main title. Sections get H2, their parts get H3, and the levels go in order, with no gaps: after an H2 you do not jump straight to an H4. The size of the letters has nothing to do with it: if you want a large font, you set it with styles, and you choose the level by the place in the structure. A screen reader and a search engine read headings as an outline, and a person using a screen reader jumps between them, so the order of levels is a matter of convenience, not taste.\n\nText is split into meaningful pieces. A paragraph is the p element, and consecutive spaces get collapsed by the browser into one, so you cannot make indents with blank lines. A bulleted list is ul, a numbered one is ol, and in both of them every item sits in an li element: if the order matters, use a numbered list. A definition list, dl, holds pairs of a term, dt, and a description, dd. A long quotation is marked up with blockquote, and a short quotation inside a line with the q element. Code goes in the code element, and a multiline listing is wrapped in pre, so that spaces and line breaks are preserved.\n\nA link is the a element with an href attribute. An absolute address contains the protocol and the domain, while a relative one is counted from the current page: folder, slash, page, or two dots and a slash to go one step up. An address made of a hash sign and a name is an anchor: it scrolls to the element with that identifier on the same page. The target attribute with the value blank opens the link in a new tab, and you add a rel attribute with the values noopener and noreferrer, so that the other page does not get power over yours. The link text must make sense without its surroundings: not click here, but download the report.\n\nPages used to be assembled from faceless divs, but today there are meaningful containers. Header is the masthead of a page or a section, nav is the block of main navigation, main is the main content, and there is only one of it on a page. Article is a self-contained fragment that makes sense apart from the page: a story, a card, a comment. Section is a thematic part, usually with its own heading, aside is secondary content like a sidebar, and footer is the bottom. They look like ordinary blocks, but they carry meaning, and meaning is what search engines, screen readers and reader modes read.\n\nWhat if there is no suitable meaningful element? Then div and span come in handy: neutral containers with no meaning of their own. Div is a block and span is inline, and both exist so you can attach a class or group elements for styles and scripts. This is a fallback, not the first choice: before writing a div, ask yourself whether there is a suitable element. A page built only of divs is called div soup: it works, but to a program it is just a set of rectangles. A button should be a button, not a div with a click handler.\n\nSome users work without a mouse, others without a screen: blind people listen to the page with a screen reader, and the rest drive it from the keyboard. A screen reader reads the tree of elements, not the picture. It can list the headings and the landmarks, the areas of a page such as navigation, main content and footer, and those landmarks come from semantic tags. An image needs an alt attribute with a short description, and a purely decorative one needs an empty alt, so that it gets skipped. An input field needs a label, a link needs clear text, and focus moving with the Tab key should follow a logical order.\n\nThe browser does not show markup errors: it builds a tree, fixing what it can. You forgot to close a paragraph, and it closes by itself when a new block begins. You put a tag in the wrong place, and parsing moves it according to the rules of the standard. The parsing rules are described in great detail, so all browsers get the same tree, which is called the DOM. This is what styles and scripts work with, not your text. Forgiveness of errors is convenient but treacherous: the page looks fine, yet the structure is no longer what you meant, so markup is checked with a validator and by looking into developer tools.\n\nLet us wrap up with a checklist for a good page. The doctype, the language and the encoding are in place, and the page has a meaningful title. There is one H1, and the other headings go in order. The header, navigation, main content and footer are marked up with their own elements, and there is only one main. Lists are made as lists, buttons as buttons, and div and span appear only when there is no suitable meaning. Every image has an alt, every field has a label, every link has clear text, and parsing goes through without errors. These rules will be useful in every following chapter.
