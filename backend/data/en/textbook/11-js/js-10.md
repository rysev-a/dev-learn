#CHAPTER 10 | Promises and async/await: Chains, Errors, Concurrency
Modern Frontend. Chapter 10. Promises and async await: chains, errors, concurrency. Almost everything interesting on the web doesn't happen right away: a request goes to the server, the user clicks, a timer fires. JavaScript is single-threaded, and you can't stop everything else to wait for a result. So code is arranged this way: an operation is started, and the result arrives later. The way we describe this later has gone through three stages: callbacks, promises, and finally async await, which reads almost like ordinary sequential code. In this chapter we will go through all three, understand why the order of execution sometimes surprises us, and learn to run operations in parallel and to cancel them.\n\nLet's start with callbacks. A function takes another function and calls it when the work is done. By convention the error comes first and the result second. This style works, but it grows quickly: to run three steps one after another you nest them inside each other, and you get a staircase known as callback hell. Worse, you hand control to someone else's function and hope it calls your callback exactly once: not twice, not too early. Error handling is smeared across every level. These are exactly the problems that promises solve.\n\nA promise is an object that represents the result of an operation that hasn't finished yet. It has three states: pending, fulfilled and rejected. From pending it moves to one of the other two exactly once, and after that it never changes. The constructor takes an executor function with two parameters: resolve, to pass a value, and reject, to report an error. You subscribe to the result with the then method, and to the error with the catch method. The executor runs immediately, while subscribers are always called asynchronously, even if the promise is already fulfilled. The word thenable means any object with a then method: promises know how to unwrap it.\n\nThe main property of a promise is chaining. The then method returns a new promise. If the handler returned a value, it becomes the result of the next link. If it returned another promise, the chain waits for it. If it threw an exception, the next promise is rejected, and the error travels down the chain until it meets a catch. Catch, in turn, returns a promise, so you can continue after it: the error is recovered. The finally method runs in any case and doesn't change the result. Instead of a staircase of nesting you get a flat list of steps, and errors are handled in one place at the end.\n\nNow let's talk about order. Promise handlers go into the microtask queue, which is processed right after the current synchronous code finishes, before timers and events. So in code that first sets a timer with zero delay, then a promise with then, and then prints a line, the line comes out first, then the promise result, and only then the timer. Microtasks added while microtasks are being processed also run before the next timer, so an endless loop of microtasks can freeze the page. We will cover the full design of the event loop in the chapter about the browser.\n\nFor several promises there are combinators. Promise all waits for every one and returns an array of results in the original order, but it rejects on the first error. All settled always waits for every one and reports on each: whether it was fulfilled or rejected, and with what. Race finishes as soon as the fastest one finishes, with its result or its error. Any waits for the first success and rejects only if all of them failed, with an AggregateError. Modern versions added the static method with resolvers, which returns a promise together with the functions that settle it, which is handy when the result will come from an event.\n\nAsync await is syntactic sugar over promises. A function marked async always returns a promise: the returned value becomes the result, and an exception becomes a rejection. Inside it, the word await pauses execution until the promise settles, without blocking the rest of the program, and gives you its value. You catch errors with an ordinary try-catch. The code reads from top to bottom, like synchronous code, and loops and conditions work as usual. Under the hood these are the same microtasks: await splits the function into parts, and the continuation runs when the promise is ready. Top-level await is allowed in modules, so scripts don't need a wrapper.\n\nConvenience breeds typical mistakes. A forgotten await: instead of a value you get a promise, and an error from it goes uncaught. An await inside the forEach method waits for nothing: forEach calls the async functions and returns immediately, so for sequential traversal you use a for-of loop. Two independent awaits in a row run one after the other, though they could run in parallel: if the operations don't depend on each other, start both and wait with Promise all. A promise constructor wrapped around an existing promise is an antipattern. Returning a promise from a try block without await skips the catch: the error slips right past it.\n\nConcurrency has to be limited. If you fire off a thousand requests at once, you overload the server and exhaust the browser's connections. The usual technique is a pool: several workers take tasks from a shared queue, and no more than the set number run at the same time. Another technique is a semaphore: you take a permit before working, return it afterwards, and the waiting ones line up in a queue. You keep the order of results by writing each one at its index. This kind of logic shows up in file uploaders, site crawlers and bundlers. For events that arrive often, such as typing in a search box, you take into account only the latest request and drop stale responses.\n\nA promise can't be cancelled: it runs to the end, but you can stop listening to it. The standard way is AbortController. You create a controller, pass its signal into the operation, and when you need to cancel, you call abort. Fetch responds by rejecting with an AbortError; your own operations must subscribe to the abort event on the signal and stop working. For timeouts there is a ready-made signal with a time limit, and you can combine several signals with the any method. Cancellation matters especially in interfaces: when the user has left the screen, the request is no longer needed, and the response must not change the state.\n\nAsync iterators represent a stream of values that arrive over time. The for await of loop waits for each value in turn. Such a loop is handy for paginated loading: a generator function declared with async and a star requests a page, yields the items one by one, and moves on to the next page until the server says there are no more. Streams in Node.js and in the browser can also be read with this loop. The generator is lazy: the next page is requested only when the consumer asks for the next item, and leaving the loop stops the loading. This is a natural way to describe line-by-line reading and event subscriptions.\n\nThere are other ways to schedule a task. The queue microtask function puts code into the microtask queue without a promise. Set timeout with zero delay runs it after the microtasks, but no earlier than four milliseconds in nested calls. Set immediate in Node.js fires after the current input-output phase. The promisify function from Node.js turns callback style into promises, and many built-in modules already have a promise variant. An unhandled promise rejection counts as an error: in Node.js it terminates the process, and in the browser it fires an event. Every promise must be handled somewhere with a catch or an await, otherwise the error is lost.\n\nLet's sum up. Callbacks lead to a staircase and smeared error handling, and a promise solves this with a result object that changes once. Then and catch chains give a flat flow, and handlers go into the microtask queue. All, all settled, race and any combine promises. Async await makes code readable, but doesn't remove the need for care: don't forget await, don't use forEach, and run independent work in parallel. Concurrency is limited with a pool, cancellation is done with AbortController, and streams are read with for await of. In the next chapter we take the functional approach and apply it to data and effects.
