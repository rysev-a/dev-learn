#CHAPTER 23 | The DOM Tree: Finding, Changing, and Creating Nodes
Modern Frontend. Chapter 23. The DOM Tree: finding, changing, and creating nodes. The DOM, the Document Object Model, is how the browser shows a page to JavaScript: the markup is turned into a tree of objects, and you read and change them through a programming interface. Every change to the tree is instantly reflected on the screen. Knowing the DOM is the foundation of any frontend work, even if you later work through a framework: it still builds and updates that very same tree. In this chapter we will look at how nodes are organized, how to search, create and change them, the difference between attributes and properties, observers, and security, and then we will write our own simplified versions of these mechanisms.\n\nThe tree is made of nodes of different types. The root is the document, then come elements, text nodes and comments, and there is also the document fragment, which lives separately from the page. Every node has a parent, children, and a previous and next sibling. Through children you get only elements, through childNodes you get all the nodes, including the whitespace between tags, so the first child of an element is often a text node, not a tag. The nodeType property returns a number, the type. Collections come in two kinds, live and static: the list returned by getElementsByClassName updates itself when the tree changes, while the result of querySelectorAll is a snapshot taken at the moment of the call.\n\nSearch is the main operation. getElementById finds a single element by its identifier, and it is the fastest way. querySelector takes any CSS selector and returns the first matching element, and querySelectorAll returns all of them, in document order. You can search not only in the document but inside an element too: then only its subtree is walked. The matches method checks whether the element itself fits a selector, and closest climbs up through the ancestors and returns the nearest one that fits: this is the basis of event delegation. A selector can be put together from parts: a tag, an identifier, a class, an attribute, a descendant, a direct child, and a sibling.\n\nReading and writing content work differently. The textContent property gives and accepts plain text, and assigning to it is safe: any angle brackets just become letters. innerHTML parses the string as markup, so assigning user input to it is a direct road to cross-site scripting, because someone can inject a tag with a handler. innerText takes rendering into account and is therefore slower. The rule is this: insert text through textContent or by creating text nodes, and insert markup only from trusted sources or through a sanitizer. For security policies, browsers also have Trusted Types.\n\nCreation starts with the createElement method, which returns an empty element, and with createTextNode. Insertion is done with the methods append, prepend, before, after and replaceWith, and removal with the method remove. They accept several nodes and strings at once. To insert markup next to an element there is insertAdjacentHTML, with four positions. cloneNode copies a node together with its descendants if you pass true. To insert many elements at once, you collect them in a document fragment and add them in a single action: the page tree changes once, not a hundred times. The template tag keeps a blueprint of markup that you clone and fill in.\n\nAttributes and properties are not the same thing. An attribute is what is written in the markup, and it is always a string. A property is a field of an object, and its type can be anything. Many of them are linked: changing the id property changes the id attribute. But there are differences too: the value property of an input field changes as the user types, while the value attribute keeps the initial value. Boolean attributes such as disabled work by presence, not by value: even disabled equals false turns the element off. It is more convenient to change classes through classList with its add, remove and toggle methods, data through dataset, and styles through style, with getComputedStyle for the final values.\n\nWalking the tree can be written recursively, and for harder cases there is TreeWalker: it moves through the nodes, filtering by type and with a selection function. The contains method checks whether a node lies inside another one, and compareDocumentPosition reports the relative position of two nodes: before or after, ancestor or descendant. These operations are needed, for example, when sorting elements in document order and when checking where a click landed. Remember that walking the whole tree is expensive, and a selector search inside a small container is always better than one over the whole document.\n\nWeb components let you create your own tags. A custom element is registered with the define method, its name must contain a hyphen, and the class receives callbacks: connectedCallback when it is added to the document, disconnectedCallback when it is removed, and attributeChangedCallback when observed attributes change. Shadow DOM creates an isolated subtree: styles and selectors from outside do not get in, and from the inside they do not see the page. Slots define where the element's children end up in the shadow tree. This is how independent widgets are built, and many libraries are based on it.\n\nYou can subscribe to changes not by polling but with observers. MutationObserver reports added and removed nodes and changes of attributes and text, and it delivers the records in a batch as a microtask. IntersectionObserver tells you how much of an element is visible in the viewport, and it is used for lazy loading of images and for infinite feeds. ResizeObserver reports changes in the size of an element and replaces the window resize event where you need the dimensions of a particular block. All three work asynchronously and do not make the browser recalculate the layout, unlike manual measurements.\n\nDOM performance is determined by the number of layout recalculations. Do not read geometry between writes, collect changes into batches, and use fragments and classes instead of a dozen separate styles. Live collections are more expensive than ordinary arrays, so they are turned into an array before a loop. For long lists you show only the visible part and do not create the rest. Frameworks hide these concerns behind a virtual tree: they compare the description of the new state with the old one and apply only the difference. We will write such an algorithm in the last part of the book, but for now it is important to understand exactly what it optimizes.\n\nMarkup is turned into a tree by a well-defined algorithm. The parser fixes errors: unclosed tags, nested links, tables without a body. So the tree can differ from the text you wrote: for example, inside a table a tbody element will always appear. DOMParser parses a string into a separate document, and the reverse operation, serialization, turns a node into markup through outerHTML. For working with selection there are the Range and Selection objects, which point to positions inside text nodes and are used in editors and in copy features.\n\nThe DOM is also the foundation of accessibility. From it the browser builds the accessibility tree, which is read by screen readers. Semantic tags, such as a button, a list, a heading and a form, already carry a role and behavior: a button is reachable from the keyboard and announces itself. If your own element behaves like a button, it needs a role, ARIA attributes, focus management, and a tab order. The accessible name of an element comes from aria-label, an associated label, or its content. A correct DOM helps people, search engines, and tests alike. Developer tools let you inspect the tree, change attributes, and find handlers.\n\nLet us sum up. The DOM is a tree of nodes of different types, and children and childNodes show different things. The most convenient way to search is querySelector, matches and closest; live collections update themselves, static ones do not. Insert text through textContent, and markup only from trusted sources. Create nodes with the create methods and insert them in batches through a fragment or a template. Attributes are strings from the markup, properties are the state of objects. Custom elements and Shadow DOM give isolation, and observers report changes without polling. In the next chapter we will move on to styling: the cascade, flexbox, and grid.
