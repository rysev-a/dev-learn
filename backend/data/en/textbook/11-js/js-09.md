#CHAPTER 9 | Modules and Errors: ES Modules, CommonJS, Exceptions
Modern Frontend. Chapter 9. Modules and Errors: ES modules, CommonJS and exceptions. As long as a program fits in one file, everything is simple. But a real application consists of hundreds of files, and we need a way to split code into parts that don't clash over names and clearly declare what they take and what they give. These are modules. And we need a way to report failures honestly, so that one error doesn't bring everything down. These are exceptions. In this chapter we will go through both mechanisms. Modules prepare us for bundlers and packages, and errors prepare us for asynchronous code, where proper handling separates a good project from an unreliable one.\n\nA standard module, also known as an ES module, is a file with its own scope: its variables don't leak into the global scope. To hand something to the outside, you put the word export in front of a declaration. To take something, you write import, with curly braces and names, followed by the path to the file. A module can have many named exports, but only one default export, and that one is imported without braces, under any name you like. Modules always run in strict mode and execute only once, no matter how many times they are imported, and the result is kept in a cache. The extension m-j-s, or the type field in the package file, tells Node.js that the file is a module.\n\nHere is a peculiarity of imports: they don't copy values, they create live bindings. If a module changes an exported variable, every importer sees the new value. But you can't change an imported name from the outside, it is read-only. Imports are hoisted to the top and run before the rest of the code, so a conditional import inside an if is impossible. For such cases there is the dynamic import: the import function returns a promise with the module, so you can load code on demand, for example when a button is clicked. This is the basis of splitting an application into chunks. The address of the current module is available in the import meta object, and in the browser you include a module with a script tag of type module.\n\nThe old CommonJS format works differently. A file is a function that receives require, module and exports. Require is synchronous: it reads the file, runs it, and returns its exports. That's why you can call require anywhere in your code, even inside a condition. The result is set by assigning to module dot exports. The bindings here are not live: you get a copy of the reference to the object as it was at the moment of the call. These two worlds clashed for a long time. From an ES module you can import CommonJS, but going the other way you have to use a dynamic import. Most new packages are written in the standard format and published in both formats.\n\nModules can depend on each other in a circle: A imports B, and B imports A. In CommonJS the second module receives the first one's half-built exports, as we saw in the exercise in the chapter about history. In ES modules all bindings are created before any code runs, and touching a variable that is not yet initialized throws a reference error. It's better to avoid cycles: move the shared part into a third module. Another typical problem is barrels: an index file that re-exports everything in a folder. They are convenient, but they break up code splitting: by importing a single function you may drag in hundreds of files. Explicit imports are more precise.\n\nHow does the engine find a module? A path starting with a dot is relative: it is looked up next to the current file, and in the standard the extension is required. A path without a dot, such as lodash, is called a bare specifier: Node.js looks for such a package in node modules folders, climbing from the current folder to the root, and then reads the package file, where the exports field lists which entry points are open to the outside, and for each one you can name different files for different conditions: import, require, browser. The browser has no packages folder, so bare names there are mapped by an import map: a small piece of JSON in the page that links a name to an address. Bundlers solve the same problem ahead of time.\n\nNow let's move on to errors. An exception is an object that interrupts the normal flow of the program and bubbles up the call stack until a try-catch block catches it. You throw it with the throw statement. You can throw anything, but the convention is to throw an instance of the Error class or one of its subclasses. An error has a name, a message and a stack trace, a string with the chain of functions leading to the place where it was thrown. The built-in subclasses are TypeError, RangeError, SyntaxError and ReferenceError. The finally block always runs, even when you leave the function through a return, so that is where you release resources: close files and connections.\n\nA good error tells you what happened and what to do about it. Write your own classes: validation, network, not found. Put a machine-readable code and some context into them. The cause field, added in recent versions, lets you wrap the original error in a more meaningful one without losing the root cause: the new error gets an object with a cause field as its second argument. Then the log shows a chain: failed to save the order, caused by a dropped connection, caused by a timeout. AggregateError combines several errors at once, for example when several requests fail in parallel. Catch only what you know how to handle, and let the rest bubble up.\n\nNot every failure has to become an exception. Expected outcomes are better returned as values: searching an array returns undefined, and parsing user input returns a success-or-error object with fields. This approach is called a result. It forces the calling code to check the outcome explicitly and doesn't let you forget to handle it. Keep exceptions for the truly exceptional: broken contracts and unrecoverable failures. Before writing a handler, tell programmer errors, such as touching undefined, apart from operational errors: the disk is full, the network is gone. The first kind you fix in the code, the second you handle at runtime and try again.\n\nRetries are a typical technique. A network request can fail because of a temporary glitch, and it makes sense to try again. But you have to do it wisely: limit the number of attempts, increase the pause between them exponentially, and add some randomness so that thousands of clients don't hit the server at the same moment. You can retry only idempotent operations, meaning those where repeating does no harm: reading, but not charging money. Another technique is a fallback value: if you couldn't fetch fresh data, show stale data. And finally, the timeout: every input-output operation must have a waiting limit, otherwise a hung request will freeze the program forever.\n\nWhat happens if nobody catches an exception? In the browser, the error is printed to the console, but the page keeps living. In Node.js, an unhandled exception terminates the process. For the last line of defense there are global handlers: in the browser, the error event on the window and the unhandled rejection event for promises, and in Node.js, the uncaught exception and unhandled rejection events on the process. They are used to send a report to a monitoring system, but not to pretend that everything is fine: after an uncaught error the state of the program is unknown, and it is safer to shut down gracefully. Monitoring tools like Sentry collect such reports together with a source map.\n\nSome useful debugging habits. Read the stack from the bottom up: the bottom line is where it all started, the top line is where it was thrown. Turn on pausing on exceptions in the console and look at the values at the moment of failure. Assertions, the assert function from the Node.js module, quickly check your assumptions. Write messages with context: not invalid value, but age must be between zero and one hundred fifty, got minus five. Don't swallow exceptions with an empty catch: it is the most common way to turn an error into a mystery. And don't throw strings: they have no stack, and you can't tell one failure from another by them.\n\nLet's sum up. A standard module has its own scope, live bindings, a default export and named exports, and dynamic import loads code on demand. CommonJS is synchronous and returns a copy, and dependency cycles are better removed. Exceptions bubble up the stack, you catch them with try-catch, and finally releases resources. Custom error classes and the cause field make failures easy to understand. Expected outcomes are returned as values, network calls are retried with a pause and a timeout, and uncaught errors go to monitoring. In the next chapter we move on to asynchrony: promises and async await.
