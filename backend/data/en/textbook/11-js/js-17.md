#CHAPTER 17 | CSS: the Cascade, Inheritance, Units and Variables
Modern Frontend. Chapter 17. CSS: the cascade, inheritance, units and variables. The first word in the name, cascading style sheets, is not decoration, it is the essence of the language. Styles reach a single element from several sources at once: the browser's built-in sheet, the author's files, the style attribute, and sometimes the reader's own settings. Rules easily contradict each other: one paints a paragraph red, another blue. The cascade is a set of strict rules by which the browser, with no randomness at all, picks exactly one winner for every property of every element.\n\nWhen rules disagree, the browser walks down a ladder of steps. First it looks at origin and importance: a declaration marked important beats an ordinary one. Then at the layer, if layers are in use. Then it compares the specificity of the selectors: an ID weighs more than a class, and a class more than an element name. If it is still a tie, the rule written later wins. Notice that it is not whole rules that compete, but individual declarations about the same property. So an element's color can come from one rule and its padding from another, and nothing gets lost.\n\nThe important flag lifts a declaration above all ordinary ones, which is why people love it and hate it so much. The only way to override it is with the same flag and a higher specificity, and your styles turn into an arms race. It is justified in utility classes that must always win, for example a class that hides an element. For real order, cascade layers were invented. You declare them as a list, and a layer named later beats the earlier ones regardless of specificity. A reset, a library and your own code line up in a clear queue, and nobody has to shout.\n\nSome properties children receive from their parents on their own, and this is called inheritance. Text properties are inherited: color, font family and size, weight, style, line height, alignment. That is why it is enough to set the font once on the body of the page, and it reaches every paragraph and every link. Padding, borders, background, sizes and positioning are not inherited: otherwise every nested card would draw its border all over again. The background only looks inherited: by default it is transparent, and the parent simply shows through the child.\n\nYou can control inheritance by hand with four keywords. Inherit tells the element to take the value from its parent, even if the property is not normally inherited. Initial resets the property to its starting value from the specification. Unset is the clever one: for inherited properties it works like inherit, for all the others like initial. Revert rolls the property back to the browser's styles, that is, to what you would get without your stylesheet. A classic example: form fields do not take the page font by default until you explicitly ask them to inherit the font from the parent.\n\nLengths come in absolute and relative kinds. The pixel is a screen unit: clear, but deaf to the reader's settings. Relative units scale. The em is computed from the font size of the element itself, and nested ems multiply: at the third level of nesting it is easy to end up with huge text. The rem is computed from the font size of the root element, so it is predictable and respects the browser's settings. Percentages are taken from something on the parent, and from what exactly depends on the property. Font sizes and spacing are usually written in rems, thin lines and borders in pixels.\n\nThere are also units tied to the window. V-w is one hundredth of the window width, v-h one hundredth of its height. On a phone the window height jumps when the address bar hides, so dynamic variants appeared: d-v-h always equals the visible part. There are also units tied to the text: ch equals the width of a zero in the current font, and l-h equals the line height. It makes sense to limit the width of a text column to sixty or seventy characters: such a line is comfortable to read, and it holds on any screen by itself, without media queries.\n\nA color can be written in different ways. Names like red or navy are fine for sketches. Hexadecimal notation with a hash sign is the most common: two digits each for red, green and blue. The rgb function does the same with decimal numbers. HSL describes a color the human way: a hue on the color wheel in degrees, saturation and lightness in percent, and you can make a color darker or paler by changing a single number. Transparency is set by a separate parameter. And the keyword currentcolor means the text color of this element, and lets a border or an icon paint itself to match the text.\n\nCalculation functions let you mix different units. Calc evaluates an expression, say, the window width minus a fixed margin. Min takes the smallest of its values, max the largest. Clamp takes three numbers: a lower bound, a preferred value and an upper bound. The result grows with the window but never leaves its bounds. That is how fluid typography is made: a heading grows smoothly from sixteen to forty pixels without a single media query. It is worth writing the preferred value together with rems, so that the browser's page zoom keeps working.\n\nCustom properties are the variables of CSS. A name begins with two hyphens, and they are declared like ordinary properties inside a rule. You read them with the var function, and the second argument can give a fallback value in case the variable does not exist. The main difference from the variables of ordinary languages: they are inherited and live in the cascade. Declared on the root, a variable is visible everywhere. Redefined inside a block, it changes only for that block and its descendants. So the same component can be recolored simply by setting a different value on its parent.\n\nThemes are built on variables. First, on the root, you declare a set of semantic colors: background, text, accent, border. All the other rules use only these names and know nothing about colors themselves. To get a dark theme, it is enough to redefine the same names inside a block with a special class or inside a media query about the preferred color scheme. The browser itself reports which scheme the person chose in their system, and the site adapts without a single extra line. It is also good practice to add a manual switch and to remember the choice in storage.\n\nThe troubles of the cascade repeat themselves. A rule does not apply because a more specific one overrides it, and you are editing the wrong selector. A typo in a property name is silently discarded. A unit is forgotten: zero without a unit is allowed, but ten without a unit is not, and the whole declaration vanishes. Nested ems blow up the font. ID selectors cement the order for good. You look for the cause in the developer panel: it shows which rules were applied, which are crossed out and why, and the computed tab gives the final result for each property and where it came from.\n\nLet us sum up. Do not fight the cascade, design it: simple class selectors, low specificity, the important flag only for utility cases. Set the font and color on the root and make use of inheritance. Write text sizes in rems, line length in characters, fluid sizes with clamp. Move colors and spacing into variables, and get themes by redefining them. When in doubt, open the developer panel instead of adding one more ID. In the next chapter we will see how the browser lays out boxes on the page: margins, borders and flow.
