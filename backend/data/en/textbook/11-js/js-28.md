#CHAPTER 28 | Performance: what to measure and how to speed up
Modern Frontend. Chapter 28. Frontend performance. A fast site is not a high score in a lab test. It is the feeling the user has: the page appears quickly, responds to taps and clicks, and doesn't jump around. Optimizing blindly makes no sense, so first we'll pick the metrics, then go through loading, size, the main thread, layout, long lists and memory, and finally learn to profile and to catch regressions. In the exercises we'll write our own metric calculations, a task scheduler, a virtual list, an image picker, a leak tracker and a budget checker.\n\nThe key metrics are called the Core Web Vitals. Largest Contentful Paint shows when the main part of the page appeared; a good value is no more than two and a half seconds. Interaction to Next Paint is the worst response time to clicks and key presses; good means under two hundred milliseconds. Cumulative Layout Shift measures how much elements jump around; good means no more than point one. They are judged at the seventy-fifth percentile of real users, while lab measurements, such as Lighthouse, only help you find the cause.\n\nPage loading comes down to the critical rendering path: the browser doesn't paint until it has the markup and has processed the styles, and ordinary scripts block parsing of the document. Scripts are marked with the async and defer attributes. Hints to the browser speed up what it would discover too late: preconnecting to a third-party origin, preloading a font or the main image, and a fetch priority for the main image. Don't overdo it: every extra hint takes bandwidth away from what really matters.\n\nFewer bytes means everything is faster. Text is compressed with the Brotli algorithm, code is minified, and unused code is cut out by tree shaking. Images are served in modern formats, and a set of sizes is described with the srcset and sizes attributes, so that a phone doesn't download a huge file. The width and height attributes reserve space and reduce layout shifts, and lazy loading postpones whatever is off screen. For fonts, you pick a character subset and a display mode: while the font is loading, it's better to show a fallback than an empty gap.\n\nCode splitting removes from the first load everything the user doesn't need yet. A dynamic import turns a module into a separate file that loads on navigation to a route or on a click, and neighboring routes can be prefetched ahead of time while the browser is idle. Keep an eye on the budget: total script size, the number of requests, and the weight of each entry point. A bundle analyzer shows which dependency bloated the build, and it often turns out that a whole library is included for the sake of a single function.\n\nThere is only one main thread, and tasks longer than fifty milliseconds count as long: while they run, the page doesn't respond. Heavy work is cut into pieces, handing control back to the browser between them, and fully independent computations are moved to a worker. For deferred work, use a scheduler with priorities and the browser's idle time; for animations and measurements, use the animation frame callback, which runs before every paint. The main idea is that user input should get its turn before background tasks.\n\nLayout and repaint are a frequent cause of slowdowns. Reading dimensions right after changing styles forces the browser to recalculate the layout immediately; do that in a loop and you get what is called layout thrashing. The cure is to read everything first and then write everything, and to batch the changes into a single frame. Animate only transform and opacity, because they run on the compositor without any layout. The containment and content-visibility properties let the browser skip processing what the user can't see.\n\nLong lists are not rendered in full. Virtualization keeps only the visible rows in the document, plus a small margin, and imitates the total height with an empty block; as the user scrolls, you compute which indexes to show. For rows of different heights, you store running sums and find the index with a binary search. The appearance of elements in the viewport is tracked with an intersection observer, and changes of size with a resize observer: neither puts constant position checks on the main thread.\n\nMemory leaks make an application slower and slower. Typical causes are forgotten event listeners, timers and subscriptions, closures that hold large objects, and detached document nodes that are still referenced. Weak references and weak maps help, since they don't prevent the garbage collector from doing its job, and so does the habit of unsubscribing when a component is destroyed. In the developer tools, you compare memory snapshots before and after an action: if the number of objects grows on every repeat, you've found a leak.\n\nProfiling starts with measurement. The performance panel shows a flame chart: what ran, and for how long. In code, you use marks and user-timing measures, and a performance observer receives entries about long tasks, paints and layout shifts. Real data is collected right from users: sampled, in batches, and sent with a beacon when the user leaves the page. This way you see how the application behaves on weak phones and slow networks, and not only on the developer's machine.\n\nCaching and the network complement the code. Static files with a hash in the name are served with the immutable directive for a year, while pages get a short revalidation. The back-forward cache gives an instant return when the user presses the back button, but unload handlers, a ban on caching and open connections all break it. You can also hint to the browser where the user will go next: speculation rules let it prefetch or even prerender the next page, but you have to take data saving and network speed into account.\n\nPart of the work can be moved to the server: send ready-made markup, and turn on hydration of the interactive parts only when needed, on load, when idle, when they appear on screen, or on first interaction. This approach is called islands architecture. So that speed doesn't slide back, add budgets to the change checks: the build fails if a size or a metric goes over its limit. You should compare the medians of several runs, because a single measurement is almost always noisy.\n\nLet's sum up. First we measure: the core metrics from real users, and lab measurements to find the causes. We speed up loading with hints, compression, the right images and code splitting. We free the main thread, spare the layout, and virtualize long lists. We watch memory, profile, and collect real-world data, and budgets in the checks keep speed from sliding back. In the next chapter we'll move to the server and see how Node.js works inside.
