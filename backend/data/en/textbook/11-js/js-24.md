#CHAPTER 24 | Events: Bubbling, Capturing, and Delegation
Modern Frontend. Chapter 24. Events: bubbling, capturing, and delegation. A page lives on reactions: the user clicked, typed, scrolled, the network answered, a timer fired. All of these are events. The model is simple: an object announces that something happened, and subscribers get a notification and react. But in the browser an event travels a path through the tree, it has a default action that can be canceled, and there are many subtleties that make a handler fire in the wrong place or at the wrong time. In this chapter we will look at how events work, the three phases, delegation, the mouse and the keyboard, custom events, and ways to deal with frequent events.\n\nYou subscribe with the addEventListener method: the event name, a function, and optional parameters. You can remove a handler with removeEventListener, but you need the same reference to the function, so an anonymous arrow function cannot be removed. The parameters let you specify once, to run one time and unsubscribe, passive, a promise not to cancel the default action, and signal, to unsubscribe many listeners at once through an AbortController. Handlers can also be written to the onclick property or as an attribute, but the property holds only one function, and the attribute mixes markup with code, so we use listeners. The handler receives an event object describing what happened.\n\nAn event has a path. When the user clicks a nested element, the event goes through three phases. First comes capturing: from the window down through the ancestors to the target. Then the target phase, where the handlers of the element itself fire. Then bubbling: back up to the window. A subscription listens to bubbling by default, and the third parameter, capture, subscribes to the capturing phase. The target property is the element where the event originated, and currentTarget is the one whose handler is running right now. Some events do not bubble, for example focus and blur; for them there are the paired events focusin and focusout, and the mouseenter event fires only on the element itself.\n\nYou can stop the path with the stopPropagation method: the event will not go to the next elements in the chain, but the other handlers on the current element still run. The stopImmediatePropagation method stops those too. You should not overuse stopping: it breaks other people's handlers and analytics, which count on bubbling. If you need to know that an event has already been handled, it is better to keep your own flag or to check cancelable and defaultPrevented. The whole path of an event can be obtained with the composedPath method; it is useful for debugging and when working with Shadow DOM.\n\nDelegation follows from bubbling. Instead of a hundred handlers on a hundred buttons, you put one on a common parent and use the target to find out where the event landed. For this you need the closest method: the event may come from a small icon inside a button, and you have to climb up to the element you need. You save memory, and you get the main advantage: elements added later work without any extra subscription. The action is often stored in a data-action attribute, and one handler picks a function by its name. The limits: the event must bubble, and the target you found must lie inside the container.\n\nMany events have a default action: a click on a link goes to its address, submitting a form reloads the page, the space bar scrolls the window. The preventDefault method cancels it, but only if the event is cancelable. Scroll and touch handlers can be marked passive: then the browser does not have to wait for the handler to finish before it starts scrolling, and the interface stays smooth, but you can no longer call preventDefault from such a handler. The habit of returning false from onclick has long been outdated. Remember other tools too: text selection, the context menu, and dragging also have standard behavior.\n\nFor the mouse there are click, double click, press, release, and move. But today it is more convenient to use the unified pointer events: pointerdown, pointermove, pointerup, and pointercancel. They work the same way for a mouse, a pen, and a finger, every pointer has its own identifier, and the setPointerCapture method lets an element receive all the events of a pointer even when the cursor has left its borders: dragging and sliders are built on this. Coordinates can be relative to the window, to the document, and to the element, and they are easy to mix up. The old touch events, touchstart and touchmove, are used when you need support for gestures such as a pinch.\n\nThe keyboard events are keydown and keyup. The keypress event is obsolete. The key property tells you which character will result, taking the layout into account, while code says which physical key was pressed, and for hotkeys you usually need code, so that the combinations work in any layout. The repeat property shows auto-repeat while a key is held down. The modifiers, Control, Shift, Alt, and Meta, are in the event too. For typing in Asian languages there are composition events: they report text being entered through an editor, and you must not react to keydown at such moments. Do not forget accessibility: an interactive element must also be operable from the keyboard.\n\nForm and focus events. Focus and blur fire when you enter and leave a field, and they do not bubble. The input event fires on every change of the value, and change fires when the change is finished, usually when focus is lost. The submit event arrives on the form, and it is intercepted to send the data without a page reload. The beforeinput event lets you check the input in advance, and the clipboard events copy, paste, and cut let you change what ends up in the clipboard. To manage focus from code there is the focus method, and the Tab order is set by tabindex and the structure of the document.\n\nYou create your own events with the CustomEvent constructor: a name and an options object, where the detail field carries the data, bubbles allows bubbling, and composed allows leaving the boundaries of Shadow DOM. You send them with the dispatchEvent method. Any object can become an event target if it inherits from EventTarget, and in Node.js there is EventEmitter for the same role. An event bus helps decouple the parts of an application, but overusing it turns a program into a tangle of invisible links. Events are not the cheapest mechanism: subscriptions must be removed when a component leaves the page, otherwise the handler keeps objects alive in memory.\n\nSome events arrive very often: scroll, resize, mouse move. If you do heavy work on each of them, the interface starts to stutter. Debounce postpones the call until there is a pause in the events, and it suits search while typing. Throttling lets calls through no more often than a given interval, and it suits scrolling. For animations you keep the last value and process it in requestAnimationFrame. To track visibility, IntersectionObserver is better than a scroll handler. Passive listeners and one AbortController per component make both speed and cleanup simpler.\n\nEvent handlers run as tasks of the event loop, and between them the browser clears the microtasks. But if you call the click method or dispatchEvent yourself, the handlers run synchronously, inside your call, and the microtask queue is not processed yet. This matters for tests and for the order of effects. Complex interactions, such as dragging, long press, double tap, and swipe, are convenient to describe with finite state machines: a state and transitions on events. Then the logic is separate from the handlers, and the edge cases, such as canceling a drag with the Escape key, are visible right away.\n\nLet us sum up. Subscribing is addEventListener with the options once, passive, and signal; a handler can be removed only by the same reference. An event goes through capturing, the target, and bubbling, and target and currentTarget differ. Delegation puts one handler on a container and uses closest. preventDefault cancels the standard action, and passive listeners speed up scrolling. Pointer events and key codes smooth out the differences between devices. CustomEvent and EventTarget create your own events, debounce and throttling tame the frequent ones, and complex gestures are described with state machines. In the next chapter we will move on to forms and data storage.
