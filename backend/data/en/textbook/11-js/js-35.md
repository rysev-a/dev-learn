#CHAPTER 35 | TypeScript, linters and formatting: tsc, ESLint, Prettier
Modern Frontend. Chapter 35. TypeScript, linters and formatting: tsc, ESLint, Prettier. JavaScript does not check types: a typo in a field name or a call with the wrong argument shows up only when the code runs, and sometimes only in production. TypeScript adds a description of types to the language and checks them before execution. It is a superset of JavaScript: any valid JavaScript is also valid TypeScript. Types exist only during checking and are erased at build time, so the code runs just as fast as plain JavaScript. And linters and a formatter take care of style mistakes and arguments about spaces.\n\nThe basic types are string, number, boolean, null and undefined. An array is written with square brackets after the type. An object type lists its fields. A union allows one of several values: a string or a number. A literal type allows exactly one value, for example the word up. Annotations go after the name, separated by a colon. But TypeScript infers types from assignments on its own, so local variables usually need no annotations; they are needed at the boundaries: in function parameters and in the public interfaces of modules.\n\nThe shape of an object is described by an interface or by a type alias. A field can be optional, marked with a question mark, or read-only. The main feature of TypeScript is structural typing: a value fits a type if it has all the required fields of the required types, no matter how it was created. Extra fields are fine, except in an object literal, where an excess property counts as an error. Interfaces extend one another, and aliases combine through intersection. For functions, unions and computed types you use aliases; for describing objects, both options work.\n\nFor a function you type the parameters and the result. A generic, a type parameter, lets you describe the relationship between them: the function takes an array of elements of type T and returns an element of the same type. TypeScript infers T from the arguments on its own. The extends constraint narrows the allowed types: T must have a length field. Generics exist for arrays, promises, maps and sets. A well-written generic function preserves type information instead of turning everything into any, and that is one of the main advantages over manual checks.\n\nA value of type string or number cannot be used as a string until it has been checked. Type checks, the in operator, instanceof and comparison with a literal narrow the type inside a branch: after a typeof check for string, TypeScript knows it is a string. Discriminated unions are especially handy: every variant has a tag field, say kind, and checking the tag identifies the whole variant. If all variants are handled, what remains has the type never, the impossible value, and adding a new variant will highlight the places where you forgot to handle it. It is a way to get a completeness guarantee straight from the compiler.\n\nTypeScript can compute types from other types. Partial makes all fields optional, Required makes them mandatory, Pick selects the fields you need, Omit excludes the extra ones, and Record builds a dictionary. ReturnType extracts the type of a function's result, and Parameters the types of its parameters. Behind them stand mapped and conditional types, which you can write yourself. A rule of thumb: derived types are best computed from a single source, so that a change in one place automatically reaches the others, instead of copying field descriptions.\n\nThe compiler's behavior is set by the tsconfig file. The strict option turns on a set of strict checks: a ban on implicit any, checking for null and undefined, strict function types, and mandatory initialization of class properties. For a new project it is always on. The target defines which version of the language to emit, and module and module resolution define which import rules to apply. The no-emit option says the compiler only checks, and another tool does the build. Configs can extend one another, so the shared part is moved into a base file.\n\nTo run TypeScript, it is enough to strip out the types: esbuild and SWC do this in milliseconds, but they do not check correctness. Checking is a separate step: tsc with no-emit runs in the editor and in continuous integration. For JavaScript libraries, types live in files with the dot d dot ts extension. For popular packages the community writes them in the DefinitelyTyped project, and they are installed as at-types packages. Library authors generate such files themselves during the build and name them in the manifest with the types field.\n\nTypes exist only at check time, while data arrives at run time: from the network, from files, from the user. If you write that a server response has such-and-such a type, TypeScript will believe you but will not verify it. So at the boundary of the system you accept the value as unknown and check it, with a type guard function or with a validation library such as Zod. The result of the check is then safe to use as typed. The as keyword and the any type switch checks off and should be rare exceptions, not a way to make the compiler keep quiet.\n\nESLint reads the code, builds an abstract syntax tree and checks it against rules. A rule finds a specific problem: an unused variable, a loose equality comparison, a forgotten await. Each rule can be turned off, made a warning, or made an error. The flat config lists blocks of settings for different files, and plugins add new rules: for TypeScript, for React, for accessibility. Many findings are fixed automatically with the fix flag. ESLint catches what types cannot see, and its warnings are worth reading, not suppressing.\n\nPrettier is a formatter with a minimum of settings. It parses the code into a tree and prints it again by one set of rules: line width, quotes, semicolons, trailing commas. The result does not depend on how the code was written, so a commit diff shows only real changes. The linter and the formatter must not argue: the eslint-config-prettier configuration turns off the style rules that conflict. The editorconfig file stores indentation and line endings for every editor on the team, and Prettier decides the rest.\n\nStyle and checks work only if they run automatically. Before a commit, Husky runs lint-staged: the linter and the formatter process only the changed files, which is fast. In continuous integration, all the checks run in full: tsc with no output, ESLint, Prettier with the check flag, and the tests. If even one fails, the changes are not accepted. The editor shows the same errors as you type, so by the time of the commit there are almost none left. Shared settings live in the repository, and a newcomer gets a working environment with one command.\n\nLet's sum up. TypeScript checks types before running and erases them at build time. Types describe the shapes of objects, and structural compatibility is decided by fields. Generics preserve the relationships between types, narrowing works through checks, and discriminated unions give exhaustive handling. Utility types derive some types from others. Strict mode in tsconfig is a must. Data from outside is checked with validators. ESLint catches bad practices, Prettier evens out style, and Husky and continuous integration run it all automatically.
