#CHAPTER 32 | Package managers: npm, pnpm, Yarn, package.json, semver and lock files
Modern Frontend. Chapter 32. Package managers: npm, pnpm, Yarn, package.json, semver and lock files. A modern project consists mostly of other people's code. Some dependencies you add yourself, others come in transitively, and in the end the node modules folder holds hundreds or even thousands of packages. The package manager is responsible for finding the right versions, downloading them, laying them out on disk, and making sure every developer and the build server end up with exactly the same result. In this chapter we'll look at how a package is structured, how versioning works, how dependencies are resolved, and how the managers differ.\n\nThe main file of a project is called package.json. It holds the name and version, the dependencies, the scripts and the entry points. The dependencies field lists what the code cannot work without, and dev dependencies lists what is needed only during development: tests, the bundler, the linter. Peer dependencies says which version of a library the host must provide, for example React for a plugin. The type field chooses the module system, exports defines the public entry points, and scripts holds the commands you run through npm run. This is the passport of the project, and you need to be able to read it.\n\nPackage versions follow the semver convention: three numbers separated by dots. The first, major, goes up when compatibility breaks. The second, minor, goes up when new features are added without breaking the old ones. The third, patch, goes up when bugs are fixed. After a hyphen there can be a prerelease tag: alpha, beta, release candidate; such a version is considered earlier than the release without a tag. A plus sign adds build information, which is ignored when versions are compared. The convention works only if authors follow it, so you cannot trust it completely.\n\nIn dependencies you usually specify not an exact version but a range. A caret with version one point two point three allows any version from that one up to, but not including, the next major, that is, up to two point zero point zero. A tilde allows only patches: from one point two point three up to one point three point zero. For zero versions the caret is stricter: zero point two point three allows only zero point two point anything, because while the version is zero, any change may break things. There are also comparisons, the asterisk, hyphen ranges, and union with two vertical bars. An exact version with no symbols pins the package, but then you are responsible for every update yourself.\n\nEvery package has its own dependencies, and those have theirs, so you get a tree. For each dependency the manager picks the highest matching version from the registry. To avoid storing the same thing many times, shared versions are hoisted up into the root node modules folder. If two packages require incompatible versions, one stays at the top, and the other is nested in a node modules folder inside the package that needs it. That is why in a large project the same package can show up in several versions, and this is the second reason, after the dependencies themselves, why disk usage keeps growing.\n\nRanges mean that today and a month from now you will get different versions, and the project can break without any change to your code. The lock file solves this problem: it records the exact versions of all packages in the tree, together with their addresses and checksums. The manager installs exactly those and updates them only when you tell it to. The file is committed to the repository. On the build server you use npm ci: it installs strictly from the lock file, fails if the lock file disagrees with the manifest, and deletes the old node modules folder. The checksum protects against the contents of a package being tampered with.\n\npnpm solves two problems. The first is space and speed: all packages live in one store on your computer, files are addressed by their content, and they get into a project as hard links, without copying. The second is honesty about dependencies. In an ordinary node modules folder, because of hoisting, code can import a package that is not in the manifest: it simply happened to be nearby. Such phantom dependencies break on any update. In pnpm only the declared packages are available, and the rest are hidden in a service folder.\n\nYarn appeared as a faster and more reliable replacement for the early versions of npm, and it introduced much of what later became standard: the lock file, workspaces, the cache. Modern Yarn, called Berry, went further: Plug'n'Play mode stores packages as archives and connects them through its own loader, with no node modules folder at all. This is faster and stricter, but it needs support from the tools, and not all of them have it. For a project, the choice between managers is a matter of team and tooling: the important thing is not to mix them in one repository and to pin the version of the manager.\n\nWhen a project has several packages, they are kept in one repository, a monorepo. In the root manifest the workspaces field lists the package folders, and the manager installs dependencies once for all of them and connects the packages to each other through local links. In pnpm and Yarn there is a workspace protocol for this: an asterisk or a version, and on publishing it is replaced with the real version. Shared tools, such as the linter and the tests, live in the root. The advantage is atomic changes across several packages at once, and the price is a more complex build and configuration.\n\nThe scripts field turns a project into a set of commands: build, test, run. The npm run command adds the node modules slash dot bin folder to the PATH variable, so installed tools can be called by name without a global install. A script can have hooks: pre followed by the name runs before, and post followed by the name runs after. To run a package once without installing it, use npx, and in pnpm the equivalent is pnpm dlx. Scripts are a single entry point for both people and the build server, and if they are described, a newcomer can start the project with one command.\n\nDependencies need to be updated, otherwise vulnerabilities and lag pile up, and you end up catching up in one painful rush. The outdated command shows which packages are out of date and by how much: patch, minor or major. Patches and minors are usually safe, while majors are read about in the changelog. The audit command reports known vulnerabilities from an advisory database. Services like Dependabot and Renovate help automate the process: they create update requests on their own, and the tests in continuous integration confirm that nothing broke.\n\nHere are the problems you meet most often. A phantom dependency: the code imports something that is not in the manifest. A peer dependency conflict: a plugin needs a version of a library that the project doesn't have. Duplicates: one package in several versions bloats the bundle. A dependency with a huge tree pulled in for a single function. A forgotten lock file, or two different ones in one repository. Installing from untrusted sources. There is one cure: look at the tree, since the npm ls command will show it, keep the manifest honest and the lock file fresh, and regularly remove whatever you don't use.\n\nLet's sum up. The package manager finds, downloads and lays out dependencies. The manifest describes the package, its dependencies and its scripts. Versions follow semver, and ranges with a caret and a tilde define the allowed updates. The manager builds a tree, hoisting shared versions to the top. The lock file pins exact versions and hashes, and continuous integration installs from it. pnpm saves space and forbids phantom dependencies, while Yarn offers Plug'n'Play and workspaces. Updates and audits should be done regularly. In the next chapter we'll look at where packages come from: registries and supply chain security.
