#CHAPTER 30 | An HTTP Server in Node.js: Routes, Middleware and a JSON API
Modern Frontend. Chapter 30. An HTTP Server in Node.js: Routes, Middleware and a JSON API. It is useful for a frontend developer to understand what sits on the other side of a request, and Node lets you write a server in the same language. The built-in http module already has everything you need: listening on a port, parsing requests and sending responses. Step by step we will build a router, a chain of handlers, request body parsing, JSON responses and error handling, and in the exercises we will test everything against a real server that runs on the loopback address inside the sandbox.\n\nThe createServer function takes a handler with two arguments: a request and a response. The request is a readable stream: it has a method, a URL and headers. The response is a writable stream: first you set the status code and headers, then you write the body and call end. The listen method binds the server to a port; if you pass zero, the system picks a free one, and you can ask the server for the address. The handler is called separately for every request, and they all run in one thread, so a handler must never block for long.\n\nThe router decides which handler to call. A route key is a method and a path: a GET to the users address returns a list, and a POST to the same address creates a new user. Paths can be static or have parameters, for example users, colon, id: from the address users slash forty-two the parameter is the string forty-two. The request URL should be parsed with the URL class, separating the path from the query string. For an unknown path you answer four hundred four, and if the path exists but the method does not fit, you answer four hundred five with an Allow header that lists the permitted methods.\n\nThe request body arrives in pieces. The request is a stream, so the data has to be collected: subscribe to the data event, push the chunks into an array, and on the end event join and parse them. The modern way is an asynchronous loop over the request. The size must be limited: a client can send gigabytes, so when the limit is exceeded you answer four hundred thirteen and stop reading. The body is parsed depending on the Content-Type header. If the JSON is invalid, you answer four hundred instead of crashing with an exception: a server must not die because of a bad client.\n\nA server response consists of a code, headers and a body. For a JSON API the Content-Type header is application slash json, and the body is produced with JSON stringify. The status code must describe the outcome precisely. Two hundred is success, two hundred one is created, two hundred four is success with no body. Four hundred is an error in the request, four hundred four is not found, and four hundred twenty-two means the body was parsed but failed validation. The five hundreds are server errors. A single format for the error body, for example with the fields code and message, saves clients from guessing.\n\nCommon actions such as logging, token checking and body parsing are moved into intermediate handlers, called middleware. Each one receives the request, the response and a function called next. It can do its own work and call next, passing control further, or finish the response itself. Order matters: first the log, then the access check, then body parsing, then the route. The chain can be assembled with a function called compose: it calls the handlers one by one and stops if somebody did not call next. This is how Express, Koa and many other frameworks work, and the mechanism fits into twenty lines.\n\nAn exception in a handler must not bring the process down. If the handler is asynchronous, you need to wait for its result and catch the promise rejection: a forgotten promise with an error stays unhandled, and in modern versions of Node it terminates the process. For this the chain has an error handler: it receives the error and builds a response. Known errors, for example not found or failed validation, turn into their own codes, and all the others become a five hundred with no details sent out. The details are written to the log, so that the client does not see the inner workings.\n\nFilters, sorting and pages are passed in the query string. It is parsed by the URLSearchParams class: it handles repeated keys and decodes percent signs. All values arrive as strings, so numbers have to be converted and their bounds checked: the page is at least one, and the page size is at most one hundred. A list response is best accompanied by metadata: the total number of records and links to the next and previous pages. Safe defaults free the client from required parameters, and hard limits protect the server from requests for a million rows.\n\nA browser will not let a page from one origin read a response from another unless the server explicitly allows it. The permission is given by the Access-Control-Allow-Origin header. For requests with non-standard headers or methods, the browser first sends a preliminary OPTIONS request and waits for the list of allowed methods and headers. The server answers it with no body and with the right headers. It is better to allow specific addresses from a list than an asterisk, especially when cookies are involved. And do not forget the security headers: the ban on content type sniffing and the content security policy.\n\nStatic files are served as a stream: the createReadStream function reads in chunks, and pipe sends them straight into the response without loading the whole file into memory. The content type is determined by the extension. The most dangerous spot is the path. If you put the address into the file name as is, a request with dot-dot segments will step outside the directory and read other people's files. So you join the path with the root and check that the result stayed inside the root. For large files you support the Range header, so the client can fetch the rest later, and for caching you use ETag.\n\nA server on the internet meets not only well-behaved clients. A slow client can hold a connection for hours, a huge body eats memory, and a flood of requests from one address gets in the way of everyone else. Protection consists of limits: a timeout for receiving headers and the request, a maximum body size, a limit on the request rate, and the number of simultaneous connections. Keep-alive lets you reuse a connection, but it too has an idle timeout. Graceful shutdown works the same way as in the previous chapter: stop accepting new connections and wait for the current ones.\n\nA server is convenient to test as a black box. The test starts it on port zero, finds out which port was chosen, and calls it with the ordinary fetch that Node has. This way real headers, codes and bodies are checked, with no faked requests. Each test starts its own server and closes it at the end, so tests do not affect one another. Logic not tied to the network, for example route parsing and input validation, is better moved into pure functions and tested separately: such tests show faster and more precisely where something broke.\n\nLet's sum up. An HTTP server in Node is a handler that receives a request and writes a response. The router picks a handler by method and path, and parameters are cut out of the pattern. The body is read as a stream with a size limit. Responses should be sent with exact codes and a single error format. Middleware forms a chain, and errors turn into responses. Static files are served as a stream with path protection, limits and timeouts protect against hostile clients, and tests start the server on port zero. For the frontend, a server is above all a contract: addresses, codes, the error format and headers, and it matters more than the framework you pick.
