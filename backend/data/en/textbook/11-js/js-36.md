#CHAPTER 36 | Reactivity: signals, subscriptions and computed values
Modern Frontend. Chapter 36. Reactivity: signals, subscriptions and computed values. We begin the last part of the book: we are going to build our own mini-framework. The idea behind every modern framework is simple: the interface is a function of state. The state changed, so the interface must change. Updating every DOM element by hand is tedious and breeds bugs: somewhere you forgot, somewhere you updated twice. Reactivity takes this job on itself: it knows which part of the interface depends on which data, and when something changes it recomputes exactly what is needed. We will implement this core from scratch in a few dozen lines.\n\nThe simplest reactivity is the observer. A store holds a value and a list of subscriber functions. The subscribe method adds a function and returns an unsubscribe function. The set method changes the value and calls all the subscribers. That is enough to connect data and view, but the inconvenience is that subscriptions have to be wired by hand: who is subscribed to what is up to the programmer, and it is easy to forget to unsubscribe. Signals automate exactly this part: the dependencies between data and its consumers are tracked on their own instead of being spelled out by hand.\n\nA signal is a value that can report its changes. You create it with the signal function and an initial value, you read it by calling it, and you write it with the set method. All the magic is in the reading: if it happens inside an effect or a computed value, the signal remembers the reader in its list of subscribers. When a new value that differs from the old one is written, it wakes up all the subscribers. If the same value is written, nothing happens. This way dependencies appear as a by-product of ordinary reading, and the programmer does not have to list anything.\n\nAn effect is a function that runs immediately and then runs again every time any signal read inside it changes. How does the framework know who is reading? Before running an effect, it writes itself into a global variable, the current observer. Each signal, when read, looks at this variable and, if somebody is there, adds it to its subscribers. After the run the variable is restored. That is all the magic: ten lines of code give automatic tracking. Effects are used to update the DOM, to write to a log, and to synchronize with the outside world.\n\nA computed value is derived from other signals: a full name from a first name and a last name, a cart total from a list of items. It is both a reader and a source: it reads the source signals and itself behaves like a signal for its own consumers. It is evaluated lazily: until somebody reads it, nothing is computed. The result is cached and is not recomputed until the sources change. Thanks to this, heavy computations run exactly when they are needed, and the dependency graph emerges naturally, without separate manual links.\n\nAn effect may read different signals depending on conditions: if a mode is on, read one, otherwise read another. So the set of dependencies cannot be determined once and for all. Before every run, the effect clears its previous subscriptions, and during the run it collects new ones: it is subscribed only to what it actually read this time. If a condition made a branch unreachable, changes to that branch's signals no longer bother the effect. This saves work and avoids extra triggers, but it needs a careful implementation: subscriptions must be removed from both sides, from the effect and from the signal.\n\nSuppose two computed values depend on one signal, and a third depends on both. That is a diamond. When the signal changes, a naive implementation first recomputes one value and runs the code that depends on it while the second one is still old: the consumer sees an inconsistent state, a so-called glitch, and then the second, correct, recomputed version. A good implementation first marks everything affected as stale, and then recomputes on demand, in the right order. Then the consumer fires once and sees only consistent values.\n\nIf a click handler changes three signals in a row, and an effect depends on all of them, then without grouping it will fire three times. The first two times with an incomplete state. The batch function postpones running effects until the end of the function you pass in, and then runs each needed effect exactly once. It is implemented with a nesting counter and a queue: writes to signals put the subscribers into a set of pending ones, and on leaving the outermost batch the set is cleared and the effects run. Many frameworks do this automatically, deferring the run until the end of the current task.\n\nEffects create side effects: timers, event subscriptions, connections. They have to be stopped. So an effect can return a cleanup function, which is called before the next run and on removal. The dispose method unsubscribes the effect from all its sources and calls the last cleanup. If you don't do this, the effects created every time a component is shown pile up and work for nothing. For groups of effects you create a scope: everything created inside it is released with one call. This is the prototype of the component lifecycle, which will appear in one of the following chapters.\n\nA signal wakes its subscribers only if the new value differs from the old one, and the comparison is usually shallow, by reference, through Object-is. So mutating an object in place goes unnoticed: the signal holds the same reference. The right way is immutable updates: instead of adding an element to an array, we write a new array. You can pass your own comparison function: for numbers with a tolerance, or for deep equality. The choice between explicit immutability and automatic mutation tracking defines two families of frameworks, and each has its own advantages and traps.\n\nAnother way to get reactivity is a proxy. A reactive object is wrapped in a proxy: reading a field triggers the get trap, which records that the current effect depends on this field; writing triggers the set trap, which wakes the subscribers of exactly that field. This is how Vue works. The convenience is that you can write ordinary code with assignments. The price is that you have to keep the proxy in mind: destructuring or copying loses the connection, and comparing a proxy with the original gives false. Signals, by contrast, are explicit: each value is a separate object with a clear boundary.\n\nReactivity runs into asynchronous code. An effect that requests data when an identifier changes may get the responses in a different order: the old response arrives later than the new one and overwrites it. The defense is to remember the number of the last request and ignore stale ones. Such logic is often wrapped in a resource: it holds the loading state, the value and the error. An error in one effect must not stop the others: it is caught, passed to a handler, and work continues. For infinite loops, when an effect changes what it reads itself, you set a safety fuse with a limit on repeats.\n\nLet's sum up. Reactivity connects data and interface: when data changes, only what depends on it is recomputed. The observer keeps subscribers, the signal automates subscription through reading, the effect runs again when what it read changes, and the computed value is lazily cached. Dependencies are collected anew on every run. Diamond dependencies require a consistent order, batch groups writes, and cleanup releases resources. Reference equality calls for immutable updates, while proxies track mutations. Races and errors are handled separately. In the next chapter we will build templates and a virtual DOM on top of this core.
