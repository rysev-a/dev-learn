Modern Frontend. Chapter 15. HTML: forms and accessibility. A form is a contract between the page and the server: the page promises to send the data in a known shape, and the server promises to understand it. Everything the user types passes through markup, and the markup decides whether the data arrives, whether a person can fill in the field at all, and what a screen reader tells them along the way. In earlier chapters we built the structure of the page, and here we take its liveliest part. We will go from the form tag to a checklist for an accessible form, and leave scripts and intercepting the submit for the chapter on forms in JavaScript.\n\nThe form tag is a container with two main attributes. Action is the address the request goes to, and method says how exactly: GET or POST. GET puts the data into the address bar after a question mark, so it suits search and filters: such an address can be bookmarked and sent to a friend. POST hides the data in the body of the request, and you choose it for login, ordering, and any change on the server. If the method is missing, the browser uses GET, and without an action it sends the data to the same page. The submit button starts the sending, and the browser does the rest.\n\nWhat exactly goes into the request is decided by the name attribute. The browser walks through the fields of the form and builds pairs: the field name, an equals sign, the value. A field without a name does not get into the request at all, no matter how much the person typed, and this is the most common cause of the complaint that the data does not arrive. The id attribute works differently: it is unique on the page and is needed for links, styles and scripts, but it does not go into the request. Names may repeat: radio buttons share one, and several checked boxes with the same name give several pairs. Spaces and Russian letters are encoded by the browser itself.\n\nEvery field needs a label, and it is made with the label tag. The first way: the label has a for attribute equal to the id of the field, and then they are linked wherever they stand. The second way: wrap the field in the label entirely, and the link appears by itself. Why does it matter? A click on the label puts the cursor in the field or toggles the checkbox, so the target for tapping becomes bigger. A screen reader reads the label when the person enters the field, and without it you hear only edit text, and the meaning has to be guessed. A placeholder does not count as a label: it disappears when you type, it is pale, and it is not always announced.\n\nThe type of a field is set by the type attribute. Text and password are clear without words. Email, URL, phone and search look like text, but give the phone a suitable keyboard: with the at sign, with a slash, or with digits. Number adds arrows and, together with min, max and step, sets the limits. Date opens a calendar, and range gives a slider on a scale. Checkbox means independent boxes, radio means choosing one from a group, and file opens a chooser dialog. The hidden field is not visible, but it goes into the request: that is how you pass service values, such as a record number. An unknown type is treated by the browser as text.\n\nFor choosing from a closed set there is select with nested options: each has a value that goes to the server and a text that the person sees. Long lists are grouped with the optgroup tag with a heading, and the multiple attribute allows checking several options. Multiline text is typed into a textarea: the value sits between the tags, and the size is set in rows and columns. There is also a golden mean: a field with suggestions. Datalist is a list of options attached to an input through the list attribute; the person picks from it, but may also write their own. The server still checks the value itself, because a suggestion is not protection.\n\nA button is the button tag, not a div with a click handler. A real button gets keyboard focus, is pressed with Space and Enter, and is announced by the screen reader as a button, while a div would have to be taught all of this by hand. A button has three types. Submit sends the form and is the default, so any button inside a form without a type will send it, and this is a classic trap. Button does nothing by itself and is meant for scripts: show the password, add a row. Reset returns the fields to their initial values, and one accidental press can wipe a long input. The label of a button names the action instead of saying OK.\n\nRelated fields are grouped with the fieldset tag, and the heading of the group is written in legend. For a screen reader this is context: landing on the first radio button, it first reads the question of the group and then the option. Without it the words by mail and by courier hang in the air. Radio buttons choose one option if they have the same name, so the name is shared and the value of each is its own. The checked attribute sets the default choice, and the arrow keys switch the options inside the group: you enter it with Tab once, not once per button. A disabled fieldset turns off all the fields inside at once, which is handy for whole sections of a form.\n\nThe browser can validate a form before sending, without scripts. Required makes a field mandatory. The email type demands the shape of something, at sign, something. Minlength and maxlength limit the length, min and max limit a number or a date, and pattern accepts a regular expression, for example a code of six digits. If validation fails, the browser does not send the form, puts the focus on the problem field, and shows a bubble with an explanation. The novalidate attribute on the form turns this behavior off when a script takes over the checking. But remember: browser validation is a convenience, not protection. A request is easy to forge, so the server checks everything again.\n\nThe autocomplete attribute tells the browser and the password manager what the field is asking for: a name, an email, an address, a one-time code, the current or a new password. Inputmode changes only the keyboard: the numeric value shows digits without turning the field into a numeric one, which is handy for codes. Now about states. Disabled turns the field off: it gets no focus and does not go into the request. Readonly keeps the field visible and selectable, the value goes into the request, but it cannot be edited. For styles there are pseudo-classes: invalid fires at once, and user-invalid only after the person has typed something themselves.\n\nMarkup gives accessibility almost for free, and ARIA fills in where the meaning falls short. A hint for a field, such as password requirements or a date format, is linked with the aria-describedby attribute to the id of the hint: the screen reader reads it after the name of the field. When a field fails validation, it gets aria-invalid set to true, and assistive technology reports the error. The order of walking with the Tab key matches the order in the markup, so do not break it with styles. Tabindex zero adds a nonstandard element to the walk, minus one gives focus only from code, and positive values are best never used.\n\nAn error message is text next to the field, not just a red border: people with color vision deficiencies cannot tell the color, and a screen reader cannot hear it. A good message says what happened and how to fix it: password is shorter than eight characters instead of invalid. It is linked to the field through describedby, and to have its appearance announced it is placed in a region with the alert role. After a failed submit, the focus is moved to the first error or to a summary above the form with links to the problem fields. Do not erase what the person has already typed, and do not clear the form after an error.\n\nLet us put together a checklist for an accessible form. Every field has a label and a name. The right type is chosen and autocomplete is set. Groups are wrapped in a fieldset with a legend. Buttons are real, with clear text and the right type. Required fields are marked both in words and with an attribute, and hints are linked through describedby. Errors are written as text next to the field, and the focus goes to the first of them. The form can be completed with the keyboard alone. Such a form works before the scripts start and without them. In the next chapter, on forms in JavaScript, we will add intercepting the submit, the FormData object, custom checks, and saving drafts.
