#CHAPTER 26 | The Network: fetch, CORS, WebSocket and Server-Sent Events
Modern Frontend. Chapter 26. The Network in the Browser: fetch, CORS, WebSockets and Server-Sent Events. Almost every application lives on data from a server, so knowing how to work with the network is the foundation of frontend. In this chapter we will cover fetch and its objects, cancelling and retrying requests, the same-origin policy and cross-origin requests, caching, authorization, the new protocol versions, and then two ways to receive data in real time. In the exercises we will write header parsing, retries with a delay, a CORS check, a cache with conditional requests, an event stream parser and a WebSocket client ourselves.\n\nIn the past, requests were made with the XMLHttpRequest object, with callbacks and an awkward interface. The modern way is the fetch function: it returns a promise with a response. Three objects live around it: Request, Response and Headers. An important feature: fetch rejects the promise only on a network error, such as no connection, a refused connection, or a CORS block. A response with code four hundred and four or five hundred is a normal response, and you have to check its success yourself, using the ok field or the status.\n\nIn a request you set the method, the headers and the body. The body can be a string, JSON, a form, a Blob or a binary buffer. For JSON, do not forget the Content-Type header and the serialization of the body. A response is read with one of the methods: json, text, blob, arrayBuffer. The body can be read only once, and a second call will throw an error; if you need two copies, you make a clone before reading. Headers are case-insensitive, and repeated values are joined with a comma.\n\nThe response body is a stream. The method for reading the stream gives you a reader, which hands out chunks of bytes as they arrive. This lets you show download progress: compare the accumulated bytes with the length from the header, decode text piece by piece with a TextDecoder, and process lines on the fly without waiting for the end. Remember the boundaries: a chunk can cut a character or a line in the middle, so the remainder is accumulated in a buffer. As for upload progress to the server, fetch still cannot do it properly, and XMLHttpRequest remains for that.\n\nNetwork requests must be cancellable. To do that, you create an AbortController and pass its signal into the request; calling abort breaks the connection, and the promise is rejected with an error named AbortError. This is how you cancel outdated search requests, leaving a page, or a slow response. For a timeout there is a ready-made signal for a given number of milliseconds. Retries are done only for safe and idempotent requests, with a growing delay and random jitter, so that clients do not rush at the server all at once.\n\nThe browser protects the user with the same-origin policy. An origin is the scheme, the host and the port; a page from one origin cannot read responses from another. For the server to allow reading, it answers with CORS headers, the main one being the allowed origin. Simple requests go out immediately, while for the rest the browser first sends a preflight request with the OPTIONS method and asks which methods and headers are allowed. CORS protects the reading of the response, but the request itself still reaches the server. For a request to carry cookies, the client sets the credentials mode, and the server must return the exact origin instead of an asterisk; if the response depends on the origin, you need the Vary header. You cannot fix CORS on the client: it is configured only on the server.\n\nCaching is the cheapest way to speed up the network. The Cache-Control header sets the lifetime and the rules: maximum age, a ban on caching, mandatory revalidation. When the lifetime is over, the browser does not have to download everything again: it sends a conditional request with the version identifier from the ETag header, and the server answers with code three hundred and four without a body if the data has not changed. The pattern of serving the stale copy and updating in the background speeds up the interface. Fetch itself has cache modes, which can also be changed.\n\nAuthorization in requests is built in two ways. The first is cookies with a session: the browser attaches them to requests to the same site by itself, and protection against request forgery comes from the SameSite attribute and tokens. The second is the Authorization header with a token, which the application stores and attaches itself. On a response of four hundred and one, the client tries to refresh the token once and repeat the request; on four hundred and three, access is forbidden and repeating makes no sense. It is important that parallel requests do not start a dozen token refreshes at the same time.\n\nThe protocol evolves too. Version one point one opens many connections and waits for responses in turn. Version two multiplexes many requests in a single connection, compresses headers, and removes the need to concatenate files and spread resources across domains. Version three works on top of the QUIC protocol, built on UDP, and does not suffer from the loss of a single packet. For the frontend, the conclusions are these: use Brotli compression, do not abuse eager loading through preload, and trust the browser with priorities. All of this is turned on on the server and in the content delivery network.\n\nWhen data is needed instantly, a WebSocket fits. The connection starts with an ordinary request with the Upgrade header, the server answers with code one hundred and one, and from then on frames go in both directions over the same channel. The object has events for open, message, error and close, and the close event carries a code and a reason. The channel does not reconnect by itself, so the client does it: with exponential delay, pings to check that the connection is alive, and a queue of messages accumulated during the outage.\n\nFor one-way broadcasting from the server there is a simpler solution: Server-Sent Events. The client creates an EventSource object, and the browser keeps an ordinary connection through which the server sends a text stream. Each event is a few lines with the fields data, event and id, separated by an empty line. If the connection is lost, the browser reconnects by itself and tells the server the last identifier it received, so the server can resend what was missed. The limitations: only the GET method and only text, but it works over plain HTTP and passes through proxies.\n\nIn practice, the network layer has to be built carefully. The application watches the online state and accumulates requests in a queue during an outage. Optimistic updates show the result immediately and roll it back on error. Duplicates of identical requests are merged, responses are cached with a clear lifetime, and errors are turned into typed results and shown to the user in a human way, not as a scary stack trace. This is exactly the work done by client libraries like React Query and SWR, and now we understand what is inside them.\n\nLet us sum up. Fetch returns a response even on server errors, the body is read once, and it can be received as a stream. Requests are cancelled with an AbortController, and retries are done carefully. CORS is configured by the server, the preflight request checks permissions, and credentials require an exact origin. Caching and conditional requests save traffic, a WebSocket gives a two-way channel, and Server-Sent Events give a one-way channel with automatic reconnection. In the next chapter we will talk about service workers and applications that work without a network.
