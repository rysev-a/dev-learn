#CHAPTER 38 | Components and the Router
Modern Frontend. Chapter 38. Components and the Router. We have reactivity and a virtual DOM. Now we need architecture: how to split an interface into parts and tie them into an application. The main technique is components. A component bundles the markup, behavior and state of one piece of the interface: a button, a form, a card, a page. Data flows down the tree through props, and messages about events travel up through handlers. This one-way flow of data makes behavior predictable: you can always tell where a value came from and who changed it.\n\nProps are a component's input, and it must not change them: they belong to the parent. So a component behaves like a function of its props. Props can have default values, required fields and type checks. Children and slots let a parent put content inside a component: a title and a body in a card, any text in a modal window. This is called composition, and it is more flexible than inheritance: you build complex components out of small independent ones by combining them, not by extending class hierarchies.\n\nA component can have its own state: whether a list is open, what has been typed into a field. If only that component needs the state, it stays inside. If several components use it, you lift it to the nearest common ancestor and pass down values and functions for changing it. If there are too many such components and the path through ancestors gets long, you use context or a shared store. The rule is simple: keep state as close to where it is used as possible, and lift it only when you really have to. Needless global state makes testing and debugging harder.\n\nA component has three moments in its life. Mounting: it appears in the tree for the first time, and this is where you subscribe to events, start timers and load data. Updating: props or state changed, so you need to redraw a part and maybe re-sync side effects. Unmounting: the component leaves, and you must unsubscribe, stop timers and cancel requests. Modern frameworks express this with effects that have cleanup. An effect runs on mount and whenever its dependencies change, and the function it returns is called before the next run and on removal.\n\nEvents in an interface bubble: an element reports a click, and then the event rises to its ancestors. This is used for delegation. Instead of a hundred listeners on the rows of a list, you put one on the container and use the event target to work out which row was clicked. A component reports its events upward by calling a handler function from its props, or by emitting its own events. The parent decides what to do with them. Bubbling can be stopped, and the default action can be canceled. An event should not carry anything extra: just the data the receiver needs.\n\nSometimes the same value is needed by many components at different depths: the theme, the language, the current user. Passing it through the props of every component in between is tedious. Context solves this. An ancestor provides a value, and any descendant asks for it by key and gets the nearest one up the tree. Dependency injection works the same way: swapping a service in a test is just another provider. But don't overuse it. Implicit dependencies make code harder to read, so put only truly cross-cutting things into context.\n\nWhen state is shared by the whole application, you gather it in a store. The store holds a single value, and it changes only when you dispatch actions: plain objects with a type. A pure function called a reducer takes the old state and an action and returns a new state without changing the old one. Subscribers get notified about changes. This approach makes the history of changes transparent: you can record all the actions and replay the state, step back through it, and test the reducer like any ordinary function. Asynchrony is added with middleware: loggers and thunks.\n\nA single-page application does not load a new page on navigation, but the address in the browser bar still has to change, so the link can be shared and the Back button works. That is the router's job. It maps the address to components, and when the user navigates, it updates the address through the browser's history interface: the pushState method adds an entry, and replaceState replaces the current one. For the Back and Forward buttons, the browser sends a popstate event, and the router shows the matching view. The variant with a hash in the address works without any server setup, but it looks worse.\n\nRoutes are described by patterns: users, a colon, id. Parameters are cut out of the address, and the query string is parsed separately. Routes nest: a shared page layout is chosen by prefix, and inside it a specific page is chosen by the rest of the path, so the result of matching is a chain of matched routes. The order of checking matters: more specific patterns go before general ones. A catch-all route goes last for unknown addresses, and it shows a not-found page. It is good when addresses can be built back from a pattern and parameters, instead of gluing strings together.\n\nA link component must stay a real link: it has an address, and a middle click or a click with a modifier key opens a new tab. The router intercepts only a plain left click, without modifiers, on a link to the same site and without a target attribute, and leaves everything else to the browser. Before navigation, guards run: functions that can allow it, block it, or redirect, for example to a login page. Guards can be asynchronous, and a new navigation cancels the unfinished previous one. Redirects need a depth limit so that a loop does not hang the app.\n\nYou don't need to load the code of every page at once. A route is described by a function that returns a dynamic import, and the bundler turns each page into a separate file. On the first navigation the code is loaded; while you wait, a spinner is shown, and if loading fails, a fallback view. The result is cached, so a repeat navigation is instant. You can also start loading ahead of time: when the cursor hovers over a link, or when the link enters the viewport. The balance is simple: the main screen should open fast, and the rest should load so that the user doesn't notice the wait.\n\nA page usually needs data, and it is handy to tie loading it to the route: each matched route has a loader, and they all run in parallel, not one after another. While data is on its way, a loading state is shown, and if a loader returns an error, it must not bring down the whole application. For this you put an error boundary around parts of the interface: it catches an exception raised while rendering child components and shows a fallback view with the option to retry. Don't forget accessibility either: on navigation, update the page title and announce the page change to screen readers.\n\nLet's sum up. A component is a unit of interface: props go down, events go up. Composition through children and slots is more flexible than inheritance. Keep state as close to its use as possible and lift it when needed, and pass cross-cutting values through context. A shared store changes only through actions and pure reducers. The lifecycle is expressed with effects that have cleanup. The router ties an address to a view through the history interface, matches patterns with parameters and nesting, intercepts links and runs guards. Pages load lazily, and data loads in parallel. In the last chapter we will assemble a whole project.
