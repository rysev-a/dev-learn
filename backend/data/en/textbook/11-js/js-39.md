#CHAPTER 39 | Putting the Project Together: Vite, Tests and Deploy
Modern Frontend. Chapter 39. Putting the Project Together: Vite, Tests and Deploy. We have written reactivity, a virtual DOM, components and a router. What's left is to turn all this into a real project that a team can grow and publish on the internet. For that we need three things. A bundler and a dev server, so we see the result fast. Tests, so we can change code with confidence. And automatic deploy, so that publishing doesn't depend on somebody's memory. In this chapter we go from an empty folder to a working site and build a small pipeline around it.\n\nLet's start with the structure. In the root there is the package manifest, the lockfile with exact versions, the bundler config and the entry page. The src folder holds the source code: the entry point, components, routes, styles. The public folder holds static files that must be served unchanged: icons, robots.txt, the manifest. The build result goes into the dist folder, which you never edit by hand and never add to the repository. A good rule: from a file's location you should be able to tell what it is for and who changes it, a person or the build.\n\nThe Vite dev server starts in a fraction of a second. The secret is that it doesn't build the whole project in advance. Browsers can load modules themselves, and Vite serves each file on request, transforming it on the fly: TypeScript, JSX, preprocessors. Dependencies from node_modules are built once and cached. When you edit a file, hot module replacement kicks in: only the changed part is swapped, and the page state is preserved. So the edit-to-result loop takes milliseconds, and development stops waiting for the build.\n\nVite's configuration is an ordinary JavaScript file. This is where you plug in plugins, for example for React or Vue. Aliases such as the at sign for the src folder save you from long relative paths. A proxy forwards requests with the api prefix to the backend, so in development you don't need any cross-origin settings. Environment variables that start with the VITE prefix reach the client code through a special object, and the rest stay on the machine. An important rule: never put secrets in client code, because anything that ends up in the build is visible to every user.\n\nFor production, the code is built. Modules are merged into a few files, and unused code is thrown out, which is called tree shaking. The code is minified: names get shorter and whitespace disappears. A hash of the content is added to file names: if a file hasn't changed, its name is the same and the browser takes it from the cache, and if it has changed, the name is new and the cache is bypassed. Dynamic imports turn into separate chunks that load lazily. Source maps let you debug a minified file in terms of the original sources. The result is a small, fast, cacheable set of files.\n\nNow tests. The foundation is unit tests: small checks of individual functions and modules. A pure function is ideal for a test: feed in an input, compare the output. Reducers, address parsing, formatting, validation are all checked without a browser and run in milliseconds. Vitest uses the same config as Vite, so aliases and plugins work the same way. A test has three parts: arrange, act, assert. A good test checks behavior, not structure: after a refactoring it should stay green if nothing changed on the outside.\n\nComponents are tested in an environment that imitates a browser: jsdom or happy-dom create a document and events right inside Node. The test renders a component, finds elements the way a user does, by role, label and text, clicks, types, and checks the result on the page. Searching by role and text keeps the test close to real use and also checks accessibility. Don't look elements up by internal classes or check internal state: such tests break at any refactoring, even though the user noticed nothing.\n\nA test must be fast and repeatable, so everything external is replaced: the network, time, random numbers, storage. The request function is replaced with a stub that returns a canned response or an error, and you check how the component reacts. Timers are replaced with controlled clocks and fast-forwarded without waiting. For the network layer, request interceptors are handy: the app still makes a real request, but the test makes up the response. The limit of replacing is your own logic: if you replace everything, the test checks only the stubs. You replace the boundaries of the system, not its core.\n\nEnd-to-end tests launch a real browser and walk through a whole scenario: open the site, log in, add an item, place an order. They catch what the others can't see: how the parts integrate, the real network, behavior across different browsers. But they are slower and more capricious, so you write few of them and only for the main paths. Waits must be smart: the test waits for an element to appear instead of sleeping a fixed time. The classic pyramid is many fast unit tests, fewer component tests, and very few end-to-end tests. The top must be thin.\n\nSome errors can be caught without running anything at all. A linter finds suspicious code: unused variables, forgotten effect dependencies, risky patterns. A formatter ends style arguments once and for all: code is formatted automatically, and reviews discuss meaning, not indentation. TypeScript checks the consistency of types across the whole project. All this runs in the editor, before a commit through Git hooks, and in the shared check on the server. The rule is simple: whatever a machine can check, a machine should check, and people look at what a machine can't understand.\n\nChecks are useful only if they always run. That's what continuous integration is for: on every commit and merge request, the server, in a clean environment, installs dependencies strictly from the lockfile, and runs the linter, the type check, the tests and the build. If anything is red, the merge is blocked. A clean environment rules out "it works on my machine": the result doesn't depend on anybody's computer. A dependency cache speeds up the run, and a matrix of Node versions checks compatibility. The speed of the pipeline matters: if it takes half an hour, people will start to bypass it, so keep it fast.\n\nThe finished build has to be published. A client application is a set of static files, so you put them on static hosting or on a content delivery network, which serves copies from the nearest servers. The server needs one rule: any path that isn't among the files returns the main page, otherwise client-side routing breaks on reload. Files with a hash are cached for a long time, and the main page never. Good platforms make a preview for every merge request and let you roll back to the previous version with one switch. Deploy should be boring and reversible.\n\nLet's sum up the chapter and the whole book. A project consists of sources, static files and configs, and Vite gives a fast dev server and an optimized build. Tests form a pyramid: many unit tests, fewer component tests, a few end-to-end ones, with external things replaced at the boundaries. A linter, a formatter and types work automatically, and continuous integration guarantees that they always run. Deploy is publishing static files with caching and rollback. We have gone from the history of JavaScript and the language, through the browser and Node, to our own mini-framework and a finished project. Now you can confidently study any ready-made framework: you can see what is under its hood.
