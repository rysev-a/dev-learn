Computer Architecture. Chapter 20. Virtual memory. When a hundred programs are running on a computer, each of them believes that the memory belongs to it alone: each has its own set of addresses starting from zero, and there is no risk that another program will overwrite your data. Of course, there wouldn't be enough physical memory for everyone, but the illusion works. It is provided by virtual memory, one of the most important achievements in architecture. Today we'll look at how the processor translates virtual addresses into physical ones, what pages and page tables are, how multilevel tables and the translation cache are built, what happens when a page is not in memory, how the system chooses which page to evict, and how the same machinery implements protection and copy-on-write.\n\nWithout virtual memory, all programs would use real physical addresses. Then each of them would have to know where in memory it lives, nobody could stop a buggy program from writing data into someone else's area, and a shortage of space could be solved only by hand. The virtual approach introduces a layer: a program works with virtual addresses, and a special device in the processor, the memory management unit, the MMU, turns them into physical ones on the fly. The same virtual address in two processes can point to different places in physical memory, or may point nowhere at all.\n\nMemory is divided into equal blocks. In the virtual space they are called pages, and in physical memory they are called frames. The most common size is four kilobytes. A virtual address consists of two parts: the low twelve bits make up the offset within the page, and the high bits are the virtual page number. During translation the offset stays the same, and the page number is replaced by the frame number. This scheme is very simple: translation comes down to replacing the high bits of the address. All the bytes of one page lie in one frame, one after another, so there is nothing to translate inside a page.\n\nThe correspondence between pages and frames is stored in a page table, a separate one for each process. The virtual page number serves as the index, and the cell holds the frame number and a few flags. If the page isn't in the table or is marked as absent, accessing it causes a page fault: control passes to the operating system, which decides what to do. Translation is very simple to implement: compute the page number, take the entry from the table, and add the frame number, shifted by the width of the offset, to the offset. The flags do the rest.\n\nA page table entry holds more than just a frame number. The present bit says whether the page is in memory. The write bit allows modification, and pages with program code are often made read-only. The user bit says whether an ordinary program can access the page or only the kernel. The hardware sets the accessed bit on every read, and the dirty bit on every write. The last two help the operating system decide which pages are rarely used, and which don't need to be written to disk because their contents haven't changed. All of this is stored in a few bits next to the frame number.\n\nThe problem is the size of the table. Sixty-four-bit processors use forty-eight bits of virtual address. With four-kilobyte pages that is two to the power of thirty-six pages, and with eight bytes per entry a flat table would take five hundred and twelve gibibytes for each process. That's absurd, but most of the address space is empty. The solution is multilevel tables. The page number is split into parts, and each part indexes the table of its own level. A table fits exactly into one page, so it holds five hundred and twelve entries: nine bits per level. Forty-eight bits need four levels, and the tables for empty regions are simply never created.\n\nTranslation through a multilevel table works like this. The processor takes the root table, uses the first part of the number to find an entry that leads to the second-level table, uses the second part to find an entry in it, and so on, until at the last level it gets the frame number. If at any step the entry is missing, a page fault occurs. The price for saving memory is four memory accesses instead of one for every translation, and the accesses form a dependent chain: the next address is known only after the previous entry has been read. Doing this walk on every data access would be catastrophically slow.\n\nThat's why translation results are cached in a special small fast memory, the translation lookaside buffer, the TLB. It holds a few dozen or a few hundred of the most recent page and frame pairs. On an access, the processor first looks for the page in this buffer and, if it finds it, gets the frame in one cycle. Only on a miss does the table walk start. Thanks to locality, the hit rate is above ninety-nine percent, and the expensive walk happens rarely. When switching between processes, the contents of the buffer are either flushed or tagged with a process identifier, so that one process's translations are not confused with another's.\n\nWhen the page is not in memory, the operating system takes control. It checks that the access is legitimate, finds a free frame, reads the needed data from disk, updates the table, and restarts the instruction that caused the fault. The program notices nothing except a pause. This approach is called demand paging: pages are loaded only when they are first accessed. That's why a huge program starts quickly: only the parts in use are read into memory. The first access to each page is a mandatory fault, and all the later ones, as long as the page stays in memory, go through without delay.\n\nWhen no free frames are left, we have to choose a victim and write it out to disk. The best victim is the page that will be needed later than all the others, but we don't know the future. The FIFO policy evicts the oldest page, but surprisingly it can get worse as memory grows: this is Belady's anomaly. The LRU policy evicts the least recently used page; it is closer to the ideal, but it requires tracking accesses. So systems use approximations, for example the clock algorithm with a second chance: the pages are arranged in a circle, and the hand skips a page whose accessed bit is set, clearing it, and evicts the first one whose bit is clear.\n\nIf there are more active pages than frames, thrashing sets in. The program keeps accessing a page that was just evicted, the system continuously reads and writes the disk, and almost no useful work gets done. A classic example: a loop over five pages with four frames and the LRU policy causes a fault on every access, while with five frames all the faults reduce to the first five. The working set, that is, the set of pages the program will need in the near future, must fit into memory entirely. Otherwise the only help is to add memory or run fewer programs at the same time.\n\nThe same mechanism gives several more capabilities. Protection: another process's page is simply not mapped in your process's table. Shared memory: two processes map the same physical page. File mapping: the pages of a file are read straight into the address space. And copy-on-write. When a child process is created, the page table is copied, but the frames remain shared and are marked read-only. Only when someone tries to write does the system make a copy of the frame for them. This makes creating a process cheap, and the memory savings are huge.\n\nLet's sum up. Virtual memory gives each process its own address space and protection from other programs' bugs. An address is split into a page number and an offset, and the page table translates pages into frames. Multilevel tables save memory, and the TLB hides the cost of the walk. A page fault lets us load data on demand, replacement algorithms choose the victim, and thrashing occurs when the working set doesn't fit in memory. Copy-on-write makes process creation cheap.
