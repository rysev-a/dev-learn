Computer Architecture. Chapter 3. Standards and Open Architectures. Why does a charger from one phone work with another, and why does one manufacturer's memory work in another's computer? Because standards exist. A standard is an agreement about what interfaces should look like: voltages, connectors, data formats, instruction sets. If both sides follow it, the parts on each side can be changed independently. This is exactly the design discipline we discussed in the first chapter: interchangeable parts and the principle of modularity.\n\nLet us start at the lowest level, with voltage. Four families of logic have dominated since the seventies: TTL and CMOS at five volts, and the low-voltage LVTTL and LVCMOS at three point three volts. Each has its own levels: for example, TTL accepts anything above two volts as a one, while CMOS requires more than three point one five. Not all families are compatible: a TTL output does not rise high enough for CMOS to recognize a one. And a five-volt signal on the input of a three-volt chip can damage it.\n\nAbove the level of voltages lie the interfaces between devices. Main memory connects to the processor through the DDR standard, which is maintained by the JEDEC committee. Graphics cards and fast drives use PCI Express. Peripherals connect through USB, and monitors through HDMI or DisplayPort. Each standard defines the connector, voltages, speed, and exchange protocol. Thanks to this, modules from different manufacturers can be assembled into one computer, and the market competes on quality rather than on compatibility.\n\nThere are standards for data, too. Text in a computer is written according to a character table: ASCII for English letters, and Unicode for all the languages of the world, whose most popular encoding, UTF-8, uses from one to four bytes per character. Real numbers are stored according to the IEEE 754 standard: sign, exponent, and mantissa. Even the order of bytes in multi-byte numbers is a matter of convention: least significant byte first, or most significant. We will look at these formats in detail in the chapters on numbers and text.\n\nNow the most important standard for our course: the instruction set architecture, or ISA. It is a contract between programmers and hardware: which instructions exist, which registers, and how memory is organized. A compiler produces instructions according to this contract, and the processor is obliged to execute exactly those. As long as the contract is respected, the same binary file will run on different processors, fast and slow, expensive and cheap. The architecture is what cannot be changed, while the microarchitecture can be improved for years.\n\nHistorically, the best-known instruction sets belonged to companies. The x86 architecture was developed by Intel and AMD, and producing such processors without permission is not allowed. The ARM architecture was developed by a British company that sells licenses to other firms and collects royalties on every chip. This model has advantages: a huge ecosystem has grown around ARM. But licenses cost money, the rights to make changes belong to the owner, and a small startup or a university cannot freely build its own processor.\n\nIn two thousand ten, at the University of California, Berkeley, they came up with RISC-V: an instruction set that was meant to be clean and simple and, most importantly, open. Anyone can download its specification and build a chip without paying license fees. In two thousand fifteen a foundation was created, which today is called RISC-V International: it maintains the specification, approves extensions, and checks compatibility. An open standard is like Linux for processors: it belongs to the community and lets everyone take part.\n\nA distinctive feature of RISC-V is modularity. There is a small base set of integer instructions, called RV32I for thirty-two bits and RV64I for sixty-four bits. Standard extensions are added to it: multiplication and division, atomic operations, single- and double-precision floating-point numbers, and compressed instructions. The name of a processor lists its modules: for example, RV32IMAC. A manufacturer can keep only the parts it needs and, if necessary, add its own extension without breaking compatibility with the standard.\n\nThe contract between a program and the operating system kernel is also standardized. The application binary interface, the ABI, describes which registers carry arguments, which registers a function must preserve, and how the stack is organized. Linux system calls take their number in one register and their arguments in others, and are invoked with the ecall instruction. A common operating system interface, the POSIX standard, lets programs be moved between systems. These are the conventions we will use when we start writing RISC-V assembly programs.\n\nSo how are standards born? Usually a group of interested parties creates a working group, prepares a draft, puts it up for public discussion, revises it, and publishes the final version. The IEEE and ISO committees do this work, the IETF publishes internet standards, and JEDEC publishes memory standards. An important part of the process is compatibility tests: only they show that a device really follows the standard. Our course uses two instruction sets: the simplified teaching processor Mini-8, so that we can see how a processor works down to the last gate, and the real RISC-V.
