Computer Architecture. Chapter 22. Parallelism: multicore, coherence, SIMD, and GPUs. About twenty years ago, processor frequency grew every year, and programs got faster on their own. Then the growth hit a ceiling: the heat produced became too great. Since then processors have sped up mainly through parallelism: several cores are placed on a chip, each core is taught to process several pieces of data with one instruction, and for heavy tasks graphics cards and other accelerators are brought in. But parallelism is not free: cores share memory and get in each other's way, and programs have to be written differently. Today we'll look at why the number of cores grew, how their caches are kept consistent, what data races and atomic operations are, how vector instructions and graphics processors work, and why specialized accelerators are needed.\n\nWhy can't we just keep raising the frequency? The dynamic power of a processor grows roughly as the product of the frequency and the square of the voltage, and the voltage has to be raised along with the frequency. As a result, power grows almost as the cube of the frequency: doubling the speed means eight times the heat. Hence the idea: instead of one very fast core, put in two cores that are each half as fast. They give the same total performance, provided the task can be parallelized, while consuming only a quarter of the power. This is the reason why even phones today have eight cores.\n\nParallelism comes at several levels. We have already seen instruction-level parallelism in the pipeline and in superscalar execution: the processor itself finds independent instructions. Data parallelism means applying one operation to many values; these are vector instructions and graphics processors. Thread-level parallelism uses several cores, each with its own program, and task- and machine-level parallelism covers clusters of servers. But the possibilities are limited by Amdahl's law: with ninety-five percent of the work parallel, eight cores give a speedup of about six, and sixty-four cores only about fifteen.\n\nEach core has its own cache, but the memory is shared, and this is where a problem arises. Suppose the value of a variable sits in memory and in the caches of two cores. The first core writes a new value, but only into its own cache, and the second one keeps reading the old copy. The program sees an inconsistent picture of the world. This problem is called cache coherence. So that programmers can reason about memory as a single whole, the hardware must guarantee that all cores eventually see the same value of every cell. This guarantee is provided by coherence protocols that work between the caches.\n\nThe best-known protocol is called MESI, after the first letters of the cache line states. A line can be modified, exclusive, shared, or invalid. When a core reads a line that nobody else has, it gets it in the exclusive state. If the line is already held by others, all the holders move to the shared state. When a core wants to write, it broadcasts an invalidation signal to the rest: their copies become invalid, and the writer's line moves to the modified state. If someone then reads the line, the modified version is handed over and becomes shared. This guarantees that at any moment the modified copy is unique.\n\nCoherence works with cache lines, not with individual variables, and this creates a nasty problem, false sharing. Suppose two threads often write to two different variables, but the variables lie next to each other and ended up in the same sixty-four-byte line. Logically the threads don't overlap, but the line keeps flying between the cores' caches like a ball, and every write invalidates the other's copy. The program runs several times slower than if the variables lay in different lines. The cure is alignment: the hot variables of different threads are spaced apart by the size of a line.\n\nIf several threads modify shared data without coordination, the result is a data race. The classic example: two threads increment the same counter. The operation add one actually consists of three steps: read the value, add, write. If both threads read zero before anyone has written, both will write one, and one of the increments is lost. The outcome depends on the order of the steps, which is random, so the error shows up rarely and is hard to reproduce. This is one of the most unpleasant categories of bugs in programming.\n\nTo make an operation indivisible, processors offer atomic instructions. The most universal one is called compare-and-swap, or CAS: it writes a new value only if the current one equals the expected one, and reports whether it succeeded. A counter is incremented like this: read the value, try to replace it with the value plus one, and if that fails because someone got there first, repeat. This is how locks, queues, and other structures without ordinary locks are built. Another atomic instruction, test-and-set, underlies the spinlock: threads try in a loop to take a flag.\n\nThere is an even subtler problem. To avoid waiting for slow memory, cores use a write buffer and reorder instructions. So on different cores the order of visible changes can differ from the order of instructions in the program. The classic experiment: one thread writes to x and reads y, another writes to y and reads x. With strict sequential consistency at least one of them would read a one, but on real processors both sometimes read zero. To restore order there are memory barriers and atomic operations with ordering: they forbid reordering instructions across the boundary. The memory models of programming languages describe what is guaranteed to the programmer.\n\nVector instructions, SIMD, apply one operation to several values at once, packed into a wide register. A register two hundred fifty-six bits wide holds eight single-precision floating-point numbers, so one add instruction performs eight additions. Processing an array of one thousand twenty-four numbers takes one hundred twenty-eight vector instructions instead of one thousand twenty-four. The remainder of the array, which doesn't fill a vector, is handled with ordinary instructions. Compilers can vectorize simple loops automatically, and numerical libraries use vector instructions inside.\n\nGraphics processors, GPUs, go further. Instead of a few powerful cores they have thousands of simple ones, grouped into units that execute the same instruction on different data at the same time. This model is called SIMT. A group of thirty-two threads, a warp, works in lockstep. If the threads within a warp take different branches of a condition, both branches are executed one after the other, and the unneeded threads sit idle. Such divergence cuts the speed in half. That is why graphics cards handle graphics, matrices, and neural networks well, where the data is uniform, and handle branchy logic badly.\n\nToday the main limit is energy and heat. So manufacturers use heterogeneous cores: fast ones for heavy tasks and frugal ones for background work, as in phones. Specialized accelerators have appeared: neural processors, tensor units, video codecs. Each performs a narrow class of operations tens of times more efficiently per watt than a general-purpose processor. Operations per second per watt has become the main measure of quality, and the programmer has to decide on which device to run each part of the work and how much data to move between them.\n\nLet's sum up. The growth of frequency stopped because of heat, so performance now grows through parallelism: multicore, vector instructions, graphics processors, and accelerators. The consistency of the cores' caches is handled by a coherence protocol, such as MESI, but false sharing can wipe out the gain. Shared data requires atomic operations and a careful attitude to the memory model, otherwise races appear. Amdahl's law limits the speedup, and energy efficiency determines the choice of device. This completes our course on computer architecture. Next we'll study how the operating system manages all this hardware.
