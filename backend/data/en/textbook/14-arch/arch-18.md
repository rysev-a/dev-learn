#CHAPTER 18 | Memory hierarchy and cache
Computer Architecture. Chapter 18. Memory hierarchy and cache. A processor can execute an instruction in a fraction of a nanosecond, but reaching main memory takes about a hundred times longer. If the processor waited for memory every time, it would sit idle almost all the time. The way out was to put several layers of faster and faster, but smaller and smaller, memory between the processor and main memory, holding copies of the most needed data. Today we'll look at the memory hierarchy, the property of locality that makes it work, and how a cache is built: addresses, lines, direct-mapped and associative placement, replacement and write policies. We'll learn to compute the average access time, and we'll see why the order in which you walk through an array can speed a program up several times over.\n\nLet's look at the numbers. A register is read in one clock cycle, roughly a third of a nanosecond. The first-level cache answers in three or four cycles, the second level in about ten, the third in a few dozen. Main memory answers in a hundred nanoseconds or more, which is hundreds of cycles. A solid-state drive is slower by another factor of a thousand, and a spinning disk by orders of magnitude more. Each next level holds thousands of times more, but is just as many times slower. This ladder is called the memory hierarchy, and the whole trick of the architecture is to find the data you need on the upper rungs almost every time.\n\nWhy is fast memory more expensive and smaller? Fast memory, static, or SRAM, stores each bit in a latch of six transistors. It needs no refreshing and answers instantly, but takes up a lot of space on the chip. Main memory, dynamic, or DRAM, stores a bit in a tiny capacitor with a single transistor, so it holds far more. The capacitor slowly discharges, so the charge has to be refreshed regularly, and reading is destructive and requires writing the value back. That's why main memory is dense and cheap, but slow. Caches are built from SRAM, and main memory from DRAM.\n\nA cache works because programs don't access memory randomly. Temporal locality: if we've just used some data, we'll need it again soon, like a loop counter variable. Spatial locality: if we've read one cell, we'll soon read its neighbor, as when walking through an array. So a cache stores not single bytes but lines, usually sixty-four bytes each, and on a miss it loads the whole line at once. Walking through an array of a thousand numbers in order touches just sixty-four lines, while reading with a stride of one line touches a thousand lines: the amount of data is the same, but the load on the cache is sixteen times higher.\n\nHow does a cache find the line it needs? The address is split into three fields. The low bits, the offset, point to a byte inside the line. The next bits, the index, choose a place in the cache. The high bits, the tag, are stored next to the line and let us confirm that it holds exactly the data we want. If the tag matches, that's a hit, and the data is returned in just a few cycles. If not, it's a miss: the line is loaded from the next level, and the new tag is written into the cache. The number of bits in each field is determined by the sizes of the line and of the cache.\n\nThe simplest cache is the direct-mapped one. Each block of memory can live in only one cache line, determined by the index. The check is fast: a single tag comparison. But there's a drawback: two blocks with the same index keep evicting each other, even if the rest of the cache is empty. These misses are called conflict misses. Picture a program that alternately reads two arrays placed so that their starts land on the same lines: the cache will spin its wheels even though there's plenty of room.\n\nTo soften conflicts, caches are made set-associative. The index chooses not a single line but a set of several, for example two, four or eight. A block can live in any line of the set, and several tags are checked at once. Under the same conditions, the two conflicting blocks now live side by side, and the number of misses drops. The extreme case, where there is just one set and it contains the whole cache, is called fully associative: it's flexible but expensive, because all the tags must be compared at once. Modern caches are usually four-way or eight-way: a compromise between speed and the number of conflicts.\n\nIf a set is full, we have to decide which line to evict. Most often the choice is the least recently used one: that's the LRU policy. It relies on temporal locality, but it requires keeping track of the order of accesses. A simpler policy is first in, first out, FIFO, and simpler still is a random choice. There is also an ideal but unattainable policy: evict whatever will be needed latest. It can only be applied to a trace of accesses recorded in advance, but it shows the limit of what's possible and lets us judge how close the real policies come to it.\n\nWhat happens on a write? Write-through writes the data both into the cache and straight to memory: simple, but memory is busy all the time. Write-back changes only the cache and marks the line as dirty, and the data goes to memory only when the line is evicted. If a program changes one variable a hundred times in a row, memory gets one write instead of a hundred. The price is that on power loss, or with several processors, the data in the cache and in memory diverge, and extra mechanisms are needed to keep them consistent. On a write miss, the line is usually loaded first: this is called write-allocate.\n\nTo judge how much a cache helps, we use the average memory access time. It equals the hit time plus the miss rate times the miss penalty. For a multi-level hierarchy the formula is applied recursively: the first level's miss penalty is the average access time of the second. Suppose the first-level cache answers in one cycle and misses five percent of the time, and an average access to the second level takes fifty cycles. We get one plus zero point zero five times fifty, which is three and a half cycles. Without a cache, every access would cost hundreds of cycles.\n\nThe consequences for a programmer are very practical. A two-dimensional array lies in memory row by row. If we walk through it row by row, we read neighboring cells, and every cache line we load is used in full. If we walk down the columns, each next access lands in a different line, which has already been evicted by the time we come back. For a sixty-four by sixty-four array, walking by rows gives two hundred fifty-six misses, and walking by columns gives all four thousand ninety-six. That's a sixteen-fold difference in memory accesses. So nest your loops so that the inner one walks through neighboring addresses.\n\nThe idea of a cache reaches far beyond the processor. A browser keeps recently opened pages, a database holds frequently read pages in memory, a web service remembers the result of an expensive computation. Programs often memoize the results of recent function calls so they don't compute them again. The same questions come up everywhere: what to keep, how much, what to throw out when space runs short, and how to avoid serving stale data. That last question is especially hard; there's a saying that there are only two hard things in programming: cache invalidation and naming variables.\n\nLet's sum up. The memory hierarchy hides the gap between processor speed and memory speed: small fast levels hold copies of data from large slow ones. It works thanks to temporal and spatial locality. A cache splits the address into tag, index and offset; direct mapping is simple but suffers from conflicts, associativity softens them, and replacement policies decide what to evict. The write policy determines when data reaches memory. The average access time shows the benefit of a cache, and the order in which you walk through data can change a program's speed several times over.
