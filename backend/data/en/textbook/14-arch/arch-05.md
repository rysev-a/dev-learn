#CHAPTER 5 | Text and data protection
Computer Architecture. Chapter 5. Text and data protection. We already know how to store numbers, and text is numbers too: every character is assigned a number. But how do we agree on these numbers for all the languages of the world? How do we write a character in bytes so that a string does not turn into a set of meaningless symbols? And how do we make sure the data was not corrupted on its way over the network, on a disk, or in main memory, where a bit sometimes flips by itself? Today we will talk about encodings, from ASCII to Unicode and UTF-8, about the traps connected with string length, and then about methods of detecting and correcting errors: the parity bit, checksums, the cyclic code and the Hamming code.\n\nThe oldest encoding is called ASCII. It uses seven bits, that is, a hundred and twenty-eight values: digits, Latin letters, punctuation marks and control characters such as the line feed. Capital A has number sixty-five, lowercase a has ninety-seven. The difference is exactly thirty-two, which is a single bit: to turn a lowercase letter into a capital one, it is enough to toggle one bit. ASCII is great for English, but it has no room for Russian, Chinese or Arabic.\n\nWhen other languages came to computers, each country started extending ASCII in its own way: using the eighth bit and adding its own characters. This is how code pages appeared. For Russian there were several, for example Windows twelve fifty-one and KOI8-R. The trouble is that the same byte meant different letters. If a text is written in one encoding and a program reads it in another, you get nonsense instead of words, which is called mojibake. The Russian word privet, written in the Windows encoding, turns into a set of random letters when read as KOI8-R. A single standard was needed.\n\nSuch a standard is Unicode. It does not define how to store characters in bytes, it simply gives every character a unique number, called a code point. The Cyrillic letter Zhe is U plus zero four one six, the number one thousand forty-six. Unicode has more than a million possible code points: it includes all modern scripts, mathematical signs and emoji. But be careful: what we perceive as one character may consist of several code points. The letter e with an accent can be written as one code point or as two: a letter and a separate combining mark. Then the strings look the same, but are not equal to each other.\n\nWhat remains is to decide how to write code points in bytes. The most popular way is UTF-8. It has variable length: ASCII characters take one byte and coincide with ASCII, so any English text is saved as it was. Letters of Russian and many other alphabets take two bytes, most Chinese characters take three, and emoji take four. The first byte of a character hints at its length: a zero in the top bit means one byte, one one zero means two, one one one zero means three, one one one one zero means four. All the following bytes start with the bits one zero. So in UTF-8 you can always find the start of the next character.\n\nLet us see how this works with an example. The letter Zhe has code point one thousand forty-six, which in binary is eleven significant bits. They do not fit into seven bits, so two bytes are needed, following the pattern one one zero and one zero. We lay the bits out along the pattern and get the hexadecimal bytes D zero and nine six. The euro sign, number eight thousand three hundred sixty-four, takes three bytes, and a smiley takes four. If you read the wrong bytes as UTF-8, you get a decoding error or a special replacement character.\n\nThis leads to an important conclusion: string length and size in bytes are different things. The Russian word privet consists of six characters, but in UTF-8 it takes twelve bytes. One smiley is one character and four bytes. For network protocols, databases and files, the number of bytes matters, and for the user, the number of characters. It is even worse to confuse them when truncating a string: if we cut the sequence in the middle of a multi-byte character, we get broken data. So you need to know exactly what you are counting, and always specify the encoding explicitly when reading and writing files.\n\nLet us move on to errors. Data can get corrupted because of noise in a wire, disk defects or cosmic rays. The simplest protection is the parity bit: a bit is added to each word so that the total number of ones is even. If on receipt the number of ones is odd, some bit has flipped. This is very cheap, but the method is not perfect. It does not find the error when two bits flip at once, and it does not tell you which bit is wrong. Still, parity checking was used in memory, on buses and in serial ports, and its idea underlies stronger methods.\n\nA checksum works in a similar way, but protects a whole block of data. We add up all the bytes and store the remainder of division by two hundred fifty-six. The receiver repeats the calculation and compares. The drawback is that byte order is not taken into account: if you swap two neighboring bytes, the sum stays the same, and the error goes unnoticed. XOR of all the bytes suffers from the same problem. For reliable protection, the result must depend on every byte and on its position. Cyclic codes have this property, and we will talk about them now.\n\nThe cyclic redundancy check, CRC, treats the data as a huge binary number and divides it by a fixed polynomial, and the remainder of the division is used as the check value. The division is carried out without carries: instead of subtraction, XOR is used. Thanks to this, CRC detects all short burst errors, any error of one or two bits, and almost any more complex one. It is computed by a simple and very fast circuit made of a shift register and XOR gates. The thirty-two-bit CRC protects Ethernet frames, ZIP archives and file systems.\n\nCan we not only detect an error, but also correct it? Yes, with the Hamming code. Four information bits are supplemented with three check bits, which are computed as the parities of different subsets. The receiver repeats the checks and gets a three-bit number called the syndrome. If it is zero, there are no errors, and otherwise it directly points to the number of the flipped bit, and it is enough to flip it back. The minimum Hamming distance between valid words, the number of differing bits, is three: one error is corrected, two are detected. This is how error-correcting memory works, and similar Reed-Solomon codes protect compact discs, QR codes and satellite communication.\n\nThe cyclic code and the Hamming code protect against random failures, but not against malicious intent: for a CRC it is easy to find other data with the same value. To protect against tampering, cryptographic hash functions are used, for example SHA-256. A hash turns data of any length into a short fingerprint of fixed size, and if you change just one bit of the source, you get a completely different fingerprint: this is called the avalanche effect. Finding two different files with the same hash is practically impossible. That is why hashes are used to verify downloaded programs, and version control systems use them as commit names. For random errors a CRC is enough, for deliberate ones you need a hash.\n\nLet us sum up. Text is numbers, and agreeing on the encoding is critically important. Unicode gives every character a number, UTF-8 writes it in variable-length bytes and is compatible with ASCII. The number of characters and the number of bytes are different quantities. To protect data from errors, we use the parity bit, checksums, cyclic codes and Hamming codes: the stronger the protection, the more redundant bits it requires. In the following chapters we will start building digital logic and reach the processor itself.
