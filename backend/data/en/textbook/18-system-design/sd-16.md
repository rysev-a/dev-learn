#CHAPTER 16 | CI/CD and Zero-Downtime Deployment
Chapter 16. Continuous integration, delivery, and zero-downtime deployment. The most common cause of outages is not broken hardware but our own deployments. That is why the way code is delivered is as much a part of the design as the database and the cache. Practice shows a paradox: the more often you deploy, the safer it is. A small change is easy to check, quick to roll back, and easy to understand if it broke the service. Rare big releases accumulate risk. In this chapter we will walk through the pipeline from commit to users, and the ways to deploy without stopping.\n\nContinuous integration means that every code change is built and checked right away. The pipeline runs the build, unit tests, style checks, static analysis, and a scan for vulnerabilities in dependencies. The checks have to be fast, under ten minutes, otherwise people work around them. Developers' branches are kept short and merged into the main branch often: long-lived branches lead to painful merges. A broken main branch is a reason to stop and fix it, not to pile up red builds. A healthy pipeline is the foundation of trust in changes.\n\nThe result of a build is an artifact, most often a container image. The rule is: build once, deploy everywhere. The same image that passed the tests goes to the staging environment and then to production, and only the configuration makes the difference. The artifact gets an immutable version, usually the commit hash, and is stored in a registry. Rebuilding the image for each environment is dangerous: what reaches production is not what was tested. Immutability also gives you a fast rollback: you just deploy the previous version, which is already sitting in the registry.\n\nContinuous delivery extends the pipeline: after the build and tests, the artifact is automatically deployed to staging, passes integration and acceptance checks, and then reaches production, automatically or at the push of a button. In GitLab the pipeline is described in a file: stages, jobs inside them that runners execute, and environments with a history of deployments. Reproducibility matters: the pipeline is described as code and stored together with the project. The deployments themselves should be boring: one button, no manual steps.\n\nThere are four main ways to update a service. Stop and replace: simple, but with downtime. Rolling update: servers are replaced one at a time or in batches, and the service does not stop. Blue-green: a full new copy is brought up alongside, and traffic is switched over to it. Canary: a small share of users gets the new version while everyone else keeps running on the old one. The safer the method, the more expensive or complicated it is. The choice depends on the acceptable risk, the budget, and how easy it is to roll back.\n\nIn a rolling update, the orchestrator takes one server out of rotation, updates it, waits until it is ready, and moves on to the next. The service does not stop, and no extra resources are needed. But during the deployment the capacity drops by one server, so the headroom has to cover that: with two servers, losing one is half. The readiness check is critical: a server that starts taking traffic before it has warmed up drags the metrics down. Two versions of the code run at the same time, so changes have to be backward compatible.\n\nBlue-green: the production environment serves users, and next to it you deploy an exact copy with the new version. It is fully tested, and then a single switch redirects all the traffic. Rollback is instant too: switch back. The deployment does not reduce capacity, and the two versions never run side by side under load. The price is double the resource spend during the deployment, and the question of the shared database: both environments use the same database, so the schema has to be compatible with both versions of the code.\n\nThe name comes from the canary in the coal mine. The new version gets one or two percent of the traffic. The system is compared with the old one by metrics: errors, latency, saturation. If everything is fine, the share is raised in steps: five, twenty-five, fifty, a hundred. If the metrics get worse, the deployment is rolled back automatically, and only a small percentage of users were affected. The approach needs good observability and enough traffic on the canary. It combines well with cells: the new version goes into one cell first, then into the rest.\n\nDeploying and turning on a feature are different things. Feature flags let you ship the code switched off and turn it on later, as you wish, for some of the users: employees, one percent, one country. If the feature misbehaves, you switch it off instantly, with no deployment. Flags also enable dark launches, where the new code runs in parallel with the old one without affecting the response, and the results are compared. The price: flags have to be removed after the feature is on, otherwise the code gets overgrown with branches, and combinations of flags become impossible to test.\n\nThe database schema is shared by the old and the new version of the code, so it has to be changed reversibly and without locks. The rule is expand and contract. First we add the new column or table without removing the old one: both versions of the code work. Then we deploy code that writes to both places and reads the new one. We migrate the old data in the background. And only when all versions have switched over and confirmed that things work, we remove the old. This takes several deployments, but needs no downtime. Large tables are changed without locks using special tools.\n\nRollback has to be a fast, well-practiced operation: deploy the previous artifact, which is already in the registry. The decision to roll back is made quickly, without digging into causes: first you bring the service back to a working state. But there is a catch: code is easy to roll back, data is not. If the new version has already written data in a new format, the old one may not understand it. So data changes are made backward compatible, and in hard cases you fix forward, quickly releasing a new version. Rollback should be rehearsed just like region failover.\n\nThe pipeline is a privileged target: it has the right to change production. Secrets are kept in a dedicated vault and handed to jobs for a limited time, not put in the repository. Artifacts are signed, and production accepts only signed ones. Permissions are restricted: the test job should not have access to production keys. Dependencies are scanned for vulnerabilities, and their versions are pinned. All this is called supply chain security: it is easier for an attacker to swap a dependency or the pipeline than to break into the service itself.\n\nLet's sum up. Frequent small deployments are safer than rare big ones. Continuous integration checks every change, the artifact is built once and never changes, and the pipeline is described as code. Deployments are gradual, through blue-green or canary, chosen by cost and risk. Flags separate deploying from turning on, the database schema is changed in three steps, and rollback is rehearsed. The supply chain is protected, and the health of delivery is measured by deployment frequency, lead time for changes, failure rate, and recovery time. In the exercises you will pick a deployment strategy and calculate the capacity headroom.
