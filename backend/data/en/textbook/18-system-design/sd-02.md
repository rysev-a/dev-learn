#CHAPTER 2 | Scaling and load balancing
Chapter 2. Scaling and load balancing. The service is growing, and one server can no longer cope. There are two ways out. You can buy a more powerful machine: more processors, more memory, a faster disk. That is vertical scaling. Or you can put several more identical servers next to it and split the requests between them. That is horizontal scaling. Each path has its own limits, prices, and demands on the program. Knowing them, you understand in advance when a simple solution still works and when it is time to rebuild the whole design.\n\nVertical scaling is the simplest: you don't need to change the program, you just take a bigger machine. For a small service this is often the best choice. But it has three limitations. The ceiling: the biggest server has a limit, and there is nowhere to grow beyond it. The price: a machine twice as powerful costs noticeably more than twice as much. And reliability: there is a single server, and when it breaks or is updated, the service is unavailable. So you use vertical growth while it is cheap, and right away prepare the program to run on several machines.\n\nHorizontal scaling adds identical servers. Capacity grows almost in proportion to their number, and so does the price, while the failure of one machine stops being a catastrophe. You pay with complexity. You need a load balancer that distributes requests. You need any server to be able to handle any request, which means the program must not keep locally anything its neighbors don't have. This property is called statelessness, and it is what turns horizontal scaling from a dream into working practice.\n\nA stateless server remembers nothing between requests: everything it needs it takes from the request or from an external store. User sessions live in a fast shared store. Uploaded files go to object storage. Data goes to the database. Then any instance can replace any other: you can add one, remove one, restart one, and users won't notice. But if a server keeps a session in its own memory, the request from the next click has to land on the same machine, and all the beauty of balancing is gone.\n\nThere are three ways to store a user's login. The first is sticky sessions: the balancer always sends a person to the same server. It's simple, but when that server goes down, users get logged out, and the load is spread unevenly. The second is a shared session store, for example a fast in-memory database: any server will find the session by its identifier. The third is a signed token that the client carries with it: the server only needs to verify the signature. A token removes the need for a store, but it is hard to revoke early, so its lifetime is made short.\n\nA load balancer stands at the entrance and does several jobs. It distributes requests among servers. It checks whether each server is alive and stops sending requests to faulty ones. It often terminates encryption: it accepts a secure connection from the client and then talks to the servers in plain text or with its own internal encryption. It can limit the rate, compress responses, and cache. A single balancer withstands tens of thousands of requests per second, so under moderate load it is rarely the bottleneck, but it can very well be a point of failure.\n\nThe simplest algorithm is round robin: the first request to the first server, the second to the second, and so on. It works well for identical servers and short requests. If requests vary in length, it is better to send to the server with the fewest active connections. For unequal machines, you introduce weights: the powerful one gets more. And if you need the same key, a user or a product, to land on the same server, you apply a hash of the key. This gives you server-side caching and stickiness, but the load can become skewed.\n\nLoad balancers come at two levels. Layer four works with connections: it looks at addresses and ports and forwards bytes. It is very fast and cheap, but it doesn't understand the content. Layer seven parses the application-level protocol: it sees the path, headers, and cookies. That's why it can send requests to different services by path, add headers, retry failed requests, and compress responses. You pay with latency and resources. Often both are used: a fast layer four outside and a smart layer seven inside.\n\nThe balancer periodically polls the servers: does the port respond, does a special check address return success. After several failures a server is taken out of rotation, and after several successes it comes back. The check must be meaningful: if it doesn't touch the database, a server that has lost its connection to the database will be considered healthy and will get requests it can't serve. During a rollout, a server is first put into drain mode: it receives no new requests and calmly finishes the current ones.\n\nThe balancer solves the problem of server failures, but it becomes a single point of failure itself. The solution is a pair: two balancers share one address, and if the primary goes silent, the standby takes the address over. Another approach is several balancers with one address announced from different places in the network: requests go to the nearest live one. And in the cloud, the balancer is a managed service that the provider has already made fault tolerant. In any case, the question to ask is: what happens if this very component fails.\n\nLoad changes over the course of a day, and keeping a fleet sized for the maximum is expensive. Autoscaling adds servers when load grows and removes them when it drops. Usually it goes by average processor utilization or queue length. Three things must be taken into account. A new server doesn't start instantly: startup and warm-up take minutes, so the threshold is set with a margin. Sharp spikes are faster than the system's reaction, and you keep a reserve for them. And to keep the number of servers from jumping back and forth, you introduce a pause between decisions.\n\nHow many servers do you really need? Calculate how many are required for the peak at a comfortable utilization, and add one more: if any one of them is lost, the rest will carry the load. This is headroom in the N plus one scheme. If you need to survive the loss of a whole availability zone out of three, you need one and a half times the calculated minimum of servers. Headroom costs money, but less than downtime. It also makes rollouts easier: servers are updated one at a time, and the service never loses more than one node of capacity.\n\nLet's sum up. Vertical scaling is simple but limited by a ceiling, a price, and a single server. Horizontal scaling grows almost linearly and raises reliability, but it requires statelessness and a load balancer. Sessions are moved to an external store or into tokens. The balancer distributes requests, checks health, and must itself be made redundant. Layer four is faster, layer seven is smarter. Autoscaling adjusts the fleet to the load, and N plus one headroom protects against the loss of a node. In the exercises you will choose between approaches and teach the design to survive failures.
