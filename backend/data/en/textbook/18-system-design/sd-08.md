#CHAPTER 8 | Queues and Workers
Chapter 8. Queues and Workers. So far a user's request has been handled from start to finish while the user waits for the answer. But a lot of work can be done later. An email does not have to go out within milliseconds, an image thumbnail can wait, and recalculating recommendations is not needed right now at all. If we accept the task, put it in a queue, and immediately answer that everything is accepted, the user does not wait, and the system gets a buffer between its fast and slow parts. This is one of the most useful techniques there is, and it has its own rules.\n\nA message queue has three parts. The producer creates a message: an order was placed, a file was uploaded. The broker stores it reliably on disk and is responsible for ordering. The consumer, or worker, picks up the message and does the work. The producer does not need to know who will process it, or when. Consumers can be added and removed independently. If they stop, messages pile up in the queue instead of being lost. This turns a rigid coupling between services into a soft one, through a shared buffer.\n\nA queue solves several problems at once. It smooths out peaks: the database accepts writes at its own pace, while the spike waits in the queue. It decouples services: sending emails does not fail along with the mail provider. It allows retries: a failed task can be taken again. And it lets you postpone work to the night, or to a moment when resources are free. The price is that the system becomes asynchronous, the result does not appear immediately, and ordering and retries have to be handled by hand. So a queue goes where delay is acceptable.\n\nThere are two models. A point-to-point queue: each message goes to just one of the consumers, so several workers share the work. Publish and subscribe: a message is sent to a topic, and every subscribed group gets its own copy independently. This way a single event, order placed, is handled at once by the delivery service, the analytics service, and notifications. Within a group, consumers share the work, as in a queue. The combination of these models is the modern broker, for example one built on an event log.\n\nTo let a queue withstand a big stream, it is split into partitions. Each partition is an ordered log that is read by one consumer from the group. Order is guaranteed only within a partition, so messages whose order matters, for example the events of one order, are sent by the same key into the same partition. The number of partitions limits parallelism: a group cannot have more consumers than partitions, or the extra ones sit idle. Queue throughput grows with the number of partitions.\n\nHow does the broker know a message has been processed? The consumer acknowledges it after finishing the work. Until the acknowledgment arrives, the broker considers the message busy, and when the timeout expires it returns the message to the queue for another consumer. The consequence: if a worker did the job and crashed before acknowledging, the message will come again. This is at-least-once delivery. Acknowledging before processing is dangerous: on a failure the message is lost. The right order is to do the work first, then acknowledge.\n\nAt-least-once delivery brings a requirement: the worker must be idempotent. In practice it works like this: every message has a unique identifier, the worker writes the result together with the identifier in one transaction, and on a repeat it sees it has already done this and skips it. Order is not absolute either: with several partitions and retries, messages can arrive out of order. If order matters, use one key per entity and check the version. Without these two measures, a queue produces rare and very unpleasant bugs.\n\nSometimes there is a message that cannot be processed: broken data, a bug in the code. If it is returned to the queue forever, it blocks the others and steals resources. So the number of attempts is limited, with retries after a growing pause, and after the last one the message is sent to a separate dead letter queue. There it can be examined by hand, the code fixed, and the message returned. The length of this queue is watched, and an alert is set up: growth in dead letters means something is broken in the system and users are already suffering.\n\nHow many workers do you need? Divide the rate of incoming messages by the rate at which one worker processes them, and add some headroom. The main metric of a queue is lag: the time or the number of messages waiting to be processed. If lag grows, there are too few workers; if it is zero and they sit idle, there are too many. Autoscaling is built on this: more workers when the queue grows, fewer when it is empty. Do not forget the limit: no more consumers than partitions, and the workers must not overload the database they write to.\n\nA queue is not infinite. If producers outpace consumers for long enough, it overflows, and messages start getting lost. We need feedback, or backpressure. There are several options. Slow down the producers: they get a refusal and retry later. Drop the less important: ratings and metrics can be skipped, payments cannot. Prioritize: urgent tasks go to a separate fast queue. And the real answer is to add consumers in time. The queue size and the alert threshold are set in advance, not after an outage.\n\nNot all work is urgent. Delayed messages are delivered after a set time: remind the user in a day, cancel an unpaid order in fifteen minutes. Periodic tasks are run on a schedule: nightly reports, cleanup. It is important that the schedule works reliably in a cluster: two copies of the scheduler must not launch a task twice, and a long task must not overlap with the next run. So the scheduler itself puts the task into a queue, and ordinary idempotent workers execute it.\n\nA common mistake: first write the order to the database, then send a message to the queue. If the process crashes between the two, the order exists but the message does not. The reverse order is worse: the message went out, but there is no record. The solution is the outbox pattern. The message is written to a special table in the same transaction as the data. A separate process reads the table and publishes the messages to the broker, marking the sent ones. Delivery is at-least-once, but loss is ruled out: the record and the intent are saved atomically.\n\nLet us sum up. A queue turns synchronous work into asynchronous work: the user does not wait, peaks are smoothed, and services are decoupled. Partitions set order and parallelism. The consumer acknowledges work after finishing it, which means duplicates are unavoidable and workers are idempotent. Poison messages go to the dead letter queue. The main metric is lag, and workers are scaled by it. Overflow calls for backpressure. The write and the message are tied together by the outbox table. In the exercises you will learn to smooth out a peak and to choose the number of workers.
