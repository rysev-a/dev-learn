#CHAPTER 4 | Databases: Replication
Chapter 4. Databases: replication. We have learned to scale application servers almost for free, because they hold no state. All the state lives in the database, and that is exactly why it becomes the main bottleneck and the main point of failure. A single machine can be made stronger, but not without limit, and it is still just one machine. So the database is copied: we keep several instances with the same data. Replication solves two problems at once: it gives headroom for reads and lets us survive the loss of a machine. But we pay with consistency.\n\nThe most common scheme is one leader and several followers. All writes go to the leader: it puts them in order and records them in a log. The followers read this log and apply the same changes in the same order. Reads can be served by any of them. This scheme is simple and easy to reason about: there are no write conflicts, because there is only one writer. Its limit is the leader's write performance: by adding followers we scale only reads. Writes will need a different technique, which we will cover in the next chapter.\n\nFor most services there are far more reads than writes, and replicas are the cheapest way to grow. If one database handles a thousand reads per second, a leader with four replicas will handle about four thousand, while writes still go only to the leader. The application has to distinguish two connections: one for writes to the leader and one for reads to a pool of replicas. Combined with a cache, this is often enough for a long time. Make sure the replicas are not smaller than the leader: otherwise, after failing over to a replica, the service will sag.\n\nWhen does the leader confirm a write to the client? If it does so right away, without waiting for the copies, that is asynchronous replication: the write is fast, and the replicas lag behind by milliseconds or seconds. If the leader waits for confirmation from the replicas, that is synchronous replication: data is not lost when the leader fails, but writes are slower and depend on the slowest replica. A middle road is often chosen: one synchronous replica for durability, the rest asynchronous for reads. The choice determines what you are ready to sacrifice: write speed, or freshness and safety of the data.\n\nAsynchronous replicas lag behind the leader. In quiet times that is tens of milliseconds, but during a burst of writes or a heavy operation on the replica, the lag grows to seconds and minutes. The user sees the consequences: a comment they just posted has vanished, because the read landed on a lagging replica. That is why lag is measured and shown on a dashboard, and when it exceeds a threshold the replica is temporarily removed from the read pool. Lag is not a bug but a property of the design, and the application must know how to live with it.\n\nA user has the right to expect to see their own changes. This guarantee is called read-your-writes. There are several ways to provide it. A simple one: after a write, for a few seconds read that user from the leader. A more precise one: remember the log position that the write reached, and read only from a replica that has already applied it. Another guarantee is monotonic reads: a user must not see something new and then something old. For that, one person's requests are pinned to a single replica.\n\nWhat do we do if the leader dies? We need to detect the failure after several missed health checks, pick the replica with the freshest log, declare it the leader, and redirect writes to it. Automatic failover cuts downtime to seconds, but it is dangerous because of false alarms: a network hiccup can make the system appoint a second leader, and then two nodes accept writes. This is called split brain. The defenses are a quorum and fencing: the old leader is forcibly shut off, and the decision is made by a majority of nodes.\n\nWith asynchronous replication, the leader may have confirmed a write to the client but not yet sent it to a replica. If it dies at that moment, the write is lost, and the new leader knows nothing about it. The acceptable amount of loss is called the recovery point objective, R-P-O for short. The acceptable downtime is the recovery time objective, R-T-O. If losing even a second of data is unacceptable, you need a synchronous replica. If it is acceptable, there is no need to pay for synchrony. These two numbers belong in the requirements alongside latency and volume.\n\nThere are systems with no dedicated leader: a write is sent to several nodes at once, and a read also reads from several. Say there are N copies in total, a write is confirmed by W nodes, and a read queries R nodes. If W plus R is greater than N, the sets overlap, and the reader is sure to see at least one node with the latest write. A typical choice is three copies, with two for the write and two for the read. Such a scheme survives the loss of a node without any failover, but it makes conflict resolution harder, and it is used in key-value stores.\n\nReplication allows different topologies. When there are many replicas, it is hard for the leader to send the log to all of them, so some replicas receive changes from other replicas in a cascade. Replicas can be placed in other availability zones to protect against the loss of a data center, and in other regions: reads get closer to users, but lag grows because of the distance. There is also a dedicated replica for analytics: heavy reports go to it and do not interfere with the main workload. That way the analysts never have to touch the production database.\n\nA replica is not a replacement for a backup. If someone runs a delete by mistake, it is applied instantly on all the replicas: the copies are identical, including in their mistakes. So you also make backups: periodic snapshots and a change log that lets you restore the database to any second. Backups are stored separately, for example in another region, and, most importantly, restoring from them is tested regularly: a backup that has never been restored exists only on paper. This is an unpleasant but important rule for any serious service.\n\nThe list of typical mistakes is short. Reading from a replica right after a write and being surprised that the data is missing. Not watching the lag and learning about it from users. Keeping replicas weaker than the leader, so the service sags after a failover. Never testing failover on a real failure: it breaks exactly when you need it. And treating replication as a substitute for a backup. To avoid all of them, run drills regularly: shut down the leader in a test environment and watch how the system survives the failure.\n\nLet us sum up. Replication copies data to several nodes: the leader accepts writes, the followers answer reads. It scales reads and protects against the loss of a machine. Synchronous replication is safer but slower; asynchronous is faster but loses data and lags. Your own writes should be read from the leader, or with a check of the log position. Leader failover needs a quorum so that you do not end up with two leaders. A replica does not replace a backup. Now, in the simulator, you will add replicas, turn on failover, and fight for low lag.
