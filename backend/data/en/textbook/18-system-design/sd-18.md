#CHAPTER 18 | Final Project: A Short-Video Service
Chapter 18. Final project. Let's pull everything we have learned into one service: a short-video platform. Users upload clips, watch a feed, leave likes, and search by title. We will walk the whole path of a designer: requirements, estimates, a first simple diagram, bottlenecks, hardening, media, asynchronous processing, search, fault tolerance, observability, and cost. In the exercises the diagram will grow stage by stage, like a real service, and it will end with an exam where you assemble the final architecture from scratch.\n\nWe start with requirements. Functions: upload a clip, watch it, scroll a feed of subscriptions, search by title, leave likes. Non-functional requirements: fifty million daily active users, two orders of magnitude more views than uploads, availability of ninety-nine point nine percent, a feed response within two hundred milliseconds, durability of the clips, and tolerance for a small delay before a clip shows up in the feed and in search. The budget is limited, so we take nothing extra. These numbers are the compass for every decision that follows.\n\nNow we count the load. Fifty million users with twenty actions a day each make a billion requests, which is about twelve thousand per second, and the peak is three times higher. Most of these are requests for video, images, and segments. Metadata is read once every few seconds per user. Uploads are one million a day, or twelve per second. Video volume grows by hundreds of terabytes a day: petabytes a year, but these are objects in storage, served through a content delivery network. The metadata database, on the other hand, fits in a few hundred gigabytes.\n\nThe first diagram is always simple: users talk to an application server, and it keeps data in a database. For a thousand users and a hundred requests per second that is enough, and adding anything more would be premature. At first the video can even be stored next to the application. It is useful to calculate right away how long this diagram will last: one small server handles three hundred requests per second, and the database handles a thousand reads. From here on, we take each step because a calculation showed a bottleneck, not because that is how it's done.\n\nThe load has grown tenfold, and the database is the first to give out: metadata reads have overloaded it. We strengthen the system in order. We put in a load balancer and several stateless servers. We add a metadata cache: the working set is small, and ninety percent of reads no longer reach the database. A database replica gives both headroom and fault tolerance. We back every decision with a calculation: node utilization and the cache hit rate. And we immediately notice the risk we discussed in the chapter on caching: if the cache disappears, the database cannot cope, so the cache needs a replica too.\n\nThe next bottleneck is the video. If we serve it through application servers, no fleet will be big enough. We move the files to object storage and put a content delivery network in front of it: popular clips are served close to the user, and the storage gets only rare requests. The application servers return just metadata and signed links. We make cache lifetimes in the network long, and versions in file names solve staleness. Upload goes straight to the storage through a temporary link. Now the bulk of the traffic and request load is off our infrastructure.\n\nAn uploaded clip has to be transcoded into several resolutions and given a preview. This is heavy and slow work, so it is done asynchronously. When the upload finishes, an event goes into a queue, and workers take tasks and write the results to storage. The workers are idempotent: a repeated delivery does no harm, and they can safely run on cheap interruptible servers. We tune the number of workers by the queue backlog. The user sees right away that the clip was accepted and gets a notification when processing is done. As a bonus, the queue smooths out upload spikes.\n\nThe subscription feed is built as a hybrid: for ordinary authors, ready-made feeds are put into the cache at publication time, while celebrity posts are mixed in at read time. Like counters accumulate in a fast store and are written to the database in batches. Search goes into a separate cluster, with shards by index size and replicas by load. It is updated from database events with a delay of a few seconds, and the requirements allow that. When metadata writes outgrow a single leader, we shard the database by a hash of the user identifier.\n\nNow reliability. The servers, cache, workers, and database are placed in three availability zones with enough spare capacity to lose one. The load balancers are redundant. The application has timeouts, retries with a pause, and a circuit breaker, and at the entrance there is a rate limiter, so that an attack or a client bug cannot bring everything down. Deployment goes one server at a time, and a new version first receives a small share of traffic. We test the diagram by mentally failing each component, and confirm it in the simulator: losing a zone, a server, the cache, or the database must not stop the service.\n\nWithout observability, a service like this cannot be operated. Golden-signal metrics for every component, logs with an end-to-end request identifier, and traces for slow requests. The goals: availability of ninety-nine point nine percent and a ninety-ninth percentile feed response of two hundred milliseconds over a thirty-day window. The error budget decides when we ship something new and when we fix. Alerts are tied to symptoms and to the burn rate of the budget, and each one has a runbook. After incidents we write a blameless postmortem.\n\nNow cost. For the application servers, which carry a constant base load, we switch to reserved capacity. The transcoding workers are idempotent, so we move them to spot instances. Autoscaling removes extra servers at night. Old clips move to cooler storage classes, and rarely watched ones go to the archive. The content delivery network lowers both the traffic bill and the number of servers. Infrastructure is described as code, costs are tagged to teams, and there is a budget with alerts. Every saving is checked against the reliability goal: we do not sacrifice nines for a dollar.\n\nHow should you present this kind of design in an interview or a defense? Build your answer step by step. Requirements and numbers: out loud, with figures. A simple diagram. Load calculation and the bottleneck. Hardening node by node, with a reason for each choice. Failures of every component. Trade-offs: what you chose and what you gave up, and how the diagram changes at ten times the growth. Don't try to list every technology: show a chain of cause and effect. The interviewer is judging how you reason, ask questions, and change your solution, not whether you guess someone else's diagram.\n\nLet's sum up the book. System design is a single cycle: requirements and numbers, load calculation, finding the bottleneck, strengthening with known techniques, and analyzing failures. We have covered scaling and balancing, caches and content delivery networks, replication and sharding, consistency and idempotency, search and file storage, queues, resilience, microservices, real time, feeds and typical problems, observability, zones and regions, deployment, and cost. Now comes the exam: assemble the final diagram step by step and defend every decision.
