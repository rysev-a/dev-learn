#CHAPTER 3 | Caching and CDN
Chapter 3. Caching and content delivery networks. The cheapest request is the one that never reached the database. If the answer is already known, you can serve it from fast memory in a fraction of a millisecond and touch neither the application server nor the disk. A cache is the most powerful and the most dangerous tool in system design: it speeds things up tenfold or more, and at the same time it brings a new problem, stale data. In this chapter we will look at where to put caches, how to fill them, how to measure their benefit, and what they put at risk.\n\nThere are caches at every step of the request path. The browser keeps files on the user's machine and does not touch the network at all. A content delivery network keeps copies of static files close to the person. A reverse proxy in front of the application remembers whole pages. The application cache, in fast memory, stores the results of database queries. And finally the database itself keeps recently used pages in memory. The closer a cache is to the user, the cheaper and faster the answer, but the harder it is to clear when the data has changed.\n\nA content delivery network, or CDN, serves images, scripts, and video from servers located near the user. The request first goes to the nearest point of presence; if the copy is not there, that point contacts your server once and remembers the response. The lifetime of an entry is set by a caching header: the longer it is, the higher the hit ratio. Purging stale files is expensive and slow, so people add a version or a hash to the file name: the new version gets a new name, and the old one simply stops being requested.\n\nThe most common approach is the cache-aside pattern. The application looks in the cache first. If the entry is found, that is a hit, and the database is not involved. If not, that is a miss: the application reads the database, puts the result into the cache with a time to live, and responds to the user. A write goes to the database, and the old copy in the cache is deleted or updated. The scheme is simple and resilient: if the cache is unavailable, the system keeps working, just more slowly. Its main drawback is a window in which the cache may serve stale data.\n\nThere are other write strategies too. Write-through writes data to the cache and to the database at the same time: the cache is always fresh, and the write is a little slower. Write-back first puts the data in the cache and confirms success, and flushes it to the database later, in batches. It takes most of the writes off the database, so it suits counters and metrics. But if the cache crashes before flushing, the data is lost. The choice depends on the price of a loss: acceptable for likes, not acceptable for payments.\n\nThe main cache metric is the hit ratio. It depends on several things. On size: the bigger the cache relative to the working set, that is, the data that is read often, the better. On time to live: a short one lowers the ratio, a long one raises the risk of staleness. On the share of writes: every write spoils a copy. And on the distribution of requests: if a few popular keys receive most of the traffic, even a small cache already gives ninety percent. If all keys are equally likely, a cache barely helps.\n\nWhen the cache memory is full, you have to decide what to throw out. The least recently used algorithm removes the entry that has not been accessed for the longest time: it is simple and works well when access has locality. The least frequently used algorithm keeps entries with high overall popularity and survives one-off scans better. An entry's time to live does not depend on eviction: when it runs out, the entry is deleted in any case. Cache size is chosen so that the working set fits entirely, not by the principle of how much we can spare.\n\nThey joke that computer science has two hard problems: naming things and cache invalidation. There are three main approaches. Time to live: the data expires by itself, and the acceptable delay is a business decision. Events: when a record changes, the application deletes it from the cache, but between the database write and the cache deletion a race can leave a stale value behind. A version in the key: on change you increase the version number, new requests go to the new key, and the old ones die on their own. Choose according to how painful it is to show old data.\n\nA popular key expires. At that moment a thousand requests all see a miss and rush to the database for the same value. The database is overloaded, responses slow down, and the new requests only make things worse. This is a cache stampede. There are three defenses. Single flight: while one request recomputes the value, the others wait for its result. A random addition to the time to live, so keys do not expire at the same moment. Early refresh: the value is recomputed in the background while the old one is still valid. For the hottest keys, all three techniques are used together.\n\nTwo related troubles. Cache penetration: clients request keys that do not exist, for example random identifiers. The cache does not find them, the database does not either, and every request reaches the storage. The defense is to cache negative answers for a short time, or to put a Bloom filter in front of the database, which quickly says that such a key definitely does not exist. Avalanche: many keys received the same time to live and expired together, for example after a cache restart. The cure is spreading out the lifetimes and warming up gradually.\n\nSometimes a single key receives a huge share of the traffic: a celebrity's profile, the home page on the day of a sale. It lives on one cache node, and that node becomes the bottleneck while the others sit idle. The remedy is a second level: a small local cache right in the memory of each application server, with a short time to live, a few seconds. Requests for the hottest keys do not even reach the network. The price is a few seconds of possible inconsistency between servers, and for many services that is acceptable.\n\nWhen the cache takes ninety percent of reads, the database is sized only for the remaining ten. So a cache failure or restart knocks the database over: all the requests flood into it at once. To prevent that, you keep replicas of the cache and spread keys across several nodes, so that losing one affects only a small share. After a cold start, the empty cache is warmed up in advance, and the load on the database is limited. A useful question in a design review: what happens if the cache disappears right now? The honest answer decides whether you need redundancy.\n\nLet us sum up. Caches sit at every level, from the browser to the database. A content delivery network serves static files close to the user, and a version in the file name solves the staleness problem. The main scheme is cache-aside: a miss leads to the database and fills the cache. Write-back relieves write load but puts data at risk. The hit ratio is determined by size, time to live, and the distribution of requests. A cache stampede and an avalanche are cured by single flight and by spreading out lifetimes. And a cache failure must not knock over the database. Now let us practice in the simulator.
