#CHAPTER 7 | Search and File Storage
Chapter 7. Search and File Storage. So far we have kept our records in a database. But users have two wishes that an ordinary database handles poorly. Finding things by the words inside the text, and uploading or downloading a big file: a photo, a video, a document. A dedicated search engine exists for the first, and object storage for the second. They are cheaper and faster for their jobs, but they add new nodes to the diagram and new questions about consistency.\n\nThe simplest way to search text is a substring condition in a database query. It scans the whole table and kills performance: such a query is two to five times heavier than a normal one, and on millions of rows it takes seconds. It knows nothing about the morphology of a language, it cannot rank results, and it does not forgive typos. So for real search we build a special index of words. It answers in milliseconds, does not load the main database, and can scale independently of it.\n\nThe core of search is the inverted index. Each document is first split into words, the words are reduced to a normal form, the filler words are dropped, and for every word we store the list of documents where it occurs. A query with several words is an intersection of lists, not a scan of texts. Stemming lets us find the word dog when the user types dogs, and every language needs its own analyzer. The index takes about as much space as the original text, but it answers almost instantly.\n\nFinding documents is not enough, we also have to order them. The basic approach is to look at how often a word appears in the document and how rare it is across the whole collection. A rare word in a document tells us more about it than a common one. The modern formula, B M twenty-five, develops this idea by capping the contribution of repeats and taking the length of the text into account. On top of that we add popularity, freshness, and personal preferences. Ranking quality is checked on labeled queries, not by eye: a search that merely finds things does not satisfy the user.\n\nSearch lives in a separate cluster. The index is cut into shards, and every shard has replicas for reads and for reliability. A query first arrives at a coordinator node, which sends it to all the shards and merges the best results. It is important to remember that the search index is a derived copy of the data, not the source of truth. The source is the main database. If the index is lost, it can be rebuilt from the database. That is why critical data is never kept only in a search index.\n\nHow does the index learn about changes in the database? The application could send a document to search itself when it writes, but then a failure between the two writes makes them diverge. It is more reliable to read the database's change log and send events to a queue, from which a worker updates the index. This way the index lags by seconds but never loses a change. The consequence is that a freshly created document may not show up in search right away, and the interface has to explain that. Periodically the index is fully rebuilt and reconciled.\n\nSearch queries have no single key, so they always go to all the shards, each shard returns its own best results, and the coordinator combines them. The more shards, the more overhead, but a shard that is too big gets slow, so shard size is kept to a few tens of gigabytes. Shards are determined by data volume, and replicas by throughput: to handle more queries, we add replicas. So we need to count with two numbers: shards by volume, and replicas by load and fault tolerance.\n\nGood search also helps you type the query. Autocomplete is built on prefix trees or on separate indexes of popular queries: latency must be tens of milliseconds, so these indexes are kept in memory and updated separately. Typo correction relies on edit distance: how many letters must change to get another word. To pick candidates quickly, words are split into short pieces called n-grams. All these features cost memory and load, so turn them on where they really pay off.\n\nStoring files in an ordinary database is expensive and inconvenient: it bloats, backups slow down, and reading large objects pushes useful data out of memory. For files there is object storage: a flat space where an object lies under a key, and every copy is kept in several zones. It is cheap, almost unlimited in size, and handles huge throughput. The database keeps only the metadata: the name, the size, the owner, and the object's key in the storage.\n\nIf uploads pass through the application servers, those servers spend connections and memory just moving bytes. It is better to hand the client a temporary signed link, so it uploads the file straight into object storage. The application only checks permissions and creates a record, and gets a notification when the upload finishes. Large files are uploaded in parts, in parallel, and after a break only the missing parts are resumed. The size and type of the file are limited in advance, and the content is checked by a separate worker: an uploaded file can never be trusted.\n\nServing files directly from the storage is expensive and slow for faraway users. In front of the storage we put a content delivery network: popular files sit near the user, and the storage gets only rare requests. For public files, caching headers and versions in file names are enough. For private ones we issue a signed link with a limited lifetime: it checks permissions and stops working after a few minutes. This keeps private documents private, and the load on the application does not grow.\n\nAn uploaded image or video usually needs processing: making thumbnails, and transcoding to several formats and resolutions. This work is heavy and slow, so it is done asynchronously. On upload the storage emits an event, the event lands in a queue, workers pick up tasks, write the results back to the storage, and update the metadata. The user immediately sees that the file was accepted, and the processing status changes later. The number of workers is tuned by the queue: if the queue grows, we add workers.\n\nLet us sum up. A substring in a database query is poor search: it is heavy and does not rank. Real search is built on an inverted index, lives in a separate cluster, and is updated by events, so it is eventually consistent. Shards are chosen by index volume, and replicas by load. Files are stored in object storage, uploaded directly through signed links, and served through a content delivery network. Heavy processing goes to a queue. In the exercises you will connect search, calculate shards, and take the file load off the application.
