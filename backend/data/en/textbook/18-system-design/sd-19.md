#CHAPTER 19 | Project: Cloud Drive (Google Drive)
Chapter 19. Project: a cloud drive. We are designing a service like Google Drive. A user uploads files, opens them from any device, shares a link, and changes made on the computer show up on the phone by themselves. Earlier versions of a file can be restored, and deleted files sit in the trash. At first glance this is just storage, but under the hood there are several problems at once: a huge volume of data, durable storage, real-time synchronization, access rights, and cost. We will walk the whole path from the first version to the exam.\n\nLet's begin with requirements. Five hundred million users, a hundred million of them active daily, with a few gigabytes each on average: hundreds of petabytes in total. The main requirement is durability: losing a file is worse than being unavailable for an hour, so storage durability is measured in eleven nines. Metadata reads and writes run at thousands per second, while files are orders of magnitude bigger in volume but rarer in the number of accesses. One conclusion follows right away: metadata and file contents live in different systems and scale differently.\n\nPrinciple one: separate metadata from content. Metadata is the folder tree, names, sizes, owners, permissions, and the list of versions. There is not much of it, it is read and changed often, so it lives in a sharded database with a cache. Content is the bytes of the files: they are huge, immutable once written, and well suited to object storage. The metadata holds only references to content blocks. That way the database stays fast and small, while the storage grows independently and gets cheaper through storage classes.\n\nA file is not stored whole: it is cut into blocks, say four megabytes each, and every block is stored under the hash of its content. This gives three things at once. Resumable upload: if an upload breaks, we send only the missing blocks. Delta sync: if one piece of a big file changed, we transfer just one block. And deduplication: identical blocks from different files and different users are stored once. A file version is simply a list of block hashes, so a new version costs almost nothing when little has changed.\n\nUpload bypasses the application servers. The client sends the block hashes, the server replies with which of them already exist, and issues signed links for the rest. The blocks are uploaded in parallel straight into object storage. When all the blocks are in place, the client sends a commit: in one transaction the server creates the file version in the metadata. Until the commit, the file is not visible, and background cleanup later removes orphaned blocks. A repeated commit is safe: it is idempotent and uses an operation key.\n\nDownload is the most frequent path by traffic. A block addressed by its hash never changes, so it can be cached in the content delivery network for a long time. The application server checks permissions, finds the blocks of the version, and issues signed links valid for a limited time. The client assembles the file from blocks in parallel and can read ranges, for example for video. Popular files are served almost entirely by the delivery network, and object storage gets only the misses. This way the load on our servers does not grow with traffic.\n\nThe metadata database grows with the number of files, and it has to be sharded. A good key is the owner identifier: a user's whole tree sits on one shard, a folder listing does not walk across the cluster, and operations inside the tree are transactional. The difficulties start with shared folders: one owner's data is seen by others. For those, references and permissions are stored separately. A move between owners turns into a saga. Popular operations, such as a folder listing, are cached, and changes invalidate the cache through events.\n\nHow does a phone learn about an edit on the computer? Clients keep a persistent connection to a gateway, and on any change the server sends a short signal. The client then requests the list of changes separately, by a cursor, that is, the number of the last change it knows, and gets a delta: what was created, changed, and deleted. If the connection drops, nothing is lost: the cursor lets the client catch up. Changes are published to an event stream, from which notifications, search, and analytics consume them without loading the main path.\n\nTwo people changed the same file without seeing each other. Arbitrary files cannot be merged automatically, so the system keeps both results: the version committed first wins, and the second is saved next to it as a conflict copy. For text documents there is collaborative editing with a separate protocol. All versions are lists of block references, and keeping dozens of versions is cheap. Deletion first moves the file to the trash for thirty days, and only then does background cleanup free the blocks that nobody references anymore.\n\nAccess rights are a critical part of a drive. Permissions are set on folders and inherited downward, and a file can be given separate access for a person, a group, or through a secret link. A check is needed on every read and every change, so the sign-in and permissions service is called on every request and must be fast and reliable. Its answers are cached for seconds. Revoking access must take effect quickly, so signed links have a short lifetime, and a permission change is published as an event to clear caches.\n\nUsers search for files by name and by the text inside. This needs a separate search index. Names get there right away from the change stream, while text has to be extracted from the documents: that is heavy work, done asynchronously by workers from a queue. So a freshly uploaded file is not found by its text instantly. A special problem is permissions: search results must be filtered by what the user is allowed to see, and the indexes are sharded by owner so that a query goes only to the relevant parts.\n\nFor a drive, the main expense is not servers but storing hundreds of petabytes. It is reduced like this. Storage classes: fresh files sit in hot storage, and old ones that haven't been touched for a long time automatically move to cold storage, several times cheaper but with slow access. Deduplication removes identical blocks. Instead of three full copies, erasure coding is used: a block is split into parts and parity parts are added, giving the same durability at one and a half times the cost. Quotas and emptying the trash also help.\n\nLet's sum up. A cloud drive separates metadata from content: a database with shards and a cache holds the tree and versions, and object storage holds blocks under hashes. Upload and download bypass the servers, using signed links and the delivery network. Synchronization is built on a signal and a delta by cursor through an event stream. A separate service checks permissions, search works asynchronously, and storage costs are cut with storage classes and deduplication. Files sit in three zones and are verified by hashes: you can lose availability for a minute, but not data. In the exercises you will build this service in stages, and then take the exam.
