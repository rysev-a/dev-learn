#CHAPTER 15 | Resilience: Zones and Regions
Chapter 15. Resilience: zones and regions. So far we have survived the failure of a server or a database. But whole data centers fail too: the power goes out, a backbone line gets cut, an operator's mistake takes down the network. One such event stops everything that lived in that data center, no matter how many servers were there. To survive it, the system has to be spread across several independent sites. This chapter is about how to do that and what it costs.\n\nA failure domain is a set of resources that can break at the same time. A single host, a rack with shared power, an availability zone, an entire region. Two copies of the data in the same rack will not protect you from losing the rack. So copies are placed in different domains. The bigger the domain, the more rarely it fails, and the more expensive it is to protect against. The provider publishes guarantees for each level. The designer's question is this: which failure domain are we protecting against, and which failure are we ready to survive with some downtime?\n\nA region consists of several availability zones: independent data centers with separate power and networking, but connected by fast links. The typical layout is three zones. The application servers and their load balancers are spread evenly. Data is replicated between zones. If a zone goes down, two thirds of the capacity remains, and the capacity plan has to account for that: the load on the remaining servers grows by one and a half times. For zones, this layout is almost always enough: it protects against the most common data center failures.\n\nZones within one region are connected by links with a latency of about one millisecond. That makes synchronous replication between zones possible: the write acknowledgment includes a copy in another zone, so if a zone is lost, no data is lost. The database leader lives in one zone, the replicas in others, and automatic failover promotes a replica if the zone disappears. Caches and queues are spread out as well: the cache has a replica in another zone, and the queue has partitions in different zones. That way the whole request path survives the loss of one zone, not just the application servers.\n\nSometimes zones are not enough. A whole region can go down because of a provider error or a natural disaster. Besides, users on another continent get responses a hundred or two hundred milliseconds slower, and the laws of some countries require citizens' data to be stored inside the country. These reasons lead to multiple regions. But you pay for it with doubled resources, complicated data replication, and a latency between regions of tens or hundreds of milliseconds. That is why a multi-region design is built deliberately, when the cost of downtime or latency justifies the expense.\n\nThere are two main modes. Active-passive: the working region serves traffic, and the standby is ready to take over. The standby can be cold: only backups, and it takes hours to bring up. Warm: data is replicated, capacity is minimal, and it comes up in minutes. Hot: a full set of capacity, and failover takes seconds. Then there is active-active: both regions serve users, and each can replace the other. It uses resources more efficiently and fails over unnoticed, but it requires solving the problem of data consistency between regions. The choice depends on the acceptable downtime and data loss.\n\nHow does a user reach the right region? The first way is geo-DNS: the service name resolves to the address of the nearest healthy region. The drawback is record caching: after a failure, clients keep using the old address for a few more minutes, so the time to live is kept short. The second way is a global load balancer, which accepts connections on one address and distributes them across regions with health checks. The third is announcing one address from several places in the network, so packets go to the nearest live one. Health checks have to be meaningful, so that you do not fail over on a false alarm.\n\nThe speed of light is a limit: it is a hundred milliseconds between regions, and a synchronous write would slow down every operation. So replication is asynchronous, with a lag of seconds, and if a region is lost, the latest writes may disappear. If both regions are active and writes are possible in both, conflicts are inevitable: the same object was changed at the same time. They are resolved with rules, for example last write wins, or with special data structures. Often it is simpler to pin each user to a home region: their writes go there, and the other region keeps a copy for reads and for disasters.\n\nFailing over between regions is a risky operation. Automatic failover is faster, but prone to false triggers: a temporary network hiccup causes a failover that itself creates problems. So you set thresholds, confirmation from several vantage points, and manual approval for big decisions. Failing back is done carefully and not right away, so the system is not yanked back and forth. But the most important thing is to rehearse. A setup that has never been switched over will very likely not switch over when it matters: forgotten dependencies and wrong settings will turn up.\n\nA two-region setup can have one shared dependency that takes both down. It could be the name service, certificate issuance, the configuration store, the authentication system, the internal image registry, or the deployment platform. If they all live in one region, losing it stops the second region too. At design time it is useful to walk through each dependency and ask what happens if it becomes unavailable. The answer may be a copy in another region, a local cache good for a few hours, or a conscious assumption. The main thing is that it is made in advance.\n\nThere is an approach that limits not only hardware failures but also bugs in code. The service is divided into cells: each one is a complete, independent instance with its own servers, databases, and queues, serving a share of users, say five percent. A failure, a bad deploy, or an avalanche of requests damages one cell, and the others keep working. A new version is rolled out to a single cell first. A router on top determines the user's cell. The price is duplication and added complexity, but the blast radius is measured in percent, not in all of your users.\n\nReliability costs money. A single-zone setup is the baseline: one. Three zones with headroom: about one and a half. A hot standby region: about two. Active-active in two regions with enough capacity to lose one: more than two. To choose, weigh the cost of downtime against the recovery objectives you can accept: how long you can be down and how much data you can lose. For an internal reporting service, one zone and backups are enough. For a payment system, you need a second region. There is no universally right design, only a decision that fits the price of a mistake.\n\nLet's sum up. Copies are placed in different failure domains. Three zones of a region protect against the loss of a data center, and synchronous replication is possible between them. Multiple regions are needed when region failure, proximity to users, or legal requirements matter. The modes of operation are active-passive and active-active. Between regions replication is asynchronous, and traffic is directed through geo-DNS, a global load balancer, or address announcement. Failovers are rehearsed, hidden shared dependencies are hunted down, and the blast radius is limited with cells. In the exercises you will spread a system across zones and regions.
