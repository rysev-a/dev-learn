#CHAPTER 11 | Real Time: WebSockets and Chat
Chapter 11. Real time: WebSockets and chat. In the usual scheme the client asks and the server answers. But in a chat, a message from the other person has to show up right away, not whenever you happen to refresh the page. The same goes for notifications, stock quotes, collaborative editing, and games. The server has to be able to write first. That breaks familiar assumptions: connections live for hours, not milliseconds, and the scarce resource is no longer processing speed but the number of connections open at the same time.\n\nThere are several ways to do it. Frequent polling: the client asks every few seconds; it is simple, but the load is huge and the delay equals the polling period. Long polling: the server holds the request open until data appears. Server-sent events are a one-way stream from the server to the client over plain HTTP, which works well for notifications. A WebSocket is a full two-way channel, suited to chats and games. Choose the simplest option that covers the need: not every notification requires a WebSocket.\n\nA WebSocket starts with an ordinary HTTP request asking to switch to another protocol. After the handshake the connection stays open, and both sides send each other small frames at any moment. To tell that the other side is still alive, they periodically exchange service messages called ping and pong. The client does not notice a network drop right away, so you need timeouts and reconnection. An open connection occupies memory and a descriptor on the server even when nothing flows through it, and that is exactly what determines how you scale.\n\nIf you have a hundred thousand clients, you have a hundred thousand open connections. A modern event-driven server holds tens of thousands per machine, limited by descriptors and buffer memory. That is why connections are handled by a separate thin layer of gateways, while business logic lives in ordinary application servers. The gateway accepts frames, checks permissions, passes messages on, and delivers replies to the client. This lets you scale gateways by the number of connections and applications by the number of messages, independently of each other.\n\nLong-lived connections have their own load balancing quirks. What gets distributed is not a stream of requests but a number of connections, and once established, a connection stays on its server for hours, so new servers fill up slowly. Rolling out a new version takes care: you put a gateway into drain mode and ask clients to reconnect in batches. Otherwise, if a gateway stops suddenly, all its clients rush to the remaining gateways at once. The client should reconnect with a growing pause and random jitter, and gateways should limit the rate at which they accept new connections.\n\nUser A sent a message to user B. They are connected to different gateways. How do we deliver it? The gateway needs a registry of who is on which gateway, kept in a fast shared store. Or you use a publish-subscribe bus: each gateway subscribes to the channels of its users, and the message is published to the recipient's channel. The gateway that receives it delivers it over the open connection. If the recipient is offline, the message is saved and a notification is sent to the device through a push notification platform.\n\nThe network is unreliable, so messages can be lost and can arrive twice. Every message gets an identifier and a sequence number within the chat. The client acknowledges receipt, and the server resends anything unacknowledged. Duplicates are dropped by identifier. Order is determined by the number, not by arrival time. On reconnecting, the client reports the last number it saw, and the server sends what was missed, so the history is restored without losses. This is the same at-least-once delivery plus idempotence principle, applied to chat.\n\nThere are a lot of messages, they are written constantly, and mostly the fresh ones are read. So the best fit is storage that scales for writes and is sharded by chat identifier: all messages of a chat lie together and are read in a single query. Writes are offloaded to a queue: the gateway hands over the message, workers save it at their own pace, and delivery runs in parallel. There are also hot chats: a big group or a channel with a million readers. They get a separate scheme, because a single shard cannot withstand the whole load.\n\nIn a private chat a message has one recipient, in a group a few dozen, in a channel millions. Multiplying a message across all participants is called fan-out. For small groups the message is sent right away to everyone connected. For large channels that is too expensive: the message is stored once, and participants either fetch it when they open the channel or get a short notification that something new has arrived. For rare readers, a push notification is enough. The choice between immediate delivery and lazy reading determines both the load and the feeling of speed.\n\nThe green dot next to a name seems trivial, but with millions of users it is a huge stream of updates. The approach is this: the client or the gateway periodically sends a heartbeat, and a fast cache holds a record with a short time to live. As long as the heartbeat keeps coming, the record is refreshed; when it stops, the record expires and the user counts as gone. Accuracy down to the second is not needed, so the status is not written to the main database and not pushed to every friend on each change; it is requested when it is actually displayed.\n\nA gateway failure cuts all its connections, say fifteen thousand, and the clients immediately try to connect again. Without protection they create a connection storm that brings down the other gateways too. The protection is the same as elsewhere: a growing pause and random jitter on the client, a cap on new connections per second on the gateway, and spare capacity to lose several gateways. Place gateways in several availability zones so that losing one zone does not cut everyone at once. After reconnecting, the client fetches the missing messages by number.\n\nA long-lived connection is a convenient target for abuse. Authentication is checked at the handshake, and permissions on every message, because the user's role may have changed. Message size and sending rate per connection are limited. A slow client must not be allowed to build up an endless outgoing queue: when the limit is exceeded, the connection is closed, otherwise the gateway's memory runs out. Encryption is mandatory, just as for ordinary HTTP. That way the real-time channel stays efficient and does not become a weak spot.\n\nLet's sum up. For real time, you choose the simplest suitable method: polling, server-sent events, or a WebSocket. Open connections are the main resource, so separate gateways handle them, scaled by the number of connections. Messages are routed through a registry or a bus, get identifiers and numbers, are acknowledged, and are saved through a queue. Presence is kept in a cache with a short time to live. And reconnections are always done with a pause and jitter. In the exercises you will pick the number of gateways and work through the message flow.
