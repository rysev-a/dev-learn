Chapter 5. Sharding. Replicas save you on reads, but every write still goes to a single leader, and all the data still has to fit on one machine. When a service hits a wall on writes or on volume, there is only one way out: cut the data into pieces and spread them across different machines. Each such piece is called a shard. Sharding is the most powerful technique for working with data, and also the most expensive in complexity. It solves one problem, but it creates several new ones, and you need to understand them before you press the button.\n\nDon't confuse shards with replicas. A replica is a full copy of the data: it helps you read and survive a failure, but it shrinks neither the volume nor the write load. A shard is a separate part of the data: each one stores only a share of the records, and writes go to different machines at the same time. Sharding scales writes, volume, and reads too. In a mature setup these techniques are combined: the data is split into shards, and each shard has its own leader and several replicas.\n\nThe main decision is the shard key, which determines which shard a record lives on. A good key has three properties. It spreads data and queries evenly, so that no single shard gets overloaded. It keeps together what is read together, for example all the orders of one user, so that a query does not have to visit every shard. And it does not change, because a record whose key changed would have to be moved to another machine. There is no universal key; you choose one for the main queries of your service.\n\nThere are two main strategies. By range: a shard is responsible for an interval of keys, for example last names from A to K. Interval queries like that are fast and touch only one or two shards, but the load can easily become skewed. By hash: the key goes through a hash function, and the remainder of a division picks the shard. The load is spread evenly, but the ordering is lost, and a range query has to be sent to all the shards. For user identifiers people usually choose a hash; for time series, ranges, with some caveats.\n\nThe most common mistake is a monotonic key. If you shard by time or by an auto-increment number, all new records land in the last range, that is, on a single shard, while the others sit idle. The cure is a hash, or a composite key with a prefix. Another trouble is hot keys: a celebrity has millions of followers, and every request for their data lands on one shard. What helps is a cache for the hottest keys, and splitting such a key into several parts.\n\nSay you have four shards, and the key is determined by the remainder of division by four. You add a fifth, and for most keys the remainder changes: almost all the data has to be moved. Consistent hashing solves this. Keys and nodes are placed on an imaginary ring, and a key belongs to the nearest node clockwise. A new node takes keys only from its neighbor and leaves the rest alone: about one fifth of the data moves. To keep the load even, each node is placed on the ring several times, as virtual nodes.\n\nSooner or later you run short of shards, and you have to add new ones. This has to be done on a running service. The usual order is this. First, the new shard is filled with a copy of the needed data in the background. Then you turn on double writes: changes go both to the old place and to the new one. After checking consistency, you switch the reads over. Finally, the old data is deleted. The operation is long and puts a load on the network and the disks, so it is planned in advance and never postponed until the shards are already at their limit.\n\nAs long as a query contains the shard key, it goes to one shard. But a query without the key has to be sent to all the shards, and the answers stitched together: this is called scatter-gather. It is slower and loads everyone, and its latency is set by the slowest shard. Joining tables across shards is expensive: the data has to travel over the network. Transactions across shards require two-phase commit or weaker schemes. That is why the data schema is designed so that the main queries fit within a single shard.\n\nWhat do you do about searching on a field that is not the shard key? There are two approaches. A local index: each shard indexes only its own data. Writes are cheap, but a search has to visit all the shards. A global index: it is itself partitioned by the field's value and stored separately. A search goes to one shard of the index, but a write updates both the data shard and the index shard, often with a delay. For complex search, a dedicated search engine is used; we will talk about it in later chapters.\n\nSomebody has to know which shard a key lives on. There are three options. A library inside the client computes the shard itself: simple and fast, but the logic has to be updated everywhere. A proxy server between the application and the database hides the shards from the client. A metadata service stores the shard map, and clients request it and cache it. The map is a critical component: its failure stops everything, so it is kept in a fault-tolerant store, and moving data is accompanied by an atomic update of the map.\n\nIn a production setup, shards are complemented with replicas. Each shard has its own leader and its own replicas, and a write goes to the leader of the right shard. If there are no replicas, a shard failure makes a share of the data unavailable: with ten shards, one tenth of the users. This is called a limited blast radius, and there is a benefit in it: an outage affects only part of the system. But for critical data you still keep replicas. The cost grows multiplicatively: the number of shards is multiplied by the number of copies, and you need to account for that in the budget.\n\nSharding complicates everything: queries, transactions, migrations, monitoring. That is why you come to it last. First you add indexes and fix the heavy queries. Then you put in a cache and replicas. Next you separate the data by meaning: move logs and archives into separate stores, and partition tables on a single server. And only when the write load or the volume still doesn't fit on one machine do you divide the data between machines. Modern databases with horizontal scaling take on part of this work for you.\n\nLet's sum up. Replicas scale reads; shards scale writes and volume. The shard key determines everything: it must spread data evenly and keep related data together. A hash gives evenness, a range gives ordering, and monotonic keys and celebrities create hot spots. Consistent hashing limits how much moves as you grow. Queries without a key sweep all the shards, and resharding is done without downtime. Keep every shard with replicas. And shard last. In the trainer you will cut a database apart and fight skew.
