Chapter 13. Classic design problems. Among system design questions there are classics: a link shortener, a view counter, an ID generator, a rate limiter, notifications, a leaderboard. They keep coming back because each one shows how the building blocks you have already learned actually work. The solution always follows one template: clarify the requirements and the numbers, draw a simple diagram, find the bottleneck, strengthen it, and walk through the failures. This chapter is a set of examples on which you will practice that template.\n\nA link shortener takes a long address and returns a short one, and when someone opens the short one, it redirects to the long one. Say a hundred million links are created per month, which is about forty per second, and there are a hundred times more clicks, four thousand per second, with peaks several times higher. Over five years you accumulate six billion records of roughly half a kilobyte each: three terabytes. It all comes down to fast reads by key, so the data fits nicely into a key-value store with a cache in front.\n\nThe key is made of digits and Latin letters, sixty-two characters in all. Seven characters give more than three and a half trillion combinations: enough for centuries. How do you get a unique key? A counter converted to base sixty-two is simple, but a central counter becomes a bottleneck, and the keys are guessable. A hash of the address can produce collisions, which you have to check for. The best option is to hand out ranges of numbers to servers in advance: each server issues keys from its own range without talking to its neighbors.\n\nFor storage, a key-value store or a wide-column database works well: one write, a read by key, no joins. Hot links are mostly read from the cache, since there aren't many popular ones. There are two kinds of redirect. Status three-oh-one is permanent: the browser remembers it and never comes back to us, which offloads the service but makes it impossible to count clicks. Status three-oh-two is temporary: every click passes through the service, but you can keep statistics. The choice depends on your analytics requirements.\n\nThe second classic problem is a service for storing text snippets, like Pastebin. The solution repeats the file-storage design: the metadata, that is the key, the author, and the lifetime, lives in a database, while the content sits in object storage and is served through a content delivery network. Records have a time to live, so you need background cleanup: it finds expired items and deletes them from both the database and the storage. For short notes, you can keep the content right in the database. The key judgment here is choosing between simplicity and scale based on realistic data sizes.\n\nA view counter seems trivial until you get thousands of updates per second to a single row. The row turns into a hot spot: transactions line up in a queue. The solutions are these. Buffering: accumulate increments in memory and flush them in batches every few seconds, which is the write-back idea from the caching chapter. Sharded counters: split one counter into several parts by a random key and sum them up on read. Approximate structures: unique visitors are counted with HyperLogLog, with an error of about one percent and just kilobytes of memory.\n\nA distributed system needs unique identifiers without a central authority. A universally unique identifier needs no coordination, but it takes sixteen bytes and is poorly ordered, which hurts indexes. A database auto-increment is ordered, but it hits the limit of a single machine. The Snowflake approach builds an identifier from three parts: the time, the node number, and a counter within the millisecond. It fits into eight bytes, is roughly ordered by time, and is generated on each server independently. You only need to watch the clocks and make sure node numbers are never handed out twice.\n\nA rate limiter spread over several servers must have a shared counter, otherwise each server will let through its own full quota. The counters are kept in a fast in-memory store, and the check and the update are done atomically, in a single operation, so that parallel requests can't overtake each other. To avoid a network call on every request, servers keep a local reserve of tokens and refill it in portions. If the store is unavailable, you decide in advance: let everyone through or reject everyone. For most services it's safer to let requests through and raise an alert than to stop working.\n\nA notification system sends push messages, emails, and text messages. An event arrives at a service that decides, based on the user's settings, what to send and where. Then the messages go into separate queues per channel, because each channel has its own provider, its own speed, and its own limits. You need templates with substitution, deduplication so that a person doesn't get the same email twice, retries with a pause when a provider fails, and priorities: a confirmation code is more urgent than a marketing campaign. For bulk sends, you add rate limiting so you don't end up in spam.\n\nA scheduler runs tasks at the right time: reminders, delayed orders, periodic reports. The schedule is stored in a database with an index on the run time. Worker processes regularly pick up the tasks whose time has come and put them into an execution queue. To keep two copies of the scheduler from taking the same task, you use a lock or a conditional status update. If a worker crashes, the task is returned after a timeout. The database is sharded by time or by identifier, and execution is idempotent: a failure may lead to a repeated run.\n\nA leaderboard shows the top players and the position of each one. Sorting millions of rows in a database on every request is expensive, so you use a sorted set in a fast store: insertion and fetching the top positions take logarithmic time. For daily and weekly boards you keep separate sets with a limited time to live. For very large volumes, the exact rank isn't needed, and an approximate percentile is enough. Updates go through a queue and reads come from a cache: a player will see their position with a one-second delay, and that is acceptable.\n\nWhat do you do with an unfamiliar problem? Almost always it's assembled from familiar building blocks. Find out the numbers: the load, the volume, the latency and consistency requirements. Draw the simplest diagram. Calculate which component will hit its limit first. Strengthen it with a familiar technique: a cache, a replica, shards, a queue. Repeat. Then walk through the failure of each node and say out loud which trade-offs you accepted. Don't try to guess the one right answer: what gets evaluated is not the diagram but your chain of reasoning, and your ability to change the solution when the requirements change.\n\nLet's sum up. A link shortener is about reading by key: a key-value store, a cache, and keys issued in ranges. Storing blobs splits the data into metadata and objects. Counters fight the hot row with buffering and sharding. Identifiers without a central authority come from schemes like Snowflake. A rate limiter keeps a shared counter with atomic operations. Notifications flow through per-channel queues, a scheduler works from a schedule with locks, and a leaderboard is built on a sorted set. In the exercises you will assemble several of these systems.
