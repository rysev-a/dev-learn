Linux Administration. Chapter 13. nftables and firewalld. The packet filter lives in the kernel and is called Netfilter: a set of hooks along a packet's path through the network stack, where modules can look at the packet and decide its fate. nftables is the modern way to write rules for those hooks, and its command is nft. The older iptables solved the same problem. firewalld on the RHEL family and ufw on Debian and Ubuntu are front ends that write the rules for you.\n\nA packet passes through five hooks. An incoming packet first meets prerouting. If it is addressed to this host, input comes next. If it must be forwarded, it goes through forward and then postrouting. A packet from a local program passes output and postrouting. Chains of one hook run in order of priority: minus 200 for connection tracking, minus 100 for rewriting the destination, zero for ordinary filtering, 100 for rewriting the source. The smaller number runs first.\n\nThe model is: table, chain, rule. A table belongs to a family: ip for IPv4, ip6, inet for both versions at once, and also arp, bridge and netdev. A chain is either a base chain, with a type, a hook, a priority and a policy, or a regular chain that you can only enter with the jump verdict. The default policy is accept, and that is worth remembering. A rule consists of conditions and a verdict. The whole set is shown by nft list ruleset, and you choose the table names yourself.\n\nVerdicts do not behave the way iptables users expect. Drop ends everything at once and cannot be overridden. Reject sends the sender an error message and also discards the packet. Accept finishes only the current base chain, and the packet moves on to the chains of the same hook with a larger priority number. So an allow rule in one table guarantees nothing: a strict chain next door can still throw the packet out. Jump comes back, goto does not, and at the end of a base chain the policy applies.\n\nThe first rule of almost any firewall accepts connections that are already established. Connection tracking marks every packet with a state: new for the first packet, established once the other side has answered, related for associated traffic such as error messages, invalid for packets that make no sense, untracked for packets excluded from tracking. A comma-separated list and the same list in braces mean the same thing. Without it, any conversation already open that has no rule of its own, say SSH on a non-standard port, is cut as soon as a drop policy takes effect.\n\nSets and maps make rules shorter and faster. An anonymous set is written right in the rule: ports 80 and 443 in braces. A named set is declared in the table with a type, such as an IPv4 address, plus the interval flag for ranges and networks, and the rule refers to it with an at sign. Elements can be added on the fly. A map links a key to a value, say a port to a translation address, and a verdict map links a key to a verdict. The key type must match the tested field.\n\nAddress translation lives in chains of type nat. Dnat and redirect are valid in prerouting and output, at priority minus 100, while snat and masquerade belong in postrouting, at priority 100, and masquerade makes sense only there. A nat rule sees only the first packet of a connection, tracking rewrites the rest, so never filter in nat chains. A translated packet still goes through forward, where the new destination address is already visible. You must allow it there and enable forwarding in the kernel. This is how Docker networking and the libvirt NAT network work.\n\niptables did not disappear, but under one name there are two implementations. iptables-nft accepts the old commands and turns them into nftables rules, while legacy works through the old kernel interface. The version shows which one is installed: the parentheses usually say nf_tables or legacy. Rules of the nft variant are visible in nft list ruleset, and iptables-save prints them in the old format. But the meaning shifts: a table becomes a separate chain on a hook, and an accept in it does not cancel a drop in the next one. Better not to mix legacy and nft.\n\nfirewalld keeps rules in zones. A zone is a trust level: public by default, internal, trusted, drop. An interface or an address range is bound to one zone. For a packet the source is checked first, then the interface, otherwise the default zone is used; in newer versions the order can be changed by a zone priority. A zone allows services, ports and protocols, and exact conditions are given by rich rules. The command firewall-cmd with list-all prints a whole zone. Changes without the permanent flag live until the rules are reloaded. In Ubuntu ufw is off by default.\n\nHow to change rules on a remote server without losing access. First check the file with nft and the c flag, keep a second session and a console, and load the file as a whole: it is applied in one operation. Do not run flush ruleset on a hypervisor, it removes the firewalld tables and the libvirt tables too. If a packet vanishes, look at the counters and the trace. In oVirt the engine configures the firewall itself when a host is added and opens the ports: SSH, 54321, libvirt and image transfer.
