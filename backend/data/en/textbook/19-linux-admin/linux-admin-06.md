#CHAPTER 6 | cgroups v2 by hand: slices, CPUQuota, MemoryMax, systemd-run
Linux Administration. Chapter 6. cgroups v2 by hand. One process can eat all the memory, all the processor or all the disk, and then its neighbours suffer. Per-process priorities and limits do not help when a whole service misbehaves. For that the kernel has control groups, or cgroups. They form a tree of process groups, and for every group the kernel keeps accounts and enforces limits. Every systemd service, every container and every libvirt virtual machine lives in its own group, and an administrator must be able to read it and adjust it.\n\nThe interface comes in two versions. In the first, every controller had its own tree, and combining them was painful. In the second there is a single tree, mounted at /sys/fs/cgroup. Checking is easy: stat with the flags f, c and percent T prints cgroup2fs. Modern distributions, for example RHEL 9, Debian 11 and Ubuntu 22.04, run on version 2 by default. A process's group is shown by the file /proc/PID/cgroup: in pure version 2 it is a single line with a zero and a path.\n\nA group is an ordinary directory. Create a directory with mkdir and the group appears; remove the empty directory and it is gone. Inside lie the control files. The file cgroup.controllers lists the controllers available to this group. To enable them for the children, you write a plus and a name into cgroup.subtree_control. To move a process, you write its number into cgroup.procs, one process per write. And cgroup.events, with its populated line, tells you whether the group or its descendants contain live processes.\n\nTwo rules trip everybody up. The first: a controller can be enabled for the children only if it is enabled in the parent, so the list is built from the top down. The second, the no-internal-process rule: a group that is not the root distributes resources to its descendants only when it has no processes of its own. The root group is exempt from this rule. That is why services sit in leaf groups and not in intermediate ones. If a controller will not enable, first check whether the group holds processes of its own.\n\nThe processor is shared in two ways. cpu.weight sets a weight from one to ten thousand, by default one hundred. It acts only under shortage: while the processor is idle, a group takes what it wants, and in a dispute neighbours split it in proportion to their weights. cpu.max sets a hard ceiling with two numbers, quota and period, in microseconds. The default is max and one hundred thousand, meaning no limit. Two hundred thousand over one hundred thousand means two processors. Once the quota is spent, the group is held back until the period ends, and a counter in cpu.stat grows.\n\nFour main files drive memory. memory.current shows how much the group occupies now. memory.high is a soft ceiling: above it the processes are throttled and the group is made to give memory back, but the OOM killer does not come. memory.max is a hard one: if memory cannot be freed, the OOM killer runs inside the group. memory.low and memory.min work the other way, as protection: the kernel tries not to take memory from a group below that border, low as best effort, min as a hard guarantee. The tallies are kept in the file memory.events.\n\nThe disk gets a weight and a ceiling. io.weight resembles the processor weight: from one to ten thousand, by default one hundred. A weight divides throughput among neighbours, but according to the kernel documentation it works only when the device uses cost-based control or the BFQ scheduler. io.max is a hard ceiling for a disk named by its major and minor numbers: bytes per second for reads and writes, and operations per second. And pids.max limits the number of tasks, that is processes and threads: it is a defence against a fork bomb.\n\nIn practice cgroups are rarely edited by hand: systemd manages them. At the top is the root slice; under it are the system slice for services, the user slice for sessions and the machine slice for virtual machines and containers. Every service gets its own group inside a slice, by default the system one. The tree is printed by systemd-cgls, and systemd-cgtop shows the load of the groups in real time, like an ordinary top. Libvirt puts each guest machine into a scope group inside the machine slice, which will matter in the chapters on KVM.\n\nsystemd turns unit properties into file writes. CPUQuota of fifty percent becomes fifty thousand and one hundred thousand in cpu.max: it is a share of one processor, and more than one hundred percent is allowed. CPUWeight, MemoryHigh, MemoryMax, IOWeight and TasksMax land in the files of the same names. You can change them on the fly with systemctl set-property: by default the change is stored, and with the runtime flag it lasts until reboot. For a one-off launch there is systemd-run with the scope flag and the p flag.\n\nThe last rule: the tightest limit on the path from the group to the root wins. If a slice has MemoryMax of two gigabytes and a service inside it has ten, the service hits two, and together with all its neighbours in that slice. systemd shows the result in the property EffectiveMemoryMax. When a service suddenly died, open memory.events: growth of the max and oom counters points to the limit of the group. The oom_kill counter also counts system-wide kills, so compare it with the kernel log. A ceiling on the machine slice likewise caps all guest machines at once.
