Linux Administration. Chapter 26. System calls: strace, open/read/write, errno. A program never touches the disk or the network itself: it asks the kernel, and the border between them is called a system call. The calls are described in section two of the manual, the wrappers of the C library in section three. On failure a wrapper returns minus one and stores the reason in errno, although the kernel itself hands back a negative code. The raw call is reachable through the syscall function. Chapter 28 will use this interface to talk to the KVM device directly.\n\nThe strace utility shows the system calls of a live program line by line: the name, the arguments and the result. It works through ptrace, so it slows the process down; be careful on production. Put strace before a command, or attach to a running process with the p flag. Read a line: the call name, the arguments in parentheses, the result after the equals sign. An error is minus one, a name such as ENOENT and a text in parentheses. Opening a missing file is the most common find. A zero from read means end of file.\n\nA few flags make strace a working tool. The f flag follows children and threads. The e flag with a trace condition keeps only what you need, such as calls that take file names. The c flag prints a table instead of a log: calls and failures per name. Capital T adds each call's duration, tt a timestamp, y labels descriptors with paths, and o writes to a file. Attaching to someone else's process is normally allowed to its owner or root; some distributions restrict it further with the ptrace scope setting.\n\nEverything a program exchanges with the world it holds as a descriptor, a small integer. Zero, one and two are input, output and errors. An opening call always returns the lowest free number, and redirection is built on that: dup2 closes the target number and puts a copy of another descriptor there. The copies share one file offset. The O_CLOEXEC flag closes the descriptor when another program is executed, so it does not leak into the child. Who holds what is visible in slash proc, the process number, slash fd: links named by the numbers.\n\nThe open call takes a path, flags and, when creating, a mode. The access mode is read only, write only or both. O_CREAT creates the file, and the umask of the process trims the mode you pass. O_CREAT with O_EXCL creates the file only if it is not there yet, otherwise the error is EEXIST: locks and safe temporary files rest on that. O_TRUNC empties an existing file. O_APPEND moves the offset to the end before every write, in one indivisible step, which suits logs. Network file systems add caveats.\n\nRead returns the number of bytes it got, and that may be fewer than requested: pipes, terminals and sockets do this, and a regular file near its end. Zero means end of file, not an error. Write may also store fewer bytes than asked, for example after a signal or when space runs out. So correct code reads and writes in a loop, moving the pointer past what is done. Calling write once and assuming everything is written is a classic cause of truncated files and lost messages.\n\nIf a signal interrupts a call before a single byte has passed, the call fails with EINTR, and you simply repeat it. A handler installed with SA_RESTART restarts some calls by itself, but not all: poll and sleep calls are always interrupted. If the descriptor is non-blocking and no data is there yet, read fails with EAGAIN, which on Linux equals EWOULDBLOCK. That is not a failure but a request to come back later, usually through poll or epoll. A read loop separates the outcomes: data, the end, a retry and a real error.\n\nThe file offset lives with the open file, and lseek moves it. The pread and pwrite calls take the offset as an argument and leave the shared one alone, so they are safe for several threads on one descriptor. Closing can fail too: on network file systems a deferred write reports a lack of space or an I/O error exactly at close. On Linux the descriptor is closed anyway, so never repeat close. When reliability matters, call fsync before closing and check its result.\n\nThe errno variable belongs to its own thread, and it means something only right after a failure. A successful call may change it, and the library never resets it to zero. So save the value before any cleanup, or close will overwrite the cause of the error. The perror function prints a prefix and the description, strerror returns a string, and threaded code uses strerror_r. The text may depend on the locale, while a name such as ENOENT does not, so logs should carry both the number and the name.\n\nNot every call really reaches the kernel: the time, for example, is read from the vDSO page that the kernel maps into the process, and strace does not see such calls. Library calls, as opposed to kernel calls, are shown by ltrace. Reading strace pays off on a virtualization host: run it on a QEMU process and the log shows a loop of ioctl calls with the KVM_RUN request, and opening a disk shows the image path. The next chapter builds a pipeline from fork, exec, mmap and ioctl, and then we go to the KVM device itself.
