Linux Administration. Chapter 14. Persistent network configuration. The ip addr add command changes only the kernel's state in memory: after a reboot, or when an interface is recreated, the addresses and routes are gone. To make a setting survive, a service must read files at boot and configure the kernel. Linux has several such services. The Red Hat family, meaning Fedora, Rocky and Alma, runs NetworkManager. Ubuntu Server uses netplan, which writes configuration for systemd-networkd, and on a desktop usually for NetworkManager. A classic Debian install uses ifupdown. The main rule: every interface has exactly one owner.\n\nNetworkManager distinguishes a profile from a device. A profile, called a connection, holds settings: a name, a UUID, a type, a binding to an interface, addresses. The device is the network card itself. The command nmcli connection show prints profiles: name, UUID, type, and the device on which the profile is currently active; an inactive profile has an empty device. The command nmcli device status prints devices and their state: connected, disconnected, unmanaged. One card can have several profiles, for example a home one and an office one, but only one of them is active at a time.\n\nChanges are made with nmcli connection modify. It writes the profile to disk but usually does not touch a running interface: to apply it, bring the profile up with connection up. A plus before a property name appends to a list instead of replacing it. If you edited a file by hand, run connection reload. For scripts there is the -t mode: fields are separated by colons, and a colon or backslash inside a value is escaped with a backslash. For risky remote changes there is device checkpoint, which rolls changes back unless you confirm them.\n\nProfiles are files in keyfile format in /etc/NetworkManager/system-connections, usually with the extension .nmconnection. It is an ini format with the sections connection, ethernet and ipv4. An address is the key address1: address, slash, prefix length, and a gateway after a comma. A route is route1: network, gateway, metric. DNS servers are separated by semicolons. The manager ignores a file accessible to anyone but root, so use mode 0600. In RHEL 9 new profiles are keyfiles by default, the old ifcfg files are deprecated, and connection migrate converts them.\n\nNetplan is not a daemon but a generator. You describe the network in YAML files in /etc/netplan: version 2, then the sections ethernets, bonds, bridges and vlans, each device with its own ID. The renderer property picks the executor: systemd-networkd by default, or NetworkManager. The command netplan generate turns the YAML into the executor's files, and netplan apply applies them. For a card you set DHCP or addresses, routes with to, via and metric, and name servers. A match rule selects cards by name, MAC address or driver. The deprecated gateway4 is replaced by a route.\n\nNetplan reads three directories: lib, etc and run. A file with the same name in run shadows the one in etc, which shadows the one in lib. Files with different names are taken in order of their names, whatever the directory: later ones add to or override earlier ones. Numbers and strings are overwritten, lists are concatenated, so addresses from two files add up, and mappings merge element by element. The order is by string: ten comes before nine. Keep your changes in a file numbered higher than cloud-init's. Newer versions warn if a file is accessible to anyone but root.\n\nWhen you change the network over SSH, it is easy to saw off the branch you sit on. That is what netplan try is for. It applies the configuration and waits; if you have not confirmed within 120 seconds, the default, it rolls back. The timeout option changes the time. If the new setup cut your session, you cannot confirm, and the rollback restores everything. NetworkManager has a similar device checkpoint, currently 15 seconds by default. Keep a second session open. And remember: netplan apply does not delete virtual devices such as bridges you removed from the YAML.\n\nsystemd-networkd is configured by files in /etc/systemd/network. A .netdev file creates a virtual device: a bridge, a bond or a VLAN. A .network file configures an interface: the Match section holds conditions on name, MAC address, type and driver, and below it addresses, gateways, DNS and bridge or bond membership. Of all matching files only the first in alphabetical order is applied. Same-named files in /etc override /run and /usr/lib, and an empty file or a link to /dev/null masks one. A .link file is read by udev when a device appears and sets its name and parameters.\n\nnetworkctl shows the state. The list command prints the index, name, type, operational and setup columns. Operational is the state of the link: routable means there is carrier and a routable address, degraded means only a local address, no-carrier means no carrier. Setup is systemd-networkd's relation to the interface: configured, configuring, failed or unmanaged. Unmanaged means the daemon does not handle the interface. The reload command rereads the .netdev and .network files and reconfigures the matching interfaces, but existing virtual devices may keep some old parameters, for example a VLAN ID. Reconfigure does not reread the files.\n\nThe most common trouble is two owners for one card. NetworkManager brings up a profile while systemd-networkd or ifupdown configures the same card: addresses duplicate, routes flap, and DNS vanishes after a reboot. Find out who owns what: nmcli device status and networkctl list together should name each card exactly once. Switch off the extra owner: in netplan pick one renderer, in NetworkManager mark the card unmanaged. A bridge for virtual machines, such as ovirtmgmt, is also a profile or file of its owner. oVirt usually configures the host network itself, so do not edit it by hand.
