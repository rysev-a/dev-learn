Linux Administration. Chapter 20. Backups: rsync, LVM snapshots, restic and borg, restore tests. A backup is a copy you can restore from after the original is gone. RAID is not one: it only survives a dead disk. A snapshot on the same volume is not one: it dies with the volume. A replica is not one: it faithfully copies your accidental delete. The plan rests on two numbers. The first, RPO, is how much recent data you can afford to lose. The second, RTO, is how long the restore may take.\n\nThe classic rule is three-two-one: three copies of the data, on two different kinds of media, one of them off site. The copies themselves come in three kinds. A full copy takes everything. An incremental copy takes what changed since the previous copy of any kind, so a restore needs the last full copy plus every increment after it. A differential copy takes what changed since the last full one, so a restore needs just two pieces. A short chain restores faster and breaks less often, while a long one is cheaper to make.\n\nThe workhorse of file backups is rsync. Archive mode keeps permissions, owners, times, and symbolic links, while hard links, ACLs, and extended attributes need their own switches. The classic trap is the trailing slash: a source with a slash copies the directory's contents, while a source without it copies the directory itself under its own name. The delete switch makes the destination an exact mirror, so run a dry run first. And the itemize switch prints one line per change, which shows what really happened.\n\nFilter rules decide what rsync touches, and the first matching rule wins. To copy only one kind of file, include the directories, include the files you want, and exclude everything else at the very end. Excluded files are also protected from deletion on the destination. Read the exit code, not just the log. Zero is success. Twenty-four means some files vanished while they were being read, which is normal on a live system. Twenty-three is a partial transfer caused by real errors, and your monitoring must treat it as a failure.\n\nIt is easy to turn rsync into a snapshot machine. Copy into a new dated directory and point the link-dest option at the previous one. Unchanged files become hard links to the old copies and take no space, and only changed files are copied. Every directory looks like a full backup, and a plain copy brings a file back. Deleting an old snapshot frees only what nobody else links to. There is a weak spot: a damaged file is shared by every snapshot that links to it. So you also need an independent copy and a check.\n\nFiles change while you copy them, and a database may be half written. A snapshot freezes a consistent view. In chapter 16 we saw how LVM makes one. For a backup the order is: prepare the application, create the snapshot, mount it read-only, copy, unmount, remove. The snapshot needs room for every block the origin changes during the copy, so size it as the write rate times the copy time plus a margin. If it fills up, it becomes invalid and the backup must be repeated. XFS usually also needs a special mount option because of the duplicate UUID.\n\nRestic and borg are backup programs with a repository. They cut data into chunks, store each unique chunk once, usually compress and encrypt it, and record every run as a snapshot, which borg calls an archive. That gives deduplication: a nightly copy of a hundred nearly identical virtual machine images costs little. You create the repository once with init, back up with backup, and list the snapshots. The password is a key here: lose it and the repository cannot be read, so keep it somewhere else. Borg has a key export for exactly this reason.\n\nKeeping everything forever is not a plan, so you set a retention policy. In restic the forget command with the keep-daily, keep-weekly, keep-monthly, and keep-yearly options keeps the newest snapshot in each of the last periods that contain any snapshot at all, and a snapshot that fits any rule stays. A dry run shows the table in advance. Forget only unlinks snapshots, while prune frees the space. Borg counts differently: a rule does not count archives already kept by a more frequent one, and the compact command gives the space back.\n\nWhole files are not yet a whole application. A database copied in the middle of a write may refuse to start. Take a dump with its own tool, or snapshot after the data is flushed, and make sure a failed dump fails the whole backup instead of being stored as an empty file: restic's read-from-command option works exactly that way. For virtual machines the recipe is the same: snapshot the disk, copy it, merge it back. In oVirt the engine has a backup interface for disk snapshots and incremental backups, so a backup program reads them without stopping the machine.\n\nA backup that has never been restored from is only a hope. Schedule a test: restore into an empty directory, compare the checksums with a manifest taken at backup time, start the application, and write down how long it took. That is how you learn your real RTO. Run the backups from a systemd timer with the persistent option, as in chapter 3, so a missed night runs after boot. The script returns a non-zero code on failure, and you need an alert on silence as well: two days without a backup message is an incident.
