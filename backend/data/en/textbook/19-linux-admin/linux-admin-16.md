#CHAPTER 16 | LVM: physical volumes, groups, snapshots, thin pools
Linux Administration. Chapter 16. LVM: physical volumes, groups, snapshots, thin pools. A partition is welded to its place on the disk, so LVM adds a layer. A physical volume, PV, is a disk or partition handed to LVM. A volume group, VG, pools several PVs into one reserve of space. A logical volume, LV, is cut from that reserve and looks like a plain block device. You can resize it live and move its data between disks. An oVirt block storage domain works the same way: one volume group on a shared disk, one logical volume per VM disk.\n\nThe space in a group is divided into equal pieces called extents. The default physical extent is 4 MiB, set by physical_extent_size in lvm.conf. A logical volume is built from logical extents, each mapped to one physical extent, so its size is always a multiple of the extent. A requested size is rounded up; a percentage is rounded down when you create a volume and up when you extend one. The first MiB of a PV holds the label and metadata, so slightly fewer extents are usable. oVirt uses a 128 MiB extent.\n\nCreation takes three commands: pvcreate, vgcreate, and lvcreate. The size can be given in two ways. Capital L takes a size with a unit, such as 10G. Input units are always binary, the case does not matter, and with no unit the number means mebibytes. Lowercase l takes a number of extents or a percentage of the group, of the free space, or of the listed disks, and 100%FREE takes everything that is left. The -n option names the volume. Then you make a filesystem on it and mount /dev/vgname/lvname.\n\nThree commands report the state: pvs, vgs, and lvs. The Attr column of an LV has ten characters. The first is the type: V thin volume, t thin pool, s snapshot, o origin of a snapshot. The fifth is the state: a active, capital I an invalid snapshot. The -a option adds hidden internal volumes in square brackets, and -o +devices shows which disks hold the extents. Under /dev/mapper the group and volume names are joined by a hyphen, and hyphens inside names are doubled. Scripts are safer with the /dev/vgname/lvname path.\n\nGrowing is easy. If the group has free space, lvextend with a plus adds it to the volume, and -r grows the filesystem too, through fsadm. If there is no room, add a disk with vgextend. Ext4 and XFS can both grow while mounted. XFS cannot be shrunk at all, and ext4 only while unmounted. Shrinking is dangerous: lvreduce cuts extents from the end, and whatever lived there is gone. The order is filesystem first, volume second, and -r performs both steps. Take a copy of the data beforehand.\n\nHardware changes without downtime. pvmove carries the allocated extents of a chosen PV to free space on the other PVs while the volumes stay mounted and in use. It creates a temporary internal volume, and an interrupted move is resumed by running the same command with no arguments. Once the disk is empty, vgreduce removes it from the group and pvremove wipes the label. First check that the remaining disks have enough free extents. You control placement at creation: -i stripes data across several disks, and type raid1 with -m keeps copies, normally on different disks.\n\nA classic snapshot is a frozen view of a volume. You give it a size at creation, and about a fifth of the origin is often enough. The first write to a block of the origin copies the old data into the snapshot area first: that is copy-on-write. When the area fills up, the snapshot becomes useless: capital I appears in Attr and reads return errors. So watch the Data column and enable automatic extension with snapshot_autoextend_threshold in lvm.conf. lvconvert --mergesnapshot rolls the origin back to the snapshot. A backup snapshot should live briefly.\n\nA thin pool shares space. It consists of a data volume and a metadata volume, shown as _tdata and _tmeta by lvs -a. Thin volumes get a virtual size and take pool data only as they are written, so their total can exceed the pool: that is overprovisioning. Watch the Data and Meta columns. When data runs out, writes wait for an extension, by default up to 60 seconds, then fail. Full metadata is worse: corruption is possible. thin_pool_autoextend_threshold in lvm.conf enables automatic extension. A thin snapshot needs no size and does not go invalid like a classic one.\n\nLVM keeps its metadata on the PVs themselves and saves a text copy in /etc/lvm/backup on every change, with older versions in the archive. vgcfgrestore uses these, but restores only the description, not the data. A group is activated with vgchange -ay, and at boot service units usually do it. Filters in lvm.conf, or the devices file system.devices, decide which devices LVM looks at. On a virtualization host this matters: oVirt installs a filter with vdsm-tool and disables autoactivation for its own groups, otherwise the host would poke into volumes that are not its own.\n\nLet us sum up. For calculations think in extents: a size is a multiple of the extent, and a percentage is rounded by the command's rules. For diagnosis read Attr, the Data and Meta columns, and the -a and devices options. For scripts, lvs offers --reportformat json: each report row becomes an object, and -o picks the fields, so you never cut the table by spaces. We return to this in the Python chapters. Before a risky operation, save the metadata and the data. Next in the storage section come software RAID and disk diagnostics.
