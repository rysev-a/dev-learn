#CHAPTER 7 | Namespaces by hand: unshare, nsenter, ip netns
Linux Administration. Chapter 7. Namespaces by hand: unshare, nsenter, ip netns. A container does not exist as a kernel object. It is ordinary processes to which the kernel shows a trimmed-down picture of the world: their own process numbers, network interfaces, hostname and mount points. Each such slice is called a namespace. Together with the control groups of the previous chapter, namespaces are everything a container runtime is built from. Today we assemble isolation by hand and see that there is no magic in it.\n\nThere are eight kinds of namespace. Mount hides foreign mount points. PID gives its own numbering, where the first process becomes number one. Net isolates interfaces, routing tables, firewall rules and ports. UTS covers the hostname. IPC hides System V objects and POSIX message queues. User separates user and group numbers. Cgroup shows the control group tree from a different root. Time shifts the monotonic and boot clocks, but not the ordinary calendar clock.\n\nHow do you tell which namespace a process lives in? Look into the directory proc, PID, ns. It holds one link per type, and the link text is the type and a number in square brackets. That is an inode number. If two processes show the same number, they share the namespace, so compare the numbers, not the names. While a descriptor of such a link is open, or a file is mounted on top of it, the namespace stays alive even with no processes inside. That is how ip netns keeps named networks.\n\nWalking process directories is tedious, so there is lsns. It scans every process and prints a table: the namespace number, the type, the number of processes, the lowest process number in it, its owner and the command. The default set of columns may change between versions, so scripts name them explicitly. The t flag selects a type, the p flag shows the namespaces of one process. An extra net line that a clean host does not have usually means a container or an isolated service. Run it as root: otherwise other users' links cannot be read.\n\nThe unshare command runs a program in new namespaces: one flag per type. Network, hostname and mounts are one flag each. Process numbers have a subtlety: the new namespace goes to the children, not to the caller, so you need the fork flag, and then the program becomes process number one. For ps to see only inner processes you need a fresh proc: the mount-proc flag, which also implies a separate mount namespace. Without root, add map-root-user: it creates a user namespace and shows you as root inside.\n\nThe reverse action is to enter an existing one. nsenter takes a process number through the t flag and flags for the types: n for network, m for mount, p for PID, u for the hostname. The a flag takes all namespaces of the target at once. With no command it starts your shell. It is the administrator's main tool: to see a container's network you run nsenter, t, the number, n, and then the ordinary ip and ss work inside that network while staying programs of the host. No tools need to be installed into the image.\n\nFor networks there is a convenient wrapper: ip netns. The add command creates a named namespace and mounts it over a file in the directory var, run, netns, which holds it with no processes. The list command prints the names and, when the namespace has an identifier, that too. The exec command runs a program inside. A new namespace has only a loopback interface, normally down: bring it up yourself. Then one end of a veth pair is moved in: a container network, which chapter twelve builds.\n\nA user namespace changes what the numbers mean. The uid map file has three numbers per line: the first number inside, the number it corresponds to outside, and the length of the range. The line zero, one thousand, one means: inside zero is outside one thousand. IDs outside the map appear as 65534 by default. The map is written once, with at most 340 lines, and ranges must not overlap. An ordinary user may describe only their own number, in one line, and for groups must first deny setgroups. A privileged process may describe any ranges.\n\nFrom here comes the idea of rootless containers. An ordinary user creates a user namespace, gets a full set of privileges inside it, and creates the other namespaces there. For several numbers inside, you need ranges from the subuid and subgid files: the administrator has allotted the user, say, 65536 numbers, and the map is written by the newuidmap and newgidmap utilities. Root inside such a container is only your own user outside. The price is that some abilities are unavailable: loading modules and creating device nodes.\n\nNow let us assemble the picture. Docker run creates new mount, process, network, hostname and interprocess-communication namespaces, puts the process into its own control group, and starts it. Options only choose what to keep shared: pid equals host keeps the host's processes, network host gives the host's network, and network container, colon, a name gives a neighbour's network, which is how sidecars work. The user namespace is shared with the host by default. A virtual machine is isolated differently: it has its own kernel, and the QEMU process usually lives in the host's network and process list.
