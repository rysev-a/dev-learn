Linux Administration. Chapter 30. QEMU: the main loop, AioContext, vCPU threads, virtio-blk. This is the second exercise of Step 4 of the roadmap: trace how QEMU manages asynchronous I/O and how it brings up a virtual disk. The file and function names here were checked against the QEMU 10.2.0 sources, and the key places were rechecked on 11.1. Names drift between releases, so you find them with the methods of the previous chapter. We start with what is visible, the threads of the process, and arrive at a single disk request.\n\nOne virtual machine is one QEMU process. Its main thread runs the main loop: the function qemu_main_loop calls main_loop_wait again and again. It holds the Big QEMU Lock, the BQL, and releases it only while waiting for events. With the KVM accelerator every virtual processor has its own thread named CPU, a number, slash, KVM. There are helper threads too: worker for blocking jobs and call_rcu. The names show in ps with the T flag, but only if the debug-threads parameter is on; libvirt usually turns it on.\n\nA processor thread starts in the function kvm_vcpu_thread_fn. It takes the lock, prepares the processor and enters the loop in kvm_cpu_exec. This is where the KVM_RUN request from chapter 28 lives. Before it the function releases the lock, so the guest runs without getting in anyone's way. Port and address exits are handled in this same thread without the lock; the device code takes the lock itself if it is not built to work without it. A guest halt is handled under the lock. A sleeping processor waits on a condition variable, and a signal wakes it.\n\nThe main loop is wrapped around glib. The function main_loop_wait gathers the descriptors to wait on, releases the lock, calls ppoll through qemu_poll_ns, takes the lock again and hands out the events. The main context, qemu_aio_context, takes part too: qemu_init_main_loop creates it. A context does four things: it watches descriptors, accepts signals from other threads through event notifiers, sets timers and runs deferred calls, the bottom halves. Every iothread has a context of the same kind.\n\nOne pass of the event loop is the function aio_poll. First comes the wait: in 10.2 the context takes io_uring if the build supports it and it is available; otherwise epoll, which switches on when the number of descriptors reaches sixty-four, and plain ppoll before that. After the wait, in order: io_uring completions, deferred calls, ready descriptors, timers. A deferred call scheduled from another such call waits for the next pass. Do not confuse this with the aio parameter of a disk file: that one picks the engine of the disk I/O itself.\n\nThe main loop and the big lock are a bottleneck, so a disk can be given its own thread: the option object iothread with an id. The thread is named IO, a space, the id; its function iothread_run calls aio_poll in a loop on its own context and does not take the lock. So its code must use context functions such as aio_set_fd_handler, not the old main-loop ones. Threads are listed by the QMP command query-iothreads and the monitor's info iothreads. The kernel refuses a name that is too long, so the thread may keep its default name.\n\nQEMU's block layer is written as sequential code on coroutines. A coroutine gets its own stack and can give up control, and when an event arrives the loop enters it again. Such functions are marked coroutine_fn, and their names usually contain co: blk_co_preadv, bdrv_co_preadv. The layers are: the block backend, then a format such as qcow2, then the file protocol driver. It sends the request to a thread from the worker pool, or through native AIO, or through io_uring, as the aio parameter says. In a Linux build coroutines run on ucontext by default.\n\nNow the disk. The function virtio_blk_device_realize checks the parameters, calls virtio_init and creates the queues: each through virtio_add_queue, with the size from the queue-size parameter, 256 by default, and the handler virtio_blk_handle_output. For the PCI variant the default number of queues equals the number of processors. Then a context is chosen for each queue: the main one, or the iothread's if the iothread parameter is set. When the guest driver writes the DRIVER_OK status, the ioeventfd start runs: an eventfd is hung on the notify address of each queue, and its handler goes into the queue's context.\n\nLet us follow a read request. The guest puts a chain of descriptors into the table, the number of its head into the avail ring, bumps the index and writes to the notify address. KVM does not exit to QEMU: the write only signals the eventfd, and the context's handler calls virtio_blk_handle_output. That one pops chains in a loop with virtqueue_pop, parses them and submits the reads to blk_aio_preadv. On completion virtio_blk_rw_complete calls virtqueue_push, which writes an element into the used ring, and virtio_notify; from an iothread the interrupt goes through a notifier and an irqfd.\n\nLet us sum up the book. Chapters 1 to 4 taught you to keep a server without a screen: SSH, packages, systemd, logs. Chapters 5 to 20 covered processes, network and storage by hand. Chapters 21 to 25 built a management layer in Python and libvirt, and chapters 26 to 30 went down to C, /dev/kvm and the QEMU sources. Now the chain oVirt, VDSM, libvirt, QEMU, KVM is no black box: you can see its layers down to a disk request. Next: diagnostics in chapter 31, security and the final incidents in chapter 32.
