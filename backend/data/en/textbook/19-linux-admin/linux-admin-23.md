Linux Administration. Chapter 23. Idempotent automation: dry-run, desired state, the idea of Ansible. An ordinary script describes steps: do this, then that, and a second run repeats everything. Another approach describes the result: the host must have this line in a config, that package, this service running. The program compares the goal with what exists and does only the difference. When a second run changes nothing, the run is called idempotent. Such automation is safe to put on a timer, and a change in its report tells you at once that the host has drifted from the norm.\n\nIdempotence is easy to lose. An echo with a double greater-than appends a line on every run, and the config keeps growing. useradd on an existing name exits with status 9, and mkdir without -p fails if the directory is already there. The cure is one: before changing something, check whether it is needed. A directory has mkdir -p, a line has grep with -q and -x, a user has the id command. When there is no ready flag, write the check in code and shape the result so that a repeat is harmless.\n\nFrom such checks you build small functions that all have one shape: read, compute the new content, write only if it differs, and return a changed flag. The model is Ansible's lineinfile module. When a pattern is given, it looks for matching lines and replaces the last one found; with no match, the line goes at the end or after a given pattern. The absent state removes lines. The write goes through a temporary file and a replace, as in the previous chapter, and the file mode is compared separately. The flag feeds the report and the handlers.\n\nDry-run is the same code without the write: the function computes everything, returns the same changed value and a diff, and skips the write. The tools have familiar flags: apt-get -s, rsync -n, and ansible-playbook with --check and --diff. A diff shows old lines with a minus and new lines with a plus. But a forecast is not a guarantee: a module without check mode support reports nothing and does nothing, and steps that depend on earlier results may come out differently. The command module in check mode works only when creates or removes is given.\n\nFor a whole host the scheme plan, then apply, is convenient. The desired state lies in a dictionary: packages, users, files with content and mode, services. A planner compares it with the actual state and produces an ordered list of actions: packages and users first, then files, services last, because there is nowhere to write a config without the package. The list can be printed and reviewed. After applying, a new plan must be empty. If you save state snapshots to a file, comparing two of them gives a drift report: what was added, vanished, or changed.\n\nThe nginx config has changed, so the service must reread it. But restarting it on every script run is not acceptable: connections would be dropped. So the action is hung on a handler. A task that reported changed notifies the handler by name. In Ansible, handlers run at the end of each section of a play, each only once however many tasks called it, and in the order in which they are defined. If another task later fails on that host, handlers by default do not run; force_handlers changes that. The meta flush_handlers step runs the accumulated ones immediately.\n\nThat is Ansible's idea: you describe the desired state, and it brings the hosts to it. By default it works over SSH, with no agent on the host. The inventory names hosts and groups and holds variables. Precedence: the all group is weaker than a parent group, a parent weaker than a child, and a host's own variables beat everything; same-level groups merge alphabetically, the last wins. A playbook is a list of plays, each with hosts, tasks, and handlers. A task calls a module, and the module reports whether it changed anything and whether it failed.\n\nA run is read line by line. A task prints ok if the state is already right, and changed if the module changed something; skipping if it was skipped, and fatal if it failed. At the end comes the PLAY RECAP summary: one line per host with the counters ok, changed, unreachable, failed, skipped, rescued, and ignored. Checking idempotence is simple: run the playbook twice, and the second time changed must be zero. Command modules usually report changed every time, so they get a changed_when or a marker file with creates. A nonzero unreachable or failed means alarm.\n\nNow reliability. Transient failures, such as a network blip or a busy repository, are cured by retries. Ansible's until, retries, and delay give a fixed pause, by default three attempts five seconds apart. In Python you build an exponential pause with a cap and a total time limit. You also need a flock -n lock against colliding runs, and a timestamped log. The systemd timer from chapter 3 with Persistent catches up a missed run. And the exit code: zero when all is well, the rest by your own table; SuccessExitStatus can make code 2 a success for systemd.\n\nLet us sum up. Check, then change. Every function returns changed. The order is plan, apply, and an empty second plan. Handlers restart services only after a change. Retries go with a growing pause, a lock keeps a double run out, and the exit code is clear to the timer. In the oVirt world the modules of the ovirt.ovirt collection, for example ovirt_host, are written in the same spirit, and the hosted engine setup is packaged as Ansible roles.
