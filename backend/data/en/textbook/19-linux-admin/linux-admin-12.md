#CHAPTER 12 | A container network by hand: netns, veth and NAT
Linux Administration. Chapter 12. A container network by hand: netns, veth and NAT. In chapter 7 we created a namespace, and in chapter 8 we saw what Docker builds. Now we assemble the same thing ourselves. There are four stages: a namespace with a cable, a bridge on the host, an address and a route inside, then forwarding and address translation on the host. Each stage is checked with a ping, and where the ping breaks shows which step is missing. Build it once, and Docker's network and the network of virtual machines read like familiar text.\n\nStart with the namespace and the cable. The command ip netns add creates the namespace red. The command ip link add with type veth and the word peer creates a pair: whatever enters one end instantly arrives at the other, and if either end is down, the pair is down. One end stays on the host; the other moves into the namespace with ip link set, netns. After the move the interface is normally down with no address, so the rest is configured inside. There we rename it eth0 and bring up the loopback, which as a rule is down.\n\nThe host end of the cable must be plugged into something: a bridge, covered in chapter 10. We create a bridge br0, give it the address 10.200.0.1 slash 24, and bring it up. Then we attach the host end of the cable with the word master and bring it up. The bridge's address is the host's address in this network, and it will become the namespace's gateway. Attach a cable from a second namespace to the same bridge and you have a switch with software ports, as in Docker and in libvirt's default network.\n\nNow the inner part. Inside the namespace we give the renamed interface the address 10.200.0.2 slash 24 and bring it up. The kernel adds the route for the whole network itself, so the gateway at address one and neighbouring namespaces already answer a ping. An address outside the network is still unreachable: ping says Network is unreachable, because there is no default route. We add it with route add default via 10.200.0.1. Commands run either through ip netns exec, or with the short global flag minus n and the namespace name.\n\nA packet for an external address reaches the bridge, but the host will not forward it further. Forwarding is controlled by the sysctl net.ipv4.ip_forward, which defaults to zero. Enable it with sysctl minus w. The setting is kept per network namespace, and what matters is its value where the router sits, on the host. The command holds until reboot; to survive one, the value goes into a file in /etc/sysctl.d. If the host's firewall forbids forwarding by default, as Docker sets it up, the forwarded packets need a separate allowing rule.\n\nThe packet now leaves the host, but with a source address in 10.200.0.0, which the provider does not route, so no reply comes. We need source address translation, masquerade. The rule sits in the nat table, in the postrouting chain: packets from the namespace's subnet that leave other than through the bridge get the address of the interface they leave by. Docker installs the same rule; here it is written by hand, in iptables or nftables syntax. Masquerade suits dynamic addresses; for a static one the documentation recommends SNAT. Replies are rewritten back by the kernel, from its connection table.\n\nThe connection table is read with conntrack -L, from the package conntrack or conntrack-tools. Each line holds two tuples: the original, as the packet went from the client, and the reply, as the answer will come back. If the reply's destination differs from the original source, source translation happened. If the reply's source differs from the original destination, destination translation happened. ASSURED means traffic has been seen in both directions. The flags minus n and minus g filter source and destination translations. This is the best place to check that NAT works.\n\nNow the other direction: reaching a server inside the namespace from outside, that is port publishing. A DNAT rule goes into the prerouting chain of the nat table: packets for host port 8080 get the destination 10.200.0.2, port 80. Connections made from the host itself need the same rule in the output chain; address 127.0.0.1 usually also needs the route_localnet parameter, which is why Docker often serves such connections through a userland proxy. The packet is now forwarded, so the forwarding rules must let it through. The DNAT rule listens on nothing: it is a table entry.\n\nDebugging follows the packet's path. Enter the namespace with ip netns exec and check the address, the route and a ping to the gateway. Then run tcpdump with the minus n flag at several points: inside the namespace, on the bridge, on the outgoing interface. A request seen on the bridge but not on the outgoing interface means forwarding or a filter. Seen there with a private address, masquerade is missing. Left with the host's address but no reply: look outside and at conntrack. A reply seen outside but not on the bridge was lost on the way back.\n\nYou have already seen everything we built. Docker makes the docker0 bridge, a veth pair per container, masquerade, and DNAT for published ports. Each network from docker network create gets its own bridge and a subnet from the pools: by default /16 networks starting at 172.17, and 192.168 cut into /20 at the end of the list. Libvirt's default network is the bridge virbr0 at 192.168.122.1 in NAT mode, with virtual machines' tap devices as ports. Cleaning up is simple: delete the namespace, the bridge and the rules.
