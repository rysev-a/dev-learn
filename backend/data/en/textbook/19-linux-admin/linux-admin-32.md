Linux Administration. Chapter 32. Security and the final exam. Ordinary permissions are decided by the owner of a file: that is discretionary access, and a root process bypasses almost every check. So the kernel has a second layer, mandatory access control, supplied by security modules. There are two main ones: SELinux on the Red Hat family, that is Fedora, Rocky and Alma, and AppArmor, which Debian and Ubuntu usually enable. Both follow the principle of least privilege: a program may do only what it needs. Then come auditing, host hardening and the exam of incidents.\n\nSELinux has three modes. Enforcing blocks and logs. Permissive only logs, which is how you test a policy. Disabled turns it off. The commands getenforce and sestatus show the mode, setenforce flips the running mode until the next reboot, and the permanent choice is the SELINUX line in /etc/selinux/config. Every process and file carries a context of four parts: user, role, type and level. In the targeted policy only the type matters: a web server runs in the type httpd_t and may read files of the type httpd_sys_content_t. The option capital Z of ls and ps shows these labels.\n\nMost SELinux problems are wrong labels. A copied or moved file keeps the label of its old place, and the service refuses it. The cure is not chmod. Record a rule with semanage fcontext, which takes a type and a path pattern, and apply it with restorecon, options R and v. The command chcon changes a label at once but loses it at the next relabel. The second knob is booleans: getsebool lists them, setsebool with the option P sets one permanently. You met one in chapter nineteen: virt_use_nfs, for virtual machines on NFS. Ports have semanage port.\n\nA refusal is written to /var/log/audit/audit.log as a record of type AVC. It holds the word denied, the permission in braces, the process, then scontext, the label of the subject, tcontext, the label of the object, and tclass, its class. The field permissive says whether the refusal was only logged. Search with ausearch, options m AVC and ts recent, and audit2why explains the cause. Fix in this order: a wrong label, a boolean, a port, and only last a custom policy module made with audit2allow. Leaving permissive on is not a cure.\n\nAppArmor works with paths, not labels. A profile in /etc/apparmor.d is tied to a program and lists the files, capabilities and networks it may use. A profile is in enforce mode, which blocks, or in complain mode, which only logs. The command aa-status shows how many profiles are loaded and in which mode; aa-complain and aa-enforce switch one. A refusal appears in the kernel log or the journal as a line with apparmor equals DENIED, then the operation, the profile, the file name and the masks. In complain mode the same line says ALLOWED.\n\nLibvirt adds a layer called sVirt, so one compromised virtual machine cannot read the disk of another. With SELinux, each guest runs in the type svirt_t with its own pair of categories, such as s0:c123,c456, and libvirt gives its disk images the same pair. With AppArmor, each guest gets its own profile named libvirt and the UUID, kept in /etc/apparmor.d/libvirt. This explains old puzzles: an image copied by hand wears the wrong label, and NFS cannot store labels, so it needs virt_use_nfs or a mount option. The QEMU process of chapter thirty runs under exactly this protection.\n\nAuditing answers who did what; the daemon auditd writes audit.log. Watching a file is set by auditctl: option w with the path, option p with the letters r, w, x or a, and option k with a key. A system call rule is option a, always comma exit, then options F arch and S. Permanent rules live in /etc/audit/rules.d and augenrules compiles them. One event is several lines with the same number after the colon: SYSCALL, CWD, PATH and PROCTITLE. Search by key with ausearch option k, summarize with aureport; the rule minus e 2 locks the rules until reboot.\n\nHardening is a short checklist. SSH: read the real configuration with sshd option capital T, where keywords are printed in lowercase; forbid root with a password, prefer keys, limit the users. Sudo: grant specific commands, not ALL, and do not skip the password for people. Kernel: dmesg_restrict, kptr_restrict, rp_filter and the protection of links and files. List programs with the setuid bit and with file capabilities, and compare them with what you expect. Close the firewall by default, patch on a schedule, and keep secrets out of command lines, because ps shows them to other users.\n\nNow the exam. An incident is solved by a fixed order of questions, not by guessing. First, what changed and when. Then go down the layers: link and addresses, routes, firewall, whether the service listens, then labels and profiles, then resources, memory and disk, and hardware last of all. Take the evidence as text, as the earlier chapters showed: the journal, dmesg, df, ip addr, the audit log. Name one cause, quote what proves it, choose the smallest reversible fix and write down what you saw. Change one thing at a time and check again.\n\nThat is the end of the course. You can log in to a bare server, keep it patched and read its journal. You can limit processes with cgroups, build networks and storage by hand, and script it all in Python. You can follow a system call into the kernel and a disk request through QEMU, find a fault with the methods of chapter thirty one, and lock the host down.
