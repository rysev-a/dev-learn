Linux Administration. Chapter 29. How to read a big project: git grep, ctags, gdb, perf. This is Step 4 of the roadmap: clone QEMU and trace how it runs virtual processors and disks. QEMU is a huge C project, and nobody reads it file by file from the top. You need a method: take something you can observe from outside, such as a system call, a thread name or a log line, and walk from it to the code that produces it. Examples here were checked against QEMU 11.1.0; names change between releases, so verify against your own tree.\n\nStart from an observable. In chapter 28 you saw the ioctl with KVM_RUN in strace. In ps with the T option, or in top with H, QEMU threads have names such as CPU 0 slash KVM. The QMP command query-cpus-fast reports the host thread id of every virtual CPU. A trace event has a name too. All of these are strings, and a string can be searched. Searching the tree for the format string CPU percent d slash KVM leads to one function that builds the name and starts the thread. Read forward from there, not from main.\n\ngit grep searches only tracked files, so it skips the build directory and is fast. The option -n prints line numbers; several -e patterns joined with --and must all appear on one line. The option -p shows the name of the function around a match, and -W shows the whole function. --heading prints each file name once. You can search an old release too, by adding a tag name at the end. Look for the definition first, then for the callers, and keep a note of the chain you follow.\n\nCode has a history that often explains why. git log -S with a string finds commits that changed how many times it occurs; -G takes a regular expression over the changed lines. --follow tracks one file across renames, and -L follows one function. git blame with -w and -C ignores whitespace and notices moved lines. --porcelain gives a stable format for scripts, and a file named in blame.ignoreRevsFile hides mass-reformatting commits; QEMU keeps such a file in its root. Then git show opens the commit and its message.\n\nTo jump between definitions you need an index. ctags builds a file named tags: one line per symbol, with the name, the file, an address and fields, the main one being the kind. In C a function is kind f, a struct s, a typedef t, and the field file: marks a symbol static to its file. QEMU's Makefile has targets ctags, TAGS and cscope. For C, clangd navigates more cleverly; it needs a compilation database, compile_commands.json, which Meson usually writes into the build directory. Indexes misread macros and function pointers, so confirm with git grep.\n\nYou need a map. In QEMU 11.1, accel/kvm holds the KVM accelerator, hw/virtio and hw/block the virtio and block devices, block the image formats and the block layer, util the helpers and the event loop, system the machine and the main loop, target the processor architectures; migration, qapi and docs/devel hold the rest. Names carry meaning: usually qemu_ for general helpers, aio_ for the event loop, blk_ for the block layer, virtio_ for virtio. Macros hide structure: container_of is in include/qemu/compiler.h, the QTAILQ lists in include/qemu/queue.h, and types are declared with TYPE_ names in the object model, QOM.\n\nA running process shows its structure. strace with -f and -p attaches to all threads, so you see which thread makes which calls. ps with -T lists threads with their ids, and top with -H shows them live. QEMU names its threads: CPU, a number and /KVM for a virtual processor; IO and an id for an iothread; worker for the thread pool; call_rcu for deferred freeing. The kernel's vhost thread is named vhost and a number. A thread name holds at most fifteen characters. The main thread is the one whose id equals the process id.\n\ngdb stops the threads of a process while it looks inside, so attach to a production virtual machine with care. gdb -p and a process id attaches; -batch with -ex runs commands and exits. info threads lists threads with ids and names, and thread apply all bt prints every stack. A frame line holds the number, an address, the function with arguments, and file and line if debug information exists; otherwise you see question marks or a library name. Distributions ship symbols separately, and debuginfod can fetch them. gcore, like a core file, saves the state for later.\n\nperf shows where the time goes. perf top is a live view. perf record with -g and -p saves samples with call stacks for one process, and perf report with --stdio prints a table. When stacks are recorded, the table has two columns: Self, the time in the function itself, and Children, the time in it and everything it called. perf script prints raw samples, which tools fold into one line per stack for a flame graph. perf trace is a strace-like tool. Find the heaviest stack, and then read exactly that code.\n\nQEMU has its own tracing. Every directory declares events in a file named trace-events, for example kvm_run_exit next to the accelerator. The option -trace with a pattern such as kvm_ star turns events on, and -d enables other log items while -D chooses the file for them. Now put it together: from the KVM_RUN line in strace, git grep finds kvm_cpu_exec; gdb shows the thread stacks; perf shows where the time goes; a trace event confirms the exit reason. In the next chapter we walk the main loop and virtio-blk the same way.
