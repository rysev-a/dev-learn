Linux Administration. Chapter 8. Docker through an administrator's eyes. When you type docker run, the client sends a request to the Docker daemon, the daemon hands the work to containerd, and containerd calls runc. No virtual machine is created anywhere: runc starts an ordinary Linux process and wraps it in four layers. These are namespaces, a control group, a root filesystem built from image layers, and a virtual network cable to a bridge. Everything else in Docker is image packaging and convenient commands on top of these four kernel mechanisms.\n\nThe first two layers are visible on the host with simple tools. The container's process is in the ordinary process list, and docker inspect shows its number. By default it gets its own mount, process, network, IPC and hostname namespaces, and on cgroup version two a cgroup namespace as well. There is no user namespace, so root in the container is the same user with ID zero as on the host, only with a trimmed set of capabilities. With the systemd driver the control group is a scope named docker, a dash, the container ID, inside system.slice.\n\nDocker translates the limit flags into writes to control group files. The memory limit lands in the memory.max file. The memory-swap flag sets the sum of memory and swap, so the swap file gets the difference. The cpus flag becomes cpu.max: a quota and a period, the period usually 100000 microseconds, so one and a half CPUs means 150000. The process limit goes to pids.max. The relative cpu-shares weight defaults to 1024, but how it converts to a weight depends on the runc version, so read the file itself.\n\nThree commands show what is happening on the host. docker ps lists containers: ID, image, command, age, status, ports and name. docker stats shows live load: CPU percent, memory as used slash limit, network, disk and the number of processes. Memory there is counted without cache: the inactive file cache is subtracted from the total. With no limit set, the percentage is taken against the host's memory. And docker system df shows how much space images, containers, volumes and the build cache take, and how much of it can be reclaimed.\n\ndocker inspect prints JSON, and an administrator needs four pieces of it. The State section holds the status, the exit code, the OOMKilled flag and the number of the main process on the host. HostConfig holds the limits that were set: memory in bytes, NanoCpus in billionths of a CPU, the process limit and the restart policy. Mounts gives the type, source, destination and write flag of each mount. NetworkSettings gives the address and gateway in each network. A zero or empty limit means there is no restriction. The format flag with a template pulls out a single field.\n\nA container's root is an overlay filesystem. The image layers are mounted read-only as lowerdir, and the topmost layer comes first, on the left. The writable layer is upperdir, the service directory is workdir, and the resulting view is merged. All of it lives under /var/lib/docker/overlay2. On the first write to an image file the whole file is copied up. Deleting a lower-layer file leaves a character device 0/0 in the upper layer, a whiteout. So keep frequently changing data in a volume. On newer installs the image store may differ, and the directories look different.\n\nThe default network is the docker0 bridge. Each container gets a pair of virtual interfaces: one end is eth0 in the container's network namespace, the other is attached to the bridge on the host. The container gets an address from the bridge's subnet, most often 172.17.0.0/16. Outbound traffic is masqueraded: the sender's address becomes the host's. A port published with the p flag is a destination-rewrite rule in the nat table. Docker enables packet forwarding and by default installs its rules through iptables; the nftables backend is marked experimental in the documentation.\n\nThe exit code is the first clue. 137 is 128 plus 9: the process was killed by the kill signal. Either docker stop did not get a clean shutdown and, after TERM and a ten-second wait, sent KILL, or the kernel killed the process for lack of memory. The OOMKilled flag in inspect, the oom_kill counter in the memory.events file and a line in dmesg tell them apart. 143 is a stop by the TERM signal, 139 is a segmentation fault. Codes 125, 126 and 127 point to a problem with starting, not with the program itself.\n\nThe Docker daemon listens on the socket /var/run/docker.sock, and access to it is root on the host. The docker group gives superuser rights: you can start a container, mount the host's root into it and change anything there. The same holds for a container with that socket mounted into it: it controls the daemon, and so the host. Do not expose the API over the network without encryption. For protection there is rootless mode, where the daemon runs inside a user namespace, and Podman, which has no permanent daemon. For virtual machines libvirt plays the same role.\n\nA container is not a virtual machine. The host and all containers share one kernel: a container's system call is handled by the host kernel, so a kernel vulnerability affects everyone. Isolation comes from namespaces, control groups, trimmed capabilities and syscall filters. A KVM virtual machine has its own kernel, and its boundary with the host passes through hardware virtualization and the QEMU process. That is an ordinary process: libvirt places it in machine.slice and limits it with the same groups. A container is lighter and starts faster; a machine is isolated harder. The choice depends on whom you trust.
