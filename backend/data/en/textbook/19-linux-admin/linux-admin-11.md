#CHAPTER 11 | Bond, team, MTU, ethtool
Linux Administration. Chapter 11. Bond, team, MTU, ethtool. One network cable is one point of failure and one speed ceiling. To remove both limits, several interfaces are combined into one logical interface, and in Linux the bonding driver does this. There is an alternative, the team daemon, but Red Hat Enterprise Linux 10 removed it and recommends bonding, so we learn the bond. Two more topics stand next to it, and without them a bond cannot be debugged: ethtool shows what is happening with the card, and the MTU decides which frames will pass along the whole path.\n\nThe bonding driver has seven modes, each with a number and a name. Mode zero, balance-rr, sends packets in turn and is the default. Mode one, active-backup, keeps one working interface while the others wait. Modes two, balance-xor, and four, 802.3ad, pick an interface by a hash of the flow. Mode three, broadcast, duplicates everything on all interfaces. Modes five and six, tlb and alb, balance on their own. Modes one, five and six need no special switch configuration; the others usually need grouped ports, and mode four needs LACP as well.\n\nA bond is created with ip link add, type bond, and parameters: the mode, the link check period, the hash policy. It is an ordinary network interface, so it can get an address or have a bridge on top. A physical card is added like this: first bring it down, then make the bond its master. If the card is up, the kernel replies it cannot be enslaved while up. The kernel also gives the card the same MTU as the bond. Then you bring the bond up and check the result with ip dash d link show.\n\nThe main document about a bond's state is the file bond0 in the directory proc, net, bonding. The top part describes the bond itself: the mode, the hash policy, the active interface, the link polling period and the delays in milliseconds. Below comes a block for every enslaved interface: the status, the link failure counter, the permanent hardware MAC address. The status is not only up and down: there are intermediate going down and going back while a delay is being counted. A failure counter that keeps growing betrays a flapping cable or port, even if everything works right now.\n\nHow does the bond learn that an interface has failed? The miimon parameter sets the polling period in milliseconds: each time the driver looks at whether the card has a carrier. Zero disables polling, and one hundred is a sensible starting point. The delays downdelay and updelay exist so the bond does not jump at flapping: an interface is declared failed downdelay after the carrier is lost, and returned to work updelay after it comes back. Make both multiples of miimon, or they are rounded down. ARP monitoring cannot be enabled together with miimon, and mode four needs miimon.\n\nIn modes two and four the enslaved interface is chosen by a hash. The layer2 policy takes the last bytes of the MAC addresses and the protocol type, so all traffic to one neighbor goes through one interface. Layer2 plus 3 adds the IP addresses. Layer3 plus 4 adds the ports, and different TCP connections between the same pair of hosts spread over the interfaces. But one connection always stays on one interface, so a single flow will not add the speeds of the interfaces together. Only mode zero can, at the price of packets arriving out of order.\n\nMode four works only together with a switch: LACP aggregation has to be enabled on its ports. The two sides exchange LACPDU frames, once a second at the fast rate or once in thirty seconds at the slow one, and combine ports of the same speed and duplex into one aggregator. The bond file shows the aggregator number, the keys and the partner's MAC. If an interface landed in another aggregator, or the partner's MAC is zero, the settings of the two sides did not match: the port is in the wrong channel, the key differs, or LACP is off.\n\nEthtool asks the card's driver directly. Without options it shows the link: speed, duplex, auto-negotiation and the Link detected line. If there is no link, the speed and duplex are unknown. The dash capital S key prints the driver's counters: the names differ by vendor, but checksum errors and drops from a lack of buffers exist almost everywhere. Dash lowercase k shows the offloads, and the fixed mark means they cannot be changed. Dash capital K changes them, and dash lowercase g shows the sizes of the card's rings.\n\nThe MTU is the largest IP packet that passes along a link without fragmentation. On ordinary Ethernet it is fifteen hundred, and jumbo frames of nine thousand work only if every device on the path is configured the same way. A VLAN tag adds four bytes to the frame, not to the MTU, but a VLAN interface cannot get a larger MTU than its parent. A VXLAN tunnel takes fifty bytes over IPv4 and seventy over IPv6. The inner interface must be smaller by that difference.\n\nThe classic MTU failure looks strange: ping works, SSH lets you in, but a big file or a web page hangs. Small packets pass, large ones are silently lost: somewhere the MTU is smaller, and the reply asking for fragmentation is often filtered. The limit is found with a ping that forbids fragmentation, trying different sizes. The message message too long means the interface's own MTU is too small, while a Frag needed reply with a number came from a router on the path. For an oVirt host, check the whole chain: cards, bond, VLAN, bridge and switch ports.
