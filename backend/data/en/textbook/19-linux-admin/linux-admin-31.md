Linux Administration. Chapter 31. Diagnostics: /proc, /sys, top, vmstat, iostat, ss, perf, and bpftrace. A host is slow, and the first urge is to restart something. Resist it: a restart destroys the evidence. Work by method instead. For each resource, be it CPU, memory, disk, or network, ask three questions: how busy is it, is there a queue of waiters, and are there errors. That is the USE method: utilization, saturation, errors. Then loop: form one hypothesis, take one measurement, draw a conclusion. Change one thing at a time, and write down what you saw.\n\nNearly every tool in this chapter reads the same files. The /proc directory is a window into the kernel: load average, memory, CPU counters, and a subdirectory for each process with its state, I/O, open files, and cgroup. The /sys directory shows devices: disk queues and the counters of network cards. Most numbers there are cumulative and grow from boot, so they mean something only as two snapshots a few seconds apart: the difference divided by the interval. That is exactly how vmstat and iostat work, and how you will compute in your own scripts.\n\nLoad average is three numbers: for one, five, and fifteen minutes. It is not CPU percent. Linux counts the tasks that are running or waiting for a CPU, plus those in uninterruptible sleep, usually waiting for a disk. Compare the number with the core count that nproc prints. Four cores and a load of eight mean a queue twice as long as the machine can serve. High load while the CPU idles? Then tasks are stuck on I/O or a lock. And if the one-minute figure is above the fifteen-minute one, the problem is growing.\n\nFree memory always looks scarce, and that is normal: the kernel fills the rest with the file cache and gives it back when needed. So read MemAvailable in meminfo, not the free column: it estimates how much can be obtained without swapping. The free command computes used as total minus available. The real warning signs are different: little available memory, growing swap, and pages constantly moving back and forth. Recall chapter 5 on the OOM killer and chapter 6 on a cgroup's memory limit: a group's limit can fire while the host still has free memory.\n\nOpen top and read the header first. The CPU line splits time into states: us is user code, sy the kernel, ni niced processes, id idle, wa waiting for I/O, hi and si interrupts, and st time stolen by the hypervisor. Inside a virtual machine, an st clearly above zero means the host is short of CPU, and the fix belongs there; see chapter 6 and the virtualization book. In the process list, VIRT is the address space, RES is memory actually held, and the state letter D means uninterruptible sleep.\n\nVmstat with a one-second interval is the best first look at a host. The first line gives averages since boot, so skip it. Column r is tasks queued for a CPU, and b is tasks blocked on I/O. Then come memory, swap traffic si and so, block I/O bi and bo, interrupts, context switches, and CPU percentages down to wa and st. Read it like this. An r above the core count: the CPU is overloaded. High b and wa: blame the disk. Nonzero si and so: memory is short. High st: the virtualization host is crowded.\n\nIostat with the x option shows every block device. Take the second and later reports: the first is again computed from boot. The main columns are reads and writes per second, kilobytes per second, read and write wait in milliseconds, the average queue length, and percent utilization. The old svctm column is gone. A hundred percent utilization on an ordinary disk means saturation, but on solid-state drives and arrays that serve requests in parallel it says little; look at the wait and the queue. Alongside work mpstat for cores, pidstat for processes, and sar, which keeps history.\n\nNow the network. The ss command with the s option summarizes how many sockets are in each state. With t and i it shows, per connection, the round-trip time, the congestion window, and retransmissions. Many retransmits relative to segments sent point to the network or an overloaded receiver. For a listening socket the two queues mean something else: the first is the connections waiting for accept, the second is their limit. Card counters live in /sys/class/net: growing errors and drops point to a cable, a bridge, or a queue. Driver faults and OOM kills show in dmesg.\n\nModern kernels also provide pressure, abbreviated PSI. In /proc/pressure there are three files: CPU, memory, and I/O. The some line shows the share of time when at least one task waited for the resource, and the full line when all of them waited, a direct sign of overload. To see who burns the CPU, take perf stat and perf top from chapter 29. To see what a process does to the kernel, take strace with the c option from chapter 26: it folds system calls into a table by time and errors.\n\nWhen ready-made tools run out, reach for bpftrace. A one-line program picks an observation point (a tracepoint, a kprobe, or a timer), a filter, and an action on a map. Counting file opens by process name is a map keyed by comm with a counter; hist gives a distribution, such as latencies, in power-of-two buckets. Maps are printed on exit. Ready-made bcc utilities such as biolatency and opensnoop do this for you. The overhead is small but not zero: on a production host run it briefly and record the result. That closes troubleshooting; the last chapter turns to security.
