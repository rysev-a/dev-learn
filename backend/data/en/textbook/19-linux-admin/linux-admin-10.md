#CHAPTER 10 | Bridges, veth and VLAN
Linux Administration. Chapter 10. Bridges, veth and VLAN. A Linux bridge is a software switch inside the kernel. Any network interface can become its port: a physical card, one end of a veth pair, or the tap device of a virtual machine. The bridge reads the destination MAC address of each Ethernet frame and passes the frame to the right port. It works at layer two and knows nothing about IP. The bridge also appears as an interface of its own, so the host can keep an address on it. KVM, libvirt and oVirt all rely on this.\n\nA bridge takes three commands of the ip tool. Add a device of type bridge, bring it up, and enslave an interface to it with set master. Taking the interface out again is nomaster. The old brctl tool from the bridge-utils package does the same, but it is considered obsolete. Notice what happens to addresses: once an interface is a port, the bridge takes over its traffic, so the IP address of the host belongs on the bridge itself, not on the port. A separate command called bridge, from the iproute2 package, shows ports, the forwarding table and VLANs.\n\nA veth is a virtual Ethernet cable. The device is always created as a pair, and a frame sent into one end comes out of the other. If one end is down, the link of the pair is down too. One end usually goes into a network namespace and the other joins a bridge on the host, which is how a container gets its network. The interface list shows the ends as veth0 at veth1. The ethtool statistics report the peer's interface index, so the far end can be found. Chapter twelve builds a container network from this.\n\nTo read a bridge, run ip with the -d flag. The times in the bridge line are in hundredths of a second: ageing_time 30000 is the usual 300 seconds, forward_delay 1500 is 15 seconds, hello_time 200 is two. stp_state 0 means spanning tree is off, the priority is 32768, and vlan_filtering 0 means VLAN tags are ignored. The bridge_id is the priority and the bridge MAC, by default the lowest MAC among its ports. For a port, the bridge_slave line shows the state, priority and cost. The bridge MTU follows the smallest port MTU unless you set it.\n\nEvery bridge keeps a forwarding table, the FDB. When a frame arrives, the bridge records its source MAC against the port it came in on. For the destination it looks up an entry: a known address goes to one port, while an unknown unicast or a broadcast is flooded to all other ports, never back to the source. Learned entries are dynamic and age out, by default 300 seconds after the last frame from that source. A host that moves is simply learned again on its new port. The addresses of the bridge and its ports are permanent.\n\nSpanning tree, STP, stops loops: connect two ports of one bridge to the same switch and a broadcast circulates forever. On a Linux bridge STP is off by default. Turn it on and a port walks through blocking, listening, learning and forwarding, spending the forward delay, 15 seconds by default, in each of the two middle states. Listening drops data frames; learning records addresses but does not forward. The port cost comes from link speed: 19 for 100 megabit, 5 for gigabit, 2 for ten gigabit. Libvirt bridges, per its documentation, have STP on with a delay of zero.\n\nA VLAN subinterface gives the host a tagged port. You create it on a parent interface with type vlan and an id. Everything sent through it leaves the parent with an 802.1Q tag of that id, and frames carrying that tag arrive on it untagged. Usable ids are one to 4094. A name like eth0.100 is only a convention; ip with the -d flag shows the real protocol and id. The subinterface MTU starts equal to the parent's and cannot exceed it, yet the frame on the wire is four bytes longer, and the switch port must accept it.\n\nInstead of one bridge per VLAN, turn on VLAN filtering and serve all VLANs with a single bridge. Each port gets a list of allowed VLANs. An untagged frame is assigned to the port's PVID, and without a PVID it is dropped. A tagged frame is accepted only if its id is in the list. On egress, a VLAN marked untagged loses its tag, the others keep it. A new port gets VLAN one, untagged and PVID. The forwarding table is keyed by MAC and VLAN, and flooding stays inside the VLAN. The bridge vlan show command prints the result.\n\nNow the tie to virtualization. When libvirt starts a virtual machine, it creates a tap device, usually named vnet0, vnet1 and so on, and makes it a port of the network's bridge. In the default network that bridge is virbr0, where the host holds 192.168.122.1. To put a machine on the local network, create your own bridge, say br0, add the physical card, and move the host address onto the bridge. Classic oVirt does the same: a bridge per VM network, sitting on a tagged device such as bond0.50 when the network has a VLAN.\n\nIf a machine has no network, walk the bridge from the bottom up. First: is the port in this bridge, and forwarding? A blocking or disabled port drops everything. Second: with VLAN filtering on, does the port have the right VLAN, and does its PVID match the guest's untagged frames? Third: has the bridge learned the guest MAC on exactly this port? No entry, no frames. Fourth: do the port counters grow? Remember too that iptables sees bridged traffic only with the br_netfilter module loaded.
