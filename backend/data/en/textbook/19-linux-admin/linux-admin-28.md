Linux Administration. Chapter 28. /dev/kvm: the API version, creating a VM and a vCPU, a tiny guest. This is Step 3 of the roadmap: C is here not for big programs but for talking to the kernel with your own hands. KVM is exposed to processes as the character device /dev/kvm, and all control goes through ioctl calls. The kernel does one thing: it runs guest code on the processor. Memory contents, disks, network and console are the job of a monitor in user space. QEMU and libvirt do exactly that; we will write the shortest version without them.\n\nCheck the host before writing code. The kvm module creates the device file, together with kvm_intel or kvm_amd; lsmod shows them. If the file is missing, open fails with no such file: the module is not loaded, the processor lacks virtualization extensions, they are off in the firmware, or you are inside a machine without nested virtualization. The extensions appear as the vmx or svm flags in /proc/cpuinfo. If the file exists but open says permission denied, look at ls -l. The group is usually kvm; upstream systemd defaults to mode 0666, but distributions may tighten it.\n\nKVM has three levels of descriptors. Opening /dev/kvm gives the system descriptor: through it you ask for the version and features and create machines. Creating a machine returns a machine descriptor, where you set up memory and create virtual processors. Creating a processor returns the third descriptor, and the guest runs on that one. A request of the wrong level is rejected. The documentation asks you to issue machine requests from the creating process, and processor requests from the thread that created the processor. In strace output the three levels are plain: every call names its descriptor.\n\nThe first thing any monitor does is open /dev/kvm for reading and writing, with the close-on-exec flag, and ask for the version. KVM_GET_API_VERSION returns twelve, and the documentation demands refusing to work with any other value. Since kernel 2.6.22 the binary interface is stable; new things arrive as extensions, not as a new number. The third argument must be zero: in the kernel source a non-zero one gives invalid argument. This is the roadmap exercise. An error comes as minus one plus errno, so save the error number before closing the descriptor.\n\nKernel features are found not by kernel version but with KVM_CHECK_EXTENSION and a capability number. Zero means no, a positive number means yes, and sometimes it also carries data: the recommended and maximum number of processors, the number of memory slots. Always ask first, and handle absence instead of crashing. Ask on the machine descriptor if you can, because the documentation notes that machines may differ in capabilities. QEMU and libvirt do the same, and their startup checks explain why they refuse to run on an odd kernel or in a trimmed nested environment.\n\nKVM_CREATE_VM creates a machine; its argument, zero, is the machine type. A new machine has neither processors nor memory. The guest's memory is ordinary memory of your process: you take it with mmap and describe it to the kernel with KVM_SET_USER_MEMORY_REGION: the slot number, the guest physical address, the size and the address in your process. Addresses and size must be multiples of the page, otherwise invalid argument; slots must not overlap in guest addresses, otherwise already exists. The kernel does not copy memory: whatever you change in your mapping, the guest sees at once.\n\nNow the processor: KVM_CREATE_VCPU on the machine descriptor, with the processor number, returns its descriptor. The number of processors is limited, and an extra one fails, as does a repeated number. To talk to the processor you need a shared area holding the kvm_run structure. Its size comes from KVM_GET_VCPU_MMAP_SIZE on the system descriptor, and you map it with mmap on the processor descriptor at offset zero. Use exactly that size, not the structure's: in the kernel source, on x86 it also covers a port data page and a coalesced MMIO page, and I/O data sits beyond the structure.\n\nNext is the loop, the heart of a monitor. KVM_RUN hands the processor to the guest and returns when the guest has done something the kernel cannot do itself. Zero means the guest exited; the reason is in exit_reason in the run area. Port I/O is KVM_EXIT_IO: direction, size, port, count and the offset where the data lies in the area. A halt is KVM_EXIT_HLT, access to a device by address is KVM_EXIT_MMIO, and shutdown, fail-entry and internal-error mean trouble. A signal interrupts the request with EINTR, and then you simply call it again. Ports are noticeably faster than MMIO.\n\nA tiny guest in its real form is a few bytes of code. The 2015 LWN article "Using the KVM API" by Josh Triplett puts a small real-mode program into one page of memory, sets the initial registers and runs it; to show something, the program touches a port and the monitor sees an I/O exit. Registers are set by separate, architecture-dependent requests. Our sandbox has no /dev/kvm, so a model stands in for the kernel, and the guest is a toy with its own instruction set. The monitor code is still real: the same constants, structures and requests.\n\nLet us sum up. The path: open /dev/kvm, check version twelve, ask about features, create a machine, map memory, create a processor, map the run area and spin the loop, closing everything on every exit path. QEMU does the same, with devices, disks, the network and a thread per processor around it; chapter thirty covers that. Libvirt starts QEMU, and oVirt manages libvirt through VDSM. So when a machine will not start, run strace on QEMU and look at /dev/kvm: no such file or permission denied is readable at once.
