Linux Administration. Chapter 3. systemd: units, targets, dependencies, timers. When a server powers on, the kernel starts the first process, and in modern distributions that is systemd. It brings services up in the right order, restarts the ones that fall over, follows the schedule, and collects their logs. Everything it manages is called a unit: a service, a timer, a mount point, a group of services. Every administrator's question sounds the same: what should be running, why did it not start, and what depends on what. This chapter teaches you to answer from the documentation, not from guesses.\n\nA unit description is an ordinary text file with sections. The files live in several directories, and the order matters. Packages put their units in /usr/lib/systemd/system, and on many systems the same directory is also visible as /lib/systemd/system. Temporary units live under /run, and your own files and changes live in /etc/systemd/system. If one name turns up in several places, /etc wins, then /run, then /usr/lib. That is why you do not edit a file that came from a package, you override it: the package manager will update it without touching your changes.\n\nA typical service file has three sections. Unit holds the description and dependencies. Service says how to run it: an ExecStart line and the service type. Type simple counts the service as started right after the process is created, exec once the program has really started, forking when the parent exits, oneshot when the program has run to completion. Type notify waits for a readiness message. In Install, a WantedBy line says which target the enable command hooks the service into. In practice that is just a symbolic link in the target's directory.\n\nThe main trap in systemd is that dependency and order are different things. Wants means I would like that unit to start too, but if it fails I start anyway. Requires is stricter: if the required unit fails and an order is set, my unit will not start. After and Before set only the queue and start nothing. Without After, even units linked by Requires start at the same time. So for an application and its database you normally write both lines: requires and after. Harder variants, such as Requisite and BindsTo, are needed less often.\n\nA target is a synchronization point, a group of units under one name. The multi-user target is the ordinary multi-user mode without graphics, and on servers it is usually the default; the graphical target adds a graphical login on top of it. The get-default command shows which target is loaded at boot, and set-default changes it. The isolate command switches the running system to another target and stops everything else, so use it with care over a remote session. The services of a virtualization host, libvirt for instance, are usually hooked into the multi-user target.\n\nYou do not edit someone else's file, that is what a drop-in is for: extra files in a directory named after the unit plus dot d. The systemctl edit command creates override.conf there and reloads the configuration itself after you save. Files are merged alphabetically, and a later one wins. But list settings accumulate values, so to replace the start command you must first assign an empty value and then the new one. Otherwise an ordinary service ends up with two start commands and will not load. The cat command shows the result, revert rolls it back.\n\nThe Restart setting says when systemd brings a failed service back. On-failure restarts after a nonzero exit code, an unclean signal, a timeout or a watchdog trigger, and a clean exit with code zero counts as normal. On-abnormal ignores exit codes. Always restarts in every case. The pause before the start is RestartSec, 100 milliseconds by default. But there is a fuse: more than five starts in ten seconds, and the unit is stopped in the failed state. The limits are configurable, and reset-failed clears the counter. A stop command never triggers a restart.\n\nA timer is a separate unit that starts the service with the same name. Calendar triggers are set by an OnCalendar string: an optional weekday, a date with asterisks, a time. Daily and weekly are ready-made shortcuts. A comma lists values, two dots give a range, a slash gives a step. Persistent=true saves the time of the last run on disk, so a run missed while the machine was off happens when it powers on. The default accuracy is one minute, and RandomizedDelaySec spreads the load. Check an expression with systemd-analyze calendar.\n\nHow to read a sick service. First the list of failed units: systemctl list-units with the failed option. Then the status of the specific unit. The Loaded line says whether the file was found, where it is, and whether the unit is enabled. The Active line gives the state and the reason, for example failed with the result exit-code. Main PID shows the main process and, if it has died, its exit code; Memory shows memory use if accounting is on. Below are the last journal lines, which the next chapter covers. After the repair, reset-failed clears the failed state.\n\nIf a server boots slowly, systemd-analyze helps. Blame lists units by start time, longest first. But a long unit may just be waiting for a neighbor, and services of type simple barely show up there. Critical-chain draws the chain that determined the boot time: after the at sign comes the moment of the start, after the plus how long the start took. Read it from the bottom up, from the root cause. On an oVirt host this shows whose waiting holds back libvirt and VDSM: often it is the network, not the services.
