Linux Administration. Chapter 22. os, pathlib, shutil: files, permissions, atomic writes, lock files. A control script spends most of its life changing files: configuration, state, copies, lock files. Python gives three tools for it. The os module is a thin layer over system calls, pathlib describes paths as objects, and shutil copies, moves and deletes whole trees. The hard part is how they fail: a path escapes its directory, a crash leaves half a file, two copies of a script edit the same thing. VDSM on an oVirt host must survive all of this.\n\nStart with paths. A Path is an object, not a string: the slash operator joins parts, and parent, name, stem and suffix take a path apart again. Methods such as read_text, write_text, iterdir, glob and mkdir with parents and exist_ok replace a dozen os calls. There is a trap: if the right side of the slash is an absolute path, the left side is simply discarded, so base slash user input can point anywhere. Pure paths only manipulate text, concrete paths go to the disk. Keep that difference in mind, the next check depends on it.\n\nNow safety. A name came from outside, and you may write only inside one directory. Looking for two dots in the string is not enough: a symbolic link inside the directory can lead out. The reliable recipe is to join the paths, call resolve, which follows links and removes the dots, and only then ask is_relative_to against the resolved base. is_relative_to itself is purely textual, so resolve must come first. A gap remains between check and use, so for untrusted input open the file in a way that refuses a final link, for example with O_NOFOLLOW.\n\nPermissions live in st_mode. The low nine bits are read, write and execute for owner, group and others. Above them sit three special bits: set-user-ID, set-group-ID and sticky. The highest bits give the file type. The stat function follows a link, lstat looks at the link itself. S_IMODE extracts the permission bits, and stat.filemode draws the familiar ls string. chmod sets a mode; the owner is changed with chown or shutil.chown, which accepts names, and the pwd and grp modules translate names to numbers. Changing the owner normally requires root.\n\nNow the creation mask, umask. A new file gets the requested mode minus the bits of the mask. With the usual mask 022, a file requested with mode 666 ends up as 644, and a directory requested with 777 becomes 755. The mask applies only at creation and never affects chmod. os.umask changes it for the whole process and returns the old one, so touching the mask inside a library is rude. For secrets, create the file with mode 600 right away through os.open, instead of creating it open to everyone and fixing it afterwards.\n\nWriting straight into a file is dangerous: opening it for writing truncates it first, so a crash or a full disk leaves an empty or half-written file. The safe way: write a temporary file in the same directory, flush Python's buffer, call fsync on the descriptor, and rename it over the target with os.replace. A reader sees either the whole old file or the whole new one. Then fsync the directory so the rename survives a power cut. The temporary file must be on the same filesystem, or you get EXDEV, and it should receive the old file's mode.\n\nTwo copies of a script must not edit the same state. The classic lock file is created with O_CREAT and O_EXCL: if it exists you get EEXIST, and the owner writes its PID into it. The weakness is that a crashed owner never deletes it, so others must check whether the PID is alive, for example with signal zero, and PIDs get reused. Safer is flock on an open file: the kernel drops the lock when the process dies. With LOCK_NB you get an exception instead of waiting. Locks are advisory: they bind only programs that ask.\n\nshutil handles whole trees. copy copies data and mode, copy2 also tries to keep timestamps and other metadata, and copytree copies a directory and fails if the target exists unless dirs_exist_ok is set. rmtree deletes a tree and refuses a symbolic link as its argument. move first tries a plain rename; if source and target are on different filesystems that fails with EXDEV, and move copies and then deletes, which is no longer atomic. disk_usage returns total, used and free bytes, so check the space before a large copy. which finds a program through the PATH variable.\n\nWalking a tree means os.walk or scandir. Entries arrive in arbitrary order, so sort when order matters. Walking top-down lets you edit the list of subdirectory names in place: remove a name and walk will not enter it, which is how you skip a cache or a foreign mount point. Bottom-up walking cannot prune. By default walk does not enter symbolic links to directories, although it lists them. For scratch space there is tempfile: mkstemp creates a file with mode 600 and returns the descriptor and the path, mkdtemp makes a private directory, and TemporaryDirectory cleans up after itself.\n\nFailures arrive as an OSError with a number. Python turns common ones into subclasses: FileNotFoundError for ENOENT, PermissionError for EACCES and EPERM, FileExistsError for EEXIST. EXDEV means a rename crossed filesystems, ENOSPC means a full disk. Do the operation and catch the error rather than checking first, because things change between check and act. With an atomic write a full disk costs only the temporary file: delete it and the old file is intact. Watching files for changes rests on inotify and is a topic of its own.
