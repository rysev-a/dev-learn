#CHAPTER 2 | Packages and updates: apt, dnf, repositories, kernels
Linux Administration. Chapter 2. Packages and updates: apt, dnf, repositories, kernels. On a headless server almost everything you run arrived in a package. A package is an archive of files, metadata and install scripts, and every system update changes thousands of files without being allowed to break the running services. For a future administrator of KVM hosts this matters even more: the hypervisor, the drivers and the management agent are all installed as packages, and a bad kernel update stops dozens of virtual machines.\n\nThe design is the same everywhere: two levels. The lower one installs and removes individual package files and knows nothing about the network: on Debian and Ubuntu it is dpkg, in the Red Hat family, meaning Fedora, Rocky and Alma, it is rpm. The upper one, apt or dnf, downloads packages from repositories, solves dependencies and installs everything in one transaction. The list of what is installed is kept locally: for dpkg it is the status file in /var/lib/dpkg, rpm has its own database, in modern versions built on SQLite. If the upper level breaks, the lower one remains your emergency tool.\n\nA repository is a directory on a server with packages and an index. On Debian and Ubuntu it is described in the sources.list file or, in newer releases, in files with the sources extension: the fields Types, URIs, Suites and Components, and a source can be switched off with a separate field. In the Red Hat family each repository is a section in a file with the repo extension in /etc/yum.repos.d: the address, whether it is enabled and whether to check signatures. The client works not with the directory but with a cache of the index. apt update only refreshes the knowledge of versions and installs nothing, while dnf refreshes its cache itself once it has expired.\n\nYou trust packages exactly as much as the repository key. On Debian the index is signed, the key is placed in a separate file, for example in /etc/apt/keyrings, and the repository description points to it with the Signed-By field, so that the key applies only to that source. The old apt-key command is considered deprecated. In the Red Hat family the repo section has gpgcheck=1, and the signature of the metadata itself is enabled by a separate parameter. Switching the check off just to make it work is the worst decision: you allow someone else's code to run as root. Get the key from the repository owner over a verified channel.\n\nTo tell which is newer you need an exact version order, and plain string comparison will not do: 1.10 cannot be older than 1.9. On Debian a version consists of an epoch, the upstream version and the package revision. The comparison goes in pieces: first text, then a number, and the tilde counts as less than even nothing, so 1.0~rc1 is older than 1.0. In rpm there is a similar triple: epoch, version, release. The tilde lowers there too, while the caret, on the contrary, raises. The epoch beats everything else, so it should be added with great care.\n\nThe working cycle is this: refresh the indexes, look at what will change, and only then apply. On Debian that is apt update, then apt list with the upgradable flag. The apt upgrade command never removes packages, and if an update needs a removal, that package simply stays as it was, while apt full-upgrade does go for removals. In the Red Hat family dnf check-update returns code 100 when updates exist, and dnf upgrade applies them; the security flag restricts the choice to security fixes. On a production server read the list first and only then confirm.\n\nSometimes a version has to be frozen: a third-party driver does not work with the new library, or the cluster is not ready for the update. On Debian there is apt-mark hold for that, and the list of frozen packages is shown by apt-mark showhold. A held package is neither upgraded nor removed, and the packages that need its newer version must be held back as well. In dnf the same idea is called versionlock and lives in a plugin. A freeze is a debt. Write down who set it and why, because a forgotten hold gradually turns into an unclosed security hole.\n\nKernels are installed side by side: the old one stays in /boot and in the boot loader menu, so after a bad update you can pick the previous one. Which one is running is shown by uname with the r flag. In dnf the number of kernels kept is set by installonly_limit, three by default, and the running kernel is protected from removal by default; the extra ones are removed by remove with the oldinstallonly flag. On Debian and Ubuntu apt autoremove tries to keep the running and the newest kernel. A new kernel works only after a reboot: the file reboot-required in /var/run says so, and in the Red Hat family the needs-restarting command with the r flag does.\n\nAutomatic updates are a compromise. On Debian and Ubuntu the unattended-upgrades package by default installs only security updates and writes its log to /var/log/unattended-upgrades. In the Red Hat family this is done by dnf-automatic: it has a configuration in /etc/dnf and timers, and you choose the mode, notify only, download only, or apply. For ordinary servers this is reasonable. For virtualization hosts it is not: the kernel there is updated deliberately, after putting the host into maintenance mode so that the machines move to neighbouring hosts beforehand.\n\nRollback is where the package managers part ways. apt has no real rollback: read the logs in /var/log/apt/history.log and /var/log/dpkg.log and install the wanted older version explicitly, package name, equals sign and version. dnf keeps a transaction history: history undo cancels one, history rollback cancels all after the chosen one and refuses if the state of the database has already changed. Most reliable is a snapshot before the update. A repository failure is recognisable from messages: 404, no public key, failed to download metadata. The cure is a mirror, not switching the check off.
