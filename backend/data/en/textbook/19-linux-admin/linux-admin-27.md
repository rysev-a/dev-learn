#CHAPTER 27 | fork, exec, mmap and ioctl
Linux Administration. Chapter 27. fork, exec, mmap and ioctl. A new process on Linux is not born from nothing, it is copied. The fork system call creates a near-exact copy of its caller and returns twice: the child's number goes to the parent, and zero goes to the child. A failure returns minus one. The child then usually calls exec and replaces itself with another program. A shell does exactly this when you type a command. The trio of fork, exec and wait underlies everything that starts processes, from the shell to libvirt and QEMU.\n\nThe copy is cheap because memory is not duplicated up front. The kernel copies the page tables, and the pages themselves stay shared until someone writes to one, and only then is that page copied. This is copy-on-write. File descriptors are duplicated too, but they refer to the same open file description, so the read offset is shared between parent and child. Pending signals, timers and memory locks are not inherited, and the child has a single thread, the one that called fork. Remember the stdout buffer as well: unflushed text ends up in both processes.\n\nA parent has to find out how its child ended. The wait and waitpid calls return a status, an integer, and you must take it apart only with macros. WIFEXITED says the process left on its own, and WEXITSTATUS gives the code: the low eight bits of what was passed to exit. WIFSIGNALED says a signal killed the process, WTERMSIG gives its number, and WCOREDUMP tells whether a core dump was written. With the WNOHANG flag the call does not block and returns zero if nobody has finished yet. When there are no children, the error is ECHILD.\n\nA child that has finished does not disappear until the parent calls wait: the kernel keeps its number and status, and the process list shows it as a zombie, state Z, marked defunct. A zombie uses no memory or CPU, but it holds a process ID and a table slot. You cannot kill it, it is already dead, so fix the parent. If the parent dies first, living children become orphans, and process number one or the nearest subreaper adopts them. In a container your program is often the first process, and if it never calls wait, zombies pile up.\n\nThe execve call takes a program path, an array of arguments and an array of environment strings. Both arrays end with a null pointer, and by convention argument zero is the program name. On success the call does not return: the process image has been replaced. The process ID, open descriptors without close-on-exec, and ignored signals are kept; memory mappings and signal handlers disappear. Variants with the letter p search the directories in PATH. Typical errors: ENOENT, no such file, EACCES, no execute permission, and ENOEXEC, unrecognized format. Scripts start with a shebang line.\n\nThe pipeline ls piped into wc is built from these primitives. The parent creates a pipe and spawns two processes. In the first, dup2 puts the pipe's write end onto descriptor one; in the second, the read end goes onto descriptor zero. Each then closes both pipe ends and calls exec. The parent also closes both ends and waits for the children. Closing the spare ends is mandatory: while any write end stays open, the reader never sees end-of-file and hangs. With no readers left, a write raises SIGPIPE.\n\nThe mmap call maps into the address space either a file or anonymous memory filled with zeros. MAP_PRIVATE works on copy-on-write terms: changes stay in your process. MAP_SHARED shares with other processes and, for a file, is written through to it; msync controls the moment of writing. The file offset must be a multiple of the page size. Failure is reported by the value MAP_FAILED, not by zero. The mapping survives closing the descriptor and is removed by munmap. Touching a page beyond the end of the file raises SIGBUS. The protection flags are PROT_READ, PROT_WRITE and PROT_EXEC.\n\nMappings are inherited across fork. If the parent creates an anonymous shared mapping before forking, the children write into it, and after wait the parent sees the result: the simplest shared memory between related processes. With MAP_PRIVATE each side would have its own copy. A virtual machine works the same way: the guest's RAM in QEMU is simply a mapping made by a process. The KVM kernel module is given the address of that mapping and declares it to be the guest's physical memory. We return to this in chapter 28, with a tiny guest.\n\nNot everything fits into read and write: a terminal's window size, the unread bytes in a pipe, a network interface's address, creating a virtual machine. For such commands ioctl takes a descriptor, a request number and a third argument, usually a pointer to a structure whose type depends on the request. Success most often returns zero, failure minus one. A request the object does not understand gives ENOTTY, a bad descriptor gives EBADF. Examples: FIONREAD on a pipe, TIOCGWINSZ on a terminal, SIOCGIFADDR on a socket. Descriptor flags are managed by fcntl.\n\nA request number is a packed number of four fields. The top two bits give the direction, then come fourteen bits of argument size, eight bits of type, the driver's letter, and eight bits of command number. That is the layout on x86, ARM and RISC-V; some other architectures split the bits differently. The macros _IO, _IOR, _IOW and _IOWR build such a number, and the direction is counted from the user's side. KVM uses hexadecimal AE as its letter, and request zero returns the interface version. strace prints request names; you can also decode a number by hand.
