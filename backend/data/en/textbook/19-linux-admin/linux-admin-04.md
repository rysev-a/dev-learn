Linux Administration. Chapter 4. Logs: journald, rsyslog, logrotate. When a server without a screen starts behaving strangely, you have one key witness: the logs. They answer three questions: what happened, when, and in what order. In modern Linux, records travel along two paths: the structured journal of the system manager, and the good old text files under var log. In this chapter we will see how they are connected, how to read them, how to keep them from eating the disk, and how to assemble the story of a failure.\n\nLet us start with journald. It is a systemd service that accepts messages from units, the kernel and programs and stores them in a binary format where every record has fields: the text, the priority, the unit name, the boot identifier. The Storage setting decides where it writes. If the directory var log journal exists, then with the value auto the journal is persistent and survives a reboot. If the directory does not exist, the journal lives in memory, under run log journal, and disappears at reboot. Defaults differ between distributions, so check your own machine.\n\nThe journal is read with the journalctl command, and all its power is in the filters. Dash u selects a unit, dash p sets a priority: a single level means that level and every more serious one, and two dots give a range. Dash b limits output to one boot, and dash b minus one means the previous boot. The since and until options set the time. Dash k shows only kernel messages, dash f follows the stream, and json output hands the fields to scripts. Filters combine, which is far faster than scrolling through a file.\n\nPriorities and facilities come from classic syslog. A priority is a number from zero to seven: zero is an emergency, three an error, four a warning, six information, seven debug. The facility says where a message comes from: the kernel, mail, daemons, authorization, the scheduler, plus eight free local facilities. In a record they are glued into one number: the facility multiplied by eight, plus the priority. That is why the value one hundred sixty-five means local facility number four with the priority notice.\n\nRsyslog is the classic daemon of text logs. It receives messages from systemd and sorts them into files by the rules in rsyslog dot conf and the rsyslog dot d directory. A rule is a selector and an action: a facility, a dot, a priority, then a file. A priority means that level and higher, an equals sign picks exactly one, the word none excludes a facility, and a semicolon combines selectors from left to right. Debian and Ubuntu usually have var log syslog, the RHEL family has var log messages. Debian 12 does not install rsyslog by default.\n\nA line in a text log follows an old standard: the month, the day, the time, the host name, the program tag with a process number in square brackets, a colon and the text. There is no year, and a day below ten is padded with a space, so parse it carefully. The tag ends at the first bracket or colon. The process number is optional: the kernel has none. You search for records by tag and number, and you tell machines apart by host name when logs are collected in one place.\n\nText files keep growing, and logrotate looks after them. A timer or cron starts it once a day, and its rules live in logrotate dot conf and the logrotate dot d directory. For every log you set a frequency, day, week or month, or a size. The rotate setting says how many old copies to keep, compress squeezes them, and delaycompress postpones compression to the next cycle so a program still writing to the old file is not disturbed. Missingok forgives an absent file, notifempty skips an empty one, and a postrotate script tells the daemon the file has changed.\n\nLet us see what is left on disk. By default, numbered copies lie next to the log: dot one, dot two, up to the chosen count; at each rotation the numbers shift and the oldest copy is deleted. The dateext setting puts a date into the name instead. If the daemon keeps the file open, there is the copytruncate mode: logrotate copies the file and truncates the original, but the tiny gap between the two actions may cost a few lines. A size can be given as size, maxsize or minsize, and each combines with the schedule differently.\n\nNow the disk. A persistent journal is not infinite: by default it takes no more than ten percent of the file system, fifteen percent must stay free, and both values are capped at four gigabytes. The SystemMaxUse and SystemKeepFree settings change these limits. When space runs short, only archived files are deleted, oldest first; journalctl with the vacuum size option does the same by hand. Chatty services are also limited: by default ten thousand messages per thirty seconds per service, and the rest is dropped until the interval ends.\n\nFinally, how to read a failure. First fix the window: in which boot and at what time everything began; the previous boot is dash b minus one. Then filter the errors and find the very first one: consequences usually shout louder than the cause. Look at what other units did in the neighboring seconds: that is how the chain shows up, for example memory ran out, the database died, the application lost its connection. Do not forget the kernel: out-of-memory events and disk errors appear there. For virtualization this matters twice: the host journal explains why a machine went down.
