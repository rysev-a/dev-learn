#CHAPTER 5 | Processes and limits: ulimit, prlimit, nice, the OOM killer
Linux Administration. Chapter 5. Processes and limits. A typical complaint goes like this: a service logs too many open files, a fork fails, and then a process simply vanishes from the list. Each story has its own mechanism behind it: a resource limit, a scheduler priority, or the out-of-memory killer. This chapter teaches you to look at them as an administrator: which file to read, which command to run, and what the number means. It all matters on virtualization hosts too, where a KVM guest is just a process.\n\nStart with ulimit. It is a bash builtin: it changes limits only for the current shell and its children. Each resource has two values. The soft one is the value actually enforced, and the hard one is a ceiling above which an ordinary user cannot raise the soft one. Plain ulimit -n shows the soft value, and with -H it shows the hard one. Careful: if you set a number without any flag, both values change, and without administrator rights you cannot get the hard one back. To change only the soft limit, add -S.\n\nTo look inside a running process without restarting it there are two tools. The limits file under /proc and the process number shows a table: the limit name, the soft and hard values, and the units; the word unlimited means no restriction. The prlimit command from util-linux prints the same numbers, and with an option such as --nofile it also changes them on the fly. A new limit applies to whatever the process does next and is inherited by its children. Only an administrator can raise another process's hard value.\n\nWhere does a process get its limits? The first process of the system gets them from the kernel, and every child inherits a copy of its parent's. When you log in over SSH, the pam_limits module reads limits.conf and the limits.d directory and sets the limits of your session. A service started by systemd does not go through such a session, so limits.conf does not affect it: its limits come from the unit itself. Hence the classic mistake: an administrator edits limits.conf, restarts the service, and nothing changes.\n\nA line in limits.conf has four fields. The domain: a user name, a group with an at sign, or an asterisk for everyone. The type: soft, hard, or a dash for both values. The limit name, for example nofile or nproc. And the value. The more specific entry wins: a user beats a group, and a group beats the asterisk. At equal specificity the later line wins, and the files of limits.d are read after the main file, in name order and only with the .conf suffix. Only new logins see the changes.\n\nFor services, limits go into the unit. The LimitNOFILE directive takes one number for both values or a soft-colon-hard pair, and the word infinity removes the restriction. Whatever the unit does not set comes from the DefaultLimit directives in system.conf; according to the documentation, for open files this is 1024 and 524288. The ceiling for one process is the kernel parameter nr_open, and the total number of open files in the system is bounded by file-max. If you set a limit above nr_open, the kernel refuses.\n\nLimits forbid, priorities share the processor. The nice value runs from minus twenty, the most favorable, to nineteen, the least favorable; the default is zero. The nice command starts a program with an adjustment, and renice changes a running process. An ordinary user can only raise the number; lowering it takes privileges or a suitable limit. A difference of one unit changes the processor share by a factor of about 1.25. For the disk there is ionice with its classes, and for scheduling policies there is chrt: a high-priority real-time task can freeze a host.\n\nWhen memory is completely gone, the kernel calls the out-of-memory killer. It chooses the victim by a score: the more resident memory, swap, and page tables a process holds, the higher the score. The score is in /proc/PID/oom_score. An adjustment, oom_score_adj, from -1000 to +1000, is added to it: +1000 makes a process the first candidate, and -1000 removes it from the choice entirely. In a unit the directive is OOMScoreAdjust. A KVM guest process holds the memory of the whole guest, so it is often first in line.\n\nHow do you know the killer came by? Read the kernel log: dmesg, or journalctl with -k. First comes a record of which process asked for memory, with the words invoked oom-killer. Then a table of processes in pages and a line with the victim's control group. The main line starts with Out of memory, Killed process: the number, the name, the virtual size, then the anonymous, file, and shared resident parts and the adjustment. If a control group hit its ceiling, the line starts with Memory cgroup. The service itself ends with signal nine.\n\nWhat remains is the memory around the killer. The kernel lets programs allocate more than exists. In overcommit mode zero only an obvious excess is refused, mode one allows everything, and mode two computes a ceiling as swap plus a share of RAM: a program gets a refusal at allocation time instead of a killer later. In ps output the VSZ column shows the address space and RSS shows what is really resident; in free, look at the available column, not free. Swap gives headroom, but heavy swapping slows the host.
