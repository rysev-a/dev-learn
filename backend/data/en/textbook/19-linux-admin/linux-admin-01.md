#CHAPTER 1 | A headless server: SSH, keys, tmux, sudo
Linux Administration. Chapter 1. A headless server: SSH, keys, tmux, sudo. A real server sits in a rack or a cloud, with no monitor and no keyboard. All you have is a remote command line. So the first habit of an administrator is this: do not saw off the branch you are sitting on. Make every change to access in a way that leaves a way back. We cover SSH logins, keys, the daemon's configuration, tmux, and sudo. The same skills are needed on oVirt hosts.\n\nWhat happens when you type ssh. The client and the server agree on algorithms, exchange keys, and compute a shared secret, after which the channel is encrypted. The server presents its host key and signs the exchange with it. The client compares that key with the known_hosts file in your home directory. An unfamiliar server raises a question with a fingerprint; if you agree, the key is remembered. If the key of a familiar server has changed, the client refuses loudly. That protects against impersonation, so check the fingerprint over another channel, such as the cloud console.\n\nLogging in with a password on a server with a public address is dangerous: bots start guessing within minutes. Use a key pair instead. The secret half stays with you, the public half lies on the server. By default ssh-keygen creates an Ed25519 key, which is short, fast, and reliable. Protect the secret key with a passphrase, and keep it in ssh-agent so you do not type the passphrase every time. ssh-copy-id copies the public half to the server, and ssh-keygen with the -l flag shows a key's fingerprint.\n\nPublic keys live in the authorized_keys file in the user's .ssh directory. One line is one key: optional options, the type, the key itself in base64, and a comment. From limits the source addresses, command forcibly runs one command, and restrict switches off port forwarding, the agent, X11, and the terminal at once. The daemon also checks permissions: while StrictModes is on, a key is not used if the home directory, .ssh, or the file is writable by others. Usually the directory gets 700 and the file 600.\n\nThe daemon's settings live in /etc/ssh/sshd_config. The main rule: for each setting the first value found is used, not the last. In Debian, Ubuntu and modern RHEL-family distributions the file starts with an Include line for the sshd_config.d directory, so files from there override everything below. A Match block lasts until the next Match and fits only a given user, group, or address. But if a setting is already set above, that value wins. The result is shown by sshd with the capital -T flag, and the connection conditions follow capital -C.\n\nThe client file .ssh/config is similar, but blocks open with the word Host. The first value wins here too, so specific blocks go higher and the general Host star goes at the very bottom. The name after Host is what you typed in the command; the real address comes from HostName. IdentityFile values pile up in a list. IdentitiesOnly stops the agent offering extra keys, which could get you cut off after a few attempts. For hosts behind a bastion use ProxyJump: ssh walks the chain itself and no secret key is sent anywhere, unlike with ForwardAgent.\n\nThe classic beginner's mistake: edit sshd_config, restart the daemon, and lock yourself out. The order is this. Open a second session and keep it. Check the syntax with sshd -t. Apply the settings with reload; sessions that are already open stay. Then from a third window check that a new login works, and if not, roll back from the second session. The service name depends on the distribution: ssh in Debian and Ubuntu, sshd in the RHEL family. On recent Ubuntu, socket activation through ssh.socket affects a port change. And open the port in the firewall.\n\nA dropped ssh session kills the processes started in it, together with your work. Tmux solves this: its server is a separate process that keeps sessions, windows, and panes until you close them or the machine reboots. The command tmux new with the -s flag creates a named session. Press Ctrl-b, then d, and you are detached while the session keeps running. The command tmux ls shows the list, and tmux attach with the -t flag brings you back. Run long jobs, such as a package upgrade or a disk copy, inside tmux.\n\nDo not work as root all the time; use sudo. The rules live in /etc/sudoers and in the sudoers.d directory, and you edit them only through visudo, which checks the syntax before saving, because an error there could leave you without privileges. A rule reads: who, on which hosts, as whom, which commands. Of all matching entries the last one applies, not the most specific. NOPASSWD removes the password prompt. Files in sudoers.d with a dot in the name or a trailing tilde are ignored. The admin group is sudo in Debian and Ubuntu, wheel in the RHEL family.\n\nLet us assemble a checklist. Keys instead of passwords. The first value in a config wins, so line order matters. Before editing sshd, open a second session and run a syntax check. Run long jobs in tmux. Grant sudo sparingly, and remember that the last entry wins. Now, why this belongs in a book that leads to virtualization. The oVirt engine usually manages hosts over SSH, with its key placed in the root user's authorized_keys. Closing root login or spoiling the permissions on .ssh makes a host unreachable for the engine. Next chapter: packages.
