#CHAPTER 19 | NFS, loop devices, qemu-img (raw/qcow2)
Linux Administration. Chapter 19. NFS, loop devices and qemu-img. The disk of a virtual machine is in the end a file, and an administrator has to do three things with such files. Share a directory with other servers over the network: that is NFS, and oVirt file storage domains are very often built on it. Make an ordinary file pretend to be a disk: that is what loop devices are for. And create, inspect and join images with qemu-img. This chapter walks through the three tools in turn, with real command output.\n\nThe NFS server is configured by the file /etc/exports. A line holds a directory first and then the clients, each with its options in parentheses and no space before them. Access is read-only by default, and the rw option opens writing. The sync option means the server replies only after the data is on stable storage, and it is the default. Async is faster, but after a server crash data can be lost or corrupted. The exportfs command with the flags r and a applies the file, and with v it shows what is really exported.\n\nA client in exports can be named by host name, network with a mask, wildcard, netgroup with an at sign in front, or a bare star for everyone. When several entries match, the most specific wins: a host beats a network, a network beats a wildcard, a wildcard beats a netgroup, and the star is weakest, whatever the line order. A star in a wildcard also matches dots. Root has its own rule: by default its requests become the anonymous user, number 65534, and no_root_squash turns that off. All_squash makes everyone anonymous, and anonuid sets the number.\n\nA client mounts an export with mount and type nfs: the server name, a colon, the path. If the server runs the mount service, showmount with the -e flag lists its exports. The protocol version is set by the vers option; without it the client tries 4.2 first and steps down until the server agrees. A permanent mount goes into fstab. systemd already knows that NFS needs the network, and the _netdev option is for cases where the type alone does not tell it. Which options really apply is shown by nfsstat with the -m flag.\n\nWhat happens when the server disappears? With the hard option, the default, a request is retried forever and the program hangs. The kernel log says the server is not responding and the client keeps trying, and later that the server is OK. The soft option returns an I/O error after the set number of retransmissions, and the manual warns that this can silently corrupt data. The timeo value is in tenths of a second, 600 by default over TCP, and it grows with each retry. The vdsm source shows oVirt mounting with soft, so know the price.\n\nNow permissions. The oVirt agent, vdsm, runs as the vdsm user with number thirty-six, and the kvm group has the same number. So the owner of the export directory is set to 36 colon 36 with mode 0755. On a host with SELinux the virt_use_nfs boolean may also be needed. The error Stale file handle usually means that the file handle the client remembers no longer means anything on the server: the directory was recreated or the file system was swapped. Most often the remedy is to unmount and mount again, after dealing with the cause on the server.\n\nNext, loop devices. A file can be made sparse: truncate with -s sets the length, and holes take no disk space. fallocate does the opposite and reserves blocks in advance. The difference shows in stat: the size is the file length, while the number of 512-byte blocks is what is really allocated. losetup with -f and --show finds a free loop device and attaches the file, and -P makes the kernel read the partition table. The -a flag lists everything attached, and mount with the loop option attaches a file by itself. Detach with -d.\n\nNow qemu-img. The create command makes an image: the -f flag sets the format and the size comes last. The raw format is just the bytes of the disk. The internals of qcow2 are covered in chapter nine of the virtualization book, so here are only the commands. The info command shows the virtual size, which is what the guest sees, and the disk size, which is how much the file really occupies. The default cluster size is sixty-four kilobytes. With JSON output a program can read the same facts, and the format details sit in a separate section.\n\nAn image can point to a base image. Create it with the -b flag; the capital -F flag, naming the base format, is now required. Info with --backing-chain prints the chain top to bottom. Commit writes the clusters of the top layer into the base, leaving the layer empty but still linked. Rebase rebuilds the chain: in safe mode it copies into the layer whatever would otherwise change for the guest, and with -u it only changes the name of the base, leaving consistency to you. For a running machine this is dangerous; libvirt has block commit.\n\nPreallocation is set with the preallocation option. For raw the choices are off, falloc and full; qcow2 adds metadata, meaning only the tables. Full writes zeros, falloc reserves blocks faster. The check command verifies an image: exit code zero is fine, two is corruption, three is leaked clusters, which only waste space. Convert changes the format, for example raw to qcow2, and resize changes the size; shrinking needs the --shrink flag after shrinking the file system inside. Measure tells in advance how much space an image will need. Such images lie in oVirt file domains.
