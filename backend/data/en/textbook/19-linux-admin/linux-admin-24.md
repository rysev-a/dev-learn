Linux Administration. Chapter 24. libvirt and virsh: domains, XML, pools, networks, cloud-init. libvirt is a single programming interface to hypervisors: QEMU with KVM, and also Xen and containers. In its vocabulary a virtual machine is called a domain, and every domain has a description in XML. The virsh command is just one client of this interface, like virt-manager or the Python library of the next chapter. VDSM in oVirt also talks to libvirt, not to QEMU directly. This chapter teaches you to read and write what libvirt sees.\n\nThe libvirt daemon comes in two kinds: the old monolithic libvirtd and, on newer distributions, modular daemons. virtqemud runs the guests, virtnetworkd the networks, virtstoraged the storage; systemd starts them at the first connection to a socket. The client picks an instance by URI. The qemu:///system URI is the system instance: it runs as root and manages the guests of all users. The qemu:///session URI is a personal instance of an ordinary user. Set the URI with the -c option or an environment variable; a remote host goes through plus ssh. In scripts, always write the URI explicitly.\n\nWho may manage the system instance is decided by socket permissions. Without polkit, the read-write socket is open to root only, the read-only one to everyone. With polkit, the rule is tied to the manage action, and administrators are usually added to the libvirt group. The guests themselves run as a dedicated user, not root: qemu on most distributions, libvirt-qemu on Debian and Ubuntu, so images need a fitting owner and permissions. Every guest gets its own scope under the machine slice, as in the chapter on cgroups. Limits are set with virsh schedinfo, memtune, and blkiotune.\n\nA domain description is the root element domain with a type attribute: kvm for hardware acceleration, plain qemu for emulation. Inside are the name, the UUID, and the memory. The memory element holds the maximum, currentMemory what is given now. The default unit is the kibibyte, but the unit attribute allows gibibytes. A bare number is in kibibytes: just over two million is only two gibibytes. Then come the virtual CPU count, the hvm boot type with the device order, and the CPU mode. Host-passthrough gives the guest the host CPU as it is, but hinders migration.\n\nDevices live in the devices element. A disk is a disk element. Type file or block says where the image lies, and the device field tells a disk from a CD-ROM. The driver sets the format, qcow2 or raw. The target is the name inside the guest and the bus: vda with virtio, sda with sata; the name is only a hint to the guest. A network card is the interface element: type network with source default, or type bridge with source br0, model virtio, and a MAC address. Domblklist and domiflist print all this as tables.\n\nA domain's life fits in a few commands. Define stores the description without starting the guest; start does. Shutdown asks the guest to power off through ACPI or the agent, with no guarantee: the guest may ignore it. Destroy pulls the plug, and the disks stay. Suspend pauses, resume continues. Undefine removes the description, and a running domain becomes transient. Autostart starts it with the host. The virsh list command with the all option shows states, domstate with reason explains the cause, and dominfo prints memory, CPUs, persistence, and autostart.\n\nStorage in libvirt means pools and volumes. A pool can be a directory, a filesystem, a network filesystem, a logical pool, that is an LVM group from chapter 16, a disk, or iSCSI, SCSI, multipath. In a directory the volumes are files; in a logical pool they are logical volumes. A pool has three sizes in bytes: capacity, allocation, available. A volume has two: capacity, what the guest sees, and allocation, what lies on the host, because qcow2 grows as it is written. VDSM prepares disks itself and writes the paths into the domain XML.\n\nThe network called default uses address translation: the bridge virbr0 at 192.168.122.1, handing out addresses from 2 to 254. The forward element sets the mode: nat, route, open, or bridge; without it the network is isolated. The range must lie inside the subnet. Permanent addresses use the host element: a MAC address, a name, and an address. The net-list command with the all option also shows inactive networks, and net-dhcp-leases shows issued leases. For a guest to live directly in the local network, attach its interface to a host bridge, from the chapter on bridges.\n\nSnapshots keep a domain's state. Snapshot-create-as makes one, and snapshot-list shows a list, with a parent column or as a tree. An internal snapshot lives inside the qcow2 file itself, an external one in a separate file, and the earlier file becomes its backing file. Snapshot-revert rolls the domain back and loses everything done after the snapshot. Deleting without options merges the snapshot into its children; the children option removes the whole branch. A snapshot is not a backup: it usually lies on the same storage as the image and disappears with it.\n\nWhat is left is a guest from a ready cloud image. At first boot cloud-init reads settings from the NoCloud source: a disk labeled cidata, a vfat or ISO filesystem, with the files user-data and meta-data in its root. User-data starts with a first line of hash cloud-config. Meta-data needs an instance-id: from it cloud-init knows this is the first boot. Virt-install with the cloud-init option builds such a disk itself and attaches it as a CD-ROM for the first boot only. The next chapter does the same from Python.
