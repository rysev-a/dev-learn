#CHAPTER 17 | RAID (mdadm) and SMART
Linux Administration. Chapter 17. RAID with mdadm and SMART. A disk will die one day; the only question is whether the server stops with it. Software RAID in the kernel, the md subsystem, joins several disks into one block device, and the mdadm command manages it. RAID survives a disk failure, but not a human mistake, a virus, or a fire, so it is not a backup. SMART is the self-monitoring a disk keeps about itself, and it often shows trouble in advance. A hardware RAID controller solves the same problem in silicon.\n\nRAID levels differ in capacity and in how many failures they survive. Level zero stripes data: fast, but any failure destroys everything. Level one mirrors: the capacity of one disk, and the data lives while one disk is intact. Level five keeps one parity, gives up one disk of capacity and survives one failure. Level six keeps two parities, gives up two disks and survives two failures. Level ten in md is not a nested RAID but mirrored copies in a stripe, and it works with an odd number of disks. The smallest disk sets the size.\n\nRedundancy has a price. On a wide array, a small write to RAID five means reading the old data and the old parity and then two writes: four operations instead of one, and six in RAID six. The driver picks the cheaper of two methods: reread the old blocks or read the neighbouring chunks. Worse, a rebuild reads every surviving disk end to end, and on big disks a single unreadable sector along the way is likely. So for large disks people choose RAID six or ten, and find bad sectors early with a regular array check.\n\nAn array is created with one command: the level, the number of disks and the partitions themselves. The default chunk is 512 kilobytes, and the metadata is version 1.2. For RAID five, mdadm creates the array without its last disk and then builds that disk, because this is faster than recomputing the parity of a full array. A hot spare is added with its own option, and a write-intent bitmap with the bitmap option. The array is usable at once while synchronization runs in the background. The filesystem on md0 is made like on any disk.\n\nThe file /proc/mdstat shows the state of the arrays in real time. The array line says it is active, what its level is and which disks belong to it, with the role number of each in square brackets. The letter F in parentheses marks a failed disk, S marks a spare. Below are two numbers: how many disks there should be and how many work, followed by a string of U letters and underscores, where an underscore is a missing disk. During a rebuild a progress bar appears with the percentage, the estimated time and the speed.\n\nDetails come from mdadm --detail on the array. The State field shows clean or active and, if disks are missing, the word degraded; during a rebuild recovering or resyncing is added. Below are the counters of active, working, failed and spare disks and a table of slots: active sync is a healthy disk, faulty a failed one, removed an empty slot, spare a spare. The examine command, by contrast, reads the superblock of a single disk: the array identifier, the disk's role and an event counter. A disk with a lagging counter is the one that dropped out.\n\nReplacing a disk takes four steps. First the disk is marked as failed, if the kernel has not done it already. Then it is removed from the array. Next you swap it and partition the new disk like the old one. Finally you add it, and the rebuild begins; you watch it in /proc/mdstat. If the array has a hot spare, it joins by itself at the moment of failure, and your new disk becomes the next spare. On boot disks also install the bootloader on the new one, or the server may fail to boot.\n\nFor arrays to assemble at boot under their own names, they are recorded in a configuration file. On Debian and Ubuntu it is /etc/mdadm/mdadm.conf, in the Red Hat family it is /etc/mdadm.conf. The array lines come from the detail command with the scan option, and then the initramfs is rebuilt. The address for mail is given by the MAILADDR keyword, and monitoring reports a failure. Once a month it is worth running a check: reading the whole array finds bad sectors while the neighbouring disk is still alive. Usually the package schedules it for you.\n\nSMART is a set of counters the disk keeps about itself. The smartctl command with the -H option prints a verdict: passed or failed. But passed only means that no threshold has been crossed yet. So you read the attribute table with the -A option. An attribute has a normalized value, a worst value and a threshold: a pre-failure attribute that falls to its threshold means failure is near. More often the alarm comes from the raw numbers: reallocated sectors, pending sectors and uncorrectable ones. Any nonzero and growing value is a reason to prepare a replacement.\n\nAn NVMe disk has no attribute table; instead there is a block: the critical warning, temperature, remaining spare, percentage of life used and media integrity errors. The last two matter most. The smartd daemon reads its configuration file and sends mail when something changes: a DEVICESCAN line with the -a option and an address is enough. Behind a hardware RAID controller the disks are often visible only through the -d option and the controller type. On virtualization hosts mdadm usually protects the system and local disks, while oVirt's shared storage domains get their redundancy from the storage array.
