#CHAPTER 14 | Inheritance and composition
Python as a first language. Chapter 14. Inheritance and composition. When you have many classes, relationships appear between them. A dog is an animal, a cat is an animal too, and both have a name, an age, and the ability to make a sound. Writing the same thing in every class means copying code, with all the trouble that brings. That is what inheritance is for: a new class takes the best of an existing one and adds its own. Another way to link classes is called composition: one object contains another as a part, the way a car contains an engine. Today we will look at both ways, learn to override methods, use the super function, create abstract classes, and, most importantly, understand when to choose which approach. This is one of the most important topics in object-oriented design.\n\nInheritance is written like this: the name of the new class, and in parentheses, the name of the parent. Class Dog, with Animal in parentheses. Dog automatically gets all the attributes and methods of Animal: you can call anything defined in the parent, and then add your own. The parent is called the base class or superclass, and the heir is called the derived class or subclass. Two functions help you check the relationship: isinstance asks whether an object belongs to a class or to one of its descendants, and issubclass asks whether one class is a subclass of another. A dog is an animal, so isinstance of a dog and Animal returns true, but not the other way around: not every animal is a dog. This is the is-a relationship, and it is the main sign that inheritance is appropriate.\n\nA subclass can override a parent's method: define a method with the same name, and that one will be called instead. In Animal, the voice method returns an unknown sound, in Dog it is overridden to return a bark, and in Cat, a meow. But often you do not want to replace the behavior, you want to extend it. For that there is the super function, which gives you access to the parent class. The most common use is the constructor: the dog's init method calls super, then init, with the name, so the parent records the shared attributes, and then it adds its own. If you forget to call the parent's init, the shared attributes will not appear, and the object will be left half-built. The rule is this: when you override a method, think about whether you need the parent's version, and if you do, call it explicitly through super.\n\nThe main payoff of inheritance is polymorphism, which means many forms. Say you have a list of animals: a dog, a cat, and a cow. In a loop, you call the voice method on each one, and each answers in its own way. The loop does not know and does not ask who is in front of it: all it needs is that the object has a method with the right name. Add a new class, a duck, and the loop starts quacking without a single edit. That is the power of the object approach: you can extend a program without touching working code. In Python, polymorphism works even without a common parent, by the principle of duck typing: if it walks like a duck and quacks like a duck, then it is a duck. You need a voice method, and it does not matter where the class got it from.\n\nPython allows multiple inheritance: a class can have several parents, listed separated by commas. Then a question arises: in what order do we look for a method if both parents have it? The answer is called the method resolution order. It is computed by a strict rule and is available as a class attribute called mro. First we look in the class itself, then in the parents from left to right, then in their ancestors, with a shared ancestor postponed until last. Multiple inheritance is a powerful but dangerous tool, and most often it is used for so-called mixins: small classes that add one ability, for example, the ability to save an object to a file. If you are unsure whether you need it, you probably do not. Try composition.\n\nSometimes a base class is meant only as a template, and no standalone objects should ever be created from it. Such a class is called abstract. The standard library has the abc module for this: you inherit the class from ABC, and mark the required methods with the abstract method decorator. Trying to create an instance of such a class, or of a subclass that did not implement all the abstract methods, ends with a type error. This is how we fix a contract: every descendant must be able to do such and such. A simpler version of the same trick is a method that raises a not implemented error: less strict, but no extra modules needed. Abstract classes are especially useful when the subclasses are written by different people and it is important that the interface matches.\n\nInheritance expresses is-a, and composition expresses has-a. A car has an engine, but it is not an engine. If you make Car a subclass of Engine just to inherit the start method, you get nonsense: the car acquires revolutions and displacement as its own properties, and later you need a second engine, and everything breaks. The right way is to keep the engine inside the car as an attribute and delegate the work to it: the go method calls the engine's start method. That is composition. A wise design rule says: prefer composition to inheritance. It is more flexible, because the parts can be swapped without touching the rest, and it is easier to understand: there are no deep chains of ancestors that you have to wander through in search of the method you need.\n\nYou often have to check types, and there are two ways to do it. The type function returns the exact class of an object, and a comparison through it ignores subclasses: to type, a dog is not an animal. The isinstance function takes the hierarchy into account and is almost always better. But the truly Pythonic approach is not to check types at all, but to try: if the object can do what you need, use it, and if not, catch the error. This philosophy is called easier to ask forgiveness than permission. To check whether a method exists, there is the hasattr function. Explicit type checks make sense at the boundaries of a program, for example when parsing external data, but inside your code, prefer to rely on interfaces and duck typing. Fewer checks mean more flexible code.\n\nSubclasses are also a good place to override magic methods. The parent's repr method can be written in a universal way: it gets the class name through the type function applied to self, and then every descendant shows its own name in the output with no extra edits. The str method can be extended: call super, then str, and add your own part to the result. The eq method is inherited too, but carefully: if a subclass adds new attributes, comparison by the parent's rule will not see them, and such objects will turn out equal even though they differ. So when a subclass adds data, revisit the comparison and hashing methods. The general advice is this: when you override a method, keep the same meaning as in the parent, so that a subclass can be substituted anywhere a parent was expected.\n\nA separate technique of multiple inheritance is mixins. A mixin is a small class that does not describe a standalone entity, but adds one ability. For example, a mixin for dictionaries: it has one method that collects the object's attributes into an ordinary dictionary. The User class inherits from this mixin and immediately gets a method for turning itself into a dictionary, without having to become a dictionary itself. The is-a relationship is weak here, but the code is reused without copying. Good mixins are simple, independent of each other, and do not keep any data of their own. If a mixin starts to depend on its neighbors and gets cleverly tangled up with them, it is time to stop and replace it with composition: a separate helper object.\n\nLet us put together an example: geometric shapes. The base class Shape declares an abstract method area and knows how to print itself nicely through str. The subclasses Circle and Rectangle each implement area in their own way, and Square inherits from Rectangle and passes the same value for both sides in its constructor. A list of shapes can be sorted by area, the total area can be added up in a single sum over a generator, and large ones can be filtered out. The code that works with shapes knows nothing about the concrete classes, and a new shape, say a Triangle, is added with just one class. This is exactly how graphics editors, games, and banking systems are built: a common interface on top, a variety of implementations underneath.\n\nCommon mistakes. The first: forgetting to call super, then init, in the subclass constructor, so the parent's attributes are never created. The second: inheritance for code reuse when there is no is-a relationship. In that case composition or an ordinary function is better. Next to it is one more: hierarchies that are too deep, five or six levels, which are impossible to navigate. The third: overriding a method with different parameters, so the calling code written for the parent breaks. The fourth: a change in the base class unexpectedly changes the behavior of all its descendants, which is why base classes must be designed especially carefully. The fifth: diamond-shaped multiple inheritance without understanding the resolution order. The sixth: type checks instead of polymorphism, long chains of isinstance where a method would do.\n\nLet us sum up. A subclass takes the attributes and methods of its parent and can add or override its own; the link expresses the is-a relationship. The super function gives access to the parent, and the subclass constructor should call the parent's init. Polymorphism lets you work with different objects through a common interface, and in Python, duck typing helps with that. Abstract classes define the required methods. Composition expresses has-a and in most cases is more flexible than inheritance, so prefer it. The isinstance function takes the hierarchy into account, and type does not. We are done with classes: now you can describe your own data types. In the next section we cover exceptions and files: how a program copes with errors and communicates with the outside world.
