#CHAPTER 38 | Data and types: dataclasses, enum, typing, copy
Python as a first language. Chapter 38. Data and types: dataclasses, enumerations, type hints, and copying. Big programs deal with more and more data, and we have to describe it carefully. An ordinary class with a constructor, a repr, and comparison takes a lot of repetitive code: list the fields, assign them, print them, compare them. Dataclasses write that code for you. Enumerations give meaningful names to fixed sets of values: statuses, days of the week, colors. Type hints make code document itself and let tools find mistakes before you even run it. The copy module takes care of copying complex objects correctly. This is what separates a tidy project from a messy pile of functions. Today we'll go through each of these topics, and at the end we'll meet structural pattern matching, which makes parsing data very expressive.\n\nA dataclass is created with a decorator on an ordinary class that lists fields with type annotations: name, a string; age, an integer. You don't need to write anything else. The decorator generates the constructor, the text representation, and equality comparison for you. Two records with the same field values turn out equal, and printing shows a neat line: the class name, then the values in parentheses. Fields can have default values, and after a field with a default, required fields can't follow. Instead of twenty lines with a constructor and methods, you get five lines of declaration. That is exactly why dataclasses became the standard way to describe records: an order, a user, a setting. The type annotations here serve as a description, not a check: Python won't reject a value of a different type.\n\nDataclasses come with parameters and tools. For mutable defaults, like a list, you use the field function with the default factory parameter: each instance gets its own list, and the shared list trap disappears. The frozen parameter makes instances immutable, and then you can use them as dictionary keys. The order parameter generates less-than and greater-than comparisons following the order of the fields, so records can be sorted. The slots parameter saves memory. The special post-init method runs after the constructor and is good for validation and computed fields. The as-dict and as-tuple functions turn a record into a dictionary or a tuple, and replace creates a copy with some fields changed. This is the very work we used to do by hand with named tuples and classes.\n\nHow do you choose between a dictionary, a tuple, a named tuple, a class, and a dataclass? A dictionary suits data with a free structure: a service response, settings. A tuple is for a small record of a few values returned from a function. A named tuple is for an immutable record with no logic. A dataclass is for a record with typed fields, possibly mutable, and, if you like, methods. An ordinary class is for when behavior and complex initialization matter. The choice comes down to meaning: what matters more, structure or behavior. A good test is how you plan to use the record. If you mostly read its fields, a dataclass fits. If there are many methods around it, it's time to move to a full class, and you can still use a dataclass as the foundation.\n\nAn enumeration is a set of named constants. You inherit a class from Enum and list the members: red, green, blue. Each member has a name and a value, and you reach them as class attributes: Color dot RED. You can loop over all of them by iterating over the class itself. You get a member by value by calling the class with a number, and by name with square brackets and a string. Comparison works with the is operator and with equality. The auto function hands out values automatically. Why bother, if you can just use strings or numbers? To make the code readable and safe. Instead of the magic number three, you write Status dot SHIPPED. A typo raises an error right away, and the editor suggests the options. You can't create a value that doesn't exist: calling with a wrong number raises a value error.\n\nEnumerations come in several flavors. With IntEnum, the members behave like integers and compare with them. With Flag, the members can be combined with bitwise operations, which suits sets of permissions: read, write, execute. String enumerations hold strings and are handy when exchanging data through JSON. You can add methods and properties to an enumeration, and then each member can do something: for example, a day of the week with an is-weekend method. Members are immutable and exist as a single instance each, so you can use them as dictionary keys. Enumerations combine nicely with dataclasses: an order's status field has the enumeration as its type, and the reader immediately sees the allowed values. It's an example of how types describe the problem domain.\n\nType hints are annotations that describe which values are expected. A function parameter gets a colon and a type, and the result gets an arrow and a type: def add of a colon int and b colon int, arrow int. For collections you write list of ints, dictionary from strings to ints, tuple; for optional values, a type or None, joined with a vertical bar. The typing module holds helper tools: Callable for functions, Any for any type, Literal for a set of allowed values, TypeVar for generics. Hints don't check anything while the program runs: Python will happily execute code with the wrong types. They are read by people, by editors, and by special programs such as mypy, which find errors statically. For a reader, a function with annotations says more than ten comments.\n\nWhy have hints if they aren't checked? Three reasons. First, documentation that doesn't lie: an annotation describes what's expected, and the editor shows it when you call the function. Second, finding errors before running: a static analyzer will notice that you passed a string where a number is needed, or forgot to handle an empty value. Third, help for tools: autocompletion and refactoring work noticeably better. Gradual adoption is another advantage: you can add hints to your code piece by piece, starting with the most important functions. Don't overcomplicate things: simple annotations are better than perfect ones. Remember that every annotation is a promise, and you have to maintain it: an outdated hint is worse than none at all. For data from the outside world, you still need a check at run time.\n\nTyped structures. A typed dictionary describes which keys, and of which types, live in a dictionary: it serves as documentation for data like service responses. A typed named tuple is the modern way to write a named tuple, as a class with annotations. A protocol describes an interface: an object fits if it has the right methods, and no inheritance is required. It's duck typing made formal. Generics let you describe containers without knowing the type of their elements. All of this develops one idea: types are not a punishment, they are a language for describing the structure of data. You can use them minimally and still benefit, or you can take them all the way to strict checking when the project is built. Pick the depth by the size of the team and the lifespan of the project: the longer the code lives, the more useful the hints.\n\nStructural pattern matching, the match and case statement, lets you parse data by its shape. Instead of a chain of conditions, you describe patterns. A literal pattern compares with a value. A tuple or list pattern unpacks a sequence: the first element, then the rest. A dictionary pattern checks that keys are present. A class pattern checks the type and the attributes. You can add a condition to any pattern with if, and capture a piece under a name. The underscore is the match-everything pattern, and you put it last. Matching is great for parsing commands, messages, syntax trees. For example, the command go ten is a tuple of a word and a number, and one case catches it together with the number. It's one more way to make code more expressive without losing clarity.\n\nThe copy module is responsible for copying. We found out that assignment doesn't copy an object. The copy function makes a shallow copy: a new outer object is created, while the nested ones stay shared. The deepcopy function copies recursively: at every level, nested lists and dictionaries get their own copies. It can handle circular references. For your own classes, you can override the copying methods. The rule of choice: for flat data a shallow copy is enough, and for nested data you need a deep one. A deep copy is slower and takes more memory, so use it deliberately. For dataclasses there is replace, for lists there is a slice, and for dictionaries there is the copy method. You need deepcopy only when there are mutable objects inside that must be independent.\n\nCommon mistakes. First: a mutable default value in a dataclass instead of field with a factory. Python will even forbid that form for a list. Second: assuming that annotations are checked, and not validating outside data. Third: changing a field of a frozen dataclass and getting an error. Fourth: comparing enumeration members by value where you should compare the members themselves, and the other way around. Fifth: using strings instead of an enumeration and allowing typos. Sixth: overcomplicating hints until they get in the way of reading. Seventh: forgetting that a shallow copy shares nested objects. Eighth: forgetting the match-everything pattern in a match statement, so some value goes unhandled. Ninth: putting a default value before a required field of a dataclass.\n\nLet's sum up. A dataclass generates a constructor, a repr, and comparison by fields; field with a factory solves the problem of mutable defaults, and frozen and order add more power. The choice between a dictionary, a tuple, a named tuple, a dataclass, and a class depends on what the data means. Enumerations give meaningful names to fixed sets and protect you from typos. Type hints document your code and let a static analyzer find errors, but they are not checked while the program runs. A typed dictionary, a protocol, and generics extend the description language. Structural pattern matching parses data by its shape. Copy and deepcopy make shallow and deep copies.
