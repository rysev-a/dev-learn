#CHAPTER 24 | Generators in depth: send, throw and yield from
Python as a first language. Chapter 24. Generators in depth: send, throw and yield from. In the earlier chapters a generator was a supplier: it hands out values and we collect them. But a function that can pause and then resume from the same place is capable of much more. It can receive values from outside, learn about errors, clean up after itself at the right moment, and delegate work to other generators. All of this turns a generator into a coroutine, and asynchronous programs grew out of exactly this idea. Today we will go through the mechanics, so that asynchronous code does not feel like magic later on.\n\nA generator has a life cycle with four states. Right after you call a generator function, it is created, but not a single line of its body has run yet. After the first request it is running, it pauses at every yield, and once it has finished it is closed. You can find out the state with the get generator state function from the inspect module. The first request has to be an ordinary one: run the body up to the first yield. If you send a value in right away, Python answers with a type error: there is nothing to receive it yet, because the yield expression has not been reached.\n\nNow for the main point. Yield is not only a statement, it is also an expression: it has a value. The send method pushes a value inside: the generator wakes up, the yield expression evaluates to the value that was sent, the code runs on to the next yield, and send returns whatever that next yield handed out. The classic example is a running average. The coroutine waits for a number, adds it to the total, increases the counter and hands out the average. You send numbers one at a time and immediately get the up-to-date average, while the total and the counter live in local variables.\n\nBecause of the first-request rule, every such coroutine has to be primed with a call to next, which runs it up to the first yield. It is very easy to forget this, and then the very first send fails with an error. So in practice people write a small decorator: it creates the generator, makes the first request and returns an object that is already ready. Sending an empty value gives the same result, since it is equivalent to next. The habit of priming a coroutine right when you create it saves you from a whole class of confusion, especially if the program has many coroutines and they are connected in chains.\n\nThe throw method throws an exception into the generator at the point where it is paused, as if a raise statement stood in place of the yield. The generator is free to catch it and carry on, for example to reset a counter or reconnect, and then throw returns the next value that was handed out. If it does not catch it, the exception flies out to the caller. This is how outside code tells a coroutine about special events without inventing special values. Notice the symmetry: next and send move the generator forward with data, throw moves it forward with an error, and in every case control comes back at the next yield.\n\nThe close method ends a generator early. At the point where it is paused, a special exception called generator exit is thrown inside; you do not need to catch it, it simply unwinds the stack, and the finally blocks get a chance to run. That is why cleanup of resources inside a generator is written in a try block with finally. If the generator then tries to hand out a value, a runtime error is raised. On top of that, the garbage collector calls close by itself on forgotten generators, so a file opened inside will get closed, although you should not rely on that: close it explicitly, or use a context manager.\n\nA generator function can have a return statement with a value. It is not handed out in a loop: when the generator finishes, Python raises stop iteration, and the returned value sits in its value attribute. A for loop silently throws this value away, but next and send let you catch it. Why would you want this? A generator can not only produce intermediate results but also sum things up: how many items were processed, what the total is, what came out. The real value of this return shows up in combination with yield from, which we are about to look at.\n\nThe yield from expression delegates work to a nested generator. For a while the outer generator becomes a transparent channel: everything the nested one hands out goes outward, everything sent in from outside through send reaches the nested one, and exceptions and close are passed inside. When the nested generator finishes, the value of its return becomes the value of the whole yield from expression. Without this construct you would have to write a loop and forward sends and errors by hand. The nested object can be any iterable, and then yield from simply hands out its items.\n\nThe most vivid example is a recursive traversal. To flatten nested lists of any depth, the function goes through the items: if an item is a list, it delegates to itself through yield from, otherwise it hands out the item. Strings have to be treated as leaves, otherwise the recursion never ends: a string is made of strings. The same technique works for walking a directory tree or a binary tree from left to right. The code turns out almost as short as the mathematical definition, and memory is used only in proportion to the nesting depth.\n\nIt is convenient to connect coroutines into a pipeline in which data is not pulled but pushed. The source sends values to the first coroutine, a filter, which picks the ones it needs and forwards them to the next, and the last one stores the result or prints it. Each stage is a small generator with an infinite loop that receives a value, does something with it and passes it on. This architecture is reminiscent of a command pipeline in the shell. The usual way to shut down the chain is to close the source first and then the others in order, so that the finally blocks run in the right sequence.\n\nAnother important role is cooperative multitasking. Imagine several generator tasks. A scheduler takes a queue, asks each task in turn for its next step, and if the task has not finished, puts it at the back of the queue. Every yield means: I am ready to give up control. This way a single thread runs many tasks that politely wait for each other without getting in the way. There are no locks and no races, because switching happens only in the places where you yourself wrote a yield. This is almost exactly the model of what the event loop of an asynchronous program does.\n\nNow the continuity makes sense. Once upon a time, asynchronous code in Python was written exactly like this: coroutines built on generators and yield from. Later the words async def and await appeared, coroutines became a separate kind of object, and the old decorator from the asyncio module was removed in version three point eleven. But the principle stayed: await is a pause that hands control back to the scheduler, just like yield from, only stricter and clearer. Once you understand generators, you can read asynchronous code without fear: behind it are the same pauses, sends and thrown errors.\n\nLet us sum up. A generator has four states, and the first request is always next. Send pushes a value into the yield expression, throw throws an exception, close throws generator exit, and cleanup goes in finally. A return with a value ends up in stop iteration, and yield from delegates work to a nested generator and returns its result. Recursive traversals, coroutine pipelines and schedulers are built on this, and in the end asynchronous programs too. Next we will return to functions and take a deeper look at decorators.
