#CHAPTER 46 | Async iterators, generators, and context managers
Python as a first language. Chapter 46. Async iterators, generators, and context managers. In the previous chapters we learned to run coroutines and wait for their results. But many real tasks look like a stream: pages of a server response, lines from a network connection, events from a message broker. Each next item does not arrive right away, and while we wait for it, the program should be busy with other work. The ordinary for loop is helpless here: it blocks. That is why iteration and context managers have asynchronous versions, in which waiting is allowed. In this chapter we will go through them and build pipelines out of them.\n\nLet's start with the protocol. An async iterator is an object with two methods. The dunder aiter method returns the iterator itself, and the dunder anext method is a coroutine whose result is the next value. When there are no more items, anext raises the StopAsyncIteration exception. Such an object is traversed by the async for loop, which on every step awaits anext, and while it waits, hands control back to the event loop. Since Python three point ten there are also the built-in functions aiter and anext, the counterparts of iter and next.\n\nWriting a class with two methods is tedious, so there are async generators. This is a function declared with async def that has a yield inside. Calling it gives you an async iterator, and both await and yield are allowed inside. One caveat: you cannot return a value with return in an async generator, that is a syntax error, but a bare return is allowed. The other rules are familiar: laziness, state kept between requests, finishing when the function ends. If all you need is a stream of values, a generator is almost always simpler than a class.\n\nThe most typical example is paginated loading. The generator asks the server for the first page, yields its items one by one, then asks for the next page, and so on until an empty response. The calling code sees an ordinary async for loop over items and does not think about pages. Memory is spent on only one page, and if the consumer has had enough, it leaves the loop and no extra requests are made. This is laziness at its best, combined with non-blocking waiting: while a page is on its way, the event loop works on other coroutines.\n\nAsync comprehensions let you build lists, dictionaries, and sets from asynchronous sources. Inside the square brackets you can write async for and a condition, and use await inside the expression. The result is an ordinary list. This form works only inside an async function, because waiting is possible only there. Such comprehensions are handy when you need to collect the whole result: for example, to read all the lines or all the items of a stream in a test. But remember: you lose laziness and keep everything in memory.\n\nNow context managers. The async with statement calls the coroutines aenter and aexit on an object. Locks and semaphores from asyncio are asynchronous, because acquiring a lock may have to wait. A task group and a timeout, which we discussed earlier, work the same way, and so do network connections and database transactions. Anything that needs waiting on opening or closing, such as a handshake with a server or confirmation of a write, is described by an async manager. The rules for suppressing exceptions are the same as in the ordinary one: a true value returned from aexit swallows the error.\n\nAs in the synchronous case, you do not always have to write two methods. The async context manager decorator from the contextlib module turns an async generator into a manager: before the yield comes opening, after the yield comes closing, and try with finally guarantees cleanup on error. If you need to open a variable number of resources, async exit stack comes to the rescue: it keeps a stack of managers and closes them in reverse order. This is how you assemble connections that are set up from configuration and make sure nothing is left open after a failure.\n\nCleaning up after async generators needs attention. If you leave an async for loop early, the generator stays suspended, and the finally block inside it does not run right away. It will be closed by the garbage collector or by the event loop at shutdown, but at an unpredictable moment. The right way is to call the aclose coroutine or to wrap the generator in the aclosing manager from contextlib. Then, when the block exits, a GeneratorExit exception is thrown inside, and cleanup happens at once. The asyncio run function closes any remaining generators on its own when it finishes, but you should not count on it.\n\nAsync generators have counterparts of send and throw: asend and athrow. They let you send a value into a yield and throw an error in, just like ordinary generators, but every call must be awaited. In everyday code they are rare: two-way streams are usually built on queues. Still, it is useful to know that the mechanics are the same as the ones we covered in the chapter on coroutines: yield is a stopping point where you can receive a value or an exception, and aclose throws in the signal to finish.\n\nAsync generators connect into pipelines very well. The first one reads the source, the second transforms the values, the third groups them into batches, and the fourth writes them out. Each one sits in an async for chain over the previous one. This gives natural backpressure: the source produces a value only when the consumer has asked for it. If you need real parallelism between the stages, you put a queue between them. Several streams can be merged into one by starting tasks that put items into a shared queue and yielding them from a single generator.\n\nCancellation and timeouts work inside streams too. If you wrap an async for loop in a timeout manager, then when time runs out a cancellation is thrown into the waiting point, the loop is interrupted, and the finally blocks run. The cancellation exception must not be suppressed: it has to propagate outward, otherwise the task cannot be stopped. Catch specific errors, not just any error, and after handling, raise the cancellation further. This preserves the main property of asynchronous programs: any task can be stopped at any waiting point.\n\nTesting async streams is helped by the async test case class from the unittest module. Sources are replaced with fake generators that call asyncio sleep with zero duration: that is enough to hand over control and check the order. You collect the result with a list comprehension and compare it with what you expect. To check cleanup, it is enough to put a record into a list in the finally block and make sure it appears immediately after the exit. No real networks or delays are needed for this, so the tests are fast and stable.\n\nCommon mistakes. Iterating an async iterator with an ordinary for: you get an error saying the object is not iterable. Forgetting await before a coroutine inside an async manager. Returning a value from an async generator. Leaving a loop and not closing the generator. A blocking call inside a stream: it freezes the whole event loop. Suppressing cancellation with a broad exception handler. Let's sum up. An async iterator has aiter and anext and ends with StopAsyncIteration, an async generator is written with async def and yield, and a manager is written with aenter and aexit or with a decorator. Close generators with aclosing, build pipelines, and do not forget about cancellation.
