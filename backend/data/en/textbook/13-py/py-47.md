#CHAPTER 47 | Memory, garbage collection, and weak references
Python as a first language. Chapter 47. Memory, reference counting, garbage collection, and weak references. Python frees us from managing memory by hand: we create objects and do not think about when to delete them. But that does not mean we can skip understanding memory. Leaks in long-running services, unexpected pauses, extra copies of huge data, and oddities with del are all consequences of how memory works in Python. This chapter opens the section about the internals of the language. We will look at the standard implementation, called CPython, and find out how objects live, how they die, and how to keep an eye on them.\n\nLet's start with the essentials. A variable in Python is not a box holding a value, but a name that refers to an object. The objects themselves live in the heap, and each one has a header with its type and a reference count. Assignment copies not the object but a reference to it: two names can point to the same list, and a change made through one is visible through the other. The id function shows the identity of an object, the is operator compares identities, and the equals operator compares contents. Small integers and some strings are cached, so is sometimes gives True for equal numbers, but that is an implementation detail and you cannot rely on it.\n\nReference counting is the first freeing mechanism. Every time a new reference to an object appears, the count goes up: we assigned it to a name, put it in a list, passed it to a function. When a reference disappears, the count goes down: the name was reassigned, the list was deleted, the function returned. As soon as the count reaches zero, the object is destroyed immediately and the memory is returned. That is why in CPython a file that has lost its last reference is closed at once. You can look at the number of references with the getrefcount function from the sys module: it returns one more than you might expect, because the call itself temporarily adds a reference.\n\nBefore an object is destroyed, its del method is called, the finalizer. It is convenient only at first glance. The moment of the call depends on the implementation and on whether references remain; when the interpreter shuts down, the order of destruction is undefined. Exceptions inside del are not passed outward, they are only printed as warnings. The object can even come back to life by saving a reference to itself. So for releasing resources use context managers and explicit closing, and to react to an object's death use weak references and finalize. Leave del for extreme cases.\n\nReference counting cannot cope with cycles. If object a refers to b, and b refers to a, then after the outside names are deleted the counts will not drop to zero: each one holds the other. For such cases there is the cyclic garbage collector, the gc module. It periodically scans the containers that can take part in cycles, finds unreachable groups, and frees them. The collector divides objects into generations: young ones are checked often, old ones less often, because long-lived objects are unlikely to die soon. You can force a collection by calling collect, and you can look at the counters with the get count function.\n\nThe collector starts automatically when the difference between container creations and deletions exceeds a threshold. Sometimes it is turned off for the duration of fast work with a huge number of objects, or before forking a process, but that is a decision for specialists: afterwards you must turn collection back on. Since version three point four, objects with finalizers in cycles are collected too. The collector's implementation changes from version to version, so do not rely on the details of the algorithm, and check the behavior by measuring. The practical takeaway: try not to create needless cycles, but if they do appear, the system will cope.\n\nHow much memory does an object take? The getsizeof function returns the size of the object itself without the nested ones, so for a list it will not count the elements. To see the real picture, use the tracemalloc module: it records which lines of code allocated memory, and lets you compare two snapshots and find the hungriest places. Notice a few features: lists allocate space with a reserve, strings store text compactly, and each small object carries a header. For dense numeric data, arrays from the array module or the NumPy library are better than a list of numbers.\n\nNow weak references. An ordinary reference keeps an object alive, but a weak one does not: the weakref module creates a reference that does not increase the count. Calling a weak reference returns the object if it is still alive, or None if it has already been deleted. This is how caches and registries are built that must not extend the life of objects. Not every type supports weak references: lists, dictionaries, tuples, and numbers do not, while instances of ordinary classes do; classes with slots need a special weakref name added. You can also give a weak reference a function that will be called when the object dies.\n\nReady-made collections are built on weak references. A weak value dictionary stores values weakly: an entry disappears when nobody else refers to the value, and you get a cache without leaks. A weak key dictionary stores keys weakly, so you can attach information to other people's objects without keeping them from dying. A weak set is a set of observed objects. And finalize registers a function that will run when the object dies or when the program exits, and it is more reliable than del: it does not receive the object itself, and therefore does not interfere with its deletion.\n\nLeaks happen in Python even though memory is automatic. The most common kinds are these: global caches and lists that only grow; an lru cache with no size limit; closures and event handlers that hold large objects; exception tracebacks that keep stack frames with all their variables; and subscribers that were forgotten and never unsubscribed. To hunt for a leak, use tracemalloc, compare snapshots, and count objects by type. Leaks are cured by limiting size, using weak references, unsubscribing explicitly, and clearing caches. Remember that growing memory is not always a leak: maybe the program simply holds a lot of data.\n\nCopying is another topic where it is important to understand references. A shallow copy creates a new container with the same nested objects, while a deep copy copies the nested ones too. The copy module provides both operations, and deepcopy can handle cycles by remembering what it has already copied in a dictionary called memo. Your own classes control copying through the copy and deepcopy methods, for example to avoid copying a cache or a connection. A classic trap is a mutable default value: it is created once and shared among all calls of the function, and that too is a question about references.\n\nHow does Python allocate memory for small objects? It has its own allocator for them, which carves blocks out of large areas and reuses freed ones, while large requests go to the system allocator. That is why memory freed inside the program is not always returned to the operating system, and the size of the process after deleting a big structure may not shrink. Practical conclusions: process data as a stream, through generators and iterators; use slots for millions of small objects; and for working with buffers without copying, use memoryview and bytearray.\n\nLet's sum up. Names refer to objects, and objects keep a reference count and are freed when it drops to zero. Cycles are removed by the garbage collector from the gc module. The del method is unreliable: close resources explicitly, and watch for the death of objects with weak references and finalize. For measuring memory there are getsizeof and tracemalloc. Leaks are most often caused by caches and forgotten subscriptions. Copying can be shallow or deep. In the next chapter we will look deeper: at bytecode, the interpreter, the global lock, and a future without it.
