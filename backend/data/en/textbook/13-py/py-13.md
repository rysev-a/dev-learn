#CHAPTER 13 | Classes: methods and properties
Python as a first language. Chapter 13. Classes: methods and properties. You already know how to define a class, create objects and call methods. But the real beauty of Python shows when your own objects start behaving like the built-in ones: you can add them with a plus sign, compare them, sort them, ask them for their length, take an element from them by index. All of this is done with special methods whose names are surrounded by double underscores, and they are called magic, or dunder, methods. Today we'll go through the most useful of them. Then we'll meet properties, a way to turn a method into an ordinary-looking attribute with data validation. And we'll finish with class methods and static methods. After this chapter your classes will start to look like parts of the language itself.\n\nA magic method is called not by you but by Python itself, in response to an operation. When you write a plus b, Python looks for the dunder add method on the object a and calls it with the argument b. So the plus operator is just a nice way of writing a method call. Let's take a vector on a plane as an example: it has two numbers, x and y. The add method takes another vector and returns a new one, adding the coordinates pairwise. After that, vector plus vector works the way we're used to in math. Subtraction, multiplication and division work the same way: every operator has its own magic method. A rule of good manners: an operator method doesn't change the original objects but returns a new one, just as plus does for numbers and strings.\n\nBy default, the double equals sign for objects checks whether it's the same object. Two points with identical coordinates turn out to be different, and that's not what you expect from a point. To compare by value, you define the method eq: it takes another object and returns true if the data matches. There's an important connection here. Objects that can be used as dictionary keys or stored in sets must have a hash, a number computed from the contents. If you define eq and say nothing about hash, Python disables hashing: such an object can no longer be used as a key. To get this ability back, you define the method hash, built from the same data: the hash of a tuple of x and y.\n\nTo make objects sortable, it's enough to teach them to compare with less-than: the method lt returns true if the current object is less than the other one. Then the function sorted and the list method sort can order a list of such objects without any key parameter, and the functions min and max can find the extreme values. You can define the other comparison methods too: le, gt, ge. But writing all four is tedious, and the standard library has a decorator for that, total ordering, which we'll talk about later: it's enough to define eq and one ordering operator, and it builds the rest. An alternative for one-off cases is to sort by a key, giving the key parameter a function that pulls out the needed attribute: there's no need to change the class itself.\n\nNow let's teach our object to pretend to be a container. The method len returns the length, and then the function len works with your object, and an empty object with zero length also counts as false. The method getitem takes an index and returns an element, and then square brackets work: the object, then zero in square brackets. The method contains answers the question of the word in: whether a value is inside. If getitem is defined, Python by default can even iterate over the object with a for loop, pulling indexes in order. The rule is simple: if you want an object to behave like a list, implement the methods you need. For example, a Playlist class keeps a list of songs inside, and shows the outside world its length, its elements by number, and a membership check.\n\nA property is a method that looks like an attribute. Say a rectangle has a width and a height, and the area is computed from them. You can make an area method and call it with parentheses, or you can turn it into a property: put the property decorator above the method, and access it without parentheses, like an ordinary attribute. The area is now always up to date: change the width, and the area is recalculated by itself, because what is stored is not a value but a way to get it. Properties are handy for computed values, and the user doesn't need to know whether the value is stored inside or calculated on the fly. If the class changes tomorrow, the outside code won't have to be rewritten, because the interface stays the same.\n\nA property can also support writing, and that's where it becomes a guardian of your data. The value is conventionally stored in an attribute with an underscore, while access is opened through the property. For writing, you define a second method with the same name and the decorator name dot setter. In it you check the value: an age can't be negative, a temperature can't be below absolute zero. If the value is wrong, you raise an error, and the object stays intact. From outside it all looks like a simple assignment: person dot age equals twenty, but under the hood Python calls the check. If there is no setter, an attempt to assign a value ends in an attribute error: the property is read-only. It's a great way to make immutable fields without extra words.\n\nA class method is a method that receives not the instance but the class itself, and it's defined with the class method decorator. The first parameter is conventionally called cls. The main use is alternative constructors. For example, the class Point has an ordinary constructor from two numbers, and we'll add a class method from string: it takes a string like three comma four, parses it, and returns a new object through cls. Thanks to cls, the method also works for subclasses: it returns an object of exactly the class it was called on. This is how, for instance, creating a date from a string or from a timestamp works in the standard library. The rule: when you need to create an object in a different way than the main constructor, write a class method named like from something.\n\nA static method is an ordinary function that lives inside a class for the sake of order. It receives neither self nor cls, and it's defined with the static method decorator. For example, a class Temperature can have a static method for converting degrees that doesn't depend on any particular object. It's called through the class or through an instance. Why bother, if you can write a function next to the class? To group helper code with what it belongs to and not clutter the global namespace. However, in Python modules are a good enough way to group things, and static methods are needed less often than in other languages. Let's compare the three kinds: an ordinary method knows the object, a class method knows the class, and a static method knows nobody.\n\nOne more topic is underscores in names. One underscore at the start is a convention meaning this is internal, don't touch it from outside; Python forbids nothing, but the readers will take the hint. Two underscores at the start switch on so-called name mangling: Python quietly renames the attribute, adding the class name to it, so that subclasses don't overwrite it by accident. This isn't protection, it's insurance against conflicts. Two underscores on both sides are reserved for magic methods, and you must not invent your own names like that. A lone underscore used as a variable name says that you don't need the value. These small conventions make code predictable for anyone who knows the language, and it's worth getting into the habit of following them from the very first days.\n\nLet's put it all together in one example: a library of books. The class Book stores a title, an author and a year, and can print itself with the str method. The class Library keeps the books in a list, can add a book, search by author, and thanks to the methods len and contains it answers the questions how many books and whether there is such a book. Books are compared by value and sorted by year, so the list can be ordered with a single function. A property lets us get the oldest book. The result is a small but complete piece of a program that reads like a description of the problem domain: nothing extra, just the concepts of the task and the actions on them. That's the style to aim for: code that explains itself.\n\nThe typical mistakes of this chapter. First: you defined the method eq and didn't define hash, and then the object can't be used as a dictionary key. Second: an operator method changes the original object instead of returning a new one. A question to check yourself: what should the method return if it was given an object of another type? There is a special value for that, NotImplemented. Third: a property without a setter, and you still try to assign to it, which gives an attribute error. Fourth, a sneaky one: inside the setter you assign the value to the same name without the underscore, and you get infinite recursion. The value has to be stored in the attribute with the underscore. Fifth: mixing up a class method and an ordinary method, forgetting the decorator or confusing self with cls. Sixth: too much magic. You don't need to implement every method, only the ones you need.\n\nLet's sum up. Magic methods are called by Python itself: add for plus, eq for double equals, lt for less-than, len for length, getitem for square brackets, contains for the word in. If you define eq, define hash too, otherwise the object can't be used as a key. A property turns a method into an attribute, and a setter adds validation of the value. A class method receives cls and is good for alternative constructors, while a static method is an ordinary function inside a class. One underscore means internal, two at the start mean name mangling. Taken together, this lets you build your own types that are indistinguishable from the built-in ones.
