Python as a first language. Chapter 18. Special methods. You have already written quite a few classes, and you may have noticed something odd: built-in functions and operators do not work with your objects on their own. The length function asks an object how many elements it holds. A comparison asks whether two values are equal. Printing asks how the object wants to look. None of this is interpreter magic. It is an agreement: if an object knows how to answer such a question, Python asks it. This set of agreements is called the data model, and this chapter opens a series of four in which we will study it properly.\n\nThe questions are asked through special methods. Their names begin and end with a double underscore, so in conversation they are called dunder methods, from "double underscore". You write such a method, and the interpreter calls it: when you ask for the length of an object, Python finds the length method on the object's type and runs it. Calling it directly is almost always a mistake: write the built-in function, not the method. And an important detail: the lookup goes through the type, not through the object itself, so attaching a method to a single instance is not enough.\n\nLet's start with the birth of an object. When you call a class like a function, Python takes two steps. First the new method creates an empty object and returns it, then the init method fills the object with data. Almost always you write only the second one. The first is needed where an object cannot be changed after creation, as with tuples and strings, or when a class must always return the same instance, as in a singleton. If new returns an object of a different type, init is not called. And init itself must not return anything: no value at all except None.\n\nNow appearance. An object has two text representations. The repr method gives an exact description for the programmer: it should make clear what the object is, and ideally you could paste it into code and get an identical object. The str method gives a nice presentation for the user. Printing and f-strings use str, while the console and the contents of lists show repr. If str is not written, repr is used, but not the other way around, so it is worth always writing repr. And the marker with an exclamation mark and the letter r inside an f-string forces repr specifically.\n\nWhen an f-string has a specification after the colon, say a width or a number of digits, Python calls the format method and passes it that specification as a string. Built-in types understand their own mini-language: for dates these are codes for months and days, for numbers it is precision and number base. Your class can invent its own: for a temperature, for example, one letter gives degrees Celsius and another gives degrees Fahrenheit. By default an empty specification gives the same result as str, and an unknown specification is conventionally rejected with a value error.\n\nAny value can be tested in a condition, and you know that empty collections and zero count as false. This is also an agreement. First Python looks for the bool method and takes its result. If there is no such method, it asks for the length: a zero length means false. If there is no length either, the object is always true. So a basket class only needs a length, while for an account with a balance it is better to write bool explicitly: a zero balance may mean an empty account. The result of bool must be a real boolean value, otherwise you get a type error.\n\nEquality. By default two objects are equal only if they are one and the same object. The eq method changes the rule: two points with the same coordinates can be declared equal. But there is a law: equal objects must have the same hash, otherwise dictionaries and sets break. So as soon as you write eq, Python itself disables hash, and the object becomes unhashable. If you want to put such objects into sets and use them as keys, write hash as well, from the same fields, and do not change those fields after creation.\n\nFor ordering there are six comparison methods: less than, less than or equal, greater than, greater than or equal, equal, and not equal. Writing all six is tedious. The total ordering decorator from the functools module fills in the missing ones if you write equality and one of less than or greater than. There is also an important detail: if your method cannot compare with a foreign type, it should return not an error but the special value NotImplemented. Then Python tries the reflected operation on the second operand, and only after that politely refuses with a type error.\n\nNow attribute access. The getattr method is called only when the ordinary lookup finds the name neither in the object nor in the class. This is handy for proxy objects, dynamic records, and settings, where dictionary keys become attributes. If you cannot find the name either, raise an attribute error, otherwise the hasattr function and copying start to behave strangely. Its relative, getattribute, is called on every access, even to existing names. It is much more dangerous and is rarely needed.\n\nAssigning and deleting attributes can also be intercepted: the setattr method is called on every write with the dot, and delattr on deletion. The trap is that inside you cannot simply write the attribute with the dot: that calls the same method again, and you get infinite recursion. The write is done through the parent class, by calling its method. On these methods people build immutable objects, validation on write, a change log, and protection against typos in names.\n\nHow does Python find special methods? For implicit calls, such as length or addition, it looks straight in the type and does not consult the object itself or getattr. So giving an instance its own length is useless, and a proxy built on getattr will not behave like the original for operators: every method you need has to be written explicitly. On the other hand, the direct lookup is fast, and for built-in types it happens at the level of the C language, without running any Python code.\n\nA few rules of good manners. Do not invent your own names with double underscores: they are reserved for the language and may appear in future versions. Keep behavior expected: equality is symmetric, hash agrees with equality, and repr does not raise exceptions. Do not abuse magic: if an action is surprising, a regular method with a clear name is better. And remember data classes: they generate init, repr, eq, and on request hash and ordering for you. You need to write these methods by hand where the logic is non-standard.\n\nLet's sum up. Special methods are an agreement between your class and the language: functions and operators ask, and the object answers. New and init create an object, repr, str, and format describe it, bool and length determine truthiness, eq and hash define equality, and the six comparison methods define order. Attributes are intercepted by getattr, setattr, and delattr, and implicit calls go through the type. In the next chapter, on this foundation, we will teach objects to add, multiply, and behave like numbers.
