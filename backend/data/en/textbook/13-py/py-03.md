#CHAPTER 3 | Conditions
Python as a first language. Chapter 3. Conditions. Until today your programs were a straight road: commands ran one after another, top to bottom, without a single turn. But real programs make decisions all the time: check a password and decide whether to let the user in, give a discount by age, raise an alarm if the server is overloaded. All of these are forks in the road, and today you will learn to write them. In the discrete mathematics course you have already met the if-then construct: from truth follows truth, and every argument rests on implication. Now this construct becomes executable code: not an abstraction on paper, but a command that Python will carry out for you. After this lesson you will freely read and write programs that choose what to do on their own.\n\nLet's start with the keyword if. After it you write a condition, after the condition you put a colon, and everything that should run when the condition is true is shifted to the right by four spaces. Such a shifted piece is called a block, and it is by the indentation that Python understands which commands belong to the condition. Indentation in Python is not decoration and not a matter of taste, but a part of the language itself: remove it, and you change the meaning of the program. This is how the code shows clearly: here are the commands that run if the condition is true, and here is the place where the block ended and execution goes on always, regardless of the check. In other languages blocks are marked with braces, but Python trusts the structure of the text. Get used to it once, and you will see the boundaries of blocks faster than any braces.\n\nTo write conditions you need comparisons, and here begins the famous beginner's trap. Equality is checked with two equals signs in a row: one sign is assignment, put a value into a variable, and two signs are a question, are the values equal. Say it to yourself: one sign is a command, two signs are a question, and you will never mix them up. Next come not equal, greater than, and less than, as well as the versions with or equal, when a match on the boundary also counts. The result of any comparison is True or False, the very same values from the last chapter. A comparison is a small bridge: on one side numbers and strings, on the other pure logic. And that is exactly why comparisons give us ready-made conditions for our forks.\n\nA fork would be incomplete if we knew only what to do when the condition is true. For the false case there is the word else. After it comes a colon and, of course, an indented block. For example, if the password fits, we let the user into the system, otherwise we show an error message, and both options are described side by side, in one place. A strict guarantee works here: exactly one of the two roads runs, either the upper or the lower, and never both at once. This is precisely the spirit of the law of the excluded middle from logic: true and false exhaust all the options. You can rely on this guarantee when building the whole program: you know for sure that after the fork you are in one of two states. Fewer surprises, fewer bugs.\n\nWhen there are more than two options, elif comes to the rescue, which is short for else if. The chain of checks reads from top to bottom: first the first condition, if it is false the second, then the third, and so on. The first matching check runs, and Python will not even look at all the others: the road is still just one. At the very end it is customary to put else, the general case, where everything that did not fit above lands. And here the order of conditions is the very logic of your program: special cases first, then general ones. If you put the general case first, the special ones will never get their turn, and the code will quietly work wrong. It is like sorting mail: first the important addressees by name, and only then the box for everything else.\n\nConditions can be combined, and for that Python has three words that you know very well from propositional logic. The connective and is true only when both parts are true: the user entered a password, and the password matched. The connective or is true when at least one is true: on weekends or on a holiday the shop is closed. The word not flips the value: did not win means lost. They have different priorities: not binds stronger than and, and and binds stronger than or, but it is more honest to add parentheses and remove all doubt. Remember De Morgan's laws: not of a or b is not a and not b, and symmetrically for and. In discrete mathematics that was theory, and in Python real code is written on these laws every day.\n\nNow a pleasant surprise that many other languages do not have. A check that a number lies within bounds can be written in Python in one line: zero is less than or equal to x, and x is less than or equal to one hundred. This is called a chain of comparisons, and it reads as in school mathematics: x from zero to one hundred inclusive. Joining two checks with the word and is not necessary, although that version also works and means exactly the same. The chain is shorter, clearer, and does not tempt you to mix up the variables. This is how you check an age within allowed limits, a server load percentage, a grade on a scale from one to five. When a comparison looks like in a math textbook, it becomes noticeably harder to make mistakes.\n\nA condition can be placed inside another condition, and this is called nesting. First we check that the user is logged in at all, and only inside that check do we look at whether they are an administrator. It works flawlessly: every new indent is one more floor of the nesting doll, and Python will understand everything correctly. But the nesting doll has a price: the more floors, the harder it is to read the code and keep track of where each block ends. The rule is simple: three floors of nesting is a signal to stop and simplify. Most often the whole construct collapses into a single elif chain or into one condition with the word and. Flat code reads from top to bottom like a story, not like a labyrinth.\n\nWith strings, comparisons follow their own rules. Two strings are equal when they match character by character, and case matters: yes in lowercase and Yes with a capital are different strings, because a capital letter differs from a lowercase one. That is why in real projects user input is usually brought to one case before comparing: otherwise yes, Yes and YES end up as three different answers. And strings also have the membership operator, in code the word in. It answers the question of whether one thing is inside another: the word error is contained in the message connection error, and the operator honestly answers True. It is a handy way to catch keywords in a command, in a log, in a server response. Just remember: membership is not a full match, and a part of a word counts too.\n\nA comparison does not have to live only inside a condition: its result can be saved into a variable. For example, a variable with a telling name receives the result of a comparison: age greater than or equal to eighteen. It is immediately True or False, without any if, and you get a switch that can be passed to another function, saved in a database, or checked later. Such flags are the basis of program state: has the user logged in, has the order been paid, has the form been submitted. Instead of comparing the age again in five places, you compared once and then work with the ready flag. It is customary to phrase a flag name affirmatively: not blocked, but active, so that conditions with it read without double negatives. A small habit, and the code becomes noticeably clearer.\n\nLet's go through typical beginner mistakes so you can recognize them by sight. The first is one equals sign where two are needed: instead of the question are they equal you get an assignment, and the condition works nothing like you intended. The second is a lost indentation: you forgot to shift a line by four spaces, and Python decides the block has already ended, so the program does the wrong thing or honestly reports an error. The third trap is the sneakiest: comparing a number with a string. The string eighteen and the number eighteen are never equal, even if they look the same on screen. Everything that comes from user input is a string, so you first convert it to a number and only then compare. Python does not guess intentions and tells types apart strictly: check types, indentation and equals signs, and half of the classic bugs will no longer be yours.\n\nAnd now a skill that distinguishes a confident developer: reading someone else's code. In front of you is a chain of three checks that gives a grade for a test. If the score is at least ninety, we print excellent; else if it is at least seventy, we print good; else we print needs review. Let's walk through the chain: the first check cuts off the top students, the second catches the solid middle, and else gathers everyone else. Notice that in the second check you do not need to add and less than ninety: the position in the chain already guarantees it, because only those who did not score ninety get there. Say each branch out loud: if the score is ninety or more, excellent, and so on in order. Reading conditions out loud sounds naive, but it honestly catches half of the bugs before the program even runs.\n\nLet's sum up. You have mastered the selection construct: if, elif and else, and now the program can choose the road itself. Comparisons have become questions for you: equality is checked with two equals signs, and magnitudes with greater than, less than and their versions with or equal. Conditions are combined with and, or and not, the direct heirs of propositional logic and De Morgan's laws. Chains of comparisons write bounds in one line, as in school mathematics, and an indent of four spaces is not formatting but real syntax of the language. You saw how to compare strings with case taken into account, check membership, and store the result of a comparison in a flag. Today the program made its first choice for you. In the next chapter we will teach you to assemble code into blocks: functions turn a long script into a program made of clear bricks.
