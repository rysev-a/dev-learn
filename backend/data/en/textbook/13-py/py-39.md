Python as a first language. Chapter 39. Testing. A program that nobody has tested is a program that simply hasn't broken in front of a user yet. Checking code by hand after every change is slow and boring, and above all unreliable: something is sure to be forgotten. Automated tests solve the problem. They are small programs that call your code and compare the result with what you expect. Run them, and in a second you know whether everything is fine. Tests give you the confidence to change code: if something breaks, you see right away what and where. The standard library has two tools for this: unittest, the classic framework for tests, and doctest, which checks the examples in your documentation. Today we'll look at how to write tests, how to check errors and edge cases, how to isolate code from the outside world with stand-in objects, and how to design programs so they're easy to test.\n\nThe simplest test is a function with an assert. You write a function and a couple of checks: assert add of two and three equals five. If everything is fine, nothing happens. If not, the program crashes with an assertion error. That is exactly how your code is checked in the trainer. For small scripts this is enough, but the approach has drawbacks: the first failed check stops everything, so you never learn about the others; there is no overall report; and the tests aren't separated from the code. That's why real projects use dedicated tools. The core idea stays the same: call the code with known inputs and compare the result with the expected one. A good test is small, fast, independent of other tests, and fails only when the code under test is broken.\n\nThe unittest module is the standard framework, which came from other languages. Tests are described in a class that inherits from TestCase. Every method whose name starts with the word test is a separate check. Inside, you use assertion methods: assertEqual compares two values, assertTrue and assertFalse check boolean values, assertIn checks membership, assertIsInstance checks a type, and there are similar checks for collections. To run the tests, add a call to unittest dot main at the end of the file, or run the module with a command from the terminal. The result is a report: how many tests passed, which ones failed, on which line, and with which values. Each test runs independently, so one failure doesn't hide the others. This is fundamentally better than bare asserts.\n\nTestCase has hooks for common actions. The setUp method runs before each test and prepares the environment: it creates an object, a temporary file, some test data. The tearDown method runs after each test and cleans up behind it. There are also variants for the whole class. Thanks to this, tests are independent: each one gets a clean environment. Inside a method you can use subTest, a context manager that runs a check with different data and reports failures separately for each case. You loop over a table of values, and each set is checked on its own instead of stopping at the first one. A table of input and expected-result pairs is one of the handiest forms: to add a case, you just add one line.\n\nYou need to check not only the happy path, but errors too. The assertRaises context manager says that an exception of a given type must be raised inside the block; if it isn't, the test fails. The manager has an exception attribute, so you can check the error message. Edge cases are the main source of hidden bugs: an empty list, zero, a negative number, a very large value, a single record, duplicate elements, the end of a range. A good test suite includes a typical case, boundary values, and invalid input. This skill comes with experience, but you've already learned to apply it: all our exercises contained exactly such checks. Notice how often a solution that looks beautiful falls over on an empty list or on zero.\n\nDoctest turns documentation into a test. In a function's docstring, you write an example the way it would look in the interactive console: three greater-than signs, a call to the function, and on the next line the expected result. Running the doctest module finds such examples, executes them, and compares the output. You get living documentation: if the code changed but the example didn't, the test fails, and the example stops lying. For small pure functions this is the ideal option: the test and the description are in one place. But the method has limits: complex cases and environment setup don't fit into a docstring, and exact output comparison is brittle. So doctest complements unit tests but does not replace them.\n\nTests shouldn't depend on the outside world: the network, the time, random numbers, a real database. Otherwise they are slow, unstable, and can fail for no reason. The unittest dot mock module provides stand-in objects. A mock is an object that pretends to be anything, records how it was called, and returns whatever you configured. The patch decorator or context manager temporarily replaces a real object in a given module with a mock: for example, a function that goes to the network is replaced with a stub that returns a ready-made answer. After the test, the replacement is undone. You can check calls, too: assert called with checks that the function was called with the right arguments. Mocks are a powerful tool, but don't overuse them: a test made entirely of replacements checks the replacements themselves, not your code.\n\nIn the Python world, a third-party framework, pytest, is also popular. It isn't part of the standard library, but many projects use exactly this one. Tests are ordinary functions, checks are ordinary asserts, and when one fails, pytest nicely shows the values on both sides. Fixtures are functions that prepare data and are plugged in by the name of a parameter. Parametrization is a decorator that runs one test over a table of values. It can also run unittest classes, so you can switch gradually. What matters for us is that the principles are the same: small independent tests, clear names, tables of cases, edge values, isolation. Once you've mastered unittest, you'll move to pytest without difficulty when you need it in a project.\n\nTest-driven development is an approach where the test is written before the code. It's a cycle of three steps. Red: we write a test for a new feature and run it, and it fails, because the code isn't there yet. Green: we write the minimal code to make the test pass. Refactor: we tidy the code up without changing its behavior, and the tests confirm that nothing broke. Then we take the next case. This order makes you think first about how the function will be used, and it keeps you from writing anything extra. You don't have to follow it every time, but for tricky logic it's an excellent way to move in small steps. It also gives you a sense of progress: every green test is a small victory. If you can't manage to write a test, that's a signal: the code is too tangled.\n\nWrite code so that it's easy to test. Pure functions are the best candidates: data in, result out, no hidden state. Push everything that talks to the outside world to the edge. A function gets data through parameters instead of reading a file inside itself; it takes the time as a parameter instead of calling the clock; it receives an object for talking to the network instead of creating one. This technique is called dependency injection, and it makes swapping in test versions trivial. Short functions with one job are easier to check. If a test needs ten things set up, the function is most likely doing too much. Testable code also turns out to be well designed: these are two sides of the same coin.\n\nWhat else is worth remembering? Coverage shows which lines of code ran during the tests. It's a useful guide, but not a goal: a hundred percent coverage doesn't guarantee correctness. Random tests with a fixed seed help find unexpected cases: we generate lots of inputs and check properties of the result, for example, after sorting, every element is no greater than the next. This approach is called property-based testing. Tests should be run often, ideally automatically on every change: that's what continuous integration is for. Keep test data next to the tests. And one last thing: a failing test is not an enemy but a friend, one that told you about a problem before a user saw it. Get used to thanking it and fixing the problem right away, rather than switching the test off.\n\nCommon mistakes. First: a test depends on the order of execution or on the results of another test. Second: a test checks too much at once, and when it fails it's unclear why. Third: no checks for edge cases, only the happy path. Fourth: a test depends on time, the network, or randomness, and fails every other run. Fifth: replacements everywhere, so the test checks the replacements themselves. Sixth: the tests are never run, so they go stale. Seventh: fixing a failing test by weakening the check instead of fixing the code. Eighth: testing the internal structure instead of the behavior, so any change breaks dozens of tests. Ninth: long, unmemorable test names instead of a description of the case. One principle helps fix most of these problems: a test should be small, fast, and describe one idea.\n\nLet's sum up. Automated tests call the code and compare the result with an expectation. Asserts are fine for small checks, while unittest gives you classes, assertion methods, setUp and tearDown, subTest, and a report. assertRaises checks errors, and a test suite should include a typical case, edge values, and invalid input. Doctest turns examples in a docstring into checks. Mocks and patch replace the network, the time, and randomness, but shouldn't be overused. Pytest is a popular layer on top with the same principles. Test-driven development follows the cycle red, green, refactor. Code whose dependencies are passed in as parameters and whose logic is pure is easy to test. Congratulations: you've come all the way from your first line to tests for your own programs. Next up are algorithms in Python, and later, asynchrony.
