#CHAPTER 26 | Closures and decorators
Python as a first language. Chapter 26. Closures and decorators. In the last chapter we saw that functions are values, just like numbers. That means a function can not only be passed around, but also created inside another function and returned to the outside. This opens up two powerful techniques. The first is called a closure: an inner function remembers the variables of the outer one, even long after the outer one has finished. The second is decorators: functions that take a function and return an improved version of it, for example one that measures time, checks permissions, or caches results. You've already met decorators, the ones with the at sign above methods: property, class method, context manager. Today we'll see how they work and learn to write our own. It's one of the most elegant and useful features of the language.\n\nA function can be defined inside another function. A nested function is visible only inside the outer one, and it can read the outer function's variables. Python looks up a name along a chain of scopes: first in the function itself, then in the enclosing function, then in the module, then among the built-ins. This rule is known by the first letters of the scopes. Reading the outer function's variables is perfectly fine, but assigning to them is not: an assignment would create a new local variable. If you really need to change an outer name, you write the word nonlocal in front of it inside the nested function. It's similar to global, but it points to the nearest enclosing function rather than to the whole module. You don't need nonlocal often, but you can't do without it in counters and accumulators, which we'll talk about shortly.\n\nNow for the main point. If you return a nested function to the outside, it carries along all the variables of the outer function that it uses. That is a closure. Here's an example: a function make multiplier of n defines an inner function that multiplies its argument by n, and returns it. Calling make multiplier with three returns a function that always multiplies by three. Calling it with five gives a different function that multiplies by five. The outer function has already finished, but the number n stays alive inside the inner one, as if in a capsule. Each call of the factory creates its own independent capsule. This is how you build functions tuned to a task: a greeting with a given name, a check with a given threshold, formatting with a chosen separator.\n\nClosures can hold mutable state. The classic example is a counter: the outer function creates a variable count set to zero, and the nested function declares it nonlocal, adds one, and returns it. Each call of the nested function gives the next number, and every counter you create has its own independent state. You get something like an object with a single method, and indeed classes and closures solve closely related problems. If you need one method and a little state, a closure is shorter. If there are several methods, or the object needs attributes to read, a class is clearer. You can even peek inside a closure: the function has an attribute with the closure cells, and each cell holds a captured value. That's handy for debugging, but ordinary code doesn't touch it.\n\nThere is a well-known trap connected with closures: late binding. An inner function remembers not the value of a variable but the variable itself, and looks up its value at the moment of the call. If you create a list of lambdas in a loop, each using the loop variable, all the lambdas will see its last value: the loop finished long ago, and the variable stayed equal to the last item. The cure is simple: fix the value by passing it as a default parameter, lambda with i equals i, or use partial from functools. Another way is to move the creation of the function into a separate factory: the factory's parameter becomes its own capsule for each value. Remember this effect: it pops up in the most unexpected places, for example when you create handlers in loops.\n\nA decorator is a function that takes a function and returns a new one. The new one usually calls the old one, adding something before or after. Let's write a decorator that measures time: the function timer takes func, defines a wrapper inside, which records the time, calls func, prints the elapsed time and returns the result, and then timer returns that wrapper. You can use it by hand: fast equals timer of slow. But Python offers a shorthand: put an at sign and the decorator's name above the function definition. The line at timer above def means exactly the same as assigning the name the result of calling the decorator. From then on, every call of the function quietly goes through the wrapper. Decorators are closures: the wrapper remembers the original function.\n\nThe wrapper must accept any arguments and return whatever the original function returned, otherwise the decorator will break functions that have parameters and a result. For that, its header says args and kwargs: the stars collect everything that was passed in, and when the original function is called they unpack it back. The typical beginner's mistake is to forget to return the result in the wrapper: the function works, but returns nothing. The second is to forget to return the wrapper itself from the decorator: then the function's name becomes nothing. The decorator template is worth learning by heart: define an inner function with args and kwargs, call the original, do what you need, return the result, and at the end return the inner function. All other decorators are variations on this theme.\n\nA wrapped function loses its name and documentation: a function you defined as compute is now called wrapper, and help shows someone else's description. That gets in the way of debugging and tools. For this case the functools module has a decorator called wraps. You put it above the inner function, passing the original into it: it copies the name, the docstring and other details. It's yet another decorator, applied inside a decorator, and at first it looks clumsy, but you get used to it quickly. A good practice: decorate every decorator you write with wraps. Then error tracebacks, help and testing tools see the real function rather than a faceless wrapper, and life gets noticeably easier for whoever reads your program.\n\nSometimes a decorator needs settings: how many times to repeat, which logging level, how many seconds to wait. Then you add one more level: the outer function takes the settings and returns the decorator itself, and that one takes the function. Three nested functions instead of two. Using it looks like this: at repeat with three above a function definition. First Python calls repeat with three and gets a decorator, then applies it to the function. Such constructions feel unusual at first: keep in mind that the parentheses after the decorator's name mean calling a factory. One example is repeat: the decorator calls the function a given number of times. Another is retry on error: if the function fails, wait and try again until the attempts run out. Things like these are written once and plugged in with a single line.\n\nWhich decorators do you meet in practice? Timing and logging calls are the simplest. Caching results: if the function was called with the same arguments, return the saved answer. Permission checks and authentication in web applications. Retrying on network errors. Checking the types and values of arguments. Registering functions: the decorator puts the function into a dictionary of handlers, which is how routes work in web frameworks. In Python itself the decorators are property, static method and class method, and in the standard library they are lru cache, total ordering, dataclass and context manager. Each of them hides repetitive mechanics, leaving in your code only the essence: what exactly the function does, not how it has to be serviced.\n\nA decorator doesn't have to be a function: it can be any object with a call method, and then an instance of the class is called like a function. A class decorator is handy when you need to keep state: for example, to count how many times a function was called and expose the counter as an attribute. There are also class decorators in the other sense: a function that takes a class and returns the same class, extended with methods. That's how dataclass works, which we'll cover in the standard library. Decorators can be stacked: several at signs one above another are applied from the bottom up, so the one closest to the function runs first. The order matters: a cache on top of timing and timing on top of a cache give different results. For class methods the decorator receives a function with self, so a wrapper with args and kwargs works there too.\n\nCommon mistakes. First: the wrapper doesn't return the original's result. Second: the decorator doesn't return the wrapper. Third: you forgot wraps, and the name got lost. Fourth: you mixed up a decorator without parameters and one with parameters, forgetting the parentheses or adding extra ones. Fifth: lambdas in a loop and late binding. Sixth: mutable state in a closure shared by all calls, when you needed it independent. Seventh: the decorator does too much and hides the function's real behavior from the reader. Eighth: the order of several decorators wasn't thought through. To check a decorator, it helps to call it by hand without the at sign: the function plus a call shows exactly what you are returning. Once the picture is clear in your head, writing them is a pleasure.\n\nLet's sum up. A nested function sees the variables of the outer one, and nonlocal lets it change them. A closure is a function that carried its environment away with it: factories of functions and counters with state are built on it. Late binding makes lambdas in a loop see the variable's last value. A decorator takes a function and returns a wrapper; the at sign is a shorthand. The wrapper accepts args and kwargs and returns the original's result. Wraps from functools keeps the name and the docstring. A decorator with parameters is one more level of nesting. In practice, decorators are used for timing, caches, checks and registration.
