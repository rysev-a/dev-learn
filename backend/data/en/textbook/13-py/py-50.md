#CHAPTER 50 | Packages, environments and uv
Python as a first language. Chapter 50. Packages, virtual environments and uv. So far we have been writing single files. A real program is a project: several modules, dependencies on other people's libraries, tests, settings, a version, and a way to run it. For a project to work somewhere other than your own computer, you need to know how packages are organized, how to isolate dependencies, and how to pin down exactly which library versions you need. In this chapter we will go from a module to a finished project, and meet a modern tool called uv that ties all these steps together.\n\nLet's start with how code is organized. A module is a single file, and a package is a directory of modules. It used to be that every package had to contain an empty file named init, and it is still a good idea: that is where you can gather the public interface. Imports are either absolute, starting from the root of the package, or relative, written with dots. Python looks for modules in a list of directories called sys path: first the directory of the script you ran, then the installed libraries. Running a module as a program with the dash m flag handles packages correctly, and the check of name equals main lets a file be both a library and a program. Circular imports are fixed by moving code around, or by importing inside a function.\n\nA project's structure should be predictable. The recommended option is called the src layout: the root holds the project description file and a directory of tests, while the package itself is tucked away in a subdirectory called src. That way the tests check the installed package, not a random copy in the current directory. The central file is pyproject dot toml. It holds the name, the version, the description, the required Python version, the list of dependencies, the entry points, and the settings of your tools: the linter, the tests, the formatter. One file instead of a scattering of setup dot py, requirements, and setup dot cfg.\n\nDependencies need to be isolated. If you install libraries into the system Python, different projects start to conflict: one needs version two, another needs version three. The solution is called a virtual environment: a separate directory with its own interpreter and its own folder of installed packages. You create it with the command python dash m venv. After you activate it, the pip command installs libraries only there. The environment directory is not added to the repository; instead, the project is described by a dependency file, so anyone can recreate the environment. Never install project libraries into the system interpreter: that is a road to breakage.\n\nuv is a modern project and package manager, written in Rust, that is an order of magnitude faster than the older tools. It replaces several of them at once: creating a project, creating an environment, installing libraries, locking versions, and installing the Python version you need. The command uv init creates a project, uv add adds a dependency and records it in pyproject, uv run runs a command in the right environment, and uv sync recreates the environment from the lock file. This very course is built with uv: the backend is started with uv run. The environment is created and updated automatically along the way.\n\nDependency versions are written as conditions: greater than or equal, less than, equal, and also compatible release, which allows fixes within one branch. The best practice is to set a lower bound and a cautious upper bound: that way you get the fixes, but you are protected from breaking changes. We distinguish direct dependencies, which you chose yourself, from transitive ones, which came along inside them. Controlling everything by hand is impossible, so there is a lock file: it records the exact versions and checksums of all the packages, transitive ones included, and makes the build reproducible.\n\nNot every dependency is needed in production. Libraries for development, such as tests, linters and formatters, go into separate dependency groups that are installed only for developers. Optional features of a library are packaged as extras: when installing, you list the ones you want in square brackets. The required Python version is recorded in the project, and the installer will refuse to install the package into an incompatible interpreter. And uv can even download the right Python version by itself, so you don't need to install a system interpreter for every project.\n\nHow do you share a project? You build a distribution from the directory: a source archive and a wheel. A wheel is a ready-to-install file; it is fast, and it doesn't run anyone else's build code, because everything is already laid out inside. You build with the command uv build. You publish to PyPI, the shared catalog of packages, with uv publish or the twine program, preferably with trusted publishing, which doesn't require storing passwords. Versions follow the rules of semantic versioning: a major version for incompatible changes, a minor version for new features, and a patch for fixes.\n\nA program should be convenient to launch. In the scripts section of the project you describe entry points: the name of a command and the function it calls; once installed, a ready-made command appears in the environment. Command line arguments are parsed with the argparse module, and for more complex interfaces, click and typer are a good fit. Settings that differ between machines are read from environment variables: the database address, the debug mode, access keys. Secrets must never be kept in the code or in the repository, and the file with local values is excluded from version control.\n\nTests, formatting and checks are built into the same project. The settings for pytest, the linter and the type checker live in pyproject, and you run them with uv run pytest. For teamwork, you add pre-commit hooks that automatically format and check the code. And in a continuous integration system you repeat the same commands in a clean environment, on several Python versions. If the project passes them both on your machine and in integration, it doesn't depend on the accidents of your computer.\n\nSupply chain security is a concern of its own. Every dependency is someone else's code that runs on your machine. Check the names: attackers publish packages with typos in popular names. Pin versions and checksums with a lock file, update deliberately, and read the changelog. Use audit tools that compare the installed versions against a database of known vulnerabilities. Don't add a dependency for a single function that is easy to write yourself. And never run unverified install scripts with administrator rights.\n\nDeploying in a container uses the very same pieces. In the image you take a lightweight base with the right Python version, copy in the lock file and the project description, install the dependencies from the frozen lock, and only then copy the code. The order of the layers matters: dependencies change less often than code, so they are cached separately. The program runs as an ordinary user, not as an administrator. That way the built image is reproducible and small, and it runs the same on a laptop and on a server.\n\nLet's sum up. Modules are gathered into packages, and the project is described by pyproject dot toml. Dependencies are isolated in a virtual environment, versions are pinned by a lock file, and development groups are kept apart from production ones. uv combines creating the project, the environment, installing, running and building. Entry points give the program a command, settings come from the environment, and secrets are stored separately. On top of that, the project is checked with tests and a linter in integration, and protected against supply chain risks. In the last chapter we will talk about code quality.
