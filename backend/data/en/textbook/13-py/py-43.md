#CHAPTER 43 | Concurrency: Threads, Processes and the GIL
Python as a first language. Chapter 43. Concurrency: threads, processes and the GIL. So far our programs did one thing at a time: start, wait, move on to the next. But real programs are constantly waiting for something: a server's reply, a read from disk, the user. While one task waits, the processor sits idle, even though it could be working on another. Concurrency is the ability to handle several things at once, or interleaved. This whole section is devoted to it, and we'll begin with the classics: threads and processes. First, an important distinction. Concurrency is organizing several tasks so that they make progress in turns. Parallelism is when tasks really run at the very same moment on different cores. And one more thing: some tasks are bound by the processor, such as calculations, and some are bound by waiting, such as the network and the disk. They need different tools, and learning to tell one kind from the other is the first thing we'll do.\n\nA thread is a separate sequence of execution inside one program. All threads live in the shared memory of the process and see the same variables. The threading module creates a thread like this: the Thread class takes a target parameter, the function to run, and args, its arguments. The start method launches the thread, and the join method waits for it to finish. While the main thread waits on join, the second one works. If you start several threads that each wait for something, for example sleep, all the waits happen at the same time: three threads sleeping one second each take about a second in total, not three. That is the gain from threads: while one waits, the others work. You can find out a thread's name and number through the current thread, which is handy when debugging.\n\nShared memory is the main advantage of threads and the main source of trouble. Suppose two threads each increase one counter a million times. We expect two million, but we get less, and a different number every time. The cause is a race condition: the operation of reading, adding and writing back is not indivisible, and threads can interleave, overwriting each other's changes. The solution is a lock: the Lock object. A thread takes the lock before touching the shared data and releases it afterwards: while the lock is held, the other threads wait their turn. It is best to use the with statement: the lock is released automatically, even if an error happens inside. There are two traps: holding a lock for too long destroys the benefit, and two threads waiting for each other's locks form a deadlock, and the program hangs forever.\n\nSo why don't calculations get faster in Python even with threads? Because of the global interpreter lock, or GIL for short. It is a lock inside Python itself: at any moment only one thread executes bytecode. It protects internal structures from races and simplifies the language, but it means that two threads doing pure computation will not run in parallel on two cores. However, the GIL is released while waiting: when reading from the network, from disk, during sleep. That is why threads are excellent for input and output tasks and useless for calculations. Newer versions of Python have an experimental mode without the GIL, but it has not become the standard yet. The main takeaway: for waiting, use threads; for computing, use processes.\n\nManaging threads by hand is tedious, so the standard library has a convenient module called concurrent futures. The ThreadPoolExecutor class creates a pool of threads and manages them itself. The map method applies a function to all items of a collection in threads and returns the results in the original order. The submit method schedules a single task and returns a future object: its result method waits until it is ready and returns the value, or raises the exception that occurred in the task. The as completed function hands out finished futures as they complete, not in the order they were started. You use the pool with the with statement, and on exit it waits for all tasks. This interface spares you from thinking about starting and waiting for threads by hand: you describe what to do, and you get the results.\n\nFor calculations you need processes. Each process has its own interpreter, its own memory and its own GIL, so on several cores the work really does run in parallel. The multiprocessing module and the ProcessPoolExecutor class from concurrent futures offer the same interface as threads: map and submit. The price of the power is overhead. Starting a process is more expensive than starting a thread. Data is not shared between processes but copied through serialization, so arguments and results must be serializable: lambdas and some objects won't get through. Also, the startup code must be protected with the check that the name equals main: otherwise the child processes will start launching themselves. The gain is noticeable for heavy calculations; for short tasks the overhead eats everything.\n\nThreads need some way to exchange data, and the safe way is a queue. The Queue class from the queue module is thread-safe: it locks access by itself. One thread puts jobs in with the put method, others take them out with the get method, which waits until something new appears. This is how the classic producer and consumer scheme is built: a fast source and slow workers, connected by a queue. The task done method reports that a job has been processed, and join on the queue waits until all of them are handled. To stop the consumers, you put a special sentinel value into the queue, and when they see it, they leave the loop. Queues replace locks wherever threads simply hand data to each other: less shared state means fewer races. For processes there is a queue of their own with the same interface.\n\nBesides the lock, there are other synchronization primitives. An event is a flag you can wait on: a thread calls wait and sleeps until another one calls set. This is how you signal that it's time to stop or that data is ready. A semaphore limits the number of simultaneous participants: for example, no more than five threads download files at the same time. A condition lets you wait for some condition to hold. A barrier makes a group of threads wait for each other at a certain point. Many methods have a timeout parameter: never wait forever, or a hang will turn into an outage. These primitives are building blocks, but most of the time queues and pools are enough. The rule: the less shared mutable data, the simpler and safer the program.\n\nA few more important details. Threads can be background threads: the daemon parameter makes a thread get cut off when the program ends, without waiting for it. Ordinary threads the program does wait for. An exception that occurs in a thread does not reach the main one: it is printed and the thread dies, and you might not even notice. Futures solve the problem: the exception is stored in the object and raised when you read the result. Thread-local data is kept by the threading local object: each thread has its own value under the same name. You cannot interrupt a thread from outside: you can only ask it to finish through an event. These peculiarities explain why managing threads by hand is considered hard, and why pools and queues are the preferred tools.\n\nHow do you choose a model? Question one: what is slow, computation or waiting? If it's waiting, threads or asynchrony are enough. If it's computation, use processes. Question two: how many simultaneous tasks? For dozens, threads are fine; for tens of thousands of simultaneous connections threads are expensive, and asynchrony, which the next two chapters cover, wins. Question three: do you need shared memory? Threads have it, processes don't. For heavy numerical work people often use libraries written in C that release the GIL themselves, and then threads run in parallel. There is no universal answer, but these three questions help you avoid mistakes: most often a thread pool for the network and a process pool for calculations is enough.\n\nYou should judge the effect by measuring. The perf counter function before and after a run will show what you got. A typical picture: a hundred network requests one after another take a hundred seconds, while in a pool of twenty threads they take about five. A calculation in processes on four cores speeds up two or three times, not four: overhead and the part of the work that can't be split. This is described by Amdahl's law: if part of a task cannot be parallelized, it limits the overall gain. And for small tasks concurrency does harm: starting a pool costs more than the work itself. Before making things more complicated, always ask yourself whether the program is really slow and where exactly. Profiling and measurements are friends, guesses are enemies. First make it right, then make it fast, and only where it's needed.\n\nCommon mistakes. First: changing shared data from threads without a lock and getting rare, unreproducible failures. Second: forgetting join, so the program ends before the threads do, or the threads hang around. Third: waiting for a lock that no one will release: a deadlock. Fourth: using threads for calculations and being surprised there is no speedup. Fifth: passing to processes something that can't be serialized, such as lambdas. Sixth: forgetting the main module check when starting processes. Seventh: waiting on a queue with no timeout and no stop signal. Eighth: not noticing exceptions inside threads. Ninth: creating more threads than needed: a thousand threads will eat your memory. Don't try to invent a universal solution: you pick the right tool for the task.\n\nLet's sum up. Concurrency organizes several tasks interleaved, parallelism runs them at the same time. Threads share memory and speed up waiting, but because of the GIL they don't speed up pure computation. Shared data is protected with locks, and it's better to pass it through queues. The thread pool and process pool from concurrent futures give one convenient interface with futures. Processes are used for calculations, at the price of copying data. Events, semaphores and conditions synchronize threads, and timeouts save you from waiting forever. The choice of model is determined by the type of task and the number of simultaneous jobs. In the next chapter, asynchrony: a way to handle thousands of jobs with a single thread.
