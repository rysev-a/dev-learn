#CHAPTER 40 | Abstract classes
Python as a first language. Chapter 40. Abstract classes. Python is famous for duck typing: if an object can quack, we don't care whether it is really a duck. For small programs that is enough. But as a project grows, questions appear. Which methods must an object have to fit this function? What happens if a developer forgets to implement one of them? How do we find out before the program runs, and not three days after the release? Abstract classes answer these questions: they describe a contract, that is, a promise which every subclass has to keep. Today we will see how to write them and when they are worth it.\n\nThe tool is called ABC, short for abstract base class. To make a class abstract, inherit it from ABC, which lives in the abc module, and mark the required methods with the abstractmethod decorator. Now you cannot create an instance of such a class: Python raises a type error and lists the methods that are not implemented. The same happens with a subclass that implemented only some of them. The contract is enforced automatically, and a forgotten method is discovered when the object is created, not when it is used far away from the place of the mistake.\n\nHow does it work under the hood? We studied metaclasses, and ABC is built exactly that way: it has a metaclass called ABCMeta, which, when the class is created, collects the names of the abstract methods into a special set. The check happens when an instance is created: if the set is not empty, creation is rejected. An important consequence: if you forgot to inherit from ABC and simply attached the decorator, nothing happens, and the decorator is silently ignored. So make sure the abstract class is really set up correctly, for example by trying to create an instance in a test.\n\nAn abstract method may have a body. It won't run by itself, but a subclass is free to call it through super, to reuse the shared part and extend it. Not only ordinary methods can be abstract. Properties are made abstract by putting abstractmethod under the property decorator, and class methods and static methods are declared the same way. The order of the decorators matters: property or classmethod goes on top, and abstractmethod sits closest to the function. This way subclasses are forced to define the property, the factory, and everything else that belongs to the contract.\n\nA classic pattern is the template method. The base class contains a ready-made algorithm of several steps and leaves the details of each step abstract. A report is assembled from a header, a body and a footer: the header and footer are shared and already implemented, while the body is different for every kind of report. A subclass implements only the missing steps, and the order of the calls stays the same. This is how frameworks define the life cycle of objects: you write the steps, and they are called in the right order. It is one of the main uses of abstract classes in real projects.\n\nAbstract classes have one more trick: virtual subclasses. The register method declares that a class counts as a subclass without any real inheritance, and an isinstance check will confirm it. This is useful when you need to attach foreign classes to your hierarchy. And the special method subclasshook lets you describe the condition automatically: any class with the right set of methods counts as a subclass. That is how Sized and Iterable work: an object with a length method is already Sized, even though nobody inherited anything. It is duck typing with a check on demand.\n\nThe standard library already has ready-made abstract classes in the collections abc module: sequence, mapping, set, iterable, iterator, callable. You inherit from them, implement a few required methods, and get the rest for free. For a sequence, for example, you need the length and item access by index, and iteration, membership, counting, searching for an index and reverse order appear on their own. The same classes are handy for checks: isinstance with Iterable accepts any iterable object, not just lists.\n\nAnother family of abstract classes is the numeric tower in the numbers module. Number, Real, Rational, Integral: each next one is narrower than the previous. An isinstance check against Integral accepts integers of any kind, including boolean values and numbers from third-party libraries, while a check against int rejects foreign types. If you write a universal function, use abstract classes instead of concrete ones: then it will fit both your types and other people's types. But don't overdo type checks: often it is enough to simply try the operation and handle the error.\n\nAbstract classes are closely tied to the Liskov substitution principle: a subclass must be usable wherever the base class is required. That means it may not demand more than the base class does, and it must promise no less. If the base method accepts any numbers and the subclass rejects negative ones, the program will break unexpectedly. If the base method returns a list, the subclass must not return an empty value. A contract consists not only of method names but also of meaning, and an abstract class is a good place to write this agreement down in the documentation.\n\nIn practice, abstract classes are convenient for defining the interfaces of storages, message senders and payment systems. The base class describes what any storage can do: read and write. Next to it live the implementations: in memory for tests, on disk, in the cloud. The application code takes the base type and doesn't know which implementation it works with, and in tests a simple stand-in is plugged in. This kind of swapping is called dependency injection, and it makes a program flexible: by changing the implementation in one place, you don't touch the rest of the code.\n\nPitfalls. If you leave only pass in an abstract method, a subclass that calls it through super will get an empty value and won't notice the problem. It is better to raise a not-implemented error or to leave a meaningful body. Don't make too many methods abstract: a contract of ten required operations is hard to fulfil. Remember metaclass conflicts when combining with other libraries. And above all, don't turn every class into an abstract one: if there is only one implementation and it won't change, the extra layer only gets in the way.\n\nLet's compare three ways to express a contract. Duck typing is simple, but it is checked only at run time. Abstract classes are checked when an object is created and require inheritance, but they give you shared implementations and isinstance. Protocols, which we will talk about in the next chapter, are checked statically and don't require inheritance. The choice depends on the task: for shared behavior and template methods take an abstract class, for a light description of an interface of foreign types take a protocol, and for small scripts you can get by with ducks.\n\nLet's sum up. An abstract class inherits from ABC and marks the required methods with the abstractmethod decorator: until they are implemented, you cannot create an instance. Properties and factories can be abstract as well. A template method builds an algorithm from shared and abstract steps. Register and subclasshook create virtual subclasses, and the standard abstract classes give you ready-made implementations. Follow the substitution principle and don't create unnecessary layers. In the next chapter we will meet protocols and generics, to describe interfaces without inheritance.
