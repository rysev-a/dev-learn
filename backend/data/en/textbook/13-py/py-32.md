#CHAPTER 32 | ast, eval, exec and dis
Python as a first language. Chapter 32. Code as data: the ast and dis modules. A program's source text is not the last stage: Python turns it into a tree, then into bytecode, and each of these stages can be read and even changed. That opens up possibilities that linters, test frameworks, code generators and safe calculators are built on. In this chapter we will walk the path from a string to the commands of the virtual machine: we will learn to run strings of code, parse them into a tree, walk and modify that tree, and then read the bytecode and understand why a program works the way it does.\n\nLet's start with the simplest and most dangerous tool. The eval function evaluates an expression from a string and returns the result, while exec runs arbitrary statements. You can pass both of them dictionaries of global and local names, and then the code runs in its own namespace without touching yours. Remember the main rule: never execute strings that come from outside. Even with an empty namespace, such code can reach the built-in functions and imports. For parsing safe literals there is the literal eval function from the ast module: it understands numbers, strings, lists, dictionaries, sets and tuples, but not function calls.\n\nBetween a string and its execution stands the compile function. It turns source text into a code object, and it takes a mode: an expression, a module, or a single console statement. A code object can be stored and executed many times without parsing the string again. Inside, it holds constants, names, the number of local variables and the bytes of the instructions themselves. This is how import works: Python reads the file, compiles it, and executes the code object in the module's namespace. The file name in the call is only used for error messages, but it is good practice to always provide it.\n\nParsing a string into a tree is done by the parse function of the ast module. The result is a tree of nodes: a module, a function definition, an assignment, a binary operation, a call, a name, a constant. Each node has fields with child nodes, plus a line number and a column in the source. The dump function prints the tree in a readable, indented form, and it is the best way to study the structure: write a short line of code and see how it was parsed. The expression one plus two times three becomes a binary operation with a multiplication nested on the right: operator precedence is already taken into account.\n\nThere are several ways to walk a tree. The ast walk function goes through all the nodes one after another, while the NodeVisitor class calls a method named visit followed by the node type: each node is handled by its own method. If a method does not call generic visit, the walk does not go deeper. This kind of traversal is used to collect the names of called functions, imports and definitions, and to measure complexity. This is exactly how linters work: they parse a file, look for patterns in the tree and issue warnings without running the program. It is safe and fast, and it lets you check code of any size.\n\nA tree can be modified, not just read. The NodeTransformer class is similar to a visitor, but the visit method returns a new node to replace the old one, or None to delete it. After making changes you need to call fix missing locations so that the new nodes get line numbers, then compile the tree back and run it. The unparse function, which appeared in version three point nine, turns a tree back into text. Automatic refactoring is built on this: renaming variables, replacing deprecated calls, computing constants in advance. An example is rewriting two times three as six.\n\nLet's return to the safe calculator. Instead of eval, parse the expression into a tree and allow only the nodes you understand: numbers, and the unary and binary operations from a fixed list. Any other node, especially a call, an attribute access or a name, raises an error. The evaluation is done recursively, node by node, and under no circumstances can the user run foreign code. This approach is flexible: you can add functions from a whitelist and variables from a dictionary. It is safer than filtering strings, because it relies on the grammar rather than on searching for substrings.\n\nNow the second stage: from the tree to bytecode. Every function has a code attribute, and it holds the bytes of the virtual machine's instructions. The code object itself is immutable, but it has a replace method that creates a copy with some fields changed. A function can be built from a code object by providing a dictionary of globals. This is rarely needed, but it shows that a function in Python is just a wrapper around code: the wrapper holds the default values, the closure, the name and the docstring, and what actually runs is the code object.\n\nYou can read the instructions with the dis module. Calling dis dot dis on a function prints a table: the source line number, the instruction offset, the operation name, the argument and its explanation. Python runs a program on a stack machine: load instructions push values onto the stack, and operations take them from there and push back the result. Adding two parameters turns into two loads, an add operation and a return. The set of instructions changes from version to version, so don't rely on the exact names in production code: the dis module is there to help you understand and explain, not to guarantee compatibility.\n\nWhat can you learn from bytecode? The compiler evaluates constant expressions in advance: two times three becomes six before the program even runs. A membership test against a literal of constants uses a ready-made immutable set. A for loop unfolds into getting an iterator and a loop instruction that jumps back until the iterator is exhausted. Nested functions get separate code objects, and captured variables are loaded from cells. In version three point twelve, list, dictionary and set comprehensions are inlined right into the surrounding function. Reading bytecode helps explain performance and odd behavior.\n\nWhere is this used in real life? Test frameworks rewrite the tree of assertions to show the values of subexpressions when a test fails. Libraries such as data classes and named tuples generate methods as strings and run them through exec. Formatting tools, dead code finders and migration tools between versions all work with the tree. Profilers and code coverage rely on line numbers and code objects. And in domain-specific languages embedded in Python, expressions are built from operators and turned into a tree before they are executed.\n\nSome rules of safety and common sense. Don't execute other people's strings, even supposedly checked ones: any filter can be bypassed. Don't assemble code by gluing strings together where you could build a tree or just use ordinary functions. If you do have to generate code, do it in one place, give it a meaningful file name for error messages, and write tests. Remember that the tree and the bytecode are tied to the interpreter version: relying on the exact names of nodes and instructions in a long-lived project is risky, so stick to the stable part of the interface.\n\nLet's sum up. Eval and exec run strings, but they must never be applied to foreign strings, while literal eval parses only literals. Compile turns text into a code object. Parse builds a tree, a visitor and a transformer read and change it, and unparse brings the text back. A safe calculator allows only known nodes. The dis module shows the commands of the stack machine and explains optimizations. All of these are tools for linters, tests, generators and code transformers. With this we have finished the metaprogramming section, and next we will return to the standard library and new features of the language.
