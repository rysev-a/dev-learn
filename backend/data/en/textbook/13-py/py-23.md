#CHAPTER 23 | Generators
Python as a first language. Chapter 23. Generators. In the last chapter we wrote iterators by hand: a class, two magic methods, a field for the current position, a manual StopIteration. It works, but it is wordy, and every new iterator takes a dozen lines. Python offers a shortcut. An ordinary function in which the word yield appears turns into a generator: Python itself builds a full-fledged iterator out of it, remembers where it stopped, and correctly reports the end. Today we will see how generator functions and generator expressions work, how to build data processing pipelines, how yield from helps, how context managers are built on generators, and which techniques turn up in practice. Generators are one of the most elegant tools in Python, and with them many tasks come out three times shorter.\n\nA function becomes a generator if its body contains the word yield. Instead of return, which hands back a result and ends the function, yield hands back a value and pauses the function, remembering all of its state: the local variables and the position in the code. Calling such a function executes nothing, and returns a generator object. Execution starts only on the first next and runs to the first yield; on the second next it continues from the same place to the next one. The simplest example: a function countdown from n, where a while loop, as long as n is greater than zero, yields n and decreases it. The same countdown that last time required a class now takes four lines and reads like an ordinary loop.\n\nLet's look closely at the order of events. Suppose that inside a generator, before each yield, there is a print with a message. Calling the generator itself prints nothing. The first next prints the first message and returns the first value; the program has returned to the calling code, and the generator sleeps. The second next wakes it up: it prints the second message and hands out the second value. When the body of the function ends, StopIteration is raised, and the for loop quietly exits. This explains laziness: the code inside a generator runs exactly as far as values are requested from it. If you want to get everything at once, wrap it in list. If you want one at a time, go with a loop or call next. The interleaved execution of two programs, the caller and the generator, is the essence of generators.\n\nA generator is an iterator, which means everything from the last chapter works: the for loop, the functions list, sum, and max, the in operator, unpacking. And all its properties are the same: a generator is single-use, and once exhausted it is empty. If you need to go over the result twice, either save it in a list, or call the generator function again and get a fresh generator. Because of this, generator functions are convenient as factories of sequences: each call is a new independent cursor. An interesting consequence: a generator can be interrupted at any moment with break, and the remaining values will not be computed at all, so no work is wasted. By comparison, an ordinary function that returns a list computes everything down to the last element.\n\nGenerators are ideal for infinite sequences. The Fibonacci numbers: two variables, an eternal while True loop, and inside it a yield of a and an update of the pair by swapping values. No class, no StopIteration, and no storing of the whole sequence. To take the first ten numbers, you write a loop with a break, or use a slice from itertools, which we will study later. In the same way it is easy to describe an infinite counter, prime numbers, random data for tests. The main rule still holds: an infinite generator must be limited, otherwise a for loop over it never finishes, and the function list on it uses up all the memory. But by themselves such generators consume nothing: values are born on demand and immediately forgotten.\n\nGenerator expressions are a close sibling of list comprehensions. The notation differs by round brackets instead of square ones: x times x for x in range of a million. The result is not a list, but a lazy generator: the values are not computed until someone asks for them. When the expression is the only argument of a function, you do not need to double the brackets: sum of x times x for x in range of a million. This line computes the sum of squares without creating a huge list in memory. A rule for choosing: if you need a result that is accessed by index or looped over several times, use a list comprehension; if you need to run through it once and fold it into a number or a chain, use a generator expression. For small data there is almost no difference, and for big data it is enormous.\n\nGenerators are convenient to connect into a pipeline. The first one reads the lines of a file and knows nothing about what comes next. The second takes a source of lines and passes on only the non-empty ones. The third takes those and transforms them: strips the spaces, converts to lower case. The fourth counts, or selects by a condition. Each stage is a small generator function or a generator expression, and they are glued together by calling one inside another. The data flows one element at a time through the whole chain, and only a single element occupies memory, so such a pipeline will process a hundred-gigabyte file as neatly as a hundred-kilobyte one. This is a beautiful way to organize code: each function does one simple thing, and the whole picture reads like a diagram of pipes.\n\nInside a generator you can call another generator. Instead of a loop with a yield for every element, you write one thing: yield from and an iterable. All the values of the nested source are handed out in order. An example is flattening nested lists of any depth: the function flat goes over the elements, and if an element is a list, it does yield from flat of it, otherwise it yields the element. This gives you a recursive traversal in five lines. Directory trees, parse trees, and graphs are traversed the same way. Yield from also passes along the values that are sent into the generator, and the returned value of the nested generator, but at the basic level it is enough to remember that it delegates the work to another iterator and spares you a manual loop.\n\nA generator can not only hand out values, but also receive them. The method send pushes a value inside: the yield expression inside the generator becomes a value you can work with. This is how coroutines are written: functions that carry on a conversation with the calling side. A simple example: a generator accumulates an average, gets a new number on each send, and returns the current average. The method close finishes the generator, and the method throw throws an exception into it. In everyday practice send is rarely needed, but the idea is important: it underlies asynchronous programming, where functions pause while they wait for the network or the disk and yield the processor to others. We will come back to it when we reach asynchrony.\n\nGenerators also underlie context managers. In earlier chapters we described a manager with a class that has the methods enter and exit. The module contextlib lets you do the same with a function. You put the decorator contextmanager over a generator function, do the setup inside, then a single yield, then the cleanup. Everything before the yield is the entry into the with block, the value of the yield is what lands in the variable after as, and everything after is the exit. To make the cleanup run even on an error, you wrap the yield in try and finally. You get a compact manager of ten lines instead of a class. For example, a stopwatch, a temporary change of working directory, a lock on a resource. This is one of the most practical techniques, and you will use it all the time.\n\nLet's look at typical tasks. Reading a file in blocks: a function that in a loop reads a portion and yields it, until the portions run out. Cutting a list into batches of n elements: a loop over indexes with a step and a yield of a slice. A sliding window: pairs of neighboring elements, obtained by gluing a list to its shifted copy with zip. Pages of a service response: the generator requests a page, yields its elements, and asks for the next one. Prime numbers: an infinite generator with a divisibility check. In all cases the gain is the same: the consumer does not know how the source is built, and the source does not know why the values are needed. This decoupling makes code flexible, and you will quickly get used to looking in a task for a sequence that is convenient to describe with a generator.\n\nCommon mistakes. First: expecting that calling a generator function will execute something: it only creates a generator. Second: going over a generator twice and getting nothing the second time. Third: returning a list where a lazy stream is needed, and the other way round: turning the result into a list out of habit and losing the benefit. Fourth: forgetting the limit on an infinite generator. Fifth: mixing return with a value and yield: a return inside a generator simply ends it, and the value hides in an attribute of the exception. Sixth: modifying the source while a generator is going over it. Seventh: complicated logic inside a generator expression: if the notation is not readable, rewrite it as a function with yield. The main criterion is clarity, as everywhere in Python.\n\nLet's sum up. The word yield turns a function into a generator: a call creates an object, and execution goes in portions on requests from next, remembering the state. A generator is an iterator: lazy and single-use. Infinite generators are described with an endless loop and limited from outside. A generator expression in round brackets computes lazily and saves memory. Pipelines of generators process huge data one element at a time. Yield from delegates work to a nested iterator and simplifies recursive traversals. Send pushes values into a generator, and the contextmanager decorator builds managers around a single yield.
