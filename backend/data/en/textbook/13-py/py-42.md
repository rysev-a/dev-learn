#CHAPTER 42 | Multiple Inheritance and MRO
Python as a first language. Chapter 42. Multiple inheritance and method resolution order. We are used to a class having one parent. But Python lets you list several: the class gathers its behavior from multiple sources. That freedom is both useful and dangerous. Useful, because you can mix in small abilities: logging, serialization, validation. Dangerous, because questions come up. If two parents have a method with the same name, which one gets called? And what if both parents share a common ancestor? In this chapter we will see how Python answers these questions, and learn to use multiple inheritance safely.\n\nThe answer is called the method resolution order, or M-R-O for short. It is the list of classes Python walks through when it looks up an attribute: it takes the first class in the list where the name is found. You can see it in the class's mro attribute, or by calling the mro method. For an ordinary chain of inheritance the order is obvious: the class itself, its parent, its parent's parent, and finally object. For multiple inheritance the order is computed by a special algorithm, and it guarantees that every class appears exactly once.\n\nLet's look at a diamond. Class A defines a method, classes B and C inherit from A and override it, and class D inherits from B and C. The order for D is: D itself, then B, then C, then A, then object. Notice that A comes after both of its descendants, because you can't look at an ancestor before its children. So a method lookup in D will find B's implementation if there is one. If there isn't, it will find C's, and only then A's. The diamond stops being a problem: the order is always unambiguous.\n\nThe algorithm is called C3 linearization, and it has three rules. A class always comes before its parents. The order in which you listed the parents is preserved. And the order is monotonic: if in one of the parents class X came before Y, then in the final list X comes before Y too. Sometimes these requirements are incompatible, for example if you listed an ancestor before its descendant. Then the class cannot be created: Python raises a type error saying it cannot build a consistent order. That is not a bug, but a safeguard against a tangled hierarchy.\n\nNow let's look at super. Many people think it calls the parent. In fact, super calls the next class in the method resolution order of the object's own type. If you have an object of class D, then super inside B passes control not to A, but to C, because that is the order for D. This is cooperative inheritance: each method does its own part and calls super, so that the chain passes through every class exactly once. If you call the parent by name instead, in a diamond the common ancestor will run twice.\n\nCooperation matters especially in the init method. When several classes in the chain take parameters, each one takes what it needs and passes the rest along using double-star kwargs. At the end of the chain stands object, which takes no arguments: if something unexpected reaches it, a type error is raised. That is why the chain needs a base class that absorbs the extra parameters or checks them. Agree on parameter names and pass them by keyword only: then the order of the classes won't affect how the arguments are parsed.\n\nThe safest form of multiple inheritance is mixin classes. A mixin is a small class with a single ability: logging, converting to JSON, comparing by fields. It has no state of its own, is never used on its own, and is designed to be combined with another class. Mixins go to the left of the main base class: that way their methods come earlier in the order and can wrap the main behavior through super. You can see this in the standard library: the threading mixin for servers handles each request in a separate thread.\n\nDon't forget the alternative: composition. A hierarchy of five parents is harder to read than an object that holds five helpers. Inheritance expresses is-a, composition expresses has-a. If you inherit only to reuse code, not for substitution, it is better to make a field and delegate. But if you need a small addition of behavior for several unrelated classes, a mixin is more convenient. The rule of thumb: inherit from one main class and add mixins, rather than stacking several equal bases.\n\nThere are also technical limitations. If two parents have different memory layouts, for example both define slots, you can't create a subclass, and Python raises a layout conflict error. Attribute names that clash between different parents lead to silent overwrites: one class writes a field, another clobbers it. To protect yourself, names that belong only to the class start with two underscores, and Python mangles them by adding the class name. And the metaclasses of the parents must be compatible: we talked about this in the section on metaprogramming.\n\nHow do you make sense of someone else's hierarchy? Print the resolution order: it shows who comes after whom. The inspect module does the same with the get M-R-O function. In the console, help on a class lists its methods and shows where each one came from. Debug printing at the start of each method, with the class name, shows the order in which they are called. And finding where a name is defined comes down to one question: what is the first class in the order that has this name in its dictionary? A simple check along the list gives the answer.\n\nAbstract classes and protocols fit into the same picture. An abstract class is an ordinary participant in the order, but with the A-B-C-meta metaclass, and that metaclass is inherited. A protocol can be among a class's bases and also takes part in the order. A generic class adds Generic to its bases, and it takes its place in the list. So when you read a complex hierarchy, look at the whole resolution order, not just the class definition line: that shows which classes really take part in the lookup.\n\nCommon mistakes. Calling the parent by name instead of super in a hierarchy with a diamond: the common ancestor runs twice. Expecting super to mean the immediate parent. Forgetting kwargs in a mixin's init method, which breaks the chain. A clash of attribute names. A hierarchy so deep that you can't predict the order. A mixin with its own state, which turns into an ordinary parent. If it is hard for you to say which method will be called, the hierarchy is too complex, and it is time to simplify it or replace it with composition.\n\nLet's sum up. Python looks up an attribute by the method resolution order: it is computed by the C3 algorithm, every class appears once, children come before parents, and the order of the bases is preserved. Super calls the next class in the order, not the parent, and that's why methods must be cooperative, especially init with kwargs. Mixins add small abilities and go on the left. Prefer composition and shallow hierarchies, and check complex cases by printing the order. This concludes the section on class design, and we move on to asynchronous programming.
