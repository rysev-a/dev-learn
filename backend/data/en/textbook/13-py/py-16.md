#CHAPTER 16 | Files
Python as a first language. Chapter 16. Files. Everything we have done so far lived in memory and vanished the moment the program finished. But real programs have to remember things: save results, read settings, process data that was handed to them in advance. That is what files are for. A file is a named sequence of bytes on disk, and what lies inside is decided by convention: a text file holds lines, a photo holds pixel brightness, an archive holds compressed data. Today we will learn to open files for reading and writing, to use the with statement, to read and write text line by line, to deal with encodings, and to catch the typical errors. This is one of the most practical skills there is: most real tasks start with a file one way or another.\n\nA file is opened with the open function. The first argument is the path, the second is the mode. Mode r means reading and is the default; w means writing and wipes the file first; a means appending to the end; x means creating, and it fails if the file already exists. Adding the letter b gives binary mode, and without it the file is treated as text. For text files, always give the encoding explicitly: the encoding parameter set to UTF-8. Open returns a file object, and you work with it through methods. The main rule is that an open file has to be closed, so that the data reaches the disk and the system frees the resource. Doing this by hand is inconvenient and risky, so Python has a more reliable way.\n\nIt is called a context manager, and you write it with the word with. With open, then the path and the mode, then as f. Inside the block the file is open and available under the name f, and when the block ends, normally or because of an error, the file is closed automatically. With this form it is impossible to forget to close the file. The read method returns the entire contents as one string. That is handy for small files and a poor fit for huge ones, because all the information ends up in memory. The habit of writing with instead of closing by hand is one of the signs of good code. The with statement is universal: it is used not only for files but also for locks, network connections, and any resource that has to be released.\n\nWhen a file is big, it is read line by line. A file object knows how to be looped over by the for loop: on each turn you get the next line, and only that one line sits in memory at a time. This is the most common way to process text: for line in f, and then you work with each line. Pay attention to the end of the line: every line, except possibly the last one, ends with a newline character, and you usually remove it with the strip method. The readline method reads a single line, and readlines returns a list of all the lines at once, but it again drags the whole file into memory. For small files it is convenient to take the entire text with the read method and split it with splitlines; for big ones, loop over the file. The choice depends on the size of the data.\n\nYou write with the write method: it takes a string and puts it into the file. An important difference from print: write does not add a newline by itself, so you have to append a backslash n. The writelines method takes a collection of strings, but it does not add newlines either. You can also use print: its file parameter says where to write, and the newline is added for you. Don't forget about the modes. Mode w wipes the old contents at the moment of opening, even if you never write anything afterwards. Mode a appends to the end and suits logs. Only strings can be written: a number first has to be turned into a string with the str function. A typical beginner mistake is trying to write a number directly.\n\nText in a file is stored as bytes, and an encoding decides how characters turn into bytes. Today's standard is UTF-8: it can represent every character in the world, Russian letters included. If a file was created in a different encoding and you open it as UTF-8, you get a decoding error. The fix is to state the right encoding, or to choose an error-handling mode. In binary mode you work with bytes directly: read returns a bytes object, and there is no conversion to text at all. That is how you read pictures, archives, and any non-text data. The bytes type is immutable and looks like a tuple of numbers from zero to two hundred fifty-five, and you can turn it into a string with the decode method, naming the encoding.\n\nAn open file has a position: the place where the next read or write will happen. The tell method reports it, and the seek method moves it: seek to zero takes you back to the start. Once you have read the whole file, you are at the end, and a second read returns an empty string: you need to rewind. You can also read in portions: read with a number returns at most that many characters, and in binary mode, that many bytes. This is how files that do not fit in memory are processed: take a block, process it, take the next one. When writing, data first goes into a buffer and reaches the disk later. Closing the file flushes the buffer, and the flush method does it immediately, for example so that a log is written out before a possible crash of the program.\n\nHow does with work inside? An object that can be used after that word must have two magic methods: enter and exit, each with double underscores on both sides. The first is called on entering the block and returns what lands in the variable after as. The second is called on leaving, including on an error, and it is the one that closes the file. This means with can be used with more than files. You can easily write your own class with these two methods: for example, a stopwatch that notes the time on entry and prints the elapsed time on exit. The contextlib module has a shorter way: the contextmanager decorator turns a generator function into a manager. We will meet it once we cover generators. The main thing is to grasp the idea: with guarantees that the cleanup will happen.\n\nFile operations are one of the main sources of exceptions. The file may not exist: a file not found error. You may lack permissions: a permission error. Instead of a file there may be a folder: an is a directory error. All of these errors inherit from a common ancestor, the OS error, and you can catch them separately or all at once. Wrap the try around open, not around the whole block of work with the file, so you don't catch more than you meant to. A good style is to tell the user which path failed to open and why. Checking in advance whether the file exists and then opening it is less reliable than simply opening it and catching the error: between the check and the opening, the state of the disk could change.\n\nLet's go through typical tasks. Counting the lines in a file: a loop with a counter. Counting words: split each line with the split method and add up the lengths. Finding lines with a given word: a condition inside the loop. Copying a file with processing: open two files in a single with, one for reading and one for writing, and rewrite the lines, changing what you need along the way. Filtering a log by severity level. Counting word frequencies by combining reading a file with the dictionary from the chapter on dictionaries. All of them fit one pattern: open, loop over the lines, do something with each, and it closes by itself. Notice how knowledge from different chapters comes together: loops, strings, dictionaries, exceptions, and files work as one mechanism.\n\nSometimes you need a file for just a minute: an intermediate result, test data. For this there is the tempfile module. It creates a temporary file or folder with a unique name in the system's folder for temporary data, and it cleans up after itself if you use it with the with statement. This is safer than inventing a name by hand: there is no risk of overwriting someone else's file or leaving garbage behind. Temporary files are indispensable in tests: prepare the data, run the code, check the result, and everything disappears. It is also a good way to learn without fear of damaging real data: all the examples from this chapter can be safely run on temporary files. We will get to know tempfile better when we reach the standard library.\n\nTypical mistakes. The first is forgetting to close the file or not using with: the data may not reach the disk. The second is not stating the encoding and getting garbled text or an error on another system. The third is opening a file for writing and wiping something important: mode w does not ask. The fourth is reading a huge file whole with the read method. The fifth is forgetting the newline when writing and gluing everything into one line. The sixth is trying to read after writing without rewinding. The seventh is a relative path: it is counted from the folder you launched from, not from where the script lies, and the file is not found. The eighth is writing a number instead of a string. Most of these mistakes go away within seconds if you remember a couple of habits: with, and an explicit encoding.\n\nLet's sum up. Files are opened with the open function and a mode: r, w, a, x, and the letter b turns on binary mode. For text files, state the UTF-8 encoding. The with statement closes the file automatically, even on an error. Big files are read line by line with a for loop, small ones whole with the read method. Write does not add a newline, mode w wipes the file, and a appends. The position in a file is changed with the seek method. A context manager is an object with the enter and exit methods. File errors are descendants of the OS error, and you catch them around open. Temporary files are created by the tempfile module.
