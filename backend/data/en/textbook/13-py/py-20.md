#CHAPTER 20 | Containers, callables and context managers
Python as a first language. Chapter 20. Containers, callables and context managers. A list, a dictionary, a set, a string: you can do the same things with all of them. You can ask for the length, take an element by index, check membership, and loop over them. These abilities are not tied to particular types. They are described by conventions, just like the operators in the previous chapter. Implement a few special methods, and your class becomes a full-fledged container. In this chapter we will go through the container protocols, then teach objects to be called like functions, and at the end we will add support for the with statement.\n\nLet's start with a sequence. Two methods are enough: the length and getting an item by index. The get-item method receives an index and returns the element, and if there is no such index, it raises an IndexError. This matters: that error is how Python knows where to stop iterating. You get negative indexes for free if you hand the work to an internal list. As a bonus, the for loop, the membership test and the reversed function start working: for an object without its own iterator, Python walks through the indexes in order until it gets an IndexError.\n\nSquare brackets accept more than a number. When you write a slice, the get-item method receives a special slice object with a start, a stop and a step. Its indices method takes a length and gives back ready-made bounds, taking negative values into account. If your container should return the same kind of container for a slice, rather than a bare list, check the type of the key and wrap the result. That is how the built-in types behave: slicing a list gives a list, slicing a string gives a string, slicing a tuple gives a tuple.\n\nA mutable container is completed with the set-item and delete-item methods. The first is called when you assign with square brackets, the second when you delete. Here you are free to add checks: reject keys of the wrong type, limit the range, keep a log of changes. The convention for errors is this: for sequences it is an IndexError, for mappings it is a KeyError. And if your container cannot do something, say, assignment in an immutable one, just don't define the method: Python will report that the object does not support item assignment.\n\nThe in operator checks membership and calls the contains method. If you haven't written it, Python doesn't give up: first it tries to iterate over the object with an iterator, and if there is none, it goes through the indexes. This works, but slowly. For dictionaries and sets the check is fast, because it relies on a hash. So if membership in your class can be checked more cheaply than by iterating, write the method explicitly. For coordinates on a game board, for example, it is enough to check two inequalities rather than walk over all the cells.\n\nThe key in square brackets doesn't have to be a number or a string. Writing a name with two numbers separated by a comma inside the brackets passes the method a tuple of two values, as if you had put parentheses around them. This is how the arrays of the NumPy library and many game boards work. You write a method that unpacks the tuple, checks the bounds, and reaches into an internal list of lists. Going outside the board is usually reported as an IndexError, so that the behavior matches other sequences and iteration over such a board stops correctly.\n\nFor mappings, a key arrives instead of an index, and when it is missing, a KeyError is raised. Implement three methods: getting by key, iterating over keys, and the length, and inherit your class from Mapping in the abstract collections module. Everything else you get for free: keys, values, items, the get method, membership and comparison. For mutable mappings there is MutableMapping, which additionally requires assignment and deletion. This path is more reliable than inheriting from dict, and shorter than writing every operation by hand.\n\nIt is tempting to inherit straight from dict or list and override a couple of methods. Be careful: the built-in types are written in C and often don't call your overrides. For example, updating a dictionary does not go through your set-item method, so it will bypass the check you put there. For such cases the standard library has the wrappers UserDict, UserList and UserString: they are written in Python and honestly call your methods. A special case is the missing method in subclasses of dict: it is called when a key is absent, and defaultdict is built on it.\n\nNow callable objects. The call method turns an instance into something you can call with parentheses, like a function. Why would you need that? An ordinary function remembers nothing between calls, but an object does. A counter, a cache, a multiplier with a configurable factor, a handler with parameters: all of these are convenient to write as a class with a call method. The built-in function callable lets you check whether a value can be called. Functions, classes and methods are called the same way, so code that accepts anything callable will accept your object too.\n\nThe with statement guarantees that setup and cleanup run as a pair. It calls the object's enter method, stores its result under the name after as, and when the block ends, normally or abnormally, it calls the exit method. The exit method receives three values: the exception type, the exception itself and the traceback; if the block finished without errors, all three are empty. If exit returns a true value, the exception is suppressed; otherwise it flies on. Suppress errors carefully, and only the ones you definitely expect.\n\nWriting a class for two methods can be cumbersome. The contextmanager decorator from the contextlib module turns a generator function into a context manager. Everything before the yield runs on entry, the value after yield goes to the name after as, and everything after it runs on exit. To make sure the cleanup happens on an error too, wrap the yield in try with finally. The same module has suppress for suppressing errors, redirect stdout for redirecting output, and ExitStack, which combines several managers into one. You have seen with on files and locks, and now you can do the same.\n\nLet's put it all together with a game board. The class stores a width, a height and cells. It has a length, getting and setting by a tuple of coordinates with bounds checking, a membership check for coordinates, and iteration. The class can be called like a function to get a copy with a different fill, and a context manager rolls back all the changes if an error happens inside the block. Each feature takes a few lines, and each one plugs into familiar syntax. Such code reads like working with built-in types and needs no separate documentation.\n\nLet's sum up. A sequence needs a length and a get-item method that raises an IndexError. Slices arrive as a slice object. Assignment and deletion add the set-item and delete-item methods, and membership is checked by the contains method. Mappings are easier to build on the abstract collection classes than by inheriting from dict. The call method makes an object callable, and enter and exit connect it to the with statement. In the next chapter we will talk about a deeper part of the data model: descriptors, properties and slots.
