#CHAPTER 4 | Functions
Python as a first language. Chapter 4. Functions. So far we have written programs from top to bottom: one command after another, like a recipe on a sheet of paper. But by the second dozen lines, repeated chunks start to appear: the same area calculation, the same password check, the same nicely formatted output. Copying them is a path to bugs: you fix one place and forget the others. The solution is called a function. It is a named block of code: you describe it once and call it as many times as you need. You have been using ready-made functions for a long time: print, len, type, int. Today we learn to write our own. You have already seen the word def in the exercises, and now we will see how it all works inside. Functions are the main tool that turns a long script into a program built from clear bricks.\n\nA function is defined with the word def, short for define. After it comes the name of the function, a pair of empty parentheses and a colon, and then the body: lines indented by four spaces. For example: def hello, parentheses, colon, and in the body a print command with a greeting. Here is a moment where beginners often stumble: the definition itself executes nothing. Python simply remembers that under the name hello there is hidden such-and-such code. To make the code run, you have to call the function: write its name and parentheses. Every call runs the body again. Three calls, three greetings, and the code is written only once. And one more thing, the order: you must define a function before you call it, otherwise Python will say it does not know that name.\n\nA function that always does the same thing is not very useful. Real power comes with parameters: these are the names in parentheses after the function name, through which data is passed in. Define hello with a parameter name: inside the body, name is an ordinary variable. When you call hello with the string Anya, that string becomes the value of the parameter name, and the function greets exactly Anya. The difference between the terms is simple: a parameter is the name in the function definition, and an argument is the actual value at the call. There can be several parameters, separated by commas, and at the call the values are matched in order: the first value goes to the first parameter, the second to the second. This way one function serves a thousand different cases.\n\nSo far our functions only printed. But more often a function should not show a result but return it, so that it can be used further. For that there is the return command. Define square of x: return x times x. Now the call square of five is an expression with a value, twenty five: you can put it in a variable, print it, use it in a calculation, or pass it to another function. Here hides the most common confusion. Print shows a value on the screen, and then it disappears. Return hands the value to the calling code. If a function has no return, it returns a special value meaning nothing, called None. Remember the difference: print is for the human, return is for the program.\n\nReturn does not just hand over a value, it also ends the function immediately: whatever is written after it will not run. This is handy for early exits. For example, a function that gives the sign of a number: if x is greater than zero, return positive; if less, return negative; otherwise return zero. The conditions from the previous chapter live perfectly well inside functions, and every branch ends with its own return. An important rule: on every path of execution, the function must return something. If some branch forgets its return, the calling code gets None and will crash in an unexpected place. A good habit: after writing a function, mentally walk through all the branches and ask yourself what each of them returns.\n\nOften a parameter has a sensible everyday value, and then you specify it right in the definition: define power of x and n, where n equals two. Now power of five returns twenty five, because n takes its default, and power of five and three returns one hundred twenty five. Parameters with defaults must come after the regular ones, otherwise Python cannot tell which value belongs to whom. There is a second way to pass an argument: by name. Power of five, n equals three. When there are many parameters, the name makes the call readable, because from the values alone you cannot tell which is which. Keyword arguments can be passed in any order. Many built-in Python functions work this way, for example print with its end parameter.\n\nAn important topic is scope. Variables created inside a function live only inside it: these are local variables. When the function finishes, they disappear, and you cannot reach them from outside. Parameters are local too. The reverse is not true: a function can read variables declared outside, but as soon as you assign a value to such a name inside, Python creates a new, local variable with the same name and leaves the outer one untouched. The error about a local variable being used before assignment is exactly about this. There is a global command that lets you change an outer name, but in practice it is avoided: a function that receives data through parameters and returns the answer through return is clear and predictable, while a function that edits outer variables is a source of mysterious bugs.\n\nUnder the function header it is customary to write a short description in triple quotes: what the function does, what parameters it takes and what it returns. This is called a docstring, a documentation string. It does not affect how the code works, but it makes the code explain itself: the built-in help for a function shows exactly that text, and editors display it as you type. Next to the docstring, good names matter. A function is named with a verb or with an answer to a question: compute the total, is even. A one-letter name, or something like function one, tells the reader nothing. Another rule: one function, one task. If you have to build the description of a function with the words and, as well as, and while we are at it, you should most likely split it in two.\n\nFunctions call other functions, and that is how big programs are built. Suppose we need to find out whether a year is a leap year. One small function checks divisibility by a given number, and another uses it three times: for four, for one hundred, and for four hundred. Each brick can be checked separately, and the overall logic reads like a sentence. This is called decomposition: you cut a big task into small ones until each becomes obvious. Notice that the order in which functions are defined does not matter, as long as the call happens after all the definitions have been read. Functions are the basis of any design: a good program looks like the table of contents of a book, where each chapter briefly and clearly names its task.\n\nA function can call itself, and this is called recursion. The classic example is the factorial: the factorial of zero equals one, and the factorial of n equals n times the factorial of n minus one. In code it is a function with two branches. The first is the base case: if n equals zero, return one. Without it, recursion would never stop. The second is the step: return n times a call of the same function with a smaller argument. Each call postpones its multiplication until the deepest one returns one, and then the answers come back along the chain. Recursion has a depth limit, and with numbers that are too big Python will stop the program. But for problems that themselves consist of similar subproblems, it gives short and elegant solutions.\n\nHow can you make sure a function works? The simplest way is checks right in the code, with the assert command, which means I claim. Assert followed by an expression: if it is true, nothing happens, and if it is false, the program stops with an error. For example, assert that square of three equals nine. A couple of such lines under the function, and you instantly learn what broke after an edit. Check not only typical values but also edge cases: zero, negative numbers, the empty string. This is exactly how the checks in our trainer work: your function is called with a set of arguments, and the result is compared with the expected one. The habit of writing checks is one of the most valuable things you will take away from this course, because it separates programmers who are trusted from the rest.\n\nLet us collect the typical mistakes. The first: a call without parentheses. The name of a function without parentheses is the function itself as an object, not its result, and print will show a strange representation. The second: a forgotten return, giving None instead of an answer. The third: mixing up print and return, where the function printed the result but did not return it, and it cannot be used further. The fourth: the wrong order of arguments, especially in functions with several parameters of the same type. The fifth: editing an outer variable inside a function and getting an unexpected local variable error. The sixth: calling a function before its definition. And the seventh, a global one: a function that does too much. If you need the word and to describe it, split it. Most of these are caught in a minute by reading the code aloud.\n\nLet us sum up. A function is defined with the word def, a name, parameters in parentheses and an indented body; the definition itself executes nothing, and the code runs at the call. Parameters accept data, return gives back the result and ends the function, and without it you get None. Print shows, return hands over. Parameters can have default values, and arguments can be passed by name. Local variables live only inside the function, and data is best passed through parameters. A docstring and good names make code readable, and small functions call each other. Recursion needs a base case, and assert checks the result. And now that we have blocks of code, it is time to teach the program to repeat actions: in the next chapter, loops.
