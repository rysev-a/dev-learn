#CHAPTER 15 | Exceptions
Python as a first language. Chapter 15. Exceptions. Errors in programs are inevitable, and it is not because of bad programmers. A user types a letter where a number was expected. A file that was on the disk yesterday has vanished today. A server does not answer, and the network drops halfway through. A program that crashes at every surprise is only good for a textbook. A real program anticipates failures and copes with them: it reports a clear reason, tries again, rolls back what it started, instead of falling apart with a cryptic traceback. Python has a mechanism for this, called exceptions. Today we will see how to read error messages, how to catch exceptions, how to raise your own, how to create your own error types, and how not to turn error handling into a way of hiding problems.\n\nWhen a program crashes, Python prints a traceback. You read it from the bottom up. The very last line holds the error type and the message: value error, type error, key error, index error, division by zero, unknown name, no such attribute. Above it is the chain of calls: the file, the line number, and the line itself where it all happened, and higher up, where it was called from. The line that matters most to you almost always sits at the end of the chain. The error type is a hint: an index error says you went outside the bounds of a list, a key error says the dictionary has no such key, and a type error says the operation does not apply to that kind of value. Once you learn to read the traceback, you will fix half of your errors in a minute.\n\nExceptions are caught with the try and except construct. You put the code that might fail in the try block, and in the except block, with the name of an error, what to do when that failure happens. For example, the user enters a number: we try to convert the string to an integer with the int function, then in except we catch the value error and print: that is not a number. The program does not crash and goes on. It is important to catch a specific error type: that way you react exactly to the situation you anticipated, while all the other, unexpected ones will still announce themselves loudly. The try block should be as short as possible: only the lines that can really fail, so you do not catch something extra by accident.\n\nOne try can have several excepts: one for each situation. Python checks them from top to bottom and runs the first one that fits. You can list several types in parentheses if the reaction is the same. To get hold of the error itself, you write except, the type, as, and a name: the variable holds the exception object, and you can print its message or look at the details. There is a temptation to write except with no type, to catch everything at once. Do not do that: a bare except even catches the keyboard interrupt and hides the programmer's real mistakes. If you need to catch almost everything, write except Exception: that is the base class of ordinary errors, and system signals stay untouched.\n\nA try has two more optional parts. The else block runs only if there was no exception: it is a handy place for code that depends on success but should not catch its own errors. The finally block runs always: on success, on error, and even if there was a return or a break out of a loop inside. It is meant for cleanup: closing a file, releasing a resource, writing the outcome to a log. The order is this: try, then except, then else, then finally. When you need only cleanup and no catching, you write try and finally without except: the error flies on, but the cleanup still gets done. Later we will see that for files the with statement makes this even simpler.\n\nYou can raise exceptions yourself with the raise command. Raise a value error with a message stops the function just the way the built-in checks do. A typical case is guarding input data: a function gets a negative age and reports it, instead of carrying on with garbage. The rule is this: raise the error as early and as precisely as possible. You write the message for the person who will be figuring it out: what happened and what value came in. If you caught an error in except but decided that it cannot be handled here, just write raise with no arguments: the exception flies on, keeping its whole traceback. There is no shame in raising errors: it is an honest way of saying that the conditions were not met.\n\nBuilt-in types are often not enough to tell situations apart in your own problem domain. Then you create your own exceptions: an ordinary class that inherits from Exception. It is enough to define a class with a name and the pass statement. For example, insufficient funds, bad file format, user not found. Now the calling code can tell exactly this error from the others: except insufficient funds. A good practice is to create a common base class for all the errors of your library and make the specific ones its subclasses: then you can catch either a specific situation or the whole family at once. You can add attributes to your own class, for example the amount that was missing, and use them in handling. Names usually end with the word error.\n\nExceptions form a class hierarchy. At the top is the base exception, under it Exception, and under that all the ordinary errors. Arithmetic errors, division by zero and overflow, share a common ancestor. Lookup errors, key error and index error, also have a common ancestor. So if you catch the common ancestor, you catch all its descendants, and if you catch a specific descendant, you do not touch the other relatives. From the hierarchy follows the rule for the order of excepts: the more specific first, the general ones after, otherwise the general one will catch everything and the specific one will never get its turn. System exceptions such as the keyboard interrupt stand apart from Exception, and ordinary handlers do not touch them. That is by design.\n\nPythonistas have a motto: easier to ask forgiveness than permission. It means: instead of long checks before an action, perform the action itself and catch the error if it happens. A classic example is reading a value from a dictionary. You can check for the key with the in operator, or you can just do the read and catch the key error. For files this style is indispensable: between checking that a file exists and opening it, someone could delete it, while trying to open it and catching the error is reliable. But the style has a cost: exceptions are slower than ordinary checks if they happen all the time. So if a missing key is a normal, frequent situation, use the get method; if it is rare and alarming, use an exception. Choose by meaning, not by habit.\n\nSometimes you need to catch an error and turn it into another, clearer one. For that there is the construct raise new error from old error: Python keeps the old one in the chain, and the traceback shows both. For example, while parsing settings you caught a key error and raised a configuration error with a clear message, and the original cause stayed in the cause attribute. If you leave out from, Python still remembers the context: it will show that the second error happened while handling the first. Chains exist so that you do not lose information. The main thing to remember: a handler must not swallow an error silently. Either you fixed it and moved on, or you reported it and raised it further, or you turned it into a clearer one, but you did not hide it.\n\nThe assert statement, familiar to us from the function checks, is also tied to exceptions: if the condition is false, an assertion error is raised. But assert is meant for different jobs than raise. It checks the programmer's own internal assumptions: at this point the list cannot be empty. You must not check data from a user or from a file with assert, because when Python runs with optimization, all asserts are turned off and your protection disappears. To check input data, use raise with a real exception. For checking invariants that must hold if the code is written correctly, assert is the right tool: in production it costs nothing, and during development it catches logic errors. A short rule: assert is for the programmer's mistakes, raise is for the mistakes of users and the environment.\n\nLet us collect the typical mistakes. The first is a bare except without a type, which hides everything. The second is a try block that is too wide, fifty lines long, so it is unclear what exactly failed. The third is swallowing: an except with only pass inside, and the error vanishes without a trace. The fourth is losing the traceback: after except, you wrote raise with a new object instead of a bare raise, and the real place of the error was lost. The fifth is a return inside finally, which silently cancels the exception. The sixth is using exceptions for ordinary flow control in a hot loop, where a simple check would do. The seventh is validating user data with assert. A good rule: catch only what you know how to handle, and let the program crash loudly, with a traceback, on everything else.\n\nLet us sum up. An exception is a mechanism that lets a program survive a failure. You read the traceback from the bottom up: the error type and message are in the last line. The try block wraps dangerous code, except catches specific types, as gives access to the error, else runs when nothing failed, and finally always runs. Raise throws an exception, and a bare raise passes it on. Custom exceptions are classes that inherit from Exception. The hierarchy determines the order of excepts: specific ones first. Raise from builds a chain of causes. Assert is for internal assumptions, and raise is for validating input data. Catch only what you know how to handle. In the next chapter we cover files: the most common place where such failures happen.
