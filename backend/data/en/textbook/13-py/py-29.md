#CHAPTER 29 | Decorators in depth
Python as a first language. Chapter 29. Decorators in depth. You already know how to write a simple decorator: a function that takes a function and returns a wrapper. But in real projects decorators are everywhere and are more intricate: they are stacked on top of each other, configured with parameters, applied to methods and to whole classes, made asynchronous, and turned into classes. This chapter begins the section on metaprogramming: code that works with code. Decorators are its gentlest form, and they are worth understanding thoroughly before we move on to metaclasses and syntax trees.\n\nLet's start with the order. Writing two decorators in a row means nested application: first the lower one wraps the function, then the upper one wraps the result. So when you call the function, the upper one fires first, while the lower one sits closer to the original function. If the decorators add markup, say bold and italic, the order decides which tag ends up on the outside. Remember a simple rule: it is read from top to bottom, and applied from bottom to top. This small detail explains a great many strange bugs, especially when one decorator checks permissions and another caches the result.\n\nOften you want one decorator to work both without parentheses and with parameters: both plain repeat and repeat three times. A common trick is to make the decorator's first argument a function with a default value of None, and to accept the settings by keyword only. If a function was passed, the decorator wraps it right away; if not, it returns the real decorator, which will wait for the function. Many libraries are written this way. The only danger is confusing when the first argument is a function and when it is a setting, which is why settings are conventionally made keyword-only.\n\nMethods are decorated the same way as functions, because at the moment of definition a method is an ordinary function, and self passes through the wrapper as the first argument along with the rest. The subtlety is the order with classmethod, staticmethod, and property: these decorators create descriptors and must be placed on top, otherwise your wrapper will receive a descriptor instead of a function and break. So your own decorator always goes below them. Also remember that the wrapper doesn't know in advance whether it is wrapping a method or a function, so it accepts any arguments.\n\nA decorator can be applied not to a function but to a class. Such a decorator receives the finished class, and it can modify it or return a different one. The most common jobs are registering the class in a shared registry, adding methods, checking for required attributes, and replacing the class with a singleton. A dataclass is exactly such a decorator: it uses the annotations to build the initializer, representation, and comparison methods. If you don't need to control the process of creating the class itself, a class decorator is simpler and clearer than a metaclass: it is applied after the class already exists.\n\nA wrapper hides the original: it has a different name, a different docstring, and a different signature. The wraps decorator from the functools module copies the name, the documentation, and the module, and, most importantly, adds an attribute that links to the original function. Thanks to that link, inspect.signature shows the real parameters, instead of a faceless star args and star star kwargs, and help in the console stays useful. For subtle cases there is the function update_wrapper, which wraps itself relies on. The habit of always writing wraps is what separates careful code from sloppy code.\n\nA decorator often needs state: how many times it was called, when it was last called, what has already been computed. The simplest way to keep it is an attribute of the wrapper function itself: the call counter is then available from outside. If there is a lot of state, you make the decorator a class with a call method: the object stores the data and is itself called. But such a wrapper has a catch: an instance of a class does not turn into a method automatically. For a class decorator to work on methods, it needs the get method from the descriptor protocol, which supplies the instance, the way functions do.\n\nAsynchronous functions need special attention. If an ordinary wrapper calls an async function, it gets a coroutine that nobody ran and nobody awaited, and the timing or the retry will be counted wrongly. So async functions need an async wrapper that awaits the result. A universal decorator determines the kind of function by checking inspect.iscoroutinefunction and picks the right wrapper. This is one of the most common sources of silent errors in modern code, so check the async case with a separate test.\n\nA special class of decorators doesn't wrap the function at all, it only remembers it. This is how the routes of web frameworks work: the decorator takes an address, records the function in a table, and returns it unchanged. The same goes for registering event handlers, console commands, plugins, and tests. The function remains callable as usual, and the table is filled at the moment the module is imported. A consequence follows: such decorators fire at definition time, not at call time, and the module that contains them must be imported, otherwise the handler will not be registered.\n\nLet's look at some practical examples. Retrying after a temporary error with a growing pause between attempts. Measuring the time of a call. Checking permissions before running. Warning about a deprecated function through the warnings module. Checking arguments against annotations: the decorator takes the signature, binds the call to it, and checks the types. Caching through lru_cache with information about hits. Each of them takes about ten lines and removes duplication from dozens of functions, leaving only the essence in the functions themselves.\n\nThe signature of a decorated function matters for typing too: type-checking tools need to know that the wrapper accepts the same arguments as the original. For that, the typing module has ParamSpec and Concatenate, which describe somebody else's signature. For now it is enough to know that the idea exists: a decorator must not break type hints. If you write a library, annotate your decorators carefully, so that editors keep suggesting parameters to your users instead of showing a faceless wrapper.\n\nCommon mistakes. Forgetting to return the original's result from the wrapper. Forgetting to return the wrapper itself from the decorator, so that the function turns into None. Forgetting wraps. Changing a shared mutable default parameter. Writing code with side effects at the decorator level and being surprised that it runs at import time. Putting the decorator in the wrong order relative to classmethod. And finally, writing a far too clever decorator where an ordinary function would do: if the logic isn't repeated, you don't need a decorator.\n\nLet's sum up. Several decorators are applied from the bottom up. A decorator that works both with and without parentheses takes the function as an optional argument and the settings by keyword only. Methods are wrapped like functions, while classmethod, staticmethod, and property are placed on top. A class decorator receives the finished class. Always use wraps, for state keep attributes or a class with the get method, for async functions make an async wrapper, and have registering decorators return the function unchanged. In the next chapter we will look inside objects with the help of introspection.
