#CHAPTER 51 | Code quality and design patterns
Python as a first language. Chapter 51. Code quality: style, tests, design patterns. Code is read far more often than it is written, and changed more often than it is read. So good code is not just code that works, but code that is clearly organized, covered by tests, and safe to change. Quality is not created by heroic effort at the end: it builds up from small habits and automatic checks that run on every change. In this last chapter we will gather those habits: style and checks, tests, documentation, error handling, design principles and patterns, and also how to safely improve existing code.\n\nLet's start with style. Python has a standard called PEP eight: lowercase names with underscores for functions and variables, class names starting with a capital letter, four spaces for indentation, and a sensible line length. But you don't need to argue about commas and quotes: formatters like black and the formatting mode of ruff do it automatically, and the same way for the whole team. The ruff linter finds unused imports, undefined names, dangerous constructs and outdated calls in a fraction of a second. Connect both to pre-commit hooks and to continuous integration, and talk about style disappears from your discussions.\n\nType hints, which we covered earlier, are also part of quality. A type checker catches a whole class of errors before you run anything: passing the wrong type, accessing a field of an empty value, a forgotten result. Run it together with the linter and the tests, and raise its strictness gradually. Types document your intent better than comments, because they are checked automatically. A good rule of thumb: the public functions of a library and the boundaries between modules should always be annotated, while for small internal functions annotations are a matter of taste.\n\nTests are the main way to trust your code. The de facto standard is pytest: a test is an ordinary function, a check is an ordinary assert, and when it fails the message shows the values of the subexpressions. A test has three parts: arrange, act, assert. Fixtures build shared data, and parametrization runs one test over a table of inputs, which removes copy and paste. Coverage shows which lines were executed, but it does not prove correctness: one hundred percent coverage without checks is useless. Aim for the important scenarios and the edge cases, not for a number.\n\nA good test checks behavior, not internal structure. If renaming a private function breaks ten tests, they are tied to the implementation and get in the way of the code's development. A test must be deterministic: time, randomness, the network and the file system are replaced with substitutes, otherwise the test will be flaky. For substitution there is the mock from unittest: it records calls, and you can check that an external service was called with the right arguments. The idea of property-based tests takes this further: instead of individual examples, you check a general property over many random inputs, for example that sorting does not lose any elements.\n\nDocumentation is part of the code. Docstrings describe a function's purpose, parameters, result and errors, and the doctest module can check the examples in them, so an outdated example turns into a failing test. In the README file you write what the project does and how to install and run it, and in the changelog what changed between versions. Don't retell in comments what is already visible from the code: a comment should explain why, not what. The most valuable comment is the one that warns about a non-obvious limitation or the reason for a strange decision.\n\nError handling and logging. Don't swallow exceptions silently, and don't catch everything indiscriminately. Create your own exception hierarchy for the application: a base class for application errors and subclasses for specific situations, so that the calling code can catch the group it needs. Instead of print, use the logging module: levels, formats, handlers, and the ability to turn detail on and off without editing the code. A log message should say what happened and with what data, but must not contain secrets. Log at the boundaries: the arrival of a request, calls to external services, unexpected situations.\n\nDesign principles help you write code that is easy to change. The single responsibility principle: a function or class has one reason to change. The dependency inversion principle: high-level modules depend on interfaces, not on concrete implementations, and we saw this with protocols. Prefer composition to inheritance, and pure functions with no side effects to functions that depend on global state. Don't repeat yourself, but don't invent a general solution before it is needed: two similar functions are better than a premature abstraction. A simple solution that works today is almost always better than a complicated one built for the future.\n\nDesign patterns in Python are often shorter than in other languages, because the language provides ready-made tools. A strategy is simply a function passed as a parameter. A factory is a function or a class method that creates an object. A singleton is an ordinary module-level object. An observer is a list of callback functions. An adapter is a small wrapper that makes someone else's interface fit the one you need. The iterator and the context manager are built into the language, and the decorator exists as syntax. Dependency injection is passing the objects you need in as parameters. Knowing the patterns is useful above all as a shared vocabulary for talking with colleagues.\n\nPython idioms make code shorter and clearer. Unpacking instead of indexes. Looping with enumerate and zip instead of index loops. Comprehensions instead of manual accumulation. Context managers for resources. The pathlib module instead of gluing paths together. F-strings instead of adding strings. Checking for the empty value with is, not with equality. The principle of easier to ask forgiveness than permission: try to perform the action and handle the exception, instead of checking all the conditions up front. Data classes instead of hand-written methods, and sensible defaults instead of mutable ones.\n\nImproving existing code is called refactoring: we change the structure without changing the behavior. The golden rule: tests first, then small steps, and run the checks after each one. Signs that it is time to step in: a function a hundred lines long, deep nesting, duplication, a class that does everything, unexplained numbers instead of named constants. The simplest techniques: rename, extract a function, remove nesting with an early return, replace a condition with a dictionary. Leave the code a little cleaner than you found it: ten such small improvements give you more than one big rewrite.\n\nWorking in a team is also part of quality. Small changes are easier to check: a review of ten lines can actually be read, a review of a thousand cannot. The reviewer looks at clarity, tests and possible bugs, not at commas, which the automatic checks take care of. The author explains why the change was made. The integration pipeline runs formatting, the linter, types, tests and the build on every change, and merging is impossible until it is green. Release versions are labeled by the rules of semantic versioning, and the changelog tells users what is new.\n\nLet's sum up this whole chapter and this whole part. Quality is made of automatic checks and habits: a formatter and a linter, types, tests, documentation, error handling and logging. Design simply: single responsibility, composition, pure functions, and patterns as a shared vocabulary. Write in a Pythonic way, and improve in small steps under the protection of tests. We have come a long way from the first line to the tools of a real project: variables and functions, classes and the data model, iterators and asynchronous programming, the internals and performance. Now your task is to write projects, read other people's code, and choose the tool that fits the job.
