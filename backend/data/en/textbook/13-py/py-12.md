#CHAPTER 12 | Classes
Python as a first language. Chapter 12. Classes. So far, data and actions have lived separately: one variable holds a number or a list, and somewhere else in the program a function is described that works with it. While the program is small, that's convenient. But when a game has hundreds of characters, each with its own health, name and set of skills, keeping everything in a pile of lists and dictionaries starts to hurt. A class solves the problem differently: it combines data and the actions on that data into one type. You already use classes every day: a string, a list and a dictionary are all classes, and methods like append and split are the actions attached to them. Today we'll learn to create our own classes, and with them our own data types that speak the language of the problem.\n\nA class is written with the word class, then a name starting with a capital letter, and a colon. The shortest possible class is class Dog, with a single word pass in the body. It's a blueprint from which objects are made. To get an object, you write the class name with parentheses: dog equals Dog with parentheses. Such an object is called an instance of the class. From one blueprint you can get as many instances as you like, and each one lives on its own. A good analogy is a cookie cutter: there is one cutter, but you can cut out as many cookies as you want, and taking a bite out of one doesn't touch the others. The function type will show you an object's class, and checking whether an object belongs to a class is done with the function isinstance. Class names are conventionally written with a capital letter and no underscores, to tell them apart from functions.\n\nAn empty object can't do much, so it needs data, called attributes. An attribute is a variable attached to an object, and you reach it with a dot: dog dot name equals Sharik. But setting attributes by hand after creating the object is inconvenient, and it's easy to forget one. For this there is a special method, init, with double underscores on both sides, and it is called the constructor. Python calls it automatically when an instance is created and passes in the arguments from the parentheses. Inside the method you write self dot name equals name, and that is how the value gets stored in the object. Now dog equals Dog of Sharik and three creates an object right away with its name and age already set. The constructor guarantees that every object is born in perfect order.\n\nFunctions described inside a class are called methods. They define what an object can do. The first parameter of any method is self, and Python fills it in by itself when the method is called. For example, the class Counter has a method inc that increases an internal number by one: self dot value plus-equals one. You call a method with a dot after the object's name: counter dot inc with parentheses. The method sees its own object's data and can read it, change it, and return a result based on it. That way data and actions end up side by side: to understand what a counter can do, you don't need to hunt for functions all over the file, you just read its class. That's the main win: code is organized by meaning, not by scattered names.\n\nWhat is self? It is the object itself, the one the method was called on. Python turns counter dot inc with parentheses into a call of Counter dot inc with the counter as its argument: the object becomes the first argument. That is why the method definition needs the extra parameter. The name self is just a convention, but everyone follows it: break it, and the readers of your code won't understand you. An important consequence follows: every object has its own data. If you create two counters and increase one, the other stays at zero. There is one method shared by everybody, while the attributes belong to each instance, and self points to exactly whose they are. If you forget to write self in the method header, you'll get an error about an unexpected number of arguments, and that's the most common beginner mistake.\n\nAttributes come in two kinds. Those created through self dot name in the init method belong to the instance: every dog has its own name. But if you assign a value directly in the class body, at the level of the definition, you get a class attribute, shared by all instances. For example, the number of legs a dog has, or a counter of created objects. You can read it both through the class and through any instance. Here lies a classic trap. A mutable value, say a list, declared at the class level will be shared by all objects: add an item through one dog, and you'll see it in another. So create mutable data inside init, so that every instance gets its own list, and leave only immutable constants at the class level.\n\nObjects are mutable, and the same reference rules apply to them as to lists. The assignment b equals a does not copy the object: both names point to the same instance. Pass an object to a function, and the function receives a reference, so if it changes attributes, it changes the original. That's handy when the change is intended, and dangerous when it isn't. Comparing with a double equals sign by default checks whether it's the same object, not whether the data is the same: two dogs with the same name are different dogs. We'll learn to customize this behavior in the next chapter. For now, remember: an object behaves like a package with an address, not like a value, and copying it has to be a conscious decision, for example with the function copy from the standard library.\n\nIf you print an object of your own class, Python shows a vague string with the class name and a memory address. This is fixed with the method str: it returns the string a person will see. We describe str to return a string like Dog Sharik, three years old, and now print of the dog outputs exactly that. There is a second, similar method, repr: it should return an unambiguous description for the programmer, ideally one from which the object can be recreated. The debugger and the console show it. A good rule: repr is for the developer, str is for the user, and if you define only repr, print will use it in the absence of str. These methods are the first step toward making your own objects behave like built-in types.\n\nMethods are needed not only for getting data but also for protecting order. Take a bank account: the balance must never go negative, and you may only deposit a positive amount. If the balance is stored in an ordinary attribute, any code can write anything into it. So changes are made through methods: the deposit method checks the amount and only then changes the balance. Python has no true privacy, as other languages do, but it has a convention: an attribute with one leading underscore is internal, so don't touch it from outside. That is enough for discipline: the class guarantees its rules as long as the users of the object go through its methods. This approach is called encapsulation: we hide the details and expose clear operations.\n\nObjects live happily in collections. A list of objects is a table of records, and unlike a dictionary, each record has its own methods. To filter dogs older than two years, use a list comprehension with a condition on an attribute. To sort by age, use sorted with the key parameter, which pulls out the needed attribute. To add up the health of all characters, use sum of a generator. A dictionary of objects lets you look up a record by name: the key is the name, the value is the instance itself. Everything you learned about lists and dictionaries keeps working, only the elements have become richer. That is the point of classes: to keep in collections not faceless numbers and strings, but meaningful entities that have both data and behavior.\n\nHow do you come up with classes? Here is a simple rule from practice. Read the description of the task and underline the nouns: these are candidates for classes, such as dog, account, order, player. Underline the verbs: these are candidates for methods, such as deposit, withdraw, add, shoot. The adjectives and numbers around the nouns are attributes: name, balance, health. Take the stack, which we know from lists: a class Stack with an internal list, a method push, a method pop and a method is-empty. From outside, the user sees only clear operations, and how it works inside, they don't know and don't have to know. If tomorrow you replace the list with something else, the code around it won't change, and that is the benefit of classes.\n\nLet's collect the typical mistakes. First: a forgotten self in the method header, and an error about an extra argument. Second: a forgotten word self with a dot when accessing an attribute inside a method: a name without it is an ordinary local variable, not an attribute. Third: a mistake in the name of the init method: you need two underscores on each side, otherwise it's just a method with an unusual name, and the constructor won't run. Fourth: a mutable attribute at the class level, shared by everyone. Fifth: calling a method without parentheses, which gives you the method itself instead of the result. Sixth: trying to access a nonexistent attribute, an attribute error, which is often caused by a typo. They're caught quickly if you read the code aloud and check every line on a single object.\n\nLet's sum up. A class is a blueprint for a data type, an object is its instance, and attributes and methods describe what the object stores and what it can do. When an object is created, the init method writes the initial data through self, and self in every method is the object itself. Instance attributes belong to each instance, class attributes are shared, and mutable values must not be kept in the class. Objects are passed by reference, and the default comparison tells apart the objects themselves, not their data. The methods str and repr are responsible for the text representation. It's better to change state through methods, so that the class guards its own rules. Objects work well in lists and dictionaries. In the next chapter: magic methods, properties and class methods.
