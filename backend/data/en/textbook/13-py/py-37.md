Python as a first language. Chapter 37. Programs and environment: sys, argparse, logging, subprocess. So far our programs have lived inside an editor and started with the press of a single button. But a real program is a utility: it is launched from a terminal with parameters, it reads input data, writes results and error messages, keeps a log, and calls other programs. The standard library has a set of modules for this. The sys module gives access to the launch parameters and to the input and output streams. The os module knows about the environment and the file system. The argparse module parses command-line arguments and builds the help text. The logging module writes a log instead of scattered prints. The subprocess module runs external commands and reads their output. Today we will go through each of them and put together a template for a real utility, which will turn your scripts into proper tools.\n\nThe sys module is a window into the interpreter. The list sys dot argv holds the command-line arguments: element zero is the script name, and the rest is whatever the user passed. The function sys dot exit ends the program with a code: zero means success, any other number means an error, and that is exactly how the shell and other programs learn how it went. Sys dot path is the list of folders where Python looks for modules. The interpreter version and the platform are available as sys dot version and sys dot platform. The standard input, output and error streams are sys dot stdin, stdout and stderr: print writes to stdout by default, while error messages are customarily sent to stderr, so they can be separated from the data when output is redirected.\n\nYou can read arguments straight from the argv list, but it quickly gets cramped: you need default values, type checks, help text, flags. For that there is the argparse module. You create a parser and describe the arguments in it with the add argument method. Positional arguments are written simply by name and are required. Optional ones start with two hyphens, for example two hyphens and the word count. The type parameter sets the type and automatically converts the string to a number, default is the default value, and help is an explanation. Then the parse args method parses the command line and returns an object with attributes. If the user makes a mistake or asks for help, the parser itself prints a clear message and ends the program. With a single description you get parsing, validation and instructions.\n\nArgparse has a few techniques that come up all the time. Flags without a value are described with the store true action: if the flag is given, the value is true, otherwise false. A list of values is the nargs parameter with a star or a plus. A choice from a fixed set is the choices parameter: the user will not be able to enter anything else. Short names, such as hyphen v, are added next to the long ones. Subcommands work like in the git utility: a separate parser for each action, for example add, remove, show; they are created with the add subparsers method. For complex utilities this is the neatest way to organize the interface. And do not forget about help: the help parameter is documentation that the user will see with the help flag, and it should explain the purpose, not repeat the name.\n\nThe os module knows about the environment of the process. The dictionary os dot environ holds the environment variables: passwords, paths and operating modes are passed through them. The get method with a default value is a safe way to read them. The getcwd function returns the current folder, listdir lists its contents, os dot walk recursively traverses a tree of folders, and os dot cpu count reports the number of processors. We met this module in the chapter about files, and modern operations on paths are done by pathlib. The function os dot getpid, which returns the process number, can also be useful. For the platform there is the platform module: it names the operating system and the architecture. All of this is needed so that a utility can behave differently on different systems, and behave correctly, without making unnecessary assumptions about where it was launched.\n\nInput and output streams. The input function reads a line from the keyboard and returns it without the newline: fine for a dialogue, but not needed in automated scenarios. More universal is reading from sys dot stdin: the program reads data passed through a shell pipeline, so the utility can be connected to others, where one produces lines and ours processes them. Print with the file parameter set to sys dot stderr writes error messages separately from the data. Thanks to shell redirection, the data can be saved to a file while the errors are still visible on the screen. The return code is also part of the interface: a successful utility ends with zero and, on an error, with a non-zero number, so the scripts that call you can make a decision.\n\nPrints are fine for debugging, but real programs use the logging module for messages. How it differs: messages have severity levels, which are debug, info, warning, error and critical; you can enable output for only the levels you need; each message can include the time, the module name and the line number; and the output can be directed to a file, to the screen or to the network without changing the code. The minimal setup is the basic config function with a level and a format. After that, the code simply calls logging dot info, logging dot error and so on. It is convenient to leave debug messages in the code instead of prints: in normal operation they stay silent, and when you hunt for a bug, you just switch the level and everything becomes visible. This is a cheap and reliable way to understand what happened in a program without a debugger.\n\nLoggers are organized into a hierarchy by name. The usual practice is for each module to get its own logger by calling get logger with the module name: then you can see in the message where it came from, and you can tune the verbosity for individual parts of the program. Handlers are attached to a logger and decide where to write: a handler for the screen, for a file, for a rotating log file. Each handler has its own level and its own format. The exception method inside an except block records the error together with the traceback, which print cannot do. A log is the first thing people ask you to send when you report a bug, so the habit of keeping one from the very beginning saves you many evenings spent guessing. Do not write passwords or personal data to the log: what gets in there once stays there forever.\n\nThe subprocess module runs external programs. The main function is run: it takes a list, the command and its arguments, and returns an object with the result. The capture output parameter collects the output, text equals true converts it from bytes to a string, check equals true raises an exception if the command ended with an error, and timeout limits the waiting time. The result has the attributes returncode, stdout and stderr. Pass the command as a list, not as a string, and do not turn on shell mode without extreme necessity: otherwise user data can turn into shell commands, and that is one of the most dangerous vulnerabilities. Subprocesses are needed to call system utilities, run tests, build a project, and use programs written in other languages.\n\nLet's put together a template for a real utility. The file starts with imports, then come the functions, and at the end there is the check if name equals main. This line means that the code under it runs only when the file is launched as a program, not when it is imported as a module. Inside, you call the main function: it builds the parser, parses the arguments, sets up the log, does the work and returns the exit code, which is passed to sys dot exit. This structure lets you both run the script and import its functions from tests without launching the program itself. The main logic lives in separate functions that take data and return a result, so they are easy to test. Everything that talks to the outside world, meaning arguments, files and printing, is collected at the entrance and the exit of the program.\n\nModules and packages. Any file with the py extension is a module, and you can bring it in with the word import. Python looks for a module in the launch folder, then in the standard library and in the installed packages. A folder with an init file becomes a package: related modules live inside it. Imports are either absolute or relative, and the sensible style is absolute. For third-party libraries there is the package manager pip, and to isolate each project's dependencies there is the virtual environment, venv: the project gets its own copy of the interpreter and packages, and different projects do not interfere with each other. Modern tools such as uv combine installation and the environment. The habit of creating an environment for every project will save you from version conflicts that you would otherwise spend hours tracking down.\n\nTypical mistakes. First: printing errors to stdout, mixing them with the data. Second: parsing arguments by hand instead of using argparse. Third: forgetting about the exit code, so there is an error but the program returned zero. Fourth: writing passwords, tokens and personal data to the log. Fifth: leaving top-level code without the check if name equals main, so that the module starts working on import. Sixth: running subprocesses through the shell with a string from user input. Seventh: not limiting how long to wait for a subprocess. Eighth: configuring logging in a library module instead of only getting a logger. Ninth: confusing positional and named command-line arguments and forgetting about the default value.\n\nLet's sum up. Sys gives the command-line arguments, exit codes and input and output streams: we write errors to stderr. Argparse describes arguments, types, defaults, flags, choices and subcommands, and builds the help text itself. Os shows the environment and the file system, and we read environment variables safely through get. Logging replaces prints: levels, formats, handlers, the hierarchy of loggers. Subprocess runs external commands with a list of arguments, with a timeout and a check of the result, without a shell. The template of a utility is the main function and the check if name equals main. A venv environment isolates a project's dependencies.
