#CHAPTER 49 | Performance: measure and speed up
Python as a first language. Chapter 49. Performance: measuring, profiling, speeding up. People often say that Python is slow. That is true for some calculations and completely untrue for typical tasks, where the program is waiting for the network, the disk or a person. Real speed depends not on the language but on the algorithm, the data structures and the habit of measuring. In this chapter we will go through the order of actions: first correctness, then measurement, then a profile, and only after that fixing the bottleneck. Optimizing by guesswork almost always spends time on what does not matter and ruins the readability of the code.\n\nLet's start with measurements. For a rough estimate, the function perf counter from the time module is a good fit: it returns the value of a monotonic high-resolution clock. For small fragments the timeit module is better: it runs the code many times, turns off the garbage collector during the measurement, and returns the time of a series. A good trick is to repeat the series several times and take the minimum, because it contains the least noise from other processes. Compare options on the same data and in the same environment, since the result depends on the computer and the version of the interpreter.\n\nMicrobenchmarks are easy to fool. The compiler computes constant expressions in advance, so you end up measuring nothing. Processor and interpreter caches make the second run faster than the first. Small input hides the difference between algorithms. So take your measurement on a real workload, or on data of the same size, and use micro tests only to choose between close variants. Remember that a twenty percent speedup in a function that takes two percent of the time speeds up the program by four tenths of a percent.\n\nTo find where the time goes, you need a profiler. The cProfile module from the standard library runs the program and records how many times each function was called, how much time it took on its own, and how much together with the functions it called. Running it from the command line with sorting by cumulative time shows the top of the list right away. The result is read with the pstats module, and third-party programs draw nice diagrams. There are separate profilers for line-by-line analysis, and for production servers, sampling profilers such as py-spy work well: they hardly slow the program down.\n\nThe first thing to check is algorithms and data structures. A search in a list takes time proportional to its length, while in a set or a dictionary it takes almost constant time. Sorting a list of a million elements takes seconds, while a binary search in a sorted list takes microseconds. Counting frequencies with a double loop grows quadratically, while a counter does it in one pass. A queue based on a deque removes the expensive insertions at the start of a list. Replacing a quadratic algorithm with a linear one gives a speedup of thousands of times, and no micro-optimizations can compare with that.\n\nNext come the built-in tools. The functions sum, min, max, sorted, any and all are written in C and run faster than equivalent loops. A generator or a comprehension is usually faster than a loop that appends one item at a time. Joining a large number of strings is faster with join than by adding them in a loop. The itertools and collections modules give you ready-made fast tools. But the algorithm still comes first: a fast loop over a million elements will not save you from an extra nested loop over another million.\n\nCaching removes repeated work. The decorators cache and lru cache from functools remember the results of pure functions, and the recursive computation of Fibonacci numbers turns from exponential into linear. Cached property caches a heavy property. Regular expressions are compiled once, not on every call in a hot loop. Data that is needed often should be read in advance. But a cache costs memory and risks stale values: limit its size, think about when it gets cleared, and don't cache functions with side effects.\n\nInput and output often matter more than computation. Reading a file line by line in buffered mode is efficient, and reading it one byte at a time is not. Many small requests to a database or a service are replaced with one batch request: the familiar n plus one trap, where a separate request goes out for every record. Independent network requests are run concurrently with asyncio. Data is compressed when the network or the disk is slower than the processor. Before you optimize calculations, check with a profile whether the program is simply standing and waiting.\n\nFor numerical computing, vectorization is used. Instead of a loop over a million numbers in Python, the operation is carried out on a whole array in NumPy or pandas, where the loop runs in C. The difference reaches tens and hundreds of times. For critical sections there are other paths too: compilers such as Numba and Cython, extensions in C and Rust, alternative implementations such as PyPy. But these tools add complexity to building and debugging, so reach for them when the profile shows one small hot spot.\n\nParallelism is a separate branch of speeding up. For input and output, asynchronous code and threads fit, and for calculations, processes or, in the new builds, free threads. But parallelism has a price: startup, data transfer, synchronization. Amdahl's law reminds us that the speedup is limited by the share of the sequential part: if ten percent of the work cannot be parallelized, then even on a hundred cores you will get a speedup of no more than ten times. So first measure what can be split up, and then decide whether it is worth the added complexity.\n\nMemory and speed are connected. Extra intermediate lists force data to be copied and load the garbage collector, while generators process a stream without storing it. Slots shrink millions of small objects. Dense arrays are better than sparse lists of objects: the data lies in a row, and the processor reads it more efficiently. A huge structure that does not fit in the processor cache slows down regardless of the language. So the memory profile from the last chapter often explains speed problems too, and sometimes the best speedup comes from simply cutting the amount of data.\n\nHow do you put optimization into practice? Set a goal: how many milliseconds are acceptable. Measure the current state and save it as a baseline. Find the bottleneck with a profiler and fix it with a single change. Measure again and make sure it got better and the tests pass. Add a performance check to the automated tests so that regressions don't creep in. Write in a comment why the code is arranged in an unusual way, otherwise the next developer will simplify it. And remember: the fastest code is the code that doesn't need to run, so sometimes the gain comes from dropping unnecessary work.\n\nLet's sum up. First correctness, then measurements: perf counter and timeit, with repeats and the minimum. Bottlenecks are found with cProfile. The first thing to look at is algorithms and data structures, then built-in tools, caching and input and output. For numbers, vectorize; for hot spots, bring in compilers and extensions if needed. Parallelism has a price and is limited by Amdahl's law. Lock in the result with performance tests. With this we have finished the section on the inner workings of Python, and next we will work on projects and tooling.
