#CHAPTER 41 | Protocols and generics
Python as a first language. Chapter 41. Protocols and generics. Type hints are not checked at run time: Python will happily execute a function that was given the wrong thing. But they are invaluable for people and for programs. An editor uses them to suggest methods, and checkers such as mypy and pyright find errors before the program runs. In the previous chapter we described contracts through inheritance. Now let's see how to describe interfaces without inheritance, using protocols, and how to write code that works with any types while still keeping information about them, using generics.\n\nA protocol is structural subtyping, in other words duck typing written down for the checkers. You inherit a class from Protocol, which lives in the typing module, and describe the methods you need. Any object that has such methods with suitable signatures counts as matching, and no inheritance is needed. Say a function needs an object with a close method. Describe a Closeable protocol with that method, and files, sockets, connections and your own classes will all fit, with no common ancestor. This is the main difference from abstract classes, where inheritance is mandatory.\n\nWhether a structure matches is decided by the checker, not by the interpreter. If you need a check at run time, add the runtime checkable decorator. Then isinstance will work, but with an important caveat: it checks only that the methods exist, not their signatures and not the types of values. So don't build serious protection on it. Protocols can also describe data: a required attribute is declared with an annotation in the body of the protocol. Explicit inheritance from a protocol is allowed too, and then the class gets ready-made implementations of the methods.\n\nThe standard library has plenty of ready-made protocols. Sized requires a length, Iterable requires iteration, Container requires a membership check, Hashable requires a hash. There are SupportsInt, SupportsAbs, SupportsIndex and others: they express that an object can be converted to an integer, give an absolute value, or serve as an index. A good design rule: accept the least demanding type. If a function only iterates over its argument, write Iterable, not list: then it works with tuples, sets and generators too. And return the most specific type that you really return.\n\nNow generics. A function has to return the first element of a sequence. If you write that it accepts a sequence of anything and returns anything, the checker loses the link between input and output. For this there is a type variable, TypeVar. We write: it accepts a sequence of elements of type T and returns T. Now for a list of numbers the result is a number, and for a list of strings the result is a string. A type variable is like a function parameter, but on the level of types. You can restrict it: bound sets an upper limit, and a list of options allows only the listed types.\n\nClasses can be generic too. A stack, a queue, a box, a query result: all of these are containers for elements of some type. You inherit the class from Generic with a type parameter, and then Stack with square brackets and int means a stack of integers. At run time the brackets merely create an alias, but the checker understands the meaning: it will forbid putting a string into a stack of integers. Starting with Python 3.12 there is a simplified syntax: type parameters are written right in square brackets after the name of the class or function, with no separate declaration and no Generic.\n\nThe relationships between generic types are called variance. A list of integers is not a list of objects: otherwise you could put a string into it through a variable of type list of objects. We say that list is invariant. An immutable sequence of integers, however, fits perfectly where a sequence of objects is expected: it is covariant, because it only gives values out. A function that accepts values is, on the contrary, contravariant in its arguments. You don't need to memorize the details: with the new syntax the checker works out the variance by itself, and when there are errors the message shows what is wrong.\n\nAmong other things, typing has Self for methods that return an instance of the same class: method chains in builders and alternative constructors keep the type of the subclass. Literal restricts values to specific constants, for example file opening modes. Final forbids overriding. TypedDict describes dictionaries with known keys. Callable and ParamSpec describe functions. For optional values you write a type, then a vertical bar and None; the Optional notation means the same thing. Together these tools make type hints expressive.\n\nFunction overloading by types is described with the overload decorator. In the standard form you write several stubs with different signatures and one real implementation that sorts out the arguments. The stubs are needed only by the checker: it knows that a string gives a string, and a list gives a list. At run time the last function is the one that works. If you need real dispatch by type, you use singledispatch from functools. Don't mix up these two mechanisms: the first is for hints, the second is for behavior.\n\nCheckers work gradually: you can annotate only part of the code, and the rest is treated as Any, that is, anything goes. Don't confuse Any with object: Any turns the checks off, while object allows only the common operations. The type ignore comment suppresses an error on a line, but it should be used rarely and with an explanation. Run mypy or pyright in the automatic check of every change, and the hints will start to pay off. Turn strictness on in parts: first the new modules, then the old ones.\n\nProtocols are especially good for dependency injection and tests. A library describes a protocol for what it needs: for example, an object with get and put methods. The user writes their own class, without importing the library and without inheriting, and everything works. In tests a simple stand-in is plugged in. This style reduces coupling between modules: they depend on a shape, not on specific classes. That is why protocols have become the standard way to describe interfaces in modern projects and in the standard library itself.\n\nCommon mistakes. Expecting hints to take effect at run time. Using isinstance with a generic type such as list of int: you can't do that, a type error is raised. Trying to check signatures with runtime checkable. Input hints that are too narrow. Mixing up protocols and abstract classes when one of them would be enough. And a type ignore on every second line: that way hints stop meaning anything. It is better to fix the code or refine the annotations than to switch the checks off.\n\nLet's sum up. Type hints are for people and checkers, not for the interpreter. A protocol describes a shape: any object with the right methods fits, without inheritance. Runtime checkable checks only that the methods exist. TypeVar links input and output, and generic classes inherit from Generic or use the new syntax with square brackets. Accept the least demanding type, return the precise one. Self, Literal, overload and TypedDict complete the picture. In the next chapter we will look at multiple inheritance and the method resolution order.
