#CHAPTER 48 | Bytecode, the interpreter, the GIL and free threading
Python as a first language. Chapter 48. Bytecode, the interpreter, the global lock and a future without it. In the last chapter we found out how Python stores objects. Now let's see how it runs a program. What happens between pressing run and seeing the result? Why don't two threads speed up calculations? And what does it mean when the news says the global lock is finally becoming optional? There are many implementation details here, and they change from version to version, so we will focus on lasting ideas and point out the versions where important changes appeared. Everything we say is about the standard implementation, CPython.\n\nThe path of a program goes like this. The source text is parsed into a tree and compiled into code objects with bytecode. If the file was imported as a module, the result is saved in the pycache directory next to the source, in a file with the extension pyc. The name carries a tag with the interpreter version, and inside is a stamp of the source, so when the source changes, the cache is rebuilt. Thanks to this, the second run starts faster: there is no compilation, only loading. The main file that you run directly is not cached this way, so move heavy logic into modules.\n\nThe bytecode is executed by the evaluation loop, the main loop of the interpreter. For every function call a frame is created: it holds a pointer to the current instruction, a value stack and the local variables. Instruction by instruction, the interpreter reads an operation and carries it out: load a value, add, call, return. Since Python three point eleven, frames have become lighter, and calls between Python functions do not use up the C stack, but the recursion depth is still limited: you can find the limit with the function get recursion limit, and when it is exceeded, a recursion error is raised.\n\nVersion three point eleven brought the specializing adaptive interpreter. The idea is that in real programs, types almost never change. When an instruction has run many times, the interpreter notices which types it sees and replaces it with a specialized version. For example, adding two integers turns into a fast instruction, and reading an instance attribute turns into an instruction with a ready-made offset. If the types suddenly change, the specialization is rolled back. You can see the result with the adaptive flag of dis. The lesson for practice: code with stable types in hot spots runs faster than code in which a variable's type keeps jumping around.\n\nSome other improvements. In version three point eleven, exceptions became free when nothing goes wrong: a try block costs nothing until an exception is raised. Reading a local variable is still faster than reading a global one, because a global name is looked up in a dictionary, while a local one is read by its number. That is why, in the hottest loops, people sometimes copy global functions into local names. But don't make it a habit: measure first and optimize afterwards, because the modern interpreter does a lot for you.\n\nVersion three point thirteen added an experimental JIT compiler. It works by the copy-and-patch method: ready-made templates of machine code are stitched together for frequently executed sections. By default it is switched off, and you turn it on when building the interpreter and with an environment variable. The gain is modest for now, it is groundwork for the future: it shows that the direction of development is to get faster without changing the language. You shouldn't rely on it yet, but it is useful to know that bytecode is not the final stage.\n\nNow to the main limitation. The global interpreter lock, the GIL, guarantees that at any moment only one thread executes bytecode. It protects internal structures and reference counts: without it, two threads could change a counter at the same time and corrupt it. Every five milliseconds, which is the switch interval, the lock is handed to another thread; before input and output operations and while waiting, it is released. That is why threads are good for input and output: while one waits for the network, another works. But calculations on the processor are not sped up by threads: there is one core's worth of work, and one thread runs.\n\nIt is important to understand that the lock does not make your code thread-safe. The simple statement x plus-equals one is several instructions: read, add, write, and a thread can be switched out between them. If two threads increase a shared counter this way, some of the increments will be lost. Single operations such as appending to a list run as a whole, but compound sequences do not. So protect shared data with a lock from the threading module, or pass it through a queue. Races rarely show up in tests and often show up in production, so it is more reliable to prevent them than to catch them.\n\nHow do you get around the limitation? For calculations on several cores you use processes: each has its own interpreter and its own lock. Process pools from concurrent futures hide the details, at the price of copying data between processes. Extensions written in C, such as NumPy, release the lock while they compute, so threads running them work in parallel. For input and output, threads and asynchronous code fit well. Since version three point twelve, subinterpreters have their own lock, and in three point fourteen their interface appeared in the standard library: it is lightweight isolation inside one process.\n\nThe most noticeable news is the mode without the lock. Under proposal number seven hundred and three, Python three point thirteen got an experimental build with free threads, and in three point fourteen it became officially supported. You install a separate variant of the interpreter, usually with the letter t in its name. You can find out whether the lock is enabled with the function sys underscore is gil enabled, and the type of build is shown by the configuration parameter Py GIL disabled in the sysconfig module. The environment variable Python GIL lets you switch the lock back on if you need to.\n\nHow does it work? Reference counts became biased: the owner of an object changes them without expensive atomic operations, while the other threads use a shared counter. Some objects, such as small numbers, became immortal and do not count references at all. A special scheme is used for deferred references to functions and modules. The built-in containers got internal locks, so changing a list from several threads at once does not corrupt memory. The price is a slight slowdown of single-threaded code. C extensions must declare support explicitly, otherwise the lock is switched back on when they are loaded, with a warning.\n\nWhat should you do in practice? Don't rewrite your programs in advance for the new build. For input and output, asynchronous code and threads are still better; for processor-bound tasks, processes are reliable today. Free threads are useful where you need many cores and shared memory: numerical computing, in-memory processing, servers with shared caches. But synchronization is now always mandatory: races that used to happen rarely will show up more often. Check libraries for compatibility, measure on your own data, and upgrade as the ecosystem gets ready.\n\nLet's sum up. Source code is compiled to bytecode, cached in pycache and executed by the main loop with frames. The specializing interpreter speeds up stable types, and the experimental JIT paves the way for the future. The global lock lets only one thread run at a time, suits input and output, does not speed up calculations, and does not make code thread-safe either. You can get around it with processes, C extensions and subinterpreters, and now with the build without the lock, which brings new rules and new risks. In the next chapter we will talk about how to measure and speed up programs.
