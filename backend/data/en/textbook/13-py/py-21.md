#CHAPTER 21 | Descriptors, properties and slots
Python as a first language. Chapter 21. Descriptors, properties and slots. When you write a dot and a name, it seems that Python just looks into the object's dictionary. In reality it is trickier: properties, ordinary methods, class methods and static methods, slots, and the fields of database models all work through the same mechanism. It is called descriptors. This is one of the deepest ideas of the data model, and after this chapter you will see how many things you have been using from the very beginning are built, from the familiar property decorator to why a method receives self.\n\nLet's start with something familiar. The property decorator turns a method into an attribute: when you read it, a getter function is called, when you write it, a setter function, and when you delete it, a deleter function. This is how you write computed attributes, for example an area from the sides, and validate values on assignment, for example an age that cannot be negative. From the outside it is an ordinary attribute without parentheses, and on the inside it is code. A good practice: first make a public attribute, and if you later need validation, turn it into a property without breaking those who already use the class.\n\nWhat is a property, really? It is a class-level object that has the get, set and delete methods. Any object with such methods that sits in a class attribute is called a descriptor. The get method receives the instance through which the attribute was accessed, and the class. The set method receives the instance and the new value. When you read or write an instance attribute, Python looks in the class first: if there is a descriptor there, control is handed to it. A property is simply a ready-made descriptor, and you can write your own.\n\nDescriptors come in two kinds. If an object has a set or a delete method, it is a data descriptor. If it has only get, it is a non-data descriptor. The difference determines priority. A data descriptor outranks the instance dictionary: writing and reading always go through it. A non-data descriptor is weaker: if the instance dictionary has the same name, that one wins. This is why you cannot shadow a property by assigning on an instance, while an ordinary method you can, although almost nobody does that.\n\nThe most common descriptor is a function. An ordinary function defined in a class has a get method. When you access it through an instance, this method returns a bound method: an object that remembers the instance and passes it as the first argument. That is where self comes from: no magic, just the get method of a function. Through the class, the function is returned as it is. A class method and a static method are descriptors too: the first passes the class, the second passes nothing. Now the oddity of the instance being passed automatically stops being an oddity.\n\nSuppose that in several classes you need to check that a number is positive. Copying properties is tedious. Write a data descriptor once and apply it to any field. The set-name method is called when the class is created and tells the descriptor the name under which it was placed, so that it can store the value in the instance under a related name. The get method, when accessed through the class, receives an empty instance, and it is customary to return the descriptor itself. This way the check lives in one place, and fields are declared in a single line.\n\nThe main trap is that a descriptor belongs to the class, not to the instance. If you store the value right in the descriptor, it ends up shared by all instances, and one order will change the price in another. The value must be stored in the instance itself: in its dictionary or in an attribute with an underscore. You can also store the value in the instance dictionary under the same name: the data descriptor still wins during lookup, and writing straight into the dictionary bypasses your set method and therefore does not cause recursion.\n\nA non-data descriptor is indispensable for lazy computation. The cached property decorator from the functools module computes the value on first access and writes the result into the instance dictionary under the same name. After that the lookup finds the value right in the dictionary, and the function never runs again: a non-data descriptor is weaker than the dictionary. To reset the cache, just delete the attribute. It suits heavy computations that don't change: parsing a file, processing a big table. But it needs the instance dictionary, so it is incompatible with slots.\n\nNow the complete order of attribute lookup. First Python walks through the classes in inheritance order and looks for the name. If a data descriptor is found, it decides everything. Otherwise the instance dictionary is checked. If it is empty there, a non-data descriptor or a plain class value is used. If the name is found nowhere, the getattr method is called, the one we discussed in the first chapter of the series, and after it an AttributeError is raised. This order explains properties, methods, and the behavior of caching attributes.\n\nSlots solve a different problem. By default every object has a dictionary for its attributes: it is flexible, but it takes memory. If you declare a tuple of names called slots in a class, Python allocates space for exactly those fields and creates no dictionary. The fields themselves are also implemented as descriptors: for every name, the class gets a special member descriptor. The price is rigidity: you cannot add arbitrary new attributes, weak references have to be requested separately, and a subclass without slots gets the dictionary back.\n\nWhen is this needed? When there are millions of instances: points on a map, tree nodes, events in a stream. Slots reduce memory use and speed up access a little. For ordinary classes the gain does not justify the inconvenience. Data classes can turn slots on with a single parameter. Slots are also useful because they catch typos: trying to assign a nonexistent field raises an error instead of creating a new attribute. Measure first, optimize later: a profiler will tell you whether your program needs slots.\n\nHow do you choose between the tools? For a single attribute with validation or computation, a property is enough. For repeated logic across many fields, write a descriptor. For a heavy lazy value, take cached property. For millions of lightweight objects, add slots. Descriptors underlie properties, methods and slots, as well as database models and data validation systems: when you describe a field in a class, the library usually puts a descriptor there, and the work with the record goes on in its methods. Now you understand what stands behind it.\n\nLet's sum up. A descriptor is an object in a class attribute with the get, set or delete methods. Properties, methods, class methods and static methods are descriptors. A data descriptor outranks the instance dictionary, a non-data descriptor is weaker. Store the value in the instance, not in the descriptor, and use set-name. Cached property caches the result, and slots save memory at the cost of flexibility. In the coming chapters we will use this model to build abstractions and interfaces, and right next we will look at iterators and generators in more depth.
