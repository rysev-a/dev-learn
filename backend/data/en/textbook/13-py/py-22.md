#CHAPTER 22 | Iterators
Python as a first language. Chapter 22. Iterators. The for loop is the most familiar construct in the language: we loop over lists, strings, dictionaries, ranges, the lines of a file, and the pairs from zip and enumerate. It looks as if for can work with a dozen different types, and Python keeps a separate mechanism for each. In fact there is just one mechanism, and it is called the iteration protocol. Any object that follows it can be looped over, turned into a list, or passed to sum or to zip. Today we look under the hood: we will see how an iterable differs from an iterator, how the for loop works inside, how to write your own iterator, and why iterators are single-use. This knowledge is the key to generators and to lazy evaluation.\n\nLet's introduce two terms. An iterable is an object you can loop over: a list, a string, a dictionary, a tuple, a file. It has a method that returns an iterator. An iterator is a separate object that remembers where it stopped and knows how to produce the next element. The function iter gives you an iterator: iter of a list returns an iterator over that list. The function next takes the following element: each call returns the next value and moves the position forward. A list is iterable, but it is not itself an iterator: next of a list raises a type error. But iter of a list is already an iterator, and next works on it. The difference is subtle but important: a list can be looped over as many times as you like, while an iterator can be looped over only once.\n\nWhat happens when an iterator reaches the end? The next call to next raises a special exception, StopIteration. It is not an error in the usual sense, but a signal that the elements have run out. This is exactly how the for loop works: first it calls iter on the object to get an iterator, then in an endless loop it calls next and assigns the result to the loop variable, and when it catches StopIteration, it quietly leaves the loop. Any for can be rewritten with while True, try, and except StopIteration, and nothing changes. Now it is clear why the loop can go over just about anything: it only cares about one thing, that the object can hand out an iterator, and that the iterator can produce values and report the end.\n\nThe main property of an iterator is that it is single-use. It moves only forward: what has been produced has been produced, and you cannot go back. When an iterator is exhausted, looping over it again yields nothing, and this often confuses beginners: they went through an iterator with a loop, and a second loop over it printed nothing. Many objects you already know are iterators: an open file, the result of zip, enumerate, map, and filter. You can turn such an iterator into a list too, but that exhausts it. If you need the data several times, save it in a list or create the iterator again. And range, on the contrary, is an iterable, not an iterator: you can walk over it a thousand times, because every loop gets a fresh iterator.\n\nYour own iterator is a class with two magic methods: iter and next. The iter method returns the object itself, because it already is an iterator. The next method returns the next value, or raises StopIteration when the values are over. An example is a countdown: the object stores the current number, and the next method first checks whether we have reached zero, then decreases the counter and returns the previous value. After that, a for loop over the countdown object prints the numbers from the starting one down to one, and the function list turns it into a list. A custom iterator lets you loop over anything: table rows, pages of a service response, tree nodes. The main thing is to raise StopIteration at the right moment, otherwise the loop never ends.\n\nAn iterator has one limitation: it is single-use. To make a class that can be looped over many times, we split two roles. The class itself becomes iterable: its iter method creates and returns a new iterator every time, an object of another, auxiliary class. Then each for loop gets a fresh iterator and starts from the beginning. This is how lists and ranges are built: the list is iterable, and the iterator over it is a small separate object that remembers only the current position. A design rule: collections are iterable, and iterators are created on demand. If an iterable class returns itself from iter, it becomes single-use, and the second attempt to loop over it comes out empty. This is a frequent cause of mysterious bugs in your own classes.\n\nThe standard library has plenty of ready-made helpers for iterators. Enumerate numbers the elements, zip glues several sources together, reversed goes from the end, and range creates numbers on demand. The functions map and filter apply an operation and select elements lazily. The function iter can do something else too: with two arguments it calls a function again and again until it returns a sentinel value. The same StopIteration is at the heart of the consuming functions: list, tuple, sum, min, max, any, all, join, and the in operator. Each of them runs through an iterator to the end and collects a result. Knowing this protocol makes all these functions one family: what one of them understands, they all understand.\n\nUnpacking deserves a separate mention. Assigning to a, b, c from an iterable takes apart any iterable object, and a star before a name collects the rest. A star in a function call spreads an iterable into arguments: print with a star before a list prints the elements separated by spaces. The function next takes a second argument, a default value: next of an iterator with the default None returns None instead of raising an error when the elements are over. This is handy for finding the first matching item: next of a generator that goes over the candidates, plus a fallback value. All of this works with any iterable source, whether it is a list, a file, a dictionary, or your own class.\n\nThe main advantage of iterators is laziness. An iterator does not keep all the values in advance, but produces each one at the moment it is requested. A range from zero to a trillion takes a few dozen bytes, while a list with that many numbers would not fit into any memory. A file is read line by line, and only one line sits in memory at a time. Map and filter compute nothing until you start looping over the result. Laziness saves both memory and time: if you need only the first matching element, the rest will not be computed at all. This is a fundamentally new way of thinking: instead of compute everything, then select, you describe a pipeline and pull from it one item at a time. Later we will see how easily such pipelines are built with generators.\n\nIterators can be infinite. Let's describe a class that produces Fibonacci numbers: it stores the last two numbers, and on each call to next it returns the following one, never raising StopIteration. A for loop over such an object will not stop by itself, so it has to be interrupted with break, or you take only as many items as you need. An infinite iterator takes no memory and does not break the program until you try to turn it into a list in full: the function list on an infinite iterator never returns and eats all the memory. The rule for infinite streams: always limit them, for example with a counter or a condition. For tidy slicing of iterators the standard library has special tools, and we will meet them in the chapter on itertools.\n\nDictionaries are a topic of their own. A loop over a dictionary gives its keys, and the methods keys, values, and items return special iterable views: they do not copy the data, but look at the dictionary itself. That is why changing the size of a dictionary during iteration is forbidden: the iterator would lose consistency, and Python stops the program with an error. In modern versions, reversed works with dictionaries too: the keys come in reverse insertion order. The order of traversal of a dictionary is the insertion order, and you can rely on it. Strings iterate over characters, files over lines, and tuples and lists over elements. In all cases the same protocol works, which means the same for loop and the same consumers.\n\nCommon mistakes. First: reusing an exhausted iterator and being surprised by an empty result. Second: calling next on a list and getting a type error: you must take iter first. Third: an iterable class whose iter method returns self, and so is good for only one pass. Fourth: forgetting to raise StopIteration in your own iterator, so that the loop never ends. Fifth: modifying a collection while looping over it. Sixth: turning an infinite iterator into a list. Seventh: expecting map and filter to have computed something right away: they are lazy, and without a loop nothing happens. Most of these mistakes disappear if you remember a simple rule: an iterator is a single-use cursor, and an iterable is a source of fresh cursors.\n\nLet's sum up. An iterable can hand out an iterator through iter, and an iterator produces values through next and reports the end with StopIteration. The for loop is iter plus a repeated next until that signal. Iterators are single-use: a file, zip, enumerate, map, and filter are exhausted after the first pass, while a list and a range are sources of new iterators. A custom iterator is a class with the methods iter and next; a reusable class creates a new iterator in iter. Iterators are lazy and can be infinite, and consumers such as list and sum run through them to the end. Next with a default value safely takes a single element.
