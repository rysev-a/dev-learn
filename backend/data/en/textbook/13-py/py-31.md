#CHAPTER 31 | Metaclasses and init subclass
Python as a first language. Chapter 31. Metaclasses and the init subclass hook. In Python everything is an object, and classes are no exception. You can pass a class to a function, put it in a list, return it from a function. But if a class is an object, then it has a class of its own. What is it? The answer is unexpected and beautiful: the class of classes is called type. And if you can control what type does when it creates a class, you can intercept and change the process itself. This is how enumerations, abstract classes, and many libraries work. In this chapter we will take the mechanism apart without any magic and understand when it is needed.\n\nLet's check it in practice. The type of the number three is int, and the type of the class int is type. The type of type itself is also type, it closes on itself, and all classes ultimately inherit from object. The type function with one argument returns the type of a value, but with three arguments it works differently: it creates a new class. You pass it a name, a tuple of parents, and a dictionary of attributes, which can hold functions that become methods. The ordinary class statement is just a convenient way to write such a call, and the result is the same.\n\nThat is why classes can be created dynamically. Suppose you read a description of fields from a file and want to make a class with those fields that can print itself. You build a dictionary with methods, call type, and get a finished class that is no different from one written by hand. This is how namedtuple and similar tools create classes from a description. Dynamic creation is handy for generating classes from a schema, but don't overuse it: static analysis and your editor will not see such classes.\n\nWhat exactly happens when the class statement runs? Step one: the parents and the metaclass are determined, that is, the thing that will create the class. Step two: the metaclass prepares a namespace for the body, usually an empty dictionary, and the prepare method lets you replace it. Step three: the class body runs as ordinary code, and all the definitions land in that namespace. Step four: the metaclass is called with the name, the parents, and the namespace, and it returns the finished class. Step five: set name is called on descriptors, and the init subclass hook is called on the parent.\n\nA metaclass is a class whose instances are themselves classes. To write your own, you inherit from type and override new, which receives the name, the parents, and the namespace: you can change the dictionary, add methods, check for required attributes, or register the result. You use it through the keyword argument metaclass in parentheses after the class name. A metaclass is inherited: all descendants are automatically created by the same metaclass. And if two parents have different metaclasses that are incompatible, you get a conflict error.\n\nWhy is this needed? The language's own authors say that ninety-nine percent of programmers do not need metaclasses, and that is true. Still, they sit underneath useful things. Enumerations use a metaclass to iterate over members in the order they were defined and to forbid reassignment. Abstract classes use a metaclass to forbid creating an instance when some methods are not implemented. Database models build a table schema from the fields of a class. All of this is done at the moment the class is created, not later, and so mistakes in the description show up immediately.\n\nLet's see a metaclass in action. Suppose we want every command class to collect its own handlers. In its new method, the metaclass looks through the namespace, picks the functions whose names start with cmd and an underscore, stores them in a dictionary under their short names, and adds that dictionary to the class. Now any class with this metaclass gets a table of commands without a single extra line from its author. Notice a subtlety: the metaclass receives the namespace before the class is created, so it can not only read it but also modify it.\n\nA metaclass controls not only the creation of a class but also the creation of instances. When you call a class with parentheses, what actually runs is the call method of the metaclass. It in turn calls the new and init methods of the class. If you override it, you can step into this process: return the same instance every time, as in a singleton, keep count of created objects, or cache instances by arguments. Remember the order: the call method of the metaclass runs first, then new of the class, then init of the class. It is useful to keep this in mind when debugging.\n\nIn most cases, something simpler is enough for the tasks that used to be solved with metaclasses. Starting with Python three point six, there is the init subclass hook: a class method that is called on the parent every time a descendant is defined. It receives the new class and any keyword arguments given after the parents. It suits registering plugins, checking required attributes, and configuring descendants. You need neither a new metaclass nor the tangle of metaclass inheritance. If a hook is enough, use the hook: it is clearer, easier to debug, and creates no conflicts.\n\nLet's give an example of a registry. The base class takes an optional name and records the descendant in a shared dictionary: the name comes from the argument or from the class name in lowercase. Now anyone who inherits from the base class automatically ends up in the registry, and the program picks the right implementation by a string from the settings. The same technique suits command handlers, file formats, and validation rules. The same hook is also good for checks: if a descendant does not define a required attribute, raise a type error right when the class is created.\n\nThere are two more related hooks. The class get item method is called when you put square brackets after the class itself: that is how a list with a type hint returns a generic alias. And the prepare method of a metaclass lets you slip in your own object instead of a dictionary, one that, for example, forbids duplicate method names or remembers their order. These techniques are rarely needed, but they show that class creation is fully open to customization and not hidden inside the interpreter.\n\nTypical traps. Metaclasses are hard to read and debug, and editors and type checkers often do not understand them. A metaclass conflict appears with multiple inheritance and is solved by creating a common metaclass that inherits from both. Overriding the new method of a metaclass without calling the parent one breaks class creation. Deep tampering with call complicates ordinary things, such as copying. And, strangely enough, the most common mistake remains using a metaclass where a class decorator, a descriptor, or the init subclass hook would have been enough.\n\nLet's sum up. A class is an object, it is created by type, and type can also be called directly, with three arguments. The class statement runs the body, calls the metaclass, and then set name and init subclass. A metaclass inherits from type, and it controls class creation through new and instance creation through call. For registration and checks, the init subclass hook is usually enough. Choose the simplest tool: a decorator, a descriptor, a hook, and only then a metaclass. In the next chapter we will go even deeper and treat code as data, with the ast and dis modules.
