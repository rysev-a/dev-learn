#CHAPTER 30 | Introspection and inspect
Python as a first language. Chapter 30. Introspection and the inspect module. A Python program can study itself while it runs: find out the types of values, list attributes, read function signatures, locate source code, and even look at the functions that called it. This ability is called introspection, or reflection. It underlies debuggers, test frameworks, documentation tools, serialization, and dependency injection systems. When you write a decorator that checks arguments, or a library that finds your classes on its own, you are relying on it. In this chapter we will meet the set of tools that hides behind the familiar built-in functions.\n\nLet's start with types. The type function returns the class of a value, isinstance checks membership while taking inheritance into account, and issubclass compares classes with each other. Every class has a bases attribute with its direct parents, an mro attribute with the full lookup order, and a subclasses method with the list of known descendants. That last one is especially handy for plugins: a base class can find all its heirs by itself, without any registry. This is how Python answers the questions what is this and where did it come from, without needing any hints from the author of the code.\n\nThe next question is what an object has. The dir function returns a sorted list of attribute names, including inherited and special ones, which is handy for exploring an unfamiliar object in the console. The vars function returns a dictionary of the instance's own attributes, that is, its dict, but it cannot be called on objects that use slots. Dir answers what is available, vars answers what is stored right here. Also remember that some names from dir are provided by descriptors, so reading a value may run code rather than just fetch data.\n\nFunctions getattr, setattr, hasattr, and delattr let you read and change attributes by a name given as a string. Getattr takes a default value as a third argument, so you don't have to catch an attribute error. This kind of access is needed when the name isn't known in advance: it came from a configuration file, from the command line, or from a query string. For example, a user's command turns into a method name, and the object decides what to do. But keep security in mind: a name from the outside world must not be used without checking, otherwise a user gets access to anything, including internal attributes.\n\nThe inspect module can tell kinds of objects apart. The functions isclass, isfunction, ismethod, iscoroutinefunction, and isgeneratorfunction tell you what you are looking at: a class, an ordinary function, a bound method, an asynchronous function, or a generator function. The built-in callable function only says whether a value can be called. Telling the kinds apart matters when code has to behave differently: a decorator for asynchronous functions, a serializer for classes, a test runner that picks only functions. There is no need to check by name or by the string form of the type, because ready-made predicates exist for that.\n\nThe main treasure of the module is signature. For any callable object it returns the signature: a list of parameters with their kinds, default values, and annotations, plus the return annotation. Parameter kinds distinguish positional-only, positional-or-keyword, keyword-only, and the ones that collect extra values with stars. The bind method attaches a specific call to the signature and tells you which values went to which parameters, and if they don't match it raises a type error. Argument validation, automatic command-line help, and dependency injection are built on this: a web framework looks at the parameters of your function and decides by itself what to pass in.\n\nA function is also an object with attributes. It holds the name, the qualified name that reflects nesting, the documentation, the module, the default values, the annotations, and the global namespace. Inside the code attribute lives the compiled body: the number of arguments, the names of local variables, the constants, and the names of free variables. And the closure attribute holds the closure cells, from which you can read the captured values. This is useful for debugging: seeing exactly what a nested function carried away is easier than guessing. Just be careful when changing these attributes: they alter the behavior of the function, and in ordinary code this is rarely done.\n\nSometimes you need to find the source code. The getsource function returns the text of a function or class definition, getfile returns the path to the file, and getdoc returns the documentation with the indentation cleaned up. For objects created in the interactive console or through exec, the source is unavailable, and you will get an error. A separate feature is the call stack. The currentframe function returns the frame of the current function, and that frame has a reference to the frame of the caller, with the line number, the name, and the local variables. This is how logging libraries find out where a log call came from. After working with frames it is better to delete the references to them: they create cycles and hold on to memory.\n\nType annotations can be read as well. A function has an annotations dictionary, but sometimes it contains strings, especially when deferred evaluation is turned on. To turn them into real types, use get type hints from the typing module, and starting with Python three point fourteen annotations are evaluated lazily, and the annotationlib module was added for reading them. The practical conclusion is simple: don't read the annotations dictionary directly, use the standard getter functions. Data classes, data validation libraries, and interface frameworks rest entirely on reading annotations.\n\nIntrospection works at the level of modules too. The import module function from the importlib module loads a module by a name given as a string, the modules dictionary in sys shows the ones already loaded, and a module has the file and name attributes. The pkgutil module lists the submodules of a package, and importlib metadata reads the descriptions of installed packages and entry points. This is how plugin systems work: the application finds packages by a naming convention or by entry points and loads them without an explicit list. A dotted string like package, module, function is also how a callable setting is built in configuration files.\n\nLet's look at typical uses. A generic representation of an object built from its attributes. Serializing a class to a dictionary through its fields. Discovering tests by a name prefix. An automatic command-line interface built from a function's signature. Dependency injection based on parameter annotations. Documentation assembled from help texts and signatures. Each of these techniques takes a few lines, because all the information already lives in the objects. You only need to ask: what are you, what do you have, how are you called.\n\nThere are pitfalls as well. Names that start with two underscores inside a class are mangled, so such an attribute has to be read under its mangled name. For some built-in functions written in C, the signature cannot be determined, and signature will raise a value error. Introspection slows a program down and makes it harder to read: whoever looks at the code can't see which names will be called. Passing names from outside into getattr without checking is dangerous. And finally, don't use reflection where a direct call would do: explicit code is always easier to debug.\n\nLet's sum up. Type, isinstance, mro, and subclasses answer questions about types. Dir and vars show attributes, while getattr and setattr work with them by name. The inspect module distinguishes kinds of objects, and reads signatures through signature, source code, and the call stack. Function attributes reveal the code, closures, and annotations. Import module loads modules by a string. This is the foundation of plugins, decorators, and frameworks. And in the next chapter we will go even deeper and see how classes themselves are created and what metaclasses are.
