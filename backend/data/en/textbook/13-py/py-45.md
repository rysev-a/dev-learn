#CHAPTER 45 | asyncio in practice: networking, structure, tests, web
Python as a first language. Chapter 45. asyncio in practice: networking, program structure, tests and the web. We have covered coroutines, tasks, queues and limits. Now let us see how real programs are built from these bricks. The asynchronous approach was born for the network: most real applications talk to other servers, and waiting for a reply is the main thing the program does. Today we will meet asyncio streams, write a simple server and client, look at launching external processes, build a proper application skeleton with a clean shutdown, discuss patterns such as fan out and fan in and load limiting, retries with a delay, testing coroutines, debugging, and use in web frameworks. After this chapter you will understand how asynchronous services are built, and why our own server written with FastAPI is built exactly this way.\n\nAsyncio can work with the network without any third party libraries. The open connection function opens a connection and returns a pair of objects: a reader and a writer. The reader has the coroutines read, readline and readexactly, and the writer has the write method and the drain coroutine, which waits until the data has gone out. The start server function, on the contrary, listens on a port and for every connection calls your handler coroutine, also with a reader and a writer. All of this runs on one thread, yet the server serves thousands of clients: while one handler waits for data, the event loop deals with the others. Ready made clients for web requests are external libraries, for example aiohttp or httpx. They are built on the same principles: asynchronous requests, connection pools, timeouts.\n\nLet us build an echo server: it reads a line from the client and sends it back in capital letters. The handler receives the reader and the writer, waits for a line, converts it, writes it, calls drain and closes the connection. The server is started by the start server function on the local address with port zero, which means any free port. The client opens a connection, sends a line, waits for the reply and closes. Both can be run in one program in different tasks, so you can see the whole thing working without leaving the editor. This is exactly what the skeleton of any network service looks like: accept connections, read the request, process it, reply. Real protocols, such as HTTP, web sockets and databases, add a message format, but the principle stays the same.\n\nAsyncio can run external programs without blocking. The create subprocess exec function takes a command and arguments and returns a process object, which has the coroutine communicate: it sends data, waits for completion and returns the output. This is the asynchronous sibling of the subprocess module we know from the chapter about programs. You can start ten commands at once without creating threads, and wait for all of them through gather. It is used for building projects, processing files with external utilities, running tests. The same safety rules apply: pass arguments as a list, never glue commands together from user input, and always set a timeout. Parameters let you redirect the process streams, so you can read its output line by line as it appears, rather than after it finishes.\n\nThe skeleton of an asynchronous program. All the logic is gathered into a coroutine called main, and it is started with a single call of asyncio run at the end of the file. Inside main, background tasks are created and awaited through a task group or gather. Do not call asyncio run in a nested way and do not create the event loop by hand: the modern interface does everything itself. For a clean shutdown it is important to catch signals and cancel tasks: on exit you need to close connections, finish writing data and release resources. The pattern is this: worker tasks spin in an endless loop, and main waits for a stop event. When a signal arrives, the event is set, the tasks are cancelled, and cleanup runs in finally. This discipline turns a prototype into a service that can be deployed and restarted without fear.\n\nA few proven patterns. Fan out and collect: start many independent requests and collect the answers, like gather or a task group. Load limiting: a semaphore does not let more than twenty requests go out at once. Pipeline: stages connected by queues, where each stage has its own workers: read, parse, save. First successful: start several sources and take the fastest answer, cancelling the rest. Periodic tasks: a loop with asyncio sleep between repetitions. The producer and consumer pattern with a bounded queue creates natural pressure: if the consumers cannot keep up, the producer slows down. These techniques solve most of the problems met in network programs, and they are easy to combine with each other.\n\nNetwork failures are the norm, not the exception. A request may not arrive, a server may reply with an error, a connection may break. So everything that goes to the network needs two protections: a timeout and retries. A retry without a pause only finishes off an overloaded server, so we wait: first a second, then two, then four. This is called exponential backoff. A random addition is added to it, so that clients do not knock at the same moment. Only safe actions can be retried: a read with no side effects is fine, a payment is not, until you are sure it did not go through. A shared deadline helps too: the whole chain of actions must fit into the allotted time, and each step gets what remains. These practices separate a resilient service from one that falls over at the first failure of a neighbor.\n\nTesting coroutines. An ordinary test cannot wait for a coroutine, but the unittest module has the class for asynchronous test cases: its methods are declared as async def and run on a real event loop. Inside you can write await and check the result with ordinary asserts. To replace external objects there is the asynchronous mock, whose calls can be awaited too. Be careful with time: waiting real seconds in tests is a bad idea. Substitute short delays, and base your checks on the order of events and on results, not on exact seconds. Tests of asynchronous code are brittle if they rely on speed: they should check logic, not race with the scheduler. All the testing principles from the previous section still apply: isolation, small cases, pure functions wherever possible.\n\nHow to debug an asynchronous program. Turn on the asyncio debug mode: an environment variable, or a parameter of asyncio run. It warns about coroutines that were never awaited and about long blockings of the loop: if a step ran longer than usual, you will see the name of the culprit. The all tasks function returns all live tasks, and from them you can tell what hung. Give your tasks names when you create them: in tracebacks and reports it helps a lot. Logging in asynchronous code is doubly useful: write when a task started, when it finished, and with what result. An important skill is telling two kinds of problems apart: logic errors, where the result is wrong, and scheduling errors, where something did not finish in time or blocked the loop. The second kind is cured by exactly these tools.\n\nAsynchronous code in web servers. Modern frameworks such as FastAPI are built on a standard called ASGI: the server accepts connections and calls your handlers as coroutines. A handler declared as async def can use await for requests to a database, to other services and to files, and while it waits, the server serves everyone else. That is exactly what we studied: the event loop, tasks, waiting. Our own course server is written with FastAPI. An important nuance: if you call a blocking function inside an asynchronous handler, the entire server stops. For such cases the framework can run ordinary functions in a thread pool. So the rule is the same as before: waiting goes to the event loop, and blocking work goes to threads or processes.\n\nOne more feature is context variables. Ordinary global variables are dangerous in asynchronous code: thousands of tasks share them. The contextvars module provides variables whose value is separate for each task: this way you can automatically add a request number to the log without passing it through all the functions. A task copies the current context when it is created, and changes inside it are not visible outside. For those who have used thread local data, this is the analog for coroutines. Such variables are needed for tracing requests, for user data, for transactions. They work unnoticed, but when you need them, nothing else can replace them. Get used to treating state carefully: in asynchronous code it is either passed explicitly or lives in the context of the task.\n\nTypical mistakes. First: a blocking call in a handler, and a hung server. Second: a forgotten timeout on network operations, because of which a task hangs forever. Third: a retry with no delay and no limit on the number of attempts. Fourth: the writer is not closed and connections pile up: you need to close it and wait for the closing. Fifth: no clean shutdown, so data is lost on exit. Sixth: tests that depend on real time. Seventh: shared mutable state between tasks handled carelessly: between two awaits another task has time to change everything. Eighth: thousands of tasks with no limit, so the server overloads itself and overloads its neighbors. Ninth: an exception in a background task that nobody awaits, and it goes unnoticed.\n\nLet us sum up. Asyncio works with the network through a reader and a writer, with open connection and start server, and external processes are launched with the coroutine create subprocess exec. The skeleton of a program is a main coroutine and a single asyncio run, with a clean shutdown on a signal. Useful patterns are collecting, limiting with a semaphore, a pipeline on queues, and first successful. The network requires timeouts and retries with growing delays, and only for safe actions. Coroutines are tested with the asynchronous test case, and debugged with debug mode and task names. Web frameworks on ASGI call handlers as coroutines, and blocking code is moved out to threads. Context variables keep state separately for each task. You have finished the section on asynchronous programming and the whole book on Python. Next come algorithms, where everything you have learned will be useful in practice.
