#CHAPTER 44 | asyncio: coroutines and async/await
Python as a first language. Chapter 44. asyncio: coroutines and async await. Threads are fine as long as you have dozens of them. But imagine a service that holds ten thousand open connections, and almost all of them are just waiting. Ten thousand threads would eat memory and burn time on switching. Asynchronous programming solves the problem differently: one program, one thread, but functions can voluntarily hand over control at the points where they have to wait. While one waits for a server's reply, another one works, then a third. This is the job of the event loop, a dispatcher that hands out time to whoever is ready. In Python this model is built into the language with the words async and await, and the library is called asyncio. Today we will look at coroutines, tasks, waiting for several things at once, timeouts and cancellation, and the typical traps. This is one of the most practical topics in modern Python.\n\nA function declared with the words async def is called a coroutine. Calling it does not run the body. It returns a coroutine object, a piece of prepared work that still has to be started. The event loop is started by the run function of asyncio: it takes a coroutine, runs it to the end and returns the result. Inside a coroutine you can put the word await in front of another coroutine. It means: run this and wait for the result, and while waiting, let the event loop give time to everyone else. The word await may only be written inside async functions. Calling a coroutine function without await and without starting it is a classic mistake: the body will not run, and Python will warn you that the coroutine was never awaited. Coroutines are like recipes, and asyncio run is like a cook who works through them.\n\nThe main switching point is await. Every time a coroutine reaches an await and the result is not ready yet, it is suspended, and the loop picks another ready one. The simplest example of waiting is the sleep function of asyncio, which can sleep without blocking. Compare it with the ordinary sleep from the time module: that one puts the whole thread to sleep, and therefore the whole event loop, so every other coroutine stands still. This is the number one trap for beginners: any blocking call inside an async function freezes the entire program. Real switching happens only at await, so the word cooperative in the name of this model is no accident: coroutines must yield on their own. If a coroutine computes for a long time without a single await, everyone else has to wait for it.\n\nCalling two coroutines one after another with await means running them in turn: until the first one finishes, the second does not start. For real concurrency you need tasks. The create task function of asyncio wraps a coroutine into a task and immediately puts it on the loop's schedule: the task starts running at the earliest opportunity, without waiting for you. Later you write await on the task and get the result. If you create three tasks of one second each and then wait for them, the total time will be about one second, not three. That is the gain of asynchronous code: the waits overlap. It is important to keep a reference to the task: the loop holds only a weak reference to it, and a forgotten task may be removed by the garbage collector before it finishes.\n\nFor a group of coroutines there is the gather function of asyncio. It takes several coroutines, runs them concurrently and returns a list of results in the same order in which you passed them, not in the order they finished. If one of them fails, by default the exception is raised immediately, while the others keep running in the background. The parameter return exceptions set to true turns errors into ordinary items of the result, and you sort out what succeeded yourself. This approach is ideal when you need to make ten independent requests and collect the answers. In code it is a single line: results equals await gather of several calls. A star in front of a list unpacks it into arguments, which is handy when the number of requests is not known in advance.\n\nYou cannot wait forever. To limit time, modern versions have the timeout context manager of asyncio: inside its block everything must finish within the given number of seconds, otherwise a timeout error is raised. An older form is wait for, which wraps a single coroutine. When time runs out, the task is cancelled. Cancellation is a separate mechanism: a task has a cancel method, and it receives a cancellation exception at the nearest await point. This exception must be passed on, or at least not suppressed: it signals that the work was asked to stop. Inside a coroutine it is useful to put cleanup in a finally block: it will run on cancellation too. Knowing how to cancel correctly is a sign of a mature asynchronous program: hanging requests must not live forever and pile up.\n\nErrors in tasks need attention. An exception inside a task will not fly out by itself: it is stored in the task and raised when you wait for the result. If you forgot to wait, Python will only warn you later, when the task is deleted. The modern construct, the task group of asyncio, solves the problem: the block's manager creates tasks inside, and on exit waits for all of them. If one fails, the rest are cancelled automatically, and the exceptions are collected into a group. This is called structured concurrency: the lifetime of tasks is limited to a block of code, and they do not leak. This form is more reliable than gather and is becoming the standard way to run several things at once. If you want to catch the errors of a group, you use a special kind of catch: except with a star.\n\nNot only functions can be asynchronous. An asynchronous iterator lets you receive values while waiting for each one: the async for loop goes through it and waits when needed. An asynchronous generator is written as async def with the word yield inside: it can wait between portions. An asynchronous context manager is async with: entering and exiting can wait too, for example when opening a connection. These constructs are convenient for streams of data coming from the network: each message is received without blocking. They work on the same principles as ordinary iterators and context managers, only the methods get the prefix a: anext, a enter, a exit. If you have understood ordinary generators and context managers, the asynchronous versions will feel like a natural continuation.\n\nFor exchanging data between coroutines there is an asynchronous queue, the queue class of asyncio. Its put and get methods are coroutines: get waits until an item appears, without blocking the others. The producer and consumers scheme is built the same way as with threads, but without locks and races, because switching happens only at await. The task done method and join let you wait until all items are processed. A worker pool, several consumer coroutines taking jobs from one queue, is the classic way to limit parallelism and spread the work. A queue can be limited in size: then the producer slows down by itself if the consumers cannot keep up, and memory does not blow up. These techniques underlie almost every asynchronous service.\n\nWhen there are very many concurrent jobs, their number has to be limited. The asynchronous semaphore lets no more than a given number of coroutines into a block: the others wait their turn. A typical case: a thousand requests to one site, but no more than twenty at a time, so as not to overload it and not to hit rate limits. The asynchronous lock protects a section that must not run simultaneously, for example a write to a shared resource with several awaits inside. An event lets one coroutine signal others. All of them are used with async with. Note that ordinary thread locks do not work here: they block the loop. The asynchronous versions wait without disturbing the rest.\n\nSometimes you cannot do without blocking code: calculations, reading a big file, an old library with no asynchronous interface. You cannot call such code directly in a coroutine: the loop would freeze. For this there is the to thread function of asyncio: it runs an ordinary function in a separate thread and returns a coroutine that you can await. For heavy calculations a process pool will do, through the run in executor method of the event loop. So threads and processes do not compete with asynchronous code, they complement it: the event loop is responsible for waiting, and blocking work is moved outside. Remember the rule: a coroutine must never do long calculations or blocking calls, otherwise it lets everyone else down.\n\nTypical mistakes. First: forgetting await before a coroutine call. The body will not run, and a warning will come. Second: a blocking call, such as time sleep or an ordinary network read, inside an async function. The whole program hangs. Third: creating a task and losing the reference to it. Fourth: calling asyncio run inside an already running loop. It is allowed only at the top level. Fifth: suppressing the cancellation exception and making a task unstoppable. Sixth: starting thousands of tasks with no limit. Seventh: assuming that the order of completion equals the order of starting. Gather returns results in the order of passing, not of completion. Eighth: shared mutable state handled carelessly. Between two awaits other coroutines have time to change everything. Ninth: waiting without a timeout.\n\nLet us sum up. Async def declares a coroutine, and await waits for a result and lets the event loop switch. Asyncio run runs the whole program on a loop. Create task starts a coroutine concurrently, gather waits for several and returns the results in the order of passing, and the task group manages the lifetime of tasks. Timeouts and cancellation keep work from hanging, and the cancellation exception must not be swallowed. Async for, async with and asynchronous generators work with streams of data, while the queue, semaphore, lock and event organize the interaction of coroutines. Blocking code is moved out through to thread. The model is cooperative: a coroutine must yield. In the next chapter: asyncio in practice, with networking, program structure, tests and the web.
