Databases. Chapter 21. Non-relational databases: keys, documents, columns, graphs. The relational model is universal, but it is not free: a fixed schema, joins, transactions on everything. When there is a huge amount of data, the queries are uniform, and the structure changes every week, other approaches appear, called non-relational, or NoSQL, short for not only SQL. Each of them has its own data model, tuned for its own kind of query: key-value pairs, documents, wide columns, graphs. They share one idea: narrow the capabilities in order to be faster or simpler in your own area. In this chapter we will see what each kind can do, what it pays for that, and how to model data for it.\n\nThe simplest model is key-value. The database stores a dictionary: by key you can read, write and delete a value, and the value itself is a black box to the database, whether it is a number, a string or a chunk of bytes. This is how Redis, Memcached and DynamoDB work. Since there are no other operations, everything is very fast and scales easily, because the key uniquely determines the location. Often a time to live, or TTL, is added to a record: the value disappears by itself after a set period, which is handy for sessions and caches. Many stores support atomic operations on a value, for example incrementing a counter, without reading and writing in the application.\n\nThe price of simplicity is that you cannot query by value. You cannot ask to find all users from Kazan: you have to know the key. That is why keys are designed in advance: meaning is built into them, for example user, forty-two, profile, separated by colons. Composite keys let you store related data side by side and fetch it by prefix. If you need a reverse lookup, say by email, you create a second key that points to the first one, and you maintain it yourself. Relationships between entities also fall on the application. This model is ideal for caches, sessions, counters and queues, but it is cramped for data with complex relationships.\n\nA document database stores documents: self-contained structures made of fields, usually in JSON format. A document can be nested, it can contain arrays and objects, and different documents in the same collection can have different fields. A typical representative is MongoDB. Unlike key-value, the database understands the structure: you can search by fields, including nested ones, build indexes, and run selections with conditions like greater than or in a list. An order with its line items is naturally written as a single document, and with one read we get everything needed to show on the page.\n\nDocument modeling comes down to a choice: embed or reference. Embedding is fast: related data lies together, and reading takes one lookup. But duplicating data means that when a product name changes, it has to be fixed in many orders, and the document size is limited. A reference by identifier keeps a fact in a single place, but it brings us back to joins: the application makes a second query. The rule is this: embed what is read together and rarely changes, and reference what is shared and changes often. Atomicity is usually guaranteed at the level of a single document, and between documents not always.\n\nA flexible schema is a double-edged advantage. The database does not force you to describe fields in advance, and you can add a field just by writing it. But the schema does not disappear, it moves into the code: the application assumes that the field exists and has the right type. That is why people talk about schema on read, as opposed to schema on write in relational databases. Old documents stay in their old shape, and the code must be able to read all versions. In practice, you add a schema version to the document, plus validation: rules by which the database rejects documents with wrong types or without required fields.\n\nWhat do non-relational databases give up in return? Most often, joins, foreign keys and multi-part transactions. Usually a single operation on a single key or document is atomic, and the consistency of relationships between different records is the application's concern. If a transfer touches two documents, you either have to use multi-document transactions, which modern databases like MongoDB can do, though with caveats about speed, or build a sequence of steps with compensations, known as a saga. You also have to watch duplication yourself: when the same name is written into hundreds of documents, an update turns into a project. This is not a flaw but the price of simplicity and scale, and it has to be accounted for in the design from the very start.\n\nColumn families, or wide columns, are Cassandra and HBase. This is not the columnar storage from the previous chapter, but a model where data is split into partitions, and inside a partition rows are ordered by a clustering key. The partition key determines which node holds the data, and the clustering key determines the order inside. You can read efficiently only by the partition key, possibly with a range on the clustering key. There are no arbitrary joins or conditions. In exchange, writes scale almost linearly with the number of nodes, and the storage is built on the log-structured merge tree, which we covered in the previous chapter.\n\nThis dictates the modeling style in Cassandra: queries first, then tables. For each type of query you create its own table with a suitable key, and you duplicate the data, because disk space is cheap and there are no joins. For example, chat messages are stored with the chat number as the partition key and the time as the clustering key, so the latest messages are read as a single range. For a user's history you create a second table with a different key. Watch the partition size: a key that is too popular creates a hot spot, and a partition that is too large slows down reads. Time series with a limited lifetime fit well with record time to live.\n\nGraph databases, such as Neo4j, store nodes and edges, both of which can have properties. They are good where relationships matter: social networks, recommendations, detecting fraud schemes, routes. In a relational database the question of friends of friends is a chain of joins that gets more expensive with every step, while in a graph database following an edge costs almost nothing, because nodes store direct references to their neighbors. Queries are written in special languages, such as Cypher, describing a path pattern. The downside of graphs is that they are hard to scale across many machines and awkward for computing aggregates over the whole table.\n\nSearch engines, Elasticsearch and Lucene, build an inverted index: for each word, a list of the documents where it appears. The text first goes through an analyzer: it is split into words, converted to lowercase, and sometimes reduced to the word stem. The query turns into words, for each word the list of documents is taken, then the lists are intersected or merged, and the results are ranked by relevance, for example by how often the word appears in the document and how rare the word is in the collection. A search index is usually secondary: the main database holds the truth, and the index is updated with a small delay.\n\nThere are also narrower specializations. Time series databases are optimized for metrics: a huge stream of writes by time, compression, thinning out old data. Vector databases look for nearest neighbors among feature vectors, for example for semantic search and recommendations. We mentioned columnar analytical databases earlier. They all use the same ideas: logs, merge trees, compression. But a separate system is not always needed: modern relational databases can store JSON in a binary format, index it with GIN, and search by nested fields, while extensions add vectors and time series.\n\nLet us sum up. Key-value means speed and simplicity, but only lookup by key. Documents mean a flexible structure and queries by fields, and modeling comes down to a choice between embedding and referencing. Wide columns mean scalable writes and tables built around queries. Graphs mean cheap traversal of relationships. Search engines mean an inverted index and ranking. Choose a database by its access pattern, not by fashion. Using several databases in one system, polyglot storage, gives power, but requires synchronizing data between them.
