#CHAPTER 7 | Nested queries (subqueries)
Databases. Chapter seven. Nested queries. Sometimes the answer to a question can't be found in a single pass. Which products cost more than average? First you need to know the average price, and only then can you compare. In SQL there are subqueries for this: one SELECT in parentheses inside another. The inner query runs first, and its result is substituted into the outer one. A subquery can return a single value, a list of values, or a whole table, and that decides where you can use it: in a condition, in the column list, or in the FROM part.\n\nThe simplest kind is the scalar subquery, one that returns exactly one value: one row and one column. You can use it anywhere a number or a string is allowed. Products priced above the average is a comparison of the price with a subquery that computes the AVG. Orders whose total equals the maximum is a comparison with a subquery on MAX. If the subquery returned one row, everything works. If the result is empty, the value will be NULL. And if there are several rows, SQLite silently takes the first one, and that is a source of subtle bugs.\n\nA subquery can return a whole column of values, and then you use it with the word IN. Customers who placed orders are the customers whose ID is in the list of customer IDs from the orders table. Here the subquery doesn't depend on the outer query: you can run it on its own and get the list. This kind is called uncorrelated. It works like a chain of equalities joined with OR, but the list is built dynamically, so the query stays correct when the data changes. Duplicates in the list don't matter: the membership check doesn't depend on them.\n\nNegation is trickier. NOT IN checks that the value is not equal to every element of the list. But if one of the elements is NULL, then comparing with it gives unknown, and that means the whole expression can never be true. As a result, a query with NOT IN and a NULL in the list returns no rows at all, although you expected the opposite. Such NULLs show up unexpectedly, for example from a column where some rows have no value. The protection is simple: either filter out the missing values in the subquery, or use NOT EXISTS.\n\nThe word EXISTS checks just one thing: whether at least one row was found. What exactly is in it doesn't matter, which is why people usually write a one in the subquery. Customers who have orders: for each customer the database checks whether an order with their ID exists. EXISTS stops at the first row it finds, so it is often fast. Its main advantage is that it is immune to NULLs. The negation, NOT EXISTS, finds customers with no orders and doesn't break when the data has gaps, unlike NOT IN.\n\nIn EXISTS the subquery referred to the outer table: the condition linked the order to the customer. Such a subquery is called correlated. It can't run by itself, because it needs a value from the current row of the outer query. Conceptually the database repeats it for every outer row. A good example is products whose price is above the average of their own category: for each product the subquery computes the average over its category. Modern optimizers can turn such subqueries into joins, but you should write them the way that is easiest to read.\n\nA subquery can also take the place of a table in FROM. Then its result behaves like a temporary table, and you can select from it, join it, and aggregate it. This construct is called a derived table. It needs an alias, otherwise many databases will report an error. It is handy when you first need to compute totals and then filter or join on them: for example, the average order amount per customer, and then pick those whose average is above the overall one. Later we will learn to write the same thing with a common table expression, and the query will read better.\n\nA scalar subquery can also go into the SELECT column list. Then it is recomputed for every row of the result. For example, next to each customer show the number of their orders: a correlated subquery with COUNT that counts the orders of that customer. It's a convenient notation when you need one extra metric. But if there are many such subqueries, the query can become slow: every row needs its own count. In that case it is better to use a join with grouping, which computes everything in one pass.\n\nThe standard has the words ANY and ALL: comparison with every value, or with any value, from the subquery's list. For example, a price greater than all prices in the Books category. SQLite doesn't have these words, and they are replaced with aggregates. Greater than all values means greater than the maximum, and greater than some value means greater than the minimum. For an empty set, the maximum gives NULL and the comparison is unknown, whereas in the standard, ALL over an empty set gives true. Know about this difference if you move queries between databases.\n\nCustomers with orders can be found with a subquery using IN, with EXISTS, or with a join and DISTINCT. Which should you choose? If you need only the columns of the outer table and the question sounds like "is there any," EXISTS or IN is more convenient: the query reads like a sentence. If you need columns from both tables, you need a JOIN. If you need one metric per row, a subquery in the SELECT will do. Modern databases build similar plans for all of these, so the difference in speed is usually small, while the difference in readability is decisive.\n\nSubqueries work in data modification commands too. In an UPDATE, the value for a new column can be taken with a subquery: recompute an order's total from its line items. In a DELETE, the WHERE condition can use a subquery: delete the customers who have no orders. These techniques are used often, but carefully: first run the same subquery as a plain SELECT and look at which rows it would affect. A mistake in a condition costs more when you change data than when you read it, and a rollback is not always possible.\n\nWhat mistakes happen most often? A scalar subquery returned several rows: the database silently takes the first, and other systems raise an error. A subquery returned more columns than expected. NOT IN with a NULL in the list. A forgotten alias on a subquery in FROM. A correlated subquery that refers to the wrong table. To avoid mistakes, run the subquery on its own and see what it returns: a single value, a column, or a table, and whether it has gaps. And only then embed it into the big query.\n\nLet's sum up. A subquery is a SELECT in parentheses. A scalar one returns a single value, a subquery with IN returns a list, and EXISTS reports whether a row exists. A correlated subquery refers to the outer row. A subquery in FROM becomes a temporary table, and in SELECT it gives a value for every row. NOT IN is dangerous because of NULLs, and it is better to write NOT EXISTS instead. For complex queries in the next chapters we will also need common table expressions and window functions, but first let's learn to change data and the structure of tables.
