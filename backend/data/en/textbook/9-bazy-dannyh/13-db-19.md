#CHAPTER 19 | Indexes: B-trees, plans, and covering indexes
Databases. Chapter 19. Indexes: B-trees, plans, and covering indexes. An orders table has a million rows, and we need to find all the orders of one customer. Without any help, the database scans the whole table, row by row, and the time grows together with the size of the data. An index is an additional structure that stores the values of a column in sorted order, together with references to the rows. Like the table of contents of a book, it lets you jump straight to the right place. Well-chosen indexes turn seconds into milliseconds, while unnecessary ones slow down writes and take up space. In this chapter we will see how an index is built, how the database decides whether to use it, and why sometimes it does not.\n\nThe main index structure in relational databases is the B-tree. The data lives in pages of a fixed size, usually eight kilobytes, and every page is a node of the tree. An internal node stores ordered keys and references to child pages; it is like a signpost at a fork: up to fifty, go left; from fifty to a hundred, go straight. The search goes from top to bottom: we read the root, pick a child, and descend to a leaf. The key property is a high fan-out. One page holds hundreds of keys, so the tree turns out very shallow: three or four levels are enough for billions of rows, and a lookup costs three or four page reads.\n\nIn the classic variant, the B-plus tree, values are stored only in the leaves, and the leaves are linked into a chain in order. Because of this, the index is equally good for finding an exact value and for ranges: once we find the start of the range, we walk along the neighboring leaves without going back up. The same ordering lets us return the result already sorted. When a new key is inserted into a full leaf, the page is split in two and the middle key moves up into the parent; if needed, the split continues upward, and the tree grows in height only through the root. That is why the tree is always balanced, and all the leaves are at the same depth.\n\nAn index is created with the CREATE INDEX command. A unique index also forbids duplicates, and this is exactly how unique constraints and primary keys are implemented. An index can cover several columns; this is a composite index. The order of columns in it is essential: the data is sorted first by the first column, then within equal values by the second, and so on. So a composite index helps queries that use its left prefix. An index on city and date works for a search by city and for a search by city and date, but is useless for a search by date alone.\n\nNow let us talk about when an index does not work. If you wrap a column in a function, for example, search by lower of email, the database cannot compare the sorted values with the result of the function, and the index on the column itself does not help; the cure is an expression index. A LIKE pattern with a percent sign at the beginning does not use the ordering either, because there is no prefix. Implicit type conversions, when a number is compared with a string, turn a lookup into a scan. Conditions joined with OR on different columns often do the same. And finally, an index is useless if the query selects most of the table: jumping through the index for every row costs more than reading the table straight through.\n\nTo see what the database is doing, we use the EXPLAIN command. It shows the execution plan: how the database is going to read the tables and join them. The word SCAN means a full scan, and SEARCH with a mention of an index means an index lookup. In PostgreSQL, EXPLAIN ANALYZE also runs the query, showing the real time and the number of rows at each step. The optimizer chooses a plan by estimated cost, and the estimate relies on statistics: how many rows there are and how diverse the values are. If the statistics are stale, the plan choice can be poor, and then the ANALYZE command, which refreshes the statistics, helps.\n\nA particularly pleasant case is the covering index. If all the columns the query needs are in the index itself, the database does not have to look into the table at all: this is called an index-only scan. In an SQLite plan it is marked with the word COVERING. To cover a query, you add extra columns to the index; in PostgreSQL there is the INCLUDE keyword for that. The technique has a price: the index becomes wider, so it takes more space and is more expensive to update. Apply it to the hottest queries, not to all of them.\n\nThe effectiveness of an index is determined by selectivity: what share of the rows the condition filters out. An index on gender, where there are only two values, is almost useless, while an index on a unique number is ideal. The measure is cardinality, the number of distinct values. Sometimes we need not all the rows but only a hot part, for example, only the unpaid orders. Then we can create a partial index with a condition: it is more compact and faster to update. If queries search by a computed value, an expression index fits. Both techniques save space and work very precisely, but they require the query to contain the same condition.\n\nIndexes have a price that is often forgotten. Every insert, every change of an indexed column, and every delete requires updating all the indexes of the table, and writes become slower. Indexes take up space, sometimes more than the table itself, and compete for memory with the cache. This is called write amplification. So the rule is this: create an index for a specific query that really runs often, and periodically check whether there are indexes nobody uses, and whether one index duplicates another. An index on the first column is redundant if there is already a composite index that starts with it.\n\nIndexes help sorting too. If the order in the index matches the ORDER BY, the database reads the rows already in order and does not build a temporary sort, and with a LIMIT it stops after the first rows. Here there is a trap in pagination: a limit with an offset forces the database to read and throw away all the previous rows, so deep pages are slow. It is better to remember the last key you read and ask for the rows after it: the condition value greater than the last one uses the index and costs the same on any page. This technique is called cursor pagination, or keyset pagination.\n\nJoins live on indexes too. The simplest algorithm is the nested loop: for each row of one table, we look for matching rows in the other. Without an index, the inner loop is a full scan, and the cost grows as the product of the sizes; with an index on the join column, each lookup costs a few pages. That is why it is customary to index foreign keys: it speeds up both joins and the check when parent rows are deleted. For large sets, the optimizer chooses a hash join, building a hash table on the smaller side, or a merge join, if both sides are already sorted. The choice depends on the sizes and on the available indexes.\n\nThe B-tree is not the only index. A hash index finds an exact value faster, but cannot do ranges or sorting. The inverted index, GIN, stores a list of rows for every word and provides full-text search and search over array and document elements. The generalized search tree, GiST, serves geometry and nearest neighbors. The block range index, BRIN, stores only the minimum and maximum for large blocks of the table and suits naturally ordered data such as time. Bitmaps combine the results of several indexes. For ordinary tasks a B-tree is enough, and the others are used when the nature of the data requires it.\n\nLet us sum up. An index is a sorted copy of part of the data, most often a B-tree with a high fan-out. It speeds up lookups, ranges, sorting, and joins, but slows down writes and takes up space. The order of columns in a composite index matters: the left prefix works. Functions over a column and a leading percent sign switch the index off. Covering indexes, partial indexes, and expression indexes help in specific spots. Always check the plan with EXPLAIN and do not guess.
