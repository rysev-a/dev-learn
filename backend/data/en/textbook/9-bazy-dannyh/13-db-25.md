#CHAPTER 25 | Cache: where to live, when to die, and how not to fall over
Databases. Chapter 25. Cache: where to live, when to die, and how not to fall over. The fastest query is the one that never reached the database. A cache keeps the results of earlier work close to whoever asks for them: in memory, which is fast and near. It works because of locality: a small part of the data serves most of the requests, and if you keep that part at hand, the load on the database drops several times over. But a cache adds a second copy of the data, and with it all the problems of copies: staleness, races, and tricky behavior during failures. So a cache is not an optimization you add just in case, but a decision with a price. In this chapter: where a cache lives, how to work with it, when data dies, and how not to bring the system down when the cache fails.\n\nThere are many caches on the path of a request. The browser stores responses on the user's side. A content delivery network, a CDN, keeps static files and pages at the edges of the network. A cache inside the application process is the fastest, but every instance has its own. A shared cache such as Redis or Memcached is available to all instances, but a request to it goes over the network. Finally, the database's own buffer pool caches pages. The closer to the user, the faster and cheaper the answer, but the harder it is to remove stale data in time. The choice of level is set by the cost of latency, the staleness you can tolerate, and how the data is split between users.\n\nThe most common scheme is the side cache, cache-aside. The application asks the cache first; on a hit it returns the answer, on a miss it reads the database, puts the result into the cache, and returns it. On a write, the application changes the database and deletes or updates the entry in the cache. The scheme is simple, and the cache does not have to be reliable: a lost cache just means a cold start. The drawback is that the caching logic lives in the application, and every forgotten call becomes a source of stale data. This scheme fits almost every kind of read load and comes first on the list of options.\n\nThere are other ways to coordinate writes. With read-through, the cache itself goes to the database on a miss, and the application talks only to the cache. With write-through, a write goes to the cache and synchronously to the database: reliable, but slower. With write-back, a write goes straight to the cache and reaches the database later in a batch: very fast and it smooths out peaks, but if the cache dies, the unflushed changes are lost. With write-around, a write goes to the database bypassing the cache, so that rarely read data does not pollute it. The choice depends on the price of losing data.\n\nWhat exactly should you put in a cache? You can cache complete responses: a page or a fragment of the interface. You can cache database objects by identifier, for example a user profile. You can cache the results of expensive computations and aggregates, for example the top products of the day. The cache key is a function of all the parameters of the request: if you forget the language, the currency, or the user's permissions, one person will see an answer meant for another, and that is already a data leak. So user-specific data is cached with the user's identifier in the key, or not cached at all. Watch the size of values too: huge objects push out hundreds of small ones and slow down the network, and database errors should be cached very carefully and only briefly.\n\nMemory is limited, so a cache has to decide what to throw away. The least recently used strategy evicts the entry that nobody has touched for the longest time, and it suits most workloads. The frequency-based strategy keeps the most popular entries, but reacts slowly when interests change. A plain first-in, first-out queue is cheap, but dumb. Modern caches mix the approaches, for example with a clever frequency filter. Eviction by size is complemented by a time to live: an entry is removed after a set period, so that stale data does not live forever. It is important to measure the hit ratio and not trust intuition: cache size is often chosen by experiment.\n\nThey say there are two hard things in programming: cache invalidation and naming things. Invalidation is hard because you need to find out that an entry has gone stale, and the cache knows nothing about it. The simplest way is the time to live: we tolerate staleness for a limited period. Explicit invalidation deletes an entry when the data changes, but it requires knowing all the keys that depend on the data, and there can be many: a page, a list, a search. The key versioning trick makes invalidation cheap: a version number is built into the key, and when the data changes, the version grows, while old entries are simply never requested again and die by themselves when their time runs out.\n\nEven the simple side-cache scheme allows races. A reader got an old value from the database, then a writer updated the database and deleted the entry in the cache, and only after that the reader put its old value into the cache: the cache is now stale for a long time. The opposite also happens: two writers update the database and the cache in a different order. What helps is a short time to live as insurance, deleting the entry a second time after a small delay, versioning of values, and, in complex systems, updating the cache from a stream of changes from the database log rather than from the application. The main thing is to remember that a cache is consistent with the database only approximately, and to design with that in mind.\n\nNow let's talk about how a cache brings a system down. The first trouble is the cache stampede. A popular entry has expired, and thousands of requests miss at the same moment and go to the database for the very same thing, until someone puts the value back. A database sized for the load with the cache in front falls over. The cure is a single recomputation: the first request takes a lock and recomputes the value, and the others wait or get a slightly stale one. Early refresh helps too: the value is recomputed in the background before it expires. Random spread, called jitter, is added to the time to live so that entries do not expire in a bunch.\n\nThe second trouble is requests for keys that do not exist. They always miss and go to the database every time, and an attacker can take the database down by brute force. Caching the negative result helps: we remember that there is no such key for a short time. For huge key spaces, a Bloom filter is placed in front of the cache; it quickly answers, definitely not. The third trouble is the avalanche, when the whole cache goes down or a large share of entries expires at once, and the entire load goes to the database in one moment. Here you need spread in expiry times, cache warm-up before turning traffic on, and degradation: limiting the number of requests to the database and simplified responses.\n\nA cache has to be measured. The main indicator is the hit ratio: if it is low, the cache is useless and only adds latency and complexity. Watch the cache latency, the number of evictions, the memory in use, and the most frequent keys. Estimating the benefit is simple: the average latency equals the hit ratio times the cache latency, plus the miss ratio times the database latency. With a ninety percent hit ratio, the load on the database drops ten times. And if the data is almost unique for every request, like search queries with filters, a cache can bring only harm.\n\nA shared cache is also a distributed system. Keys are spread across nodes with consistent hashing, which we covered in the chapter on sharding, and losing a node means losing part of the cache, that is, a spike of misses. Two-level schemes combine a local in-process cache, the fastest, with a shared cache: the local one holds the very hot entries for seconds, the shared one holds the rest for minutes. Hot keys that overload a single cache node are copied to several nodes. A cache must not be the only storage: the source of truth stays the database, and the system must survive without the cache, at least under reduced load.\n\nLet's sum up. A cache speeds up reads thanks to locality, at the price of a second copy of the data. Most often a side cache is used: read through the cache, write to the database, and invalidate. Eviction and time to live limit the size and the age of entries. Invalidation and races mean that a cache is consistent with the database only approximately. Cache stampede, requests for nonexistent keys, and avalanche are typical ways to take down a database, and each has a defense. Measure the hit ratio and build the system so that it survives without the cache. Next is the last topic of the book: two worlds of data, transactional and analytical, OLTP and OLAP.
