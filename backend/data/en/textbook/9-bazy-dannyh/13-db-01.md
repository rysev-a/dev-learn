#CHAPTER 1 | Database Basics and Syntax
Databases. Chapter one. Database basics and syntax. This part of the course is hands-on: we learn to ask questions of data in the language called SQL. All the examples are built on a single practice online store. It has four tables: customers, products, orders, and order items. We will look at them through the eyes of an analyst: how many customers we have, what we sold and to whom, and where the data has holes. First we will see how a table is built and what the simplest query looks like, and then step by step we will work up to joins, grouping, and window functions.\n\nA table consists of columns and rows. A column is one property: a customer has an ID, a name, a city, and a sign-up date. Every column has its own name and its own type. A row is one record: one particular customer with all of their properties. To tell rows apart, a table gets a primary key, a column whose values never repeat. Usually it is simply a sequence number. Nobody promises you any particular order of rows: if you need one, you have to ask for it right in the query, and we will learn how in chapter three.\n\nThe store's data lives in several tables, and that is no accident. If we wrote the customer's name and city into each of their purchases, they would be repeated hundreds of times, and when the city changed we would have to fix every copy. So an order stores only the customer's number. Such a column is called a foreign key: it refers to the primary key of another table. That is how an order is linked to a buyer, and an order item is linked both to an order and to a product. The whole power of relational databases is built on these references, and in chapter six we will learn to follow them.\n\nThe simplest query consists of two words. The word SELECT says which columns you want, and the word FROM names the table to take them from. A star instead of a list of columns means all of them. So the query turns into the question: show me everything in the customers table. The semicolon at the end signals that the command is finished. The case of keywords does not matter, but it is customary to write them in capitals and to write table and column names in lowercase. A query changes nothing in the table: it only reads, and returns the result as a new table.\n\nThe star is handy for a first look, but in real queries it is better to list the columns explicitly. That way it is clear what you actually need, and no extra data travels over the network. Columns are separated by commas, and the result has them in the order you wrote, not in the order of the table. You can even output the same column twice. The operation of keeping only some of a table's columns is called projection in theory. If you misspell a column name, the database will honestly tell you with an error rather than return nothing.\n\nYou can rename a column in the result. To do that, write the word AS after the column, followed by the new name. This is called an alias. You need it when the name is awkward, when the column is computed and has no name of its own, or when another program reads the result. If an alias contains spaces or non-Latin letters, put it in double quotes. You can omit the word AS, but it is better to keep it, so the query reads without guesswork. Remember that an alias lives only in the query result, while the table itself stays as it was.\n\nA query can calculate. In the column list you can write arithmetic expressions: addition, subtraction, multiplication, division, and the remainder of a division. The precedence is the same as in school: multiplication and division first, then addition, and parentheses change the order. FROM is not required for a calculation, you can just compute an example. But there is a trap: if you divide an integer by an integer, SQLite gives an integer with the fractional part thrown away, so seven divided by two gives three. To get honest division, it is enough to make one of the numbers fractional.\n\nConstant values written right in a query are called literals. Numbers are written as they are. Strings are enclosed in single quotes: double quotes are reserved for names. If you need an apostrophe inside a string, you double it, and you get two apostrophes in a row. SQLite has no separate boolean type: true is one, false is zero, and a comparison expression simply returns one of those two numbers. Emptiness is written with the word NULL, and we will give it a chapter of its own, because it behaves in unusual ways.\n\nIn classic databases the type belongs to the column, and you cannot insert text into a numeric column. SQLite is different: every value has its own type, and the column's type is only a preference, called affinity. A value can be an integer, a real number, text, binary data, or empty. You can find out the type with the function typeof. So, just in case, check what actually sits in a column, especially if the data came from outside. Other databases, for example Postgres, are stricter, but the principle that the type determines what you can do with a value is the same everywhere.\n\nValues from different columns can be combined. Multiply the price by the stock on hand and we get the value of the inventory, and it is handy to give this new column an alias. Text has its own operation, concatenation: two vertical bars join strings into one. This way you can build a label such as name, city, or add a constant tag to every row. Keep in mind that numbers are turned into text automatically in concatenation. But if one of the joined values is empty, the result is empty too, and we will come back to this in chapter four.\n\nSometimes you do not need a list of all the rows, but a list of what occurs. Which cities our customers live in, which categories the products have, which statuses orders can have. If you simply select a column, the repeats stay. The word DISTINCT right after SELECT removes duplicates. It applies to the whole result row at once: if there are several columns, only pairs that match in every column count as identical. DISTINCT costs more than a plain select, because the database has to compare rows with each other, so do not add it just in case.\n\nWhen a query has a single table, plain column names are enough. But as soon as a second table appears with a column of the same name, confusion arises. So you can qualify a column name by writing the table name and a dot in front of it. A table can also be given a short alias right after its name. This will come in handy with joins. Service queries help you find out which tables and columns exist in the database: the list of tables lives in a system table, and the description of columns is given by a special command called pragma.\n\nLet us sum up. Every select query begins with the word SELECT. Then comes an optional DISTINCT, then a list of expressions, each with its own alias, then the word FROM and a table. Everything else, conditions, sorting, grouping, will be added to this skeleton. Remember three things: rows have no order by themselves, integer division throws away the fraction, and an empty value is contagious. Now you can read a table, choose columns, and calculate. In the next chapter we will learn to keep only the rows we need, using a condition.
