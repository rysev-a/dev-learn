#CHAPTER 29 | The optimizer: statistics, cost, joins, and reading plans
Databases. Chapter 29. The optimizer: statistics, cost, joins, and reading plans. SQL says what to get, but not how. Between the text of a query and the reading of pages from disk stands the optimizer: it considers ways to execute the query and picks the cheapest one by its own estimate. Knowing how it thinks is what separates a person who guesses at a slow query from a person who finds the cause in five minutes. In this chapter we will follow the path of a query, see where cost and row estimates come from, look at how access methods and join algorithms are chosen, and learn to read the output of the EXPLAIN command.\n\nA query goes through stages. Parsing checks the syntax, analysis matches names to tables and types, and rewriting expands views and simplifies expressions. Then the planner builds a physical plan, and the executor pushes rows up the tree of operators. The logical plan describes what to do; the physical plan chooses how: a scan or an index, and which join algorithm. Rules of equivalent transformations push filters closer to the tables, drop unneeded columns early, turn subqueries into joins, and change the join order. The result stays the same, but the running time can change by orders of magnitude.\n\nThe choice between plans is made by cost. This is an abstract unit that accounts for reading pages from disk, processing rows on the CPU, and evaluating expressions. Reading a page sequentially is cheaper than reading it at random: on magnetic disks the difference was tens of times, on solid-state drives it is smaller, and the constant is configurable. The cost estimate depends on the estimate of the number of rows at every step, and the error in it grows from node to node. If the optimizer thinks a filter will leave ten rows, but it leaves a million, the nested loops it chose turn into a disaster.\n\nWhere do the estimates come from? From the statistics collected by the ANALYZE command. For each table it remembers the number of rows and pages. For each column it keeps the fraction of nulls, the number of distinct values, a list of the most common values with their fractions, and a histogram of the rest, split into buckets with an equal number of rows. A condition like column equals value is estimated from the list of common values, or as one share of the number of distinct values. A range is estimated from the histogram. The statistics are collected from a sample, so they are approximate, and they go stale after mass changes to the data.\n\nThe estimate for several conditions relies on the independence assumption: the fractions are simply multiplied. If the conditions are related, for example a city and a postal code, multiplication underestimates the result by tens of times. Then the plan turns out to be suboptimal. For related columns, databases let you create extended statistics: functional dependencies and the number of distinct combinations. Conditions on expressions are also estimated badly: for a function over a column the database does not know the distribution and takes a generic fraction. An index on an expression collects statistics on it as a side effect.\n\nThere are different access methods for a table. A sequential scan reads all the pages in order and wins when most of the rows are needed or the table is small. An index lookup finds the needed rows through the tree and goes to a table page each time. An index-only scan, without visiting the table, is possible when the index covers the query. A bitmap collects page addresses from the index, sorts them, and reads the table sequentially once: it takes the middle ground between a scan and a lookup, when a moderate number of rows match. The choice depends on the estimated fraction of rows.\n\nJoins are chosen from three algorithms. Nested loops go through the rows of the outer table and for each one look for matches in the inner one: they are good when the outer table is small and the inner one has an index. A hash join builds a hash table on the smaller side and walks through the larger one: it is good for large unordered sets and equality conditions, but it needs memory. A merge join walks through two sorted inputs at the same time: it pays off when the sorting already exists, for example from an index. For conditions that are not equality, only nested loops fit.\n\nJoin order is critical. For a query on n tables there are far too many possible orders: the number grows factorially. The optimizer searches through them with dynamic programming, building the best plans for subsets of tables, and for small queries it finds the optimum. When there are many tables, the search is limited, or heuristics and genetic algorithms are used, and then the plan may not be the best. That is why giant queries with twenty joins are worth splitting into steps: intermediate results in common table expressions or temporary tables.\n\nReading a plan means seeing a tree of operators: the leaves read tables, and the inner nodes join, sort, and group. For each node you can see the cost estimate and the number of rows. The EXPLAIN ANALYZE command runs the query and adds the actual values: real time, real number of rows, and number of repeats. The main things to look for are these: an estimate that differs from the actual value by an order of magnitude; a scan of a large table where you expected a lookup; rows thrown away by a filter after being read; a sort on disk; nested loops with a huge number of repeats. You always start with the most expensive node and go deeper.\n\nThe typical causes of bad plans repeat. Stale statistics after loading data. A function or a type cast over an indexed column. OR conditions over different columns. A large offset in pagination. A correlated subquery that runs for every row. Selecting all columns when the index would have been enough. Parameters of different types: a number is compared with a string, and the index is not used. Each of these causes is visible in the plan. The cure: update the statistics, rewrite the condition, add a suitable index, split the query, or change the schema.\n\nPrepared queries with parameters are planned once and then executed many times. This saves parsing and planning time, but it sets a trap: a plan that is optimal for a frequent parameter value turns out to be bad for a rare one, and the other way around. Databases solve this in different ways: they build custom plans for the first calls and then compare their cost with a generic plan, and some choose the plan by the value in the first call. If a query suddenly became slow only for certain values, suspect exactly this. The fixes: hints, separate queries for edge cases, and tuning the planning mode.\n\nTuning is made of simple steps. Find the slow queries from the log and from the summary execution statistics: an extension records the number of calls, and the total and average time. Look at the plan of the most expensive ones. Check the statistics and the indexes. Increase the memory for sorts and hashes if they spill to disk. For heavy queries, turn on parallel execution. Some databases have optimizer hints, while others deliberately do not, and you have to change the query or the statistics. Always measure before and after: optimization without measurement turns into superstition.\n\nLet's sum up. A query goes through parsing, analysis, rewriting, planning, and execution. The optimizer chooses the physical plan by cost estimate, and the estimate relies on statistics and the independence assumption. The access methods are scan, index lookup, index-only scan, and bitmap. The joins are nested loops, hash, and merge, and their choice is determined by sizes and indexes. Read the plan from top to bottom and compare the estimate with the actual value.
