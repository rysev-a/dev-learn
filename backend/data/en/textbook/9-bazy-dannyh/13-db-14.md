#CHAPTER 14 | Common table expressions (CTE, WITH)
Databases. Chapter 14. Common table expressions. Complex queries quickly turn into a nesting doll: a subquery inside a subquery inside a subquery, and you have to read it from the inside out. A common table expression, or CTE, solves the problem: you give an intermediate result a name and write it down before the main query. Such a query can be read from top to bottom, like a story: first we computed one thing, then another, then we assembled the answer. The result is the same as with a subquery, but the query becomes clear and can be checked step by step.\n\nThe syntax starts with the word WITH, then the name of the future temporary table, the word AS, and a SELECT in parentheses. After the parenthesis comes the main query, where you can refer to that name as if it were an ordinary table. The expression exists only for the duration of a single query and is not saved anywhere. The columns come from the inner SELECT, but you can set their names in parentheses right after the name of the expression. If you need several queries with intermediate results, each one gets its own name, and the main query joins them. This is the same thing as a derived table, only written down in advance.\n\nThe main strength of a CTE is names. Instead of anonymous nesting you write a step with a name that describes its meaning: totals by customer, active customers, top products. Any step can be checked separately by running its SELECT. If the result is wrong, you can see at which step the mistake is. For a team it is also documentation: the reader understands the logic without digging into the details. A good practice is to give expressions short but meaningful names and to write one step per idea. One step, one thought.\n\nYou can write several expressions, separating them with commas, and the word WITH is put only once. Each next one can refer to the previous ones. This is how a processing pipeline is built: first we filtered the orders, then grouped them by customer, then picked the best, and at the end joined with the customers table to get the names. Every step is short and clear. The order of declaration matters: you cannot refer to an expression that is declared further down. This style is especially good for analytical queries, which are often revisited and extended.\n\nHow does a CTE differ from a subquery in FROM? The result is the same, but there are two advantages. The first is readability: a name and a top-to-bottom order. The second is reuse: one expression can be referenced several times in a single query, for example to join a result with itself, while a subquery would have to be written twice. The drawback is that sometimes the optimizer plans a query with an expression worse than one with a subquery, although modern versions of SQLite usually inline the expression into the main query. If in doubt, check the plan.\n\nSuppose you need to show the customers whose order total is above the average across all customers. First we compute the total for each customer in one expression. Then, from the same expression, we compute the average and compare it with each customer's total. The same expression is used twice, and we do not repeat the heavy grouping in the text of the query. The same technique works for comparing a month with the previous one and for computing shares of an overall total. The result is a query where each figure is defined once.\n\nA CTE is handy when you need to filter or join on the result of an aggregate. In the expression we compute the totals by customer, and in the main query we filter with WHERE, join with the customers table, and sort. Such a query is simpler than HAVING with a subquery, and it gives you the aggregate as an ordinary column. This is especially useful when the same total has to be used for filtering, sorting, output, and also in further calculations. HAVING is not needed here: the total is already available as a column.\n\nA special form is the recursive expression. The word RECURSIVE after WITH allows the expression to refer to itself. It consists of two parts joined by UNION ALL: a starting part, which produces the first rows, and a recursive part, which builds the next rows from the ones already obtained. The database repeats the recursive part as long as it returns new rows. This way you can get a sequence of numbers or dates, or walk along a chain of links. It is the only way to traverse a hierarchy of arbitrary depth in pure SQL, without loops in the program.\n\nThe simplest example is the numbers from one to ten. The starting part returns one. The recursive part takes the current number and returns it plus one, as long as it is less than ten. A stop condition is required, otherwise the recursion will never end. In the same way you build a series of dates: from the first of May to the last, to then join it with orders and show zeros on days without sales. Ordinary tables do not store such gaps, but a series generated by recursion lets you see and count them.\n\nThe main use of recursion is trees. In an employees table, everyone has a manager from the same table. The starting part takes the root, that is, the one who has no manager. The recursive part joins the employees found so far with the table and takes their subordinates, increasing the level by one. This gives you all the levels of the organization, and in a separate column you can collect the path from the root: the names joined with a separator. Such queries are used for categories, comment threads, folder structures and graph routes.\n\nIf the data contains a cycle, for example an employee who through a chain of managers reports to himself, the recursion will never end. The first protection is a stop condition on the level, for example a depth of no more than twenty. The second is UNION instead of UNION ALL: it discards repeated rows, and the recursion stops when new rows no longer appear. For trees without cycles UNION ALL is enough, and it is faster. For graphs that may have cycles it is better to store the path already traveled and check that the vertex is not in it, plus a limit on the result as insurance.\n\nA CTE is first of all a way of writing a query, not an optimization. SQLite inlines the expression into the main query, like a subquery, and the plan comes out the same. If an expression is used several times, you can ask for it to be computed once and stored, with the word MATERIALIZED. And conversely, NOT MATERIALIZED asks to inline it. When an intermediate result is huge and needed many times, it is better to create a temporary table and build an index on it. And for small analytical queries, expressions are the best way to make the code clear.\n\nLet's sum up. A common table expression gives an intermediate query a name and lets you write complex queries step by step from top to bottom. There can be several expressions, and each sees the previous ones. One step can be used many times. A recursive expression with UNION ALL generates series and walks trees, and it needs a stop condition. The expression by itself does not make anything faster: it is a way of writing. In the next chapter we will meet window functions, which let you compute running totals, ranks and comparisons with neighboring rows without grouping.
