#CHAPTER 12 | Grouping data: GROUP BY and HAVING
Databases. Chapter 12. Grouping data. Aggregate functions give a single total for the whole table. But usually we need totals by group: how many orders each customer has, what the revenue is in each month, how many products there are in each category. That is what GROUP BY is for: it splits the rows into groups with the same key value and applies an aggregate to each group separately. The result is one row per group. This is one of the most widely used techniques in analytics, and almost every report depends on how well you master it.\n\nThe syntax is simple: after FROM and WHERE you write GROUP BY and the column you divide by. Rows with the same value fall into the same group. Say we group orders by status: we get three groups. In the column list you can write the status itself and aggregates over the group: the number of orders and the total. The order of the groups in the result is not defined, so if you need an order, add ORDER BY. Grouping happens after the WHERE filter, so only the selected rows get into it, and that greatly reduces the work for the database.\n\nHere is the rule for the column list in a grouped query: you can write only things that are the same for the whole group, that is, the grouping keys themselves, and aggregate functions. Other columns have no single value for a group. If you select such a column, strict databases will raise an error, while SQLite will return the value from an arbitrary row of the group, and the result will be misleading. The exception is a query with min or max: the database takes the other columns from the same row where the extreme value was found. This is a quirk specific to SQLite.\n\nThere can be several grouping keys. Then a group is a unique combination of values: customer and status, category and month. If the table has three customers and four statuses, there could potentially be twelve groups, but in reality there are as many as the pairs that actually occurred in the data. The order of the keys in GROUP BY does not affect the result, and the shape of the result is affected only by the order of columns in SELECT. This kind of grouping gives detail: each customer broken down by the statuses of their orders. It is the basis of pivot tables.\n\nA group key doesn't have to be a column; it can be an expression. Grouping by month is a strftime expression over the date. Grouping by order size is a CASE that turns the total into a category. Grouping by parity of the number is a remainder of division. Write the expression in SELECT with an alias, and in GROUP BY either repeat it or refer to the alias: SQLite allows this, although the standard does not. This approach makes grouping a universal tool: any attribute you can compute is good for splitting into groups.\n\nWhat should we do about gaps in the grouping key? Grouping treats all nulls as one value, and they form a separate group. If some customers have no city specified, the result will have a row with an empty city and a combined count of those customers. Often that is exactly what you need: you can see how much data is not filled in. If such a group gets in the way, filter it out with a WHERE condition, or substitute a name through coalesce: not specified. But don't forget that aggregates over the empty column itself also ignore the gaps.\n\nWHERE filters rows before grouping and cannot use aggregates. But how do you select groups by their totals: customers whose orders add up to more than fifty thousand, or categories with more than five products? For that there is HAVING. It runs after grouping and sees the aggregates. A condition in HAVING is written the same way as in WHERE, but here you can use count, sum and other functions. HAVING without GROUP BY is also allowed: then the whole table is treated as one group, but in practice that form is rarely seen.\n\nThe rule for choosing is simple. If the condition applies to an individual row, it belongs in WHERE: for example, the order status equals paid. If the condition concerns the group's total, it belongs in HAVING: for example, the sum is greater than one thousand. A condition on the group key can be written in either place, but in WHERE it works faster, because unneeded rows are discarded before grouping. So whatever can be filtered earlier, filter in WHERE, and keep HAVING for conditions that can't be expressed without an aggregate.\n\nNow we can write down the complete order in which a query is executed. First FROM assembles the tables and joins, then WHERE selects rows, GROUP BY splits them into groups, HAVING selects groups, SELECT computes expressions and aggregates, DISTINCT removes duplicates, ORDER BY sorts, and LIMIT cuts the result. This is exactly why you can't use aliases and aggregates in WHERE, but you can in ORDER BY. Whenever you wonder why a query doesn't work, compare it with this list. It explains almost all error messages.\n\nYou can also sort by an aggregate. This is the basis of rankings: the five customers with the largest order totals, the three most popular categories. You write the grouping, then ORDER BY on the aggregate or its alias, and then LIMIT. If several groups have the same total, add a second key, for example the name, so that the order at the edge of the top is unambiguous. You should know this query by heart: it appears in reports, in interviews and in everyday work all the time, and it hardly changes from one domain to another.\n\nTo show totals per customer together with their names, you need to join the tables and group by the customer id. The name comes from the customers table, and the sums come from the orders. It is better to group by id and not by name: names can coincide, and then different customers will stick together into one group. If you also need customers without orders, you use a left join, and in the aggregate you count a column of the right table: count of the order id gives zero where there are no orders, while count star would give one.\n\nWhich mistakes are the most common? An extra column in SELECT that is neither part of the key nor an aggregate. A condition on an ordinary column in HAVING instead of WHERE: it works, but more slowly. Grouping by name instead of by key. Row multiplication after a join, when the order total is repeated for each item. Count star after a left join, which counts the empty row. Check on a small data set: calculate the result by hand on five rows and compare it with what the query returned.\n\nLet's sum up. GROUP BY splits rows into groups by a key, and aggregates are computed for each group. SELECT may contain keys and aggregates. There can be several keys, and a key can be an expression. Nulls form a separate group. HAVING filters groups by aggregates, while WHERE filters rows before grouping. Sorting by an aggregate together with LIMIT gives the top groups. The complete order of execution explains what can be used where. That completes the fourth part of the course. Next we will turn to speed: indexes and query plans.
