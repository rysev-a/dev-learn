#CHAPTER 18 | Transactions and isolation levels
Databases. Chapter 18. Transactions and isolation levels. Transferring money from one account to another is two operations: debit the sender and credit the recipient. If the server crashes between them, the money vanishes. If two transfers run at the same time, one can overwrite the result of the other. It is exactly for such cases that databases have the transaction: a group of operations that is executed as a single whole. The properties of a transaction are described by the acronym ACID: atomicity, consistency, isolation and durability. In this chapter we will go through each of them, and then see how databases achieve this.\n\nAtomicity means "all or nothing". A transaction starts with the command BEGIN and ends either with a COMMIT, which makes all the changes permanent, or with a ROLLBACK, which cancels all of them. If the connection drops or a constraint fires, the database rolls back the unfinished transaction by itself. To make that possible, the database keeps an undo log: the previous values of the changed rows. A rollback is simply restoring those values. Inside a transaction you can set savepoints and roll back to them without cancelling all the work. That way, an error in one part of a complex operation does not have to kill the rest.\n\nConsistency is a move from one valid state of the database to another. Validity is defined by constraints: foreign keys, uniqueness, checks. But there are also business rules that the database does not know: the total on the accounts must not change during a transfer. The application is responsible for upholding them, and the transaction helps: either both steps are done, or neither. Notice that consistency is the only letter the database does not guarantee on its own: it follows from the other three and from properly written logic. Constraints are checked at the moment of the change or, if declared that way, at commit.\n\nIsolation answers the question: what does a transaction see while others are working alongside it? The ideal is as if transactions ran one at a time. But that is expensive, so databases let you weaken isolation, and in exchange for speed, anomalies appear. The first of them is the dirty read: you saw the changes of someone else's transaction that was later rolled back, and made a decision based on data that never existed. This is so dangerous that most databases do not allow it at all: the lowest isolation level in Postgres rules out dirty reads.\n\nThe second anomaly is the non-repeatable read. A transaction read a row, another transaction changed it and committed, and reading again gave a different value. Within one transaction, the world changed. A related anomaly is phantoms: a repeated query with a condition returns new rows that someone else's transaction inserted. For reports that reconcile several queries with each other, this is unacceptable: the totals by parts will not add up to the overall total. Both effects are cured by an isolation level at which the transaction works with a snapshot of the data as of its start.\n\nThe most treacherous anomaly is the lost update. Two transactions read a balance of one hundred, both add ten and write one hundred ten; one top-up disappears. The pattern "read, change in the application, write" is dangerous in itself. It is cured by an atomic update right in the database, an UPDATE with arithmetic in a single query, or by locking the row on read, or by checking a version. A close relative is write skew: two transactions read the same condition, for example "at least one doctor on duty", and each takes its own doctor off duty. Each is right on its own, but together they broke the rule.\n\nThe SQL standard defines four isolation levels. Read uncommitted allows dirty reads. Read committed guarantees that you see only committed data, but each query sees a fresh snapshot. Repeatable read fixes the snapshot for the whole transaction. The serializable level guarantees a result as if the transactions ran strictly one after another. The higher the level, the fewer the anomalies and the greater the risk of conflicts and retries. In Postgres the default is read committed, in MySQL it is repeatable read, and in SQLite any write is serialized as a whole.\n\nWhat does "as if one after another" mean? Take a schedule: the order of operations of several transactions interleaved in time. Two operations conflict if they are on the same object, from different transactions, and at least one of them writes. From the conflicts we build a graph: an edge from the first transaction to the second if the first one's conflicting operation happened earlier. A schedule is serializable when this graph has no cycles, and then an equivalent serial order exists. Databases achieve this in two ways: two-phase locking, where locks are taken as you go and released only at commit, and optimistic dependency tracking, which rolls back one of the participants when a cycle appears.\n\nHow do databases let you read without getting in the way of writes? Through multiversioning, MVCC. Every change creates a new version of the row, and the old one stays as long as some snapshot needs it. A version is tagged with transaction numbers: who created it and who deleted it. A transaction gets a snapshot: the list of those who have already committed, and it sees only the versions created by them. That is why readers do not block writers, and writers do not block readers. The price is that old versions pile up, and background cleanup removes them periodically; in Postgres it is called vacuum. A forgotten long transaction keeps the cleanup from working, and the tables bloat.\n\nWhere versions are not enough, locks do the work. A shared lock allows other readers, an exclusive lock allows nobody. The query SELECT FOR UPDATE locks the selected rows until the end of the transaction, and other writers wait. Two transactions can lock each other: one holds row A and waits for B, the other holds B and waits for A. This is a deadlock. The database finds the cycle in the wait graph and forcibly rolls back one of the transactions. The main way to avoid deadlocks is to take locks in the same order and to keep the transaction short.\n\nLocking can be pessimistic, when we close off the row in advance, and optimistic, when we work freely and at write time check that nobody has changed the data. The simplest form of the optimistic approach is a version column: the update fires only if the version is unchanged, and increments it. If zero rows are affected, someone got there first, and the operation is retried. The optimistic approach wins when conflicts are rare, and the pessimistic one when they are frequent and a retry is expensive. Both are better than hoping that concurrency will not happen, because in production it certainly will.\n\nNow durability. When the database has answered "committed", the result must survive a power failure. To achieve this, changes are first written to the write-ahead log, and only after the log is forced to disk, with fsync, is the commit considered done. The data pages themselves may reach the disk later: after a crash the database replays the log. This cost shows up in commit latency, so group commit combines the records of several transactions into one fsync. Turning fsync off speeds the database up, but brings back the risk of losing confirmed data.\n\nLet us sum up and state some practical rules. Keep transactions short and do not wait inside them for a human or an external service to respond. Choose the isolation level deliberately: read committed is enough by default, but critical invariants need the serializable level or explicit locks. The application must answer serialization errors and deadlocks by retrying the whole transaction. Make operations idempotent so that a retry does not double the result. Atomicity, isolation and durability are the responsibility of the database; consistency is shared. Next we will look at how databases find the rows they need quickly: indexes.
