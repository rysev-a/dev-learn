#CHAPTER 23 | Sharding: splitting data across machines
Databases. Chapter 23. Sharding: splitting data across machines. Replication copies the same data to several machines, but it does not help when there is more data than fits on one machine, or when writes have hit the disk limit of a single leader. Then the data gets divided, and each machine stores only a part of it. This division is called sharding, and a part of the data is called a shard or a partition. You can scale one server up vertically, and that is the simplest path, until it hits the ceiling of price and capability. Horizontal scaling adds machines, but it complicates everything: queries, transactions, maintenance. In this chapter we will look at ways to divide data, routing, skew, and the price of this decision.\n\nThe main decision is the shard key: the field that determines where a row lives. The key should appear often in queries, otherwise you will have to ask every shard, and it should give an even distribution, otherwise one machine ends up overloaded. For a shop, natural keys look like the customer number or the order number; for a multi-tenant service, the tenant identifier. Once the key is chosen, you still need a function that turns the key value into a shard number. There are two families here: by ranges and by hash.\n\nRange sharding cuts the key axis into segments: from zero to a million goes to the first shard, up to two million to the second, and so on. The main advantage is that neighboring keys live side by side, so range queries go to one or two shards. The drawback is skew. If keys grow monotonically, for example time or an auto-increment counter, then all new records land in the last shard while the others sit idle. This hot spot is called tail overload. Ranges suit data where ordering and range queries matter, but the key must be chosen so that the load spreads out.\n\nHash sharding applies a hash function to the key and takes the remainder of dividing by the number of shards. The hash mixes the values, so the load is even even when keys come in sequence. The price is that neighboring keys are scattered, and range queries turn into asking every shard. But there is a more serious problem. If the number of shards changes, the remainder changes for almost every key: adding a fourth shard to three forces three quarters of the data to move. For a live system, such a mass migration is unacceptable.\n\nThe way out is consistent hashing. The hash space is closed into a ring, and both nodes and keys are placed on the ring. A key belongs to the first node clockwise from its position. When a node is added, only a part of its neighbor's keys move to it, roughly one over N of all the data, and the rest stay where they are. To even out the load, each physical node is placed on the ring in several spots; these are virtual nodes. Dynamo, Cassandra, and many caches use this mechanism. It also makes it easy to pick replicas: the next nodes along the ring.\n\nThere is also the directory approach. A separate service stores a table of key or range to shard. It is flexible: you can move one tenant to a dedicated machine, or place data closer to its country. The price is one more system, which has to be made reliable and fast, and which must not become a bottleneck. Often the two are combined: a directory for tenants, and hashing within each tenant. The choice of scheme is dictated by the queries: if almost all of them touch a single tenant, that tenant's data is better kept together.\n\nHow does a query find the right shard? You can build the rules into a client library, and then the client computes the shard itself and goes straight there: fast, but updating the rules means updating the clients. You can put in an intermediary, a proxy or router, that accepts requests and forwards them; the clients stay simple. Or you can arrange that any node knows the map and redirects on its own. The shard map changes rarely, so it is cached, and on a wrong-shard error it is requested again. This is how Redis Cluster, Vitess, and Citus work, for example.\n\nQueries that do not contain the shard key have to run on all shards and merge the results; this technique is called scatter-gather. It loads the whole system, and the response time is set by the slowest shard, so any latency tails add up noticeably. Sorting and pagination also get harder: you need to pull a few rows from each shard and merge them. Secondary indexes are also distributed in two ways. A local index lives in the shard together with the data: writes are fast, but a search goes to all shards. A global index is itself sharded by the indexed value: the search is precise, but a write touches several shards.\n\nData grows and load changes, so shards have to be redistributed, that is, rebalanced. A common practice is to split the data into many small partitions in advance, far more than there are machines, and simply move whole partitions between machines; the key is not recomputed. When a partition becomes too large or too hot, it is split in half, and when it becomes too small, it is merged with a neighbor. The move runs in the background: the data is copied, the changes from the log are caught up, and the route is switched, without stopping the system. Automatic rebalancing is convenient, but it creates load, so it is better to start it deliberately.\n\nThe most painful part of sharding is operations that touch several shards. A transaction that changes data on two machines requires coordination. The classic protocol is two-phase commit: the coordinator first asks all participants whether they are ready to commit, and only if everyone answers yes does it send out the commit command. It is reliable, but it blocks: if the coordinator crashes between the phases, the participants wait, holding their locks. That is why distributed systems prefer sagas: a sequence of local transactions with compensating actions. The best option is to design the key so that related data lands in the same shard.\n\nAnother problem is hot keys. If one customer or one celebrity generates a disproportionate stream of requests, the shard where they live is overloaded, and even hashing will not save you. Adding a random salt to the key helps: the records of one object spread across several shards, and a read gathers them together. A cache in front of the database for the most popular keys helps too, as does moving hot tenants to dedicated machines. The main thing is to monitor skew: the load on each shard and the most frequent keys, not just the averages across the cluster.\n\nBefore you shard, it is worth trying cheaper tools. Replication and a cache take the read load off. Partitioning inside a single database splits a big table into pieces by date or key, speeding up maintenance, while transactions stay ordinary. There are also systems that take sharding on themselves: Spanner, CockroachDB, Vitess, Citus. They hide routing, rebalancing, and distributed transactions, but they do not repeal the laws of physics: queries without the shard key are still expensive. Shard when other methods are exhausted, and choose the key carefully.\n\nLet's sum up. Sharding divides data between machines by a key. Ranges give ordering but skew, hashing gives evenness but loses ranges, and consistent hashing with virtual nodes lets you change the number of machines with minimal movement. Queries without a key go to all shards, transactions across shards are expensive, and hot keys need to be spread out. Rebalancing and routing are part of operations. Next we will talk about what distributed systems actually guarantee: the CAP theorem, latency, and honest promises of consistency.
