#CHAPTER 17 | Data model and queries: tables, relationships, joins and grouping
Databases. Chapter 17. Data model and queries: tables, relationships, joins and grouping. Why can't we just keep data in files? As long as there is one user, a file will do. But as soon as two processes write to it at the same time, the lines get mixed up; as soon as the program crashes in the middle of a write, the file is left half updated; and to find all the customers from Kazan, you have to read the whole thing. A database takes on exactly these concerns: concurrent access, durability, integrity and fast search. We will start with the most widespread model, the relational one, which Edgar Codd came up with in nineteen seventy, and with SQL, the language used to talk to it.\n\nThe foundation of the relational model is the table. Columns describe what information is stored, and every column has a name and a type: an integer, a string, a date. Rows are the records themselves: one customer, one product, one order. An important property: the rows in a table are not ordered, and if you need an order, you have to ask for it in the query. To tell rows apart, a table has a primary key, a column or a set of columns whose values are unique. Most often it is an integer number. For our shop example we will have four tables: customers, products, orders and order items.\n\nA read query starts with the word SELECT. In it you list the columns you need, which is called projection, and after the word FROM you name the table. The condition after the word WHERE picks rows, an operation called selection: for example, products costing more than a thousand rubles. The words ORDER BY and LIMIT sort the result and cap its size. Notice that SQL is declarative: you describe which result you want, and how to get it is decided by the database optimizer. The same query can run in completely different ways on a tiny file and on a huge table.\n\nA special place belongs to the value NULL. It means "unknown" or "not set", and it is neither zero nor an empty string. Comparing anything with NULL gives neither true nor false, but a third value, "unknown", so the condition "value equals NULL" never fires: you have to check with the operator IS NULL. Rows for which the WHERE condition is unknown do not make it into the result. Arithmetic with NULL also gives NULL. To fill in the gaps there is the function COALESCE, which returns the first value that is not NULL. The trap with the NOT IN operator is especially nasty: if the list contains a NULL, the query returns no rows at all.\n\nSo that the database can protect the data itself, columns and tables have constraints. NOT NULL forbids gaps, UNIQUE forbids duplicates, CHECK verifies an arbitrary condition, for example that a price is not negative. A primary key combines uniqueness and being required. A foreign key links tables: the column customer id in orders must refer to an existing customer, and the database will refuse to insert an order for a nonexistent person or to delete a customer who has orders. For deletion you can specify a cascade, and then the dependent rows are deleted automatically. The rule is simple: whatever can be checked in the database is best checked in the database, because there may be many applications.\n\nIn a relational database, data is spread across tables, and the relationships between them are expressed with keys. A one-to-many relationship is simple: an order has a customer, and the order holds a reference to that customer. But how do you express many-to-many? An order contains many products, and a product appears in many orders. For this you create a junction table: its row joins an order number and a product number and stores the quantity. This splitting is called normalization: every fact is recorded in exactly one place, so there is no need to fix it in several places. The price is that to assemble the whole picture, you have to join the tables.\n\nA join glues together rows of two tables by the condition after the word ON. An inner join keeps only the pairs that matched: an order together with its customer. Picture a nested loop: for every row of the left table we look for matching rows of the right one. Real databases do this more cleverly, with indexes and hash tables, but the result is the same. If there are several matching rows, the row on the left is repeated that many times. This is the main thing to remember: a join multiplies rows. Of course, for columns with identical names you have to specify the table, and tables are usually given short aliases.\n\nWhat if you also need those customers who have no orders? An inner join will lose them. This is where the left join helps: it keeps all rows of the left table, and where no pair was found, it fills in NULL. To find customers without orders, it is enough, after the left join, to keep the rows where the column of the right table is NULL. But there is a subtlety: a condition on the right table placed in WHERE will throw out exactly those rows with NULLs and quietly turn the left join into an inner one. Conditions on the right table that must not remove left rows are written in the ON clause itself.\n\nGrouping turns many rows into one. After GROUP BY, rows are collected into groups by the value of a column, and aggregate functions compute over each group: COUNT is the number of rows, SUM the total, AVG the average, MIN and MAX the extreme values. COUNT of star counts all rows, while COUNT of a column counts only those where it is not NULL. A condition on individual rows is written in WHERE, and it acts before grouping, while a condition on groups is written in HAVING, and it acts after. Every column in SELECT must either be part of the grouping or be wrapped in an aggregate, otherwise it is unclear which value from the group to take.\n\nThe main trap of reports: you joined orders with items and payments, computed a sum, and it came out three times larger than the real one. The reason is that every join multiplies rows: the order was repeated for each item, and then again for each payment. The aggregate counted the duplicates. The right way is to compute each branch separately: first collapse the items into one row per order, the payments into another, and only then join. Subqueries and temporary named queries with the word WITH, called common table expressions, are handy for this. A query with them reads top to bottom like a program, and each part can be checked separately.\n\nA subquery is a query inside a query. A scalar subquery returns a single value, for example the average price that rows are compared against. A subquery in the IN operator returns a set of values. The EXISTS operator checks whether there is at least one matching row, and it is usually faster than counting all of them. A correlated subquery depends on the outer row and, in principle, runs for each of them, although the optimizer often rewrites it into a join. A good habit is to write the query clearly first, and then, if it is slow, to look at the execution plan, which we will discuss in the chapter on indexes.\n\nData is not only read. INSERT adds rows, UPDATE changes them, DELETE removes them. UPDATE and DELETE have a dangerous feature: without a WHERE condition they affect the whole table, so before changing anything it is useful to check the same condition with a plain SELECT. Many databases can return the changed rows with the word RETURNING, which saves an extra query. And "insert, but if such a key already exists, update" is done by the ON CONFLICT construct, known as upsert. All these operations obey the constraints: if an insert violates a key, the database rejects it entirely, and the table stays untouched.\n\nLet us sum up and look at the order. Although we start writing a query with the word SELECT, logically it is executed in a different order: first FROM and the joins assemble rows, then WHERE throws out the extra ones, GROUP BY builds groups, HAVING picks groups, then SELECT computes columns, ORDER BY sorts, and LIMIT cuts off the rest. Many rules follow from this order: an alias from SELECT cannot be used in WHERE, and an aggregate cannot be used in WHERE. Tables, keys, constraints, joins and grouping are the foundation on which all the other topics of this book stand: transactions, indexes and distributed databases.
