#CHAPTER 16 | Views (VIEW)
Databases. Chapter sixteen. Views. A complex query with several joins has to be written from scratch every time, and in an application it also gets copied into a dozen places. A view solves this problem: you save a query once under a name, and then refer to it like a table. A view stores no data. It stores only the query itself and runs it on every access. So its result is always fresh, and the view itself takes up very little space.\n\nA view is created with the CREATE VIEW command: a name, the word AS, and any SELECT. A query with joins, grouping, conditions and functions will do. The view's columns take their names from the SELECT, so calculated columns need aliases. You can also set the column names in parentheses after the view's name. A good rule is to start view names with a prefix, for example v underscore, so that the name shows it is not a table. A view is removed with the DROP VIEW command, and this does not affect the table data.\n\nA view you've created is used in queries exactly like a table. You can select columns from it, filter by a condition, sort, group, and join it with other tables and views. For the caller it makes no difference what stands behind the name: a table or a complex query with five joins. This makes life easier for analysts and applications: it's enough to know one name and a list of columns. And the author of the view can change its internals without affecting those who use it, as long as the names and meaning of the columns stay the same.\n\nThe main benefit of views is to hide complexity and gather the rules in one place. What an active customer or revenue means is decided by a single view, and all reports use the same definition. If the rule changes, it is fixed once, not in twenty queries. In addition, a view gives a stable interface: the application reads from the view, and the table structure behind it can evolve. This is especially valuable in large teams, where different people write queries against the same data and must get the same answers.\n\nA view can show only part of a table: only some columns, or only the rows that match a condition. This is how you hide service fields such as passwords, internal notes and other people's data. In serious databases, permissions are set up for views: a user is given access to the view but not to the table. SQLite has no permission system of its own, so hiding works only as an agreement within the application. But even so, a view protects against accidental mistakes: if a column isn't in it, it can't be selected by oversight.\n\nA view copies nothing. A query to it is turned into a query to the tables underneath, so the data is always up to date: add an order and it is immediately visible in the totals view. The flip side is that if the query inside is complex and heavy, it will run on every access. For heavy reports that are needed often while the data changes rarely, you make a separate table and refresh it periodically. This technique is called materialization. SQLite has no dedicated materialized view, so an ordinary table takes its place.\n\nViews can be built on top of each other. The first layer gathers orders with customers, the second adds monthly totals to it, the third picks the best ones. Each layer is simple, and together they form a clear chain. But remember that in the end everything is expanded into one big query against the tables, and deep nesting makes the plan hard to understand. So make only a few layers and name them by meaning. And before changing a lower view, find out which upper views depend on it.\n\nHow do you change a view? In Postgres there is CREATE OR REPLACE VIEW, but SQLite has no such command. Here you drop the view and create it again, preferably in one transaction, so that no one sees the moment when it is missing. For re-running scripts, IF EXISTS and IF NOT EXISTS help. Also, you can't change a view with ALTER. So the text of a view's query should be kept in a migration file, not only in the database: it is easier to edit and restore from there.\n\nCan you insert and change data through a view? In SQLite, no: it is read-only. If you need to allow writing, you create an INSTEAD OF trigger, which intercepts an insert into the view and runs the needed commands on the tables. In other systems, simple views built on one table without grouping are updated automatically. For complex views with joins and grouping, updating is impossible: it's unclear which row of the source table to change. So it is better to write data directly to the tables.\n\nDoes a view affect speed? By itself, almost not at all. SQLite expands it into a query against the tables and builds a single overall plan, so table indexes work just as in an ordinary query. A condition you add to the view is often pushed inside and reduces the amount of work. But if the view contains grouping or window functions, a condition on the result can't always be pushed down, and the database first computes everything. So look at the plan of the query against the view, not only against its body.\n\nA few warnings. If a view uses a star, it is expanded once, at creation, and new table columns will not appear in it afterwards. So list the columns explicitly. If you rename or drop a column that the view refers to, accessing the view ends with an error. ORDER BY inside a view is usually pointless: the order is set by whoever uses it. And finally, long chains of views are hard to debug, so document what each of them does and what it depends on.\n\nA few habits make views convenient. Give them names with a prefix and by meaning: v underscore active customers, v underscore revenue by month. List columns explicitly and give them clear aliases. Keep definitions in migration files, not only in the database. Check the plan of access to the view on real data. And don't overuse them: if a query is used once, you don't need a view, a common table expression is enough. A view is good where the same definition is reused by many queries and many people.\n\nLet's sum up the chapter. A view is a named query that stores no data: the definition lives in one place, and the result is always fresh. In SQLite it is read-only and is changed by re-creating it.
