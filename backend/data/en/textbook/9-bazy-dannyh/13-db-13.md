#CHAPTER 13 | Indexes and optimizing simple queries
Databases. Chapter 13. Indexes and optimizing simple queries. While a table holds a dozen rows, any query runs instantly. But when there are millions of them, a query like find the orders of customer number five, with no preparation, turns into reading the whole table from the first row to the last. It is the same as looking for a surname in a book that has no alphabetical index. An index is exactly that kind of pointer: a separate structure that stores the values of a column in sorted order, along with references to the rows. With an index the database goes straight to the right place instead of checking everything in turn.\n\nInside, an index is a balanced tree, most often a B-tree. The root and the intermediate nodes hold range boundaries, and the leaves hold the key values themselves and references to the table rows. To find a value, the database descends from the root to a leaf, choosing the right branch at each step. Even for a billion rows the tree is only four or five levels deep, so a search takes a few disk accesses instead of millions. The leaves are linked to each other in order, so ranges of values are read one after another, without going back to the root.\n\nAn index is created with the CREATE INDEX command: a name, a table, and the columns in parentheses. The name is usually built from the table and the columns, for example the prefix idx, then orders, then customer. A unique index, CREATE UNIQUE INDEX, additionally forbids duplicate values: that is how the UNIQUE and primary key constraints work. For a primary key, an index is created automatically. Once it exists, the database maintains the index on every insert, update and delete, and the optimizer will use it on its own, so you never have to mention the index name in a query. An index is removed with DROP INDEX, and this does not affect the data.\n\nHow do you find out whether a query uses an index? Put the words EXPLAIN QUERY PLAN in front of the query. The database will not run the query, but will show the plan: which tables it goes through and with which indexes. The word SCAN means a full pass over the table, and the word SEARCH followed by an index name means a lookup through that index. For a query on a customer's orders you will see SCAN without an index, and after you create one, SEARCH USING INDEX. The habit of reading plans is the main optimization tool: instead of guessing, you see what the database really does.\n\nAn index speeds up conditions on equality, ranges, greater than and less than, BETWEEN and IN. It also helps with sorting: if the needed order is already in the index, ORDER BY does not need a separate sort. MIN and MAX on an indexed column are computed in one step: the database takes the first or the last leaf. And for grouping, an index on the grouping key cuts down the work of the grouping. But the optimizer makes the decision itself: if scanning the table is cheaper, for example when you need almost all of it, it will not use the index.\n\nAn index can be built on several columns at once. The values are ordered by the first column, and among equal ones by the second, and so on. That is why such an index helps a query that uses the first column, or the first and the second together, but hardly helps a query on the second column alone. This is the leftmost prefix rule. The order of the columns is chosen to fit the task: first the ones with equality conditions, then ranges and sorting. One well-chosen composite index replaces several single-column ones and takes less space.\n\nAn index is easy to bypass by accident. If the condition calls a function on a column, for example UPPER or strftime, the database cannot rely on the ordering of the values and falls back to a scan. A LIKE with a pattern that starts with a percent sign is also a scan, because you cannot search by a prefix. A condition with OR across different columns, and implicit type conversion, when a number is compared with a string, often have the same effect. The way out is to rewrite the condition so that the column stands on its own: instead of a function of the column, write a range of values.\n\nUsually, after the index lookup, the database goes to the table for the remaining columns. But if all the columns the query needs are already in the index, the trip to the table becomes unnecessary. Such an index is called covering, and in the query plan you will see the words USING COVERING INDEX. This noticeably speeds up frequent queries with a small set of columns. To get it, you add the needed columns to the index after the main ones. But every extra column makes the index bigger, so covering indexes are created only for the hottest queries.\n\nAn index has a price. Every insert, update and delete has to keep all the table's indexes up to date, which means writes get slower. Every index takes space on disk and in memory, sometimes comparable to the table itself. That is why indexes are not created just in case: each one should have a query that it helps. Tables that are mostly written to and rarely read are kept with almost no indexes. And reference tables, which are read all the time, on the contrary, are indexed generously.\n\nHow useful an index is depends on selectivity: how much the condition narrows down the result. An index on an email, where every value is unique, is ideal. An index on a flag with two values, for example VIP or not, is useless: the condition returns half of the table, and it is cheaper for the database to read everything in sequence. The optimizer estimates this from statistics, which are gathered by the ANALYZE command. So index the columns that have many distinct values and often appear in conditions, joins and sorting, and do not expect miracles from the rest.\n\nIn a join, for each row of one table the database looks for matching rows in the other. If the other table has no suitable index, it scans that table entirely for every row of the first one: that is quadratic work. That is why foreign key columns must be indexed. For the orders table that is an index on the customer number, and for order items, on the order number. You can check that a join uses an index in the query plan: next to the second table you should see the word SEARCH with an index name, not SCAN.\n\nSQLite supports special kinds of indexes. A partial index is built only for the rows that match a condition, for example only for active orders, and so it takes less space. An expression index is built on the result of a function, for example the lowercase form of an email, and then a query condition with the same function uses the index. The condition in the query must match the expression in the index letter for letter, otherwise the optimizer will not apply it. These indexes are needed rarely, but they solve exactly the tasks where ordinary ones do not help.\n\nLet's sum up. An index is a sorted structure that lets you search without reading the whole table. It is created with CREATE INDEX, and its use is checked with EXPLAIN: SCAN means a full pass, SEARCH means a lookup through an index. It helps with equality, ranges and sorting, and does not work when a function is applied to the column or when a pattern starts with a percent sign. Composite indexes follow the leftmost prefix rule. Every index costs space and write speed. In the next chapter we will learn to write long queries so that they can be read: with the help of common table expressions.
