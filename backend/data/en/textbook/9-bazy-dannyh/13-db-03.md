#CHAPTER 3 | Sorting and Limiting Rows
Databases. Chapter three. Sorting and limiting rows. The result of a query is a set of rows, and a set has no order. As long as you read a whole table, the rows usually come back in the order they were written, and that creates a false feeling that there is an order. But add an index or a condition, and the rows may come back in a different order, and an application that relied on the old one will break. If the order matters, you have to ask for it explicitly. For that, you write ORDER BY at the end of the query, and to take only part of the result, you write LIMIT.\n\nAfter the words ORDER BY, you name the column the result should be sorted by. The default order is ascending, and you can spell it out with the word ASC. To get the biggest values first, you add the word DESC, which means descending. You can sort numbers, dates, and text. The column you sort by doesn't have to be in the select list: you can order products by price without showing the price itself. Sorting happens at the very end, on top of the finished result.\n\nText is sorted alphabetically, but in a database the word alphabetical has its own meaning. By default, SQLite compares strings byte by byte, that is, by character codes. So all the uppercase Latin letters come before the lowercase ones, and Cyrillic comes after Latin. For words in the same case, the result looks the way you expect, but words that start with an uppercase letter and words that start with a lowercase one can end up far apart. If you need case-insensitive sorting, you have to convert the values to one case with a function, or specify a collation rule.\n\nOften the values in a column repeat, and then the order among equal ones is undefined. To bring order, you list several keys separated by commas. First the rows are sorted by the first key, and those that tie on it are sorted by the second, and so on. The direction is set for each key separately: for example, category ascending, and within it price descending. A useful habit is to add a unique column, such as the id, as the last key. Then the order of the rows is fully defined and reproducible.\n\nA sort key doesn't have to be a column; it can be an expression: the length of a name, or the total of an order line. Unlike WHERE, ORDER BY runs after SELECT, so it can see aliases, and you can refer to them. You can also give the number of a column in the select list, one or two. That is handy in short queries, but it makes the code fragile: change the list of columns, and the sorting goes the wrong way. In production queries, it's better to name the keys.\n\nHow do you sort empty values? The standard leaves that up to the database. In SQLite, a null is considered smaller than any other value, so in ascending order it comes first, and in descending order it comes last. In other databases it can be the opposite. To avoid depending on defaults, you can say explicitly where to put the missing values: NULLS FIRST or NULLS LAST. Modern versions of SQLite support this. If that option isn't available, you add a null check as the first key.\n\nThe word LIMIT with a number keeps only the first rows of the result. That's how we ask for the three most expensive products or the five latest orders. By itself, the word doesn't say which rows those will be: it simply cuts off the tail. That's why LIMIT almost always goes together with ORDER BY. LIMIT one gives you the most expensive, the earliest, or the newest record. If the table has fewer rows than you asked for, you get as many as there are, and no error occurs. LIMIT zero returns an empty result.\n\nORDER BY plus LIMIT is the classic way to build a ranking. First the database sorts everything that matched the condition, and only then cuts off the number of rows you need. The order of writing is fixed: ORDER BY comes before LIMIT. If you forget the sorting, you get arbitrary rows, and the result may differ from run to run. And if you sort by a non-unique value, the edge of the top list may fall on duplicates, and then the rows at the edge are random. So add a second key, such as the id, to make the result unambiguous.\n\nTo split a long result into pages, you add OFFSET to the limit, which says how many rows to skip. Limit ten, offset zero is the first page; limit ten, offset ten is the second; offset twenty is the third. You turn a page number into an offset by multiplying by the page size. Pages only make sense with a stable sort: if the order is undefined, the same rows can land on two pages while others get lost. In SQLite you can also write it more briefly: LIMIT with two numbers, but then the offset comes first.\n\nOFFSET has a price. To skip twenty thousand rows, the database has to find them and throw them away, so later pages are read more and more slowly. On top of that, if a row is added to the table between two queries, the pages shift, and one record shows up twice. With big data, people do it differently: they remember the last key value they saw and ask for the rows whose key is greater. This technique is called keyset pagination. It works equally fast on any page, but it requires ordering by that key.\n\nNow let's put it all together and look at the order of execution. First the database picks the table and filters the rows with the condition. Then it computes the expressions from the select list and removes duplicates if DISTINCT is given. After that the rows are sorted, and only then does LIMIT kick in. So cities in ascending order without duplicates is DISTINCT and ORDER BY, and the three most expensive products in a category is a condition, a sort, and a limit. Notice that in a query with DISTINCT, you can only sort by what was selected.\n\nLet's look at a typical task: find the second most expensive product. You sort the products by price descending, skip one row, and take one. That is LIMIT one and OFFSET one. If the two most expensive items have the same price, such a query returns the second one in order, not the second by value. To get the second distinct price, you apply DISTINCT first, and only then sort and skip. It's a small difference, but people get it wrong very often in interviews and in reports.\n\nLet's sum up. Without ORDER BY, the order of rows is not guaranteed. ORDER BY takes one or more keys, each with its own direction, and the keys can be expressions and aliases. In SQLite, empty values come first. LIMIT caps the number of rows, OFFSET shifts the start, and together with sorting they give you the top N and pages. In the next chapter we'll deal with empty values: they behave illogically, and they are exactly what beginners' queries usually break on.
