#CHAPTER 30 | Migrations and backups: changing the schema without downtime and being able to recover
Databases. Chapter 30. Migrations and backups: changing the schema without downtime and being able to recover. The schema lives as long as the product and changes along with it: new fields, new tables, renames, data moves. The data lives even longer and has to survive human mistakes, hardware failures, and our own bugs. In this chapter we will see how to write and apply schema changes, how to change the schema on a running system without stopping it, how to build backups of different kinds, and, most importantly, how to make sure you can actually recover from them, because a backup that has never been tested is only an assumption.\n\nA migration is a versioned change to the schema or the data, written as a file. Each migration has a number or a timestamp, and it is applied exactly once and in strict order. A service table in the database stores the list of applied versions, so the tool knows what is left to run. Instead of manual edits on a server, the schema is described in the repository next to the code: it can be reviewed, rolled back, and reproduced on a clean database and on a test environment. Rule number one: an applied migration is never edited; it is fixed with a new one. Otherwise different environments end up with different schemas.\n\nMigrations come in forward and backward kinds. A forward migration moves the schema ahead, and a backward one rolls it back. Backward migrations are handy in development, but in production you rely on them carefully: you cannot roll back the dropping of a column, because the data is already lost. So dangerous steps are split into safe ones, and a rollback is understood as rolling out a fix forward. Each migration should be small, clear, and tested on a copy of production data: what is instant on an empty database can take hours on a table of a hundred million rows.\n\nThe main danger is locks. Many schema changes take a lock on the table, and all queries to it line up in a queue. Adding a column without a default value is fast in modern databases, while adding one with a default value used to rewrite the whole table in older versions. Creating an index the usual way blocks writes, while a special concurrent mode builds it in the background at the cost of time. Changing a column type often rewrites the entire table. You need to know, for your database and version, which operations are fast and which are heavy, and to set a lock wait timeout so that the migration does not block traffic.\n\nTo change the schema without downtime, we use the expand and contract pattern. First, expand: we add a new column without removing the old one. Then the application learns to write to both places while reading from the old one. Then a background process moves the historical data in batches. Then the application switches to reading from the new one. Finally, contract: we stop writing to the old column and drop it in a separate migration. Every step is compatible with both the previous and the next version of the code, so the rollout can be stopped or rolled back at any point. A column is renamed the same way: add a new one, move the data, switch over, drop the old one.\n\nData is moved in batches. A single transaction updating a hundred million rows holds locks, bloats the log, and rolls back entirely on failure. The right way is to update in batches of a thousand or ten thousand rows, walking along the key, with a small pause so that replication keeps up and the load does not grow. The move must be idempotent and resumable: after a crash, the process continues from the last processed key. In parallel it is useful to watch replica lag and locks, and at the end to check consistency: the row count, checksums, and a sample comparison.\n\nNow about backups. A logical backup is a dump: a set of commands or a file from which the schema and data can be recreated. It is portable between versions and platforms and lets you restore a single table, but it is slow on large volumes, and restoring includes recreating the indexes. A physical backup is a copy of the data files themselves together with the log. It is faster and more exact, but tied to the version and architecture. The file copy has to be consistent: either with the database stopped, or using a base backup mechanism that marks a point in the log.\n\nThe write-ahead log turns a backup into a tool for recovery to a point in time. You take a physical backup and then continuously archive the log segments. To recover, you restore the backup and replay the log up to the desired point: before an accidental table drop, or a second before a crash. This is called point-in-time recovery. The distance between backups determines the recovery time, because more log will have to be replayed; the frequency of log archiving determines how much data you may lose if you lose the server.\n\nTwo metrics define the strategy. The recovery point objective says how much data you can afford to lose: an hour, a minute, or nothing. The recovery time objective says how long you can be unavailable. A replica does not replace a backup: it also replays the erroneous delete command, which means it repeats it within seconds. A backup protects against human errors and logical corruption, while a replica protects against hardware failure. You need both levels, plus keeping backups in another place and under another account, so that an outage or a break-in does not destroy both the data and its backups at once.\n\nA backup that has never been restored does not count as a backup. Regularly restore the latest backup to a test server, automatically: check that the database starts, that the row counts and checksums are reasonable, that the application works with it, and that the restore time fits the target. Make sure the backup is not encrypted with a key that is lost together with the server. Retention follows a policy: daily backups for a week, weekly for a month, monthly for a year, taking into account legal requirements and cost.\n\nData migrations between systems follow the same principles. A move to a new database version, to another platform, or to the cloud is done in stages: you bring up the new system, continuously copy the changes using replication or change data capture, check consistency, then switch the traffic for a short window and keep the ability to go back. Logical replication lets you move between versions with minimal downtime. Before switching, you test the load by replaying real queries, so that you do not discover plan degradation in production.\n\nThere is an organizational part too. Migrations go through review like code and are run automatically from a pipeline, not by hand. Changes in the production database are agreed on and rolled out in low-load windows. Access to it is restricted, and actions are logged. For dangerous operations, a rollback plan and messages for the team are written in advance. After incidents, the causes are analyzed without looking for someone to blame, and checks are added that will keep the mistake from happening again: migration linters, bans on dangerous commands, and lock time limits.\n\nLet's sum up. Migrations are versioned, applied once and in order, and fixed forward. Dangerous schema changes are split using the expand and contract pattern, and data is moved in batches and idempotently. Backups can be logical or physical, and the log gives point-in-time recovery. The goals for data loss and time define the strategy, a replica does not replace a backup, and an untested backup is not a backup.
