#CHAPTER 10 | Conditional logic: CASE WHEN
Databases. Chapter 10. Conditional logic: CASE WHEN. Sometimes the value in a result has to depend on a condition: a price category based on the price, a readable name instead of a technical status, a label like new customer or returning customer. In programming you have if and else for that, and in SQL you have the CASE expression. It is not a command but an expression: it returns a value, so it can be used anywhere a value is allowed: in the column list, in a condition, in sorting, inside aggregates, and even in an update.\n\nThe main form is called the searched CASE. It consists of the word CASE, one or more branches of the form WHEN condition THEN value, an optional ELSE branch, and the word END at the close. The database checks the conditions in order and returns the value of the first branch that matches. This way a price can be turned into a label: under one thousand is cheap, under ten thousand is mid-range, otherwise expensive. The conditions can be anything: comparisons, gaps, LIKE, combinations with AND and OR. Don't forget the END, or the query won't parse.\n\nIf you need to compare one expression against a set of values, there is a short form: after the word CASE you write the expression, and the WHEN branches list the values. For example, turn the order status shipped into Shipped, paid into Paid, and new into New. It is shorter than writing an equality in every branch. But the simple form has a limitation: it can only compare for equality, and it does not work with NULL, because NULL is not equal to anything, not even to itself. For complex conditions you need the searched form.\n\nWhat happens if no condition matched? If there is an ELSE branch, its value is returned. If there is none, the result is NULL. That is handy when you want a mark on only some rows and the rest should stay empty. But it is also a source of mistakes: a forgotten ELSE turns into unexpected gaps that later break counts and concatenation. A good habit: always write ELSE, even if it holds NULL, so the reader can see you thought about that case. This is especially important for statuses and categories.\n\nThe branches of CASE are checked from top to bottom, and as soon as one matches, the rest are not even considered. So the order matters. If you first put the condition price under ten thousand and then price under one thousand, the second one will never be reached: every cheap item has already landed in the first branch. The right order goes from the narrowest condition to the widest. It is the same as an if, else-if chain in programming. Watch the boundaries: a price of exactly one thousand falls into whichever branch has the less-than-or-equal sign.\n\nOne of the main uses is turning numeric values into categories. Age into an age group, an order total into a size: small, medium, large. Such a label makes a report readable and lets you group by category afterward: how many orders of each size. It is better to keep the boundaries in one place instead of copying them across queries: otherwise, when the rules change, you'll have to hunt them down everywhere. For big classifications people often create a lookup table with boundaries and join to it, but for three or four categories CASE works perfectly.\n\nOrder statuses in alphabetical order are not what you want: new, paid, shipped, cancelled should appear in the order of the life cycle. CASE inside ORDER BY solves this: each value is assigned a number, and the sorting goes by it. The same trick puts certain rows first: VIP customers first, then the rest, or values without a category last. It replaces an ordering table and is often used in user interfaces. Remember that such sorting cannot use indexes, so on big tables it is slower than a plain one.\n\nCASE inside an aggregate lets you count by a condition. How many orders are paid, how many are cancelled: you can get all of it in one pass over the table. For each row, CASE returns one if the condition holds and zero otherwise, and SUM adds up the ones. For totals, CASE returns the value or zero. This way you can compute revenue from paid orders and from cancelled ones in two neighboring columns. In SQLite a comparison itself returns one or zero, so people often write it shorter, but CASE is easier to read.\n\nIf you take several conditional aggregates in a row and add grouping, you get a pivot table: categories in rows, statuses in columns, and at the intersection the number of orders. SQL has no special command for rotating data, so it is done by hand: one result column for each value you pivot on. This is convenient when the values are known in advance and there are few of them. If there are many values or they change, such a summary is built in the application or a reporting tool, not in the query.\n\nCASE is handy in an update too. Say you need to raise prices: electronics by five percent, books by ten, leave everything else alone. You can write three updates with different conditions, or one command where the value depends on the category. The advantage is a single pass and a single transaction: either all prices change or none do. In the ELSE branch you must keep the column's current value, otherwise the remaining rows get wiped to NULL, and that is one of the nastiest mistakes with this technique.\n\nFor a simple choice between two values, SQLite has the IIF function: IIF of a condition, the value if true, the value if false. It is equivalent to a CASE with one branch. COALESCE is a CASE that returns the first non-empty value, and NULLIF is a CASE that returns NULL when the values are equal. There are also the functions MIN and MAX with several arguments, returning the smallest and largest of the values in a row. All of them are convenient, but when there are more than two branches, it's better to go back to a full CASE.\n\nA few remarks. The values of all branches should mean the same kind of thing: you can't return a number in one and a word in another, or you won't be able to add or sort them later. A condition that evaluates to NULL is not considered true, and the branch is skipped: for columns with gaps you need to write a separate IS NULL branch. Don't forget the END, and watch the range boundaries. And finally, a long CASE repeated in several places of a query is a reason to move it into a view or a common table expression, so you don't duplicate the logic.\n\nLet's sum up. CASE is a conditional expression: in the searched form each branch has its own condition, in the simple form it compares against a set of values. Branches are checked from top to bottom, and rows that match nothing get NULL if there is no ELSE. CASE works in the column list, in ORDER BY, inside aggregates and in an update. With it you build categories, custom sort orders, conditional counts and pivot tables. The short forms IIF, COALESCE and NULLIF cover the common cases.
