#CHAPTER 20 | Storage engines: pages, the log, and two camps
Databases. Chapter 20. Storage engines: pages, the log, and two camps. So far we have looked at the database from the outside: tables and queries. Now let us look inside: how rows turn into bytes on disk, and why some databases write fast while others read fast. The main thing to keep in mind is that a disk, even a fast one, is orders of magnitude slower than memory, and it reads and writes in blocks. So almost all of storage engineering is an attempt to reduce the number of disk accesses to a minimum and to make them sequential. In this chapter we will cover pages, the buffer cache, the write-ahead log, and two families of storage engines: those built on B-trees and those built on log-structured merge trees.\n\nThe basic unit of storage is the page, usually four or eight kilobytes. A table is a file made of pages, and the database always reads and writes whole pages, even if it needs a single row. Inside a page the data follows a slotted layout: at the start there is a header and an array of slots that hold the offsets and lengths of the rows, while the rows themselves fill the page from the end. This layout lets us move rows around within a page without changing their addresses from the outside: the address of a row is a pair, page number and slot number. Values that are too large, for example long texts, the database moves to a separate place and leaves a reference in the row.\n\nReading a page from disk every time would be painful, so there is a buffer pool: an area of memory where recently used pages live. If the needed page is in the pool, that is a hit, and we do not touch the disk; otherwise it is a miss, and the page has to be read in, evicting some other page. A page that has been modified in memory is called dirty, and there is no need to write it to disk immediately. For eviction, databases use approximations of the least recently used algorithm: a clock or counters. The hit ratio is the main health indicator: a database whose working set fits in memory hardly reads the disk at all.\n\nBut if dirty pages exist only in memory, they will be lost in a crash. This is where the write-ahead log, the WAL, comes to help. The rule is simple: before changing a page on disk, you must write a description of the change to the log and flush the log to disk. The log is written only at the end, that is, sequentially, and that is fast. Every record is given a sequence number, the LSN. Now a commit is fast: it is enough to flush the log, and the database will write the data pages later, whenever it is convenient, and the order in which they are written no longer matters.\n\nWhat does the database do after a crash? It reads the log and brings the pages to a consistent state. For this, every page stores the number of the last log record that has been applied to it. During recovery the database replays the log records in order and applies only those whose number is greater than the number on the page: this way, applying a record twice is harmless, which is called idempotence. Then the changes of unfinished transactions are rolled back. To avoid replaying the log from the very beginning, the database periodically makes a checkpoint: it flushes the dirty pages and remembers the number before which the log is no longer needed and can be deleted.\n\nNow about how the rows themselves are stored. There are two approaches. In a heap, rows lie on pages in the order of insertion, and indexes point to them by address; this is how PostgreSQL works. In a clustered table, the table itself is a B-tree on the primary key, and the rows lie in the leaves in key order; this is how MySQL with the InnoDB engine works, and so does SQLite with WITHOUT ROWID tables. A lookup by primary key in a clustered table is faster, and secondary indexes store the key value rather than an address. The choice affects the cost of inserts, updates, and reads.\n\nThe first camp is storage engines built on B-trees. A page is updated in place: we find the leaf, change it, and write it back. Reading is excellent, and ranges are efficient. The downsides are in writing: a write to a random place requires a random disk access, and for one small write we have to rewrite a whole page and also write the log. This is called write amplification: noticeably more bytes reach the disk than the user changed. The tree also gradually becomes fragmented, and the pages are not completely full. This is how most classic relational databases are built.\n\nThe second camp is the log-structured merge tree, the LSM. The idea is the opposite: never update in place, and write everything sequentially. New writes go into an ordered structure in memory, the memtable, and into the log. When it fills up, it is flushed to disk as an immutable sorted file, an SSTable. Gradually there are many files, and background compaction merges them, keeping the newest value for each key and throwing away the stale ones. Writing becomes very fast, because it is sequential, and the price is the background work of compaction and a more complicated read.\n\nHow do we read from such a structure? A fresh value can be anywhere: in the memtable or in any file. So a read checks memory first, then the files from newest to oldest. To avoid opening every file, each one keeps a Bloom filter: a compact structure that quickly answers either definitely not, or possibly yes. A delete cannot be done right away, since the old files still hold the old values, so a special delete marker is written, a tombstone, and the data physically disappears only during compaction. Range queries have to be merged from several files, and that is more expensive than in a B-tree.\n\nLet us compare the camps through three kinds of amplification. Write amplification: how many bytes go to disk per byte of data. Read amplification: how many places must be checked to find a value. Space amplification: how many times larger the data on disk is than the useful data. A B-tree usually wins on reads and loses on writes, and for log-structured trees it is the other way round. The choice depends on the workload: for frequent updates and event streams, RocksDB, Cassandra, and similar systems are good; for transactional applications with varied queries, PostgreSQL and MySQL. There is no universally best option, only trade-offs.\n\nThe third layout option is by columns. In a row store, all the values of one row lie together, which is convenient for transactions that touch a whole row. In a column store, the values of one column lie together. An analytical query that computes the average of one column out of a hundred reads only that column, and the data compresses very well, because the values in a column are of the same kind: repeats are replaced with a pair, value and repeat count, and dictionaries replace strings with numbers. The price is that inserting individual rows is expensive. Column stores underlie the analytical systems we will discuss at the end of the book.\n\nThat leaves the question of write reliability. The operating system caches writes, and a write call does not mean the data is on disk: only fsync gives the guarantee. A database page of eight kilobytes consists of several disk sectors of five hundred twelve bytes or four kilobytes, and in a power failure only part of it may get written; this is called a torn page. Against it, the database keeps checksums and stores a full copy of the page in the log after a checkpoint. Solid-state drives add their own kitchen: they write in blocks and move data around by themselves, so one more write amplification happens inside the drive.\n\nLet us sum up. Data is stored in pages, read and written in blocks, and hot pages are cached in the buffer pool. The write-ahead log makes a commit fast and recovery possible: first the log, then the pages. The two main layouts, the B-tree with in-place updates and the log-structured merge tree with sequential writes and compaction, choose between read speed and write speed. Columnar storage speeds up analytics. Next we will step beyond relational databases: key-value stores, documents, columns, and graphs.
