#CHAPTER 31 | Security: roles, privileges, injection and data protection
Databases. Chapter 31. Security: roles, privileges, injection and data protection. The database holds the most valuable things a product has: customers, payments, correspondence. So protecting it is not a separate feature but a set of habits at every level: who can connect, what they are allowed to do, how the application builds its queries, where and how the data is stored, and what will be left in the logs after a break-in. In this chapter we cover authentication, roles and privileges, row-level security, injection, password storage, encryption, masking, auditing, perimeter setup, and the typical attacks on databases themselves.\n\nIt all starts with authentication: how the database makes sure that whoever connects is who they claim to be. A password is never stored in plain text: the database keeps the result of a slow, salted hash, and the exchange itself follows a challenge-response scheme, so the password never travels over the network. For services, certificates or short-lived tokens issued by a secrets management system are better. For people, use single sign-on through the corporate system plus multi-factor checks. Shared accounts that the whole team uses are forbidden: you can't tell who did what from them, and you can't revoke one without cutting off everybody.\n\nNext, privileges. A role is a named set of privileges, and a user is just a role that is allowed to log in. The GRANT command gives a privilege on an object: read, insert, update, delete, and REVOKE takes it away. The main principle is least privilege: the application does not connect as the schema owner, who has the right to drop tables. Usually you create separate roles for migrations, for the application, and for reports. Privileges can be set on a database, a schema, a table, and even individual columns, and for future objects there is a separate command. Functions that run with the owner's rights give limited access through vetted code, but they need care: otherwise they become a loophole for privilege escalation.\n\nRow-level security lets different users see different rows of the same table. You enable policies on the table: a condition that the database adds to every query automatically. In multi-tenant systems the policy usually boils down to the tenant column being equal to a value from the session setting. When connecting, the application says who is working, and the database filters out other people's rows itself, even if the developer forgot the condition in a query. But all of this works only if the application does not connect as the table owner or as a superuser: they bypass policies. Policies should be verified with tests.\n\nInjection is the best-known vulnerability. If the application builds a query by gluing together a string and user input, then input like an apostrophe, then OR, then one equals one, then a double dash changes the meaning of the query: the condition is always true and the rest is commented out. The attacker reads other people's data, bypasses login, and sometimes drops tables. There is one reliable defense: parameterized queries. The query text and the values are sent separately, and the database never parses the values as code. Manual escaping is unreliable. Frameworks and query builders help, but as soon as you put a user string into a raw fragment, the protection is gone.\n\nParameters can't replace table names, column names, or the sort direction: for those you need an allowlist. The application keeps a set of permitted names and picks from it based on the user's value, rejecting everything else. Dynamic filters are handled the same way: instead of arbitrary expressions, you accept a field identifier and an operator from a fixed set. And don't trust data that is already in the database either: second-order injection happens when a safely stored string is later glued into another query. The principle is one: any external data, including data read from your own database, remains data, not code.\n\nThe passwords of application users are stored differently from database passwords. Use deliberately slow hashing algorithms: scrypt, Argon2, bcrypt. Add a random salt to every password, so that identical passwords give different hashes and rainbow tables don't work. Compare hashes in constant time, so you don't reveal how long the match was. Secrets such as access keys and tokens don't go into ordinary columns: they live in a secrets manager, and the database holds only identifiers or hashes. It is important to be able to revoke a secret and reissue it without changing the schema.\n\nEncryption protects against different threats. Disk encryption saves you when a drive is stolen, but not when a running server is hacked. Connection encryption, the TLS protocol, protects data on the network and must be mandatory, with verification of the server certificate. Encrypting individual columns or fields on the application side protects even from the database administrator and from leaked copies, but it breaks searching and indexes on them. Keys are stored separately from the data, in a key management service, and rotated on a schedule. You have to understand who you are defending against, because there is no single encryption that covers everything.\n\nPersonal data calls for minimization. Store only what you need, and only for as long as you need it. Sensitive fields are masked: when shown to an operator, only part of a card number or an email is visible. You must not copy production data into test environments as it is: it is anonymized, with names and contacts replaced by plausible fictional ones. Pseudonymization replaces an identifier with a token, and the mapping table is stored separately. Data protection laws require you to be able to find all the information about a person, correct or delete it on request, and report a leak. So the schema is designed to make such operations possible.\n\nAuditing answers the question: who did what, and when. The connection log records logins and failures. The query log and audit extensions record schema changes and access to sensitive tables. Triggers on tables write a change history: who changed which fields, and when. The log must be protected from tampering by the very people it watches: it is shipped to an external system and stored separately. Without auditing you will not learn about a break-in, and afterwards you won't be able to tell exactly what leaked, so you have to treat everything as leaked.\n\nNetwork and configuration are the first line of defense. A database is not exposed to the internet: access comes from a private network, through a gateway or a tunnel, with filtering by address. The access rules file allows connections only for the right roles, from the right addresses, and only over a secure channel. Default accounts are disabled, standard passwords are changed, security updates are installed, and backups are encrypted and stored separately, with separate permissions. Extensions and foreign data wrappers are enabled only when needed: every extension is a new attack surface.\n\nTypical attacks on databases, besides injection: password guessing, which you counter with lockout after failures and rate limiting; privilege escalation through unsafe functions that run with the owner's rights, or through schema search path tricks; leaks through backups and dumps left in shared storage; and denial of service with heavy queries. Against the last one you set limits on query execution time, number of connections and memory, and use a connection pool. For monitoring, watch for spikes of failed logins, unexpected roles, new extensions, and mass exports.\n\nLet's sum up. Authenticate strictly, with no shared accounts. Grant least privilege, and separate the owner, application and reporting roles. For multi-tenant systems, use row-level security and verify it with tests. Only parameters and allowlists protect you from injection. Store passwords with slow salted hashes and secrets in a secrets manager, encrypt the connection and, where needed, individual fields. Minimize and mask personal data, keep an audit trail, and don't expose the database to the internet.
