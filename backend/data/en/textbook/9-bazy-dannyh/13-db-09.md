#CHAPTER 9 | Creating and altering table structure (DDL)
Databases. Chapter 9. Creating and altering table structure. So far we have worked with ready-made tables. Now let's see where they come from. The commands that describe structure are called the data definition language. CREATE builds a table, ALTER changes its design, DROP removes it. Structure is the skeleton of an application: it decides what data can be stored at all and which mistakes the database will catch on its own. A well-designed table saves you hundreds of checks in application code, and a poor one forces you to fix everything by hand later.\n\nA table is created with the CREATE TABLE command, followed by column definitions in parentheses, separated by commas. For each column you give a name, a type and, if needed, constraints. Names are written in lowercase, without spaces, most often in English, because you will have to work with them in queries and code. A good rule: name tables with plural nouns and columns by their meaning, like price or created date. Creating a table is usually a one-off operation, and a mistake in it is expensive to fix later.\n\nThe column type determines what values it holds. SQLite has five type affinities: INTEGER for whole numbers, REAL for fractions, TEXT for strings, BLOB for binary data and NUMERIC for numbers chosen automatically. There is no separate type for dates: they are stored as ISO text, as a number, or as a count of seconds. Other databases have more types, and stricter ones: money, date and time, boolean. When you create a table, choose the type by the meaning of the data. Storing a price as a whole number of kopecks is a common way to avoid rounding errors.\n\nA primary key tells the rows of a table apart. It cannot repeat and cannot be empty. In SQLite, an INTEGER column marked as a primary key becomes an alias for the internal row number and is numbered automatically: if you insert without a value, the database takes the next number. The AUTOINCREMENT keyword adds a guarantee that deleted numbers are never reused, but it costs a little more and is rarely needed. It is better to make the key technical: a number that means nothing to the user and therefore never changes.\n\nThe NOT NULL constraint forbids gaps in a column: the database will refuse to insert a row with no value. It is a simple but powerful protection: required data is always there. The DEFAULT keyword sets the value that is filled in if the column is left out of an insert. For example, an order status is new by default, and a VIP flag is zero by default. Together these two constraints remove almost all gaps in important columns. Columns where a gap makes sense, like a middle name or a closing date, are left without the constraint.\n\nUNIQUE requires that values in a column do not repeat. A typical example is a user's email. Unlike a primary key, such a column allows gaps, and there can be as many as you like. CHECK tests an arbitrary condition for every row: the price is not negative, the rating is from one to five, the end date is not earlier than the start date. If the condition is violated, the insert or update is rejected. These rules are written in the table itself, so that no application can get around them.\n\nA foreign key formally links tables: the order column refers to the customer's primary key. The database checks that the value exists, and it does not let you delete a customer while something still refers to them. The behavior on deletion is set by the ON DELETE clause: CASCADE deletes the dependent rows, SET NULL clears the reference, RESTRICT forbids the deletion. In SQLite, foreign key checking is off by default and is turned on with the PRAGMA command. Without it, references are only a gentleman's agreement, and such agreements sooner or later get broken.\n\nSometimes one column is not enough for a key. In the order items table, each row is identified by a pair: the order number and the product number. Such a key is called composite, and it is declared on a separate line at the end of the table definition, listing the columns in parentheses. The combination of values must be unique, while each value on its own may repeat. Composite keys are typical for link tables in many-to-many relationships: students and courses, tags and posts. The order of columns in the key matters for search speed: put first the one you search by more often.\n\nStructure changes over time. ALTER TABLE lets you add a new column, rename a column or a table, and drop a column. An added column is filled with the default value or with gaps, so you cannot add a new required column without a default value. Dropping a column in SQLite is available since version three point thirty-five, but if the column takes part in a key, an index or a constraint, you will have to recreate the table. Changing structure on live data is always risky, so such changes are written to separate files and applied in order.\n\nDROP TABLE removes the whole table together with its data, and without a transaction you cannot roll that back. If the table does not exist, the command returns an error, but with IF EXISTS it simply does nothing. In the same way, CREATE TABLE IF NOT EXISTS will not create the table a second time. These words make scripts safe to run again. Before dropping, make sure no foreign keys or views refer to the table. And to clear data without removing the structure, use DELETE, not DROP.\n\nA table can be created straight from the result of a query: CREATE TABLE AS SELECT. The columns come from the select, and the data is copied. This is how you make snapshots of data at a given moment and intermediate tables for reports. Constraints and keys are not carried over, so you have to add them separately. For temporary data needed only in one session, there are temporary tables: they disappear when the connection closes and do not get in the way of the permanent structure. They are handy for complex multi-step calculations.\n\nYou should not change a database structure by hand. Every change is written to a separate file, numbered, and applied in order on all servers. This approach is called migrations. Thanks to them, the database can always be recreated from scratch, and you can see the history of changes. The current structure in SQLite can be viewed in the system table sqlite master: it holds the texts of the creation commands. This course works the same way: its tables and exercises are described in files from which the database can be rebuilt in seconds.\n\nLet's sum up. CREATE TABLE describes columns with types and constraints. A primary key tells rows apart, NOT NULL and DEFAULT make data required, UNIQUE and CHECK enforce rules, and a foreign key links tables. ALTER changes the structure, DROP removes it, and scripts with IF EXISTS can be run repeatedly. Structure changes are packaged as migrations. The more rules you build into the schema, the more reliable the data.
