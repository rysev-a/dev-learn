#CHAPTER 4 | Working with Text and Missing Values (NULL)
Databases. Chapter four. Working with text and missing values. In real life, data is incomplete: a customer has no city on file, a product has an unknown brand, an employee has no manager. For cases like these, SQL has a special value called null, which means unknown. It is not zero and it is not an empty string: zero is a known number, an empty string is known empty text, while null means there is no value at all, or the value is not known. You have to handle it carefully, because ordinary operations on an unknown also give an unknown.\n\nThe most common beginner mistake is to compare a column with null using an equals sign. A query like city equals null will return nothing, even if the table is full of gaps. The reason is simple: comparing any value with an unknown is neither true nor false, it is unknown too. The right checks are IS NULL and IS NOT NULL. They return an honest true or false. With the second one, it's easy to find customers who have an email on file, and with the first one, those we're missing something about. Remember this pattern once and for all.\n\nBecause of missing values, logic in SQL is not two-valued but three-valued: true, false, and unknown. True and unknown give unknown, but false and unknown give false, because false wins in an AND. For OR it's the opposite: true wins. The condition in WHERE lets through only the rows where the result is true. False and unknown are both discarded in the same way. So a row for which the condition can't be checked because of a gap simply vanishes from the result, silently. This rule explains almost all the oddities of nulls.\n\nLet's look at a tricky example. The query city not equal to Moscow looks simple: everyone who doesn't live in Moscow. But a customer whose city is not given won't make it into the result: comparing null with Moscow gives unknown, and unknown is discarded. To include such customers too, you have to write the condition explicitly: city is not Moscow, or city is null. SQLite also has a shorter operator, IS NOT, which compares values treating two nulls as the same, and never returns unknown.\n\nNull is contagious. Addition, subtraction, multiplication, joining text: if even one operand is unknown, the result is unknown too. Price plus ten, where the price is missing, gives null. Name, comma, and city, where the city is empty, gives null, and the whole label disappears. That makes sense: if you don't know one of the terms, you don't know the sum. But in practice such losses can be unpleasant, and that's why we need functions that put a fallback value in place of a gap. The next two slides are about exactly those.\n\nThe function COALESCE takes any number of arguments and returns the first one that is not null. If the city is empty, COALESCE of the city and the phrase not specified returns that phrase. If there's no home phone, you can take the work phone, and if there isn't one either, put in a dash. The short form for two arguments is called IFNULL. Thanks to COALESCE, joining text stops losing rows: every value that can be empty gets wrapped in COALESCE. But use it deliberately: replacing a gap with a zero or a word sometimes distorts the meaning of the data.\n\nThe function NULLIF works the other way around: if two values are equal, it returns null, and otherwise the first value. Its main use is protection against division by zero. If you divide by a denominator wrapped in NULLIF with zero, then when the denominator is zero you get null instead of an error. SQLite returns null on division by zero anyway, but in other databases it's an error, so the habit is a useful one. Another use is turning an empty string into a real null, so that all the functions for missing values work from there on.\n\nAre two unknown values equal? The equals operator answers: unknown. So the condition null equals null won't pass in WHERE. For a comparison that treats gaps as equal, there are IS and IS NOT. But this rule has an exception that surprises people: DISTINCT and grouping treat all nulls as one value. If three customers have empty cities, DISTINCT will show a single null. So don't expect gaps to behave the same everywhere: in comparison they're all different, in grouping they're the same, and in sorting they're the smallest.\n\nNow, text. The function UPPER converts a string to uppercase, LOWER to lowercase, LENGTH returns the length in characters, and TRIM cuts off spaces at the edges. They're needed to compare values fairly: users type addresses any which way, and you can compare emails without regard to case by converting both sides to lowercase. Watch out: in SQLite, UPPER and LOWER by default work only with Latin letters, and Cyrillic letters stay as they are. All the text functions, when given a null, return null.\n\nTo extract part of a string, there is SUBSTR: you tell it which position to start from and how many characters to take. Positions are numbered from one. The function INSTR returns the position of the first occurrence of a substring, or zero if there isn't one. The function REPLACE swaps all occurrences of one substring for another. Together they let you take apart a format: for example, cut the domain out of an email by taking everything after the at sign. To do that, you find the position of the at sign and take the substring starting from the next character.\n\nWe already know LIKE. For strict, case-sensitive matching, SQLite has GLOB: in it, a star stands for any number of characters, a question mark for exactly one character, and square brackets define a set. For example, a GLOB pattern with a range of lowercase Cyrillic letters in square brackets followed by a star will find names that start with any lowercase Russian letter. Paired with INSTR and SUBSTR, that's enough for most text-parsing tasks. But if you find yourself parsing complex formats, it's usually better to fix the data when it's written.\n\nSometimes you need to convert a value from one type to another explicitly. For that there is the function CAST: CAST of a price AS TEXT turns a number into a string, and CAST of a string AS INTEGER turns it into a number. Note that a string with junk at the start gives zero, and the fractional part is dropped when converting to an integer. It's useful to remember the implicit conversions in joining and comparison: a number and a string are compared by affinity rules, and the result isn't always obvious. To avoid guessing, convert the types yourself and check the result with the function typeof.\n\nLet's sum up. Null is an unknown value, not zero and not an empty string. Compare with it only through IS NULL and IS NOT NULL. The logic is three-valued, and WHERE lets through only true. Arithmetic and joining with null give null; to avoid that, there are COALESCE and NULLIF. For text, there are UPPER, LOWER, LENGTH, TRIM, SUBSTR, INSTR, REPLACE, LIKE and GLOB. That finishes the first part: you can now select, filter, sort, and clean values. Next comes the most interesting part: counting and joining tables.
