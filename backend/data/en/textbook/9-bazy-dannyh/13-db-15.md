#CHAPTER 15 | Window functions
Databases. Chapter fifteen. Window functions. Grouping turns many rows into one per group, and the original rows are lost. But sometimes you need to see every row with a total next to it: an order and the customer's overall spend, an employee and their place in the salary ranking, a month's sales and the running total. Window functions were invented for exactly this. They calculate a value over a set of related rows, called the window, but return a result for each row separately. The rows stay where they are, and the new column holds what used to require a join with a subquery.\n\nA window function is written like an ordinary one, followed by the word OVER with parentheses. If the parentheses are empty, the window is all the rows of the result: sum of total over empty parentheses puts the grand total next to every row. This lets you, for example, calculate each order's share of the overall sum: the order amount divided by the sum over empty parentheses. Inside the parentheses of OVER you say how to split the rows into groups, in what order to process them, and which part of the group to take into account. Let's start with the splitting.\n\nThe PARTITION BY clause splits the rows into independent windows by the value of a column. It looks like grouping, but the rows do not collapse. The sum of orders over partition by customer gives each row the total for its own customer. The windows don't see each other: one customer's total does not depend on the others. This makes it easy to calculate an order's share of the customer's total, the deviation of a price from the category average, or the number of employees in a department next to each employee. PARTITION BY can take several columns, just like GROUP BY.\n\nNow let's add ORDER BY to the window. Each row then sees not all the rows of the window, but only the previous ones and itself, in the given order. The sum over order by month gives a running total: in January, January's revenue; in February, January plus February; and so on. This is the basis of cumulative metrics: an account balance, the number of users registered by a date, the stock level in a warehouse. If the order is not uniquely defined, rows with the same sort key are counted together, and you need to keep that in mind by adding a unique key.\n\nThe ROW_NUMBER function gives each row of the window a sequence number in the given order: one, two, three, and so on, with no gaps and no repeats. For equal sort values the order among them is arbitrary, so add a unique key. With PARTITION BY the numbering starts over in every group: for example, each customer's orders by date, from the first to the last. Row numbering is the basis of many tasks: finding a customer's first order, removing duplicates, splitting a result into pages.\n\nFor rankings with equal values there are RANK and DENSE_RANK. Both give equal values the same place. The difference is in the next place: after two second places, RANK skips third and gives fourth, while DENSE_RANK carries on with the next number, that is, third. ROW_NUMBER, by contrast, gives everyone a different number. Which function to choose depends on the meaning: a place in a competition is RANK, a salary level number is DENSE_RANK, a technical row number is ROW_NUMBER. All three work with PARTITION BY.\n\nA classic task: the three most expensive products in each category. LIMIT doesn't work here, because it restricts the whole result, not each category. The solution is to number the products within the category by price, and then keep the numbers up to three. Window functions can't be used directly in WHERE, so the numbering goes into a subquery or a common table expression, and the condition is written outside. The same technique finds each customer's latest order and the earliest registration day.\n\nLAG returns the value from the previous row of the window, and LEAD from the next one. This way you can subtract the previous value and get the change: revenue growth compared with last month, the time between one customer's orders, the difference between readings. The second argument says how many rows to look back or forward, and the third is the default value for the first row, which has no previous one; otherwise you get NULL. Calculations like this used to require a self-join, and now it is a single function and a single pass over the data.\n\nFIRST_VALUE returns the value of the first row of the window, and LAST_VALUE the value of the last. For example, the price of a product at the start of a period, a customer's earliest order date, the best score in a group. There is a subtlety: the default window frame ends at the current row, so LAST_VALUE with no extra settings returns the value of the current row itself, not of the last one in the group. To get the real last row, you have to extend the frame to the end of the window. This is one of the most common misunderstandings about window functions.\n\nInside the window you can also choose a frame: which rows to count relative to the current one. ROWS BETWEEN two PRECEDING AND CURRENT ROW takes the current row and the two before it. With such a frame, AVG gives a moving average: for example, the average revenue over the last three months. You can take rows from the start of the window to the current one, or from the current one to the end, or all of them. The frame is written after ORDER BY, and by default it runs from the start of the window to the current row, which is what gives cumulative totals.\n\nThe NTILE function divides the ordered rows into a given number of groups of equal size: four groups are quartiles, ten are deciles. With it you can split customers into the top quarter and the rest by purchase amount. For shares, sum over empty parentheses works well: a value divided by the sum of all values gives the row's share of the total. There are also percent rank functions that show a row's position in the distribution. These techniques are used in analytics to compare values with each other rather than look at absolute numbers.\n\nWindow functions are evaluated at the very end of working with the data: after WHERE, GROUP BY and HAVING, but before the final ORDER BY and LIMIT. Two rules follow from this. First: the window sees only the rows that passed the filter, so a condition in WHERE changes the window's result. Second: a condition on the value of a window function can't be written in WHERE; it is moved to an outer query. A window can be used together with grouping: then it is computed over the results of the grouping, and aggregates can be fed into it as input.\n\nLet's sum up. A window function is computed over a set of rows but does not collapse them. PARTITION BY splits the rows into windows, ORDER BY sets the order and gives cumulative totals, and the frame picks the rows around the current one. ROW_NUMBER, RANK and DENSE_RANK number the rows, LAG and LEAD look at the neighbors, FIRST_VALUE and LAST_VALUE take the edge values, and NTILE splits into groups. Windows are computed after grouping, and conditions on their values are written in an outer query. The next chapter is the last in this part: views, which give queries names.
