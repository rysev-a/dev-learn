#CHAPTER 8 | Inserting, updating and deleting data (DML)
Databases. Chapter eight. Inserting, updating and deleting data. So far we have only been reading. But data has to get into the database and change: customers sign up, prices go up, orders get cancelled. There are three commands for this: INSERT adds rows, UPDATE changes existing ones, DELETE removes them. Together with SELECT they make four actions on data. Now a mistake costs more: a bad SELECT just returns the wrong thing, while a bad UPDATE corrupts your data. So in this chapter we learn to make changes carefully.\n\nINSERT adds a row to a table. After the words INSERT INTO you write the table name, then the list of columns in parentheses, then the word VALUES and the values in parentheses, in the same order. Columns you didn't list get their default value, and if there is none, NULL. If a column is required and you skipped it, the database refuses the insert. You can leave out the column list, but then you have to give all the values in table order, and the query breaks with any change to the structure. So always list the columns explicitly.\n\nIf you need to add several rows, you don't have to write several INSERTs. In one VALUES you can list many sets of values separated by commas. This is shorter and faster: the database parses the command once, and if any row has an error, none is added, because the command runs as a whole. The number of values in each row must match the number of columns. For very large loads people use special import tools, but for tens and hundreds of rows this form is quite enough.\n\nInstead of VALUES you can put a SELECT: then the rows it returns go into the table. This is how you copy data from one table to another, build an archive, or prepare a report in a temporary table. For example, move all cancelled orders to an archive. The SELECT columns are matched to the insert columns by position, not by name, so watch the order. The SELECT can be as complex as you like: with joins, grouping, conditions. This is one of the most powerful techniques, and it deserves careful use.\n\nUPDATE changes values in existing rows. The word SET introduces a comma-separated list of assignments: the new value for a column can be a number, a string, an expression, or even a subquery. WHERE decides which rows to change. For example, raise the prices in the Books category by ten percent: the price equals the price multiplied by one point one. The right-hand side of an assignment is computed from the row's old values, so you can safely change columns that depend on each other. If the condition matches many rows, all of them change.\n\nIf you forget WHERE, UPDATE changes every row of the table, and DELETE deletes all the rows. The database won't ask again: you asked for it yourself. This is the most common disaster in practice. A habit that protects you: write the WHERE first and everything else after, or even start the command with a SELECT. Many working tools have a mode that forbids changes without a condition. And one more way to protect yourself is to make changes inside a transaction, so that you can roll the result back, and we'll cover that a little later.\n\nDELETE removes the rows of a table that satisfy a condition. The table structure stays, only the records disappear. The same command without WHERE can delete everything at once, but it's better not to: other databases have a TRUNCATE command for a full clean-out, which works faster. To delete the right part, the condition must be exact: for example, on the primary key. Remember foreign keys: you can't delete a customer that orders refer to, unless cascading delete is enabled. The database will remind you with an error.\n\nThe simplest way to avoid harm is to look at what you are about to change. Take the condition from the future UPDATE or DELETE and put it into an ordinary SELECT. See how many rows you got and whether they are the right ones. If you expected three and there are a thousand, the condition is wrong. Only when the selection looks right, replace the SELECT with UPDATE or DELETE with the same WHERE. It takes half a minute and saves you from the most painful mistakes. Another useful habit is to check, after a change, the number of affected rows that the database returns.\n\nA transaction combines several commands into one whole: either all of them run, or none. BEGIN starts a transaction, COMMIT makes the changes permanent, ROLLBACK cancels everything done since the start. Until the commit, the changes are visible only to you. If something goes wrong, a rollback returns the data to its original state. The classic example is a money transfer: the debit from one account and the credit to another must happen together. In SQLite every command outside a transaction is committed automatically, so for complex changes you need to write BEGIN explicitly.\n\nThe database won't let you break the table's constraints. A skipped required column, a duplicate value in a unique column, a second row with the same primary key: all of this ends in an error, and the command doesn't run. A foreign key won't let you insert an order for a nonexistent customer or delete a customer who has orders. In SQLite, foreign key checking is turned on by a separate PRAGMA command, and you must turn it on in every connection. Constraints are your insurance: the more rules live in the database itself, the fewer surprises in the data.\n\nOften you need to say: insert the row, and if one already exists, update it. This is called an upsert. In SQLite you write it by adding to the INSERT the phrase ON CONFLICT, where you specify the key column, followed by DO UPDATE SET with the new values. Inside the update, the special name excluded means the values you tried to insert. There are cruder ways too: INSERT OR REPLACE deletes the old row and inserts a new one, and INSERT OR IGNORE silently skips the conflicting one. Use them deliberately, because REPLACE loses the values of columns you didn't specify.\n\nAfter a change you often need to know what exactly happened: what ID the new row got, what values appeared after the update. For this, modern versions of SQLite have the RETURNING clause. You add it to the end of an INSERT, UPDATE or DELETE, and the command returns a result like a SELECT. This is handy for automatic IDs: you inserted a customer and immediately got its ID. It also gives you a simple change log: you deleted rows and immediately saw exactly which ones. The clause appeared in version three point thirty-five and is supported in Postgres.\n\nLet's sum up. INSERT adds rows, and it is better to list the columns explicitly. UPDATE and DELETE without WHERE affect the whole table, so check the condition with a SELECT first. A transaction combines commands into one whole and lets you roll the result back. Constraints protect the data from wrong values. Upsert and RETURNING save you extra queries. The data changes, and the structure stays the same. In the next chapter we will learn to change the structure itself: create tables, add columns, and describe the rules that protect the data.
