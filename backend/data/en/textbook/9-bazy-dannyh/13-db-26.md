#CHAPTER 26 | OLTP and OLAP: two worlds of data and the warehouse outside the database
Databases. Chapter 26. OLTP and OLAP: two worlds of data and the warehouse outside the database. A store takes orders, and every order is a short operation on a few rows. The same store looks at a report in the morning: how much was sold by month and by category over three years. These are two different jobs. The first must finish in milliseconds and run thousands of times per second; the second reads millions of rows and can take minutes. If you mix them in one database, the report takes memory and disk away from the orders, and the site slows down. In this chapter we'll look at how these worlds differ, how data moves from one to the other, and what a data warehouse is.\n\nOLTP, online transaction processing, is the world of the operational database. Queries are short and pinpoint: find an order by number, add a line item, write off stock. Each one touches a few rows, uses an index, and finishes in milliseconds. Thousands of sessions work at the same time, so transactions, isolation, and locks matter, as we discussed at the beginning of the book. The data is normalized, so that a fact lives in one place and is updated with a single write. The main metric of this world is the number of operations per second and the latency of a single operation.\n\nOLAP, online analytical processing, is the world of reports and calculations. A query reads a huge part of a table, but takes only a few columns from it: total sales, number of customers, an average by group. Millions of rows are read, and tens of rows come back. There are few queries, but each is heavy, and what matters is scan speed, not finding a single record. Data in this world barely changes after it is written: it is appended in batches and rarely edited. The metric is different here: how many gigabytes per second the system can read and roll up.\n\nWhy not keep everything in one database? First, resources: a heavy scan pushes the hot order pages out of memory and occupies the disk. Second, locks and long transactions get in the way of cleaning up old row versions. Third, the schema: a normalized model is convenient for writing, but a report needs ten joins on it. The simple solution is a read replica, and for small reports it is enough. When there is a lot of data or a lot of analytics, you build a separate system and copy the data into it. There are also hybrid databases that combine both modes, but they are always a compromise.\n\nThe data model in a warehouse is organized differently. The most common scheme is the star. In the center is the fact table: one row per event, for example per item sold, with numbers and references. Around it are dimension tables: products, customers, dates, stores, with descriptive columns. A report joins the facts with the dimensions it needs and groups: sales by category and month. Dimensions are denormalized on purpose: the category sits right in the product row, and there are no extra joins. If the dimensions branch out further, you get a snowflake, which saves space but makes queries more complex.\n\nTo read quickly, analytical databases store data by columns. Instead of rows on a page, each column lies in its own file or block, and a query reads only the ones it needs. Similar values lie next to each other and compress very well: repeats are encoded as run lengths, strings with a dictionary, numbers with differences. Processing goes in vectors, in batches of a thousand values, and the processor uses its wide instructions. This is how ClickHouse, DuckDB, Vertica, and cloud warehouses work. The price is point changes: assembling a single row from columns is expensive, so edits are rare and come in batches.\n\nWhere does the data in a warehouse come from? The classic path is called ETL: extract data from the sources, transform it, load it. The transformation, which is cleaning, type conversion, and key matching, is done before loading on a separate server. Today ELT is used more often: raw data is loaded into the warehouse right away, and the transformations are done with SQL inside it, because it is powerful and cheap. Loading goes in batches on a schedule. The main requirement is idempotence: rerunning the same batch must not double the rows, so you load by replacing a partition or by inserting with a key check.\n\nBatch loading once a day gives you reports with yesterday's data. If you need freshness, you use change data capture, CDC. It reads the write-ahead log of the database itself, the same log that replication needs, and turns every insert, update, and delete into an event. The events go to a queue, for example Kafka, and from there to the warehouse or to other systems. The load on the source is minimal, because no queries are run against the tables. It is important to keep the order of events per key and to survive repeated delivery: an event may arrive twice.\n\nHeavy reports don't have to be computed every time they are opened. A materialized view stores the result of a query as a table and is refreshed on a schedule or incrementally. Pre-aggregates, which are sums by day and category, turn scans of billions of rows into reads of thousands. For totals at several levels there are grouping constructs: rollup adds subtotals and a grand total, cube adds all combinations, and grouping sets adds only the sets you list. The price of speed is refresh delay and space. So you pre-aggregate what is asked often and what is stable in meaning.\n\nAnalytical SQL lives on window functions and common table expressions. A window function computes a value over a group of rows without collapsing them: a running total, a rank within a category, the difference from the previous period, a moving average. Typical reports are built from them. A cohort groups customers by the month of their first purchase and looks at how many came back in the following months. A funnel counts how many people got from viewing to buying, and where they dropped off. Such queries are checked by hand on a small data set, because a mistake in a join silently distorts the numbers.\n\nWarehouses grow, and the data lake appeared: files in cheap object storage, most often in the columnar Parquet format. Storage is separated from compute: any engine reads the same files, and you pay for compute only at the moment of a query. A set of files by itself knows nothing about transactions, and that is why table formats appeared, Iceberg, Delta, and Hudi: they keep a version log and give atomic commits, schema changes, and time travel. The idea of the lakehouse is to get the capabilities of a warehouse on the files of the lake, without copying the data.\n\nData in the source changes, but the report for last year must stay the same. If a customer moved to another city, old orders belong to the old city. This is solved by a slowly changing dimension of type two: instead of editing the row, you add a new version with start and end dates. Quality and reproducibility are just as important. Check that keys are unique, that there are no gaps, and that totals match the source. Build loads so that any period can be recomputed from scratch, which is called a backfill, and then fixing a mistake does not turn into manual work.\n\nLet's sum up the chapter. OLTP is short, precise operations on rows, normalization, indexes, and transactions. OLAP is heavy scans over columns, the star schema, pre-aggregates, and columnar storage. Data moves through ETL or ELT and through change data capture, and every load must be idempotent. We have come a long way from a table and a query to transactions, indexes, storage, replication, sharding, caching, and the warehouse.
