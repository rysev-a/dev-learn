#CHAPTER 32 | The database in the application: pools, ORMs, queries in a loop and idempotency
Databases. Chapter 32. The database in the application: pools, ORMs, queries in a loop and idempotency. We know how to write fast queries, but in a real product the database is called by an application: thousands of simultaneous requests, a network between the server and the database, libraries that generate queries on their own, retries after failures. A significant share of performance and reliability problems arise not inside the database but at this boundary. In this chapter we cover connection pools, transaction boundaries, ORMs and their traps, queries in a loop, batch writes, reading from replicas, idempotency and queues, and we finish with observability and a summary of the whole book.\n\nConnecting to a database is expensive: a network handshake, encryption, a password check, and on the server every connection gets a process or a thread with its own memory. So the application does not open a connection for each request, but takes a ready one from a pool and returns it afterwards. A pool holds a limited number of connections and hands them out in turn. If the pool is exhausted, the request waits, and after a timeout it gets an error. For databases where connections are especially expensive, like PostgreSQL, an external proxy pool is placed between the application and the database, which squeezes thousands of client connections into dozens of server ones.\n\nHow big should the pool be? Bigger is not better. A database server can efficiently run only as many queries at once as it has cores and disks, and the rest just compete for resources. A good starting point is about the number of cores times a small factor, and then you measure. Little's law links three quantities: the average number of requests in the system equals the arrival rate times the average processing time. If there are a hundred requests per second and each takes twenty milliseconds, then on average two connections are busy at any moment. A huge pool hides the problem and amplifies it when things slow down.\n\nA transaction in the application is a deliberate boundary. You open it as late as possible and close it as early as possible, and inside it you do nothing slow: no calls to external services, no waiting for a human's reply, no heavy computation. A long transaction holds locks and gets in the way of version cleanup. Operations that must be atomic go into one transaction, and serialization errors and deadlocks are handled by retrying the whole transaction after a short delay. Nested savepoints let you roll back part of the work without losing the rest. An exception inside a transaction must always lead to a rollback, otherwise the connection goes back to the pool in a bad state.\n\nAn ORM, an object-relational mapper, turns rows into objects and back. It saves you from assembling queries by hand, tracks changes to objects and writes them on commit, and often manages the schema too. But the convenience hides a cost: behind a nice-looking access to an object's field there may be a database query. You need to know what queries your code produces and be able to see them: turn on query logging in development and look at the plans. An ORM is good for routine operations, but for complex reports and bulk changes it is better to write SQL directly. That is not a conflict, it is a division of labor.\n\nThe most common ORM trouble is queries in a loop, the N plus one problem. You fetched a list of a hundred orders with one query, then in a loop you access the customer of each order, and the ORM quietly makes a hundred more queries. Each one is short, but a hundred network round trips instead of one add up to seconds of delay. You can spot the problem in the log: the same query template repeats dozens of times. The cure is eager loading: a join, or a separate query with a list of identifiers followed by assembly in memory. Lazy loading is convenient, but it takes discipline.\n\nSelect only what you need. Loading all columns together with heavy fields drags extra data over the network and spoils the chances of covering indexes. For lists, take the necessary fields, and the full object only for the details page. For paging, use keyset pagination instead of offset. Counting all rows to show the total number of pages is expensive on large tables, and it is often replaced by an approximate estimate or a Next button. Limit the size of result sets: a query with no limit that returns a million rows will bring down both the database and the application.\n\nWrite in batches. Inserting a thousand rows one at a time means a thousand network round trips and a thousand log writes, while a multi-row insert or a special bulk load command does the same dozens of times faster. Updates are combined too: one query by condition or with a table of values, rather than row by row. The batch size is found by experience: too small gives no gain, too large bloats memory and locks. Network latency is multiplied by the number of round trips, so cutting the number of round trips often helps more than optimizing the query itself.\n\nReading from replicas offloads the primary, but a replica lags behind. A user saved their profile and immediately opened the page, and the replica has not yet received the change: they see old data. The solutions: read your own writes from the primary for a short time after the write, pin the session to the primary after a change, check the replica's log position, or keep a last-change marker in the session. Reads that are critical for correctness always go to the primary. It is better to do routing explicitly than to try to guess from the query text.\n\nNetworks are unreliable, so the client retries requests, which means operations must be idempotent. The client sends an idempotency key: a unique identifier of the intent. The server records it together with the result in one transaction, and on a retry returns the previous result without performing the action again. For reliable event delivery, use the outbox pattern: the event is written to a table in the same transaction as the business change, and a separate process publishes it to a queue. Delivery is then at least once, and consumers protect themselves against duplicates.\n\nConcurrent changes in the application are handled either without locks or with them. The optimistic approach stores a version number: the update succeeds only if the version is unchanged, and it increments it; if zero rows were affected, the operation is retried. The pessimistic approach locks the row when reading it. A task queue in a table is built on selecting a row with a lock while skipping busy ones: several workers take different tasks without waiting for each other. Remember execution time: a task that was taken but not finished must return to the queue on a timeout, otherwise it will be lost along with a crashed worker.\n\nFinally, observability and tests. Pool metrics: busy and waiting connections, wait time. Query metrics: count, slow ones, errors, and tracing tied to the user's request. The slow query log and their plans in the same place as the code. Tests that run against a real database of the same version, not a stand-in: the schema, constraints and subtleties of SQL behave differently. Query execution time limits protect against a single bad query. The query plan can be checked in the pipeline, so a regression is caught before the release.\n\nLet's sum up the chapter and the whole book. The application takes connections from a pool of reasonable size, keeps transactions short, retries them on failures, and makes operations idempotent. An ORM is convenient, but you have to see the queries it produces, avoid queries in a loop, select only what you need, and write in batches. We have come all the way from a table and a query through transactions, indexes, storage, replication, sharding, consistency, cache, warehouse, schema, advanced SQL, the optimizer, migrations and security, to how the application works. The main lesson is one: choose a solution for the load, measure instead of guessing, and remember that every speedup has a price.
