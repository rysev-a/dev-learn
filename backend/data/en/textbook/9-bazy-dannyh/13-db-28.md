#CHAPTER 28 | Advanced SQL: windows, common table expressions, recursion and JSON
Databases. Chapter 28. Advanced SQL: windows, common table expressions, recursion and JSON. Simple selects and groupings cover half of the tasks. The other half is a ranking within a group, running totals, comparison with the previous month, walking hierarchies, turning rows into columns, and parsing documents. SQL can do all of this, and much of it can be expressed in a single query, without pulling the data out into the application. In this chapter we will cover window functions, common table expressions, recursion, conditional aggregates, set operations, working with JSON and bulk changes, and at the end we will talk about typical mistakes and the habits that make queries reliable.\n\nA common table expression, or CTE, is introduced with the word WITH: a named subquery that you can refer to in the main query. It solves the problem of readability. Instead of deeply nested parentheses, the query reads from top to bottom: first we computed the revenue per customer, then picked the best ones, then joined their cities. Each expression can be checked on its own. In many databases the optimizer inlines such an expression into the main query, like an ordinary subquery; some versions compute it once and remember the result, which can be useful if it is referenced several times. You can see the difference in the plan.\n\nA window function computes a value for each row over a related set of rows, the window, but unlike grouping it does not collapse them. The syntax: a function, then the word OVER and, in parentheses, the partition, PARTITION BY, and the order, ORDER BY. The partition splits the rows into independent groups, and the order sets the sequence inside a group. You can show an order row together with the total of all orders of its customer, and with the share of this order in that total. Windows are computed after grouping and filtering, so you cannot use them in a WHERE condition: you need a subquery or a common expression.\n\nThere are three functions for ranking. ROW_NUMBER gives unique numbers in order: with equal values the order is arbitrary. RANK gives equal values the same number and leaves a gap after them. DENSE_RANK is also the same for equal values, but without gaps. The classic task is the top few records in each group: for example, the three most expensive products in each category. The solution: number the rows inside a category by descending price in a subquery, and take the numbers up to three. To split into equal parts there is NTILE: quartiles, deciles, percentiles.\n\nThe offset functions LAG and LEAD give the value of the previous and the next row of the window. They are used to compare periods: this month's revenue minus last month's, growth in percent, the time between two events of a user. The first and last values of the window, FIRST_VALUE and LAST_VALUE, return the boundary rows: the price at the start of a period, a customer's first order. These functions replace a self-join of the table, which is slower and harder to read. The first row has no previous one, and LAG will return NULL, or a default value that you can pass as the third argument.\n\nThe window frame specifies which rows take part in the calculation for a given row. For a running sum it is from the start up to the current row. For a three-day moving average it is the two preceding rows and the current one: rows between two preceding and current row. It is important to tell the modes apart: ROWS counts physical rows, RANGE counts order values, and all rows with an equal value are included together. If no frame is given after ORDER BY, the default is RANGE from the start to the current row, and with duplicates the running sum unexpectedly jumps by the whole group of equal values at once.\n\nConditional aggregation turns rows into columns. A sum with a CASE WHEN expression counts only the matching rows: the revenue for January, February and March as separate columns of one row, and you get a pivot table. Many databases have a handy FILTER clause after the aggregate: COUNT star with a filter on a condition. Computing shares, percentages, the number of cancelled orders in a group: these are all conditional aggregates. They read the table once, instead of running a separate query for each column of the report, so they are faster and simpler.\n\nA recursive common expression walks hierarchies and graphs. It has two parts: the anchor, the starting rows, and the recursive step, which takes the previous result and adds new rows; the parts are joined with UNION ALL. This is how you find all subordinates of an employee, all ancestors of a category, a series of numbers or dates, routes in a graph. The recursion stops when a new step yields no rows. If the data contains a cycle, it will not stop: so you limit the depth, remember the path already walked, or use UNION without ALL, which discards duplicates.\n\nSet operations combine the results of queries with the same shape. UNION collects rows and removes duplicates, UNION ALL keeps everything and works faster, INTERSECT keeps the common rows, EXCEPT subtracts. Subqueries that check existence are useful too. EXISTS keeps the rows for which a match was found, and NOT EXISTS finds rows without a match: customers without orders. It is safer than NOT IN, which returns nothing if the list contains a NULL. PostgreSQL also has LATERAL: a subquery that can refer to the columns of the preceding table, convenient for the top three for each row.\n\nDocuments in JSON format can be stored right in a column and queried from SQL. To extract values you use functions or operators: a path inside the document, and a cast to the needed type. This is convenient for rare attributes, event logs and responses from external systems. But there is a price. The planner estimates selectivity poorly, and a search by a field inside a document without an index is a full scan. So for frequently used paths you create an expression index or, in PostgreSQL, a GIN index on the whole document. A structure that you constantly join and filter on is better moved into ordinary columns.\n\nBulk changes can do a lot too. Insert with merge, the upsert, adds a row or updates the existing one on a key conflict. The RETURNING clause returns the changed rows without an additional query: to get generated identifiers, or to see what was deleted. Many databases also have the MERGE command: by a matching condition, one statement inserts, updates or deletes rows according to a source. In PostgreSQL, DISTINCT ON keeps one row per key, the first by the sort order: the latest order of each customer. All these constructs make the operation atomic and reduce the number of round trips.\n\nNow about mistakes. NULL is skipped in aggregates, and COUNT of a column is not equal to COUNT star. A join multiplies rows, and a sum over the joined table gets doubled. Without ORDER BY the order of rows is undefined, even if yesterday it happened to match what you wanted. Dividing integers truncates the fraction. A condition on the right table of a left join in WHERE turns it into an inner join. Habits that help: write the query step by step in common expressions, check the intermediate results on a small data set, look at the plan, fix the order explicitly, and add tests for edge cases.\n\nLet us sum up. Common expressions make a query readable, windows compute rankings, running totals, period comparisons and moving values without collapsing rows. Conditional aggregates build pivot tables in a single pass, and recursion walks trees and graphs. Set operations and existence checks express intersection and difference. JSON is convenient for the rare, but needs indexes. Upsert and RETURNING make bulk changes atomic. Next we will see how the database chooses a plan for all of this: the optimizer, statistics and join algorithms.
