#CHAPTER 12 | HTTP/2 and HTTP/3: Multiplexing and QUIC
Chapter 12. HTTP/2 and HTTP/3: multiplexing and QUIC. A modern page consists not of one file but of dozens or hundreds: markup, styles, scripts, fonts, images. HTTP/1.1 could deliver them only in turn, and for the sake of speed browsers and developers invented workarounds. In this chapter we will see how the second and third versions solved the problem not by working around it but by design: several requests over one connection, header compression, and then giving up TCP.\n\nLet's start with the pain. On one HTTP/1.1 connection, the response to the second request cannot begin until the first one has finished. If the first resource is slow, the rest wait. Browsers open six connections, but that means six handshakes, six congestion windows and extra load on the server. Sites spread files across several domains, glue scripts into one and draw images as sprites, all to cut the number of requests. Meanwhile the headers are repeated in every request almost unchanged and waste hundreds of bytes, especially with big cookies.\n\nHTTP/2 kept the meaning of the protocol, with the same methods, codes and headers, but changed the way it is transmitted. Instead of text there are binary frames, and one connection is split into independent streams. Each request gets its own stream, and frames from different streams alternate on one connection. This is multiplexing: hundreds of requests go in parallel with no queue and no extra handshakes. Every stream has a priority and its own window, so important things, like styles, can be delivered ahead of the rest.\n\nThe second innovation is header compression, HPACK. The client and the server keep a shared table of headers they have already seen, and anything repeated is sent as a single number instead of a whole string. A typical five-hundred-byte request shrinks to a few dozen bytes. The third is server push, the ability to send a resource before it is asked for; in practice it turned out to be awkward, and browsers dropped it. Encryption is mandatory in browsers: de facto, HTTP/2 works only over TLS, and the protocol version is negotiated inside the handshake.\n\nBut HTTP/2 kept a weakness, buried one level down. All the streams ride on a single TCP connection, and TCP guarantees the order of bytes. If one segment is lost, then until it is retransmitted, TCP will not hand the application anything that arrived later, even data from other streams that were not affected. This is head-of-line blocking at the transport level. On good links it is invisible, but on mobile networks with two or three percent loss, one connection can perform worse than the six parallel ones of the old version.\n\nHTTP/3 removes the problem radically: it changes the transport. Instead of TCP it uses QUIC, a protocol on top of UDP. Reliability, numbering, congestion control and encryption are moved inside QUIC and work for each stream separately: a lost packet delays only the stream whose data was in it. The others keep receiving data. The protocol runs in user space, not in the kernel, so it can be updated together with the browser or the application, without waiting for the operating system.\n\nThere is a gain in connection time as well. TCP and TLS together spend two or three round trips before the first byte of data, while QUIC combines the transport and cryptographic handshakes into one exchange. On a repeat visit to a familiar server, a request can be sent right away, with zero round-trip time, although this mode has caveats about replays. Another property is connection migration: the connection is tied not to a four-tuple of addresses but to an identifier, so a call does not drop when the phone moves from Wi-Fi to a mobile network.\n\nHow does a client find out that a server speaks HTTP/3? First it connects over HTTP/2 or HTTP/1, and in the response it finds an Alt-Svc header, which says: the same site is available over QUIC on port four hundred forty-three. The client tries, and if UDP does not get through for some reason, as happens on corporate firewalls, it falls back to TCP. So UDP port four hundred forty-three has to be opened on the firewall, otherwise all the advantages stay on paper.\n\nWhat changes in development? Old optimization tricks for the first version become harmful with the second and third protocols. There is no need to spread files across different domains: every new name is an extra handshake and a separate connection. Gluing all the scripts into one huge file is not necessary either, because small resources are cached separately and travel in parallel. What does matter is setting priorities correctly, hinting to the browser to preload what is needed, and still not sending anything extra: compress, cache and shrink images.\n\nLet's sum up. HTTP/2 gives multiplexing, binary frames and header compression, but runs into head-of-line blocking in TCP. HTTP/3 moves everything to QUIC over UDP: independent streams, a fast handshake, connection migration. The choice of version depends on latency and loss: the farther the server and the worse the link, the more noticeable the gain. In the exercises you will choose a protocol and open a port for QUIC. Next comes encryption: TLS.
