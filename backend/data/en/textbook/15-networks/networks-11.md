#CHAPTER 11 | HTTP/1.1: Requests, Headers, Status Codes, Cache and Cookies
Chapter 11. HTTP/1.1: requests, headers, status codes, cache and cookies. Once a name has been turned into an address and TCP has set up a connection, it is the turn of the application protocol. The best known of them is HTTP. Websites, mobile apps, programming interfaces and a good part of everything else are built on it. We will look at what a request and a response look like, what the methods and codes mean, how headers, persistent connections, caching and cookies work, and why this text protocol turned out to be so long-lived.\n\nThe model is simple: the client sends a request, the server returns a response, and the exchange is over. The server never starts anything on its own, and between requests it remembers nothing about the client; people say that the protocol is stateless. A resource is identified by an address, a URL: a scheme, for example HTTP, a host name, an optional port, the path to the resource, and parameters after the question mark. The browser breaks such an address into a name and a port, finds the IP address through DNS and opens a TCP connection, and for HTTPS it also sets up an encrypted one on top.\n\nA request is plain text. The first line is called the start line: the method, the path and the protocol version. Then come the headers, one per line, an empty line, and an optional body. For example: GET, slash, index, HTTP one point one. The Host header, which is mandatory in this version, tells which site the request is for. Thanks to it thousands of sites live on one IP address; this is called virtual hosting. Every line ends with the carriage return and line feed characters.\n\nThe method says what to do. GET retrieves a resource and changes nothing. HEAD is the same, but returns only the headers. POST sends data for processing, for example a form. PUT replaces a resource entirely, DELETE removes it, and PATCH changes it partially. OPTIONS asks what is allowed. Methods that do not change the state of the server are called safe: GET and HEAD. Methods whose repetition gives the same result are called idempotent: GET, PUT and DELETE. POST is not idempotent, so repeating it blindly is dangerous: you can create two orders.\n\nA response also begins with a start line: the version, a three-digit code and an explanation. Codes are divided into classes. Two hundred means success: two hundred OK, two hundred one Created, two hundred four No Content. Three hundred means redirection: three hundred one permanent, three hundred two temporary, three hundred four Not Modified. Four hundred means a client error: four hundred one authorization required, four hundred three forbidden, four hundred four not found, four hundred twenty-nine too many requests. Five hundred means a server error: five hundred two bad gateway, five hundred three service unavailable.\n\nHeaders carry service information. Content-Type says what is in the body: HTML, JSON, an image. Content-Length gives the length of the body, and if it is not known in advance, the server sends the body in pieces with the header Transfer-Encoding: chunked. Accept and Accept-Language state the client's preferences, and User-Agent names the program. Location gives the address for a redirect. Headers are the basis of the protocol's extensibility: an unfamiliar header is simply ignored, and new behavior is added without changing the protocol itself.\n\nWhat about performance? In version one point zero, a new connection was opened for every request, which means the handshake was paid for again and again. In version one point one the connection stays open by default, and many requests go through it one after another. But requests on one connection are handled strictly in turn, and a slow response delays all the following ones; this is head-of-line blocking. That is why browsers open up to six parallel connections to one server, and sites spread their resources across different domains. These workarounds became the reason for the next version.\n\nCaching is the main accelerator of the web. The Cache-Control header says how long a response may be stored: max-age is a number of seconds, no-store forbids storing, and no-cache requires revalidation. Validators let you check a stale copy without downloading it again: the client sends If-None-Match with the tag from the ETag header, and if the resource has not changed, the server answers briefly: three hundred four. For static files you set a long caching period and change the file name on every update. For personal pages caching must never be allowed.\n\nSince the protocol is stateless, but a user's login has to be remembered, cookies were invented. The server sends a Set-Cookie header with a name and a value, the browser saves them and sends them back in the Cookie header with every following request to that site. Usually the cookie holds a random session identifier, while the data is kept on the server. The important flags are these: HttpOnly forbids scripts to read the cookie, Secure allows sending it only over HTTPS, and SameSite protects against forged requests from other sites. Without them a session is noticeably easier to steal.\n\nLet's sum up. HTTP is a stateless text protocol of requests and responses. A request consists of a method, a path, headers and a body, and a response consists of a code, headers and a body. The classes of codes show what happened: success, redirection, a client error or a server error. Persistent connections save handshakes, the cache saves transfers, and cookies bring back state. But requests go in turn, and the next version removes this limitation. Next we will look at HTTP/2 and HTTP/3.
