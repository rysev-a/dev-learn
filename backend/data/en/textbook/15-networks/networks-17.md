#CHAPTER 17 | Load Balancing, CDN, and Reverse Proxy
Chapter 17. Load balancing, CDN, and reverse proxy. Sooner or later one server stops keeping up: the number of users grows, and failures happen. The solution is several identical servers and a node in front of them that distributes the requests. It is called a load balancer, or a reverse proxy. And for global services there is one more piece: a content delivery network, which keeps copies close to users. In this chapter we will look at how all this works, how a balancer picks a server, how it finds out about failures, and how it caches, and then we will set it all up in the exercises.\n\nWhy do we need this? The first reason is scaling. Vertical scaling means a more powerful server, and that has a limit and a price; horizontal scaling means more identical servers, and it is almost unlimited, as long as the application is ready for it. The second reason is fault tolerance: when one server fails, the others keep working, and updates can be rolled out one server at a time without stopping the service. Users see a single address, and behind it stands a pool of servers. Everything else is detail about how exactly we hand out requests and what to do with the servers that fail.\n\nBalancing happens at different levels. At the transport level the balancer sees only addresses and ports: it accepts a connection on a virtual address and forwards it to the chosen server. This is fast and works for any protocol, but it knows nothing about the requests. At the application level the balancer parses HTTP: it looks at the host name, the path, headers, and cookies. It can send the root of the site to one group of servers and slash API to another, terminate TLS encryption, and compress the response. That is flexible, but costs more processor time.\n\nHow is a server chosen? The simplest algorithm is round robin: the first request goes to the first server, the second to the second, and so on. If the servers have different power, you add weights. The least connections algorithm sends a request to whichever server is busiest the least right now, and it works well when requests are uneven. A hash on the client address or on a header always sends a given client to the same server, which is useful for caches. The choice depends on what requests arrive and how uniform they are.\n\nBut we should spread requests only across live servers. For that the balancer checks the health of the backends: it periodically opens a connection or requests a special page. A server that fails to answer several times in a row is temporarily removed from the pool, and when it comes back it is put back in. Without health checks, with three servers, every third request goes into the void, and users see random errors. When a server is shut down on purpose, people use graceful draining: new connections are not sent there, while the current ones finish their work.\n\nNow, about sessions. If a user logged in on server one, and the next request lands on server two, which does not remember them, they will have to log in again. There are two solutions. The first is session affinity: the balancer sends the client to the same server, by hash or by cookie. It is simple, but when the server dies the session is lost, and the load ends up uneven. The second, the right one, is to make the servers stateless: session data lives in an external store, and any server can serve any user. Then you can freely add and remove servers.\n\nA reverse proxy is a node that external requests arrive at, and it in turn talks to the servers inside the network. It differs from an ordinary proxy by direction: that one protects clients, while this one hides servers. A reverse proxy is a convenient place to gather common functions: TLS termination with a single certificate, routing by host and path, rate limiting, compression, protection against typical attacks, and logging. The servers inside can be kept in a closed network and not published outside at all. If a backend is unavailable, the proxy answers five oh two.\n\nAnother function of a reverse proxy is caching. Responses that do not change are stored right on it and served without asking the server. A content delivery network, a CDN, extends this idea to the whole world: the provider has edge nodes all over the planet, and the user reaches the nearest one by means of geo DNS or an address announced from many places. The first request goes all the way to the origin server, the following ones are served by a cache nearby, and latency drops from hundreds of milliseconds to a few. The main indicators are the hit ratio and the invalidation rules, that is, when a copy is considered stale.\n\nOne question remains: who balances the balancers themselves? If there is only one, it is a single point of failure. So balancers are put in pairs with a shared address that moves from the failed one to the live one by means of the VRRP protocol, and in large systems the load is split at the network level: one address is announced from several places, and routers spread the flows among them. The simplest option is several addresses in DNS, but it reacts to failures more slowly because of caches. Any scheme needs testing: stop the servers one at a time and watch what happens.\n\nSo, a load balancer distributes requests across a pool of servers for scale and fault tolerance. It works at the transport or application level, picks a server by round robin, by load, or by hash, and removes sick servers from the pool using health checks. Sessions are either pinned or moved out to an external store. A reverse proxy hides the servers, gathers common functions, and caches, and a content delivery network brings copies closer to users. Next come tunnels, encrypted access, and virtual private networks.
