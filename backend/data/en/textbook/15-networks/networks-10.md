#CHAPTER 10 | DNS: How a Name Becomes an Address
Chapter 10. DNS: how a name becomes an address. People remember names, while routers work with addresses. Between them stands the naming service, and every connection to a website starts with a question: what is the IP address of this name? The Domain Name System is one of the busiest systems in the world, and yet it is almost invisible. We will look at how it is built, how a resolver walks from the root to the right server, what kinds of records there are, how the cache works, and why "it's not DNS" has turned into the most common joke among admins.\n\nLet's start with the namespace. Domains form a tree that is read from right to left. The root is the dot at the very end, and under it are the top-level domains: com, org, ru. Under those are second-level domains, for example example dot org, and under them subdomains, like www. Each node of the tree can be managed by its own owner, which removes the need to keep all the names in one place. In the past the whole table of names was handed out as a single file; today the hosts file remains only as a local hint for the computer.\n\nNow about the servers. An authoritative server stores the records of its zone and gives the final answer for them. The root servers, thirteen addresses with hundreds of copies, only know who is responsible for each top-level domain. A top-level domain server knows who is responsible for each second-level name. Such a hint-answer is called a referral: I don't know this name, ask over there. No server knows everything, but each one knows where to send you next. This is the hierarchy of delegation.\n\nRequests from end-user programs usually go not to authoritative servers but to a recursive resolver: its address is set in the system settings and is most often provided by your ISP or by your DHCP server. The resolver does all the work for the client. It receives a single question and walks the chain: it asks the root, gets the address of the org server, asks that one, gets the address of the server for example dot org, asks that one in turn, and gets the answer. The client gets a ready address back, and the resolver remembers everything it received.\n\nWhat kinds of records are there? The A record links a name to an IP version 4 address, and the AAAA record to version 6. CNAME declares a name to be an alias of another one: the resolver keeps searching, now for the new name. MX points to the domain's mail servers. NS names the servers of the zone and underlies delegation. TXT holds text, which is used to prove ownership of a domain and to protect mail. PTR works the other way round: given an address, it returns a name. Every record has a time to live, or TTL, in seconds.\n\nA record's time to live tells resolvers how long it may be kept in the cache. That is why a second request for the same name usually gets an answer in milliseconds, without going to the root or to the authoritative server. Caching takes load off the servers and speeds everything up, but it also causes the main problem: after an address changes, some resolvers keep returning the old one for a long time. Before moving a site, the time to live is lowered in advance, and after the move it is restored. Negative answers are cached too: if a name does not exist, that is remembered as well.\n\nWhat does the client see? A reply with a result code. NOERROR means all is well. NXDOMAIN means there is no such name. SERVFAIL means the resolver could not work out the answer: the servers are not responding or the configuration is broken. REFUSED means the server declines to answer, for example for a zone that is not its own. The dig utility shows the whole reply, and nslookup shows it briefly. If there is no reply at all, then connectivity to the resolver is broken, and that is a network problem, not a naming problem.\n\nNow the traps. If the hosts file on a computer has an entry, it beats any DNS answer, and a site may fail to update for just one person. If the delegation lists a nonexistent server, the zone becomes unreachable for everyone. If a zone has no backup server, a single failure takes the domain down. A classic: you cannot use a CNAME record at the apex of a zone. And by default DNS travels as plain text over UDP, so it can be eavesdropped on and forged.\n\nSeveral mechanisms were invented for protection. DNSSEC signs records cryptographically, and the resolver can check that the answer has not been forged. DNS over TLS and DNS over HTTPS encrypt the requests between the client and the resolver, so neither the ISP nor the neighbor on your Wi-Fi can see them. Neither one hides the visit to the site itself, but they make forging a name noticeably harder. We will meet all of this again in the chapters on encryption and attacks.\n\nLet's sum up. DNS is a hierarchical distributed database of names. The root knows the top-level domains, each server delegates further, and a recursive resolver walks the whole path and caches the result. The A, CNAME, MX, NS, and other records hold different facts, and the time to live controls the cache. The response codes help tell a nonexistent name from a broken configuration. Next we will talk about what is sent once we have the address: HTTP.
