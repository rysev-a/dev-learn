#CHAPTER 6 | UDP and Sockets: Datagrams Without Guarantees
Chapter 6. UDP and sockets: datagrams without guarantees. The network layer delivers packets to a computer, but dozens of programs run on that computer: a browser, mail, a messenger, updates. We need one more layer, one that gets the data to the right program and, if we want, also takes care of reliability. This is the transport layer. Let's start with its simplest protocol, UDP, and with the interface that programs use to reach it: sockets.\n\nFirst, the port. A port is a number from zero to sixty-five thousand five hundred thirty-five that picks a program inside a computer. Ports from zero to one thousand twenty-three are called system ports: well-known services live there, for example eighty for the web and fifty-three for DNS. Ports from one thousand twenty-four to forty-nine thousand are registered ports. And from forty-nine thousand on come the temporary, or ephemeral, ports: a client gets one of them for the length of a connection. A pair of an address and a port is called a socket address.\n\nUDP, the User Datagram Protocol, is the minimum that the transport layer needs. Its header takes only eight bytes: the source port, the destination port, the length, and the checksum. There is no connection: a program sends a datagram and forgets about it. The protocol does not confirm delivery, does not number datagrams, and does not resend lost ones. A datagram can get lost, arrive out of order, and sometimes even arrive in two copies. But there is no delay for setting up a connection, and no state that has to be kept.\n\nWhy do we need such a protocol? Everything where speed and freshness matter more than completeness lives on UDP. A DNS query is a question in one datagram and an answer in one, and repeating it is cheaper than keeping a connection. Voice and video: it is better to skip a lost frame than to wait for it and hold up all the others. Games, sensor readings, DHCP. And the modern QUIC protocol builds its own reliability on top of UDP, because the application knows better what it needs.\n\nHow does a program use the transport? Through sockets, an interface that the operating system gives to applications. The server creates a socket, binds it to a port with the bind function, and waits for data with recvfrom. The client also creates a socket, but the system gives it a port, and it sends a datagram with sendto, specifying the server's address and port. The server sees the client's address and port in the received datagram and replies to the same place. There are no acknowledgments and no handshakes: every datagram lives on its own.\n\nA UDP server is simple. One socket accepts datagrams from all clients in turn: a loop of recvfrom and sendto. Message boundaries are preserved: as many bytes as were sent in one datagram, that many the receiver reads. But the size is limited: if a datagram is bigger than the MTU, the network layer cuts it into fragments, and the loss of any one fragment kills the whole datagram. That is why real protocols try to keep datagrams under about twelve hundred bytes.\n\nWhat happens if nobody is listening on the port? The receiving machine sends an ICMP message: port unreachable. If the program used a connected socket, it learns about this right away, as a connection refused error. But more often there is simply no answer, and you cannot guess the reason for the silence: the datagram may have been lost, a firewall may have dropped it, the server may not have replied. So the application sets its own timeout and repeats the request a few times. This is called reliability at the application level.\n\nHow does the receiver decide which socket gets an arriving datagram? For UDP, the destination address and port are enough: the socket bound to that port receives everything. For TCP, the socket is chosen by a four-part key: the sender's address and port and the receiver's address and port. That is why one web server on port eighty serves thousands of clients, each with its own connection. NAT uses the same idea: it tells internal hosts apart by the ports that it rewrites on the way out.\n\nUDP can do what TCP cannot: send one datagram to many receivers. A broadcast to the all-ones address reaches everyone on the local network; this is how DHCP and printer discovery work. A multicast send, multicast, reaches only those who subscribed to the group address; many device discovery services are built on it. IP version six has no broadcast at all and uses multicast instead. For reliable connections such a trick is impossible: they need exactly one receiver.\n\nSo, the transport layer delivers data to programs, and addresses them by port. UDP adds only ports and a checksum: no connection, no acknowledgments, no ordering. You choose it for speed and simplicity, and if you need reliability, the application builds it. A socket is the program's interface to the transport: bind, recvfrom, sendto. A closed port answers with ICMP, but more often the silence explains nothing. Next we will look at TCP, the protocol that takes reliability on itself.
