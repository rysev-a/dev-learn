Chapter 14. Web APIs: REST, WebSocket, Server-Sent Events and gRPC. Browsers are not the only HTTP clients. Mobile apps, microservices, smart devices and integrations between companies all talk over the network through programming interfaces: one program calls another without ever thinking about pages. In this chapter we will look at how such interfaces are built: REST-style resources and methods, pagination, authorization and rate limits, and then the ways a server can push news to a client: WebSockets, server-sent events and gRPC. You will write all of it in Python.\n\nLet's start with REST. It is a set of conventions for building an interface on top of HTTP. Everything a service manages is a resource: an order, a user, an article. Every resource has its own address: slash, orders, slash, forty-two. An action is expressed by a method: GET retrieves, POST creates, PUT replaces, DELETE removes. Collections are named in the plural, and nested resources go in the path. The client keeps nothing between requests, and neither does the server: every request is self-contained, which is why a service can be scaled out to any number of machines.\n\nA resource representation is usually sent as JSON, and the type is declared with the Content-Type header. The response codes stay the same: two hundred means success, two zero one means created, and the Location header carries the address of the new resource; four hundred means the client made a bad request, four oh four means there is no such resource, four oh nine is a conflict, and four twenty-two means the data failed validation. Errors are also best returned as JSON with a clear code and message, not as a page with a picture. The main rule: the status code must tell the truth, rather than always being two hundred.\n\nNow for everyday matters. Collections can be huge, so a list is returned in pages: the client passes a page number or a cursor, and the server's response states the total number of pages and a link to the next one. Filters and sorting go in query parameters. The version of the interface goes in the path or in a header, so that new features do not break old clients. Retries are dangerous: if the response to a POST gets lost, the client will send the request again and create a duplicate. An idempotency key protects against this: the client sends a unique identifier, and the second time the server returns the saved result.\n\nWho may call the interface, and how often? Most commonly a bearer token is used: after logging in, the client gets a token and sends it in the Authorization header with every request, while the OAuth two standard describes how a third-party program gets access without the user's password. Without a token, the answer is four zero one; without permission, four zero three. To keep a single client from eating the whole service, limits are introduced: a bucket of tokens refills at a constant rate, and an empty bucket gets a four twenty-nine response with a Retry-After header. A good client waits, and makes the pause longer after every failure: exponential backoff with a little random jitter.\n\nHTTP is built as request and response: the initiator is always the client. So what do you do when you need news from the server: a chat message, a stock price, a finished job? The first solution is polling: the client asks every few seconds. That is wasteful: hundreds of empty requests for a single event. Long polling is better: the server holds the request until data appears and only then answers. But every event still needs a new request. What we need are real two-way channels or event streams.\n\nA WebSocket is a two-way channel on top of a single TCP connection. The client opens an ordinary HTTP request with the Upgrade: websocket header and a key. The server answers with code one oh one, switching the protocol, and confirms the key by computing a hash of it. After that, short frames flow in both directions over the same connection: text, binary, ping and pong. The client's frames are masked. It suits chats, games and collaborative editing. But you have to watch for disconnections, reconnection and load yourself: the connection stays open for hours.\n\nIf you only need news in one direction, it is simpler to use server-sent events. The client opens an ordinary request, and the server answers with the text event-stream content type and does not close the response, appending lines to it: the event name, the data and an identifier. The browser parses the stream itself and reconnects by itself, passing the identifier of the last event it received, so that the server can resume from the right place. It works on top of plain HTTP and passes through proxies.\n\nAnd for calling functions between services, gRPC is popular. It works on top of HTTP two, the structure of the messages is described in a separate file, and the messages themselves are encoded in a compact binary form called protobuf: numbers become variable length, and the fields are marked with numbers. Every message comes with a prefix made of a compression flag and a length. Streaming calls can go one way or both ways. Strict typing, generated clients and speed have made gRPC a standard inside large systems, but it is not native to the browser, and it is less common on the outside.\n\nHow do you choose? For public interfaces with clear resources, REST fits: it is easy to debug, the browser understands it, and it can be cached. For one-way events, use server-sent events; for two-way live channels, a WebSocket; for fast, strictly typed calls between your own services, gRPC. Whatever you pick has to be complemented with what we discussed earlier: timeouts, input validation, size limits, encryption and rate limits.
