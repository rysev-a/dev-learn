#CHAPTER 20 | Networks in the Cloud and Containers: Docker, VPC, and Kubernetes
Chapter twenty. Networks in the cloud and in containers: Docker, VPC, and Kubernetes. We have gone through the whole book from the bottom up, and in the last chapter we will see that in modern systems the same ideas live inside virtual networks. The cloud gives you a VPC: a private network with subnets, route tables, and security groups, configured with code. Containers use bridges, virtual interface pairs, and NAT on a single node. Kubernetes assembles all of this into a cluster, where every pod has its own address and load balancing is built into the service itself. There is nothing fundamentally new here: these are the same routers, NAT, firewalls, and load balancers, only virtual.\n\nLet us start with the cloud. A virtual private cloud, or VPC, is your own slice of the provider's network with an address range you choose, for example ten dot zero dot zero dot zero slash sixteen. It is divided into subnets. A public subnet has a default route to an internet gateway, so its machines can reach the internet and accept incoming connections on public addresses. A private subnet has no such route: its machines cannot be reached from outside, and for outgoing requests, for example to fetch updates, the default route leads to a NAT gateway in the public subnet.\n\nThe role of the firewall is played by security groups. A security group is a set of rules attached to a machine's network interface. A rule allows incoming traffic from a source to a port: for example, a web server is allowed port four hundred forty-three from anywhere, while a database is allowed port three thousand three hundred six only from the group of application servers. Security groups are stateful: replies to an allowed connection pass on their own. They contain no deny rules: everything that is not allowed is closed. Besides them there are network access control lists at the subnet level; they are stateless and support explicit denies, so they are used for coarse boundaries.\n\nCloud networks are connected to one another. Peering joins two networks directly, but it is not transitive: if A can see B, and B can see C, that does not mean A can see C. For larger designs you build a transit gateway, a hub-and-spoke with a shared point in the middle. You connect to an office or a data center through a VPN or a dedicated link. And to keep traffic to cloud services from leaving for the internet, you create private endpoints: storage and a queue end up inside your network. The addresses of different networks must not overlap, or you will not be able to connect them.\n\nNow, containers. A container is an ordinary process, but with an isolated network namespace: it has its own interfaces, addresses, routing table, and firewall rules. To connect it to the outside world, a virtual pair of interfaces is created: one end inside the container, the other on the node, in a bridge. The bridge works like a switch, and all the containers on it end up in one subnet. The node, like a router, holds the bridge's address and lets containers out using NAT. In other words, everything you configured on hosts is repeated inside a single machine.\n\nIn Docker, the default network is called bridge. Containers get addresses from a private range, reach the internet through masquerading, and inside the network find each other by name thanks to the built-in DNS. To make a service inside a container visible from outside, you publish a port: Docker adds a DNAT rule from a port on the node to the address and port of the container. There are other modes too: host networking, where the container uses the node's interfaces without isolation, and no network at all. And to connect containers on different nodes, you use overlay networks.\n\nAn overlay is a network on top of a network. The container's packet is wrapped in a UDP packet between nodes, as in a virtual private network, and unwrapped on the other node. The popular VXLAN format adds a virtual network identifier, so you can keep many isolated networks on the same nodes. Such networks are attached through plugins, called CNI: each implements pod addressing, routing, and policies in its own way, from an overlay to pure routing over BGP. The MTU inside an overlay is smaller, and that again has to be taken into account.\n\nKubernetes sets simple rules: every pod has its own address, any pod can reach any other without NAT, and nodes can see all the pods. Pods are short-lived and their addresses change, so there is the Service: a permanent virtual address and a name behind which stands a set of pods. A cluster address is reachable only inside, a node port opens a port on every node, and a cloud load balancer exposes the service to the outside. Requests are spread across pods by kube-proxy through rules on the node, and a readiness probe decides which pods are ready. Internal names are resolved by the cluster DNS, and incoming traffic by host and path is accepted by an ingress, which is an ordinary reverse proxy.\n\nIsolation inside the cluster is provided by network policies: by default, all pods see all pods, and a policy says that only the application pods may talk to the database. The same firewall rules implement this, and in modern plugins, eBPF programs in the kernel do. Service meshes take over encryption and mutual authentication between pods through helper proxies next to each application. And diagnostics do not change: ping, traceroute, packet capture, and a look at routing tables and firewall rules, only now inside the namespace of the right container.\n\nLet us sum up the whole book. A network is nodes, links, and packets, organized into layers. Addresses, routes, and MAC addresses deliver a packet, TCP and UDP provide transport, application protocols and encryption build services on top of that, and firewalls, load balancers, and tunnels make them secure and scalable. The cloud and containers simply move the same mechanisms into a virtual environment. So to make sense of any new system, it is enough to ask: what are the addresses, routes, rules, and ports here? You now know how to ask these questions.
