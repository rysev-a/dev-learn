Chapter 13. TLS and HTTPS: encryption, certificates and trust. Everything we have covered so far travelled as plain text: any node along the path could read a password in a request or swap out the page in a response. For the real internet, that is not enough. The TLS protocol encrypts the connection, checks that the server on the other end is really the one you wanted, and protects the data from tampering. In this chapter we will look at the guarantees it gives, how the handshake works, and how the certificate system works.\n\nLet's start with the goals. TLS provides three properties. Confidentiality: the data is encrypted, and an eavesdropper sees a pile of random bytes. Integrity: every message is protected by a check code, so nothing can be changed without being noticed. Authentication: the client makes sure it is talking to the real server, and not to an impostor on the path. TLS slots in as a separate layer on top of TCP, and the application does not even see it. HTTP with this layer is called HTTPS, and it runs on port four forty-three.\n\nHow do you agree on encryption with someone you have never met? Two kinds of cryptography are used. Asymmetric cryptography uses a pair of keys: a public one and a private one. The public key can verify a signature made with the private key, but you cannot work out the private key from the public one. It is slow, so it is needed only for the handshake. Symmetric cryptography uses one shared key for both encryption and decryption. It is fast, and it encrypts everything else. The handshake turns the first into the second: through a key exchange, the two sides arrive at a shared secret that was never sent over the network.\n\nThe TLS one-point-three handshake takes a single round trip after TCP is established. The client sends a ClientHello: the versions and ciphers it supports, and its share of the key exchange. The server answers with a ServerHello containing its own share, then sends its certificate, a signature proving it holds the private key, and a finished message. The client checks the certificate, computes the shared secret, and sends its own finished message. From then on, everything is encrypted data. Version one-point-two needed two round trips, and older versions are simply insecure and have been switched off.\n\nWhy is the key exchange made ephemeral? For every connection, the client and the server work out a fresh secret, and the server's private key is used only to sign. This property is called forward secrecy: even if the private key is stolen a year from now, previously recorded traffic still cannot be decrypted. The data itself is encrypted with modern modes such as AES-GCM or ChaCha twenty, which check integrity at the same time. And to avoid repeating the whole handshake, the server hands out a resumption ticket, so the next visit sets up the connection faster.\n\nNow, trust: how does the client know that a public key really belongs to this particular site? A certificate is a document that contains the site's name, its public key, its validity period, and the signature of a certificate authority. An authority is an organization that is trusted in advance: the list of root authorities is built into the operating system and the browser. Root authorities sign intermediate ones, and those in turn sign the certificates of websites, which forms a chain. If the signature is correct and the root is on the trusted list, trust passes from the root down to the site.\n\nWhat exactly does the client check? First, the validity period: if the certificate has expired, the connection is rejected. Second, the name: the address the user typed must match one of the names in the certificate, in the subject alternative name field, including wildcard names such as star dot example dot org. Third, the chain: every signature must be valid, and the chain must lead to a trusted root. The server is required to send its own certificate and the intermediate ones: if you forget them, some clients will rebuild the chain on their own, while others will refuse. Fourth, revocation: the certificate may have been revoked after a key compromise.\n\nThis is exactly where administrators make the most common mistakes. An expired certificate: everything worked at night, and by morning the site is down for everyone. A certificate issued for the bare domain, without the www, while users open the site with it. A missing intermediate certificate: it opens on the administrator's computer but not for clients. An internal certificate authority that has not been added to the trusted list on devices. A self-signed certificate in a production system. Half of these problems are cured by automation: Let's Encrypt issues free, short-lived certificates using the ACME protocol and renews them with no human involved.\n\nA few more concepts. Mutual authentication: the client also presents a certificate, which is how companies protect traffic between internal services. Certificate transparency: every issuance is recorded in public logs, so a forged certificate can be noticed. The start of the connection goes in plain text: the ClientHello carries the site name, the SNI, so an observer can see which site you are connecting to, even though the content is hidden. TLS protects the channel, but it will not protect you from a malicious website or from your password being stolen on your own computer.\n\nSo, TLS gives confidentiality, integrity and authentication. The handshake exchanges keys and checks the certificate, and after that everything runs on fast symmetric encryption. Trust is built on a chain from the site, through intermediate authorities, to a root in the client's store. The validity period, the name and the chain are checked on every connection. In the exercises, you will fix an expired certificate, a wrong name, a broken chain, an untrusted authority and an outdated version. Next, we will look at the programming interfaces of the web.
