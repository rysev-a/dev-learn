Chapter 9. Sockets in your program: blocking I/O, select, epoll, and async. So far we have looked at the network from the outside. Now let's look at it through a programmer's eyes: which calls do we need to connect to a server, accept a connection, and read and write bytes. We will go through a TCP client and server, the trap of a stream with no message boundaries, timeouts and errors, and then the ways to serve thousands of clients: threads, multiplexing, and async. In the exercises you will write real Python code.\n\nA TCP client takes four steps. It creates a socket, specifying the address family and the type: stream. It calls connect with the server's address and port; this is where the handshake happens, and the call blocks until it finishes or fails. Then it sends data with sendall, which guarantees that everything is sent, and reads the reply with recv. Finally it closes the socket. If the port is closed, connect fails with a connection refused error; if the server does not answer, it fails with a timeout error.\n\nA server is a bit more complicated. It creates a socket, binds it to an address and port with bind, and switches it to listening mode with listen. The number in the argument is the length of the queue of connections that have not been accepted yet. Then, in a loop, it calls accept: that call blocks until somebody connects, and returns a new socket for talking to that client. The listening socket stays where it is and keeps accepting. If you accept nothing and the queue overflows, new clients will wait or get refused.\n\nNow the main trap. TCP carries a stream of bytes, not messages. Three writes of a hundred bytes each can arrive as three reads, as one, or as a hundred and fifty and a hundred and fifty. The recv call returns whatever has piled up so far, but no more than you asked for, and an empty result means the other side has closed the connection. So a protocol needs message boundaries: a delimiter, such as a newline, or a length in front. You have to read in a loop until you have collected everything you need.\n\nEvery network program has to expect the worst. A timeout is set with settimeout: without it, recv can block forever if the other side hangs. Typical errors are connection refused, a connection reset in the middle of a read, a broken pipe on a write, and an expired timeout. All of these must be caught, and the socket must be closed. A socket should always be closed, and the most reliable way is the with statement. Leaking sockets is a classic reason why a server stops responding after a week.\n\nHow do we serve many clients? The simplest way is a thread per client: the main thread accepts connections and starts a thread for each one, where recv can block in peace. The code is straightforward, and one client's errors do not bother the others. But threads are not free: each has its own stack, switching is expensive, and at a few thousand connections the server starts to gasp. That is fine for hundreds of clients, but tens of thousands call for a different approach.\n\nThe other approach is multiplexing. Instead of many threads, a single thread asks the operating system: which of these sockets are ready? The calls for that are select, poll, and epoll on Linux, and kqueue on BSD-family systems. The system returns a list of sockets that can be read without blocking, and the thread handles only those. Epoll scales to hundreds of thousands of sockets, because its cost depends on the number of ready sockets, not on the total. In Python there is the selectors module for this.\n\nNon-blocking sockets and an event loop are the foundation of async. The program describes an action as a coroutine: it waits for data with the await keyword, and at that moment it hands control back to the loop, which switches to another coroutine. One thread serves thousands of connections, and the code still looks almost like ordinary sequential code. Let's note the limits right away: any long computation inside a coroutine freezes the loop for everyone, so heavy work is moved out into separate processes or threads.\n\nA few rules for real services. Before restarting a server, enable address reuse, otherwise the port will be held by the TIME_WAIT state. Limit message sizes and the number of clients, so that a single attacker cannot eat all your memory. Put timeouts on everything. Don't forget encodings: bytes travel over the network, not strings. Don't send data faster than the receiver can read it: take backpressure into account, that is, slow down when the buffers are full. And log client addresses and the reasons for disconnects.\n\nSo, sockets are a program's interface to the network. A client does connect, sendall, and recv. A server does bind, listen, and accept. A stream of bytes needs its own message boundaries and read loops. Timeouts and closing are mandatory. A thread per client is simple; multiplexing and async scale.
