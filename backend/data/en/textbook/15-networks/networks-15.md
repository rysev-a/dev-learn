Chapter 15. Network diagnostics: ping, ss, tcpdump, and Wireshark. A network rarely breaks in a tidy way: a user writes that nothing opens, and the cause can be anywhere, from an unplugged cable to an expired certificate. A good engineer is not the one who knows every command, but the one who walks up the stack methodically and narrows the search quickly. In this chapter we will put together a toolkit and a workflow: ping and traceroute, dig and curl, ss, tcpdump and Wireshark, and then we will look at the classic problem of packet size.\n\nLet's start with the method. First, state the symptom clearly: what exactly does not work, for whom, since when, and what changed. Second, go from the bottom up through the layers we covered in chapter two: power and cable, port and MAC address, address and route, service port and firewall, application. Third, form a hypothesis and test it with a single measurement. Fourth, change only one thing at a time and watch the result. And fifth, write down what you found, because a diagnosis that is not recorded will have to be made all over again a month later.\n\nThe simplest tool is ping. It sends echo requests and measures the round-trip time. A reply tells you that a path exists in both directions, and the time shows load and distance. If ping to an address works but ping to a name does not, the problem is in DNS. If you can reach a neighbor but not the gateway, the address, the mask, or the link is to blame. If there is packet loss, the network is overloaded or unstable. But there is an important limitation: many networks filter ICMP, so a silent ping does not prove that the host is not there.\n\nTo see the path, people use traceroute or its improved version, MTR. The time to live grows step by step, and each router announces itself. You have to read the output with care. An asterisk on one hop while the following hops look normal means that this router does not answer ICMP but does forward packets. A break at some hop with only asterisks after it is the likely place of the problem or of a filter. A sharp jump in latency means a long link or congestion. And different paths there and back are perfectly normal: the reply travels its own route.\n\nNow let's talk about the host itself. The ip command shows interfaces, addresses, and routes, and it should be the first thing you reach for: is the port up, is there an address, where does the default route point. The ss command shows sockets: which ports the server listens on and on which addresses. A classic mistake: the service listens only on one twenty-seven dot zero dot zero dot one, that is, the loopback address, and is unreachable from outside, even though everything works on the machine itself. Connection states point to other problems as well: a pile of half-open handshakes, connections stuck in a closing state, an overflowing queue.\n\nThe application layer has its own tools. Dig shows what the resolver answered and from where. Curl with the verbose flag shows the whole HTTP request and response: status code, headers, redirects, sizes, connection time, and handshake time. The openssl command with s_client shows the certificate chain, the expiry date, and the TLS versions. Netcat helps you tell a refusal from silence: a closed port answers with a reset, while a filter stays silent. Each of these tools quickly answers the question: at which layer does it break?\n\nWhen that is not enough, you need packet capture. Tcpdump runs on the host and prints everything that passes through the interface. Filters narrow the stream by protocol, address, or port. In the output you can see the life of a connection. A SYN flag with no reply means the handshake never completes: the packet is lost or filtered. An RST flag right after a SYN is a refusal. Repeated segments mean loss. A stream without acknowledgments means a problem on the return path. To find where exactly a packet disappears, run the capture on several hosts along the chain and compare.\n\nWireshark is the graphical version of the same thing. It reads live traffic or a capture file, colors packets by protocol, and breaks them down field by field, all the way up to the application. You can follow a single stream from start to end, plot latency and throughput graphs, and see how much time went to the handshake, to waiting for the server, and to the transfer. A typical routine is to capture on the server with tcpdump, copy the file, and analyze it in Wireshark. And to decrypt TLS, you can ask the browser to write the session keys to a separate file.\n\nA classic of its own is packet size. Small requests go through, but large responses hang. This happens when there is a link with a smaller MTU somewhere along the path, a tunnel for example, and the ICMP message saying fragmentation is needed gets blocked somewhere. The sender knows nothing about the problem and keeps sending large segments with the don't-fragment bit set. It is easy to check: a ping with a large size and the don't-fragment flag shows the threshold. The cure is to lower the MTU on the interface, to clamp the segment size on the gateway, and to allow the necessary ICMP messages.\n\nLet's sum up. Diagnostics is a method: symptom, layers from the bottom up, one hypothesis, one change. Ping and traceroute show the path and the losses, ip and ss show the state of the host, dig, curl, and openssl cover the application layer, and tcpdump and Wireshark show the real packets. A refusal and silence are different diagnoses, and MTU problems look like large things not working. In the exercises you will find a lost packet, fix an MTU, and untangle a failure spanning several layers at once. Next we will talk about firewalls.
