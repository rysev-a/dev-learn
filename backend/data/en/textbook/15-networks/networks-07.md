#CHAPTER 7 | TCP: Handshake, Byte Numbering, and Closing a Connection
Chapter 7. TCP: handshake, byte numbering, and closing a connection. UDP sends and forgets, but most programs need something else: that bytes arrive intact, in order, and without repeats. A web page, a letter, a file, a command in a terminal. This service is provided by TCP, the Transmission Control Protocol. On top of unreliable IP it builds a reliable two-way stream of bytes. In this chapter we will see how a connection is opened and closed, how bytes are numbered, and how acknowledgments work.\n\nThe main difference of TCP is that it is connection-oriented. Before exchanging data, the two sides agree with each other and set up state on their ends: numbers, windows, timers. A connection is identified by a four-part key: the client's address and port, and the server's address and port. For the application it is simply a stream: it writes bytes into the socket on one side and reads them on the other, without thinking about packets. There are no message boundaries in a stream: ten sends of a hundred bytes each can be read in one chunk of a thousand.\n\nA connection starts with a three-way handshake. The client sends a segment with the SYN flag and its initial number. The server replies with a segment with the SYN and ACK flags: it acknowledges the client's number and announces its own. The client sends an acknowledgment, and the connection is open. The numbers are chosen at random, not from zero, so that foreign and old segments are not taken for your own. If the port is closed, an RST, a refusal, comes back instead of a reply. If a packet is lost or filtered, nothing comes at all, and the client repeats the SYN.\n\nNow about numbering. Every byte of the stream has a sequence number. The segment header holds the number of the first data byte, and the acknowledgment field holds the number of the next byte that the receiver expects. If the client sent a hundred bytes starting at one thousand, the acknowledgment will come back with the value one thousand one hundred. Acknowledgments are cumulative: one number says "everything up to this byte has been received". Thanks to the numbers, the receiver restores the order, drops duplicates, and notices gaps: if bytes from one thousand to one thousand one hundred and from one thousand two hundred have arrived, but the middle is missing, it acknowledges one thousand one hundred again.\n\nWhat else is in the header? Ports, header length, flags, window size, and a checksum. The flags: SYN opens a connection, ACK acknowledges, FIN closes, RST resets, and PSH asks to pass the data to the application right away. The window size tells the sender how many more bytes the receiver is ready to accept; we will talk about it in the next chapter. The maximum amount of data in a segment is called the MSS: it is chosen during the handshake so that a segment fits into the MTU and is not fragmented.\n\nHow does TCP cope with loss? After each segment, the sender starts a timer. If the acknowledgment does not arrive within the RTO time, which is computed from the measured round-trip time with a margin, the segment is sent again. There is also a fast way: three identical acknowledgments in a row mean that one particular segment is missing, and it is repeated without waiting for the timer. Meanwhile, the receiver does not hand the application data from after the gap: it waits until the gap is filled, and the order is preserved.\n\nClosing a connection is also a matter of agreement. A side that has nothing more to send sends a FIN. The other side acknowledges it but can keep sending: the connection is closed in each direction separately, and in this state it is called half-closed. When the other side is finished, it also sends a FIN, and the first side acknowledges it. After that, the side that started the closing holds the connection for some time in the TIME-WAIT state, usually a minute, so that late segments do not end up in a new connection with the same ports.\n\nConnection states are visible in the system with the ss command. LISTEN means the server is waiting for connections. SYN-SENT means the client has sent a SYN and is waiting for a reply. ESTABLISHED means the connection works. TIME-WAIT means a closed connection is still remembered. When a server sees many connections in the SYN-RECV state and clients do not finish the handshake, that is a sign of a SYN flood attack. And piles of connections in TIME-WAIT say that the application opens and closes connections too often instead of reusing them.\n\nWhere does TCP meet the rest of the network? A stateful firewall remembers connections: it allows reply segments of connections that are already open and blocks new incoming ones. NAT remembers the four-part key and rewrites the address and port. A refusal and silence are different diagnoses: an RST says that the server is alive and the port is closed, while silence says that packets are lost or filtered. You need to tell them apart right away. The main price of reliability is delay: one handshake costs one round trip, that is, some milliseconds before the first byte.\n\nLet's sum up. TCP gives a reliable stream of bytes on top of an unreliable network. A connection is opened by a handshake of three segments, bytes are numbered, acknowledgments are cumulative, and losses are caught by a timer and by repeated acknowledgments. A connection is closed by two FINs and then lives on for a minute in TIME-WAIT. A closed port answers with an RST, while a filter stays silent. Next we will see how TCP picks its speed: windows, loss, and slow start.
