Trees and Heaps. Chapter 11. Binary Search Trees. We have learned to walk through trees, and now we will make a tree do real work. Which structure should we choose if we need fast search, fast insertion, and order all at once? A sorted array searches in logarithmic time, but inserting into the middle shifts half of the elements. A hash table inserts in constant time, but knows nothing about order: the nearest key, a range, the next larger value are all out of its reach. A binary search tree gets everything at once: search, insertion, and deletion follow a single path from the root downward and cost the height of the tree, while an in-order traversal returns the keys sorted. In this chapter we will go through the rule, the operations, the danger of degeneration, and prepare the ground for balancing. At the end, fourteen exercises are waiting for you.\n\nThe search tree rule is just one, but it holds at every node: all keys in the left subtree are smaller than the node's key, and all keys in the right subtree are larger. Not only for the children, but for all descendants. From the rule, the inorder traversal follows immediately: left, node, right produces the keys in ascending order. A search tree is a sorted array hung by its middle: the root is the median, and each subtree again has its own middle. That is why checking that a tree is valid is a frequent interview question, and it is easy to get wrong: comparing a node with its children is not enough. You have to pass the allowed bounds down: a left child must be no larger than its parent and no smaller than all the ancestors at which we turned right.\n\nSearch works like this: compare the key we want with the key of the node. Equal means found. Smaller, go left; larger, go right. If we reach an empty link, there is no such key. At every step a whole subtree is discarded, just like in binary search on an array, and it costs as many steps as the height of the tree. Search is written as a loop without recursion: a variable for the current node and a comparison. The same descent finds the nearest values: while going down, remember the last node where we turned right, which is a candidate for the largest key not exceeding the target, and the last node where we turned left, which is a candidate for the smallest key not less than the target.\n\nInsertion is the same descent to an empty spot. Start from the root: smaller, go left; larger, go right; and when the needed link is empty, hang the new node there. The other nodes are not touched, so insertion costs the height of the tree and needs no shifting. It is important to decide what to do with duplicates. The options: ignore them, keep a counter in the node, or treat equal keys as belonging to the right. The choice affects all the other operations, so define the policy right away. One more subtlety: insertion is conveniently written as a recursion that returns the new root of a subtree, but for deep trees you need an iterative version with a pointer to the parent.\n\nThe minimum of a tree is the leftmost node: go left as long as you can. The maximum is the rightmost. The next larger key after a given one, the successor, is found in two cases. If the node has a right subtree, it is the minimum of that right subtree. If not, it is the nearest ancestor for which our node lies in the left subtree; you can find it with a descent from the root. The predecessor is found in the same way. The successor and predecessor are the basis of tree iterators and of node deletion. And the k-th smallest key is found by an inorder traversal that stops at the k-th visit, or, if every node stores the size of its subtree, in time proportional to the height of the tree.\n\nDeletion is the trickiest operation, and it has three cases. A leaf is simply cut off. A node with one child is replaced by that child together with its subtree. The hard case is two children: there is no simple place for a replacement. Then we take the successor, the minimum of the right subtree, copy its key into the node being deleted, and delete the successor itself from the right subtree; it has no left child, so the deletion reduces to a simple case. The order in the tree is preserved, since the successor was the closest key in value. Mistakes in deletion are the most common cause of broken trees in interviews and in production, so work through all three cases by hand.\n\nThe cost of all operations is the height of the tree, and it depends on the insertion order. If keys are inserted in random order, the average height stays on the order of a logarithm, about one and a half binary logarithms of the number of nodes. If keys are inserted in ascending order, every new one is larger than all the others, goes to the right, and the tree turns into a chain: the height equals the number of nodes, and search, insertion, and deletion cost linear time. That is how a search tree, beautiful on paper, degrades into a linked list. Sorted or nearly sorted data is everyday life: timestamps, increasing identifiers. So we need a mechanism that keeps the height small.\n\nA search tree is good at what a hash table cannot do. A range query: all keys from a to b. We descend from the root, and if a node is smaller than a, we skip its left subtree entirely; if it is larger than b, we skip the right one. The remaining keys are traversed in order. The time is the height plus the number of keys found. An ascending iterator is built on a stack: it holds the path from the root to the current node and pops the successor at each step, spending memory only on the height of the tree. The nearest key, floor and ceiling, the number of keys smaller than a given one, the median: all of these are natural operations of an ordered structure.\n\nLet's compare the tools. A sorted array: search in logarithmic time, insertion and deletion in linear time, but the best memory use and cache behavior. A hash table: search, insertion, and deletion in constant time on average, but with no order. An unbalanced search tree: everything in time of the height, good on average, linear in the worst case. A balanced tree: all operations in logarithmic time in the worst case, plus order and ranges. The rule of choice is simple. If you only need access by key, take a hash table. If you need ordering, take an ordered dictionary on a balanced tree. If the data rarely changes but is read often, take a sorted array. Such ordered dictionaries exist in Java, C plus plus, and many other languages.\n\nHow do we keep the height small? The main tool is the rotation. It is a local restructuring of three nodes: a parent and its child swap places, and the subtree that lay between them moves to the new parent. A left rotation lifts the right child up, a right rotation lifts the left one. The key property: a rotation does not break the key order, the inorder traversal stays the same, while the height changes. A rotation costs a constant number of link assignments. Self-balancing trees are built from rotations: in AVL trees, after each insertion the difference of subtree heights is checked, and a rotation is made when it exceeds one. Red-black trees use node colors; we will talk about them in one of the following chapters.\n\nTypical mistakes with search trees keep repeating. The first is checking validity by the children alone, without bounds. The second is an inconsistent duplicate policy: insertion sends equal keys to the right, while search looks for them on the left. The third is deleting a node with two children: people forget to remove the successor from its old place and get duplicates. The fourth is recursion on deep trees. The fifth is expecting logarithmic time from an unbalanced tree on ordered data. The best medicine is to write tests for degenerate cases: an empty tree, a single node, a chain, deleting the root, deleting a node with two children, repeated keys.\n\nHere is what to work on in practice. Implement a search tree with insertion, search, and deletion. Write an iterative traversal and an iterator that stores only the path. Find the k-th smallest key, the floor, and the ceiling. Compute the sum of keys in a range, cutting off subtrees. Build a balanced tree from a sorted array, always choosing the median as the root. Find a pair with a given sum by moving two iterators toward each other. That is twelve of the fourteen exercises of the chapter; the other two, insertion and validation, are familiar to you from the traversals.\n\nLet's sum up. A search tree is the rule smaller on the left, larger on the right at every node; an inorder traversal produces the keys in ascending order. Search, insertion, and deletion follow a single path from the root, and their cost equals the height. Deletion has three cases, and the hard one is solved by replacing with the successor. On random data the height is about a logarithm, on ordered data it is linear, and then the tree degenerates into a list. The medicine is rotations and self-balancing trees. A search tree preserves order, ranges, and nearest keys, which a hash table cannot give. Fourteen exercises are waiting for you.
