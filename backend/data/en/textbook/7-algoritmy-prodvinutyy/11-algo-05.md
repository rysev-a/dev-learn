Structures and Patterns. Chapter 5. Hash Tables. The hash table is the most useful data structure in everyday programming. A dictionary, a set, a counter, a cache, an index, deduplication: all of these are hash tables. Its promise sounds almost unfair: insertion, lookup and deletion in constant time on average, no matter how much data is stored. In this chapter we will build a hash table by hand and see what it is made of: a hash function, collision resolution, and rebuilding as it grows. We will look at the different schemes: chaining, linear, quadratic and double probing, Robin Hood hashing, and cuckoo hashing. And then we will use our own table for classic problems. Twenty exercises are waiting for you.\n\nThe idea of a hash table is simple. Take an array of m slots. The hash function turns any key into an integer, and the remainder of dividing it by m gives the slot number. To insert, we put the key and value pair into the slot with that number; to look up, we compute the same number and look right there. No scanning at all: we compute the number and arrive at the spot immediately. This is a development of the idea of an array with constant-time access by index, except that the index is not a number from zero to n but any key: a string, a tuple, a number. The hash function takes time proportional to the size of the key, but not to the number of elements in the table, so the operations, on average, do not depend on the volume of data.\n\nWhat makes a good hash function? First, it must be deterministic: the same key always gives the same number. Second, it must be fast. Third, it must be uniform: different keys should spread across the slots evenly, without clumps. For integers there are two classic methods. The division method takes the remainder of the key divided by the table size. It works well if the size is a prime number, and it is terrible if the keys are multiples of the size: with a table of size eight, keys that are multiples of eight all land in one slot. The multiplication method multiplies the key by a clever constant, roughly two to the power of thirty-two divided by the golden ratio, takes the low part of the product, and scales it down to the table size. This method is not afraid of multiples.\n\nFor strings, the best-known scheme is the polynomial hash. We read the characters from left to right; at each step we multiply the accumulated number by a base, for example thirty-one, add the character code, and take the remainder modulo a large number. The result is the value of a polynomial whose coefficients are the characters, so a different order of characters gives different numbers. The Rabin–Karp substring search is built on this trick: the hash of a window is easy to update when it shifts by one character. Other common functions are FNV, where a byte is combined with the accumulated value using exclusive or and then multiplied by a prime, and universal families with random parameters. Cryptographic hashes are not needed for tables: they are too slow.\n\nWhat if two different keys land in the same slot? This is called a collision, and it cannot be avoided. The pigeonhole principle says: if there are more keys than slots, at least two of them share a slot. But even in an almost empty table, collisions happen more often than intuition suggests. The birthday paradox: with a hundred slots, thirteen keys are already enough for a collision to occur with probability above one half. So the engineering of a hash table is not a fight to have no collisions, but the skill of making them cheap. There are two big families of methods: store in each slot not one value but a whole chain, or look for a spare slot by a fixed rule, which is called open addressing.\n\nThe first method is chaining. Each slot stores not a value but a list of pairs: everything that landed in the slot lives in its chain. To insert, we compute the number and look for the key in the chain; if it is there, we update the value, otherwise we append the pair. Lookup and deletion work the same way. The cost is determined by the length of the chain, and the average length equals the load factor, the number of elements divided by the number of slots. As long as it is at most one, the chains are short on average and everything runs in constant time. The strengths of chaining are simplicity and tolerance for a poor hash function and for overfilling. The weaknesses are extra memory for lists and pointers, and jumping around memory, a hello from linked lists. This is exactly how hash tables work in Java.\n\nThe second method is open addressing: all pairs live right in the array, with no lists. If the slot we need is taken, we look at the next one, then the next, and so on. This is linear probing. Lookup follows the same path: from the computed slot forward, until we find the key or hit an empty slot, which means the key is definitely not there. Everything lies contiguously in one array, so the processor cache is happy, and in practice linear probing is often faster than chaining. The weak spot is clustering: occupied slots stick together into long runs, and every new insertion into a run makes it even longer. That is why open addressing needs a roomy table: the load factor is kept below one half or two thirds.\n\nDeletion in open addressing is a delicate matter. You cannot simply clear the slot: the run would break, and the search for keys that lie further along the probe path would conclude that they are not there. So in place of the deleted key we put a tombstone, a special marker: lookup passes through it and continues, while insertion may take its place. Tombstones pile up and clutter the table, so they are thrown away when the table is rebuilt, and when counting the load they are counted just like live keys. There is also an alternative without tombstones, backward shift: after a deletion we pull the following keys back, the ones that are allowed to move. The question of why you can’t just zero out the slot is a favorite at interviews.\n\nTo fight clustering, cleverer orders of visiting the slots were invented. With quadratic probing the steps grow: first by one, then by three, then by six, following the triangular numbers; for a table whose size is a power of two, this sequence visits every slot. Keys that started in neighboring slots quickly diverge, and the runs do not stick together. With double hashing, the step is determined by a second hash function: two keys that landed in the same slot have different steps, so their further paths do not coincide. All that is needed is that the step is never zero and is coprime with the table size; the easiest way is to take a prime size. The price is access that is less friendly to the cache, and more complex code.\n\nRobin Hood is an improvement on linear probing with the motto of taking from the rich and giving to the poor. Each key remembers its distance from its home slot. When inserting, if we meet a key that has traveled a shorter distance from home than we have, the newcomer takes its place, and the former owner continues its journey from that same point. The distances even out: the unluckiest keys stop wandering far away. The gain is twofold. A lookup can stop earlier: if we meet a key whose distance is smaller than ours, there is no point looking further. And the spread of lookup times is small. Deletion is done by backward shift, without tombstones. This scheme worked for many years in the standard hash table of the Rust language.\n\nCuckoo hashing makes a different trade-off: a lookup always takes at most two checks. There are two tables and two hash functions; every key has exactly two possible homes. When inserting a key, we put it in its first home. If someone already lives there, we evict the occupant, like a cuckoo pushing out eggs, and the occupant goes to its second home, evicting the next one in turn. The chain of evictions is usually short. If it loops, the table is rebuilt with new functions or a larger size. Insertion is amortized constant, and lookup is at most two checks even in the worst case, which is valuable for network devices and real-time systems.\n\nEvery hash table keeps its load factor under control: when it exceeds a threshold, the table grows. Typical thresholds are three quarters for chaining and between one half and two thirds for open addressing. Growth is not just copying an array. The slot number depends on the table size, so it changes for every key, and all the pairs have to be inserted again. This is called rehashing. It is expensive but rare: the size doubles, and by the same argument as for a dynamic array, the amortized cost of an insertion stays constant. If the number of elements is known in advance, it is better to create the table at the right size right away, and there will be no rehashing at all.\n\nWhich keys suit a table? The main law: if two keys are equal, their hashes must be equal. Break it, and a key gets lost in the table even though it is sitting right there. This gives the second requirement: a key must not be changed while it lies in the table, otherwise its hash changes and it ends up in the wrong slot. That is why in Python you cannot use lists as keys, but you can use tuples and strings. The third point is security. If an attacker knows the hash function, they can pick thousands of keys with the same hash, and the table degenerates into a chain: queries turn from constant time into quadratic. This is called a collision attack. Modern languages defend against it with a random hash seed chosen when the program starts.\n\nNow let us use the table. The first pattern is counting. We need the frequency of each word in a text, the most frequent character, or the number of distinct elements. We create a table from element to counter and pass over the data once: if we find the key, we increase the counter; if not, we store a one. The result is linear time instead of quadratic with a nested loop. A variation is grouping: the key is computed from the element so that equivalent elements give the same key. Anagrams, for example, are identical once their letters are sorted: the key is the sorted word, and the value is the list of words in the group. If only unique elements are needed, the values are not needed at all, and the table turns into a set.\n\nThe second pattern is looking for the complement. The task: find two numbers in an array with a given sum. Instead of two nested loops, we walk through the array and for each number ask the table whether the number target minus current has already been seen. If yes, the pair is found; if not, we remember the current one. Quadratic turns into linear time, paid for with memory. The third pattern is prefix sums plus a table. How many subarrays have sum k? We go from left to right, accumulating the sum from the start, and for each position we ask how many times the accumulated sum smaller by k has occurred before. Each such occurrence is a subarray with the required sum. The table stores how many times each accumulated sum has occurred.\n\nThe fourth pattern is a table plus another structure. A cache that evicts the least recently used entries: the hash table gives instant lookup of an entry by key, and a doubly linked list orders the entries by recency. The table stores not the values but references to list nodes; on access, the node moves to the head, and on overflow the tail is removed. All in constant time. The fifth pattern is a set of visited items. For the longest run of consecutive numbers without sorting, we put all the numbers into a set and start only from those that have no predecessor; each number is visited at most twice. The sixth is a bijection: to check that two strings have the same structure, we need two tables, one in each direction, otherwise two letters could map to the same one.\n\nAnd two more applications. The rolling hash: to find a substring in a text, we compute the polynomial hash of the pattern and the hash of each window of the text, updating it in constant time as the window shifts; we perform the full check only when the hashes match. This is the Rabin–Karp algorithm. And frequent elements: we count the frequencies in a table and distribute the values into buckets whose number is the frequency; this way we find the most frequent ones without sorting everything. Both applications show the same thing: a hash turns an expensive comparison of large objects into a cheap comparison of numbers, and leaves the honest check for the rare cases of a match.\n\nLet us summarize. A hash table is an array, a hash function, and a way to resolve collisions. Chaining is simple and forgiving; open addressing is faster thanks to the cache, but needs a roomy table and care with deletion; Robin Hood evens out the runs; cuckoo guarantees two accesses per lookup. Growth with rehashing gives an amortized constant. And what can a table not do? It does not keep order, does not search ranges, and does not find the nearest key. For that we need trees, which we will get to soon. In all other cases, use a hash. Twenty exercises are waiting for you: from your own hash function to your own table and problems built on it.
