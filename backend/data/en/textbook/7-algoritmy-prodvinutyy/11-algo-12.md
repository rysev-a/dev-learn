Trees and heaps. Chapter 12. Heap and heapq. Imagine a hospital where patients are seen not in order of arrival but by how serious their condition is. Or an operating system scheduler that needs the most urgent task. Or a shortest-path algorithm that needs the nearest city it has not visited yet. Everywhere we need a structure that can add elements quickly and hand back the most urgent one quickly. That is a priority queue, and the standard implementation of a priority queue is the heap. In this chapter we will look at how a heap is built, at its two main moves, sifting up and sifting down, and we will build a heap in linear time. Then we will go from ten warm-up exercises to your own implementation of the heapq module. Fifteen exercises are waiting for you at the end.\n\nA heap is a binary tree with two properties. The first is the heap property: in a min-heap every node is no larger than its children, so the smallest element always sits at the root. The second is the shape: the tree is complete, meaning every level is full except possibly the last one, and the last level is filled from left to right. Notice that the order in a heap is only partial. A node is smaller than its descendants, but there is no order between siblings or cousins. That is exactly why a heap is cheaper than a sorted array: it maintains the minimum and nothing more. If you need the maximum, use a max-heap, where every node is no smaller than its children; everything else is a mirror image.\n\nThe complete shape gives us the main trick: a heap is stored in a plain array, without a single link. The root sits at position zero, and the levels follow one after another. For the node at index i, the children are at positions two i plus one and two i plus two, and the parent is at position i minus one, integer-divided by two. No pointers, everything is computed with arithmetic. The array is compact, friendly to the processor cache, and needs no separate memory allocation for each node. Remember three formulas: parent, left child, right child. Checking a heap takes one loop: for every index starting from one, the element must not be smaller than its parent.\n\nThe first move is sifting up. To add an element, we put it at the end of the array. The shape of the tree is preserved, but the heap property may break, because the new element could be smaller than its parent. So we swap it with its parent and repeat, until the parent is no larger or until the element reaches the root. Each swap lifts the element one level, and a complete tree has about log of the number of nodes levels. So an insertion costs on the order of a logarithm in the worst case, and on average often less: a random element usually rises only a couple of levels. The heap property is restored along the way, because the path upward stays ordered.\n\nThe second move is sifting down. To extract the minimum we have to remove the root, but a hole at the root breaks the shape. The trick: take the last element of the array, put it in the root's place, and shrink the array. The shape is intact, but now a giant is most likely sitting at the root, and the heap property is broken. We lower it: compare it with both children, swap it with the smaller of them, and repeat until both children are larger or until we reach a leaf. The swap has to be with the smaller child, so that the new parent is no larger than both of its children. The descent costs at most a logarithm of swaps, so extracting the minimum is logarithmic, while peeking at the minimum is constant: you just read element zero.\n\nLet us put the operations together. Pushing an element means appending it and sifting up, which is logarithmic. Popping the minimum means taking the root, putting the last element in its place and sifting down, which is also logarithmic. Peeking at the minimum is constant. In Python all of this lives in the heapq module: heappush pushes, heappop pops, heappushpop does push, then pop in one step, and heapreplace does pop, then push; both are faster than two separate calls. The heap here is an ordinary list, and the module only makes sure it stays a heap. Element zero is the minimum, the rest is not sorted, and printing a heap expecting to see sorted order is a common mistake.\n\nHow do we build a heap from a ready-made array? The first idea is to push the elements one at a time: n insertions, each a logarithm, so n log n in total. But there is a better way, building bottom-up, called heapify. Leaves are already heaps on their own. We walk from the last parent up to the root and sift each node down. Why is that linear time? Half of the nodes are leaves and need no work; a quarter sink at most one level; an eighth sink at most two; and the sum of these contributions converges to something proportional to n. In total, about two n comparisons, not n log n. The heapify function in heapq works exactly this way, in place, in linear time.\n\nThe heap gives us a sort. Heapsort builds a max-heap from the array, then repeats: it swaps the root, which is the largest element, with the last element of the unsorted part, shrinks the heap by one, and sifts the new root down. The largest ends up at the end, the second largest right before it, and so on until the heap is gone. The time is n log n in the worst case, the extra memory is constant, but the sort is not stable, and in practice it is slower than quicksort because of the jumps around memory. On the other hand, it has no quadratic worst case, which is exactly why it serves as the fallback in an introspective hybrid sort.\n\nPython specifics. The heapq module only supports a min-heap. If you need a maximum, you push numbers with a minus sign and flip the sign when you read them. If you need objects with priorities, you push tuples with the priority as the first element. There are two traps here. The first: when priorities are equal, Python compares the next elements of the tuple, and they may not be comparable, like dictionaries or class instances. The second: the order of equal priorities is undefined. Both problems have the same cure: put an increasing counter as the second element of the tuple. Then equal priorities come out in the order they were added, and the comparison never reaches the objects themselves.\n\nThe first pattern is the k largest elements of a stream. Storing everything and sorting costs n log n time and memory for everything. But a heap of size k is enough, and it should be a min-heap: the root is the smallest of the k best. A new element arrives: if it is larger than the root, we replace the root with it and sift down; otherwise we ignore it. At the end the heap holds exactly the k largest. The time is n log k and the memory is k; when k is much smaller than n, that is a huge win. This is exactly how the nlargest and nsmallest functions work, and the problem of the k-th largest element in a stream is the same trick, where the answer sits at the root.\n\nThe second pattern is merging k sorted sequences. We put into the heap the first element of each sequence, together with the sequence number. We pop the minimum, write it to the result, and push the next element from the same sequence. The heap never holds more than k elements, so each step costs log k, and the total is N log k, where N is the total number of elements. This is how sorted files that do not fit in memory are merged, and in Python it is the function heapq.merge. Compare it with two sequences: merging two lists is the same scheme with a heap of two elements.\n\nThe third pattern is the median of a stream. We need a structure that accepts numbers and can give the median at any moment. We take two heaps: the lower half in a max-heap, the upper half in a min-heap. A new number goes into the appropriate half, and then we balance the sizes: they must differ by at most one. The median is the root of the larger heap, or the average of the two roots. Insertion costs a logarithm, the median costs a constant. The same two-heap idea solves the problems of the sliding median and of selecting elements by percentile. See how a simple idea, two roots next to the middle, replaced sorting at every step.\n\nThe heap lives inside graph algorithms, and we will meet it again in the chapter on shortest paths. In Dijkstra's algorithm the heap holds pairs: a distance and a vertex. A heap has no decrease-key operation inside, so when a shorter path is found, a new entry is pushed and the stale one is left in place. When we pop an entry, we check it: if its distance is greater than the one already known, we simply skip it. This is called lazy deletion. The same trick works in event schedulers, where cancelling an event is marked with a flag, and cancelled events are skipped when they are popped. The queue grows, but the simplicity is worth it.\n\nHow does heapq work inside? In CPython the module is written in C, with a fallback written in Python. The way it pops is interesting. Instead of sifting the last element down with two comparisons per level, the module first lowers the empty spot all the way to a leaf, always moving the smaller child up, which is one comparison per level, and then lifts the last element up from the leaf. Since the element taken from the end is usually large and ends up near the leaves anyway, this variant makes fewer comparisons. For expensive comparison functions, like those on strings, that is a noticeable gain. The important point: the result is the same, only the order of swaps inside the array differs.\n\nCommon mistakes. Expecting the whole list to be sorted: only element zero is ordered. Changing an element inside the heap in place and not restoring the property. Forgetting that the heapq module works with the minimum only. Pushing incomparable objects without a counter. Printing the heap and taking the look of the array for the order. Using a heap where you need an ordered structure with middle elements and ranges; for that you need a search tree. It is useful to remember: a list sorted in ascending order is already a heap, but a heap is not a sorted list.\n\nLet us sum up. A heap is a complete binary tree stored in an array, with the property that a parent is no larger than its children. Sifting up gives insertion, sifting down gives extraction, and both cost a logarithm. Building bottom-up takes linear time. From the heap grow heapsort, the k best elements, merging k sequences, the median of a stream, and the priority queues of graph algorithms. Fifteen exercises are ahead of you: ten warm-ups, covering indices, sifting, insertion, extraction, building, sorting, replacement, a max-heap and a stable queue, then your own heapq module and four problems built on its ideas.
