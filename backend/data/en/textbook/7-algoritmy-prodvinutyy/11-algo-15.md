Graphs and strategies. Chapter 15. Graphs: traversals and connectivity. Everything we have studied so far had the shape of a sequence or a tree. But the world of connections is more complicated: people are friends with each other, cities are joined by roads, web pages link to one another, tasks depend on other tasks. For all of this we need a graph, the most general structure of all: a set of vertices and the edges between them. A tree, which we covered in the chapters on trees, is simply a graph without cycles and with one root. Today you will learn to store graphs, to walk them in two fundamentally different ways, and to answer questions about connectivity, the foundation on which shortest paths will stand in the next chapter.\n\nLet us start with storage. An adjacency matrix is an n by n table: the cell at the intersection of a row and a column tells whether there is an edge between the two vertices. Checking an edge is constant time, adding or removing an edge is constant time, but the memory is always quadratic, even when there are few edges. Adjacency lists give each vertex a list of its neighbors: memory is proportional to vertices plus edges, going through the neighbors is instant, but checking one particular edge requires a search in the list. The practical rule: dense graphs, with many edges, live in a matrix; sparse ones, and most real systems are sparse, live in lists. A social network with a million users and a hundred friends each is a list; a matrix would drown in a trillion empty cells.\n\nThe first way of walking is depth-first search: from each vertex we dive into the first unvisited neighbor, then into its neighbor, until we hit a dead end, and then we step back and try the next branch. The implementation is a three-line recursion or an explicit stack: mark the vertex as visited, push the neighbors onto the stack, pop one, and repeat. The visited set is mandatory: without it the search goes around the first cycle forever. One full depth-first search visits each vertex and each edge exactly the right number of times, so the total is linear in the size of the graph. This is our basic operation, and dozens of algorithms grow out of it.\n\nWhat does depth-first search give us? First, connectivity: start the search from a vertex and look at who got visited, and that is one connected component; everything unvisited belongs to other components. The number of components is how many times we had to start a search to cover the whole graph. This answers questions like "are these two people connected at all in a social network", "does the network fall apart into islands", "how many separate clusters are in the data". Second, cycle detection: if during the search we meet an edge to a vertex that is still in the middle of the current dive, we have found a cycle. For a task dependency graph, a cycle means a dead end: the build cannot continue until you break the circular dependency.\n\nHere is a refinement about cycles that saves you on directed graphs: the correct detector uses three colors. White means the vertex is untouched, gray means the dive is happening right now, and black means the vertex and its whole subtree have been explored. An edge into a gray vertex means a cycle: we have come back into our own current path. An edge into a black vertex is harmless, because that branch is finished and there is no loop through it. The naive check, "visited means cycle", gives false alarms on directed graphs: two paths that converge on one vertex do not form a ring. Three colors are the industry standard, and it is worth writing such a detector by hand once, so you never get confused again.\n\nThe third use, the most practical, is topological sorting. If a dependency graph has no cycles, depth-first search can produce an order in which the tasks can be performed: all of a task's dependencies come before it. The intuition: put a task on the answer stack after the search has returned from all of its dependencies, and then when we unload the stack, the dependencies are always in front. This is how people build module compilation orders, package installation plans, database migration sequences, and curricula where courses have prerequisites. If a cycle is found, the system of dependencies is contradictory, and depth-first search honestly detects it, pointing at the ring.\n\nTopological sorting can also be done by a second algorithm, due to Kahn, and it has a different character. Let us count the in-degree of each vertex, that is, the number of its dependencies. Vertices with in-degree zero go into a queue: they can be done right now. We take a vertex out, append it to the answer, and subtract one from the in-degree of everyone who depends on it; anyone whose in-degree has become zero joins the queue. The queue itself keeps the order, and if at the end the answer is shorter than the list of vertices, the remaining ones are sitting in a cycle. Kahn's algorithm is also convenient in production because it works incrementally: a new task with no dependencies appears, and it is immediately ready to run.\n\nThe second way of walking is breadth-first search: we do not dive, we spread out in waves. It uses the queue from the chapter on linked lists: take a vertex, put all of its unvisited neighbors at the tail, and process them in order. The first wave is the immediate neighbors, the second is neighbors of neighbors. And here is the main property: in an unweighted graph, where every edge costs one, breadth-first search finds shortest paths. The number of waves that passed before reaching a vertex is the minimum path length. This is the first shortest-path algorithm in our course, and it returns in the next chapter as a special case of Dijkstra's algorithm with equal weights.\n\nClassic applications of breadth-first search: the minimum number of moves in a game or a maze; the degree of separation between people in a social network, where friends are the first wave and friends of friends the second; checking whether one word can be turned into another by changing one letter at a time through a dictionary of intermediate words. Wherever the edges are all alike and you need the minimum number of steps, breadth-first search is the right answer, with no complications. And there lives the most important trap: if the edges have different weights, breadth-first search lies. The wave arrives sooner along many short roads than along one long road, yet the long one may weigh less. For weights you need Dijkstra's algorithm from the next chapter.\n\nDepth versus breadth is clearest in a maze. Depth-first search follows a wall: it quickly reaches some exit, but its path is winding, with loops. Breadth-first search spreads like water from the entrance: when the water first reaches the exit, the path of the water is the shortest one. The rule for choosing follows easily: if you need any path at all, quickly and with minimal memory, take depth; if you need the shortest, take breadth. Do not forget about memory either: the breadth-first queue holds whole waves and grows large on wide graphs, while the depth-first stack needs only a single line. Sometimes this very argument decides the choice of implementation.\n\nLet us look at breadth-first search as a user, through social connections. The well-known observation about six handshakes, that between any two people the chain of acquaintances is on average no longer than six links, is literally a breadth-first search experiment on the graph of humanity: the waves spread out, and by the sixth wave they cover almost the whole population. The shape of the wave also explains virality: a post was seen by friends, that is the first wave; they shared it further, the second wave; the exponential growth of reach wave by wave is the mechanism that information spreading rests on. Looking at the world through waves saves weeks of inventing things from scratch.\n\nHere is one more beautiful trick of breadth-first search: bipartite coloring. We color vertices with two colors, wave by wave: neighbors get the opposite color. If somewhere two neighbors of the same color meet, the graph is not bipartite, which means it contains a cycle of odd length; if it works out, the graph splits into two groups, and all edges go between the groups. This answers questions like "can we divide the participants into two teams so that rivals end up on different teams", "assign tasks to two workers with conflicts", "is this conflict-free schedule possible with two time slots". One traversal, one array of colors, and a non-trivial answer about the structure of the graph.\n\nPractical subtleties of traversals, which are where implementations fall apart. The first: deep recursion. In a graph of a million vertices, a chain graph will blow the recursion stack, so in production depth-first search is written iteratively with an explicit stack: the same algorithm, with no risk of overflow. The second: mark vertices as visited when you put them in the queue, not when you take them out, otherwise one vertex will land in the queue several times and the queue will balloon. The third: graphs are often large and sparse, and adjacency lists as arrays of lists are more economical than dictionaries of dictionaries. And the fourth: always decide whether the graph is directed or not; a two-way road is two edges, one in the lists of each end.\n\nA special case worth seeing separately is the grid as a graph. A picture made of cells, where land touches land vertically and horizontally, is a graph: the cells are vertices, the touching sides are edges. The number of islands problem is solved by counting connected components: we run over the cells, and each unvisited piece of land starts a depth-first search that marks the whole island. The same trick answers questions about the area of an island, its perimeter, or how many days of melting it takes to break an archipelago into pieces. The moral: graphs hide in the most unexpected data, and as soon as you have spotted the vertices and the adjacency, the traversals you already know do the rest.\n\nFor completeness, let me mention an advanced layer, without details: bridges and articulation points. A bridge is an edge whose removal breaks connectivity; an articulation point is a vertex with the same property. One modified depth-first search finds them all in linear time, and these are questions of reliability: which server is critical for the network, which route to back up, where to put a standby. If your work touches infrastructure, you will study this layer when you need it; for today it is enough to know that such questions are solved by the same depth-first search that you now know everything about.\n\nPractice for today. Imagine friends as a graph: write a depth-first search and count the connected components in a list of acquaintances. Implement breadth-first search and find the minimum number of introductions between two people. Check a small graph for bipartiteness by coloring. And work through the word ladder problem: change one letter in a word to get a word from the dictionary, and find the shortest chain of transformations; this is a classic breadth-first problem that gathers all of today into one task. And the most practical one: count the connected components in a grid of zeros and ones, where ones are land. This is the classic islands problem, in which the grid pretends to be a graph.\n\nLet us sum up. A graph is vertices and edges, stored in a matrix when dense and in lists when sparse. Depth-first search is a dive on a stack: connected components, cycles, topological order. Breadth-first search is waves on a queue: the minimum number of steps in an unweighted graph, levels of separation, bipartite coloring. Both are linear and differ only in the container, a stack or a queue, and the choice of container changes the whole strategy, just as we promised in the chapter on linked lists. In the next chapter we add weights to the edges and get the main question of routing: how to get there at the lowest cost. Dijkstra, Bellman-Ford, the A-star heuristic and spanning trees are already waiting for us.
