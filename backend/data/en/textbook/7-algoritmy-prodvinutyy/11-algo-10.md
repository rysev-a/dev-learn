#CHAPTER 10 | Trees and Traversals
Trees and Heaps. Chapter 10. Trees and Traversals. Everything we have studied so far was linear: arrays, lists, queues, with data going one item after another. But the real world branches: a file system, a company's structure, the markup of a web page, an expression with nested parentheses, an application menu. Data like this needs a branching structure, the tree. In this chapter we will see how a tree is built and how to walk through it; the next three chapters will build the main tools on top of it: search trees, the heap, and red-black trees. At the end, fourteen exercises on trees and traversals are waiting for you.\n\nLet's start with terminology. A tree consists of nodes. The top node is called the root; every node except the root has exactly one parent, and any node can have children. Nodes without children are leaves. Any node together with all its descendants forms a subtree. The depth of a node is the number of edges from the root to it, and the height of a tree is the greatest depth. A binary tree is one where each node has at most two children: a left one and a right one. The key number for a tree is its height: the cost of almost all operations depends on it. A tree with n nodes can be as short as a logarithm if it is bushy, or it can stretch into a chain of height n.\n\nHow do we store a tree? The most natural representation is nodes with links: a node has a value and links to its left and right children, and an empty link means there is no child. If the tree is complete, that is, filled level by level from left to right with no gaps, an array is enough: the root sits at position zero, and the children of the node at position i sit at positions two i plus one and two i plus two. No links at all, everything is computed with index arithmetic; this is how the heap lives, which we will cover in two chapters. For trees with an arbitrary number of children, a node stores a list of its children: this is how a file system and the markup of a page are organized.\n\nA tree is recursive by nature: a subtree is also a tree. That is why most functions on trees are written with a single pattern. The base case: an empty tree gives a simple answer, so height is zero, size is zero, sum is zero. The step: the answer for a node is assembled from the answers for the left and right subtrees and the node itself. Height is one plus the maximum of the children's heights. Size is one plus the sum of the children's sizes. Checking symmetry, mirroring a tree, comparing two trees: the same three lines with different values. Learn to see this pattern: it solves half of the tree problems.\n\nA traversal is a way to list all the nodes exactly once. The three classic depth-first traversals differ in the moment a node is visited relative to its subtrees. Preorder: first the node, then the left subtree, then the right one. Inorder: the left subtree, the node, the right subtree. Postorder: the left, the right, and only then the node. Each has its usual use. Preorder suits copying and saving a tree: the parent comes before its children. Postorder suits deleting and evaluating expressions: first the children, then the parent. Inorder on a search tree lists the values in ascending order, and we will use this connection in the very next chapter.\n\nA recursive traversal is short, but it has a price: the recursion depth equals the height of the tree. On ordinary bushy trees the height is small, but a degenerate tree of a hundred thousand nodes stretches into a chain, and the recursion overflows the call stack. So it is important to be able to write a traversal iteratively, with an explicit stack. For inorder this is a familiar scheme: we go down to the left, pushing nodes onto the stack; when there are no more left children, we pop a node, process it, and move to the right one. Preorder is even simpler: pop a node, process it, push its right child, then its left child, so that the left one comes out first.\n\nBreadth-first traversal goes differently: level by level, first the root, then all its children from left to right, then the grandchildren. It needs a queue: take a node, put its children at the tail. If you process the queue in batches the size of the current level, you get the levels separately, which is handy for problems like show the tree by levels, the right view of a tree, zigzag order, or the width of a tree. With depth we go with a stack, with breadth with a queue: as we promised in chapter two, changing the data structure changes the whole traversal strategy. The time of both traversals is linear, and the memory is linear in the height or the width of the tree.\n\nNow a technique you will meet all the time: a function returns one value, while the answer is accumulated in another. The diameter of a tree is the length of the longest path between any two nodes, and it does not have to go through the root. The idea: for every node, the longest path passing through it as its top point equals the sum of the heights of the left and right subtrees. The function returns the height of the subtree, and along the way it updates a global maximum of those sums. One bottom-up traversal, linear time. The same technique solves problems about the heaviest path, the longest path with equal values, and the maximum path sum.\n\nAnother classic is the lowest common ancestor of two nodes. The recursive solution is elegant: if the current node is empty or equals one of the targets, return it. Otherwise, ask the left and right subtrees. If both returned a non-empty answer, the targets lie on different sides, and the current node is their ancestor. If only one is non-empty, return that one. Notice that the function answers, as a side effect, the question of whether at least one node was found in the subtree. For a search tree there is a simpler way: go down from the root by values until the target values diverge to different sides.\n\nCan we restore a tree from its traversals? One traversal is not enough: different trees give identical lists. But two orders, preorder and inorder, determine a binary tree with distinct values uniquely. The first element of the preorder is the root. Finding it in the inorder, we learn how many nodes are in the left subtree: everything to the left of the root. The rest of the preorder splits into left and right parts of the same lengths, and the subtrees are built recursively. This is both an example of divide and conquer and an explanation of how trees are written to files and sent over the network: serialization.\n\nNot all trees are binary. In a file system a directory can have any number of subdirectories, in the markup of a page any number of nested elements, and in the parse tree of an expression the number of operands depends on the operator. The traversal is the same: the function processes a node and calls itself on each child. A practical tip: if your data arrives as nested structures, dictionaries inside dictionaries, lists inside lists, you are looking at a tree, and a recursive traversal with a type check solves the task. Computing the total size of a directory, finding all files by extension, flattening a nested list: all of these are traversals.\n\nA special breed of trees lives over strings: prefix trees, also known as tries. Each edge is labeled with a character, a path from the root reads a string, and common prefixes share a common path. Inserting and searching for a word costs time proportional to its length, regardless of the number of words in the dictionary. And the main advantage: the question is there any word starting like this is answered by walking down the prefix. This is what autocomplete, spell checking, and network address routing are built on. The price is memory: each node can have many links, and compressed variants are used to save space.\n\nWhy are trees so popular? The height of a tree is the number of steps from the root to a leaf, and for a balanced tree it equals the logarithm of the number of nodes. Search, insertion, and deletion, which follow a single path from the root downward, cost time proportional to the height. So for problems where order matters, such as finding the nearest value, a range, or a minimum, trees and their relatives outperform both arrays and hash tables. Databases keep their indexes on highly branching trees, where a node holds hundreds of keys, and the height in disk reads is three or four hops even on billions of records. Next we will work on the search tree: the ordering rule that turns a tree into a sorted structure.\n\nLet's sum up. A tree is nodes, a root, children, and leaves; the key number is the height. Trees are stored with links, or in an array if they are complete. The recursive pattern, a base case plus combining the children's answers, solves half of the problems. Depth-first traversals, preorder, inorder, and postorder, are done with recursion or a stack, and breadth-first with a queue by levels. The technique of returning one thing and accumulating another gives the diameter and paths, the lowest common ancestor is solved by returning the node that was found, and a tree can be restored from two traversal orders. Fourteen exercises are waiting for you: from iterative traversals to the prefix tree.
