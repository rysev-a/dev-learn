#CHAPTER 2 | Arrays and Strings
Foundations. Chapter 2. Arrays and strings. Almost every program starts with an array: a list of orders, the pixels of an image, the characters of a text, sensor readings. The array is the simplest data structure, and so the most underrated: strings, dynamic lists, stacks, heaps and hash tables are all built on top of it. In this chapter we will see how an array is laid out in memory and where its main property comes from, instant access by index. We will look at what insertion and deletion cost, how a growing list works, and why strings behave differently from what you might expect. We will go through techniques that squeeze the most out of an array: prefix sums, difference arrays, working with matrices. And at the end, twenty exercises are waiting for you.\n\nAn array is a contiguous block of memory in which elements of the same size lie right next to each other. Say the array starts at address one thousand, and each element takes eight bytes. Where does element number five live? Exactly at address one thousand forty: the start plus the index times the element size. One multiplication, one addition, and the answer is ready, no matter how many elements the array holds. That is why reading and writing by index take constant time. This is not a trick of some algorithm; it is a direct consequence of the elements standing in a row and all having the same size. It also explains why numbering starts at zero: an index is an offset from the start, and the first element has offset zero.\n\nAccess by index is fast, but it has boundaries. In an array of ten elements the valid indexes run from zero to nine, and anything outside is an error. In some languages it stops the program at once; in others it quietly reads someone else's memory. The most common trouble with arrays is the off-by-one error: a loop that runs up to the length inclusive instead of exclusive, or a slice that lost its last element. So get used to writing bounds as a half-open interval: the start is included, the end is not. The length of the interval is then simply the difference of the ends, neighboring intervals join without overlaps or gaps, and an empty interval is just one whose start and end are equal. Walking the whole array costs linear time: one step per element.\n\nThe price of contiguity is rigidity. To insert an element in the middle, you must make room for it: every element to the right shifts one position to the right. They have to be moved one at a time, starting from the last, otherwise we would overwrite our own data. That is linear work: the further left the insertion, the more shifts. Deleting from the middle is the mirror image: the right part shifts left and closes the gap. Inserting and deleting at the start is the most expensive case, and at the end the cheapest, because there is nothing to shift. Hence a practical rule. If a program keeps inserting and deleting at the start or in the middle of a large array, that is a signal to use another structure, a queue or a list. If it reads by index and appends at the end, the array is ideal.\n\nAn ordinary array has a fixed size, yet lists in Python, vectors in C plus plus and arrays in JavaScript grow as needed. The secret is simple: a dynamic array stores two numbers, the capacity and the length. As long as the length is less than the capacity, appending just writes into a free cell. When the room runs out, a new block of memory twice as large is allocated, the old elements are copied into it, and work goes on. One such copy is expensive, but it happens rarely: the next one will come only after as many appends as there are elements already stored. So on average, appending costs a constant: over n appends the copies add up to less than two n element moves. This averaged cost is called amortized.\n\nWhy grow twofold and not by ten cells? Suppose we add ten each time. Then a copy happens every ten appends, and each one drags along everything accumulated so far. With a million elements that is a hundred thousand copies, about half a million elements each on average, fifty billion operations. With doubling, the total work is one, two, four, eight and so on up to n, and the sum of such a progression is less than two n. That is why every production dynamic array grows by multiplication, usually by one and a half or two times. The price is spare memory: up to half of the capacity may sit empty. If the number of elements is known in advance, it is better to set the capacity right away: that removes all the copying.\n\nContiguity also brings a hidden gift: friendship with the processor cache. The processor reads memory not by bytes but in chunks of sixty-four bytes, called cache lines. When you touch an array element, its neighbors arrive in the fast cache along with it, and the next few accesses cost almost nothing. Walking through an array in order is the best scenario for the hardware: in practice it is often several times faster than jumping around memory with formally the same complexity. That is why, on real data, a linear scan of a small array often beats clever structures. And when choosing between two algorithms of the same complexity, the one that reads memory sequentially wins. Remember this when we get to linked lists.\n\nNow the techniques. The most basic is a single pass with accumulation: go through the array from left to right, keep in a few variables what you need to know about the part already passed, and update them at every element. This is how you find the maximum and minimum, the second largest element, or the number of elements with a given property. The second largest is a good warm-up. We keep two numbers, the largest and the second. A new element either displaces the largest, in which case the old largest becomes the second, or it competes only for second place. One pass instead of sorting, linear time and constant memory. The idea that the part already passed is described by a few numbers will come back many times: in the sliding window, in dynamic programming.\n\nMany problems require rearranging an array in place, without a second one of the same size. Reversal is done with two indexes: one at the start, one at the end; we swap the elements and move toward the middle. It is linear and uses no extra memory. On top of reversal sits a neat trick, the cyclic shift. To shift an array by k positions to the right, reverse the whole array, then separately the first k elements and separately the rest. Three reversals, and you are done. Check it on an example: one, two, three, four, five shifted right by two turns into four, five, one, two, three. Don't forget to take k modulo the length: shifting by the length puts everything back in place.\n\nA technique that will save you a lot of time is prefix sums. Suppose you need to answer many times the question: what is the sum of the elements from l to r? The naive answer is a loop over the range, linear time per query. Let's prepare once an array in which position i holds the sum of the first i elements. Then the sum from l to r inclusive is the difference of two prepared numbers: the prefix up to r plus one, minus the prefix up to l. Preparation costs linear time, and each query costs a constant. For a thousand queries on an array of a million elements, the difference is a billion operations against a million. The idea generalizes: prefix maximums, prefix products, sums over rectangles in a table.\n\nPrefix sums have a mirror image, the difference array. The task: on an array of a million zeros, run a hundred thousand commands of the form add five to all elements from l to r. Head-on, that is a hundred thousand passes over big chunks. The trick is this: store not the values themselves but the differences between neighbors. Adding to a range changes just two numbers: at position l we add five, and at position r plus one we subtract five. After all the commands, one pass with accumulation turns the differences back into values. Each command costs a constant, and the whole thing takes linear time. This is how people count room occupancy, server load, and overlaps of segments on a line.\n\nA two-dimensional array, or matrix, still lies in memory as one tape, row after row. The element in row i and column j is found by the formula: i times the width, plus j. A practical conclusion follows. Walking by rows goes through memory in order and is friendly to the cache, while walking by columns jumps across the whole width, and on large matrices the difference reaches several times at the same complexity. Typical matrix problems are transposition, where rows become columns; rotation by ninety degrees, which comes down to a transpose and a reversal of the rows; spiral traversal; zeroing rows and columns. In all of them the main thing is careful bounds and traversal order.\n\nStrings are arrays of characters with two catches. The first: in many languages strings are immutable. Any edit creates a new string, so a loop that appends one character at a time actually copies everything accumulated at each step. The result is a quiet square: a hundred thousand characters turn into five billion copies. Python's implementation sometimes hides this, but you can't count on it. The cure is to collect pieces in a list and join them once with the join method or a dedicated string builder. The second catch: a character is not a byte. In Unicode one character takes from one to four bytes, the length in characters and the length in bytes are different numbers, and a string can be cut by byte offset in the middle of a character.\n\nThe same techniques that work for arrays work for the characters of a string. An anagram check is a count of character frequencies: for permutations the counters match, and instead of sorting both strings one linear pass is enough. The common prefix of a set of strings is found by vertical scanning: compare the first characters, then the second, until we meet a mismatch. Remember the takeaway of the chapter. An array is contiguity bought at the price of rigidity: reading by index in constant time, insertion in the middle in linear time, appending at the end in amortized constant time. Prefix and difference arrays turn bulk range queries into constant-time operations. Strings are the same arrays, only immutable. And now on to practice: twenty exercises are waiting.
