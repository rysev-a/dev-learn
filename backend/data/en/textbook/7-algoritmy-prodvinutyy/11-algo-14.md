#CHAPTER 14 | Segment trees and Fenwick trees
Trees and heaps. Chapter 14. Segment trees and Fenwick trees. You are given an array, and you must answer two kinds of operations: change one element, and find the sum over a range. Or the minimum over a range, or the greatest common divisor. There are a million queries, a million elements, and scanning the range every time is out of the question. In this chapter we will look at prefix sums and their weakness, the Fenwick tree, the segment tree with queries and updates, lazy propagation for changes over a range, and the sparse table for data that never changes. At the end, twenty exercises are waiting for you. The main idea: store not the elements themselves, but the answers for well-chosen sub-ranges.\n\nLet us start with what we already know. Prefix sums answer a range-sum question in constant time: the sum from the left boundary to the right boundary is the prefix at the right minus the prefix just before the left. Preparation costs one pass. But if a single element changes, every prefix to its right becomes stale, and in the worst case an update takes linear time. So we have two extremes: a plain array updates in constant time but answers queries in linear time; prefix sums answer queries in constant time but update in linear time. We need a middle ground where both cost a logarithm. That is exactly what the trees in this chapter give us.\n\nThe Fenwick tree, also known as the binary indexed tree, is the shortest of these structures. We number the elements from one, and the cell with number i stores the sum not of one element, but of a range whose length equals the lowest set bit of i. For example, cell twelve, whose lowest bit is four, stores the sum of elements nine through twelve. Cell eight stores the sum of one through eight, and the odd cells store a single element each. Everything lives in a plain array, with no pointers. The lowest set bit of a number is found with the expression x and minus x, and the whole structure rests on this trick.\n\nTo find the prefix sum up to i, we start at cell i, add its value, and move to the cell with the lowest bit removed. For example, for seven we follow the chain seven, six, four: the ranges seven to seven, five to six, and one to four together cover everything from one to seven. Each step removes one set bit from the binary representation, so there are no more steps than there are binary digits, about a logarithm. The sum over an arbitrary range is the difference of two prefix sums: the one at the right boundary and the one just before the left boundary.\n\nThe update goes in the opposite direction. If the element with number i has changed, we must fix every cell whose range contains it. That is cell i, then the cell we get by adding the lowest bit, and so on until we run past the size. For the third element in an array of eight, those are cells three, four and eight. Once again, the number of steps is about a logarithm. The tree can be built in linear time: put the elements into the cells, and add each cell to its parent once. The structure has one restriction: the operation must be invertible, like addition, because a range is obtained by subtracting two prefixes.\n\nThe Fenwick tree generalizes easily. If you need to add a number over a range and ask for the value at a point, store the differences of neighboring elements: adding over a range is two point updates in the differences, and the value at a point is a prefix sum of the differences. If you need both range addition and range sums, you use two Fenwick trees with a clever formula. A two-dimensional tree is a tree inside a tree, and it computes sums over rectangles of a matrix in logarithm squared time. A Fenwick tree takes ten lines to write and runs faster than most alternatives, so wherever it fits, use it.\n\nWhen the operation is not invertible, such as the minimum, or when you need more complex queries, the segment tree takes the stage. It is a binary tree whose root is responsible for the whole array, whose children are responsible for the left and right halves, and so on down to the leaves, which hold the elements themselves. Each node stores the answer for its range: the sum, the minimum, the greatest common divisor, whatever you need. A node is obtained by combining the answers of its two children. For an array of n elements the tree has about two n nodes, and its height is a logarithm. It is stored in an array, like a heap: the children of node number v sit at positions two v and two v plus one.\n\nA range query breaks the range into several ready-made nodes. We descend from the root, and in each node we distinguish three cases. The node's range lies entirely inside the query: we take its answer and go no deeper. It does not intersect the query: we return the neutral value, zero for a sum, infinity for a minimum. It partially intersects: we descend into both children and combine their answers. On each level there are at most two partially overlapping nodes, so in total about four logarithms of nodes are visited. These are exactly the logarithmic queries on an arbitrary range that we were after.\n\nA point update is simpler. We change a leaf and climb to the root, recomputing each parent from its two children: a logarithm of steps. There is also a non-recursive version, short and fast: the leaves lie in the second half of an array of two n elements, the update climbs by dividing the index by two, and the query moves two pointers in from the edges and shifts them toward the root, picking up the nodes it needs. This version runs several times faster than the recursive one and suits almost every operation without lazy updates, which is why it is the one most often written in competitions.\n\nThe segment tree is not tied to the sum. Any associative operation with a neutral element fits: sum, product modulo a number, minimum, maximum, greatest common divisor, string concatenation. Order matters: nodes are combined from left to right, so the operation may even be non-commutative, like matrix multiplication. A node can also store a pair of values, for example a minimum and the number of times it occurs, or a sum and a sum of squares. Any problem of the form "the answer over a range is built from the answers over its halves" is solved by this structure in a logarithm per query.\n\nWhat if you need to change a whole range at once, adding a number to all of its elements, and still answer quickly? Lazy propagation helps. In a node fully covered by the change, we update its answer and postpone the "debt" in a tag: we do not tell the children anything yet. The tag is pushed down only when we descend there, at the next query or update. That keeps range operations logarithmic. For addition and sums, the node's answer grows by the number times the length of the range; for assignment, the tag replaces the value. The main rule of a lazy tree: always push the tag down before descending.\n\nIf the array does not change, there is a faster structure. The sparse table stores the answers for all ranges whose lengths are powers of two: row k holds the minimums over ranges of length two to the power k. It is built in n times logarithm time, each row from the previous one. A minimum query takes constant time: we take two powers of two that together cover the range and may overlap, and we take the smaller of the two values. The overlap is fine because the minimum is idempotent: the minimum of two equal values is the same value. For a sum this does not work, because the overlap would spoil the answer.\n\nLet us sum up. Prefix sums answer quickly but do not tolerate changes. The Fenwick tree gives the sum and a point update in a logarithm and takes a few lines to write, but it requires an invertible operation. The segment tree accepts any associative operation, and with lazy tags it can also change whole ranges. The sparse table answers minimum queries in constant time if the data does not change. The choice is simple: static data and an idempotent operation, the sparse table; sums with updates, Fenwick; everything else, the segment tree. In the exercises you will write all four structures.
