#CHAPTER 1 | Complexity Analysis
Foundations. Chapter 1. Complexity Analysis. Before we learn to invent algorithms, we need to learn how to compare them fairly. Running two solutions on your own laptop and seeing which is faster is not a fair comparison: the result depends on the language, the processor, the compiler version, and whether you got lucky with the input data. We need a measure that describes the solution itself, not the machine it runs on. That measure is complexity analysis, and its main language is big-O notation, which everyone has heard of but few people truly understand. Today we will make this language feel native.\n\nThe idea of big-O is simple: we don't care about the exact running time, we care about how fast the running time grows as the amount of data grows. An algorithm may barely notice a bigger input, or it may slow down dramatically. Imagine looking up a word in a dictionary. The first way is to flip through the pages one by one: if the dictionary has twice as many words, you will flip twice as long on average, so the growth is linear. The second way is to open the dictionary in the middle and keep halving the part you need: if the dictionary gets twice as thick, you need just one extra opening, so the growth is logarithmic. These two behaviors are so different that on a million elements the gap between them is measured in thousands of times, even though on ten words you would not notice it at all.\n\nThe main growth classes are worth learning like an alphabet. Constant: no matter how much data arrives, the work takes the same time, like taking an element by index, getting the length of a string, or adding two numbers. Logarithmic: every step cuts the problem in half or better, like binary search or descending a balanced tree. Linear: one pass over all the data, like finding a maximum or summing numbers. N log n: a linear pass with a logarithm hiding inside each step, which is how all decent general-purpose sorting algorithms work. Quadratic: nested loops where every element is processed against every other element, like comparing all pairs. Beyond that the steps get worse: exponential means that adding a single element multiplies the work, and such algorithms die at just a few dozen elements.\n\nIt is better to feel the difference between the classes once, in numbers, than to hear about it a hundred times. Take a million elements. A logarithm is about twenty operations. Linear is a million. N log n is roughly twenty million. Quadratic is a trillion operations, and on an ordinary processor that means hours, whereas everything before it takes a fraction of a second. Notice that this is not about sloppy code versus optimized code. You can write the quadratic algorithm in the fastest language in the world and the logarithmic one in the slowest, and on big data the logarithm will still win by a colossal margin. The growth class beats the language, beats the hardware, and beats any small tricks, and that is the main power of the analysis.\n\nThe second half of the analysis is memory. Time is not the only currency: RAM is limited too, and an algorithm that processes a billion numbers must say whether it creates a copy of that billion or works in place. Space complexity is described in the same big-O language. Merge sort, which we will meet in the chapter on searching and sorting, spends extra memory on a copy of the array, and that memory is linear. Insertion sort gets by with constant memory, rearranging elements in place. Recursion eats memory too: every nested call takes space on the stack, and the recursion depth is a hidden linear cost that people often forget until the program crashes with a stack overflow.\n\nNext to big-O live two more symbols that are useful to know when you meet them in papers. Omega describes a lower bound: the algorithm cannot run faster than omega promises, no matter how lucky the data is. Theta means the upper and lower bounds match exactly: when we say that merge sort runs in theta of n log n, we promise it is neither faster nor slower, up to constants. In practice most people say big-O while meaning theta, and this is a well-established convention, so don't be alarmed by different letters in different books, because the meaning is almost always the same. And one more thing: big-O predicts the order of growth, not concrete milliseconds, so the real speed of your code is measured with profilers and benchmarks, while complexity analysis is how you choose between solutions before the code is even written.\n\nThe most important point of this first lesson: big-O describes the shape of growth and deliberately throws away constants and small details. We write n log n even though the exact formula is more complicated, because the shape matters more than the details: as data grows, it is the shape that decides the fate of a solution. It is like the difference between far and near versus the exact number of steps to the store: to choose between walking and driving you don't need precision, and the shape of the answer decides everything. First, let's look at the best, average, and worst cases and see that a single algorithm has three such shapes at once.\n\nOne algorithm can have several faces, and telling them apart is a skill of its own. The best case is what happens on the luckiest data. The average case is what happens on typical, random data. The worst case is what happens on the nastiest data, built specially against the algorithm. The classic example is quicksort. On random data it runs in n log n and is considered one of the best, but if the pivot is chosen badly and the data is already sorted, every partition splits the array into a piece of one element and a piece of everything else, the depth becomes linear, and the complexity slides down to quadratic. For linear search the best case is constant: the number you need stands first. The worst case is linear: it is at the end or not there at all.\n\nWhy do reference books and job interviews usually quote the worst case? Because production data is not kind to us. Users, competitors, and life itself sooner or later feed the system exactly the input on which the algorithm does worst: not out of malice, but because over millions of requests a rare failure is statistically inevitable. That is why an engineer guarantees performance by the worst case and treats the average as a pleasant bonus. There is an exception, though: if bad data is physically impossible, or the data is guaranteed to be random, and the average case is radically better than the worst, it is reasonable to design for the average. Quicksort lives exactly like this: its worst case is quadratic, but the probability of hitting it with a random pivot choice is negligible, so in practice it often outruns merge sort with its beautiful guaranteed n log n.\n\nHash tables, every developer's favorite tool, deserve a separate discussion. On average, insertion and lookup take constant time, which is their superpower and the reason we reach for them. But the worst case, when all the keys pile up in one bucket, is linear in the number of elements. We will look at why this happens in detail in the chapter on hash tables, but for now fix the structure of the thought: an averaged constant with a rare linear failure is a fair deal if you will never run into the failure, and a dangerous one if your keys guarantee it. The ability to tell the two apart is what separates an engineer from someone who memorized the phrase, a dictionary works in O of one. You will come back to this pair of phrases, on average and in the worst case, throughout your career.\n\nNow let's combine time and memory, because the two are constantly traded against each other. Often you can speed an algorithm up by spending extra memory, and the other way around. Want to find a pair of numbers with a given sum in an array? The naive solution is to try all pairs: quadratic time with constant memory. A better one is to sort the array and walk inward with two pointers from the ends: n log n time because of the sort, and memory is still constant. And you can also build a hash table of all the elements and look for the complement on the fly: linear time, but now linear memory. All three solutions are correct, they simply lie on a trade-off curve: each step up in speed is bought with memory. In production this deal is made every hour, with caches, indexes, and materialized views, all of them buying speed with memory, and the sooner you learn to see this in terms of complexity, the cheaper each deal will be.\n\nAnd a small honest caveat about constants. Big-O discards them, but in reality an algorithm with a small constant and quadratic growth can beat an algorithm with a big constant and n log n growth on small data, which is exactly why library sorts switch to simple methods on small pieces. Complexity analysis answers the question of what will happen on big data, not which is faster on your ten elements. Both questions are legitimate, you just must not mix up which one each measure answers. And the last idea of today's topic is amortized analysis: an operation can cost a constant even though it sometimes takes linear time. How that is possible, we will work out right now.\n\nLet's look at the trickiest question of today's topic. A dynamic array is a structure you can keep appending elements to, and it grows by itself. How does it grow? When its internal memory runs out, the array allocates a new block one and a half to two times bigger and copies all the contents there. Copying is linear work. Does that mean that appending to the end is a linear operation? No, and here is why. For the copying to happen, say, twenty times with doubling, you need to append about a million elements, and the total work of all the copies will be on the order of two million, so on average each append accounts for a constant number of copied elements. A rare expensive operation spread over many cheap ones costs a constant on average, and that is what amortized analysis means.\n\nThe same logic lives far beyond arrays. A hash table, as it grows, moves into a new, bigger one and repacks all the elements, which is rare linear work amortized down to a constant per operation. Garbage collectors stop the world and sweep through memory, rarely, but between the stops everything flies. Database schedulers from time to time rebuild statistics and compact storage. Everywhere you see the same pattern: you must not be scared of a rare linear operation, and you must not praise a system for its average without understanding what paid for that average. Amortized analysis is a way to price such a system honestly: we divide the total work by the number of operations and get a fair cost for each one.\n\nNow the typical mistakes that trip up even experienced people. The first is hidden complexity inside ready-made tools. A string that you append to piece by piece in a loop, in languages with immutable strings, creates a new string on every step, which is quadratic where it looks linear. Checking whether an element is contained in a list is a linear search, and inside a loop it gives you quadratic; in a hash set it would be constant. A slice, a copy, or a sort inside a loop are all multipliers that are invisible in pretty code. The second mistake is counting only time. Recursion without remembering already computed branches, or copies of large structures at every step, is a memory problem, and it brings down a service just as well as a slow loop. The third is ignoring the shape of the data: an n log n algorithm can lose to a quadratic one on three elements, and context decides.\n\nHow do you use all of this in everyday work, when nobody asks you to compute big-O on a whiteboard? Habit number one: for every loop, ask what is inside it. A loop over data with a linear search or a sort inside is n log n or worse, and the question immediately becomes practical: how many elements do we have? Habit number two: know your volumes. Ten elements forgive a quadratic, a million do not, and the difference between fine and a service outage almost always comes down to the question of how much data we have now and how much we will have in a year. Habit number three: when something is mysteriously slow, first count the nesting, because nine times out of ten the bottleneck turns out to be an accidental quadratic.\n\nLet's sum up. Big-O is the language of the shape of growth, not a stopwatch: the classes from constant through logarithmic and linear to n log n, quadratic, and exponential should be known like the multiplication table, and you should feel their difference in numbers. An algorithm has best, average, and worst cases, and it is wise to design for the worst if the data is unfriendly. Time is traded for memory at a fair rate, and every cache in your system is the same kind of deal. Rare expensive operations are counted in the amortized way, and that applies equally to your arrays, hash tables, and garbage collectors. In the next lesson we will come down from the heights of analysis to the ground and see how arrays, strings, and linked lists are built, the bricks from which everything else is made.
