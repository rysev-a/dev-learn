Strings and numbers. Chapter 8. String algorithms. Text is the most common form of data: logs, source code, emails, genomes, addresses and search queries. And almost always we need to do one of three things with it: find a pattern in it, tell how similar two strings are, or quickly answer which words start with a given prefix. In this chapter we will cover the prefix function and the Knuth–Morris–Pratt search, the Z-function, string hashing and the Rabin–Karp algorithm, the prefix tree, and the Levenshtein distance. At the end you will find twenty exercises. All of these methods share one idea: do not re-read what has already been read.\n\nLet us start with the obvious solution. To find a pattern of length m in a text of length n, we place the pattern at every position of the text and compare characters from left to right; at the first mismatch we shift the pattern by one position. On ordinary text this works fast, because a mismatch usually happens almost immediately. But take a text of a thousand letters a with a letter b at the end, and a pattern of five hundred letters a with the same b: at every position we will honestly compare almost the whole pattern and stumble only on the last letter. That comes out to about n times m operations. The trouble is that at every shift we forget everything we have just learned about the text.\n\nThe prefix function helps us remember what we have learned. For a string, its value at position i is the length of the longest proper prefix of the substring up to i inclusive that is also a suffix of it. Proper means not equal to the whole substring. Take the string a-b-a-c-a-b-a. At the first position the value is zero, and at the second, for a-b, it is also zero. At the third, for a-b-a, it is one: a is both at the start and at the end. Then come zero, one, two and three: at the end, a-b-a both opens and closes the whole string. These numbers tell us how far we can shift the pattern after a mismatch without losing a single possible match.\n\nThe prefix function is computed in a single pass. Suppose we know the value for the previous position; call it k. If the next character matches the character at place k, the value grows by one. If not, we do not start over: we take the prefix function value at position k minus one, which is the next longest prefix that is also a suffix, and try again. So k jumps down the chain until it matches or reaches zero. The jumps may seem numerous, but each step to the right increases k by at most one, while jumps only decrease it. So the total number of jumps is at most the length of the string, and the time is linear.\n\nNow the search itself. We glue together the pattern, a special separator that is not in the alphabet, and the text, and compute the prefix function of the glued string. If the value at some position equals the length of the pattern, the pattern ends exactly here. The separator keeps the values from growing beyond the length of the pattern. The same algorithm can be written without gluing: walk along the text, keep the length of the current match, and on a mismatch roll it back using the pattern's table. The pointer in the text never moves backwards, so the whole search costs about n plus m. This is the Knuth–Morris–Pratt algorithm, and in the worst case it is no worse than in the best.\n\nThe prefix function can do more than search. Subtract its last value from the length of the string, and you get the length of the smallest period: a piece whose repetition builds the whole string, if the string is divisible by it. For the string a-b-c-a-b-c-a-b-c the last value is six, the length is nine, and the period is three. If it does not divide evenly, the repetition is incomplete, and the string can be completed. This is how we find the smallest compression of a string, check that one string is a cyclic shift of another, and count how many times each prefix occurs inside the string. One linear table replaces a set of separate checks, and that is a good sign of a good idea.\n\nThe second tool is the Z-function. For position i it equals the length of the longest common beginning of the string and its suffix that starts at i. Computing it straight from the definition would take quadratic time, but there is a trick: we remember the Z-block, the rightmost segment that matched the beginning of the string. If a new position lies inside the block, its value can be peeked from the mirror position at the beginning of the string, and then we only check what lies beyond the right boundary. The block moves only to the right, so everything is computed in linear time. For searching, the pattern is glued to the text through a separator, just as in the previous method.\n\nWhich tool should you choose? The prefix function and the Z-function carry the same information in different forms, and one can be converted into the other in linear time. The prefix function is handy when you need borders and periods: it answers the question of what the string has both at the start and at the end. The Z-function is handier when you need to compare every suffix with the beginning: how many characters match if the string is shifted. When solving a problem, start with whatever is formulated more naturally. If you see the words period, border, or prefix equals suffix, take the prefix function. If you see common beginning from a position, take the Z-function.\n\nThere is also a completely different approach: compare not strings but numbers. A polynomial hash turns a string into a number like this: each character is multiplied by a power of some base, and everything is summed modulo a large prime. If you precompute the hashes of all prefixes, the hash of any substring comes from two values and a power of the base in constant time. Comparing two substrings of any length also takes constant time. But equal hashes do not prove that the strings are equal: collisions are possible. The probability is small with a large modulus and a random base. To lower it even further, people use two moduli. Or, after the hashes match, they compare the strings themselves.\n\nThe Rabin–Karp algorithm is built on hashes. We compute the hash of the pattern and the hash of a text window of the same length. The window shifts by one position, and its hash is updated in constant time: subtract the contribution of the character that left, multiply by the base, and add the contribution of the new one. When the hashes are equal, we compare the strings directly. On average the time is linear; in the worst case, because of collisions, it can become quadratic. But the method generalizes easily: you can search for many patterns of the same length at once by putting their hashes into a set, and search for a two-dimensional pattern in an image. And repeated substrings are found by combining hashes with binary search on the length.\n\nNow a problem of a different kind. There is a dictionary, and we need to answer quickly whether a word is in it, and above all which words start with a given prefix. A hash table will not help here: it cannot search by prefix. What we need is a prefix tree, also called a trie. Edges labeled with letters come out of the root, and the path from the root to a marked node is a word. The common beginning of words is stored once. Insertion and lookup take as many steps as there are letters in the word, regardless of the size of the dictionary. To get all words with a prefix, we descend along its letters and traverse the subtree. This is the basis for autocomplete, spell checking and routing of network addresses.\n\nThe last tool answers the question of how similar two strings are. The Levenshtein distance is the minimum number of insertions, deletions and substitutions of a character that turn one string into another. It is computed with dynamic programming: a table cell holds the distance between the first i letters of one string and the first j letters of the other. If the last letters are equal, we take the value on the diagonal. If not, we take the minimum of three neighbors, the left one, the upper one and the diagonal one, and add one. The table is filled in about n times m steps, and it is enough to store two rows. It is used to find typos, compare versions of files and align sequences in a genome.\n\nLet us sum up. All fast methods of working with strings are built the same way: do not re-read what has already been read. The prefix function and the Z-function keep in a table how the string matches itself, and give linear-time search and periods. Hashes turn the comparison of substrings into the comparison of numbers at the price of a small probability of collision. The trie answers questions about prefixes, and the Levenshtein distance answers questions about similarity. Before writing a loop inside a loop, ask yourself: what information am I throwing away that could be remembered? You will find all of these techniques in the exercises.
