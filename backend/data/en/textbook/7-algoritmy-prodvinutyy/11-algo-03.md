Foundations. Chapter 3. Linked lists. In the previous chapter we saw the price of contiguity: an array instantly answers the question what is at index five, but inserting into the middle forces you to shift half the array. The linked list answers this price in mirror image. Its elements don't stand side by side; they are scattered around memory and hold on to each other with references. All the properties of a list follow from this picture: cheap rearrangement, expensive lookup by index, and a special discipline when working with references. In this chapter we will go through singly and doubly linked lists, fast and slow pointers, merging and sorting, a circular queue on an array, and a queue made of two stacks. At the end, twenty exercises are waiting for you.\n\nA list node is a small record with two parts: a value and a reference to the next node. The last node's reference is empty. The whole list is defined by a single reference to the first node, called the head: lose the head and you lose the entire list. To traverse a list, we take the current node, process its value, and follow the reference to the next one until we run into emptiness. A traversal costs linear time. But the element at index five hundred can't be taken directly: its address is written nowhere, and you have to honestly walk through four hundred ninety-nine references. So access by index in a list takes linear time, where an array takes a constant.\n\nNow for what a list exists for: insertion and deletion, once you are already standing at the right node. To insert a new node after node B, you need to reassign two references: first the new node must point to whatever B was pointing to, and only then does B point to the new node. The order is critical. If you do it the other way round, B already points to the newcomer, and nobody remembers the old tail of the list anymore: the whole right part is lost forever. A rule for life: before you change a reference, save what it was pointing to. Insertion and deletion are two or three operations, with no shifting and no copying: constant time, however many nodes the list has.\n\nLists are notorious for tricky special cases. Deleting a node from the middle is easy: switch the previous node's reference to the next one. But what if the head itself is being deleted? The head has no previous node, and the code has to branch on a separate condition. The same goes for inserting into an empty list and for deleting the only node. An elegant cure is the sentinel node: a fake dummy node that always stands in front of the real head. Now every real node has a previous one, there are no special cases, and the real head is simply the node after the sentinel. An extra node costs next to nothing, yet removes a whole class of bugs. Make it a habit: if your list code starts growing conditions about the head, put in a sentinel.\n\nThe first classic problem is reversing a list. You need three variables: the previous node, the current one, and the next one. At each step we remember the next node so as not to lose the rest of the list, turn the current node's reference back to the previous one, and then move all three variables one step forward. When the current node reaches emptiness, the previous one is the new head. One pass, linear time and constant memory: not a single new node is created, only references are switched. If you can draw these three arrows on paper for a list of three nodes, you understand how to work with lists: the other problems are variations on the same theme.\n\nThe second classic idea is fast and slow pointers. Let two pointers walk along the list at the same time: the slow one makes one step, the fast one two. When the fast one reaches the end, the slow one is exactly in the middle of the list. In one pass, without counting the length. The same technique solves the cycle problem. If the end of the list is closed back onto one of the earlier nodes, the fast pointer never reaches emptiness and just runs in circles. Inside the circle the fast pointer gains one step per tick on the slow one, so sooner or later they will be in the same node. This is Floyd's algorithm, known as the tortoise and the hare: the cycle is found in linear time and constant memory.\n\nFinding out whether there is a cycle is not enough; often you need to know where it begins. A beautiful observation works here. Say it takes d steps to reach the start of the cycle. When the pointers meet, the slow one has walked d plus part of a circle, and the fast one twice as much, and the difference is a whole number of circles. It follows that from the meeting point to the start of the cycle there are exactly as many steps as from the head to the start of the cycle. So we act like this: after the meeting, we put one pointer back at the head and move both one step at a time. They will meet exactly at the start of the cycle. The alternative is to remember visited nodes in a set, but that is linear memory, and here it isn't needed.\n\nLists are surprisingly good at merging. Given two sorted lists, we need to build one. We create a sentinel node and a tail of the result. At each step we compare the heads of the two lists, attach the smaller one to the result, and advance its list. When one list runs out, we attach the remaining tail of the other in one move. Not a single new node, linear time. List sorting is built on merging: split in half with the fast and slow pointers, sort the halves recursively, and merge. That gives n log n with constant extra memory, not counting the recursion stack. For an array, merge sort needs an auxiliary buffer; for a list, it doesn't.\n\nA doubly linked list stores two references in each node: to the next one and to the previous one. For the extra reference we get two possibilities. First, we can walk in both directions. Second, we can delete a node knowing only the node itself: the previous and next nodes are known from the node, so there is no need to search for the previous one. Deletion becomes two operations: the neighbors on the left and on the right declare each other their closest neighbors. The price is twice as much reference work on insertion and deletion, and more space per node. A typical mistake is to update the references in one direction and forget the other, so that forward and backward traversals show different data.\n\nA doubly linked list with two sentinels, one at the start and one at the end, is an ideal basis for a queue and a deque. Adding and removing at either end is now constant and needs no special cases: even in an empty list, the two sentinels simply look at each other. This is how queues are built in many libraries, and the double-ended queue in Python is built on a similar idea out of blocks. The same basis is used for a cache that evicts the least recently used entries: a recently used element is moved to the front in one move. We will carry this idea through in the chapter on hash tables, where the list is joined with a dictionary to give a cache with constant-time operations.\n\nA queue can also be built on an array, and then it is called circular, or a ring buffer. We create an array of fixed length and two indexes: head and tail. A new element is written at the tail position, after which the tail moves forward; removing reads the head position and moves the head. Reaching the end of the array, the index doesn't go out of bounds but returns to the start: we take the remainder of division by the length. This way the occupied region travels around the circle, while memory is neither copied nor grown. One catch remains: an empty queue and a full one can't be told apart by the indexes alone, because in both cases the head equals the tail. The way out is to keep a separate counter of occupied slots.\n\nNow for how a stack and a queue are built out of each other. A stack lives easily on any list: push and pop at the head. A queue on a singly linked list needs a pointer to the tail, otherwise appending at the end costs linear time. But here is an elegant problem: make a queue out of two stacks. New elements go onto the first stack, and we remove from the second. When the second one is empty, we pour the whole first one into it: the order gets reversed, and we start removing from the oldest. Each element is poured at most once, so removal costs an amortized constant. This is the same technique from the chapter on complexity, where a rare expensive operation is paid for by many cheap ones.\n\nNow for honesty. Theory promises lists an advantage in the middle: insertion in constant time against a linear shift. In practice, arrays often win there too. To insert into the middle of a list, you first have to get there, and that is linear time with all the jumping around memory. The nodes lie wherever they happened to land, each hop is a likely cache miss, and on top of that every node needs a separate memory allocation and extra bytes for the reference. An array in the same time will shift data with a fast machine operation over a solid block. That is why lists live in specialized roles: queues and deques, caches, the insides of schedulers and allocators, the immutable structures of functional languages.\n\nLet's sum up the chapter and name three sources of bugs. The first is losing a reference: save what you are about to redirect a pointer to before you redirect it. The second is special cases: an empty list, one element, the head and the tail; use a sentinel and check these cases explicitly with tests. The third is cycles: any traversal not protected against them will hang on a corrupted list. Draw nodes with arrows on paper until your hand gets used to it. The techniques of the chapter are reversal, fast and slow pointers, merging, the sentinel node, the ring buffer, and the queue of two stacks. Twenty exercises are waiting for you, from the length of a list to a queue with a minimum in constant time.
