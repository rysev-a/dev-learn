Foundations. Chapter 4. Searching and Sorting. Of all the problems in computer science, two are so fundamental that they show up everywhere: finding what you need in a pile of data, and putting that data in order so that finding things becomes easy. Today's lesson is about exactly these two. Let's start with searching. Linear search is about as simple as it gets: walk through the elements and compare each one; it takes linear time and needs no preparation of the data. For unordered data it is the only option. If the elements lie in no particular order, the only way to learn that the one you want isn't there is to look at all of them. But as soon as the data is ordered, a trick opens up that changes everything, and today we'll take it apart down to the last screw.\n\nWe've already met binary search in the conversation about the dictionary: you open the book in the middle, compare the word with the one you're looking for, and in a single move throw away half of the book. Then you repeat with the half that's left. Formally it goes like this: keep two boundaries, a left one and a right one, and look at the element in the middle. If it's smaller than the target, move the left boundary past the middle; if it's larger, move the right boundary to just before the middle; if it's equal, you've found it. Every step cuts the range in half, so the number of steps is a logarithm: about twenty comparisons for a million elements, about thirty for a billion. It is this speed that made binary search one of the most widely used algorithms in history.\n\nBinary search has two hard requirements. The first: the data must be sorted. The trick relies on being able to throw half away, and you can only throw half away when you know the order. The second: access to any element by its position must take constant time, as in an array. On a linked list binary search doesn't work: to reach the middle you have to walk through the whole first half, and all the savings evaporate. Remember this pairing, sorted order plus constant-time access, because it is also the foundation of database indexes, which we will meet again in this course and throughout our whole professional lives.\n\nEveryone can write binary search, but almost nobody writes it without bugs on the first try. The main source of bugs is the boundaries: off-by-one shifts, endless loops, a skipped element. The discipline goes like this. Decide in advance what the left and right boundaries mean, inclusive or not. Write the loop condition to match that decision. Move the boundaries carefully past the middle, without touching an element you've already checked. And always test your solution on arrays of zero, one and two elements, because that is where every bug lives. In languages with fixed-width integers, the middle is computed more cleverly, by adding half of the difference rather than the sum of the boundaries, so that it doesn't overflow on huge arrays.\n\nThe next step is searching for boundaries. Finding the value itself is only the tip of the iceberg. In real problems you more often need the first element that is greater than or equal to a given value, or the last one that is smaller, because equal elements may not exist at all. In libraries these functions are called the lower bound and the upper bound. The idea behind the modification is simple: when you find an equal element, don't stop, but keep shrinking the range in the right direction until the boundaries meet at the first suitable element. The loop stays logarithmic, while its usefulness soars: the lower bound answers the questions where should I insert a new value to keep the order, and how many elements are smaller than a given one, in one line and a single logarithmic pass.\n\nAnd now a real superpower, the thing that separates a confident algorithmist from someone who has merely read about it: binary search on the answer. You can apply it not only to an array, but to the space of possible answers itself. The classic example: we have logs and a sawmill, each cut takes time proportional to the length, and we need to cut a given number of logs into pieces of equal length, making that length as large as possible. Trying every length is hopeless, there are far too many. But look: if a length works, then any shorter length works too. The answer is monotonic. So we can use binary search to walk through the range of lengths: for a candidate, one linear pass tells us whether we get enough pieces, and then we narrow the range. The number of iterations is a logarithm, each check is linear, and the total is n log n instead of brute force. This pattern solves a whole class of problems that look like brute-force monsters.\n\nOn to sorting, the topic that an entire generation of algorithmists grew up on. Let's start with three elementary sorts. All of them are quadratic, but each has its own character. Bubble sort: pass through the array and swap neighboring pairs that are out of order; the maximum floats to the end in each pass, like an air bubble. Selection sort: find the minimum in the unsorted part and put it in the first place of that part. It's quadratic, but it makes the fewest swaps, which matters when moving elements is expensive. Insertion sort: it's like arranging cards in your hand, you take the next element and slide it to the left until it sits in the right place among the already ordered ones. It's quadratic on average, but here's the secret: on almost sorted data insertion sort runs in nearly linear time, because each element moves only one or two positions. Remember this, because in two paragraphs this feature will become the basis of the fastest library sorts.\n\nBefore we move on to the fast sorts, let's introduce a concept that comes up in every interview: stability. A sort is stable if equal elements keep their original order. It sounds like a minor detail until you meet a real scenario: we have a list of orders sorted by date, and we sort it by city. A stable sort keeps the chronology within each city; an unstable one shuffles it however it likes. Bubble sort and insertion sort are stable, selection sort is not. In the documentation of library sorts, stability is always stated explicitly, and you should choose it deliberately rather than hope for luck.\n\nQuicksort is the queen of practical sorts. The idea: pick a pivot element, split the array in a single linear pass into the elements smaller than the pivot and the larger ones, put the pivot in its final place, and then repeat the same for both parts. The depth of this recursion is on average logarithmic, so the result is n log n, memory use is constant, and everything happens in place. In practice quicksort outruns its competitors because each pass goes through the array sequentially and plays nicely with the processor cache, the same reason we discussed in the chapter on arrays.\n\nThe queen has a dark side. If the pivot is chosen badly, for example always the first element of an already sorted array, each part splits into one lonely element and everything else, the recursion depth becomes linear, and the complexity becomes quadratic, the one we studied in the first chapter. There are three remedies. Choose the pivot at random, and then bad data can hardly hurt you. Take the median of three: the first, the middle and the last element. And finally, the introspective approach: watch the recursion depth, and if it grows suspiciously, switch to a sort that has no bad inputs at all, which we'll cover in a couple of paragraphs. All decent libraries do exactly this.\n\nMerge sort is the opposite in character: bad data simply doesn't exist for it. We split the array in half, sort the halves recursively, and then merge the two sorted pieces into one. Merging is a linear pass with two pointers: compare the heads of the pieces and take the smaller one. The recursion depth is a logarithm, so we get a guaranteed n log n on any data, plus stability, because equal elements come from the left part first and the order is preserved. The price is linear extra memory for the merge, the very thing we recalled in the first chapter when we talked about trading time for memory.\n\nMerging as a technique is more valuable than merge sort itself. Being able to merge two sorted lists in linear time is needed in dozens of places: combining the logs of two services by timestamp, intersecting two sorted lists of subscribers, merging the results of two indexes. And if we scale the idea up, we get external sorting: the data doesn't fit in memory, so we sort it in chunks that do fit, write them to disk, and merge them into ever larger sorted runs. That's how data was sorted on tapes half a century ago, and that's how big storage systems work today. The principle hasn't changed one bit.\n\nHeapsort relies on a structure that deserves some love of its own: the heap. A heap is a tree, usually hidden inside an array, where every parent is no smaller than its children, so the maximum always sits at the top. A heap is built from an array in linear time, and then we repeatedly take off the top and restore the order in logarithmic time. The total is n log n, in place, with no extra memory. In practice heapsort is slower than quicksort because of the jumps around memory, but it has no bad inputs at all: the worst case equals the average. And the heap itself lives a separate life: it's the inside of a priority queue, of schedulers, and the best answer to the problem of returning the n largest items from a stream that never ends.\n\nWhat do the standard sorting libraries really use? Hybrids. The famous Timsort looks for runs in the data that are already sorted, sorts only small unordered pieces with insertion sort, and merges the runs with each other. On real data, which is almost always partially ordered, it runs in nearly linear time. Another hybrid is introsort, the introspective sort: quicksort by default, heapsort when it suspects the worst case, and insertion sort on small pieces. The moral of today's lesson is simple: there is no best sort in general, there is the sort that fits your data, whether it's almost sorted, random, huge, or streaming.\n\nToday's practice. Implement binary search with a lower bound and test it on arrays with duplicates. Write insertion sort and measure it on almost sorted data; the result will surprise you. Sort a list of objects by two fields by applying a stable sort twice: first by the second field, then by the first. And solve one problem with binary search on the answer, the sawmill or something similar, so that the pattern settles in your head.\n\nLet's sum up. Linear search is for unordered data, binary search is for sorted data, and boundaries are more useful than an exact hit. Binary search on the answer turns monstrous brute force into a logarithm with a linear check. Among the sorts, insertion sort rules on almost ordered data and small pieces, quicksort rules in practice, merge sort wins where you need guarantees and stability, and heapsort wins where you need the worst case under control and streams. Stability is a tool, not a detail, and it should be used deliberately. In the next chapter we'll look at a structure that at first glance makes all of this unnecessary: hash tables, which find data without any sorting, in constant time.
