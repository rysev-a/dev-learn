#CHAPTER 40 | Files, Processes, and Sockets
Learning Rust. Chapter 40. Files, processes, and sockets. In the operating systems course we talked a lot about how files, processes, and network connections are the basic objects a program uses to talk to the world. Rust expresses them as standard library types, and those types show clearly the ideas you know from Linux: descriptors, permissions, exit codes, input and output streams, addresses, and ports. Today we work with the file system, read and write with streams, take paths apart, handle errors by their kind, launch external programs, connect them with pipelines, and finally write network code on sockets: an echo server, a simple key-value protocol, and datagrams. All of it uses only the standard library.\n\nLet's start with files. The file system module offers short functions for every occasion: write text to a file, read it whole, create a directory together with all its parents, find out the size, and delete. Each of them returns a Result with an I/O error, and the question mark keeps the code linear. The main function can return such a Result too. For temporary data you use the directory returned by the temp dir function, and you give files unique names, for example by process number. These functions are thin wrappers over the system calls we discussed in the course: open, read, write, close.\n\nFor working with streams there are two traits: Read can read bytes, and Write can write them. They are implemented by files, network connections, standard input and output, and also by in-memory buffers: a cursor over a string works like a file, which is handy for tests. A buffered reader collects data in large chunks and gives you a line-by-line iterator, while a buffered writer accumulates writes and sends them less often. We already discussed that a system call is expensive, and a buffer reduces their number. Don't forget to flush the buffer or let it be dropped, otherwise the last bit of data will be lost. The take method limits a reader to a given number of bytes.\n\nPaths in Rust are separate types, not strings. The borrowed Path and the owning PathBuf work like str and String: the first is a slice, the second is a growable string. From a path you can get the file name, the extension, the file stem without the extension, the parent, and a list of components. The join method glues on a component, while push adds one in place, and the method that replaces the extension changes only that. All of this follows the rules of the platform, for example the separators. A path doesn't have to be valid text, so for printing you use the display method rather than a direct conversion to a string.\n\nWalking a directory is built on the function that reads a directory and returns an iterator of entries. The order of entries depends on the file system, so for reproducibility you collect them into a vector and sort by name. From an entry you take the name, the path, and the file type: a regular file, a directory, or a link. A recursive walk is a function that prints an entry and, for directories, calls itself with a bigger indent. You will recognize the work of the ls and find utilities. Keep links in mind: if you allow following symbolic links, the walk can loop forever, so check the type of the entry itself, not the target of the link.\n\nI/O errors carry a kind, available through the kind method. The kind not found says the file doesn't exist, permission denied says you lack the rights, and there are also already exists, interrupted, connection reset, and dozens of others. A good program matches on the kind and prints a clear message instead of a raw system error number. For unexpected kinds, the fallback branch prints the description itself. This turns the same situations you see on the command line, a missing file or missing permissions, into tidy match branches that you can cover with tests.\n\nA process is tied to its environment. Environment variables are read by the var function, which returns a Result, because the variable may not exist. Command-line arguments come from the args iterator, where element zero is the name of the program itself. You can end a process with a given code using the exit function, and returning from the main function without an error gives code zero. The convention is the same as in the shell: zero is success, anything else is an error. Programs that end up in pipelines and scripts must follow it, because conditional commands and checks in automation depend on it.\n\nLaunching external programs is done with the Command struct. We name the program, add arguments, and call output: the process starts, we wait for it to finish, and we get the standard output, the error stream, and the status. The success method of the status tells whether the code was zero, and the code method returns the number if the process was not killed by a signal. If the program doesn't exist, the launch error has the kind not found, just like in the shell. The output streams are not mixed: error messages come separately from the result. Arguments are passed as a list, not as a string for the shell, so you cannot inject a command through a space or a quote.\n\nProcesses can be connected with pipes. To do that, we configure the process streams as piped, start it with the spawn method, and get a handle that has standard input and output. We write a few lines into the input of the sort program, close the input so it learns there is no more data, and wait for the result. Closing the input is important: without it the program will wait forever for more, and we get a deadlock. This is how shell pipelines work, only now we control them from a program, and we can add error handling at every link of the chain.\n\nOn to the network. A listening socket is created by binding to an address and a port; port zero means any free port, and you can ask the socket for the real number. The accept method blocks until a client connects and returns the connection. The client connects to the server's address. To make the example work in a single program, the server is started in a separate thread. The connection reads and writes like a file and implements both Read and Write. The simplest server reads the incoming bytes and sends them back in upper case, and the client reads the reply until the connection closes.\n\nReal protocols are built on top of a byte stream. A stream connection doesn't preserve message boundaries, so the protocol needs rules for splitting: for example, one command per line. A buffered reader over the connection yields lines, and the reply is written with the writeln macro. To read and write at the same time, the connection is cloned with the try clone method. This is how we implement a tiny store: set and get commands and an error message. When the client closes the connection, the line iterator on the server ends and the handler finishes on its own: it's the same end-of-stream trick as with channels.\n\nBesides stream sockets, there are datagram sockets. The UDP protocol doesn't establish a connection; each send is a separate packet that may be lost or arrive out of order. The socket binds to a port and calls send to with the receiver's address, and it receives with the recv from call, which also returns the sender's address. Any wait can be bounded: the method that sets a read timeout turns an endless block into an error once the time runs out. Timeouts on network calls are not a luxury but a hard requirement: without them a hung neighbor freezes your program forever.\n\nLet's sum up. File system functions return a Result, and error kinds let you tell a missing file from missing permissions. The Read and Write traits unify files, connections, and buffers, and buffering reduces the number of system calls. Paths are separate types with parsing methods. Processes are launched with the Command struct, receive arguments as a list, and are connected with pipes, while exit codes follow the shell convention. Sockets work like files, but on top of them a protocol needs its own message boundaries, and every wait must have a timeout. In the next chapter we will build on this foundation the first part of a web server: parsing requests of the HTTP protocol.
