#CHAPTER 16 | Borrowing: references and the borrow checker
Learning Rust. Chapter 16. Borrowing: references and the borrow checker. At the end of the last chapter we ran into an inconvenience: to look at a string, a function has to take it away and then hand it back. Python has no such problem, because every name is already a reference to an object, and you can pass them around anywhere. In Rust a reference exists as a separate thing and is written with an ampersand. It is an ordinary pointer: eight bytes holding the address of a value, the very same address that a processor keeps in a register and follows with a load instruction. But references come with strict rules, and a part of the compiler called the borrow checker enforces them. It works at build time and costs nothing while the program runs.\n\nThe first kind of reference, and the most common, is the shared one: ampersand T. It gives you the right to read a value, but not to own it. A function takes a reference to a string, counts the vowels in it and returns a number, while the calling code stays the owner and keeps using its string after the call. This is what it means to borrow: there is one master, and the borrower does not destroy the value when it leaves scope. You can hold as many shared references to one value as you like, nobody gets in anybody's way, because nobody is changing anything. The value is effectively frozen: while someone is looking at it, it will not change.\n\nIf a function needs to change a value, it is handed a mutable reference: ampersand mut T. For this, the variable itself must be declared with mut, and the call also says ampersand mut, so at the call site you can see that the value may be changed. A function that receives a mutable reference to a vector can add elements to it, and the caller will see the result. The habit from Python, where any list can be changed from anywhere, does not work here: the right to write is granted explicitly, and you have to obtain it. To write through a mutable reference you use the star, for example, star x plus-equals one.\n\nNow for the main rule of the borrow checker. At any moment a value can have either any number of readers, or exactly one writer, but not both at once. A violation is a build error. Sound familiar? It is the same principle that processor caches rely on. In the MESI protocol several cores may hold a cache line in the shared state as long as everybody only reads, but to write, a core must get the line in the modified state and invalidate everyone else's copies. Rust applies the same rule to the whole program and checks it ahead of time. As a bonus, it rules out data races between threads: two writers, or a writer together with a reader, simply do not compile.\n\nLet us see what this protects us from. Take a vector and a reference to its first element, and then add a new number to the vector. The push method may run out of capacity, ask the allocator for a bigger buffer, move the elements there and free the old one. The reference to the first element would keep pointing at freed memory: a dangling pointer, use after free, a classic security hole. In Python and in C such code builds, and in C it might work or it might blow up. Rust refuses to compile it: while a reader exists, the vector cannot be changed. The error is called: cannot borrow as mutable because it is also borrowed as immutable.\n\nSo when does a borrow end? Not necessarily at the closing brace. The checker considers that a reference lives from its creation to the last place where it is used. This is called non-lexical lifetimes. That is why code like this is allowed: you got a reference, read the value, never touch the reference again, and right after that take a mutable reference. But if after the change you try to read through the old reference again, the error returns. Often the fix is to swap two lines or to copy the value you need: a number or a short string can be copied straight out from under a reference, and then no borrow is needed.\n\nThe second trouble the checker guards against is a reference to something that no longer exists. Suppose a function creates a string inside and returns a reference to it. At the end of the call the function's frame disappears from the stack, the string is destroyed, and the address in the result points into a dead zone. In C such code compiles, and the result is random data. Rust rejects it: the compiler sees that the reference outlived its value. The right solution is usually simple: return the string itself, that is, hand ownership to the caller. A reference can be returned only to something that lives longer than the call, for example to an input argument.\n\nA special kind of reference is the slice. A string slice, str, and an array slice, square brackets with a type, consist of two words: a pointer to the start and a length, sixteen bytes in all. They do not own data, they just point at a piece of someone else's memory. String literals in a program are slices pointing at a read-only section of the executable itself. That is why function parameters are usually declared as a slice rather than as a reference to a String or a Vec: then the function accepts a string, a literal, and a part of a string. The boundaries of a string slice are counted in bytes and must fall on a character boundary, otherwise there will be a panic.\n\nIf a function returns a reference, the compiler needs to know which of the input arguments it points to. Lifetime parameters serve this purpose: an apostrophe and a name, for example, apostrophe a. A function that picks the longest of two strings declares that both input references and the result are tied by one lifetime, a: the result will not outlive either argument. The annotations do not exist at run time and cost nothing: they are hints for the checker, and only the signature is checked, not the body. In simple cases, for example with a single input argument, the compiler fills them in by itself, and you write nothing.\n\nThe same goes for structs. If a struct stores a reference, it gets a lifetime parameter: a text parser that holds a slice of the source string and a position does not own the text and cannot outlive it. Such structs are convenient because they do not copy data: the words the parser hands out are slices of the same text. But there is a price, because the owner of the text has to live long enough. If it is hard for you to satisfy the compiler, that is a signal: maybe the struct would be better off owning its data, that is, storing a String. References in structs are for places where speed matters or where you need to avoid copying.\n\nMethods show three ways to take self. Ampersand self lets you read, ampersand mut self lets you change in place, and plain self takes the whole object, so it can be called only once, for example when finishing a builder. Traversals of collections work the same way: a loop over ampersand vector yields references to the elements, a loop over ampersand mut vector yields mutable references, and a loop over the vector itself takes the elements and the vector with them. Shared references are copied freely, but a mutable reference cannot be copied: you can only lend it out temporarily, and that is called reborrowing.\n\nA few small things that people often mix up. Methods and operators dereference references on their own: two values behind references are equal if the values are equal, not the addresses. To find out whether two references point to the very same object, like the is operator in Python, you use the function ptr eq, which compares exactly the addresses. You can see the address of a local variable by turning a reference into a pointer. If you call one function from another and compare the addresses of their local variables, the nested call will have the smaller address, because the stack grows downward, toward lower addresses, as we saw in the chapter about calls. Finally, a reference to a literal and a reference to a variable look the same to a function: it just gets an address and a length, and it does not need to know where the data lives, on the stack, on the heap, or in the constants section.\n\nLet us sum up. A reference is a pointer with a check. A shared one lets you read, a mutable one lets you change, and there are either many readers or one writer, as in a cache coherence protocol. A reference cannot outlive the value it points to, so there are no dangling pointers in Rust. Slices point at a piece of someone else's data and consist of a pointer and a length. Lifetime parameters tie references together and are checked at build time. It is not easy to get used to the checker's messages, but each of them stops a bug that in another language you would hunt for in a debugger. Next we will turn to structs, enums, and pattern matching.
