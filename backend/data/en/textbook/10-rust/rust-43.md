#CHAPTER 43 | Data and PostgreSQL
Learning Rust. Chapter 43. Data and PostgreSQL. No serious web service gets by without a database, and in our course the database role is played by PostgreSQL. In practice you plug in ready-made libraries: sqlx, tokio-postgres, or the synchronous postgres crate. But there is no magic in them: under the hood there is a binary protocol over a socket, conversion of text values into Rust types, a connection pool, transactions that roll back on error, and versioned migrations. Today we build these mechanisms on the standard library, to understand what the libraries do. We will look at the format of protocol messages, mapping result rows onto structs, protection from query injection, a query builder, a pool, transactions with automatic rollback, migrations, the repository pattern, and parsing a connection address.\n\nLet's start with the idea of typing. A relational database returns rows where every value is text, and an empty value stands for the absence of data. Rust describes the same schema with a struct whose fields have the right types. An integer becomes an integer type, a boolean becomes a bool, and a column where a gap is allowed becomes an Option. Converting a result row into a struct is a function that tries to parse the value of each column and collects the errors. Such a layer is called a mapping, and you write it once for each entity. An important property of Rust: you cannot forget to handle an empty value, because a type without an Option will not accept a gap.\n\nThe Postgres protocol is binary, but it is simple. Every server message starts with a one-byte tag, followed by the length, four bytes in network order, counting those four bytes themselves, and then the content. Client messages are built the same way, except for the very first, the startup message: it has no tag, but it has a length, a protocol version number, and name and value pairs written as strings ending in a zero byte. A simple query is the tag Q, the length, and the query text with a zero at the end. All numbers are sent most significant byte first, and strings end with a zero instead of storing a length.\n\nA server response is a sequence of messages. The row description lists the columns, and a data row contains the number of columns and, for each, a four-byte value length and the bytes themselves; a length of minus one means an empty value. The command complete message carries a tag like select three, and the ready for query message reports the transaction state. An error message consists of fields with one-byte tags: severity, a five-character state code, and text. The reading loop takes a header from the stream, checks that enough bytes have arrived, and hands out the tag with the content; an incomplete message is a reason to wait for more data.\n\nValues in text format are strings, and parsing them into types goes through the FromColumn trait. For integers we call string parsing, for booleans Postgres sends t and f, and for text the value is simply copied. A parsing error becomes a clear message with the column name. For an Option, an empty value gives None, and a non-empty one is parsed by the inner type. The implementation of the trait for a generic Option is written once and works for any type that knows how to parse itself. This is what libraries do with the derive macro for structs: it generates exactly such calls for each field.\n\nNow security. If you assemble a query by gluing strings, an attacker will send a name with a quote and an extra condition, and the query will change its meaning: this is injection. There are two ways to defend. Escaping a literal doubles the quotes inside the value and wraps it in quotes, but it is easy to forget to apply it somewhere, and it depends on server settings. The right way is parameters: the query text contains the placeholders dollar one, dollar two, while the values are passed separately, in the protocol itself, and the server never mixes them with code. Every database library is built on parameterized queries, and you must not glue values into a query by hand.\n\nA query builder helps assemble the query text in parts and keep the parameters separate. The method that adds a condition takes a column, an operation, and a value: the value goes into the list of parameters, and the placeholder with the next number appears in the text. Then the sort order and the row limit are added. The build method returns a pair of the text and the list of values. Column and table names must never be inserted into a query from user input: only values are passed as parameters, and names are chosen from a set known in advance. Note that the builder owns its data and receives itself by value, which lets us write chains of calls.\n\nEstablishing a database connection is expensive, so we use a pool. It keeps ready connections in a list under a mutex. A request for a connection takes one, and if the pool is empty, the thread waits on a condition variable. The returned connection wrapper implements the Drop trait: when destroyed, it puts the connection back itself and wakes up a waiter. The user cannot forget to return the connection, because the release is tied to the scope. The pool size is chosen so that it does not exceed the allowed number of server connections: thousands of threads are not needed, a dozen connections is enough.\n\nTransactions are expressed with the same trick. The begin function sends the begin command and returns a guard object. The commit method takes the object by ownership, sends the commit command, and marks the transaction finished. If the function exits with an error or a panic and the object is destroyed without a commit, its destructor sends a rollback. You no longer have to remember the rollback in every branch with the question mark operator: any error while the object is alive automatically cancels the changes. This is one of the best examples of how Rust's ownership and destructors make code more reliable than explicit try and finally blocks.\n\nThe database schema needs versioning too. A migration is a numbered file with commands that change the schema. A bookkeeping table stores the numbers of the migrations already applied. On startup the application sorts the migrations by number, skips the applied ones, and runs the rest one at a time, each in a transaction, recording the number after success. Running it again does nothing. This is called idempotence, and it lets you safely run migrations on every start. Rolling back to a previous version is described with paired files, but in practice people prefer to move only forward and fix mistakes with a new migration.\n\nSeparation of concerns completes the picture. Business logic should not know where the data lives, so access to it is hidden behind a repository trait with methods like add and find. One implementation works with the real database, another with an in-memory table. Application functions accept any type that implements the trait, and so they are tested with fast tests that need no database and no network. Storage errors are converted into application-level errors in one place. It is exactly this structure that lets you replace the database library without touching the rest of the code.\n\nIn practice a connection is described by an address: scheme, user name, password, host, port, and database name. It is parsed in parts: we cut off the scheme, split at the at sign, then at the colon and at the slash. The default port is five four three two. The address is taken from an environment variable and not from code: passwords must not end up in the repository. With the real sqlx library, creating a pool and a query with a bound parameter take a line or two, but underneath lie exactly the mechanisms we have just examined. It is convenient to run Postgres itself in a container, and then your application connects to it at the localhost address.\n\nLet's sum up. The Postgres protocol consists of messages of the form tag, length, content, with numbers in network order and strings ending in zero. Result rows are turned into structs by the column parsing trait, and an empty value is an Option. You must not glue values into a query: parameters are passed separately, and the query builder keeps them in a list. The connection pool and transactions rely on destructors, migrations record the applied versions, and a repository separates business logic from storage. The connection address is read from the environment and parsed in parts. With this we finish the book about Rust: you now have the language, algorithms, the system, a server, and data. Next comes a language for the interface of this server: JavaScript.
