#CHAPTER 20 | Closures and Iterators: A Pipeline with No Overhead
Learning Rust. Chapter 20. Closures and iterators: a pipeline with no overhead. Python has lambdas, list comprehensions, and generators: you write one line, and the data flows through a chain of transformations. Rust offers the same thing, closures and iterators, with one important difference: all of it compiles down to an ordinary loop, just as fast as one written by hand. The abstraction costs nothing here. And closures are tied directly to ownership: whatever they capture from their surroundings, Rust checks with the same borrowing rules you already know.\n\nA closure is a function without a name that you can put into a variable. The parameters go between vertical bars, and the body follows: either a plain expression or a block in curly braces, which can have as many lines as you like. In Python a lambda is limited to a single expression, and here there is no such limit. The types of the parameters and the result are usually inferred from the first use and then stay fixed: you cannot pass a number to the same closure and then a string. A closure is an ordinary value: you can pass it around, return it, and store it in a struct.\n\nThe main difference between a closure and a function is that a closure captures variables from its environment. If the closure only reads a variable, it takes it by reference; if it changes it, by mutable reference; and if it needs to own the value, it takes it over. The compiler picks the weakest way that works. The word move before the vertical bars forces it to take everything, for example to send the closure to another thread. Under the hood a closure is an anonymous struct holding the captured values and a call method: the more it captures, the bigger it is.\n\nThe way of capturing decides which of three traits the closure has. Fn can be called many times, because it only reads the environment. FnMut can also be called many times, but it changes what it captured, so the caller needs a mut. FnOnce can be called only a single time, because it consumes a captured value, for example by returning it. Each closure implements whichever of them fit, and functions like map or sort accept the trait, not a concrete type. This is the connection you already know between ownership and what can be done with a value.\n\nHow do you pass a closure into a function? Most often with a generic parameter and a bound: F, which implements Fn from i32 to i32. The compiler makes a separate copy of the function for each closure and inlines the call, as we saw in the chapter about traits. If you need closures of different types in one list, or a function result that depends on conditions, you use Box of dyn Fn. For simple cases a function pointer will do: it captures nothing and behaves like a function pointer in C, only without the void pointer for context, because a closure carries its context with itself.\n\nNow iterators. An iterator can produce values one at a time, and its main trait is laziness: until you ask for a value, nothing is computed. Calling iter on a vector does not copy any data, it just creates a small struct with a position. The chain of generators you are used to in Python works the same way. There are two fundamentally different kinds of methods: adapters, which build a new iterator and do nothing yet, and consumers, which start the work and return a result. Without a consumer at the end, the pipeline simply does not run, and the compiler warns you about it.\n\nAdapters are a vocabulary of transformations. Map applies a function to each element, filter keeps the ones that fit, enumerate adds an index, zip glues two iterators into pairs, take and skip take and skip elements, chain joins two iterators, and rev goes from the end. Flat map unpacks nested collections, filter map does a filter and a transformation in one step, and take while reads as long as a condition holds. Windows and chunks of slices come from the windows and chunks methods. Each adapter returns a new struct wrapped around the previous one, so the whole pipeline is a single nested struct on the stack.\n\nConsumers run the pipeline. Collect gathers the elements into a vector, a string, a hash map, or a result holding a vector, and you have to specify its type. Sum, product, count, min, and max give numbers. Any and all check conditions and stop at the first deciding element. Find and position look for the first match. The most universal consumer is fold: it takes an initial value and a closure that folds an element into an accumulator, and the others can be expressed through it. In Python the counterpart is reduce, but in Rust it shows up much more often.\n\nHere is a subtlety that trips everyone up: the types of arguments in closures. A regular iterator over a vector produces references, so in filter you get a reference to a reference. To work with the number itself, a pattern in the closure header takes it apart: a vertical bar, an ampersand, and a name. Pair elements, for example from enumerate, are taken apart with parentheses right in the parameter. The methods copied and cloned turn an iterator of references into an iterator of values. An iterator over a vector with into iter, on the other hand, takes the elements away, and you cannot use the vector afterward.\n\nWhy is all this fast? Every adapter is a separate type, and the closure call is known at compile time, so the compiler inlines everything into a single loop, merging the steps: there are no intermediate lists and no calls through pointers. Accesses to a slice go one after another, without bounds checks wherever the compiler can see the length, and summing numbers often turns into the processor's vector instructions, which add several elements per cycle. These are the same techniques you saw in the chapters about the processor pipeline and the cache: sequential access and predictable branches.\n\nFor complex streams there are extra building blocks. Peekable lets you look one element ahead without taking it, which is handy for parsing text. Scan keeps an accumulator but yields every intermediate result, for example running sums. The function from fn builds an iterator out of a closure, and successors builds one from an initial value and a rule for the next step, for example powers of two. Repeat and cycle repeat values endlessly, and take cuts them off. All this replaces Python's generator functions, which Rust does not have in stable form.\n\nClosures can be stored. A struct with a generic field F bounded by the Fn trait remembers a computation: a cache calls the closure until it has a result. A vector of boxes of dyn FnMut holds event handlers, which are called in turn and can change their own state. If a closure refers to data outside itself, you have to watch the lifetimes: a returned iterator or closure that has captured a reference must be marked as living no longer than that reference. A move closure, on the other hand, gets the data in full and can freely outlive the function.\n\nLet us sum up. A closure is an anonymous struct with captured values, and the way of capturing determines the trait: Fn, FnMut, or FnOnce. Iterators are lazy: adapters build the pipeline and consumers run it. Reference types in closures are taken apart with patterns, and the compiler folds the chain into one fast loop. Closures can be stored in structs and boxes, keeping an eye on lifetimes. The next chapter explains how Rust manages the lifetimes of references and which smart pointers the standard library has.
