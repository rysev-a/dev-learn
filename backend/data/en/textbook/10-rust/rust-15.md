#CHAPTER 15 | Ownership: who is responsible for memory
Learning Rust. Chapter 15. Ownership: who is responsible for memory. Every program has one unpleasant job: take memory, use it, and give it back on time. In Python this is done by the garbage collector: it counts references to objects and removes the ones nobody needs, and you never think about it, but you pay with pauses and extra memory use. In C it is the opposite: you call malloc and free yourself, and any mistake turns into a leak, a double free, or access to memory that has already been released. Rust chooses a third way. Memory is freed exactly on time, but the compiler decides when, and it decides at build time, using a small set of simple ownership rules. There is no garbage collector in the program, and a whole class of bugs disappears.\n\nLet us begin with the place where data lives. We already know the stack: call frames, the sp register, and variables of known size that vanish together with their frame. But a string that grows, or a list that keeps receiving elements, will not fit on the stack, because their size is not known in advance. Such data lives on the heap, and the heap is managed by an allocator, the very same malloc we studied in the chapters about process memory. Only a small record stays on the stack. For the String type it is three words, twenty-four bytes: a pointer to a buffer on the heap, a length, and a capacity. The characters themselves sit behind that pointer. The Box type is simpler: one pointer on the stack, and the value it holds lives on the heap.\n\nOwnership has three rules. Every value has an owner, that is, a variable responsible for it. At any moment there is exactly one owner. And when the owner goes out of scope, the value is destroyed and the memory goes back to the allocator. You never write an explicit call to release memory, and you cannot forget it. For a Python programmer this resembles the with statement, except that it works for every variable and always. Notice that the rules talk about the owner, not about a reference count: the question of who uses an object last is answered by the compiler ahead of time, not while the program runs.\n\nWhat does it mean to go out of scope? It is the closing curly brace of a block. At that brace the compiler inserts a call to drop for every variable in the block, in reverse order of declaration: the one created last dies first, just like frames on the stack. If a type has its own implementation of the Drop trait, your code runs on destruction: close the file, release the lock, return the connection to the pool. This technique is known as RAII: the resource belongs to a value and is released together with it. Early destruction is possible too: the drop function takes a value and swallows it, so the value ends right there, not at the brace.\n\nNow comes the part that is most unfamiliar to a Python programmer. Assign a string to the variable s, and then assign s to the variable t. In Python both names will point to the same object, and that is fine, because a reference counter is responsible for it. In Rust the value moves: those same twenty-four bytes are copied into t, and the name s is declared invalid. If both names stayed alive, at the brace someone would come to free the buffer twice, and we would get the classic double free bug. That is why an attempt to use s after the move will not compile: the compiler will tell you that the value was moved. Notice that the heap is not touched at all; only the three words on the stack have moved.\n\nBut wait: if you assign the number five to the variable s, and then assign s to t, everything works, and you can keep using the five! It all comes down to the Copy trait. Simple values that fit entirely on the stack and own nothing on the heap are copied bit by bit, like registers in a processor, and the original stays alive. Integers and floating point numbers are copied, so are booleans and characters, and also tuples and arrays made of such values. String and Vec cannot be copied: a bitwise copy of the pointer would give two owners of one buffer. You can allow Copy for your own type with the derive attribute, if all its fields are copyable too. The distinction is simple: what lives entirely on the stack is copied, and everything else moves.\n\nIf you really do need two independent strings, you say so explicitly: the clone method. It asks the allocator for a new buffer, copies all the bytes into it, and returns a separate owner. In effect it is malloc plus memcpy, and it costs time that grows with the size of the data. Rust deliberately does not make such copies silently: the price is visible in the text of the program. If your code has many clones, that is a reason to stop and ask whether they are needed, though sometimes they are exactly what you want. For a number, on the other hand, clone and an ordinary copy cost the same, because the same few bytes are copied.\n\nPassing a value to a function is also an assignment, and the same rules apply. If you hand a String to a function by value, the function becomes its owner: after the call your variable is invalid, and the string will die at the brace inside the function unless it is returned. You can give ownership back through the return value, and a tuple helps when there are several values. This style works, but it gets tiresome fast: handing things over and taking them back every time is exhausting. That is exactly why borrowing was invented: a function can be given a reference, a temporary access without a transfer of ownership. But that deserves a chapter of its own. For now, remember: calling a function with a String argument is a move.\n\nNow let us look at the Box type in more detail. Box moves a value to the heap: on the stack stays a pointer of eight bytes, and the value itself lies at that address, and the star dereferences it. Why is this useful? The first reason is that a large value is convenient to pass by pointer rather than copy. The second is more important: recursive types. Suppose a list element stores a number and the next element of the same type. The size of such a type is infinite, because it contains itself, and the compiler will refuse to build it. If the next element is hidden inside a Box, what lies in it is only a pointer of known size, and the chain goes off to the heap. This is how Rust builds lists, trees, and expressions.\n\nLet us look at a real list. A list element is an enum: either a value with a continuation inside a Box, or the end. The head of the list lies on the stack, and every next node is allocated separately on the heap, just like in the linked lists from the book about algorithms. When the head goes out of scope, drop is called for the node, then for the Box inside it, then for the next node, and the chain frees itself, link after link. An empty tail is often written as an Option of a Box: the value nothing takes the very pointer value that can never be a real address, so an Option of a Box is no thicker than an ordinary pointer. This is called a niche.\n\nSometimes you need to take a value out from under an owner that is still alive. For example, you cannot simply move a field out of a struct while the struct owns it, and you cannot pull an element out of a vector by index either: that would leave a hole in the vector. For such cases there are safe tools. The take method of Option grabs the value and leaves nothing in its place. The function mem replace puts a new value in and returns the old one, and mem swap exchanges two values. A vector hands out an element with the remove method: it shifts the tail and returns ownership. These functions take a reference to a mutable value, and we will deal with references in the next chapter; for now, think of them as permission to change a value in place.\n\nAnd what if there must be several owners? For that there is the type Rc, a reference counter. The value is stored on the heap together with a counter, and a clone of an Rc copies only the pointer and increases the counter by one. When another owner dies, the counter goes down, and at zero the value is destroyed. This is exactly the Python model, but in Rust you turn it on explicitly, where you need it, rather than having it built into every object. The contents of an Rc are read only, and for threads there is its thread-safe sibling Arc, which we will get to later. The function strong count shows the number of owners, and it is handy for checking that cloning does not copy the data.\n\nLet us sum up. Data of unknown size lives on the heap, and on the stack stays the owner: a String, a Vec, or a Box. A value always has one owner, and when that owner leaves, the memory is returned automatically, in reverse order of creation. Assignment and a function call transfer ownership, while numbers and other simple types are copied. Clone makes a deep copy, but only when you ask for it. Box is needed for recursive types, and Rc for several owners. One question remains: how do we let a function read a string without giving it away? The answer is borrowing and the borrow checker, the main tool of Rust.
