#CHAPTER 23 | Threads and Shared State: Concurrency Without Data Races
Learning Rust. Chapter 23. Threads and Shared State: Concurrency Without Data Races. Python has threads, but the global interpreter lock does not let two threads run Python code at the same time, so for heavy computation you have to start separate processes. In Rust, threads are real: each one is an operating system thread that can run on its own core, and there is no global lock. The danger is well known: when two threads write to the same memory at the same time, the result is unpredictable. That is a data race. Rust solves the problem with its type system: a program in which a data race is possible simply does not compile. In the book about computer architecture we saw what races mean for cores and caches.\n\nA thread is started with the spawn function, which takes a closure. It returns a handle with a method called join: it waits for the thread to finish and returns its result, or a sign that it panicked. The closure is usually written with move, because the thread may outlive the function that started it, so the values have to be handed over completely. Every thread is a real kernel thread with its own stack, usually two megabytes of virtual memory, so you cannot create hundreds of thousands of them. If you need to borrow local data, there is scope: inside it, threads may take references, because the compiler knows that the scope will wait for all of them.\n\nWhat is behind spawn? The library asks the kernel for a new thread: on Linux that is the clone system call. The kernel allocates a stack, creates a task structure and puts it into the queue of the scheduler we discussed in the Unix book. Switching between threads costs microseconds: the registers have to be saved, and the caches and page tables partly go cold. A blocking call, for example waiting for the network, simply puts the thread to sleep, and the kernel gives the processor to another one. How many threads to start is decided by measuring, not by intuition.\n\nWhy does the compiler not allow data races? Two marker traits are responsible for that. Send says that a value can be passed to another thread. Sync says that a reference to a value can be shared between threads. Spawn requires that the closure and everything it captured be Send. Rc is not Send: its counter is changed with plain addition, and two threads would corrupt it. A reference to a RefCell is not Sync for the same reason. The compiler derives these traits by itself from the makeup of a type, and you rarely write them yourself. If you try to pass an Rc into a thread, you get a clear error at build time.\n\nFor shared mutable state there is the mutex. It wraps the data instead of just standing next to it, as in other languages: to get to the value you call lock and receive a guard. While the guard is alive, the thread owns the data alone, and as soon as the guard goes out of scope, drop runs and the lock is released. You cannot forget to release a mutex, just as you cannot forget to close a file. For several threads to own one mutex, you put it into an Arc: an Arc of a Mutex of a value. If a thread panics while holding the lock, the mutex is poisoned, and the next lock returns an error that you can handle.\n\nIf reads are frequent and writes are rare, you use an RwLock: any number of readers at the same time, or one writer. This is the same idea we saw in the cache coherence protocol: shared state for many readers and exclusive state for a writer, only at the level of the program. A mutex is simpler and usually faster for short operations, and an RwLock pays off when reading is expensive and writing is rare. Keep the critical section as short as possible: while you are inside, the other threads stand still, and parallelism turns into a queue.\n\nAnother approach is not to share memory but to pass messages: do not communicate by sharing memory, share memory by communicating. An M-P-S-C channel is many senders and one receiver. The sender puts a value in with the send method, and the value moves into the channel, which means ownership moves with it: the one who sent it can no longer change it. The receiver calls recv and blocks until something arrives, and a loop over the receiver ends when all the senders are closed. The sender is cloned to give it to several threads. A bounded channel, sync channel, slows down a producer that is too fast.\n\nThe lowest level is atomic types: AtomicUsize, AtomicBool and others. Operations on them are indivisible and are implemented by processor instructions, for example amoadd on RISC-V or lock xadd on x86. The fetch add method increases a counter without a lock, and compare exchange writes a value only if it equals the expected one, and locks and lock-free counters are built on that. The ordering parameter chooses how strong the ordering guarantees are. Relaxed guarantees nothing except indivisibility, acquire and release link a read to a write, like the memory barriers from the cache chapter, and sequentially consistent gives one global order and is the most expensive.\n\nThreads have to be coordinated. A condition variable lets you wait for a condition: the thread goes to sleep on the wait until another one calls notify, and you check the condition in a loop, because wakeups can be spurious. That is how a bounded queue for producers and consumers is made. A barrier makes a group of threads wait for each other before the next stage. The park method puts a thread to sleep without a lock, and unpark wakes it. If you need a pool, you start a fixed number of threads in advance, and they take tasks from a shared channel, so that you do not pay for creating a thread for every small job.\n\nParallel computation is best built so that the threads touch shared data as rarely as possible. Cut the array into pieces, give each thread its own piece, let each one accumulate a partial result for itself, and then combine the sums. The chunks mut method gives non-overlapping mutable slices, and the compiler proves that the threads do not get in each other's way. This technique is called split first, merge later. It is faster than any locks, because no data moves between cores, and it gives exactly the same result in any order of execution.\n\nThe speed of a parallel program runs into memory. If two threads often write different variables that sit in the same sixty-four-byte cache line, the cores will keep tearing the line away from each other: this is false sharing, and it can kill the whole gain. The cure is to move the threads' data apart. By Amdahl's law, the speedup is limited by the sequential part: if ten percent of the work cannot be parallelized, it will never get more than ten times faster, no matter how many cores you add. The number of available cores is returned by the function available parallelism, and usually you take that many threads.\n\nWhat remains are the classic mistakes. A deadlock happens when one thread holds the first lock and waits for the second, while another does the opposite: the solution is to always take locks in the same order. Starvation is when a thread never gets a resource. Try lock attempts to take a mutex without waiting. Rust will not protect you from logic errors, but it removes a whole class of the most treacherous ones: data races. And it is important to remember that threads are not the only way to do many things at once: for thousands of simultaneous connections you use async, where instead of threads there are tasks built as state machines, and that is the topic of a separate chapter later.\n\nLet us sum up. Threads in Rust are real, and data races are forbidden by types: Send and Sync decide what can be passed and shared. A mutex owns its data and is opened through a guard, Arc shares ownership, an RwLock means readers or a writer, channels pass values together with ownership, and atomics are indivisible processor operations. The split and merge scheme scales well, and false sharing and Amdahl's law remind us about the hardware. The next part of the book applies everything we have said in practice: algorithms, a processor emulator, files and a network server.
