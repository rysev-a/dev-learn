#CHAPTER 49 | Rooms and messages: the chat REST API
Learning Rust. Chapter 49. Rooms and messages: the chat REST API. We already have the skeleton, the state, the errors, the database and the users. Now it is time to assemble the chat itself out of them. We need rooms, members, posting messages and a history we can read page by page. Live delivery over WebSockets we leave for the next chapter, but we will design things so that it sits neatly on top: every message gets a monotonic number, history can be read from any point, and sending the same thing twice does not create duplicates. The main idea of the chapter is a small set of predictable operations with exact permissions.\n\nDesign starts with resources. Rooms live under the rooms path, members live inside a room, and messages do too. The methods express intent: GET reads, POST creates, PUT sets a state, DELETE deletes. It is important to tell idempotency apart. Joining a room again with PUT leaves the world as it was, while a repeated POST would create a second message. For such cases we introduce an idempotency key. Addresses are nouns, not verbs, and the response codes are precise: created, no content, conflict. An interface like that is easy to guess, easy to document and easy to cover with tests.\n\nCreating a room means two records: the room itself and the owner as a member. They must appear together, so they run in one transaction. The name is checked for length and allowed characters before we touch the database; a repeated name is rejected by a unique index, and we answer with a conflict. A successful response carries the status created, the address of the new room in the Location header, and a description in the body. The owner is taken from the current user, not from the request body: we cannot trust the client on the question of who it is.\n\nJoining a room is an idempotent operation: an insert that ignores a repeat returns the same result no matter how often the client repeats the request. Leaving is idempotent too. The exception is the owner: they cannot leave without handing the room over, or the room would be orphaned. The visibility of rooms is limited by membership: to a non-member, a room answers exactly as a nonexistent one would, so we do not reveal which private rooms exist. The list of members is available only to members. These rules are enforced in the queries themselves, not in client code.\n\nPosting a message checks several things. The author must be a member of the room, otherwise we refuse. The text is trimmed at the edges, is never empty, and is limited in length. We count length in characters, not bytes: Russian text takes two bytes per letter. An insert with a returning clause gives back the identifier and the creation time, and both go into the response. The identifier grows monotonically within the table, and clients will use it to say what they have seen and what they have not. That is simpler and more reliable than comparing timestamps.\n\nHistory is read in pages. The client asks for the latest messages in a room, and when the user scrolls up it asks for the next ones, passing the identifier of the oldest message it has seen. This is cursor pagination: the query uses an index and does not slow down on deep pages. The limit parameter has a default and a hard ceiling, otherwise a client could pull out the whole table. The response returns the cursor for the next page, and when there are no more messages the field is absent. New messages appear at the top, so the cursor does not shift, unlike a page number.\n\nConnections drop: a phone goes into the subway, a laptop gets closed. After reconnecting, the client has to catch up on what it missed. For that we need a second reading mode: all messages newer than a given identifier, from oldest to newest. The client remembers the number of the last message it received and asks for everything after it. This way reliability does not depend on live delivery: the WebSocket is the fast path, and the request afterwards is the safety net. It is nice when both paths return messages in the same format and the same code builds them from database rows.\n\nThe network is unreliable: the client sends a message, the response is lost, and it repeats the request. Without protection the chat ends up with two identical messages. The solution is an idempotency key: the client invents a unique send number and passes it in a header. The table has a unique constraint on the triple of room, author and key. An insert that ignores a repeat changes nothing, and then we read the record that already exists and return it. The first response is created, the repeat is simply a success with the same body. The client can repeat as many times as it likes.\n\nTo show the number of unread messages, we store for every member in every room the number of the last message they have read. The unread count is the number of messages newer than that number. The marker is updated by a query that never lowers it: it takes the greater of the old and the new value, so that a late request cannot roll progress back. The counter is computed by one query for all of the user's rooms, not one query per room. A user's own messages are usually left out of the count. An index on room and identifier makes the count cheap.\n\nMessages can be edited and deleted. Only the author may edit, and the record keeps an edit timestamp so that clients can show that the message changed. Deleting is allowed to the author or to the room owner. Deletion is usually soft: the record stays but is marked, and the history shows a placeholder instead of the text. That keeps the numbering intact, and clients that received the message earlier can also receive a deletion event. Other people's messages are not exposed: permissions are checked right in the update condition, and the difference between absent and forbidden is made by a second query, only to build the response.\n\nMessage search starts simple: a case-insensitive substring. The percent sign and the underscore in the user's query must be escaped, otherwise they turn into wildcards. Such a search reads the whole room and is not suitable for large volumes. The sensible option is full-text search: the text is turned into a set of normalized words that take the language's morphology into account, and the query is matched against it with the match operator. For speed, a GIN index is placed on that expression. Results are always capped in number and sorted by recency or by relevance.\n\nA good interface is predictable in its errors. If the resource does not exist or is hidden from you, the answer is 404. If you know about the resource but the action is forbidden, 403. Invalid data is 422 with a list of fields. Too many requests is 429. Everything has a size limit: the body, the length of a name, the number of items in a batch. The format of the error body is always the same, as we agreed in the chapter on errors. And the main rule against leaks: a non-member must not be able to tell a private room from a nonexistent one in any way.\n\nLet us sum up. The chat API is built around resources, and the methods and response codes express intent precisely. A room is created in a transaction together with its owner. Joining, leaving and marking as read are idempotent, and resending a message is protected by a key. Permissions are checked inside the queries, and private rooms are hidden from outsiders. History is read with cursors in both directions: before for scrolling up, after for catch-up reading. Deletion is soft, and search is bounded and escaped. In the next chapter we will connect WebSockets and real-time message delivery.
