#CHAPTER 33 | Tokio: the Runtime, #[tokio::main], and spawn
Learning Rust. Chapter 33. Tokio: the runtime, the tokio main attribute, and spawn. This chapter begins the practical part of the section: we take a close look at Tokio, the most widely used asynchronous runtime. It consists of several parts: a task scheduler, an I/O driver, timers, and a pool for blocking operations. All of this is switched on with feature flags in the manifest: rt, rt multi thread, macros, time, net, io util, fs, sync, signal, process. The simplest thing is to enable the full flag, and that is what the teaching examples do. In real projects you pick the flags more precisely, so as not to pull in extra code and to cut build time and program size.\n\nAn asynchronous main function cannot be declared simply as async fn main: the main function has to be an ordinary one. The tokio main macro rewrites it: it creates a runtime and calls block on with the asynchronous body. Its parameters control the runtime: flavor chooses the multi-threaded or single-threaded variant, worker threads sets the number of worker threads, and start paused is for tests that involve time. For tests there is a matching macro, tokio test, which does the same for every test. These two macros are enough in ninety percent of programs, and creating a runtime by hand is needed when you embed Tokio into existing synchronous code.\n\nRuntimes come in two kinds. The multi-threaded one creates a pool of worker threads, by default one per core, and each thread has a local task queue. When a thread runs out of work, it steals tasks from its neighbors; this is called work stealing. A special slot holds the most recently woken task, so that switching between related tasks is fast. The single-threaded runtime, with the current thread flavor, runs everything on one thread: it is simpler, more predictable, does not require Send, and suits tests and small utilities. The choice depends on the job: multi-threaded for servers and heavy load, single-threaded for simplicity and determinism.\n\nFor fine-grained configuration you use a builder. Read it like this: Builder, new multi thread, then worker threads four, then thread name, then enable all, then build, and you get a runtime. Enable all turns on the I/O and timer drivers; without them networking and timers do not work. The block on method runs a future and waits for the result on the current thread. A Handle is a lightweight reference to a runtime: you get it with Handle current inside a task and use it to start tasks from ordinary threads. When a runtime is dropped, all its tasks are cancelled at the nearest await.\n\nThe main tool is the spawn function. It takes a future, runs it as a separate task, and returns a JoinHandle. The future must be Send and static: everything that lives inside it belongs to it. If you await the handle, you get a Result: Ok with the value, or a JoinError if the task panicked or was cancelled. If you simply drop the handle, the task keeps running in the background: it has become detached. The abort method cancels a task, is finished asks whether it is done, and a panic in a task is isolated: it does not bring down the runtime, and reaches whoever is waiting as an error with the is panic flag.\n\nWhen there are many tasks and you need to collect their results, JoinSet is handy. It holds a set of tasks and returns results as they finish through the join next method. It is the analog of Python's task groups and of FuturesUnordered, but the tasks in it are independent: they run on all threads. Spawn adds a task, abort all cancels them all at once, and shutdown cancels and waits. When the set is dropped, all its tasks are cancelled automatically, so it is safe: nothing leaks. The order of results is the order of completion, so if you need the launch order, attach an index to each result.\n\nBlocking code must not run in ordinary tasks: it would occupy a worker thread. For it there is spawn blocking: the closure runs in a separate thread pool, by default up to five hundred and twelve threads, and the result comes back as a future. You cannot cancel such a task once it has started: the thread will run to the end. The block in place function works differently: it turns the current worker thread into a blocking one and hands its queue to another thread, and it is suitable only on the multi-threaded runtime. For long computations on all cores, Rayon is better. Tokio's file operations use the same blocking pool inside, because operating systems do not handle asynchronous files the same way on all platforms.\n\nSometimes you need tasks that are not Send, for example with an Rc inside. For them there is LocalSet: a set of tasks that run on one thread. The spawn local method starts such a task, and run until runs the set itself. The runtime can be single-threaded here. This is needed in graphical interfaces and in thread-bound code, for example in libraries that do not support multithreading. In ordinary servers spawn local is rarely seen. You should know about it, because the compiler message saying the future is not Send can often be solved with exactly this, if the task really must not change threads.\n\nData tied to a task. The task local macro declares a variable whose value is stored separately for each task, like context variables in Python. The scope method sets the value for the duration of a future. This is handy for request identifiers that you need to carry into the log without passing them as a parameter. Every task also has its own number, which the task id function returns. For observing a runtime there is tracing, through the tracing crate, and Tokio Console, which shows live tasks, their poll times and wait times. They help find the stuck tasks we talked about earlier.\n\nScheduling in Tokio is cooperative: a task can hold a thread until it gives up control at an await. So that one task that is always ready to continue does not freeze the others, each has a budget: one hundred and twenty-eight operations, after which the resource returns Pending by itself and the scheduler gives the turn to others. This mechanism does not protect against computation without awaits: a loop that computes for a long time will occupy the thread entirely. In that case you insert a call to yield now, or move the computation into spawn blocking. A good rule: between two awaits in a task there should be no more than a few tens of microseconds of work.\n\nShutdown. When the main function returns, the runtime is destroyed, and all tasks that are still running are cancelled. In Python the remaining tasks print a warning, while in Rust they simply vanish and their destructors are called. So you need to wait for important tasks explicitly, through a JoinHandle or a JoinSet. The shutdown timeout method gives tasks time to exit cleanly, while shutdown background does not wait at all. Handling signals such as Control C is done with the signal ctrl c function: it returns a future that wakes up on the signal. In the following chapters we will build a correct server shutdown on top of this.\n\nTests. The tokio test macro creates a separate runtime for the test, single-threaded by default. For testing code that involves time, Tokio has test util: the pause function freezes time, and advance moves it forward, so a test that slept for an hour passes instantly. This needs the test util flag in the manifest, and in our sandbox it is not enabled, so the exercises use real short pauses. In real projects you enable the flag in the dev dependencies. That gives you fast, deterministic tests that do not depend on machine speed and do not interfere with each other.\n\nLet's sum up. Tokio is a scheduler, an I/O driver, timers, and a pool of blocking tasks. The tokio main attribute creates the runtime, the builder configures it, and a Handle lets you start tasks from other threads. Spawn starts a task and returns a JoinHandle, panics are isolated, and JoinSet collects results as they become ready. Spawn blocking and block in place are for blocking code, LocalSet is for tasks that are not Send. Scheduling is cooperative, so long computations must be moved out. Shutdown requires explicit waiting. In the next chapter we will look at time: timers, intervals, timeouts, and select.
