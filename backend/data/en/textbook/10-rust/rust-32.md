#CHAPTER 32 | async and await: state machines and Pin
Learning Rust. Chapter 32. Async and await: state machines and Pin. In the previous chapter we wrote futures by hand. Now let's look at what the compiler does when you write an async fn, and why Pin shows up in signatures so often. This chapter explains three things: what asynchronous functions and blocks turn into, why values need to be pinned in memory, and what restrictions borrows and Send impose. We will also cover async closures, async functions in traits, recursion and cancellation safety. This is the hardest part of asynchronous Rust, and understanding it is what separates a confident author from a beginner.\n\nAn asynchronous function is shorthand. Instead of async fn fetch, taking x of type u32 and returning a String, you can mentally write a plain fn fetch, taking x and returning impl Future with Output equal to String, whose body is an async move block. An async block creates a value of an anonymous type that implements Future, and you cannot write that type out, which is why signatures say impl Future. All of the function's arguments move into the block by value, so reference parameters make the future's lifetime depend on them. You can see this in signatures, and it explains many errors: a future that holds a reference cannot be sent to spawn, which demands static.\n\nInside a block, every await is a point where execution may suspend. The compiler splits the body at these points and creates an enum: a state for before the start, one state for each point, and a done state. Each state stores only the local variables that are still alive after that point. So the size of a future depends not on the number of variables overall, but on the largest set of live values. Variables that do not cross an await are not stored at all. A call to poll starts from the current state, runs the code up to the next point, and returns either Pending or the finished value.\n\nA problem appears when a live variable holds a reference to another local variable of the same block. Say you create an array, take a slice of it, and wait. In the state machine, the slice and the array sit in one object, and the slice points inside the state machine itself. If the state machine is later moved in memory, for example put into a vector or passed to a function, the array moves, but the slice still points to the old place. This is a self-referential struct, and ordinary Rust cannot create one safely, because values there can always be moved freely. Asynchronous Rust still has to allow such values, and the solution is Pin.\n\nPin is a wrapper around a pointer that makes a promise: the value it points to will not be moved until it is destroyed. The poll method takes a pinned mutable reference to self, so the executor must pin the future before the first call. For ordinary types pinning makes no difference, and they are marked with the Unpin trait, meaning that they can be moved even when pinned. Almost all types are Unpin, but the state machine from an async block is not. You can pin a value on the heap with Box pin, on the stack with the pin macro, and for Unpin types Pin new is enough. Beyond that, you will rarely touch Pin directly.\n\nWhere do you meet Pin in practice? In the type Pin of Box of dyn Future with Output equal to T, which is written so often that the futures crate gives it an alias, BoxFuture. In the select macro, which needs pinned futures, and in loops where a future is polled many times and pinned with the macro. In your own implementations of poll for custom combinators, where a future field has to be projected. The pin-project crate generates such projections safely, and it is recommended over writing unsafe code by hand. And if you need to wait for a future again, it is enough to pin it and call the as mut method.\n\nAsync closures. An ordinary closure that returns an async block is written like this: a vertical bar, x, a vertical bar, async move, and braces. The result type is an anonymous future, and the closure can be called many times. Since version one point eighty-five there are real async closures: async, a vertical bar, x, a vertical bar, x plus one. They work better with borrows, when the future refers to captured variables, and they come with the traits AsyncFn, AsyncFnMut and AsyncFnOnce. The new syntax replaces the workarounds people used before, and lets you write generic functions over asynchronous callbacks.\n\nBorrows and lifetimes. A reference can live across an await if the data it points to outlives the future. For functions this means that reference arguments become part of the future's type: fn longest with a lifetime a, taking x and y as references to str with lifetime a, returning impl Future plus a. A task started with spawn cannot hold references to the parent's local variables, because the parent will finish first: this is the static requirement. The way out is to pass ownership, to clone an Arc, and to move data into the task with the move keyword. This is the most common cause of errors for beginners.\n\nSend and wait points. For a multithreaded executor, a future must be Send, which means that everything it holds across an await must be Send. Rc and references without Sync make a future not Send, and the compiler will stop the build with a long message that names the variable held across an await. The trickiest trap is a guard of a regular mutex from the standard library, held across an await: it is not Send, and on top of that it can lead to a deadlock. The solutions: release the guard before the await, in a separate block; use Tokio's asynchronous mutex; or do not hold a lock across a wait at all.\n\nAsynchronous functions in traits have been stable since version one point seventy-five: you can write trait Source with async fn get, taking a reference to self and returning u32. This works through static dispatch. For dynamic dispatch, that is, for Box of dyn Source, such traits do not work: you have to return a boxed future by hand or use the async-trait crate, which does it automatically. Another subtlety is the Send requirement on the returned future, which in generic code you write explicitly as a bound on the type. These rules keep getting simpler, and newer compiler versions lift more and more restrictions.\n\nRecursion and size. An asynchronous function cannot call itself directly, because its state machine would have to contain itself infinitely. The solution is to box the recursive call with Box pin: Box pin, then factorial of n minus one, then dot await. Large futures that contain big arrays are better kept on the heap, otherwise they overflow the stack when moved, and this is a trap that Clippy finds with its large futures rule. You can measure the size of a state machine with the size of val function. To reduce it, do not hold big values across an await, and move computations into separate functions.\n\nCancellation safety. Any await may turn out to be the last: the future can simply be dropped. So code that keeps intermediate state in local variables in the middle of an operation will lose it. The classic example is reading from a stream: if part of the data is already read into a local buffer, and the read is cancelled in a select, that data is lost. For such cases you pick methods that are safe to cancel, and the Tokio documentation marks them explicitly. Cleanup is done by destructors, but the language has no asynchronous drop: a release that requires waiting is done through an explicit close method or a separate task. Keep this in mind when designing.\n\nLet's sum up. An async block is a finite state machine with a state for each await point, and its size is set by the live values. References inside a state machine make it self-referential, so it is pinned with Pin: Box pin, the pin macro, and Unpin types. Async closures and async functions in traits are now stable. Tasks require Send and static: pass ownership, and do not hold a regular mutex guard across an await. Recursion is boxed with Box pin, and code is written to survive cancellation. In the next chapter we move to Tokio: the runtime, spawn and the task model.
