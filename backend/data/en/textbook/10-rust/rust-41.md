#CHAPTER 41 | HTTP Byte by Byte
Learning Rust. Chapter 41. HTTP byte by byte. We have arrived at the main goal of the book: a web server. Real projects build one on ready-made libraries, but to use those libraries with confidence, you need to walk the path from the very bottom once. The HTTP protocol turns out to be surprisingly simple: it is text on top of a byte stream, which we already know how to read from a connection. Today we will look at how a request and a response are built, learn to parse the start line and the headers, read a body of a given length, assemble a response, decode the address and its parameters, describe methods and statuses with enums, write the first working server, build a simple data exchange format by hand, serve files safely, and turn errors into proper response codes.\n\nA request is a few lines of text. The first line is called the start line: the method, the path with parameters, and the protocol version, separated by spaces. Then come the headers, pairs of name, colon, value, one per line. Then an empty line that separates the headers from the body, and after it an optional body. A line ends with a pair of characters, carriage return and line feed. A response is built the same way: a start line with the version, a numeric status code, and a reason phrase, then headers, an empty line, and the body. So the first exercise in server development is to cut the text at the empty line and at the line endings.\n\nA parser for the start line and the headers is ordinary work with strings and a map. The start line must contain exactly three parts, otherwise the request is considered malformed and the server replies with a client error. Each header line is split at the first colon, and the name is lowercased, because header names are case-insensitive. If there is no colon, the request is malformed as well. It is convenient to put the result into a struct with the method, the path, the version, and a table of headers. That way you get a typed request that the rest of the server code works with, instead of a raw string.\n\nThe request body is read differently. The length of the body is usually given by the content length header, and you must read exactly that many bytes, no more and no fewer: extra data belongs to the next request, and missing data we have to wait for. For this there is the exact-read method, which either fills the whole buffer or returns an error. A buffered reader over the connection gives you line-by-line reading for the headers and exact reading for the body, both from the same source without losing anything. Don't trust the length blindly: you must cap it from above, otherwise an attacker will send a header claiming gigabytes and make the server allocate that memory.\n\nA response is assembled from the same parts. The start line holds the code and the reason phrase, the headers hold the content type and the length, then comes an empty line and the body. There is a subtlety that beginners trip over: the length is counted in bytes, not in characters. The Russian word privet, which means hello, takes twelve bytes in UTF-8, and a header that says six breaks the connection: the client will read half of the body or wait for more than will ever come. The len method on a string returns exactly bytes, so in Rust it is hard to get this wrong unless you recount the length by characters. The header about closing the connection makes life easier, because the client simply reads to the end of the stream.\n\nThe request address contains parameters after the question mark: pairs of name, equals sign, value, separated by ampersands. The values are encoded: a space becomes a plus, and any other unsafe byte becomes a percent sign and two hexadecimal digits. Russian letters in UTF-8 take two bytes each, which is six characters apiece in encoded form. Decoding is a small state machine: an ordinary byte is copied, a plus becomes a space, a percent with two digits is replaced by the byte, and a broken sequence is left as it is. Once the bytes are collected, we turn them into a string, replacing invalid sequences. The parameters are conveniently stored in an ordered map.\n\nMethods and statuses are best described with enums. A method is GET, POST, PUT, or DELETE, and an unknown method turns into an empty value, to which the server replies with the status for an unsupported method. A status is an enum with numeric values for its variants: casting a variant to a number gives the code, and a separate method returns the reason phrase. This notation rules out typos like a four hundred and four without the words not found. A match forces you to handle every variant, and new codes are added in one place. It is a small example of how Rust's type system turns protocol agreements into checkable code.\n\nNow the first server. It binds to an address, accepts connections, and for each one reads the request, picks a response by the path, and sends it. To test it, in the same program we start a client: it connects, sends a request, reads the response until the connection closes, and splits it into the start line and the body. We see exactly the exchange that happens between a browser and a real server. For now the server is a single thread and serves one client at a time; we will add parallelism in the next chapter, and right now it is important to make sure that the foundation of the protocol works and can be checked with tests.\n\nThe network is not obliged to deliver a request in one piece. Data arrives in portions of arbitrary size, and the headers can be cut at any byte, including in the middle of the four-character separator. So the reading loop accumulates bytes in a buffer and, after each portion, looks for the end of the headers; once it finds it, it cuts off the headers and leaves the remainder for the body. If the connection closed too early, the request is incomplete. Be sure to set a limit on the size of the headers, for example eight kilobytes, and a read timeout: otherwise a slow client will occupy a thread forever. This is the most common cause of hanging servers.\n\nA server usually replies with data in the JSON format. Full libraries can do everything, but the principle is simple: strings are enclosed in quotes, inside them the quote, the backslash, the newline, and control characters are escaped, while numbers and booleans are written as they are. An object is pairs of key, colon, value in curly braces, separated by commas. After writing two functions, escaping and assembling an object, you will understand why libraries exist: they can parse nested structures, numbers with fractional parts, and Unicode, while a hand-made solution breaks easily on unusual data. In a real project you take a proven serialization library.\n\nA server serves files too, and here it is easy to make the most famous security mistake: directory traversal. You cannot simply glue the path from the request onto the root directory: an address containing moves to the level above will take you outside the root and open other people's files, like the system password file. The rule is simple: we split the path into components and allow only ordinary names, and any move up or an absolute root is rejected entirely. The content type is determined by the extension: page, styles, script, image. For an unknown extension you set the generic binary type, so the browser does not try to execute the data.\n\nFinally, errors. A good server turns every failure into a clear response code. A malformed request is four hundred, an unknown path is four hundred and four, an unsupported method for an existing path is four hundred and five, a body that is too large is four hundred and thirteen, and an internal error is five hundred. All of this is conveniently described by an error enum with a method that returns the code, and a validation function that returns a Result. Then the connection handler converts the error into a response in one place. An important security rule: you must not show internals to the client, such as exception messages and paths on disk. Those go to the log, and only the code and a short explanation go out.\n\nLet's sum up. HTTP is text: a start line, headers, an empty line, and a body, and line endings consist of two characters. Headers are parsed at the first colon with name normalization, and the body is read exactly by the declared length, capped from above. The length in a response is counted in bytes. Parameters are decoded from percent notation, methods and statuses are described with enums, and errors are turned into codes. Reading must survive data arriving in pieces and must have a limit and a timeout, and file serving must reject any escape from the root. In the next chapter we will add a router, shared state, and a thread pool.
