#CHAPTER 35 | Tokio: channels and synchronization
Learning Rust. Chapter 35. Tokio: channels and synchronization. Asynchronous tasks run independently, but together they solve one common problem, so they need to exchange data. There are two schools of thought. Shared memory under a lock: several tasks touch the same value, and a mutex regulates the order of access. And message passing: everyone owns their own data and sends values through channels. The Go motto says: do not communicate by sharing memory, share memory by communicating. Tokio offers both approaches. We will go through four kinds of channels, locks and semaphores, and at the end we will assemble the typical patterns out of them.\n\nThe main channel is called mpsc: multiple producers, single consumer. The channel function takes a capacity and returns a pair: a sender and a receiver. The sender can be cloned, so it can be handed out to many tasks. The send method is asynchronous: it waits if the buffer is full. The recv method is asynchronous too and returns a value, or, when the channel is closed and empty, the empty variant: nothing. A channel closes when all senders are dropped, so in a receive loop the loop ends by itself. If you drop the receiver, sending returns an error: somebody has to know that nobody is listening anymore.\n\nThe capacity of a channel is not a minor detail. If the producer is faster than the consumer, the buffer fills up, and send starts waiting until there is room. This is how a slowdown of the consumer is automatically passed on to the producer, and the system does not choke. It is called backpressure. If waiting is not an option, there is try_send: it returns an error right away when the buffer is full. The reserve method books a slot in advance and returns a permit, and sending with a permit can no longer wait. The capacity method shows how much room is left. Choose the capacity deliberately: too small slows things down, too large hides problems.\n\nThere is also an unbounded channel. Its send is not asynchronous and never waits, so it can be called even from ordinary synchronous code. You pay with memory: if the consumer falls behind, messages pile up without limit, and the process can crash. That is why unbounded channels fit where the flow of messages is known to be small or is limited from the outside, for example control commands. For data streams a bounded channel is almost always better: the limit turns overload into slowdown rather than into running out of memory. This rule is worth remembering and applying by default.\n\nThe oneshot channel carries exactly one value and then closes. The sender sends without waiting, and the receiver waits for the reply with await. If the sender is dropped without sending a value, the receiver gets an error. The main use is request and reply: you send a message to a worker task and put a oneshot sender inside it; the task computes the result and sends it back through that channel. This is how asynchronous message exchange turns into an ordinary call with a return value, and it is the foundation of the actor pattern.\n\nThe broadcast channel delivers every message to all subscribers. New subscribers are created with the subscribe method and see only what was sent after they subscribed. Messages are kept in a ring buffer of fixed capacity. If a subscriber falls behind and the buffer is overwritten, its next recv returns a Lagged error with the number of missed messages, and then continues from the oldest message that survived. Broadcast fits event distribution and the stop signal: one sender, many listeners. Values must be cloneable, because every subscriber gets its own copy.\n\nThe watch channel holds exactly one current value. The sender updates it with the send method, and subscribers read the latest value through borrow or wait for a change with the changed method. Intermediate values may be skipped: if the value changed twice while a subscriber was asleep, it will see only the last one. That is exactly what you need for configuration, state, and signals like running or stopped. Watch does not accumulate a queue, so it does not suffer from slow consumers. The watch receiver can be cloned, and all copies see the same state.\n\nWhen data really has to be shared, it is put under a mutex inside an Arc. Tokio has its own mutex, whose lock is asynchronous: a waiting task does not block the thread. Its main difference is that the guard can be held across an await. With the mutex from the standard library, such a guard cannot be sent between threads, and a future holding it cannot be launched with spawn. But the ordinary mutex is faster, so for short operations with no await inside it is the better choice. The rule: do not hold a lock while waiting if you can avoid it, otherwise other tasks will stand idle.\n\nThe RwLock allows many readers at once or a single writer. If data is read often and changed rarely, this is faster than a mutex: readers do not get in each other's way. The read method returns a guard for reading, write returns one for writing. While there are readers, the writer waits, and the other way around. Tokio watches the queue so that a writer does not starve forever because of a stream of readers. The same lock is used for caches and tables of settings. But it is more expensive to maintain, so for short critical sections with little contention a simple mutex is often just as good.\n\nA semaphore holds a number of permits. The acquire method waits until a permit is available and returns a guard: while the guard is alive, the permit is taken, and when it is dropped, the permit is returned. This is how you limit the number of simultaneous operations: no more than ten database queries, no more than a hundred open connections. The acquire_owned variant hands out a permit with ownership, which can be moved into a spawned task. The try_acquire method does not wait and immediately reports that there are no free slots. A semaphore is the simplest way to put a ceiling on the load, and it is often needed together with bounded channels.\n\nNotify is the simplest signal: one task waits with the notified method, and another wakes it with notify_one. If you wake it before the task has started waiting, the permit is remembered, and the wait returns immediately. The notify_waiters method wakes everyone who is waiting. A barrier gathers a group: each task calls wait and stays there until the given number of participants has arrived, and then they all pass at once. This is how you synchronize the stages of parallel work, for example preparation and launch. Both primitives carry only a moment in time, and the data, if it is needed, is passed separately.\n\nDurable patterns are assembled from channels. An actor is a task that owns its state and accepts commands over mpsc. All changes go through one task, so no locks are needed. To get an answer, you put a oneshot sender inside the command. A worker pool is several tasks that take work from a shared channel and put the results into another one. Taking work from a single receiver by different tasks needs a shared lock or forwarding in turn. These designs are easy to test: it is enough to send commands and read the replies.\n\nLet us sum up. Tasks communicate through channels or through shared memory under a lock. The mpsc channel carries a stream of messages, a capacity limit gives backpressure, and an unbounded channel is dangerous for memory. Oneshot returns a single reply, broadcast delivers to everyone, watch keeps the latest value. The Tokio mutex can be held across an await; the ordinary one is faster, but only for short access. The RwLock allows many readers, a semaphore limits parallelism, and notify and barrier synchronize moments in time. In the next chapter we move on to networking and asynchronous input and output.
