#CHAPTER 19 | Traits and Generics: One Piece of Code for Many Types
Learning Rust. Chapter 19. Traits and generics: one piece of code for many types. In Python a function accepts anything, as long as the object happens to have the right methods. That is duck typing, and it is checked while the program runs. If the method is missing, the program crashes on that very line, and only when execution actually gets there. Rust wants the same convenience without the surprises. Generics let you write code once for many types, and traits describe what exactly a type can do. The compiler checks that everything matches ahead of time, and then turns the general code into fast, specialized processor instructions.\n\nLet us start with generics. A function that finds the largest element of a slice should not need to know whether there are numbers or strings inside. We write it with a type parameter in angle brackets and use it in place of a concrete name. But the moment we compare two elements with a greater-than sign, the compiler stops us: comparison is not defined for every type. We have to say that any type will do as long as it can be compared, which means adding a trait bound. In Python you would see such an error only when you hit an object that cannot be compared, while here it is visible at the place of the declaration.\n\nA trait is a set of methods that a type promises to provide. The closest analogues in Python are an abstract base class and a protocol. You declare a trait with an area method, and then for each type you separately write an impl block with the implementation. The implementation lives apart from the definition of the type, so a trait can be added even to somebody else's type, for example to a number, provided that you own at least the trait or the type. This is the orphan rule. It stops two libraries from implementing the same foreign trait for the same foreign type in different ways and falling out with each other.\n\nMethods in a trait may have a default implementation. A type must write only the required methods and gets the rest for free, and it can override them if it wants. This is how an iterator works: you need just one method, next element, and map, filter, and sum come ready-made. A trait can also require another trait: to be a geometric shape, know how to print yourself. This is called a supertrait. Notice that, unlike classes, a trait has no fields and no inheritance of data. It describes behavior only, and the data stays in structs.\n\nThe standard library is built on traits. Debug and Display define printing, Clone and Copy define copying, PartialEq and Eq define equality, PartialOrd and Ord define ordering, Hash defines hashing, and Default gives a default value. Most of them are obtained with the derive attribute, and when needed they are written by hand. Operators are traits too: plus is a method of the Add trait, and square brackets are Index. Once you implement these traits for your own complex number type, you can write formulas as a plus b. There is no magic here: the compiler simply replaces the operator with a method call.\n\nHow does generic code turn into machine code? The compiler performs monomorphization: for every concrete type the function is called with, it creates a separate copy of the function with that type substituted in. If you called largest for numbers and for strings, the program will contain two functions, each optimized for its own type, and the call goes directly and can be inlined. There is no runtime overhead, as if you had copied the code by hand. The price is different: the program gets bigger, which means more pressure on the instruction cache, and the build takes longer.\n\nBounds can be written in different ways. Instead of a long list in angle brackets, you put a where block after the signature, especially when there are several bounds, which are joined with a plus. For a function argument there is a short form: impl Trait means any type that implements the trait. In a return value it lets you hide the concrete type, for example a complicated iterator, and return something iterable. Under the hood it is the same monomorphized code, you just do not say the type out loud.\n\nBut sometimes the types are not known until the program runs. A list of shapes holding circles and rectangles cannot be described with a single generic type, because the elements are different. For this there are trait objects: Box of dyn Trait. The value is stored on the heap, and on the stack there is a fat pointer of two words: the address of the data and the address of the virtual method table. The table holds the destructor function, the size, the alignment, and pointers to the methods. The call goes through the table, that is, through an indirect jump, just like calling a function through a pointer in C.\n\nThe choice between static and dynamic dispatch is a familiar trade-off. Generics are faster, because calls are direct and can be inlined, but each list holds a single type, and the code gets duplicated. Trait objects let you store values of different types and plug in plugins at runtime, at the cost of an indirect call and the inability to inline. Not every trait can be made into an object: methods must not return Self by value and must not be generic, otherwise the compiler does not know the size. Start with generics and reach for dyn when you need a mix of types.\n\nA special case is associated types. The Iterator trait declares the type of its element inside itself, and for each implementation there is exactly one. This differs from a generic parameter: a type can have only one implementation of Iterator, and you do not have to repeat the element type in signatures. Once you implement the next method for a Fibonacci struct, you get all the adapters at once. In a similar way, traits can contain constants: every shape type has a number of sides. The constant is known at compile time and takes no space in the data.\n\nStructs and enums can be generic too. You have long been using them: Option of T and Vec of T. Your own Stack of T is written the same way, and an impl block with the condition only for T that can be printed adds methods only where they make sense. A powerful technique is blanket implementations: for every type that implements Display, implement ToString. That is where the to string method comes from on numbers, strings, and your own types. The size of the type is computed anew for each parameter: a stack of numbers and a stack of strings are different types with different layouts.\n\nConversion traits have a special place. From describes how to build a type out of another one, and gives you the reverse method, into, for free. TryFrom does the same but with the possibility of an error, and FromStr lets you call the parse method for your own type. AsRef accepts anything that can be viewed as a slice or a string. The question mark operator uses From to convert errors, as we saw in the chapter about Result. Small traits like these are the language in which Rust libraries agree with each other.\n\nLet us sum up. Generics let you write code once, traits describe behavior, and bounds tie them together. Monomorphization gives speed with no overhead at the expense of program size, while dyn traits give you a mix of types at the expense of an indirect call through the virtual method table. Associated types and constants make traits more precise, and blanket implementations and conversion traits connect types with one another. The next step is closures and iterators, which are built on exactly these ideas.
