#CHAPTER 11 | Strings: str in Python and String in Rust
Learning Rust. Chapter 11. Strings: str in Python and String in Rust. You work with strings in every program, and this is exactly where the move from Python to Rust feels the biggest. In chapter six we already met the two string types. Now we will match every familiar Python operation with its Rust version, and see why some things are written differently in Rust. We will go through indexing, methods, splitting, formatting, sorting, characters and Unicode, and at the end we will talk about bytes and safety. After this chapter you will be able to rewrite any text script in Rust.\n\nLet's start with a reminder. Python has one string type: immutable, made of Unicode characters. Rust has two. The type str, usually seen as a reference, reads someone else's text and sits in function parameters. The type String owns its text and sits in struct fields and in return values. To pass a String where a str is expected, it is enough to put an ampersand in front of it. To get a String from a str, you call to_string, String from, or into. So the rule goes like this: accept a str, return a String, and inside the function work with whatever you have.\n\nLength and indexes. In Python the function len returns the number of characters, and indexing and slices also go by characters: s of zero is the first letter, s of minus one is the last. In Rust, len returns the number of bytes, direct indexing is forbidden, and slices go by byte boundaries. The first and last letters are taken with chars dot next and chars dot last. A slice on letter boundaries is safe, but a slice through the middle of a character causes a panic. To work reliably with Cyrillic you almost always need to switch to chars and count characters, not bytes.\n\nThe main methods are almost one to one. Strip becomes trim, and lstrip and rstrip become trim start and trim end. Lower and upper become to lowercase and to uppercase. Startswith and endswith become starts with and ends with. The in operator for substrings is the method contains. But there is an important difference in searching: Python's find returns minus one when the substring is missing, while Rust's find returns an Option: either Some with the position, or None. Because of this you cannot mix up not found with position minus one and accidentally reach for the last character.\n\nSplitting and joining. Split in Python becomes split in Rust, but it returns an iterator that you have to gather into a vector with the method collect. Split with no arguments, which cuts on any whitespace and drops empty pieces, corresponds to split whitespace. Splitlines is the method lines. The method rsplit cuts from the right, and split once cuts only at the first occurrence: this is exactly how you parse a key equals value line. The join, where you write the separator, dot join, and then a list, is replaced by the method join, which you call on a slice: words dot join, with a comma and a space inside.\n\nFormatting. Python's f-strings and the format method turn into the format macro, which you use exactly like println. You can write variable names right inside the curly braces, as in f-strings. The specifiers are almost the same: width, alignment, fill character, precision. A colon, then an angle bracket, then a number means right alignment, as in Python. A colon, a dot, two, and f means two digits after the decimal point. The difference is that Python checks an f-string while the program runs, and Rust checks it at compile time: a typo in a variable name will not get past the build.\n\nMutability and building strings. Python strings are immutable, and concatenating them with a plus in a loop is expensive, so experienced people collect the parts in a list and call join. A String in Rust is mutable and grows in amortized constant time, so push str in a loop is fast on its own. If you know the approximate size of the result, create the string with the method with capacity: the memory is allocated once. The method retain removes characters by a condition, clear empties the string, and insert str inserts text at a position. All of this changes the String in place and requires a declaration with mut.\n\nComparison and sorting. The comparison operators work the same way: equality by value, ordering by character codes. In Python the order follows Unicode code points, in Rust it follows UTF-8 bytes, but for these two encodings the order is the same. Uppercase letters come before lowercase ones, and Russian letters come after Latin ones. To sort strings, use the vector method sort, and for case-insensitive sorting use sort by key with the key to lowercase. There is no localized sorting like Python's locale module in the standard library: for that you need external crates.\n\nIndividual characters. Python's ord and chr turn into char as u32 and char from u32. The second one returns an Option, because not every number is a character. The checking methods are is alphabetic, is numeric, is whitespace, is uppercase and is lowercase. The differences from Python are in the details: the method is digit takes the base of the number system, and for numbers like Roman numerals and fractions is numeric returns true while is ascii digit does not. Case conversion returns an iterator, because one letter can turn into several: the German sharp s in uppercase gives double S.\n\nUnicode in more depth. For a person, a character is what you see on the screen, but for Unicode it can be several code points: a letter with an accent can be written as one character or as two, and an emoji with a skin tone is made of five. Python's len and Rust's chars count code points, not what a person sees. To count visible characters you need grapheme clusters, which the standard library does not have; they come from the crate unicode segmentation. Unicode normalization, the analog of Python's unicodedata normalize, is provided by the crate unicode normalization. You need to know this so that you do not break other people's names and texts.\n\nBytes. Python's encode and decode turn into as bytes, to vec, and String from utf8. The first returns a slice of bytes without copying, the second returns a copy as a vector. The reverse conversion returns a Result: if the bytes are not valid UTF-8, you get an error. For cases when data comes from an unknown source, there is the method from utf8 lossy, which replaces invalid sequences with a special replacement character. Encodings like Windows twelve fifty-one and KOI8-R are not in the standard library: they are handled by the crate encoding rs.\n\nString safety. In Rust any string is valid UTF-8, and this is guaranteed by the type. So decoding errors in your program are possible only at the boundary, in the places where bytes are turned into a string. Slices that land in the middle of a character are caught by a panic, not by corrupted data. For file names and paths, which in operating systems may not be Unicode, there are separate types, OsString and Path: they do not promise validity, so before printing you have to convert them explicitly. This separation saves you from hidden bugs.\n\nHere are the takeaways of this comparison. Len counts bytes, not characters. There is no indexing, and slices are careful. Find returns an Option. Split returns an iterator that has to be collected. A string is built quickly with push str and with capacity, not with join. F-strings are checked at build time. Unicode means code points, and graphemes need a separate crate. All this makes working with text in Rust strict, but predictable and very fast. In the next chapter we will compare Python lists with Rust arrays and vectors: they have a lot in common, but there are enough differences too.
