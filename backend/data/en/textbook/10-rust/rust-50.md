#CHAPTER 50 | WebSocket: real-time messages
Learning Rust. Chapter 50. WebSocket: real-time messages. Request and response is fine for history, but a chat needs a message to show up for the other people at once, without them asking again. For that, the client and the server keep a persistent two-way connection, and the server sends events on its own. In this chapter we plug WebSockets into our application: we will learn to accept connections, hand messages out to a room's subscribers, cope with slow clients, watch whether a connection is alive, and reconcile the fast path with the reliable history in the database.\n\nA WebSocket begins as an ordinary request: the client asks to switch to another protocol with an Upgrade header, and the server answers with status one hundred and one. After that, frames flow over the same connection. Frames can be text or binary, there are the service frames ping and pong for checking that the other side is alive, and a close frame with a reason code. Frames from the client are masked, which protects proxies. Messages are not tied to requests: either side can send at any moment. Because of that, the server itself is responsible for ordering, limits, and what happens when connections drop.\n\nIn Axum, the upgrade is an ordinary extractor. The handler takes a WebSocketUpgrade, calls the on-upgrade method, and passes it a function that receives the ready socket. You then read from the socket with the recv method and write with the send method, and a message is an enum: text, binary data, ping, pong, close. The library answers pings by itself. The function runs in a separate Tokio task for the whole life of the connection. Authorization has to happen before the upgrade: refusing an ordinary request is simpler and more correct than closing a connection that is already established.\n\nA single connection usually needs two independent activities: reading the client's commands and writing events to it. The socket is split into two halves, and each runs in its own task. The reading one receives the client's messages, the writing one listens to an event channel and sends. When either task finishes, the other has to be stopped too, using select or cancellation. Otherwise an orphan task is left behind, holding memory and a subscription. Splitting requires the stream and sink extensions from the futures library.\n\nLet's call the shared state for fan-out a hub. For each room it holds a broadcast channel: the sender is stored in a map under a shared lock. The channel is created lazily on first use. Subscribing means getting a new receiver, and publishing means sending into the channel. The lock is held briefly and never across an await. Rooms that have emptied are cleaned up from time to time, otherwise the map grows forever. The hub is the one place that knows who hands what to whom, and that makes testing easier: you can check it without a network.\n\nOn top of the WebSocket we need our own small protocol. Let's agree that every message is JSON with a field called type. From the client come commands: subscribe to a room, send text, report typing. From the server come events: new message, joined, left, typing, error. The format is described by an enum with an internal tag, as we learned in the chapter on serde. Unknown commands and broken JSON must not bring the connection down: the server replies with an error event and keeps waiting. The message size is limited, otherwise a client could take up all the memory.\n\nA connection has to know who is on the other end. A browser does not let you set a header when connecting, so the token is passed as a URL parameter or in the first message. The first option is checked before the upgrade and is therefore cleaner, but the token ends up in logs, so it is made single-use and short-lived. Subscribing to a room checks membership in the database, otherwise anyone could subscribe to other people's messages. Membership can be revoked while the connection is open: when someone is removed, the subscription must be closed. The user's identifier comes only from the session, never from the client's messages.\n\nThe Tokio broadcast channel hands every event to all subscribers. Sending returns the number of receivers, and if there are none, an error that a chat can safely ignore. The channel is bounded: if a receiver falls behind, old events are pushed out, and on its next read it gets a Lagged error with the number of events it missed. The message is cloned for each receiver, so it is cheap to keep an event in an Arc or as a string. The server does not wait for the slowest, so one lagging client does not slow down the rest, but it must learn about the loss and recover.\n\nFor a chat, losing events silently is unacceptable. If a receiver reports that it has fallen behind, the server tells the client: you missed something, catch up. The client makes a request for everything after the last number it knows and gets the missing messages from the database. This is the very same catch-up mode from the previous chapter. If a client lags all the time, it is disconnected so as not to waste resources. Each connection's outgoing queue is bounded: an unbounded buffer turns one slow client into a memory leak for the whole server. Buffer limits are a mandatory part of any network code.\n\nConnections die silently: a phone loses its network, and the server never receives a close. So the server periodically sends a ping and waits for any activity. If the client is silent for longer than the timeout, the connection is closed. On any ending, clean or not, cleanup runs: subscriptions are dropped, a leave event is broadcast, presence is updated. A user's presence is a counter of their active connections: they are offline only when the counter reaches zero. Cleanup is reliably tied to the end of the task, not to successfully reading the last message.\n\nBroadcasting is the fast path, and the database is the source of truth. The order of actions is this: first the message is written to the database and gets a number, then the event goes out to subscribers. That way a client that received an event will always find it in the history too. Delivery works on the at-least-once principle: after reconnecting, a client may get a message both over the socket and from the catch-up request, so duplicates are dropped by number. If there are several servers, events are passed between them by the database through notifications, or by a message broker.\n\nWebSockets are tested with a real client. The server starts on port zero, the address is taken from the socket, and the clients are created by the tokio-tungstenite library. The main rule of tests with waiting is a timeout on every read: a test that waits forever is worse than a failed one. The order of events between different clients is not guaranteed, so you compare sets or sorted lists. The hub's logic is checked without a network, by plain calls, and the socket itself with a few short scenarios: subscribe, fan-out, refusal without a token, close.\n\nLet's sum up. A WebSocket is a persistent two-way connection that begins by upgrading an ordinary request. In Axum it is expressed as an extractor, and the socket is split into reading and writing. The hub keeps a broadcast channel per room, and the events are JSON with a type field. Authorization and membership are checked before subscribing, slow clients learn about losses and catch up on history, and connections are checked with pings and always cleaned up. Database first, then fan-out. In the last chapter we will put everything together: startup, shutdown, logs and tests of the finished service.
