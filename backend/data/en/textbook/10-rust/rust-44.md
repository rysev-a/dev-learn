#CHAPTER 44 | Axum: routes, handlers, and extractors
Learning Rust. Chapter 44. Axum: routes, handlers, and extractors. We have reached the final project of the book: a chat. It will have users, rooms, message history, and live delivery over WebSockets. The stack is this: Tokio under the hood, Axum as the web framework, SQLx for the database, and Serde for the data. Until now we wrote servers on bare sockets and parsed request bytes by hand. Now we take a ready-made framework, but because we know how it works from the bottom up, we will understand what it does for us.\n\nAxum is a thin layer over Hyper and Tower. Hyper parses the protocol. Tower defines the common interface of a service: take a request and asynchronously return a response. The router in Axum is a table of routes that is itself such a service. A handler is an ordinary async function, and the framework wraps it into a service. So everything Tower can do, such as layers, timeouts, and load limits, works here too. Axum hardly introduces any concepts of its own: it assembles existing building blocks into a convenient interface.\n\nA route connects a path to handlers by method: get, post, put, delete. Path parameters are written in curly braces: the name goes inside, and an asterisk before the name captures the whole remainder. One path can accept several methods, and you chain them one after another. If the path is found but the method doesn't fit, Axum itself answers with code four oh five and lists the allowed methods. If the path isn't found, it answers four oh four, and a fallback handler defines your own response for that case. The order in which you register routes doesn't matter: matching goes through a tree, not a list.\n\nA handler is an async function. Its arguments are extractors, which pull what's needed out of the request: path parameters, the query string, the body, the shared state. The return value is anything that can be turned into a response. The framework checks at compile time that the function fits: all arguments are extractors, the future can be moved between threads, and the response can be converted. If even one condition is broken, the compiler gives a long and confusing error about an unimplemented trait, and later we will learn to read it.\n\nAn extractor is a type that knows how to build itself from a request. The most common ones are the path, the query string, JSON from the body, the shared state, and headers. They come in two kinds. Some read only the headers and the address, so you can put them in any order. Others take the request body, which can be read only once, so such an extractor is allowed only as the last argument. If an extractor fails, the handler is not called: the framework immediately answers with a rejection and a suitable code. Parsing errors turn into responses without any work from you.\n\nPath parameters are parsed by the Path extractor: you can take a single type, a tuple, or a struct with fields matched by name. The query string is handled by the Query extractor: a struct with optional fields, using Option, and default values. All of this works through Serde, so the types check the format in advance: a number in the id field can't turn out to be a word. If parsing fails, the client gets a four hundred for the path and the query string, along with a message explaining why. It makes sense to describe parameters with separate structs: that way the allowed fields and their types are visible.\n\nAny response is a type with the IntoResponse trait. It is implemented for strings, bytes, status codes, JSON, web pages, and redirects. Tuples are especially handy: a status and a body, or a status, headers, and a body, and the framework assembles the response itself. For example, a pair of the Created code and JSON gives a two hundred one, with a body in JSON format. You can also return a Result: both Ok and Err must be able to turn into a response. This is the basis of error handling, which we will come back to: any application error can be taught to turn into a response.\n\nA good server returns precise codes. Two hundred is success with a body. Two oh one is created, and the Location header usually holds the address of the new resource. Two oh four is success with no body, for example after a deletion. Four oh four means the resource doesn't exist, four oh nine is a conflict, for example when a name is taken, and four twenty-two means the body is understood but the data isn't acceptable. Headers are set as a pair of a name and a value. A HEAD request is handled by Axum itself: it calls the GET handler and drops the body, and for an unsuitable method it answers four oh five.\n\nA large application is convenient to split into modules. Each one returns its own router: users, rooms, messages. The nest method mounts a router under a prefix, so paths inside the module are written from the module's own root. The merge method simply joins routers at the same level. A fallback handler answers everything that wasn't found, and you can set it separately for a nested router. This gives a clean hierarchy: the root function assembles the modules like a constructor. Tests are built by module too: the router of each one is checked separately, without starting the whole application.\n\nStarting the server takes three lines. We bind a listening socket, pass it together with the router to the serve function, and wait. If you specify port zero, the system picks a free one, and you can ask the socket for the real address. This is what people do in tests so they don't collide over ports. The server runs in a Tokio task and serves each connection in its own task. Graceful shutdown plugs into the same call, and we will cover it in the last chapter. For now, what matters is that the server is just a task, not a separate process with magic.\n\nSince the router is a service, you can call it directly, without a network. The ServiceExt extension from Tower gives a method called oneshot: it takes a request built by the request builder and returns a response. The body is read with the to_bytes function, with a size limit. You need no sockets and no ports, the test is fast and stable, and the request goes through the very same routes, extractors, and layers. When needed, you clone the router: it is cheap, because inside it holds reference counters. The whole rest of the chapter is checked exactly this way: we build a router, send a request, and compare the code and the body.\n\nThe most famous error is that a handler doesn't implement the required trait. There are usually four causes. Inside the function, a value that can't be passed between threads is held across an await, for example an ordinary lock guard. A body-reading extractor is not the last one. State was requested, but nobody gave the router state with the with_state call. Or an extractor doesn't implement the needed trait for the given type. The debug_handler attribute tells you more precisely which argument to blame. And remember one more thing: since version zero point eight, path parameters are written in curly braces, and the colon no longer works.\n\nLet's sum up. Axum is a thin layer over Hyper and Tower. The router connects paths and methods to handlers and is itself a service. A handler is an async function whose arguments are extractors and whose result is anything that turns into a response. The body is read once, and only by the last extractor. Modules are assembled with the nest and merge methods. The server starts through a listening socket and the serve function, and in tests the router is called directly through oneshot. The chat skeleton, a health check and a list of rooms, is already ready. In the next chapter we will add application state and layers.
