#CHAPTER 38 | Algorithms in Rust
Learning Rust. Chapter 38. Algorithms in Rust. We have learned the language, and now we start to apply it, and the first thing we will apply it to is the algorithms course. Everything you know about binary search, sorting, heaps, graphs and dynamic programming carries over to Rust almost one to one, but every problem makes you look anew at ownership, slices and numeric types. We will write one implementation of each basic algorithm, see how slices and generic types make them universal, how the standard collections replace hand-made structures, and go through the main traps of unsigned integers, which show up in algorithms at every step. The complexity of the algorithms stays the same, but the safety and speed of Rust are especially pleasant on large inputs.\n\nLet's begin with the habit of counting operations. To avoid guessing how fast an algorithm is, add a counter to it: a mutable reference to a number that grows with every comparison. A linear search over a thousand elements will do a thousand comparisons in the worst case, and the counter will show it. This approach makes complexity tangible and suits tests well: instead of measuring time, which depends on the machine, we check the number of operations. Real time measurements are done with separate tools and only on an optimized build, since a debug build is tens of times slower.\n\nBinary search looks for a value in a sorted slice by halving the range. The Rust version is generic: all it needs is for the type to be comparable, and it works with numbers, strings and any custom types. The range is kept as a pair of bounds, the middle is computed as an offset from the lower bound rather than as the average of two numbers, and this protects against overflow. The comparison returns an enumeration with three variants, and the match covers all of them. For a thousand elements, no more than ten steps are enough. The standard library already has such a method, and real code uses it, but writing it yourself is useful for understanding the boundaries.\n\nInsertion sort is convenient to write on a mutable slice. The function takes a reference to a slice of any type whose elements can be compared, and swaps neighboring elements with the swap method while they are in the wrong order. There is no need to copy values, so it works with strings too, where copying is expensive. The algorithm is quadratic and good only for small arrays, but it is the easiest to understand, and the standard sort uses exactly it inside for short pieces. Notice that a slice can at the same time be part of a vector, an array or another slice: the function does not care.\n\nMerge sort shows the power of slices. The split at method divides a slice into two halves without copying, both are sorted recursively, and then they are merged into a new vector with two pointers. The cost is linear memory and a logarithmic number of recursion levels, which gives n log n in total. The merge keeps the order of equal elements, that is, it is stable. Quicksort can be written in place by splitting a slice into mutable parts, and the compiler makes sure the two halves do not overlap. The standard sort is already efficient and stable, so in real projects hand-written versions are needed only for learning.\n\nA heap, the binary heap, is needed when you must always know the largest or the smallest element. In the standard library it is implemented by the BinaryHeap structure: the maximum element is on top. To get a min-heap, you wrap the elements in Reverse, which flips the order of comparison. The classic problem is the k largest: we keep a heap of the k smallest of those already seen, and when it overflows, we throw out the minimum. The algorithm runs in n log k and does not need to store the whole stream. The same heaps underlie task schedulers and shortest path search.\n\nHash tables and sets solve the problems of whether something was seen, how many times, and grouping. Two strings are made of the same letters if their sorted letters match, so the sorted letters serve as a key: all the anagram words pile up in the table under it. The entry method lets you insert or change a value in a single step, without a double lookup. The iteration order of a hash table is not defined, so to get reproducible output you sort the result. If you need the keys in order out of the box, you take the BTreeMap, which keeps them sorted at logarithmic cost.\n\nA graph is conveniently stored as an adjacency list: a vector of vectors, where the vertex number gives the list of its neighbors. Breadth-first search uses the queue from the standard library: we take a vertex, go over its neighbors, and for those not yet visited we record a distance one greater. The array of distances holds an Option: an empty value means the vertex is unreachable. This gives us shortest paths in an unweighted graph and a connectivity check, and also a path search in a maze if we treat the cells of the grid as vertices. Ownership does not get in the way here: the graph lives in one vector, and the vertices are just indices.\n\nShortest paths in a weighted graph are found by Dijkstra's algorithm. It takes from the heap the vertex with the smallest known distance and tries to improve the distances to its neighbors. The heap stores pairs of a distance and a vertex wrapped in Reverse, so that the smallest floats to the top. Stale entries left in the heap after an improvement are simply skipped when they are extracted. The weights are natural numbers, so an unsigned type fits, and infinity is the maximum value of the type. It is important to add a weight only to a distance that is not infinity, otherwise an overflow will happen.\n\nDynamic programming in Rust means tables made of vectors. The longest common subsequence of two strings is computed from a table in which every cell depends on three neighbors. Storing the whole table is not necessary: two rows are enough, the current and the previous, and the memory drops from the product of the lengths to a single length. Strings are first turned into vectors of characters, because you cannot index a string by character number: its Unicode bytes have different widths. The same techniques work for the knapsack, the edit distance and dozens of other problems.\n\nThe disjoint set union answers the question of whether two vertices are in the same component in almost constant time. Every element has a parent, and the root points to itself. Finding the root compresses the path: all the vertices passed are redirected straight to the root. Union hangs the smaller tree under the larger one. This structure underlies Kruskal's algorithm for the minimum spanning tree: the edges are sorted by weight, and an edge is taken if its ends are still in different components. The mem swap function exchanges two values without copying, and comes in handy when you need to put a pair in order.\n\nFinally, the traps of integers. The usize type, on which indices are built, has no sign, and subtracting a larger number from a smaller one leads to a panic in a debug build and to a huge value in a release build. Do not rely on the behavior at overflow: choose an explicit variant. Checked subtraction returns an Option, saturating stops at zero, wrapping counts modulo, and overflowing returns a pair of the result and a flag. The average of two large numbers can overflow too, so there is a ready-made method, midpoint. These variants are needed in algorithms all the time, especially in sorting and searching.\n\nLet's sum up. The algorithms of the course carry over to Rust with small adjustments: slices replace start and end indices, generic functions replace copies for each type, standard collections replace hand-made structures. Binary search and sorting work on slices without copying, the heap gives the k largest and priority queues, hash tables group, the queue gives breadth-first search, and the heap with the queue gives Dijkstra. Dynamic programming keeps tables in vectors, and the disjoint set union answers about connectivity. Unsigned numbers require an explicit choice of operation. In the next chapter we will go lower: to bits, bytes and the machine representation of data.
