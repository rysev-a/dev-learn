#CHAPTER 31 | Future, Poll and Waker: how it works under the hood
Learning Rust. Chapter 31. Future, Poll and Waker: how it works under the hood. To write asynchronous code with confidence and to debug its errors, it helps to build the machinery with your own hands once. In this chapter we write our own futures, our own waker, a simple executor and a timer. None of this needs Tokio or any other crate: everything we need lives in the standard library, in the future and task modules. They are tiny: one trait, two types and a few helpers. But after this chapter the words async and await will stop being magic and become understandable state-machine mechanics.\n\nThe foundation is the Future trait. It has one associated type, Output, and one method, poll. The method takes a pinned mutable reference to self and a mutable reference to a Context, and returns Poll of Output. The executor calls poll, and poll never blocks: either the value is ready, or it is not. For now, read Pin as a value that will not be moved in memory; more on that in the next chapter. The Context carries the waker. And Poll is an enum with two variants: Ready, which holds the finished value, and Pending, which means not ready yet, come back later.\n\nWhat does come back later mean? If a future returns Pending, the executor sets it aside and will not call poll again until the future itself says there is something to check. There is only one way to say that: call the waker from the context. The rule is strict: before returning Pending, a future must make sure that somebody, someday, calls wake. That could be the operating system's event machinery, another thread, a timer, or the future itself, calling wake by ref just before returning so that it is polled again right away. A forgotten wake is the most common mistake: the task hangs forever, with no error message.\n\nThe waker is a client-side handle to a task: you can clone it, send it to another thread and call it. Inside, it holds a pointer to some data and a table of four functions: clone, wake by value, wake by reference, and drop. Building that table by hand through RawWaker is unsafe, so the standard library offers a convenient trait called Wake: just implement the wake method for a value inside an Arc, and Waker from Arc builds a ready-made waker. For tests there is the noop waker. Calling it does nothing, and it is fine when you poll the future in a loop yourself.\n\nLet's write the simplest futures. Ready of T keeps a value inside an Option: on the first poll it takes the value out and returns Ready. YieldOnce, on the first poll, calls wake by ref and returns Pending; on the second poll it returns Ready with an empty tuple. That is the analogue of handing control back to the event loop. CountDown counts a number of polls. All three are just structs with one field and an implementation of the trait. Your own async code is turned by the compiler into exactly such structs, only more complex and generated automatically. So understanding a small hand-written future means understanding the big ones too.\n\nAn executor starts with a function called block on: it takes a future and keeps polling it until it finishes. The simple version is a loop that calls poll with a noop waker, and if the result is Pending, the loop goes on and burns the processor. It is better to put the thread to sleep. You make a waker that wakes this thread with the unpark method, and after a Pending the loop calls park. Then the thread sleeps until somebody calls wake. This is how block on from the futures crate works. Note the protection against spurious wakeups: park can return without any wake, so after waking up you simply call poll again, which is harmless.\n\nA timer is a real example of an event. On its first poll, the delay future spawns a thread that sleeps for the required time, sets a flag in shared state under a mutex, and calls wake. On every poll the future checks the flag: if it is set, it returns Ready; if not, it remembers the freshest waker from the context and returns Pending. You must remember the new waker on every poll, because the task may have been handed to a different executor. Sockets in Tokio work the same way, except that instead of a thread, the event comes from the operating system through epoll or kqueue, and a special driver calls the wakers.\n\nCombinators are simple too. Map wraps a future and a function: when polled, it polls the inner future and, once that is ready, applies the function. Join holds two futures and two places for results, and polls both until it has both values. Select returns the result of whichever is ready first. Structs with future fields need a pin projection, which you write with unsafe code or with the pin-project crate. We will keep it simple: we limit ourselves to futures that can be moved, and wrap them in a pinned box. The result works just like gather and wait-first in asyncio, except that all the logic is in plain sight.\n\nAn executor with a queue is the next step. Each task is a boxed future wrapped in an Arc, plus a channel into which it puts itself when woken. Spawn creates a task and puts it in the queue. The executor loop takes a task from the queue, makes a waker that puts the task back when called, and calls poll. If the task is ready, it is dropped; if not, it lies there until somebody wakes it. When the queue is empty and there are no tasks left, the executor finishes. These hundred or so lines are the core of any runtime, and Tokio adds threads, work stealing, timers, sockets and a large set of primitives on top.\n\nNow, how the compiler turns async into a state machine. A function with two await points becomes an enum with three states: start, waiting for the first, and waiting for the second, plus a finished state. Each state stores only the variables that are needed after that point. The poll method contains a loop with a match on the state: it polls the current inner future; on Pending it returns Pending and stays in the same state; on Ready it moves to the next one. That is why await is not a call but a point of possible suspension, and why the size of a future equals the largest of its states. You can check this with the size of val function on an async block.\n\nTypical pitfalls. First: Pending without a wake, that is, a hung task. Second: a wake inside poll that triggers an immediate re-poll forever. That is fine for a yield, but not for waiting on an event. Third: polling after Ready, which the contract allows to do anything, including panic, so you wrap the future in a fuse. Fourth: a blocking call inside poll, which freezes the executor. Fifth: a lost waker, where a stale one is stored. Sixth: a race between setting the event and saving the waker, which you solve with a mutex that protects the flag and the waker together. Knowing these pitfalls saves hours of debugging in real code.\n\nHow all of this works in real runtimes. Tokio consists of an I/O driver built on mio, using epoll, kqueue or io_uring, a timer wheel, a pool of worker threads with queues and work stealing, and a set of synchronization primitives. When a socket is registered, it gets a token, and when epoll reports readiness, the driver finds the entry and calls the task's waker. Timers work similarly: a hierarchical wheel stores delays by firing time. Python's asyncio is built the same way, only with a single thread and a selector. The only difference is where the state machine lives and who polls it.\n\nLet's sum up. A future is a trait with a poll method that returns Ready or Pending. Before returning Pending, you must arrange a future wake. A waker is a task handle, built from an Arc with the Wake trait. Block on spins a future and puts the thread to sleep. A timer brings a task back to life from another thread. Combinators and an executor with a queue are tens of lines each. Async compiles into a finite state machine. In the next chapter we look at exactly that compilation in detail: what Pin is, why it is needed, how references inside a state machine work, and how to write async code without mistakes.
