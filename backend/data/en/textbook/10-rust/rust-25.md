#CHAPTER 25 | Standard library collections: Vec, VecDeque, HashMap, BTreeMap, BinaryHeap
Learning Rust. Chapter 25. Standard library collections: the vector, the deque, the hash map, the tree and the heap. In the Python chapters we used the vector and the hash map without looking inside. Now let's open them up: how each collection stores its data, what its operations cost, and when to pick which one. The standard library has eight collections: the vector, the deque, the linked list, the hash map, the ordered map, the two sets and the binary heap. The main rule for choosing is this: start with a vector, and move to something else only when measurements or the logic of the task show that you need to. Most programs get by with a vector and a hash map.\n\nA vector stores three values: a pointer to the heap, a length and a capacity. The elements lie one after another, so walking over them is fast: the processor pulls the neighboring data into the cache ahead of time. Adding to the end costs amortized constant time: once in a while the memory doubles, with a copy. Inserting and removing in the middle shifts the tail and costs linear time. If the order does not matter, swap remove deletes in constant time by putting the last element in place of the removed one. The methods truncate, drain, split off and extend manage the length, and retain and dedup clean up by a condition.\n\nSlices are what you use most often when you work with vectors and arrays. A slice is a pointer and a length, and it has a great many methods: windows and chunks for sliding windows and batches, split on a separator, first and split first for the head and the tail, concat and join for gluing together, contains and starts with for searching. The method rotate left shifts the elements around a circle, fill fills with a value, copy from slice copies without allocations, and swap exchanges two elements. For sorting there is sort, which is stable, and sort unstable, which is faster but does not guarantee the order of equal elements. Binary search looks in a sorted slice in logarithmic time.\n\nThe deque, or VecDeque, is a ring buffer. The data sits in a single block of memory, but the start can be anywhere in it, so adding and removing at both ends costs constant time. Indexing works like in a vector, and the order of traversal is preserved. The price of this flexibility is that the elements do not necessarily lie in one piece: as slices returns two slices, and make contiguous moves everything into one. Use the deque for queues and sliding windows: add at the end, take from the start. For stacks a vector is enough. The deque also has rotate, retain and drain, so in its abilities it is similar to the vector.\n\nThe hash map in the standard library is built on the Swiss table, which was designed by the Google team and implemented by the crate hashbrown. It keeps the hash tags separately from the pairs and compares sixteen tags at a time with vector instructions. That is why lookup is faster than in classic chained tables. Operations cost constant time on average, and when the table fills up, it doubles and rehashes everything. The methods reserve and with capacity save you from extra rehashing. The method retain removes pairs by a condition, drain hands out and clears, and extend adds many pairs. The traversal order depends on the hash and on a random salt.\n\nA HashSet is a hash map without values, and it inherits all of its properties. Lookup, insertion and removal take constant time on average. The operations on sets return iterators: union, intersection, difference and symmetric difference. The predicates is subset, is superset and is disjoint answer the questions: is it included, does it contain, do they not overlap. Retain keeps only the elements you need, and the method take pulls an element out and removes it. Use a set when only membership matters: duplicates, visited vertices of a graph, a dictionary of unique words. For the ordered variant there is BTreeSet, with the same set of operations.\n\nBTreeMap is an ordered map based on a B-tree, in which every node holds up to eleven keys. Such a node fits into a few cache lines, so traversal and lookup work nicely with memory. Operations cost logarithmic time. The data is always traversed in ascending order of keys. The methods first key value and last key value, pop first and pop last take the extreme entries. Range returns the pairs within a range of keys, and split off cuts the tree at a key. Take a BTreeMap when you need order, range queries or predictable output. If you do not need order, take a hash map.\n\nBinaryHeap is the binary heap. It is a vector in which the elements are arranged so that every parent is at least as large as its children, so the largest one is always at the start. Push and pop cost logarithmic time, and peek costs constant time. Building a heap from a ready vector with from takes linear time, and into sorted vec returns a sorted vector. By default the heap is a max-heap; to get a min-heap, you wrap the elements in Reverse. The heap is the basis of Dijkstra's algorithm, of task schedulers and of finding the k largest values. You cannot change the priority of an element that is already inserted, so such tasks are solved by adding a new entry.\n\nLinkedList is a doubly linked list, and it does exist among the Rust collections, but you almost never need it. The elements are scattered over the heap, so traversal suffers cache misses, and even insertion in the middle, which is formally constant, is slower than in a vector in practice. The only advantages are cutting and gluing lists in constant time, and adding and removing at both ends without reallocating memory. But even for that a deque usually fits better. The documentation of the standard library directly recommends a vector and a deque instead of a list. So when an interview asks about something like a linked list, what they expect from you is a reminder about the cost of caches.\n\nAll the collections work the same way. Each one has the method iter for reading, iter mut for changing, and into iter for taking ownership. The traits IntoIterator and FromIterator are implemented for them, so collect can build any of them. The method extend accepts any iterator. Collect can build more than a vector: a hash map, a string, a Result with all the values or with an error, an Option with all the values or with nothing. The method drain takes elements out by a range and frees the space. This uniformity means that code written for one collection is easy to move to another: it is enough to change the type.\n\nThe complexity of operations. Vector: access by index and adding to the end are constant, insertion in the middle is linear. Deque: adding and removing at both ends is constant. Hash map and set: insertion, lookup and removal are constant on average. BTree: logarithmic. Heap: adding and removing the largest is logarithmic, peeking is constant. List: adding and removing at the ends is constant, search is linear. But one constant is not another: in practice a vector beats all the others while the data is smaller than a few thousand elements, thanks to the cache. So measure on real data instead of judging by the table.\n\nOutside the standard library there are useful collections too. The crate indexmap keeps the insertion order, like a Python dictionary. SmallVec holds a few elements right on the stack and moves to the heap only when there are too many. ArrayVec is a vector with a fixed capacity on the stack. Slab and slotmap hand out numeric identifiers for objects, which is convenient for graphs and game entities. BitVec stores bits, and smol str stores short strings. For parallel access to a map there is DashMap. You plug them in through Cargo. Start with the standard library, and bring in external structures when measurements have proven their value.\n\nLet's sum up. The vector is the default choice, the deque is for queues, the hash map and hash set are for fast lookup, BTree is for order and ranges, the heap is for priorities, and the linked list is almost never. The complexities point you in a direction, but the cache decides in practice. All the collections share a common interface of iterators and collect. External crates cover what the standard library lacks.
