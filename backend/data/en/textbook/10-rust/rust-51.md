#CHAPTER 51 | A production-ready service: startup, shutdown, logging, and tests
Learning Rust. Chapter 51. A production-ready service: startup, shutdown, logging, and tests. The chat works, but between working code and a service you can leave running overnight lies a set of mandatory things. Configuration that is validated at startup. Logs that tell you what happened. Graceful shutdown with no lost requests. A reaction to failures and overload. Tests at several levels. And finally, packaging and running in a container. This chapter pulls everything together into one project and closes the book: from your first program with a variable to a service ready for production.\n\nGood structure starts with separation. All the logic lives in a library crate, and the entry file is thin: it reads the configuration, builds the application, and starts the server. That way the tests call the very same application-building function as the real launch. Modules are split by meaning: configuration, database, users, rooms, messages, WebSockets. Errors and state live separately. Integration tests live in the tests directory and see only the public interface. If the project grows, you split it into crates of a workspace without changing the module boundaries.\n\nConfiguration is environment variables and, if you like, command-line arguments. The main principle is to fail fast: at startup we read everything, check types and ranges, collect all the errors into one list, and exit with a clear message, instead of discovering a wrong database address an hour later. Optional values get sensible defaults. The priority is this: arguments beat the environment, the environment beats the file, and the file beats the defaults. Secrets never reach the log: for types that hold passwords, the debug output hides the value, and connection strings are printed without the password.\n\nThe log is the main tool for investigating incidents. In Rust there is the tracing library for this. Events have a level and structured fields: not a glued-together string, but key-value pairs that you can search and aggregate. A span sets the context for the duration of a request: an identifier, a path, a user, and every record inside automatically carries it. The level filter is set with a string: info by default, and warnings only for noisy libraries. The log is written to standard output, and collecting, storing, and searching it is the job of the infrastructure, not of the application itself.\n\nAn orchestrator needs to ask two questions. Is the process alive: the answer to the health check must be instant and must not depend on external systems, otherwise a temporary database failure will restart perfectly healthy instances. And is it ready to accept traffic: the readiness check really does query the database and answers 503 while anything is unavailable. Metrics are useful alongside: the number of requests by path and status code, latencies, the pool size. They are served in a simple text format that a monitoring system understands.\n\nContainers are stopped with the termination signal, and only a limited time is given for a graceful exit. The right order is this. Stop accepting new connections. Wait for the current requests to finish. Ask the WebSockets to close with a going-away code. Close the database pool. Exit. In Axum, the serve call has a graceful shutdown method for this: you pass it a future that completes on a signal. If the requests did not finish in the allotted time, the process is terminated forcibly, and that is written to the log.\n\nFailures are inevitable, so every wait is bounded. A database query has a maximum execution time on the server side. Getting a connection from the pool has a wait after which the client gets a 503 instead of hanging forever. An incoming request has an overall timeout set by a layer. Concurrency is limited by a layer, so that overload turns into a fast rejection rather than growing queues. Retries are allowed only for safe operations and with a growing pause. A circuit breaker stops sending requests to a place where everything is bad.\n\nA panic is a bug, not a way to handle errors. For expected situations you use results. But even in flawless code something unforeseen can happen, and a single panic must not drop connections. So at the boundary you put a layer that catches the panic in the handler's future: it writes it to the log together with the request identifier and answers 500. The service keeps running. Locks from the standard library become poisoned after a panic, and you have to take that into account: either do not panic while holding a lock, or handle the poisoning deliberately.\n\nTests come in several levels. Unit tests check pure logic: parsing, validation, calculation. Integration tests build the application and send requests without a network through oneshot, but with a real database: a schema is created for each test separately, so the tests do not interfere with each other and run in parallel. End-to-end tests start a real server on a free port and walk through a user scenario, including a WebSocket. There are few of them, but they catch the integration of the layers. Every wait in tests is bounded by a timeout, and time and randomness are replaced.\n\nThe service is packaged into a container. A multi-stage build: on the first stage the compiler builds the release binary, and on the second you take a small image with just that one binary. Dependencies are cached in a separate layer, so a rebuild does not download the whole registry again. The process runs as an unprivileged user. A health check is added to the image. Configuration comes from the environment, not from files inside the image, and secrets come from the orchestrator's secret store. Migrations are run at startup or as a separate job before the rollout, but never by hand.\n\nDuring a rollout, old and new instances work with the same database for a while, so the schema is changed in a compatible way. First you expand: add an optional column, a new table, an index that does not block writes. Then you deploy code that writes to both places. Then you move the data and switch the reads. And only then do you contract: remove the old. Dangerous operations are dropping a column, adding a required column with no default value, and creating an ordinary index on a big table. Backups are verified by restoring them: a backup you have never tried to deploy is just a hope.\n\nWhat can you add to the chat next? An interface description in the OpenAPI format and generated clients. Load tests that show how many connections and messages per second one instance can take. Distributed request tracing across several services. A cache for hot data and a queue for background jobs, for example sending notifications. Horizontal scaling: several instances behind a load balancer, with events passed between them through the database or a broker. All of these topics continue what you already know, and they will be covered in the system design course.\n\nLet's sum up the chapter and the whole book. The service consists of a thin entry point and a library, the configuration is validated at startup, the logs are structured, health and readiness are checked separately, shutdown is graceful, and failures are bounded by timeouts and limits. Tests come at several levels, the image is built in several stages, and the schema changes compatibly. You have come all the way from the first variable and the ownership rules, through traits, asynchrony, networking, the database, and users, to a live chat. Now you can design whole systems, and that is what the next book of the course is about: system design.
