#CHAPTER 46 | JSON, serde, and a Single Error Type
Learning Rust. Chapter 46. JSON, serde, and a single error type. Our chat talks to clients over JSON. To make that reliable, we need two things. First, precise data types: a request is parsed into a struct, and anything invalid is rejected at the door. Second, a single error format: the client must understand what went wrong in the same way, whether it is a missing room, a taken name, or a database failure. In this chapter we will build both layers: the request and response types, and one enum of errors for the whole application.\n\nSerde is the common serialization library. It separates the data structure from the format: a struct declares that it can be turned into data and built back from it, while the format, whether JSON, YAML, or binary, is implemented separately. For structs, two derived traits are enough: Serialize and Deserialize. After that, serde JSON turns a value into a string and back. Parsing is strict: it will not forgive a wrong type or a missing required field, and it returns an error with a position. This is the foundation of a safe system boundary: only data of the expected shape gets inside.\n\nBehavior is tuned with attributes. Renaming all fields to camel case is needed for JavaScript clients. A default value lets the client omit a field. Skipping empty values makes the response more compact. The deny unknown fields attribute forbids unknown fields, so a typo in a name will not pass silently. Aliases accept old field names, and flatten puts the fields of one struct into another at the same level. Attributes are part of the contract: when you change them, you change the format that clients see, so make such changes deliberately.\n\nEnums can be represented in JSON in different ways. By default, a variant is written as an object with a single key, the name of the variant. The tag attribute makes a label field inside the object: the type equals, say, message, and the other fields sit next to it. This format is convenient for clients: they look at the type field and pick a handler. The untagged form tries all the variants in turn and is suitable only for special cases. For chat events we use an internal tag: message, user joined, user left, and each event carries its own fields.\n\nA good technique is called parse, don't validate. Instead of storing a username as a string and checking its length everywhere, you create a separate type that can only be built from a valid string. The constructor returns a result, so an invalid value simply does not exist. Through the TryFrom trait, such a type plugs into serde: an incorrect name is rejected while parsing the request body. That way the check runs once at the boundary, and inside the code you work with types whose invariants are guaranteed by the compiler and the constructor.\n\nThe Json extractor can reject a request in three ways. A syntax error gives four hundred. A wrong content type header gives four hundred fifteen. Data of the wrong shape gives four hundred twenty-two. The default response is just plain text, but the client needs the familiar format. So you write a wrapper: your own extractor that calls the standard one and, on rejection, returns an application error. After that, all parsing failures look like the other errors. In addition, it can run validation and return a list of problem fields.\n\nHaving one enum for all the application's errors is good practice. Its variants are meaningful: not found, conflict, invalid data with a list of fields, unauthorized, forbidden, internal error. Each variant knows its status code and a short machine-readable code for the client. Handlers return a result with this error type and use the question mark operator. The type implements Display for the log and the standard Error trait, so it can take part in chains of causes. That way the complicated logic of handling failures comes down to a single place.\n\nSo that a handler can return an error directly, you implement the conversion into a response for it. The status is chosen by the variant, and the body always has the same format: a machine-readable code, a human-readable message, and an optional list of fields. An important security rule: for internal errors, the client is shown only a general message, and the details are written to the log together with a request identifier. Otherwise the text of a database query or a path on disk could leak into the response. A single format also makes things simpler for the client: one parser for every case.\n\nThe question mark operator automatically converts an error through the From trait. That is why, for every external error, you write a conversion into the application error: a database error, a parsing error, an I/O error. The database is a special case: a missing row becomes not found, a uniqueness violation becomes a conflict, and everything else becomes an internal error. Handler code becomes linear: ask, receive, return, with no nested checks. There is an external library for generating such implementations, called this-error, but they are easy to write by hand.\n\nThe error format is just as much a part of the contract as the format of successful responses. A good option is an object with an error field, and inside it a machine-readable code, a message for people, and an optional array of problem fields, each with a name and a reason. The machine code is stable, and the client chooses its behavior by it, while the message can be changed and translated. All routes return errors in the same format, including those produced by the framework itself: an unknown path, a wrong method, a body that is too large. For that, you set up a fallback handler and extractor wrappers.\n\nIt is better to keep the structs used for exchange with the client separate from internal models and from database rows. The request to create a room contains only a name, while the database model also has an identifier and a creation time. A response must not show a password hash, even if it is present in the row. Separate structs let you change the database without breaking clients, and the other way around. The conversions between them are simple functions or the From trait. A little redundancy pays off: every boundary gets a precise type, and it becomes harder for an extra field to leak by accident.\n\nA contract changes over time, and it has to change in a compatible way. New fields in responses can be added freely: clients ignore them. New fields in requests are made optional. A rename goes through an alias: we accept the old and the new name, and we send the new one. Removing a field is first announced as deprecated. A strict ban on unknown fields is good for requests, where a typo is dangerous, but harmful in client models, which must tolerate extension. The difference between a missing field and an explicit null matters for partial updates, and it is expressed with a double Option.\n\nLet's sum up. Serde separates data from format, attributes define the contract, and enums with an internal tag are convenient for events. Validation is done once at the boundary, turning data into types with guarantees. A single application error type turns into a response with the right status and one common body, while the details of internal errors stay in the log. The question mark operator and From implementations keep the code linear. Requests, responses, and internal models are kept separate. In the next chapter we will connect a database through sqlx.
