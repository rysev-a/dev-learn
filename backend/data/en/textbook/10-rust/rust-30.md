#CHAPTER 30 | Async in Python and in Rust: Two Models
Learning Rust. Chapter 30. Async in Python and in Rust: Two Models. Most of the time a program is not computing anything, it is waiting: for a server's response, for a disk read, for a database query. A server holding ten thousand connections cannot give each of them its own operating system thread. Asynchrony was invented for such tasks: one thread switches between many tasks and works on whichever one has something to do. The words concurrency and parallelism are often mixed up. Concurrency means many things are in progress at once; parallelism means several things are really executing at the same moment on different cores. Asynchrony gives you concurrency, and parallelism depends on the executor.\n\nPython knows three ways of doing things at once: threads, processes, and asynchrony. Threads in the standard interpreter are limited by the global interpreter lock, so computation does not speed up, but waiting for input and output works fine. Processes get around the lock at the cost of copying data between them. The asyncio module builds everything around one thread and an event loop: a coroutine declared with async def stops at await and hands control back to the loop, which runs another one. A blocking call, such as the ordinary sleep, freezes the whole loop, and this is the most common beginner mistake. So all the code around the loop has to be written non-blocking.\n\nA coroutine in Python is an object that does nothing until it is awaited or turned into a task. Calling an async function without await only creates the object and gives you the warning that the coroutine was never awaited. The function create task puts a coroutine into the loop's queue: it starts working at the next switch, without waiting for your await. The function gather runs several coroutines and collects the results, and a timeout limits the waiting. There is one event loop per thread, managed by Python itself, and libraries like aiohttp build networking on top of it.\n\nIn Rust an async function also returns a value that does nothing by itself, and it is called a future. It is any type that implements the Future trait with a method called poll. Calling an async function creates a state machine that stores the local variables and the point where it stopped. It lives right inside the value, with no heap allocation, and the compiler knows its exact size. Until someone calls poll, not a single line of the body has run. This is laziness, and in Rust it is stricter than in Python, where create task starts the task right away. The real work is carried out by a runtime, and that is a separate part.\n\nThere is no runtime in the Rust standard library, and that is a deliberate decision. The core of the language has the keywords async and await, the Future trait, and the types Poll, Context, and Waker. Everything else, from the event loop to timers and networking, comes from a library. The most widespread is Tokio. Next to it live async-std, smol, and Embassy for microcontrollers. The futures crate provides common tools like block on and join. Choosing a runtime is not a small matter: libraries are tied to it, and mixing them is awkward. In return you can tune performance and behavior to the task, and on a device with no operating system the runtime is entirely your own.\n\nThe syntax is similar to Python's, but not completely. A declaration reads: async fn get, empty parentheses, arrow, String. Waiting in Rust is written as a postfix: get, parentheses, dot await, not await get. This is handy for chains: request dot await, question mark, dot json, dot await, question mark. The question mark inside an async function works as usual. There are also async blocks: async move with a brace creates a future out of a piece of code that you can pass anywhere. You can write await only inside an async context, and this is the basis of the so-called function coloring.\n\nRunning tasks together. Python's gather is called the join macro in Rust, from the futures or Tokio crate: it waits for all the futures and returns a tuple of results. If you need to stop at the first error, you take try join. Create task corresponds to the function spawn: it launches a future as an independent task and returns a handle you can use to wait for the result. The timeout from asyncio is the function timeout from Tokio. Task groups, which Python 3.11 calls TaskGroup, correspond to JoinSet. Iterating in order of readiness, as completed, comes from FuturesUnordered or from a stream. We will go through all these tools in detail in the following chapters.\n\nBlocking calls are harmful in both models. In Python a blocking function freezes the loop, and for long work there is run in executor: it sends the call to a thread pool. In Rust the function spawn blocking does the same: it runs ordinary code on a separate pool thread and hands back the result as a future. Computations that load the processor are better sent to Rayon or to ordinary threads, rather than to async tasks, otherwise they occupy a worker thread and get in the way of everything else. The rule is simple: an async task must quickly reach its next await.\n\nParallelism. The asyncio loop runs in a single thread, so two tasks never execute at the same moment and data races cannot happen, but you cannot use multiple cores either. The Tokio runtime is multithreaded by default: it has a pool of worker threads and a work-stealing queue, and a task can hop from thread to thread between awaits. That is why a future launched through spawn has to be Send: all the data it holds across an await must move safely between threads. The compiler checks this, which means there are no data races in safe code, even in a multithreaded setup.\n\nCancelling tasks. In Python, calling cancel throws a CancelledError exception at the point of await, and the task can catch it and clean up. In Rust everything is simpler and harsher: if you drop a future before it finishes, it simply ceases to exist. The work stops at the nearest await point, and the local values are released by their destructors in the usual order. Cancellation happens when a future is thrown out of a select, when a timeout fires, or when a task handle is cancelled with the method abort. So it is important that your code survives being stopped between any two awaits: in Rust this is called cancellation safety.\n\nAbout the cost. A Python coroutine is an object on the heap, with overhead of a few kilobytes and microseconds per switch. A Tokio task is a state machine the size of its state, often a few dozen bytes, and a switch costs tens of nanoseconds. That is why in Rust it is easy to keep hundreds of thousands of tasks and a million connections on one machine. The programmer pays the price: you have to understand what is held across an await, how the Send restrictions work, and how to avoid blocking. In return the resulting programs start fast, and they handle extreme loads with few servers.\n\nHow to choose. You need asynchrony when there are many tasks and each mostly waits: servers, proxies, chats, crawlers, database clients. When there are few tasks and they are computational, threads or Rayon are simpler and faster. Mixed programs live in two worlds: an async core and a compute pool. Async code is contagious: to call an async function you must be in an async context, and from ordinary code the bridge is the function block on, which runs a future to completion on the current thread. Do not try to make everything async: use it where there is real waiting.\n\nLet's sum up. Python builds asynchrony around one thread and an event loop, Rust around lazy futures and a runtime from a library. A Rust future is a state machine with no heap, and it does nothing until polled. Await is written after the expression. The correspondences: gather is join, create task is spawn, run in executor is spawn blocking, TaskGroup is JoinSet, cancel is drop. Tokio is multithreaded and requires Send. In the next chapter we will look under the hood: we will write our own future, our own waker, and a simple executor, to understand what async and await really do.
