#CHAPTER 48 | Users: Passwords, Sessions and Permissions
Learning Rust. Chapter 48. Users: passwords, sessions and permissions. A chat without users is just a shared screen. We need a person to sign up, log in, receive a token, and then sign every request with it. We need to store passwords so that a leaked database does not reveal them, defend against brute force, and hand out permissions: anyone logged in can write to rooms, but only the owner can change the topic. Security is an area where small mistakes are expensive, so in this chapter we lean on proven primitives and explain why each decision is made the way it is.\n\nA password must never be stored in the open, and it must not be encrypted either: sooner or later the key leaks together with the database. Instead, a password is hashed, which produces an irreversible fingerprint. Ordinary fast hashes are no good for passwords, because an attacker can try billions of candidates per second. We need deliberately slow functions that also demand a lot of memory, to slow down graphics cards as well. A random salt is added to the password, so identical passwords get different hashes and precomputed tables are useless. The salt is stored next to the hash and is not a secret.\n\nThe modern choice is Argon2. Its result is a single string in the PHC format: the algorithm, the memory and pass-count parameters, the salt and the hash itself. Everything needed for verification sits in that string, so one text column in the database is enough. Verification takes a password and the string, reads the parameters on its own, and compares in constant time. If you later decide to raise the parameters, the old hashes keep verifying, and at the next login the password can be rehashed with the new ones. Heavy hashing should also run in a way that does not block a scheduler thread.\n\nRegistration is a chain of small steps. First we validate the input: the length of the name, and the length and makeup of the password. Then we hash the password and insert the row. If the name is taken, the database itself rejects the insert with a uniqueness violation, and we translate that into a conflict response. Checking for the name with a separate query before inserting is pointless, because a race is possible between the check and the insert. The plain password is never saved anywhere and never written to the log, even when the request body fails to parse. The response contains neither the password nor the hash.\n\nLogin checks the name and the password. The main rule is not to reveal which of them is wrong. An unknown name and a wrong password return the very same response with the very same text, otherwise an attacker learns which names exist. There is also a subtlety with timing: for a nonexistent user no hash check runs, and the response comes back faster. So in that case we also run a dummy check against a prepared hash. On top of that, we limit the number of login attempts per name and per address, so that brute force becomes impractical.\n\nAfter login the server issues a session token. It must be unpredictable: thirty-two random bytes from the system generator, written as a hexadecimal string or in base sixty-four. A token is a secret just like a password, so the sessions table stores not the token itself but its hash, for example SHA-256. A fast hash is fine here, because the token is random and cannot be brute-forced. The client receives the token exactly once. On every request the server hashes the presented token and looks the session up by that hash.\n\nThe token travels in the Authorization header with the Bearer scheme. Parsing must be strict: no header, a different scheme, an empty token, extra parts, all of these mean rejection. By the standard, the scheme name is case-insensitive. A token must never be passed in the address, because addresses end up in proxy logs and browser history. The exception is a WebSocket connection, where the browser does not let you set a header; it gets its own solution, which we will come back to. For browser apps there is also a cookie-based option, but then you have to think about cross-site request forgery.\n\nThe most convenient way to model the current user is as your own extractor. It reads the header, hashes the token, looks up a live session and returns the user; on failure it responds with four oh one. A handler only has to declare an argument of that type, and protection is built into the signature: forgetting the check is impossible, because the function simply is not called without a login. The extractor gets the pool from the state through FromRef. A layer plus an extension also works, but the extractor is more honest: the dependency is visible in the function arguments, and it is easy to swap out in tests.\n\nA session has a lifetime: the record stores the moment it expires, and lookups ignore expired ones. Logout deletes the session from the database, so the token stops working immediately, which self-contained tokens cannot achieve. Logging out everywhere deletes all of a user's sessions; it is needed when the password changes or compromise is suspected. To keep the table from growing forever, you cap the number of active sessions per person and delete expired ones with a background task. These mechanisms are the main advantage of server-side sessions over signed tokens, which cannot be revoked before they expire.\n\nPermissions are checked only on the server; anything the client decides can be bypassed. Tell two refusals apart. Four oh one means the server does not know who you are. Four oh three means it knows, but this action is forbidden to you. Simple rules are expressed with roles: administrator, member. Finer ones are expressed with ownership: only the creator can change a room's topic. It is convenient to check the role in a separate extractor, and ownership in the handler itself or in the query, putting the owner condition right into the update command so that the check and the action are indivisible.\n\nA few rules close most of the trouble. Limit the number of login attempts. Send everything only over a secure connection. If the token lives in a cookie, set the flags: not readable by scripts, secure connections only, not sent from other sites. For cookies with state-changing requests you need protection against cross-site forgery, for example a paired token. Do not write passwords, tokens or the authorization header to the log. Compare secrets in constant time. And rehash passwords when you raise the parameters: security ages.\n\nThere is an alternative to server-side sessions: signed tokens such as JWT. The server signs claims, who this is and until when, with a key, and on verification it only checks the signature and the expiry, without touching the database. That is convenient between services. The price is that a token cannot be revoked before it expires, and a role change does not take effect right away. That is why signed tokens are made short-lived and complemented by a long-lived refresh token kept on the server. For our chat we choose server-side sessions: they are simpler, safer, and let us cut off access instantly.\n\nLet's sum up. Passwords are stored as slow salted hashes, and the PHC string carries all the parameters. Registration relies on the uniqueness constraint, and login returns the same response for any wrong credentials. Session tokens are random, only their hashes are in the database, and expiry and logout take effect immediately. The current user is modeled as an extractor, permissions are checked on the server, and the distinction between four oh one and four oh three stays strict.
