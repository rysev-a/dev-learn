#CHAPTER 21 | Lifetimes and smart pointers: who lives and for how long
Learning Rust. Chapter 21. Lifetimes and smart pointers: who lives and for how long. In Python nobody asks you when an object will die: every name is a reference, and the garbage is cleaned up by reference counting and the garbage collector. In Rust every value has exactly one owner, and references must not outlive it. We have already seen this in examples, and today we look at two tools in more depth. Lifetime parameters describe the relationships between references, and smart pointers, Box, Rc, Arc and RefCell, give you powers that a plain reference does not have: storing data on the heap, sharing ownership, and changing data behind shared references. And all of this without a garbage collector.\n\nA lifetime is the region of the program where a reference is valid. Usually the compiler works it out by itself, and a label, an apostrophe and a letter, is needed only to state a relationship: the result lives no longer than this argument. If a function has one input reference, the result automatically gets the same lifetime. If there are several inputs but one of them is self, the result is tied to self. In all other cases you have to write the labels by hand. These are called the elision rules, and thanks to them the labels are invisible in most functions. There is one special lifetime, static: it equals the running time of the whole program, like string literals.\n\nThe typical lifetime errors keep repeating. You cannot return a reference to a local value: it dies when the function returns. You cannot keep a reference in a struct for longer than its owner lives either: then the struct needs a lifetime parameter, and it will not outlive the data. You cannot hold two mutable references to the same value, but you can to non-overlapping parts of it, for example by splitting a slice in half. Often it is easier not to fight but to change the design: return ownership instead of a reference, store an index instead of a pointer, or clone a small string.\n\nNow the smart pointers. Box of T is the simplest one: the value lives on the heap, the stack holds a single pointer, and when the scope ends the heap memory is freed. The star dereferences a box, and the dot works through it automatically. You need a box for recursive types, for large values you do not want to copy, and for trait objects. The size of a box does not depend on the size of the value: eight bytes, like any pointer, so structs that contain a box are easy to move around in memory.\n\nWhat makes a pointer smart? Two traits. Deref describes how to dereference a value, so Box and Rc behave like references, and the compiler automatically turns a reference to a String into a reference to a str, and a reference to a Box into a reference to the inner value: this is called deref coercion. Drop describes what to do on destruction: free memory, close a file, release a lock. You write your own smart pointer by implementing these two traits. Drop runs in the reverse order of creation, and you can check this by printing messages from the implementation.\n\nSometimes a value needs several owners, like a graph node that other nodes point to. For that there is Rc, a reference counter. The value sits on the heap together with two counters, a strong one and a weak one. Calling clone on an Rc does not copy the data; it increases the strong counter by one, and destroying an owner decreases it, and at zero the value is freed. This is the same model as in Python, but in Rust you choose it deliberately, and it is not always on. The contents of an Rc are read-only, and the number of owners is shown by the function strong count.\n\nHow do you change data behind a shared reference? RefCell moves the check of the borrowing rules from compile time to run time. The method borrow hands out an ordinary reference, and borrow mut a mutable one, but a counter inside the RefCell makes sure the mutable one is the only one: a violation causes a panic, while the method try borrow mut returns an error instead of panicking. This is called interior mutability. For simple copyable values there is Cell, with no checks at all. The combination Rc of RefCell of T is the pattern for shared mutable data in a single thread. For several threads a different variant is used, which is the topic of the next chapter.\n\nIf two values refer to each other through Rc, the counters never reach zero and memory leaks: there is no collector, so the cycle cannot be broken. That is what Weak, a weak reference, is for. It does not increase the strong counter and does not prevent the value from being freed, and before use you turn it into an Option with the method upgrade: if the value is still alive you get Some with an Rc, otherwise None. The typical use is a tree where the parent owns its children through strong references, and the children know the parent through a weak one, so there is no cycle.\n\nArc is Rc for threads: the counter is changed with an atomic instruction, for example amoadd from the RISC-V instruction set, and several cores can safely clone the pointer at the same time. The price is speed: an atomic operation is slower than ordinary addition, and on several cores it also drags the cache line back and forth. That is why you use Rc within one thread, and Arc only when the value crosses a thread boundary. Safety is guaranteed by the marker traits Send and Sync, which the compiler checks by itself: an Rc will not make it into another thread.\n\nCow, clone on write, solves a different problem: avoiding needless copying. A value is stored either as borrowed or as owned. As long as you only read, there is no copy; and as soon as you need to change it, the method to mut makes a copy. A typical example is a string normalization function, which most of the time returns its input unchanged and allocates memory only for the strings that really need fixing. The result looks like an ordinary string, but underneath it may be just a reference, and that costs nothing.\n\nLet's look at sizes. A plain reference and a Box take eight bytes, a reference to a slice or a trait object takes sixteen. Rc and Arc are also a single pointer, but it points to a block on the heap that holds the counters and the value. An Option of Rc is no bigger than the Rc itself, as we saw with the niche. The functions mem swap, mem replace and mem take let you pull a value out from behind a mutable reference while leaving another one in its place, which resolves many arguments with the borrow checker with no copies and no unsafe code.\n\nHow do you choose? Start with a plain value, then a reference. Need the heap or recursion: Box. Need several owners in one thread: Rc, and with it RefCell if you need to change the data. Need shared access from threads: Arc. Need to avoid copying a string: Cow. And there is one more trick, used both in databases and in kernels: keep the objects in one vector, an arena, and refer to each other by indexes. It needs no counters, no cycles and no borrow checks, and this is how the trees in the algorithms book are built.\n\nLet's sum up. A lifetime describes how long a reference lives, and most of the time it is inferred. Box owns a value on the heap, Rc shares ownership, RefCell checks borrowing at run time, Weak breaks cycles, Arc carries the counter into the multithreaded world, and Cow copies only when it must. Drop and Deref define how smart pointers behave. The next chapter is about organizing code: modules, tests and Cargo.
