#CHAPTER 42 | A Router and a Multithreaded Server
Learning Rust. Chapter 42. A router and a multithreaded server. In the last chapter we learned to parse requests and build responses, and we ended up with a server that serves one client and answers a couple of addresses. A real application needs more: a table of routes with parameters in the address, shared code for all requests such as logging and access checks, shared state between requests, serving many clients at once, a graceful shutdown, protection from overload, and a way to check all of this with tests. Today we will build these parts from the standard library. And at the end we will look at what ready-made frameworks take on, and see why, after this chapter, reading their documentation will stop being magic.\n\nA router is a table that maps a method and an address pattern to a handler. When a request comes in, we go through the entries, look for a matching pattern, and call the handler. The result depends on three cases. Both the pattern and the method matched: we call the handler. The pattern matched but the method is different: we reply with the code for method not allowed. There is no pattern at all: the code is not found. The difference between the last two matters to clients and for the header listing the allowed methods. A handler can be an ordinary function with a known signature: a function pointer goes into a vector of entries next to the method and address strings.\n\nPatterns with parameters let us write users, colon, id. Matching goes by segments: the address and the pattern are split at the slash, the number of segments must be equal, and for each pair either the pattern segment starts with a colon and then the value is remembered under that name, or the segments must match literally. The result is a list of name and value pairs that is handed to the handler. The order of entries in the table sets the priority: a specific address like users, new must be placed before the pattern with a parameter, otherwise the word new will be taken for an id.\n\nIn general a handler takes a request and returns a response, and to keep different handlers together, they are put into boxes with a dynamic closure trait. Intermediate layers, middleware, are written as functions that take a handler and return a new, wrapped one. A logging layer records the entry and the result, and an access check layer looks at a header and either lets the request through or immediately replies unauthorized. Layers nest inside each other like matryoshka dolls, and the order of wrapping sets the order of execution. This is the one place where you describe cross-cutting behavior instead of repeating it in every handler.\n\nBetween requests you need to keep state: counters, caches, database connections, user sessions. Handlers run in different threads, so the state is wrapped in an Arc with a Mutex inside, and passed around as clones. It is customary to declare the state struct separately and give it clear methods that take the lock for a short time and return a result: that way the lock does not leak out of the method. Remember the rules from earlier chapters: don't hold the guard during long operations, take locks in a consistent order, and don't call outside code while a lock is held.\n\nA simple to-do application shows how this fits together. The store is an ordered table from a number to a record, and it has a next free number. Creating returns the new number, completing flips a flag on an existing record or returns a no such record error, and deleting reports whether the record existed. The protocol handlers turn these methods into responses: creation gives the code created, successful completion gives OK, and an error gives not found. This split into a storage layer that knows nothing about the network and a protocol layer that knows nothing about the storage makes both parts easy to test separately.\n\nA single thread for the whole application serves clients one after another, and a thread per connection costs memory and creation time. The golden mean is a thread pool: a fixed number of workers, a shared job queue, and a channel to deliver the jobs. The workers take a job in a loop and run it. When the pool is dropped, we close the sender, the workers get an error on receive and leave the loop, and we wait for them to finish. This is the graceful shutdown: jobs that were already accepted run to the end. The pool size is chosen by the number of cores and by the share of time the handlers spend waiting.\n\nStopping a server on a signal needs a way to wake up the accept loop. A blocking accept cannot be interrupted from outside, so the socket is switched to non-blocking mode, and the loop checks a shared atomic stop flag: while the flag is not raised, it tries to accept a connection, and if there is nothing to accept, it sleeps briefly. When the flag is raised, the loop exits, the pool is dropped and waits for the workers. The main thread raises the flag on a signal or an administrator's command. This trick is universal: any background loop must have a way to stop, otherwise the program can be neither updated nor restarted cleanly.\n\nA server on an open network must be protected. We already had limits on the size of headers and the body. Now we add read and write timeouts so that a slow client does not hold a worker. Rate limiting is done with token buckets: each client has a bucket that holds a few tokens and refills at a constant rate; a request spends a token, and if there are no tokens, it gets a too many requests refusal. The time is passed into the function as a parameter rather than read inside, and then the behavior can be tested without waiting. It is worth limiting the number of simultaneous connections too: the job queue is made bounded.\n\nA server is conveniently checked with integration tests. A test starts a real server on a free port, connects as a client, and compares the responses: code, headers, body. A helper request function hides the socket details, and the server runs in a thread and is limited to a number of connections so that the test finishes by itself. Such tests catch what unit tests don't see: the order of layers, mistakes in real headers, hangs on close. Run them on every change, and they pay off with the very first bug found before release. A test that sometimes fails should be investigated right away: most often it is a race or a lost wait.\n\nObservability starts with counters. Atomic numbers count requests, errors of the five hundred class, and bytes sent: this is safe from any thread and almost free. A render method turns them into text that feeds monitoring systems, and the log lines record the method, the path, the code, and the handling time. Don't log secrets or personal data, and give every request an identifier so you can tie log lines together. Metrics answer the question of what is happening to the system as a whole, the log answers what happened to this particular request, and you need both.\n\nThe project structure is usually like this. A library holds the protocol parsing, the router, the handlers, and the state, and all of it is covered by tests. A thin main program reads settings from arguments and the environment, starts the server, and waits for a signal. The settings are a separate struct with default values, flag parsing, and clear errors. Ready-made frameworks like Axum or Actix Web do the same thing: routing with parameters, layers, shared state, asynchronous work, and JSON parsing. Now you know what is hidden behind their convenient macros, and you will be able to debug their behavior.\n\nLet's sum up. A router maps a method and a pattern to a handler and tells not found apart from method not allowed; parameters are extracted by segments. Layers wrap handlers and implement cross-cutting behavior. Shared state lives in an Arc with a Mutex and is reached through small methods, and the storage is separated from the protocol. A thread pool limits parallelism and gives a graceful shutdown, and non-blocking accept with an atomic flag stops the server. Timeouts, limits, and the token bucket protect against overload, integration tests check the server as a whole, and counters and the log make it visible.
