#CHAPTER 37 | Tokio in practice: cancellation, load and shutdown
Learning Rust. Chapter 37. Tokio in practice: cancellation, load and shutdown. In textbook examples everything is simple: start, wait, exit. A real application raises three questions that you have to be able to answer. How do you cancel work that is no longer needed, because the client disconnected or the deadline passed? How do you avoid drowning when there are more requests than you can handle? And how do you stop cleanly: finish what was started, flush the buffers, close the connections, instead of breaking off in the middle of an operation? These three topics are what separate a toy from a service, and now we will put together a set of techniques in Tokio for each of them.\n\nIn asynchronous Rust, cancellation is simple: a future that has been dropped is never polled again. Everything after the nearest await never runs, and the local variables are destroyed with a call to drop. This is how timeout, select and abort on a task handle work. The abort method asks the task to stop at its nearest await, and waiting on the handle returns an error flagged as cancelled. If you merely destroy the handle, though, the task is not cancelled; it keeps running in the background. Cancellation is instant and does not need the consent of the code inside, so that code has to be ready for it.\n\nHard cancellation can interrupt work at an awkward place. The soft kind is called cooperative: the task itself listens for a signal and has time to tidy up. In tokio-util there is the cancellation token for this. You clone it and hand it out to tasks. A task waits in select on the cancelled method next to its main work, and when the token is cancelled, it leaves the loop. A token can be derived from a parent: cancelling the parent cancels all the children, while cancelling a child does not touch the parent. This is how you build a tree of tasks in which a stop at the root passes neatly down to the leaves.\n\nA graceful shutdown has three steps. First we stop accepting new work: we close the accept loop. Then we let the current tasks finish, but not forever, only up to a deadline. And only then do we exit. The signal comes from the operating system: the signal function in Tokio catches Ctrl-C and SIGTERM, and then it turns into a token cancellation or a broadcast over a channel. To wait for all the tasks, people use a JoinSet or a task tracker: they know how many tasks are running and tell you when the last one has finished.\n\nWhat if cancellation requires releasing a resource, for example deleting a temporary file or notifying the other side? The drop method is synchronous, and you cannot use await inside it. So we do it differently: in drop we perform only quick synchronous actions, and for slow ones we add an explicit asynchronous close method, which is called on a normal shutdown. For automatic cancellation there is the token's drop guard: it cancels the token when it is destroyed, and so ties the lifetime of the owner to the lifetime of the tasks. Any cleanup must be idempotent and must not panic.\n\nA service that accepts everything is the first to fall over at a peak. Load has to be limited at every step. Concurrent operations are limited by a semaphore. Queues are made bounded so that slowdown is passed back up the chain. And when a queue is full, it is better to refuse quickly, answering busy, than to accept a request and fail to handle it in time. This is called load shedding. A fast refusal keeps things working for those who have already been accepted, while endless waiting piles up tasks, memory and latency. The choice between waiting and refusing is a decision you have to make explicitly.\n\nAny call to the outside can hang: the network, the database, another service. So every call needs a timeout, and the whole request needs a common deadline that is passed down the chain of calls. Then the inner steps know how much time they have left and do not waste it on work whose result nobody needs anymore. Timeouts are chosen from real measurements: ones that are too short give false failures, ones that are too long do not protect you. And do not forget that a timeout cancels the waiting, but does not roll back what has already been done on the other side.\n\nThe most insidious problem in asynchronous programs is blocking code inside a task. A heavy computation or a synchronous call does not give up the thread, and the tasks on that thread freeze: timers run late and requests hang, even though the processor is only partly loaded. The telltale sign is high latency at low load. The solution is spawn blocking, which runs the work in a separate thread pool while the task waits for the result with await. For long computations on all cores, a separate pool such as Rayon is better. A rule of thumb for checking: an asynchronous function must not contain calls that noticeably occupy a thread.\n\nA panic inside a task does not bring down the runtime. The handle returns a join error, which can tell you whether it was a panic or a cancellation. This lets you build a supervisor: the task is awaited in a loop, and if it crashed, it is started again, with a limit on the number of restarts and a pause between them. This is usually how long-lived background jobs are built. But a panic is not a way to control flow, so expected errors are returned as a Result value, and panics are left for violated invariants. And watch out for locks: a panic while holding a standard library mutex poisons it.\n\nRetries cure temporary failures, but without moderation they do harm. If a failed service gets retries without pauses from thousands of clients, it will not be able to get back up. So the pause between attempts grows, the number of attempts is limited, and a random jitter is added to the pause. The next level of protection is called a circuit breaker: after a series of failures it stops calling the service for a while and answers with a refusal immediately, and then carefully tries again. This way you do not load the sick service and you answer your own clients quickly, and the system recovers without manual intervention.\n\nSometimes you need to limit not the number of concurrent operations but the rate: no more than ten requests per second to someone else's API. The simplest way is an interval: before each operation we wait for the next tick. A more flexible way is the token bucket: the capacity sets the allowed burst, and a background task refills the tokens on a schedule. In Tokio you build the bucket on a semaphore and the add permits method. Rate limiting protects both other people's services and you yourself from being blocked, and it is especially important in clients that can multiply requests quickly.\n\nAsynchronous code is hard to debug: there are no call stacks, and everything happens in different tasks. The tracing crate helps: it keeps structured logs with spans that are tied to tasks rather than threads. The tokio console utility shows live tasks, their states and poll times. The runtime metrics report the number of workers and the depth of the queues. For tests there is the tokio test attribute and test time: pausing and fast-forwarding make timeout checks instant. And channels and duplex streams stand in for the network, so you can check the logic without a single socket.\n\nLet's sum up the chapter and the whole part. Cancellation in asynchronous Rust is dropping a future, and the cancellation token provides the soft stop. A graceful shutdown means: stop accepting new work, wait for the current work with a deadline, exit. Load is limited by a semaphore, bounded queues and fast refusal, and timeouts go everywhere. Blocking code is moved into spawn blocking. Panics are isolated, and a supervisor restarts the tasks, while retries are done with a pause and protection. We have come all the way from a future to a resilient service. Next the language is applied in projects: algorithms, a processor, an operating system and a web server.
