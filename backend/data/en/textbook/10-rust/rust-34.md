#CHAPTER 34 | Tokio: Time, Timers, and select!
Learning Rust. Chapter 34. Tokio: time, timers, and select. Many asynchronous programs spend most of their time simply waiting: for a server's reply, for a pause between retries, for a timer to expire. For this Tokio has the time module. The main rule: inside an asynchronous task you must not put the thread to sleep with sleep from the standard library, because along with the thread, all the other tasks running on it will fall asleep too. Tokio's sleep returns a future: the task gives up the thread and wakes up later. This is the most common beginner mistake. In this chapter we will cover timers, timeouts, intervals, and waiting for several events at once.\n\nSleep takes a duration and returns a future that completes no earlier than the given time. Sleep until takes a moment and waits until it. Moments in Tokio are called Instants; they are monotonic: they only move forward and do not depend on clock adjustments. The difference between two moments gives a duration, and the elapsed method shows how much time has passed. The timer is accurate to a millisecond, and a task may wake up slightly later, but never earlier than the deadline. So neither in tests nor in programs should you count on an exact match; leave some margin.\n\nTimeout wraps any future and limits how long it can run. If the future finished in time, you get Ok with the value. If time ran out, you get Err with an Elapsed error, and the future itself is dropped: its execution simply stops at the nearest await. This is how you limit waiting for a server's reply, for reading from a socket, and for any other operation that might hang. It is important to remember that a timeout does not undo side effects already made inside: if the future managed to send a request, the request has gone out. A timeout can also be placed on a whole chain of steps.\n\nFor repeating actions there is an interval. It is created with a period, and the tick method returns a future that completes at the next moment. The first tick fires immediately, without waiting, and this is a frequent cause of surprise. After that, ticks come at a constant period, counted from the start, not from the end of the previous action. So an interval does not accumulate drift: if the work takes part of the period, the pause shrinks automatically. If the work takes longer than the period, the ticks shift, and exactly how is determined by a special missed tick setting.\n\nWhat if processing takes longer than the period and ticks run late? The behavior is set by the value of Missed Tick Behavior. Burst, the default, delivers the missed ticks one after another without pauses, to catch up with the schedule. Delay counts a new period from the moment of the late tick and shifts the whole schedule. Skip drops the lost ticks and waits for the nearest one on the original grid. The choice depends on the task: for scheduled accounting you want Burst, and for polling a sensor, Delay or Skip, so as not to overload the system after a stall.\n\nIf a multi-step operation has one shared time limit, it is more convenient to track not the remaining time but the end moment: a deadline. Sleep until waits until it, and timeout at limits any step with the same moment. That way the overall limit is not stretched by the steps. A sleep can be reset with the reset method, extending the wait, but for that the future has to be pinned in place with the pin macro. This is how an idle timeout is built: every time data arrives, the deadline moves back, and if silence lasts longer than the limit, the connection is closed.\n\nTests that wait real seconds are slow and unreliable. Tokio has a test time mode, enabled with the test util flag. When paused, time stands still, and when all tasks are waiting, it instantly jumps forward to the nearest timer. For this it is enough to use the attribute with start paused, or to call pause by hand. The advance method moves time forward by the amount you need. That way a test for an hour-long timeout runs in milliseconds. In our examples the flag is not enabled, so we use short pauses with a margin, but in your own project turn this mode on right away.\n\nThe select macro lets you wait for several events at once and react to the first one. Each branch consists of a pattern, a future, and a block of code: pattern equals future, arrow, block. When one of the futures completes, its result is matched against the pattern, the block runs, and the other futures are dropped. This is the basis of timeouts, cancellation, and merging streams of events: we wait for either a message, or a stop signal, or a timeout. The value of the block becomes the value of the whole macro, so select can be used as an expression and its result assigned to a variable.\n\nBranches have some subtle features. After the future you can write an if condition: if it is false, the branch is disabled for this iteration. If the pattern does not match the result, the branch is disabled too, and select keeps waiting for the others. When all branches are disabled, the else branch runs, and without it the macro panics. By default the order of checking is random, so that no branch starves. If you need strict priority, for example to check the stop signal first, put the word biased at the start, and the branches are polled from top to bottom.\n\nSelect has a dangerous side: the losing futures are not run to completion, they are dropped at an arbitrary point. If a future had done part of its work, it is lost. An operation is called cancel safe if nothing is lost when it is dropped at an await. Receiving from a channel is safe: the message stays in the channel. But reading an exact number of bytes from a stream is not safe: the part already read disappears. In Tokio's documentation every function has a section about cancel safety, and you should read it before using the function in select.\n\nSelect most often lives inside a loop: wait for a message or a tick, handle it, repeat. If you create a future anew on every iteration, it starts from scratch, and progress is lost. So long futures are created before the loop, pinned with the pin macro, and passed to select by mutable reference. Then, after another branch wins, the future continues from the same place. For a timer this means that one and the same deadline applies to all iterations. A typical setup: messages from a channel, a periodic heartbeat, and a shared stop signal.\n\nUnreliable operations are retried, but wisely. Each attempt gets a timeout, so that a hung call does not block everything. Between attempts you keep a pause that grows: a hundred milliseconds, two hundred, four hundred, and so on up to a limit. This is called exponential backoff, and it reduces the load on a failing service. A random spread is added to the pause, so that thousands of clients do not all rush to retry at the same moment. The number of attempts is limited, and after the last failure you return an error instead of waiting forever. Such a retry is easy to wrap in a function that takes a closure.\n\nLet's sum up. Inside tasks we wait with Tokio's sleep, which does not block the thread. Timeout limits any future, interval gives an even rhythm, and missed ticks are configurable. A shared deadline is set as a moment, and resetting a sleep lets you extend the limit. Select waits for several events and drops the losers, so remember cancel safety. In a loop, long futures are pinned and passed by reference. Retries are done with a timeout and a growing pause. For durations, use monotonic clocks. In the next chapter we will look at channels and synchronization between tasks.
