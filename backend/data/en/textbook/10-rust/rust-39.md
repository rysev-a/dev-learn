#CHAPTER 39 | Bits, bytes and a processor emulator
Learning Rust. Chapter 39. Bits, bytes and a processor emulator. In the computer architecture course we built everything out of bits: numbers in two's complement, shifts, byte order, checksums and a teaching processor. Rust is made for this kind of work: it has a predictable representation of types, a full set of bit operations and honest arithmetic with no hidden conversions. Today we will move to Rust what we did in Python. We will go through integer types and casts, bit methods, byte order, the size and alignment of structures, the representation of floating-point numbers, encodings and checksums, bit sets, and at the end we will put together a processor emulator in which memory access errors are expressed with an enum and a Result rather than a crash.\n\nLet's begin with integer types. Each has a fixed width and a sign: eight, sixteen, thirty-two, sixty-four and one hundred twenty-eight bits, plus usize and isize, as wide as a pointer. Conversions between them are done with the as keyword and are always explicit. A signed number becomes unsigned by reinterpreting the bits: minus one turns into all ones. Narrowing simply drops the high bits, so three hundred in eight bits turns into forty-four. And casting a floating-point number to an integer saturates: a value that is too large becomes the maximum of the type, the fractional part is dropped, and a not-a-number value becomes zero.\n\nBit operations are familiar from the previous course: and, or, exclusive or, not, and shifts. Besides them, every integer type has dozens of methods. The count of one bits, the number of zeros at the start and at the end, rotations left and right, swapping the bytes. To isolate the lowest set bit, use the expression of a number and minus the number, in wrapping arithmetic. These operations compile into a single processor instruction if there is one, so there is no point in writing them by hand with loops. A shift by the width of the type or more panics in a debug build, so check the shift amount.\n\nByte order in memory is a topic from the chapter on numbers. In Rust it is expressed by methods: converting a number to an array of bytes in big-endian, little-endian or the platform's native order, and the reverse methods that create a number from an array. Network protocols and file formats usually specify the order explicitly, so you almost always use the first two variants rather than the platform order. This turns the parsing of binary formats into simple work with fixed-length arrays, and byte order mistakes are visible immediately, because the methods are named plainly: from bytes, big-endian.\n\nThe size and alignment of structures are expressed in code too. The functions size of and align of return them for any type. Every field must lie at an address that is a multiple of its alignment, so empty bytes appear between the fields. Rust is free to reorder the fields to reduce the size, and a structure made of a byte, a four-byte number and another byte takes eight bytes. The repr C attribute demands the order of the C language, and the same structure takes twelve. This is needed for talking to libraries and hardware. And an Option over a Box takes exactly as much as the Box itself: the empty value hides in the forbidden null address.\n\nThe representation of floating-point numbers in Rust is the standard one, by the rules of IEEE 754. The to bits method returns the bit pattern as an integer, and from bits creates a number from the bits: this is a safe way to look inside, without an unsafe cast. One in single precision is hex three F eight followed by five zeros, and minus two and a half is hex C zero two followed by five zeros. Comparing floating-point numbers for equality, as we know, is tricky, and a not-a-number value is not equal even to itself, so there is a separate method to check for it. This is exactly why floating-point types do not implement a total order, and you cannot just put them into an ordered set.\n\nLet's move on to encodings. Hexadecimal notation turns each byte into two digits. Base encodings such as Base64 pack three bytes into four printable characters, so that binary data can be put into text. Variable-length numbers, the so-called varint, store the low seven bits in each byte, and the high bit says whether there is a continuation: small numbers take one byte, larger ones take more. Serialization protocols and databases use this format because on average it saves a lot of space. Encoding and decoding are an exercise in shifts and masks.\n\nChecksums carry over easily too. The cyclic code CRC 32 is computed from a table of two hundred fifty-six values, which is convenient to fill once and then do one operation per byte. The initial value is all ones, and at the end the result is inverted. For the word hello you get hex three six one zero A six eight six, and for a string of the digits from one to nine, hex C B F four three nine two six. These check values match the Python function, and that is a good way to verify your own implementation.\n\nAnother popular structure is the bit set. Instead of a boolean array, where every flag takes a byte, we use a vector of sixty-four-bit words: the word number is the flag number divided by sixty-four, and the bit number inside the word is the remainder. Setting, testing and counting are done with shifts and masks, and the total number of ones is computed by the method that counts one bits. For a set of two hundred elements, four words are enough. Bit sets underlie the sieve of Eratosthenes over billions of numbers, filters, and graph algorithms with compact storage.\n\nNow let's build the emulator. We describe the processor: four one-byte registers, a program counter, a zero flag and the number of steps executed. The instruction set is an enum: load a number into a register, add, subtract, conditional jump and halt. The registers, in the form of an array, are indexed by numbers, and the arithmetic is wrapping, as in hardware. The size of the enum is not equal to the size of the largest instruction: Rust adds a variant tag, and for our set it comes to twenty-four bytes. This differs from the compact two-byte instruction in the teaching processor from the architecture course, and later we will add real encoding of instructions into bytes.\n\nExecution is a loop, as before: read the instruction at the counter, increment the counter, execute through a match. Addition and subtraction update the zero flag, and a conditional jump changes the program counter. A program that sums the numbers from one to five takes nineteen steps and leaves fifteen in the first register, exactly as in the Python version. A match over an enum gives a guarantee: if we add a new instruction and forget to handle it, the program will not compile. In the Python version such a mistake would show up only at run time, as an unknown instruction.\n\nThe emulator's memory is a separate structure, and here Rust shows its strength. Reads and writes return a Result with an error type: out of bounds, stack overflow, unknown instruction. This way the emulator does not crash on a wrong program, but reports a trap, as a real processor raises an interrupt. The stack grows down, the pointer decreases on a push, and at zero an overflow occurs. The get method on a slice returns an Option, which turns into an error with a single call, and the question mark operator passes it upward. Not a single out-of-bounds index and not a single panic.\n\nLet's sum up. Integer types have a fixed width, casts are explicit, and the bit methods cover almost every task. Byte order is set by methods, size and alignment by functions and attributes. Floating-point numbers can be safely taken apart into bits. Encodings, variable-length integers and checksums are written with shifts and masks, and bit sets store flags compactly. A processor emulator built on enums and Results turns out shorter and more reliable than in Python. In the next chapter we will rise to the level of the operating system: files, processes and sockets.
