#CHAPTER 22 | Modules, tests and Cargo: how a project is organized
Learning Rust. Chapter 22. Modules, tests and Cargo: how a project is organized. In Python a project is a folder of files, a virtual environment, pip for dependencies, pytest for tests and a few more utilities, each with its own config. In Rust one program does all of this: Cargo. It creates the project, builds it, runs it, tests it, formats it and downloads dependencies. The project layout is the same for everybody, so when you open someone else's Rust repository you immediately know where everything lives. Today we look at how code is split into modules, how to control visibility, how to bring in other people's libraries and how to write tests.\n\nLet's start with Cargo. The command cargo new creates a package with a Cargo dot toml file and a folder for sources. Build compiles, run compiles and runs, check only verifies types, and so it is faster. Test runs the tests, fmt brings the code to a single style, clippy looks for suspicious constructs, and doc builds the documentation. Build results live in the folder called target. There are two build modes: the debug one builds quickly and includes overflow checks, while the release one turns on optimizations and runs many times faster, like the difference between minus O zero and minus O three in a C compiler.\n\nCode is split into crates and modules. A crate is a unit of compilation: either an executable, with a main function, or a library. A package can contain both. Inside a crate there is a tree of modules: the word mod declares a module, and its contents live either in curly braces or in a separate file with the same name. Items are reached by a path with double colons: from the crate root, from the current module through self, or from the parent through super. The use directive brings a name into scope, can rename it with as, and can pull in several names at once in curly braces.\n\nVisibility in Rust is private by default: everything you did not mark with pub is visible only in its own module and its children. Pub opens an item to the outside, pub crate opens it inside the crate, and pub super opens it to the parent. Struct fields are private separately, and that matters: while a field is private, the struct cannot be built from other modules except through your constructor, which means the constructor can check invariants. For example, a percentage can never be created out of range. In Python this stays a gentleman's agreement; in Rust it is a rule of the compiler.\n\nTo give users a convenient interface, you do not have to repeat the internal file structure. Pub use re-exports an item under a shorter path: the user writes the library name and the type, not a chain of five modules. Frequently used items are collected into a prelude that is imported with a single line. The internal parts stay private, so you can change them without breaking outside code. This is the basis of semantic versioning: the public interface is a promise, and the private part is your own business.\n\nDependencies are listed in the dependencies section of the Cargo dot toml file: the crate name and a version. An entry like one dot two means any compatible version starting from this one: Cargo will pick the newest one from the one-dot-something line and remember the choice in the Cargo dot lock file, so that builds are reproducible. Crates can be pulled in with a set of features: turn on the ones you need, and only the needed code is built. Dependencies for tests go into a separate section. Every foreign crate is code you trust, so it is worth counting and reviewing the number of dependencies.\n\nDocumentation is written right in the code. Three slashes before an item make a documentation comment, and two slashes with an exclamation mark describe a whole module or crate. Inside a comment you write code examples, and the command cargo test runs them as real tests, so documentation cannot quietly go stale. Cargo doc turns this into nice pages, just like the ones on the standard library documentation site. The habit of starting a function description with one concise sentence and giving an example pays off.\n\nNow tests. Unit tests live next to the code in a module with the attribute cfg test, which is turned on only when tests run. A function marked with the attribute test is a separate test. Inside you use the macros assert, assert eq and assert ne, and an expected panic is marked with the attribute should panic. A test can return a Result and use the question mark. Since the test module is a child, it sees even the private functions of its parent, and testing internals is convenient. By default tests run in parallel in different threads, and the output of passing ones is hidden.\n\nIntegration tests live in the folder tests next to the sources. Each file there is a separate crate that sees only the public interface of the library, exactly as a user will see it. Shared helper functions go into a subfolder with a file mod dot rs, so that Cargo does not treat it as a separate test. This split hints at what to test: internals are checked by unit tests, and the contract by integration tests. An executable crate is also usually split: a thin main calls the library, and all the logic lives in the library and is covered by tests.\n\nGood tests follow a simple pattern: prepare the data, perform the action, check the result. Tests are often written as a table: a list of pairs of input and expected result, and one loop runs them all. Most important are the edge cases: empty input, zero, the maximum, negative values. A test must be deterministic, with no random numbers and no dependence on time. To check the tests themselves, you can deliberately break the implementation and make sure at least one test turns red; this technique is called mutation testing.\n\nFor public libraries it is important to think through errors. Return a Result with your own enum of errors, implement Display and the Error trait, add From for foreign errors so that the question mark works. The method source lets you reach the cause, and this is how chains are formed. An enum can be marked non exhaustive, and then it is allowed to add variants to it in the future without breaking compatibility. Panicking in a library is acceptable only on a violation of a contract that you described in the documentation, in a section called panics.\n\nWhat remains is conditional compilation and global state. The attribute cfg and the macro cfg choose code for an operating system, a word size, a build mode or a feature. Constants and functions can be evaluated at compile time with the word const: a table of squares or factorials will end up right in the executable. Global counters are made from atomic types, and a value that must be initialized once is stored in the type OnceLock. Rust does not like mutable global variables: they need unsafe code, so they are almost never used.\n\nLet's sum up. Cargo builds, tests and manages dependencies, and a project is split into crates and modules with visibility that is private by default. Pub use shapes the public interface, features and versions control dependencies, and documentation runs as tests. Tests come as unit and integration tests, and good tests check the boundaries and catch a deliberately broken implementation.
