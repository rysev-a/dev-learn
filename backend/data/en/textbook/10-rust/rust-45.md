#CHAPTER 45 | Application state and tower layers
Learning Rust. Chapter 45. Application state and tower layers. A chat has shared things that every handler needs: settings, a pool of database connections, a list of connected clients, counters. And it has cross-cutting logic that belongs not to one route but to all of them: authorization checks, timing, a limit on request size, a header with the request number. The first problem is solved by application state, the second by layers. In this chapter we will learn both, without breaking the ownership rules and without blocking a thread.\n\nState is a value that the router stores and hands to every handler. You pass it with a call to with-state, and the handler receives a State extractor of the right type. The state type has to be cloneable: a clone is handed out for every request. That is why an Arc sits inside: only the reference counter is cloned, and the data stays shared. A type mismatch is caught at compile time: if a handler asks for state of one type and the router was given another, the program will not build. State is the main way to share the database, settings and channels between handlers.\n\nFor counters, atomic numbers are enough: they need no locks. For data that is read often and changed rarely, an RwLock fits. For short modifications, an ordinary mutex. The main rule: a lock from the standard library must not be held across an await point. Otherwise the future stops being sendable between threads, and while it waits, other tasks run into somebody else's lock. The solution is to take what you need in a short scope and release it before the await. If you really do need to hold a lock across an await, use the Tokio mutex: that is exactly what it was made for.\n\nIt is handy to keep not only data in the state, but also channel senders. Through a broadcast channel a handler sends an event to all subscribers: later we will use this to deliver chat messages over WebSockets. Through an mpsc channel a handler hands work over to a background task, for example writing to the database in batches. A sender is cheap to clone, and receivers are created on demand. This makes the coupling between parts of the application loose: the handler does not know who will process the event or how, it simply publishes it.\n\nWhen the state grows, a handler should not need to know about the whole application. The FromRef trait lets you extract a part of the state: you ask for the configuration, and you get a clone of the corresponding field. Then a handler depends on exactly what it needs, and tests supply only that part. For simple structs the implementation can be generated with a macro, for complex ones you write it by hand. So the state stays a single value for the router, but each handler sees its own narrow window. This reduces coupling and makes it easier to restructure the application.\n\nThere are two ways to pass data to a handler. State is known when the router is built, it is typed and checked by the compiler. Request extensions are added on the fly: a layer puts a value into the request, and the handler picks it up with the Extension extractor. This is how an authorization layer tells the handler who has arrived. The price of this flexibility is a check at run time: if the layer did not run, and the handler asks for an extension, the response is a server error. So keep permanent things in the state, and the data of one particular request in extensions.\n\nA layer is a factory of wrappers. It takes a service and returns a new service that does something before and after calling the original one. This is how timeouts, concurrency limits, compression and tracing are built. Layers stack like matryoshka dolls: the outer one sees the request first and gets the response last. The ServiceBuilder lets you list the layers from top to bottom, in the order they run. All of this is independent of any particular protocol, so layers from tower fit clients, servers and any other services.\n\nWriting a layer by hand takes a long time, so axum has the function from-fn. You write an async function that takes a request and the next step, and returns a response. Before calling the next step you can change the request, or stop processing altogether and return a response, for example four hundred and one. After it, you can change the response: add a header, measure the time. The variant with state gives the function access to the shared state. For small transformations there are also map-request and map-response, but from-fn covers almost everything you need in practice.\n\nThe order of layers matters. The layer method wraps everything that was added to the router before it, so the last layer added ends up the outermost and sees the request first. The route-layer method applies only to matched routes, and a request to a nonexistent path is not affected by it. In ServiceBuilder the order is the opposite: the layer listed first is the outermost. A classic mistake: the authorization layer ended up outside the tracing layer and rejected responses without anything written to the log. Check the order with a test that prints the sequence of calls.\n\nMost needs are covered by ready-made layers. Tower-http contains request tracing, cross-origin request headers, a timeout, a body size limit, compression and static file serving. Tower itself provides a concurrency limit and a simple rate limit. Such layers are plugged in with one line and behave the same in every project. Write your own layer when the logic is specific to the application: authorization, usage accounting, special request correlation. And take the common things ready-made: less code, fewer bugs.\n\nWhen the log has thousands of lines, you need a way to tie them to one request. For this, a layer assigns an identifier to every request: it takes it from an incoming header or creates a new one, puts it into the request extensions and returns it in a response header. Handlers and nested calls add the identifier to every log record. Processing time is measured by the same layer: note the start, wait for the response, record the duration. This gives you the minimum of observability, without which debugging errors in a production system turns into guesswork.\n\nA public service has to be protected. A body size limit layer answers four hundred and thirteen without reading any extra data. A timeout layer interrupts handlers that run too long and answers four hundred and eight. A concurrency limit does not let in more than a given number of requests at once, and the rest wait their turn. A token bucket rate limit cuts off overly persistent clients. These layers are cheap and cover most accidental and deliberate overloads. The values should be chosen from real measurements, not at random.\n\nLet us sum up. Application state is a typed value with shared data, with an Arc inside, and for changes, atomics and locks that are not held across an await. Request extensions carry the data of one particular request, for example who has arrived. Layers wrap services: the outer one sees the request first. Your own layers are easiest to write with from-fn, and the common ones should be taken from tower-http. Check the order with a test. In the next chapter we will deal with data: serde, JSON and a single error type for the application.
