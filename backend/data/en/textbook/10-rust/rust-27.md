Learning Rust. Chapter 27. I/O and files: Read, Write, BufRead and Path. A program talks to the world through streams of bytes: it reads the keyboard and files, and writes to the screen and to the network. In Rust these operations are described by two traits: Read for sources and Write for sinks. A file, a socket, standard input, a byte slice and a vector all implement the same interface. Thanks to this, you can write a function once and test it on data in memory, without touching the disk. Every operation returns a Result with an I/O error, so read and write errors are handled just like any other errors.\n\nThe Read trait has one required method, read. It fills a buffer and returns the number of bytes read, and zero means the end of the stream. Convenient methods are built on top of it. read_to_string reads everything into a string, read_to_end reads into a vector of bytes, and read_exact fills a buffer exactly. The take method limits reading to a number of bytes, and chain glues two sources together. Cursor wraps a vector or a slice into a source that has a position. A byte slice implements Read itself, so a string literal with the b prefix works fine as a data source.\n\nThe Write trait requires the write method: it takes a slice of bytes and returns how many were written. Usually people use write_all, which repeats the write until everything is sent. The flush method pushes buffered data through to the sink. A vector of bytes implements Write, so you can print into it and then turn it into a string. The macros write and writeln work with any Write: they format and write. This is exactly how println writes to standard output. Standard output and standard error are also Write, and by convention an error is written with eprintln, so it does not get mixed with the data.\n\nReading in small pieces is expensive: every operation is a system call. That is why a buffered wrapper is put on top of the source. BufReader reads large chunks and hands them out in parts, and the BufRead trait adds line-by-line reading: read_line appends a line to a buffer, lines returns an iterator over lines, and read_until reads up to a delimiter. For writing there is BufWriter: it collects data and writes it in a batch, and when it is dropped it flushes the rest. For console output, line by line, LineWriter is a good fit. These wrappers combine easily and do not change the shape of your code.\n\nStandard streams. The function stdin returns the input, stdout the output, and stderr the error stream. To read a line: stdin dot read_line, open parenthesis, ampersand mut buffer, close parenthesis. Each call takes a lock, so for fast reading you take the lock yourself: stdin dot lock with empty parentheses returns a BufRead, which has lines. For large output you take the stdout lock and wrap it in a BufWriter: this speeds up tasks that print a million lines by tens of times. Don't forget flush after a prompt without a newline, otherwise the text may not appear until the next output.\n\nFiles. The fs module contains the shortest ways to do things: read_to_string reads a whole file, write creates or overwrites, read returns bytes, copy copies, rename renames, remove_file deletes, create_dir_all creates a chain of directories, read_dir lists the contents, and metadata returns the size and times. For fine control there are File open, File create and OpenOptions with the flags append, truncate, write and create_new. A file closes itself at the end of its scope because it implements Drop, so you don't need to close it by hand.\n\nPaths. The type Path is a reference to a path, and PathBuf is the owning version, just like str and String. They don't have to be Unicode, because in operating systems file names are just bytes. The method join adds a component, parent returns the parent, file_name and file_stem give the last part, with and without the extension, extension gives the extension, and with_extension replaces it. components splits a path into parts, and is_absolute and exists answer questions. For printing you use the display method, which returns a wrapper with formatting. Platform differences in slashes and drives are hidden: write the code as if it runs everywhere.\n\nI/O errors. The type io::Error carries an operating system code and a kind of error, which you find out with the kind method: NotFound, PermissionDenied, AlreadyExists, Interrupted, UnexpectedEof. The question mark operator passes them up, and in top-level functions you write a Result with a boxed error, to combine different types: Box of dyn Error accepts any error. For messages with context, the anyhow crate adds a description such as "could not open such-and-such file". The expect method suits examples and scripts, but in programs for users it is better to show a clear message, not a panic.\n\nRandom access. The Seek trait lets you jump to any position: SeekFrom takes the start, the end or the current position with an offset. Both File and Cursor implement Seek. You need this for formats with offset tables, for a database, and for reading the last lines of a big log. The method set_len changes the size of a file, and sync_all asks the operating system to flush data to disk. For files of gigabytes you use memory mapping through the memmap2 crate. Be careful with simultaneous writes from different processes: the standard library does not promise atomicity, and file locks appeared only recently.\n\nWrite generic code. A function process, generic over R that is BufRead and W that is Write, taking input of type R and output of type W, works the same way with files, network connections and data in memory. When you call it from a test with a Cursor and a vector, you check the logic without a disk, quickly and without temporary files. In the main function you plug in standard input and output. This is the simplest form of dependency injection in Rust, and many command-line utilities are built exactly like this: read from a stream, transform, write to a stream.\n\nProcesses. The process module launches other programs: Command new with arguments, and the output method returns the exit code and everything the program printed. The spawn method starts it and returns a child process, which you can talk to through pipes: Stdio piped gives access to its input and output. The wait method waits for it to finish. Environment variables are passed with the env method. You set your own program's exit code with the exit function, or by returning a Result from main: an error turns into a non-zero code and a message on the standard error stream. This is how you build command-line utilities that work in scripts.\n\nBinary data. You can read numbers from a stream by hand: read four bytes and call from_le_bytes or from_be_bytes, depending on the byte order of the format. The byteorder crate gives methods like read_u32 for a chosen order. For structured data people use serde with formats such as JSON, bincode and MessagePack, and for network protocols, the bytes crate and codecs. Don't write structs directly as bytes: the memory layout and byte order depend on the platform, while explicit serialization gives you portability across processors and program versions.\n\nLet's sum up. Read and Write are a common language for files, sockets and memory. Buffering is a must when work goes in small pieces: BufReader and BufWriter. The fs module solves typical tasks in one line, Path and PathBuf describe paths, and io::Error carries the kind of the error. Seek gives random access, Command launches processes, and binary formats are read with an explicit byte order. Write your functions generic over Read and Write, and you can test them without a disk.
