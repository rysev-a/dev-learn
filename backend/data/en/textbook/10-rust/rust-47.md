Learning Rust. Chapter 47. PostgreSQL and sqlx: chat data. So far our rooms have lived in memory and vanished on every restart. A real chat needs reliable storage: users, rooms, members, and message history. We will keep all of it in PostgreSQL and talk to it through sqlx. This chapter is about the bridge between two worlds: table rows turn into structs, database errors turn into application errors, and several changes are gathered into one atomic transaction. How databases work inside is covered in detail in a separate book; here we simply take a finished one.\n\nPostgreSQL is a solid relational database. It gives you transactions with isolation and integrity constraints: uniqueness, foreign keys, and checks. Indexes speed up lookups, and multiversioning lets readers avoid blocking writers. Many server processes talk to the database at once, and it keeps order on its own. There are nice extras too: types for time, identifiers, and JSON, and a notification mechanism that we will use for the chat. We have already looked at how a client and server talk over the PostgreSQL protocol; now a reliable client library will speak it for us.\n\nsqlx is an asynchronous client with no object-relational wrapper. You write queries in real SQL, and the library takes care of connections, the protocol, parameter binding, and parsing rows into types. The driver is written in pure Rust and runs on top of Tokio. There are macros that check queries at compile time against a live database, but we will get by with functions that check the match at run time. This approach is transparent: what you write is what runs, and the performance and the query plan stay under your control.\n\nOpening a connection for every query is expensive, so we use a pool. It keeps several connections, hands out a free one on demand, and takes it back when you are done. The pool size is limited, because the database itself has a cap on simultaneous connections. If all of them are busy, the query waits, and after a set time it gets an error. The pool is cheap to clone and lives in the application state. An important rule: never hold a connection during a long unrelated operation, such as waiting for a reply from an external service. Otherwise a few slow requests will drain the pool and stop the whole application.\n\nQueries are run with the functions query, query-as, and query-scalar. The first returns raw rows, the second builds structs, and the third returns a single value. In PostgreSQL, parameters are marked with a dollar sign and a number, and you attach them with the bind call. You must never put values into a query through string formatting: that is the road to code injection. Bound parameters travel separately from the query text, so the database never mistakes them for commands. You get results with different methods: exactly one row, an optional row, all rows, or a stream. A missing row has its own error variant.\n\nThe FromRow derive builds a struct from a result row by column names. The types map naturally: a big integer to i64, text to a string, a boolean to bool, a timestamp with time zone to a chrono date-time, an identifier to a UUID, and JSON to a value or a typed wrapper. A nullable column corresponds to an Option. If a type does not fit, the error appears when the very first row is decoded, not when the data is sent to the client. Fields can be renamed with an attribute, so column names and field names do not have to match.\n\nAn insert with a RETURNING clause immediately gives back the created row or the columns you need, such as the identifier and the creation time. No second query is needed, and there is no race between the insert and the read. The ON CONFLICT clause makes an insert idempotent: either do nothing if the record already exists, or update it. The number of affected rows that execution returns tells you what actually happened. This way, creating a room with the same name again can be handled without an error, and view counters can be incremented with a single command, with no separate read and write.\n\nA transaction groups changes: either all of them are applied, or none. The begin method returns a transaction object, queries run through it, and commit makes the result permanent. If the object is dropped without a commit, for example because of an early exit on error, the changes are rolled back automatically. This works wonderfully together with the question mark operator. An example for the chat: create a room and immediately add its author as a member. For tasks like a job queue there is row locking that skips busy rows, so that several workers take different jobs and do not get in each other's way.\n\nThe database schema changes along with the code, and that has to be managed. Migrations are numbered files with SQL commands. A special table remembers which ones have already been applied, and a run applies the missing ones in numeric order, inside a transaction. An applied migration is never edited: a schema change is a new migration. sqlx can embed the migrations directory into the program at build time, and the server brings the database to the right version on startup. In the exercises we will write a tiny migration runner ourselves, to understand exactly what happens.\n\nThe chat schema is simple. Users have a unique name and a password hash. Rooms have a unique title. Members link users to rooms with a composite key. Messages store the room, the author, the text, and the time, and the identifier grows monotonically. Foreign keys do not let you refer to a room that does not exist, and a check constraint forbids empty text. An index on the room and the message identifier in descending order makes the main query fast: the latest messages of a room. A good schema is half the defense against bugs: some invalid states simply cannot be written.\n\nDatabase errors come in different kinds. A missing row is not a failure but a not-found variant. Constraint violations carry five-character codes: twenty-three oh-five-oh-five means a duplicate value in a unique column, twenty-three oh-five-oh-three means a reference to a row that does not exist, and twenty-three oh-five-one-four means a check failed. We translate them into application errors: uniqueness becomes a conflict, a foreign key becomes not found or invalid input, and anything else becomes an internal error that is written to the log. That way the client gets a meaningful answer.\n\nDatabase efficiency is mostly about writing the right queries. An index for a frequent lookup speeds it up by orders of magnitude. The classic trouble is a query in a loop: a separate members query for every room. It is solved with one query that uses a join, or one that selects by an array of identifiers. A bulk insert is done in a single command that unpacks arrays. Pagination is better built on a key: messages before a given identifier, rather than by offset, which skips more and more rows as the page number grows. And the explain command shows the query plan.\n\nLet's sum up. PostgreSQL gives the chat reliable storage with transactions and constraints. sqlx is an asynchronous client with no wrappers: a connection pool in the application state, parameters only through bind, and rows turned into structs. RETURNING and ON CONFLICT make inserts precise and repeatable. Transactions roll back on their own if you drop them. Migrations keep the schema in step with the code. Constraint violations are translated into application errors by their codes. In the next chapter we will add users: registration, password hashes, and login with a token.
