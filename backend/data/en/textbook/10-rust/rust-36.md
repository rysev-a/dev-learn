#CHAPTER 36 | Tokio: networking and asynchronous I/O
Learning Rust. Chapter 36. Tokio: networking and asynchronous I/O. Networking is the main reason asynchrony appeared at all. If you keep a separate thread for every connection, ten thousand clients will demand ten thousand threads and gigabytes of memory. The asynchronous approach is different: while a client is silent, its task sleeps and does not occupy a thread, and the operating system tells Tokio, through a mechanism like epoll, that a socket is ready. A single thread can serve thousands of connections this way. In this chapter we will write an echo server and go through reading and writing, splitting a stream, message framing, datagrams, and streams of data.\n\nA server starts with a TCP listener. The bind method attaches it to an address and a port, and accept waits for the next client and returns a socket and the client's address. If you give port zero, the operating system picks a free one, and local_addr shows which one exactly. The client calls TcpStream connect with an address and also waits through await. For testing inside one program, an address on the loopback interface is enough: the server and the client run in different tasks and talk through a real socket. This is the most convenient way to test networking code without a network.\n\nFor byte streams Tokio has two traits, AsyncRead and AsyncWrite, and the convenient methods live in extension traits. Read reads into a buffer and returns how many bytes were received. Zero means the end of the stream: the other side closed the connection. Read can return less than you asked for, so a whole message cannot be obtained with one call. Read_to_end reads until the end, read_exact reads exactly as many bytes as you specify, or fails with an error. Write may write only part of the data, so people use write_all, which writes everything. And do not forget flush for buffered writers.\n\nThe classic server scheme is an endless loop in which accept takes a client and spawn starts a separate task to serve it. The loop immediately goes back to waiting for the next client, so a slow client does not get in the way of the others. The echo server in its task reads data and writes it back until it gets the end of the stream. The task owns the socket, and when it finishes, the socket is closed. The errors of one client must be handled inside its task so that the server does not go down. You will repeat this skeleton in any networking project, changing only the handler.\n\nMany protocols are text-based: a command ends with a newline. For them there is the buffered reader: it accumulates what was read and lets you read line by line. The lines method returns an asynchronous iterator, whose next_line hands out the next line without the newline, or nothing at the end of the stream. Read_line appends a line to the variable you pass in and returns the number of bytes read. The buffered reader noticeably reduces the number of system calls: instead of reading byte by byte, it reads in large chunks. For writing there is a similar buffered writer, which you must flush.\n\nThe main thing to understand about TCP: it is a stream of bytes, not a stream of messages. Two sends can merge into one read, and one send can be split into two. So you have to define message boundaries yourself. The first way is a length prefix: first four bytes with the length, then the data; the receiver reads the header and then exactly that many bytes. The second is a delimiter, like the newline in text protocols. In tokio-util there are ready-made codecs, for example one with a length prefix, which turn a stream of bytes into a stream of whole messages.\n\nA socket can both read and write, but sometimes these actions have to run independently: one task receives data, another sends. The split method divides the socket into two halves, and into_split hands out owned halves that can be moved into different tasks. The reading half knows nothing about the writing one, so there are no borrowing problems. This is how full-duplex protocols are built: chat, multiplexing. If you need to connect two sides directly, there is the copy_bidirectional function, which pumps data in both directions and finishes when both streams are closed.\n\nYou also need to know how to close a connection. When a socket is dropped, both directions are closed. But sometimes you need to close only the writing side, saying I have sent everything, and wait for a reply. For this there is shutdown on the writing half. The other side gets the end of the stream, understands that the request is over, and sends a reply. If the connection is broken, reading returns an error: connection reset, broken pipe, or unexpected EOF. A dropped connection is routine on a network, and the client handler must survive it, recording the event and finishing only its own task.\n\nUDP is different: there is no connection, only separate datagrams. A UDP socket is attached with bind, sends with send_to and the recipient's address, and receives with recv_from, which returns the data and the sender's address. Boundaries are preserved: two sends give two reads, with no merging and no splitting. But there are no guarantees of delivery, order, or absence of repeats: a datagram can be lost or arrive twice. So UDP is used for protocols where loss is acceptable, for example games, video streaming, and service discovery on a network, and reliability, if needed, is added on top.\n\nA network is full of hanging operations: the other side stopped answering, but the connection is not closed. Without a limit, your task will wait forever. That is why every wait is bounded by a timeout or wrapped in a select together with a stop signal. The accept loop also listens for the stop signal, so that the server can shut down gracefully instead of being cut off in the middle of work. For clients you set separate limits for connecting, for the reply, and for idling. Reasonable values depend on the task, but forever is almost never right: that is how hanging tasks and sockets pile up.\n\nA stream is an asynchronous iterator: values appear over time, and each one is received through await. The tokio-stream crate and the StreamExt trait give you familiar operations: next, map, filter, take, collect. A channel receiver becomes a stream with the ReceiverStream wrapper, and a plain iterator with the iter function. To copy bytes between streams there is the copy function, which reads from one and writes to the other until the end, and duplex, a pair of streams connected in memory, very handy for testing networking code without sockets.\n\nFile operations on most systems cannot be made truly asynchronous, so tokio fs runs them in a thread pool, and the task waits for the result. The interface is familiar: read, write, open, create. Any other blocking code, for example heavy computation or an old library, is launched through spawn_blocking so as not to freeze the worker threads. Name resolution is done by the lookup_host function, and sockets within one machine are handled by UnixListener and UnixStream, which work the same way as TCP but over a path in the file system.\n\nLet us sum up. Asynchronous I/O lets one thread serve thousands of connections. A server is built on an accept loop and a spawn for each client, a client on connect. A read can return less than expected, and zero means the end of the stream, so TCP needs framing by length or by delimiter. Split gives independent halves, shutdown closes the writing side, and UDP works with datagrams. Every wait must be limited by a timeout or a stop signal. Streams give asynchronous iterators, and files and blocking code go to separate threads. In the next chapter we will put all this together into a robust application.
