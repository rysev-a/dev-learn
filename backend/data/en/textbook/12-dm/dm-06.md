#CHAPTER 6 | Predicates and quantifiers
Discrete mathematics. Chapter 6. Predicates and quantifiers. Every working day you write conditions: if the user is an admin, if the array is not empty, if the response arrived in time. Behind those lines stands a strict language that lets you talk about all the cases at once rather than checking them one by one. Today we take from the logician's table two main tools: predicates, that is, statements with a variable, and quantifiers, that is, the words "for every" and "there exists". Without them you cannot explain what "the code works for all inputs" means — and that is exactly what you prove with each of your tests.\n\nLet's start with a simple observation: the phrase "x is greater than five" is neither true nor false. It hangs in the air until we find out what x equals. Such a template with a variable is called a predicate: substitute a value and you get an ordinary statement, which is already either true or false. The predicate "age is greater than eighteen" gives true for the value twenty and false for the value fifteen. Nothing mystical: it is a function that takes a value and returns a boolean.\n\nYou use predicates constantly, you just rarely say the word. The filter method takes a predicate and keeps only the elements on which it is true. The find method looks for the first element on which the predicate becomes true. The condition inside an if is the same kind of predicate over the variables of the program's state. As soon as you start seeing statements with a variable in such functions, you have a language in which they can be reasoned about strictly.\n\nNow, how to turn predicates into complete statements. The first way is the universal quantifier, in human speech "for every" or "for all". We say: for every x it is true that x plus zero equals x — and we get a statement that is already either true or false. An everyday example: "all passengers are buckled up" is about each one without exception, and a single unbuckled passenger is enough to refute it. Notice: a statement about everyone cannot be proved by checking a couple of cases — it requires a general argument that works for any value.\n\nThe second way is the existential quantifier, in human terms "there is" or "there exists". The phrase "among the guests there is a vegetarian" is true if at least one guest fits, and false if nobody fits. Proving such a statement is easy — one example is enough, that is its charm. Refuting it is harder: you have to explain why nobody fits. In your work these are two different tasks: proving that a bug exists can be done with one reproduction, while proving that there are no bugs is a completely different conversation.\n\nIt is time to see quantifiers in your own tests. An ordinary unit test is an existence statement: on these three inputs the function gives the right answer. Property-based testing is already the universal quantifier: for all generated inputs the property must hold, for example for any two lists the concatenation preserves the length. And here an iron rule of logic works: a "for all" statement is refuted by a single counterexample. One input on which the test failed is enough — and the property is declared violated, no matter how many green runs cover for it.\n\nQuantifiers have negation rules, and they are surprisingly practical. It is not true that "for all it holds" means that there is one for whom it does not hold: if not all passengers are buckled up, then there is an unbuckled one. Symmetrically: it is not true that "there exists one for whom it holds" means that for all it does not hold: if there is no vegetarian among the guests, then every guest eats meat. These are De Morgan's mirrors for quantifiers: negation honestly moves inside, flipping the quantifier to the opposite one. No magic — just a careful translation from English into English.\n\nIn code the same rule looks like a flip. If it is not true that every element of the array passed the every check, then there is an element that failed it — and that is exactly what some will return with the negated predicate. Reading "the predicate is not true for all elements" is harder than "there is an element for which it is false", although the meaning is the same. A useful skill in review is noticing double negations and untangling them with this rule: the formulas tell you how to rewrite the phrase without getting dizzy.\n\nAnd here is the place where logic really bites: the order of quantifiers changes the meaning. Compare two statements about mothers: every person has a mother — and there is a person who is the mother of everyone at once. The first is trivially true, the second is absurd. Formally: for every x there exists a y is not the same as there exists a y for every x. In the second case one y is chosen for everyone, in the first each x gets its own. A mixed-up order of quantifiers is a classic source of errors in requirements and interfaces.\n\nLet's carry this over into the language of development. The requirement "for every request there is a handler" is normal: for each type of request a handler has been set up. The requirement "there is a handler for every request" sounds similar but means a universal stub that responds identically to everything. Requirements for a system almost always contain hidden quantifiers, and their order is part of the contract. Before arguing at planning, write the quantifiers out explicitly: it often turns out that you were arguing about different formulas.\n\nIn practice quantifiers are almost always restricted to a domain: we say not "for all x in general" but "for all x from the list of users". The restriction is the familiar filter before the check: we take not the whole world but the set we need. In property-based tests the role of the restriction is played by generators: integers from zero to a hundred, non-empty strings, valid JSON. A subtlety hides here: the test checks the quantifier not over the whole world but over the domain of the generator. If the generator never produces negative numbers, the statement "for all numbers" has in fact been checked only for the positive ones.\n\nLet's put together a pocket reference. A "for all" statement is proved by a general argument that works for any value — and is destroyed by one counterexample. A "there exists" statement is proved by one example — and is destroyed by a general argument for why nobody fits. Hence the debugging strategy too: to refute "the function is correct", look for a minimal counterexample, and to refute "the function always crashes", one successful run is enough. Logic tells you from which side it is cheaper to attack any statement.\n\nLet's sum up. A predicate is a statement with a variable, a template that becomes true or false when a value is substituted. The quantifiers "for every" and "there exists" turn templates into statements about all cases or about one, and negation simply flips the quantifier to the opposite one. The order of quantifiers is part of the meaning, and a mixed-up order changes the contract. Tests are quantifiers in practice: unit tests check "there exists", property-based ones check "for all", and one counterexample is stronger than a thousand green runs. In the next chapter we will learn to honestly prove "for all" statements on infinite sets: this is mathematical induction, the closest relative of your recursion.
