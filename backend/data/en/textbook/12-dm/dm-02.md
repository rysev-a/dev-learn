#CHAPTER 2 | Relations and functions
Discrete mathematics. Chapter 2. Relations and functions. Every database you have ever designed is full of relations: an order is linked to a customer, a post to an author, a comment to a post. Every module you have written is full of functions. Today we will see that mathematics describes both with a single vocabulary — and this vocabulary makes reasoning about data schemas and module interfaces surprisingly precise.\n\nLet's begin with a pair, but not just any pair — an ordered one. In a set, order played no role at all; here order is the essence of the thing: the first element and the second element occupy different positions. A point on a map is given by the pair latitude, longitude, and you can't swap them — you would get a different place. In code you store such things as tuples and two-element arrays where position carries meaning — and that is all the mathematics of a pair.\n\nIf you take all possible pairs from two sets, you get the Cartesian product. Three T-shirts and two pairs of trousers make six outfits — and all six are already sitting in the Cartesian product. This is the mathematical groundwork for the product rule, on which all the combinatorics of the next chapter rests. In databases the Cartesian product corresponds to the cross join of tables — the very join which, with no filtering condition, produces every combination of rows.\n\nA relation is simply a subset of the Cartesian product: some pairs are marked as related, the rest are not. The relation "an order belongs to a customer" is a set of order–customer pairs, and in a database it is stored as a foreign key. The relation "is friends with" is a set of pairs of people, symmetric by its meaning. The philosophy here is pleasant: a table in a database is a relation, and the whole theory of relational databases is the theory of relations, which is where the word "relational" came from.\n\nRelations have properties, and the first is reflexivity: every element is related to itself. The relation "equals" is reflexive: any number equals itself. The relation "less than" is not reflexive: a number is not less than itself. In a data schema reflexivity occurs more naturally than it seems: an employees table that refers to itself through a manager calmly allows records where both halves of the pair point to the same row.\n\nThe second property is symmetry: if the first is related to the second, then the second is related to the first. Friendship in a social network is symmetric: both became friends. A subscription is not symmetric: you follow an author, but the author does not follow you. It is convenient to phrase this difference exactly like that, because it instantly turns into a schema check: in a friendship table the pairs are stored in both directions, or the lookup goes in both directions, while in a subscriptions table only in one.\n\nThe third property is transitivity: if the first is related to the second, and the second to the third, then the first is related to the third as well. The relation "is an ancestor of" is transitive: an ancestor of an ancestor is also an ancestor. The relation "knows" is not transitive: a friend of your friend is not necessarily your friend, and that is exactly why social networks show them to you as a recommendation. Transitivity lives in the world of package managers too: a dependency of a dependency is your dependency, and this whole chain is called exactly that — transitive dependencies.\n\nLet's put the three properties together: a relation that is reflexive, symmetric and transitive is called an equivalence relation. The classic example is equality, but there are more interesting ones: "were born on the same day" or "have the same remainder when divided". The most important consequence: an equivalence cuts a set into non-overlapping classes inside which everything is considered the same. Grouping by a key in your favorite language is exactly a partition into equivalence classes, and the result of grouping by a field in a database is ready-made classes.\n\nThere is a second famous set of properties: reflexivity, antisymmetry and transitivity give a partial order relation — like "less than or equal to" on numbers. The word "partial" is key here: there are elements that cannot be compared with each other at all. In a dependency tree two packages from different branches are not ordered relative to each other, and that is normal. When you need to stretch the order into a line, topological sorting works — it assembles a partial order into a sequence of builds or migrations.\n\nNow functions. A function is a relation with a strict contract: every element of the first set, the domain, has exactly one image in the second set, the codomain. No two answers for one input and no inputs without an answer. A function signature in a programming language is the same contract written in types: a string comes in, a number comes out. The difference is that a mathematical function cannot crash and cannot return different results for the same inputs — and that is a standard worth striving for in code.\n\nFunctions are distinguished by how they fill the output. An injection: different inputs give different outputs, nothing is glued together — like unique user identifiers. A surjection: every element of the output is occupied by someone, there are no empty places — like seating guests so that no free chairs are left. A bijection is both at once: a one-to-one correspondence that can be turned back around. A bijection is precisely an invertible function, and encoding and decoding live exactly on bijections.\n\nA pure function in programming is a mathematical function by construction: the result depends only on the arguments, and there are no side effects. It does not look at the current time, does not read global variables and does not write to a database, so it answers the same input with the same output — as a function should. Tests love it for that: one input, one expected output, with no mocks and no environment setup. And memoization goes a step further: it saves input–output pairs in a cache, turning a computation into a ready table of correspondences — and a table of pairs, if you remember, is a relation.\n\nLet's sum up. Pairs gather into a Cartesian product, a subset of the product is a relation, and reflexivity, symmetry and transitivity divide relations into equivalences and orders. A function is a relation with the contract "exactly one output", and its varieties — injection, surjection and bijection — describe how the output is filled. Foreign keys, grouping, topological sorting and pure functions — all of this is one vocabulary. In the next chapter we take up the calculator: combinatorics will teach us to count how many there are in total — from PIN codes to poker hands.
