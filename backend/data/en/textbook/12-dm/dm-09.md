#CHAPTER 9 | Graph traversals and trees
Discrete mathematics. Chapter 9. Graph traversals and trees. While you sleep, the garbage collector walks the graph of live objects of your application, a search engine crawler walks the graph of pages, and a package manager walks the graph of dependencies, deciding what to install first. Graph traversal is the ability to visit all the vertices without getting lost and without looping, and it is one of the most reused ideas in programming. Today we will go through two ways of traversing, find out what a tree is, and what the bridges of Königsberg have to do with it. You will meet all of this later in production — already recognizing it by sight.\n\nLet's state the problem honestly. We are given a graph and a starting vertex; we need to visit everything reachable from it, each vertex exactly once. The catch is in cycles: without memory, a traversal circles forever around one ring, like a guest without a map in a maze of an apartment. That is why any traversal has two organs: a way of choosing the next vertex, and a set of visited ones, which is consulted before every step. Different ways of choosing give birth to different algorithms, while the visited set is mandatory in each of them.\n\nThe first way is depth-first traversal. The rule is simple: go forward while you can, and when you hit a dead end, step back and try another door. It is a route through a maze with a thread tied to your finger: the thread remembers where you came from, and you return along it. It is important that such a route is naturally held by a stack: each new node is put on the stack, a dead end is taken off, and the top element always tells you where we are.\n\nThe beauty of depth-first traversal is that recursion is a ready-made stack built into the language for free. The function marks a node as visited and calls itself for each unvisited neighbor; the call stack itself remembers the way back. This is how the DOM tree is walked: recursively descending to the children inside each node. This is how directories are walked: a folder is a recursive call, a file is a leaf. Any recursive function strolling through a nested structure is a depth-first traversal, even if you have never called it that.\n\nThe second way is breadth-first traversal, and its motto is the opposite: first all the near ones, then the far ones. From the starting vertex we visit all the neighbors, then all the neighbors of the neighbors — the wave spreads in circles like on water. To keep the wave in order, you need not a stack but a queue: take a vertex out, add its unvisited neighbors to the end, and the "first in, first out" order guarantees processing by circles of distance. The stack and the queue are the only difference in the code, while the behavior of the algorithms changes radically.\n\nReplacing the stack with a queue gives a valuable property: breadth-first traversal finds shortest paths in an unweighted graph. The wave reaches every vertex by the minimal number of edges, because all the options at distance one are checked first, then at distance two. This is the logic of "friends of friends": social networks suggest to you people exactly two or three handshakes away. In a maze, breadth-first traversal will lead you to the exit by the shortest route, whereas depth can drag you along a long but first-found corridor.\n\nNow a utilitarian classic: finding connected components. The algorithm is indecently simple: walk through all the vertices, and whenever you meet an unvisited one, launch a traversal from it, marking all its kin. Each launch drains exactly one component, and the number of launches equals the number of islands. This is how isolated groups of users, clusters of services and disconnected pieces of a dependency graph are counted. Depth and breadth are interchangeable here — only the fact of complete draining matters.\n\nA special place of honor on this field belongs to trees. A tree is a connected graph without cycles: from any vertex to any other there is exactly one path, so getting lost is impossible. A tree has a small but mighty formula: if there are n vertices, there are exactly n minus one edges. Check it on examples: one vertex — zero edges, three vertices in a chain — two edges. The formula works in both directions: if a connected graph has exactly n minus one edges, there are no cycles and you are looking at a tree; add an edge and a cycle is born, remove one and it falls apart into pieces.\n\nLook around: trees are the most common form of graph in everyday development. A file system: a root folder, folders and files inside, each with exactly one parent. An abstract syntax tree: a program is parsed by the compiler into a tree of expressions. The browser's DOM tree: markup turns into a tree of nodes. A company hierarchy and product categories are arranged the same way. It is no accident that almost all the recursion of the previous chapter was practiced precisely on trees — it is the ideal environment: the base on the leaves, the step on the children.\n\nFrom the tree grows a practical problem: the spanning tree. Given a connected graph — say, a network of districts where roads need to be laid — we keep exactly n minus one edges so that the graph stays connected, and get a skeleton of the network with no extra edges and no cycles. If the edges have prices, the minimum spanning tree is interesting: the cheapest way to connect everyone. This is laying cables between servers, joining offices into a network, clustering points on a map. Algorithms for this exist and are splendid, but you have already got the essence: squeeze a tree out of a graph.\n\nFinally — the oldest problem of graph theory, born of a walk. In Königsberg there were seven bridges across the river, and the townspeople argued: is it possible to take a walk crossing each one exactly once. Euler proved that it is not, and reduced the matter to the degrees of vertices: in the middle of a walk each visit to a vertex uses up two edges — entering and leaving, so odd degrees can only belong to the start and the finish. The resulting rule: an Eulerian path exists only if there are zero or two odd vertices, and in the first case the route closes into a circle. In Königsberg there were four odd vertices — the walk is impossible, and graph theory was born.\n\nLet's put the traversals back into production. The garbage collector walks the graph of objects from the root references: everything reachable is alive, the rest is garbage; this is a breadth-first or depth-first traversal, depending on the implementation. A dependency resolver walks the graph depth-first and watches the "gray" state of a node to catch a cycle. A crawler is a breadth-first traversal with a set of visited addresses, limited by depth and by politeness toward servers. Reachability checks in access rights, finding the shortest path in a game, walking the DOM tree in tests — the same pair of algorithms with a change of scenery.\n\nLet's sum up. Depth-first traversal goes to the limit with the help of a stack and is conveniently written with recursion; breadth-first traversal spreads like a wave with the help of a queue and gives shortest paths. The visited set protects against cycles, and repeated launches drain the connected components. A tree is a connected graph without cycles, with n minus one edges, and it is the shape of a file system, a syntax tree and the DOM. Spanning trees squeeze a skeleton out of a network, and the bridges of Königsberg taught us to tell traversable graphs by their odd degrees.
