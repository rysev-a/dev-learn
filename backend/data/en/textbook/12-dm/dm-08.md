#CHAPTER 8 | Graphs: the basics
Discrete mathematics. Chapter 8. Graphs: the basics. Open the developer tools: the element tree is a graph. Look into your project's dependency manifest: the dependencies are a graph too, however strange the word "tree" sounds. Scroll through a social network: friends, subscriptions, recommendations — graphs again. Today we begin to speak about them in a strict language: what vertices and edges are, how to lay a graph out in memory, and why the sum of degrees is always even. This is the foundation for the next two chapters, where we will learn to walk along graphs.\n\nLet's start with the definition, and it will pleasantly surprise you with its simplicity. A graph is a set of vertices and a set of edges, where each edge connects a pair of vertices. That's all: no coordinates, no scale, no pretty lines — only objects and the links between them. A map of friends — the vertices are people, the edges are friendship. A metro map — the vertices are stations, the edges are the stretches between them, and it doesn't matter whether a line is drawn as an arc or a broken line: for a graph only the connection "this station is connected to that one" matters.\n\nThe first question for any links is whether they are symmetric. Friendship is mutual: if I am your friend, then you are my friend — such edges are called undirected. A subscription is not mutual: I can read a blogger who doesn't notice me — that is a directed edge, an arrow from me to them. Links between pages, data flows, navigation around a site — all of these are arrows. Choosing the type of graph is the first design decision: mix it up and the algorithm will answer the wrong questions.\n\nEvery vertex has a degree: the number of edges that enter it. A popular person in a friendship graph has a large degree, a recluse has one or zero. And now a beautiful fact, the handshake lemma: the sum of the degrees of all vertices equals twice the number of edges. The reason is transparent: each edge touches exactly two vertices, so by summing degrees we count each edge twice — like each handshake at a party adds one to both participants. A non-obvious consequence: the number of vertices with an odd degree in any graph is even. Such conclusions from simple counting are the signature flavor of graph theory.\n\nNext — movement. A path is a sequence of vertices where each next one is connected to the previous one by an edge: from home to work through a shop. The length of a path is the number of edges in it. A cycle is a path that returns to the starting vertex without repeating edges: a circular route around the neighborhood. The concepts look obvious, but half of practical problems rest on them: "is the database reachable from this service" is a question about the existence of a path.\n\nA graph can fall apart into pieces. A connected graph is one in which you can get from any vertex to any other. If there are several pieces, each is called a connected component: an island within which everyone is reachable from everyone else, and between islands there are no bridges. In a social network the components are communities with no mutual acquaintances. In dependency analysis a component is a group of packages that are installed and removed only together. Finding these islands is the first utilitarian problem about graphs, and we will learn to solve it in the next chapter.\n\nLet's reinforce this with three examples that you see every day. The browser's DOM tree is a directed graph, almost a tree: each node has one parent and any number of children. Package dependencies are a directed graph in which an edge means "is needed to work", and the package manager will honestly show you a cycle in it as an error. A route map is a weighted graph: the edges carry numbers, minutes or dollars, and a navigator looks for a path with the minimal sum. Weights do not change the structure of a graph, but they add to the question "how to get there" the question "at what cost".\n\nHow do you lay a graph out in memory? The first way is the adjacency matrix: a table in which rows and columns are vertices, and a one at the intersection means "there is an edge", a zero means "there is no edge". The advantage is striking: checking whether there is an edge between two vertices is a constant, we simply look into a cell. Plus extreme simplicity: it is a two-dimensional array with no structures at all. For dense graphs, where there are many edges, the matrix is an honest choice.\n\nThe second way is adjacency lists: for each vertex we store the list of its neighbors, and that's it. For sparse graphs, where there are incomparably fewer edges than possible pairs, this is a radical saving. A social network with a billion users would need a quintillion cells in a matrix, but fits in lists: on average a person has a couple of hundred friends. The price is obvious: to find out whether two particular vertices are friends, you will have to scan a list of neighbors. But the main operation of any traversal — "list the neighbors" — is done without fiddling with thousands of empty cells.\n\nLet's reduce the choice to two questions. The first: is the graph dense or sparse — a matrix always eats the square of the number of vertices, lists take space proportional to the number of edges. The second: which operation is hot — frequent checks of a specific edge lean toward a matrix, constant iteration over neighbors leans toward lists. Development practice is almost always on the side of lists: real graphs — dependencies, social ties, routes — are sparse, and you have to walk them continuously. A matrix wins in niches: small dense graphs and point checks.\n\nA couple of words about the directed versions of these concepts. In a directed graph the degree splits into the out-degree, how many arrows leave, and the in-degree, how many enter. The sum of the out-degrees equals the number of edges, and so does the sum of the in-degrees — after all, each arrow leaves once and enters once. A whole jargon rests on these numbers: a popular page has a huge in-degree — many links point to it — while its out-degree may be zero. Once upon a time it was counting incoming arrows that gave birth to entire search engines.\n\nLet's linger separately on cycles in directed graphs, because in dependencies they are a synonym for trouble. If package a requires b, b requires c, and c requires a, none of the three can be installed first: a correct order simply does not exist. A graph without cycles lets you arrange the vertices so that every arrow leads from an earlier one to a later one — such an order is called topological, and it is exactly what the package manager builds before installing. Checking for cycles and building this order are problems we will reach in a chapter's time.\n\nLet's sum up. A graph is vertices and edges, the most economical model for everything where links matter: the DOM tree, dependencies, social networks, routes. Edges can be directed or not, and the sum of degrees always equals twice the number of edges — the handshake lemma. A path, a cycle and connectivity describe reachability, and a cycle in dependencies means that a correct installation order does not exist. The easiest way to store a graph is adjacency lists for a sparse world and a matrix for a dense one. In the next chapter we will learn to walk along graphs: depth, breadth, trees and the bridges of Königsberg.
