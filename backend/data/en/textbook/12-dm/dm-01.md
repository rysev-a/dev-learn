#CHAPTER 1 | Sets: the language of mathematics
Discrete mathematics. Chapter 1. Sets: the language of mathematics. You use sets every day, even if you never stop to think about it: unique values in code, unions and intersections in database queries, the permissions a user has. All of it is one and the same idea, which all of mathematics has relied on for a century and a half. Today we will go through it carefully, and after this lesson you will see sets in your own code as clearly as you see strings and numbers. This is the foundation of the whole course: without it you cannot make sense of relations, counting, or logic.\n\nLet's start with the definition. A set is a collection of elements about which exactly two things are known: which elements are in it, and which elements are not in it. No order and no repeats: an element either belongs to the set or it doesn't, and there is no third option. A playlist differs from a set of songs in that in a playlist one song can appear twice, and in a set it cannot. And it doesn't matter in what order the songs are listed: a set remembers only the fact of presence.\n\nTwo sets are equal if they consist of the same elements — and only that matters. The set of the numbers "one, two" and the set of the numbers "two, one, one" are the same set. There is also a special inhabitant: the empty set, which has no elements at all, like an empty set in a freshly created object. There is only one empty set, and it is a convenient starting point: the sum over nothing is zero, and a search through nothing finds nothing.\n\nNext come the operations, and you already know them, just under other names. The union of two sets gathers everything that appears in at least one of them — this is merging two sets, and the union query in a database. The intersection keeps only what is in both at once — the mutual friends of two users. The difference takes everything from the first set that is not in the second — for example, the followers who are not yet friends. Three operations, and almost any problem about lists of people or products comes down to a combination of them.\n\nThere is also a fourth operation — the complement, but it requires agreeing on what to count from. First we fix the universe: the set of all elements we are considering at all, say all users of the system. Then the complement of the set of administrators is all the other users, the non-administrators. Change the universe from users to the people on the planet, and the complement becomes different, even though the set itself has not changed. The lesson is simple: a complement is always relative, and in code it is expressed as "everything that did not pass the filter".\n\nThe operations obey laws, and the most famous are De Morgan's laws. The first: the complement of a union equals the intersection of the complements. The second: the complement of an intersection equals the union of the complements. Why this is so can be seen on any single element. If an element lies outside the union, then it is in neither the first set nor the second, that is, it is in the complement of the first and in the complement of the second, and therefore in their intersection. Now let's translate this into code. A shop shows items that are not cheap and not old. That is the same as "not" applied to the condition "cheap or old": it is false that at least one of the two conditions holds, so neither of them holds. The second law works the same way. A task is accepted if the tests are green and the review has passed. When is it not accepted? It is false that both conditions are met, so at least one is not met: either the tests are red or the review has not passed. A very common mistake: you want to filter out everyone who is neither an administrator nor an editor, and you write "not an administrator or not an editor". But that condition is true for everyone except those who are both an administrator and an editor at the same time, which means it lets almost everyone through. The correct way is to write "not an administrator and not an editor", or "not" applied to a bracket containing "or". In a database it is the same: the negation of a bracket with an "or" condition turns into two negations joined by the word "and". You don't need to memorize these laws like a spell — it is enough to feel once that negation flips "or" into "and" and back.\n\nA set has a cardinality — the number of its elements, like the size of an array or the number of records in a query result. Cardinality should be handled with care: the cardinality of a union is rarely equal to the sum of the cardinalities, because the sets can overlap. If twenty people know English and twenty know German, the union is not necessarily forty: somebody knows both languages and appeared in both lists. How to count honestly over overlapping sets we will work out in the chapter on inclusion and exclusion. For now keep this in mind: naive addition is the classic double-counting mistake.\n\nOne set is contained in another if each of its elements also belongs to the larger one — then the first is called a subset. The set of even numbers is a subset of all integers. The permissions of the "editor" role are a subset of the permissions of the "administrator" role, if an editor can do everything the same but without configuring the system. Checking for a subset comes down to an intersection: if the intersection coincided with the smaller set, then it is nested inside the larger one.\n\nNow a beautiful fact: a set has a set of all its subsets, called the power set. If the original set has n elements, then the power set has two to the power of n subsets. The logic is transparent: when you build a subset, for each element you decide whether to take it or not — two choices, and altogether two to the power of n decisions. Three elements give eight subsets, ten already give one thousand and twenty-four. Programmers know this from bit masks: one bit per element, and every number is a ready-made subset.\n\nThe power set carries a practical warning: going through all the subsets grows exponentially, and this is the most expensive operation in the course. Problems like "split the load into two groups as evenly as possible" are most honestly solved by going through the subsets, but already at thirty elements there are more than a billion options. That is why discrete mathematics treasures every chance not to enumerate but to calculate with a formula. Two to the power of n is not an abstraction but a budget of your time: if you see it in a solution, stop and think.\n\nLet's look at where all this lives in everyday work. A membership check in a hash set costs a constant, so deduplicating a list is simply converting it to a set. In SQL the same operations are called union, intersection and difference, and the database runs them on millions of rows. Analytics filters, user segments, article tags — everywhere under the hood there are sets and operations on them. When you think in sets, the code becomes shorter: instead of a loop with a flag, one intersection operation.\n\nIt is important to tell a set from a list in time, because they are different contracts. A list keeps order and allows repeats, and often that is exactly what you need: a task queue, a history of actions, paginated output. A set keeps only the fact of membership, but answers the question "is there one of these here" instantly. A bad sign is a list that you search through inside a loop: almost always it is a set disguised as a list. Choosing the right structure is half of an algorithm, and sets give you that half for free.\n\nLet's sum up. A set is elements without order and without repeats; the operations are union, intersection, difference and complement; De Morgan's laws link negation with these operations; cardinality counts the elements, and the power set contains two to the power of n subsets. You have already used all of this in sets and database queries — now these tools have a precise language. In the next chapter we will learn to link elements of different sets with each other: relations and functions are about foreign keys, table links, and the pure functions you write every day.
