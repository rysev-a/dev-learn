#CHAPTER 10 | Multi-file projects: linking, make, and libraries
From Assembler to C. Chapter 10. Multi-file projects: linking, make, and libraries. So far the whole program has fit into one file. Real projects consist of dozens of files, and C was designed for exactly that. Every file with the dot-c extension is a separate translation unit: the preprocessor expands its headers, the compiler produces assembly code, and the assembler turns that into an object file with machine code and a symbol table. You have seen all these steps in the earlier books. One step remains: the linker, which glues the object files into a finished program. This chapter shows how files agree with one another, and how make drives the build.\n\nThe main distinction is between a declaration and a definition. A declaration tells the compiler that a name exists and what type it has: an extern variable declaration, or a function prototype. A definition creates the thing itself: it reserves memory or generates code. There must be exactly one definition in the whole program, but there can be as many declarations as you like. If there are two definitions, the linker reports a multiple definition; if there is no definition at all, it reports an undefined reference. These two errors are the most common ones in multi-file projects, and both appear at link time, not at compile time.\n\nEvery name has a linkage. By default, functions and global variables are visible to the whole program: they have external linkage. The word static at file level makes a name internal: it does not go into the symbol table and does not clash with a same-named entity in another file. That is why everything that is not part of a module's interface is marked static: it is the simplest form of encapsulation in C. Inside a function, static means something different: the variable is created once and keeps its value between calls. Functions that have to live in a header are declared static inline, so that every file gets its own copy.\n\nA header is a module's interface. It holds function prototypes, extern declarations, type definitions, macros, and constants. The implementation and helper functions stay in the dot-c file. There is an idea for hiding how a structure is built, called an opaque type: the header contains only a declaration of the struct, say a stack, plus prototypes of functions that take a pointer to it, while the full definition stays in the dot-c file. A user of the module can store the pointer and pass it around, but cannot touch the fields, and you are free to change the internals without rebuilding the dependent code.\n\nEach object file contains a symbol table: which names it defines and which names it refers to. Names in C are not mangled, so two modules that both have a function called init will clash. Hence the rule: give the public names of a module a common prefix, for example list followed by an underscore. There is a subtlety with reserved names: identifiers that begin with two underscores, or with an underscore and a capital letter, belong to the implementation, and you must not use them in your own programs. You can inspect the symbol table with the nm utility, and the section sizes with the size utility.\n\nThe linker does three things. It gathers same-named sections from all the object files: code goes into the text section, initialized data into the data section, and uninitialized data into the BSS section. It assigns addresses to them, respecting alignment. And it patches the places where the code referred to an unknown address: each such entry is called a relocation, and it holds an offset, a symbol, a type, and an addend. For an absolute address, the linker writes the symbol's address plus the addend; for a relative one, it also subtracts the address of the place being patched. This is exactly what you saw in assembly with labels and jumps.\n\nSeveral object files are conveniently packed into a static library: the ar utility puts them into an archive with the dot-a extension, and the linker pulls out of it only the files it needs. The order on the command line matters: the archive is scanned once, left to right, so if the program refers to a symbol from a library that is listed before the file containing the reference, the symbol will not be found. That is why libraries are listed after the object files that depend on them. If libraries depend on each other in a circle, you put them in a group, and the scan is repeated for as long as anything keeps being found.\n\nA dynamic library works differently: its code is not copied into the program. The linker only records that certain symbols are needed, and the real binding to addresses happens at startup. Such code is compiled to be position independent with the fPIC flag. The gain is a smaller program and the ability to update the library without rebuilding the programs; the price is a dependency on the library version and slightly slower calls. The details of loading depend on the system, and we cover them in the book about Unix; here it is enough to understand the difference in when the binding happens: at build time or at run time.\n\nThe make utility automates rebuilding. A Makefile consists of rules: a target, a colon, a list of dependencies, and below them, each starting with a tab character, the commands. Make builds a dependency graph and compares file modification times: a target is rebuilt if it does not exist or is older than any of its dependencies. For each target the rule runs once, and changing one file triggers a rebuild of only what depends on it. That is how a large project rebuilds in seconds, not minutes, after a small edit. If the dependencies form a cycle, make reports an error.\n\nTo avoid repeating yourself, a Makefile uses variables and pattern rules. Variables set the compiler and the flags: C C and C flags. The pattern rule, percent dot o from percent dot c, explains how to get an object file from any dot-c file. Inside commands you can use automatic variables: dollar at is the target, dollar less-than is the first dependency, and dollar caret is all the dependencies. Targets that are not files, such as clean, are listed under phony, otherwise a file with that name would prevent them from running. A double dollar passes a dollar sign to the command itself.\n\nMake has a weak spot: it knows only what you wrote in the dependencies. If a dot-c file includes a header and you did not list it in the rule, editing the header rebuilds nothing, and you get strange errors: some object files were built with the old structure. The solution is automatic dependencies: the compiler, with the M M D and M P flags, writes next to each object file a list of the headers it included, and the Makefile pulls those files in with the include directive. That way the graph always matches the real includes.\n\nA sensible project layout is simple. Sources live in one directory, public headers in another, tests in a third, and build results in a separate one that you can delete entirely. A public header contains only what clients need, while an internal one stays next to the sources. Compiler warnings are always on, with Wall and Wextra, and for a release you add optimization. When a project grows, the commands are described in build generators such as CMake, which create Makefiles themselves, but their idea is the same dependency graph between files.\n\nLet's sum up. Each dot-c file is compiled separately, and the linker ties the object files together: there must be one definition, but there can be many declarations. Internal names are hidden with the word static, the interface is described in headers, and the structure of a type is hidden behind opaque pointers. Relocations fix the addresses at link time, static libraries are listed after the files that refer to them, and dynamic ones are bound at startup. Make rebuilds only what is out of date according to the dependency graph, and automatic header dependencies keep that graph honest.
