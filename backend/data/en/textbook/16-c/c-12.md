#CHAPTER 12 | Hash Tables, Trees, and Heaps in C
From Assembler to C. Chapter 12. Hash tables, trees, and heaps in C. In chapter five we built simple versions of a list, a tree, and a table. Now we have everything we need to build them properly: generic code with function pointers, headers, sanitizers. Choosing a data structure starts with a question: which operations do you need most often? Lookup by key, order, the minimum, or neighbors? In C, neither the library nor the language decides anything for you: you describe the element size, the hash, the comparison, and the ownership yourself. And memory matters too: the processor reads structures that sit side by side faster than nodes scattered around the heap.\n\nLet's start with the hash function. It turns a key into a number, and we ask three things of it: equal keys give equal hashes, different keys rarely collide, and flipping a single bit of the key changes many bits of the hash. For strings, FNV-1a works well: for every byte, the hash is mixed with the byte using exclusive or and then multiplied by a prime constant. For integers, a finalizer helps: it scrambles the bits with shifts and multiplications. None of these functions offers cryptographic strength, so for data chosen by an adversary you add a random salt. Otherwise their requests will pile all the keys into a single bucket.\n\nThere are two families of tables. In chained tables, each bucket holds a list of elements. They are simple and tolerate a high load, but every element is allocated separately on the heap, and following a pointer is a cache miss. In open addressing tables, all the elements live right inside the array: if a slot is taken, you look for a neighboring one by a rule called probing. Memory is used more densely and traversal is faster, but you need a lower load, and deletion calls for care. The choice depends on the size of the elements, the number of deletions, and how much speed matters.\n\nThe simplest probing is linear: move on to the next slot, and wrap around to the start at the end of the array. A search begins at the computed index and walks forward until it meets the needed key or an empty slot. An empty slot is the sign that there is nothing further to look for, so the array must always stay partly empty. The size is made a power of two, so the index is computed with a mask instead of a division. The downside of linear probing is clustering: occupied slots stick together into long runs, and inserting into such a run gets more expensive. A good hash function and a moderate load help against this.\n\nDeletion is the trickiest operation. If you simply clear the slot, the probe chain breaks, and the elements that sat behind it become unreachable. The first solution is a tombstone: the slot is marked as deleted, a search passes through it, and an insertion may take it. But tombstones pile up and slow down searches, so they are counted in the load and thrown away on a rebuild. The second solution is a backward shift: after the deletion, you check the following elements of the chain and move those that would now be closer to their ideal place. It is harder, but it leaves no garbage behind. Another option is Robin Hood hashing: on insertion, the element that is closer to its ideal place gives up the slot to the one that has wandered farther, which evens out the search lengths.\n\nThe table grows: when the share of occupied slots exceeds a threshold, say three quarters, you create an array twice as large and insert all the elements again, because the index depends on the size. This is expensive, but it happens rarely, and on average an insertion still takes constant time. An important consequence: after growth, all pointers to elements inside the table are invalid, and you must not modify the table while iterating over it. That is why an API often returns a copy of the value instead of a pointer, or states in its documentation until which call the pointer stays alive.\n\nA generic table stores keys and values as sequences of bytes of a fixed size, and at creation it accepts three functions: a hash, an equality comparison, and, if needed, a release function for the key and the value. The question of ownership is settled right away: either the table copies the key into itself, and then the caller may free their own, or it keeps the pointer it was given, and then the key must outlive the table. For strings you usually copy; for pointer identifiers you don't. A good table returns error codes instead of crashing, and lets you walk over all the elements with a callback function.\n\nNow, trees. A binary search tree degenerates into a list if the keys arrive in order, and searching becomes linear. Balanced trees keep the height on the order of a logarithm. In an AVL tree, for every node the difference between the heights of its subtrees is at most one. After an insertion or a deletion, you check the difference and, if needed, perform one of four rotations: a single right, a single left, and the double left-right and right-left. Each rotation is a rearrangement of three pointers, and it preserves the order of the keys. In other kinds of trees, such as red-black trees and treaps, the idea is the same: a small local rebuild instead of a full one.\n\nThe C implementation comes out compact if you write it recursively. The insert function takes the root of a subtree and returns the new root: after the recursive call, the height of the node is updated, then the balance is checked and rotations are performed. Deletion is similar, replacing a node with two children by the smallest node of its right subtree. The node stores its height, and if you need order statistics, the size of its subtree: then you can find the k-th key in order, or count the keys in a range. Freeing is done by a post-order traversal. Recursion is not dangerous here: the depth of an AVL tree never exceeds one and a half times the logarithm of the number of nodes.\n\nA heap is a tree stored in an array. For the element at index i, the children sit at positions two times i plus one and two times i plus two, and the parent at i minus one, divided by two. Insertion puts the element at the end and lifts it up while it is smaller than its parent. Removing the minimum moves the last element to the root and sinks it down toward the smaller child. Both operations take time on the order of a logarithm. You can build a heap from a ready-made array in linear time by sinking the elements from the middle toward the start. Heapsort is building a heap and then extracting elements one after another. A priority queue with key changes needs a map of positions, so that you can quickly find the element you need.\n\nBesides the main structures, there are many specialized ones. A prefix tree stores words letter by letter and quickly finds all words with a common beginning. A Bloom filter answers either definitely not or possibly yes, and takes only a few bits. A cache that evicts the least recently used items combines a table with a doubly linked list: the table finds the entry, and the list keeps the order of use. A disjoint set union with path compression merges sets in almost constant time. A segment tree and a Fenwick tree compute sums and minimums over ranges and change individual elements in logarithmic time. Choosing the right structure often matters more than optimizing the code.\n\nData structures are treacherous because a broken invariant does not show up right away. That's why you write a checking function for each one: the search tree is ordered, the AVL tree is balanced and its heights are right, the heap satisfies the parent property, the table contains every element in a reachable place. You call the check in tests after every operation. An even stronger method is comparison with a model: a deterministic generator feeds the same random operations to your structure and to a simple reference implementation on an array, and the results must match at every step. All of this runs under sanitizers.\n\nLet's sum up. A hash table depends on the hash function, on the way collisions are resolved, and on how deletion works, and after growth the pointers to elements are invalid. An AVL tree keeps its height logarithmic with rotations, a heap keeps its order in an array, and specialized structures solve narrow problems in logarithmic or almost constant time. In C, each of them has to come with a hash function or a comparison, with ownership rules, and with invariant checks, and it should be tested by comparison with a reference model under sanitizers. In the next chapter, we'll talk about testing and code style.
