#CHAPTER 1 | From Assembler to C: Your First Program, Types, and Compilation
From assembler to C. Chapter 1. From Assembler to C: your first program, types, and compilation. In the book about computer architecture you built a processor out of gates and wrote instructions for it: load a number into a register, add, jump on a condition. That is assembler, and it has a drawback: every program is tied to one processor, and even a simple task takes dozens of instructions. C was invented so you could write almost as close to the hardware, but in a portable way. The compiler takes your text and turns it into instructions for the right architecture on its own. In this book we will go through the whole language, and at every step we will look at what it turns into.\n\nThe path of a C program has four steps. First, the preprocessor handles the lines that start with a hash sign: it pastes in the contents of included files and expands macros. Then the compiler translates the text into assembler, optimizing it along the way. The assembler turns those instructions into machine code and saves an object file, in which the addresses of other functions are not filled in yet. Finally, the linker puts the object files and libraries together into one executable file. You can look at each step separately: the dash capital E flag of the compiler shows the output of the preprocessor, dash capital S shows the assembler, and dash lowercase c gives the object file.\n\nHere is the shortest program: a function called main that returns zero. Execution always starts there, and the number it returns is the exit code: it is what the shell later shows as the result of the last command. Zero means success, any other number means an error. To print text, you include the standard input-output header and call printf. The header only tells the compiler what the function looks like, while the code of printf itself is added by the linker from the standard library. Every statement ends with a semicolon, a block is wrapped in curly braces, and the compiler does not care about spaces and line breaks.\n\nTypes in C answer the question: how many bytes does a value take, and how should they be read? A char is one byte, a short is two, an int is usually four, and long and long long are eight. The word usually is not an accident: the standard does not fix the sizes, they depend on the platform. So when the size matters, you include the stdint header and write int thirty-two t, uint eight t, and so on: the size is part of the name, as in Rust. The sizeof operator returns the size of a type or a variable in bytes, and it is computed at compile time. Every integer type has a signed and an unsigned variant, and that decides which processor instruction the compiler picks.\n\nA variable declaration asks the compiler for a place in memory. Local variables live in the function's frame on the stack, and the compiler often keeps them in registers altogether if the address is not needed. An important difference from Python and Rust: a local variable without an initial value contains garbage, whatever was left over from earlier calls, and you must not read it. Global and static variables live in the data areas of the executable and are zero by default. The const keyword forbids changing a value, and the static keyword on a local variable makes it long-lived: it keeps its value between calls. In assembler, accessing a local variable is a load or a store at an address relative to the stack pointer register.\n\nArithmetic in C looks familiar, but with some subtleties. Integer division throws away the fractional part, and the remainder takes the sign of the dividend: minus seven divided by two gives minus three, with remainder minus one, just like in the processor. Unsigned numbers wrap around modulo on overflow, like a register: two hundred fifty-five plus one in the uint eight t type gives zero. Signed numbers are worse: their overflow is undefined behavior, and the compiler is allowed to assume it never happens. Before a calculation, small types are automatically widened to int, and this is called integer promotion. If you mix signed and unsigned numbers, it is easy to get an unexpected result.\n\nBitwise operations are the main tool of systems code. The ampersand, the vertical bar, the caret, and the tilde perform and, or, exclusive or, and negation on every bit, and the double angle brackets shift the bits left or right. They translate into instructions you already know: and, or, xor, sll, srl. A right shift of an unsigned number is logical and shifts in zeros, while for a signed number it is usually arithmetic and keeps the sign, like the sra instruction. Typical tricks: a mask to pick out a field, setting a bit with or and a one, clearing it with and and an inverted mask, and testing a bit with and. You must not shift by a number of positions equal to the width of the type or more.\n\nLogical operations in C work with numbers: zero means false, and everything else means true. A comparison produces zero or one. The double ampersand and the double vertical bar evaluate the right-hand side only when needed, and in assembler that is simply a chain of conditional jumps, like branch-if-equal. The conditional operator with a question mark gives an expression, like if in Rust. Assignment in C is also an expression, so the mistake of writing one equals sign instead of two in a condition compiles. To catch it, you turn on compiler warnings, and many people also write the comparison with the constant on the left. The dash W all and dash W extra flags are a mandatory habit.\n\nThe formatted output function printf takes a string with placeholders and arguments. Percent d prints a signed integer, percent u an unsigned one, percent x a hexadecimal number, percent c a character, percent s a string, percent f a fractional number, percent z u a size, and percent p a pointer. Before the letter you can put a width and a precision, for example percent zero eight x. The compiler cannot check that the argument's type matches the placeholder: printing a fractional number with a percent d placeholder is undefined behavior. Also remember about buffering: output to a terminal is flushed at the end of a line, while output to a file or a pipe is flushed only when the buffer fills up or when the program ends.\n\nMagic numbers in code are harmful, so C has several ways to give a value a name. The define directive substitutes text before compilation and knows nothing about types. An enumeration, or enum, defines a set of named integer constants, and the values go in order from zero until you specify your own. A variable declared with const keeps its value in memory, but in older standards you cannot use it as an array size. The compile-time check, static assert, stops the build if a condition is false, for example if a structure's size turns out to be wrong. The habit of checking assumptions about types and sizes at build time gives most of the reliability of systems code.\n\nFloating-point numbers are stored according to the IEEE seven fifty-four standard: a sign, an exponent, and a mantissa. A float takes four bytes and gives about seven correct decimal digits, and a double takes eight bytes and gives about sixteen. Fractional numbers must not be compared for exact equality: zero point one added three times is not equal to zero point three. Instead you compare the absolute value of the difference with a tolerance. Converting a fractional number to an integer drops the fractional part, and if the number does not fit, the behavior is undefined. Math functions live in the m library, which you link with the dash l m flag. As in other languages, special values, infinity and NaN, appear on division by zero and on invalid operations.\n\nNow the most important thing that sets C apart from many languages: undefined behavior. For some errors the standard does not say what should happen. Signed overflow, reading an uninitialized variable, division by zero, shifting by too many positions, going out of an array's bounds: all of this means the program may do anything. The compiler optimizes the code on the assumption that such things never happen, and the result is unpredictable: it works today and breaks tomorrow on a different version. The best defense is warnings, sanitizers, the dash f sanitize equals undefined and address flags, and the habit of checking bounds in advance.\n\nLet's sum up. C is a portable assembler: the compiler turns text into processor instructions through preprocessing, compilation, assembly, and linking. Types determine sizes, local variables without a value contain garbage, unsigned arithmetic wraps around, and signed overflow is undefined behavior. Bitwise operations and shifts translate directly into processor instructions, and printf demands exact placeholders. Next we have branches, loops, and functions, and we will see how they become the labels and jumps you have already written in assembler.
