#CHAPTER 13 | Testing and code style: assert, unit tests, and standards
From Assembler to C. Chapter 13. Testing and code style: assert, unit tests, and standards. C has no exceptions and no runtime checks, so mistakes are expensive: silent memory corruption, a wrong result with no message at all. The only safety net is tests. A test is just a program that calls your code with known inputs, compares the result with what you expect, and returns a nonzero exit code if they differ. A good test suite is also documentation: it shows how a function is supposed to behave on ordinary data and on edge cases. You write tests next to the code and run them on every change.\n\nTell apart two kinds of checks. A check that protects the contract between parts of a program is an assert: if a caller passes a null pointer where it is forbidden, the program itself is wrong, and the right reaction is to stop with a message. But if the user's input is wrong, that is not a bug in the program, it is an ordinary situation, and the function returns an error code. Conditions fall into preconditions, which the called function checks, postconditions, which the function itself guarantees, and invariants of a data structure, which hold between operations. In a release build asserts are switched off with the NDEBUG flag, so there must never be any real work inside them.\n\nA unit test framework for C can be written in half an hour with the macros from the preprocessor chapter. A test macro defines a function, and a special table or another macro registers it. The expect macros compare values; on failure they print the file, the line, the text of the expression, and both values, they bump an error counter, and they do not abort the test. The runner prints a summary and returns a nonzero code if anything failed. Ready-made libraries such as Unity, Check, and cmocka do the same thing with more comfort, but the principle is shared: tests run as an ordinary program and report the result through the exit code.\n\nWhat exactly should you check? First of all, boundaries: empty input, a single element, the maximum, the minimum, and values one below and one above each boundary. Then equivalence classes: one representative from each group of inputs that the code handles the same way is enough. Separately, errors: a null pointer, a buffer that is too small, a wrong format. In C the special risks are terminating zeros, buffer sizes, and signedness. Test cases are convenient to write as a table: an array of structs with an input and an expectation, and one loop, so adding a new case costs a single line.\n\nCode that is hard to test is usually badly designed. The first rule is to separate logic from input and output. A function that takes a string and returns a struct can be checked without any files; a function that reads a file and prints cannot. The second rule: dependencies on the outside world, such as time, files, memory, and the network, should be passed in through function pointers or structs of operations, as in the chapter on generic code. Then a test can plug in a fake clock, or a reader that serves lines from an array. For streams, fmemopen and open_memstream help, which we discussed in the chapter on input and output.\n\nTest doubles replace real dependencies. A stub returns canned values. A fake is a simplified working implementation, for example memory instead of a disk. A spy records the calls so that you can later check their order and arguments. A mock combines a spy with expectations: it describes in advance which calls must happen. Substituting memory allocation is especially important: an allocator that fails on a chosen call number lets you verify that, when memory runs out, the function frees everything it managed to allocate. This technique is called fault injection, and without it the error handling branches stay untested.\n\nCoverage shows which lines and branches ran during the tests. The compiler with the coverage flags inserts counters, and the gcov tool turns them into a report: lines the tests never reached are marked in red. It is a useful tool for finding gaps, but not a measure of quality: a test with no checks covers the code completely and proves nothing. Mutation testing complements coverage: you deliberately break the code, for instance replace less-than with less-than-or-equal, and see whether the tests notice the breakage. If they do not, the test is weak.\n\nStronger than ordinary examples are property tests. Instead of checking specific values, you state a law: encoding and then decoding returns the original, sorting is idempotent and preserves the set of elements, addition is commutative. A deterministic generator feeds in many random inputs, and on failure the starting seed is printed so you can reproduce the bug. If the input is large, you shrink it: remove pieces as long as the property keeps failing, and you end up with a minimal example. From here the approach grows into fuzzing: a mutator program corrupts input data while sanitizers catch the crashes. The inputs that were found are saved into a corpus.\n\nEvery bug you find turns into a regression test that first reproduces it and then stays forever. Tests run on every change, in an automated build on a server: this is called continuous integration. It is also useful to build and run the tests in several configurations: without optimizations and with them, with different compilers, and under the address sanitizer and the undefined behavior sanitizer separately. Many bugs with undefined behavior show up in only one of them. The make test command should work as a single line, and the result should be unambiguous: exit code zero or nonzero.\n\nCode style is an agreement, not a matter of taste. A single formatting is set by the clang-format program: arguments about spaces and braces are over, and the differences in the change history stay meaningful. Names follow rules: functions and variables are written in lowercase with underscores, macros and constants in uppercase, and public names of a module start with a prefix. A function does one thing and fits on a screen; if the nesting goes deeper than three levels, it is worth splitting. A comment explains why, rather than repeating the code, and commented-out code is deleted: the history lives in version control.\n\nSafe habits are fixed as rules. Every function that receives a buffer also receives its size. Parameters that the function does not change are marked const. Everything that is not part of the module's interface is static. Magic numbers are replaced with named constants or enumerations. The results of functions that can fail are checked. To release several resources on different paths, you use a single cleanup block at the end of the function, reached with goto: this is one of the cases where it makes the code better. And input is never assumed to be correct in advance.\n\nCoding rules are often collected into standards. The language itself evolved through editions: C99, C11, C17, and the choice of edition is pinned with the std flag. For critical systems there are MISRA C and CERT C, lists of prohibitions and recommendations checked by static analyzers. Projects write their own rules too; in the Linux kernel, for example, they are described in a separate document. There is no universal set, but the principle is the same: rules that a machine checks get followed, and rules that were only agreed on get forgotten. Put style and warning checks into the automated build.\n\nLet us sum up. A test is a program with an exit code. Assert protects contracts, while error codes describe ordinary failures. Testable code separates logic from input and output and takes its dependencies through function pointers, and an allocator that fails on demand checks how out-of-memory is handled. Coverage, mutations, properties, and fuzzing find weak spots in the tests and in the code. Style is fixed by a formatter, naming rules, and analyzers in the automated build. In the last chapter we will look at modern C: the C11 and C23 standards.
