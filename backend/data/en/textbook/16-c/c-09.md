#CHAPTER 9 | Data representation: byte order, IEEE 754 and bit tricks
From assembler to the C language. Chapter 9. Data representation: byte order, floating-point numbers and bit tricks. Memory holds no numbers, strings or structures, only bytes, and a type is simply an agreement about how to read them. You saw this idea in the book on computer architecture: a register stores just a set of bits, and the instructions decide whether to treat them as an integer or as an address. C makes the same choice openly: the size of a type is available through the sizeof operator, the ranges live in the limits header, and the stdint header provides types of an exact size. Everything in this chapter follows from that: how integer, floating-point and composite types are laid out at the level of bytes.\n\nSigned integers are stored in two's complement: the top bit carries a negative weight, minus two to the power of the width minus one. That is why the range is asymmetric: an eight-bit type runs from minus one hundred twenty-eight to one hundred twenty-seven. Unsigned overflow is defined and wraps around modulo two to the width, while signed overflow is undefined behavior, and the compiler is allowed to ignore it. There are conversion traps too: when you compare a signed value with an unsigned one, the signed one is converted, so minus one is less than one unsigned turns out to be false. And types smaller than int are promoted to int before any operation, so adding two chars cannot overflow inside the expression.\n\nByte order determines the sequence in which a multi-byte number lies in memory. In little-endian order the lowest byte comes first; that is how x86 and ARM work in their usual mode. In big-endian order the highest byte comes first, which is the convention in network protocols. Checking the order is easy: store a number and read its first byte through a pointer to unsigned char. But you must not convert the order by casting pointers. It is more reliable to rearrange bytes with shifts and masks: such code behaves the same on any platform and does not depend on alignment.\n\nReading an object's representation byte by byte is allowed: a pointer to unsigned char may look at any object, and memcpy copies bytes without regard to types. Everything else is dangerous. Reading a float through a pointer to int violates the strict aliasing rule, and the optimizer is entitled to assume such pointers never overlap and to produce wrong code. There are two safe ways: copying the bytes with memcpy, which the compiler turns into a single instruction, or reading through a union, which the C standard permits. The rule of thumb: if you want a different representation, copy the bytes.\n\nThe size of a structure is almost always larger than the sum of its fields. The processor reads numbers faster and more reliably at addresses that are multiples of their size, so the compiler inserts padding bytes between fields and adds a tail at the end, so that array elements stay aligned too. The alignment of a type comes from the alignof operator, and the offset of a field from the offsetof macro. Reordering fields from largest to smallest often shrinks the structure. The packed attribute removes the padding, but makes accesses slow, and on some processors, including some RISC-V parts, even impossible. That is why, for exchanging data, you write the fields out by hand.\n\nIntegers support bitwise operations: and, or, exclusive or, negation and shifts. Shifting left by one multiplies by two, shifting right divides, but with important caveats. A shift by an amount equal to the width of the type or larger is undefined, and so is a left shift of a negative number. A right shift of a signed value is arithmetic in common implementations, but the standard does not guarantee it. Masks are the tool for working with bits: to set a bit, or the number with a one shifted to the right position; to clear it, and with the complement of that value; to test it, and and compare with zero.\n\nA whole family of tricks is built on bits. The expression x and x minus one clears the lowest set bit, which lets you count ones in time proportional to their number, and recognize a power of two by testing for zero. The expression x and minus x isolates the lowest set bit. Rounding up to the next power of two is done with a cascade of ors and shifts. Swapping two variables with exclusive or is surprising, but in practice slower than the ordinary way. Compilers provide built-in functions for counting ones and leading and trailing zeros, and you should prefer them to hand-written loops: they turn into a single processor instruction.\n\nStructures can declare bit-fields: after the name, you give the number of bits after a colon. It looks convenient for flags and registers, but the standard leaves a lot to the implementation: the order of placement within a byte, whether fields may cross word boundaries, and the signedness of plain fields. So such structures must not be used for files and protocols, and for describing hardware registers the usual practice is to write masks and shifts explicitly. Bit-fields are appropriate where only compactness inside a single program matters and nobody relies on the exact layout.\n\nFloating-point numbers on most systems are stored according to the IEEE 754 standard. A float takes thirty-two bits: a sign bit, eight bits of exponent and twenty-three bits of mantissa; a double takes sixty-four: a sign, eleven bits of exponent and fifty-two of mantissa. The value equals the mantissa with an implicit leading one, multiplied by two to the power of the exponent minus the bias. Special exponents are reserved: an exponent of zero gives zero and denormalized numbers, and the largest exponent gives infinity and not-a-number. Because fractions are binary, the number one tenth cannot be represented exactly.\n\nRounding error is not a bug but a property of the format. The sum of zero point one and zero point two is not equal to zero point three, and you must not compare floating-point numbers with the equality operator. Instead you compare with a tolerance: an absolute one for numbers near zero and a relative one for the rest, or you count the distance in ulps, that is, the number of representable values between the two. When you subtract nearly equal numbers, the accurate digits vanish. When you add a large number to a small one, the small one can be lost entirely. That is why the order of summation matters, and why Kahan's algorithm accumulates the lost part separately.\n\nSpecial values follow their own rules. Not-a-number is not equal to anything, not even to itself, so you test for it with the isnan function. Dividing a floating-point number by zero gives infinity, and zero by zero gives not-a-number, but integer division by zero is undefined behavior. There is also a negative zero: it equals the ordinary zero, but can be told apart by its sign. Converting a floating-point value to an integer discards the fractional part, and if the value does not fit in the integer type, that is undefined behavior. For rounding there are dedicated functions: floor, ceil, round and rint.\n\nYou need to know the representation in order to encode data. Integers are sent in network order, byte by byte. Variable-length numbers are encoded seven bits per byte, as in a varint: small values take a single byte. Binary data in text is written as hexadecimal digits or in the base64 alphabet, which turns three bytes into four characters. Characters in UTF-8 take from one to four bytes, and the pattern of the high bits tells you where a character begins and ends. Checksums such as CRC catch random errors in storage and transmission.\n\nLet's sum up. Memory consists of bytes, and the type defines how they are read. Integers are stored in two's complement, signed overflow is undefined, and byte order depends on the platform. To read another representation, copy the bytes rather than casting pointers. Structures contain padding, and bit-fields are not suitable for protocols. Floating-point numbers have an exact but finite format: compare them with a tolerance and remember the special values.
