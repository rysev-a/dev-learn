#CHAPTER 8 | Input and Output: stdio, Formatting, and Buffering
From Assembler to C. Chapter 8. Input and Output: the Standard Library, Formatting, and Buffering. The C language has no print statements: output is just ordinary library functions. The central entity is the stream, a pointer to a FILE structure that holds a buffer and a current position. Three streams are ready when the program starts: standard input, standard output, and standard error. In Python you wrote print and open, in Rust you used the println macro, and here everything is more honest: you are responsible for the format, for the buffer size, and for checking errors. This chapter covers only what the language and its library can do, not how the operating system delivers bytes to the terminal.\n\nThe main output function is printf: the first argument sets the format, and the rest are substituted into the places marked with a percent sign. Integers are printed with percent d and percent u, hexadecimal with percent x, a character with percent c, a string with percent s, and floating-point numbers with percent f, percent e, and percent g. Between the percent sign and the letter you can put flags, a width, and a precision: percent zero eight d pads a number with zeros to eight digits, and percent dot three f keeps three digits after the decimal point. Two percent signs in a row print the percent sign itself. The function returns the number of characters printed, or a negative number on error.\n\nThe argument types must match the format exactly, because the function receives them through the variable-argument mechanism and does not know their types. For long you need the modifier l, for long long two of them, for size t it's z, and for single-byte types it's h h. If you write percent d but pass a long, the result is undefined, and this is one of the most treacherous mistakes, because on one platform it may happen to work. For types with an exact size, the inttypes header provides format macros, for example for printing a sixty-four-bit unsigned number. A compiler with the Wall warnings notices mismatches when the format is a literal.\n\nPrinting into a string is done by snprintf: you pass it a buffer, its size, and a format. It never writes more than the size minus one characters, always adds the terminating zero, and returns the length that would have resulted had there been enough room. That lets you detect truncation and compute the size you need: the first call with a null buffer gives the length, then you allocate memory and call it a second time. The old sprintf doesn't know the size and is considered unsafe: any extra digit corrupts memory beyond the buffer. The rule is simple: in new code, use only the variant with a size.\n\nFormatted input is read with scanf and sscanf: the format describes the expected data, and the values are written to the addresses you pass. The function returns the number of fields successfully parsed, and that is the number you need to check, not just call the function. A space in the format skips any whitespace, and the percent s specifier without a width reads a word of unlimited length, a straight road to a buffer overflow, so you set the width explicitly, for example percent fifteen s for a sixteen-byte buffer. Because of the trouble with the leftovers of a line, in practice people read the whole line and parse it separately.\n\nLines are read by fgets: you pass it a buffer, a size, and a stream. It reads up to a newline or up to the size minus one characters, always adds a zero, and returns a pointer to the buffer, or a null pointer at the end of the file. The newline stays in the buffer if it fit, so it is usually removed, found with strchr or strcspn. If there is no newline in the buffer, the line is longer than the buffer, and the rest will arrive on the next read. Reading character by character is done by fgetc, which returns a value of type int, so that a character code can be told apart from the end-of-file marker.\n\nTo parse numbers from text, use strtol and strtod, not atoi. They take a pointer where they will store the place they stopped, and a number base. If the stop position equals the start of the string, there were no digits; if extra characters remain after the number, the string as a whole was not valid. On a range overflow the function returns the extreme value and sets the variable errno to an error code, so you zero it before the call. The atoi function can't report errors at all, and on the letters a, b, c it quietly returns zero, indistinguishable from a genuine zero.\n\nA file is opened by fopen: a name and a mode, for example r for reading, w for writing with truncation, a for appending, with the addition of b for binary data. On failure it returns a null pointer, and checking is mandatory. When you're done, the stream is closed with fclose: it flushes the buffer and releases resources. The state indicators, feof and ferror, make sense only after a failed read: a loop that runs until the end of the file reads one extra time and processes the last line twice. The correct loop checks the result of the read function itself.\n\nBinary data is written by fwrite and read by fread: a pointer, the element size, the number of elements, and the stream. The result is the number of elements actually processed, and you must compare it with the number requested. Writing a whole structure is dangerous: it can contain padding bytes with undefined contents, and the byte order and type sizes depend on the platform. It's more reliable to write the fields one by one in a predefined format. The position in the stream is changed by fseek and ftell, and rewind returns you to the beginning; that way you can first write data and then read back the same data.\n\nBuffering explains many oddities. Output to a file is usually fully buffered: data accumulates in memory and goes out in blocks. Output to a terminal is line-buffered: the buffer is flushed at a newline. The error stream is unbuffered: messages appear immediately. So if a program terminates abnormally, the last lines of output without a newline may be lost. The function fflush flushes the buffer by force, and setvbuf chooses the mode and supplies your own buffer before the first input or output. Because of buffers, the order in which text from printf and from the error stream appears is not guaranteed when you mix them.\n\nStreams don't have to be tied to files. The function fmemopen wraps an area of memory in a stream, open memstream creates a growing buffer, and tmpfile makes an unnamed temporary file that disappears when closed. This is handy for testing programs: you test reading and writing functions without real files, feeding them text from a string and collecting the result in memory. For parsing formats, sscanf and snprintf play the same role. This is exactly how we'll write the tasks of this chapter: read from a string in memory, write to memory, and compare the result.\n\nYou write your own function with a variable number of arguments, such as a logger, using the stdarg header. The type va list holds a position in the argument list, va start initializes it, va arg fetches the next argument of a given type, and va end finishes. If you just need to pass the arguments along, you take vsnprintf or vprintf, which receive the list itself instead of the ellipsis. The compiler can check formats in such wrappers if you mark the function with a special attribute. The most important rule: don't call va arg more times than there are arguments passed.\n\nLet's sum up. Streams are pointers to FILE: three standard ones are ready, and the rest you open and close. Output is formatted with printf and snprintf, with exact matching of types and sizes. Input is read by lines with fgets, and numbers are parsed with strtol and strtod, checking the stop position and errno. Binary data is written with the platform in mind, and output is buffered, which is why fflush matters. Streams in memory make input and output testable. In the next chapter we'll look at how data appears in memory: byte order, floating-point numbers, and bit tricks.
