#CHAPTER 7 | The Preprocessor, Macros, and Header Files
From Assembler to C. Chapter 7. The Preprocessor, Macros, and Header Files. Before real compilation, C runs a separate program: the preprocessor. It knows nothing about types, functions, or variables. It reads text and produces new text, substituting some pieces for others. You've seen something similar in assembler: macro instructions and the directive that includes a file. Python and Rust have no such pass, so a lot of what those languages do in the language itself, C does by substituting text. You can see the result by stopping the compiler right after the preprocessor with the capital E flag, and this chapter will teach you to read that output.\n\nThe include directive pastes the contents of another file in place of the directive itself, copying its text literally. Angle brackets mean search among the system headers, such as standard input and output, while quotes look next to your own file first. By convention, a header holds declarations, not definitions: function prototypes, types, structures, constants. That way several files of a project can agree on what the shared functions look like, while the functions themselves are implemented in one place. A function body is allowed in a header only for static inline functions, which we'll get to below.\n\nIf one header is included twice, a structure gets defined twice, and the compiler reports an error. This happens quietly: a file includes two headers, and both of them include a third. The include guard protects against repeats. The first line of the header checks whether a special macro is defined, for example the file name followed by an underscore and H. If it is, all the remaining text is skipped. Otherwise the macro gets defined, and the text is read for the first time. The last line closes the check. Many compilers have a shorter form, pragma once, but the guard works everywhere and is considered the model of portability.\n\nThe define directive without parameters sets a name that the preprocessor replaces with other text everywhere below it in the file, until it meets an undef. That's how you define sizes, limits, and flags. Such a constant has no type, no address, and no scope, and it isn't visible in debugger messages, because the compiler already receives a plain number. So for a set of integer values an enumeration is better, and for a single typed constant, a constant variable. But macros remain necessary wherever a constant is needed as text: an array size in older standards, conditional compilation, gluing names together.\n\nMacros with parameters look like functions, but work differently: the arguments are substituted as text. The main rule follows from this: put every parameter in the body in parentheses, and put the whole body in parentheses too. A macro called square of x, defined as x times x, turns a call with a plus one into a plus one, times a, plus one, which is not a square at all. Parentheses around the parameters fix that, and parentheses around the body protect against neighboring operations. This trap is the most common cause of strange results in other people's code.\n\nThe second trap is side effects. A max macro that writes its argument twice in the body evaluates it twice: a call with i plus plus will increase the counter by two. There are several solutions. The best is to replace the macro with a static inline function: it has a type, the argument is evaluated once, and the compiler will still substitute the body. If you need to work with different types, compiler extensions help, for example temporary variables through typeof, or selection by type through generic from the C eleven standard. In all other cases, document it honestly: macro arguments must not have side effects.\n\nA macro made of several statements is written as do, an opening brace, the body, a closing brace, while zero. Why this wrapper? Without it, in an if branch without braces the macro would expand into two statements, and the second would end up outside the condition. The wrapper turns a set of actions into a single statement, and a loop with the condition zero runs exactly once and disappears during optimization. You don't put a semicolon after the wrapper: whoever calls the macro adds it, and the call looks like an ordinary function call. This is an idiom you'll meet in every large project.\n\nTwo special operators work only inside macros. The hash sign before a parameter turns the argument into a string literal: that's how you print the text of an expression together with its value, and how assert shows exactly which condition was violated. The double hash glues two fragments into one name: from the word function and the number one you get function one. There's a subtlety: if an argument is itself a macro, it is not expanded first. So to substitute the value, you write two levels: the outer macro passes the argument to the inner one, and by that point the name has already been replaced by its contents.\n\nThe preprocessor knows several built-in names. The file macro substitutes the name of the source file, the line macro substitutes the number of the line it's written on, and the func name, which technically is not a macro but a predefined identifier, gives the name of the current function. The date and time macros record the moment of the build, and the standard version macro tells you which standard is enabled. Debug messages are built from these: a logging macro prints the place of the call automatically, and you don't have to write it by hand. That's how diagnostics work in every reasonably serious program, and assert has the same foundation.\n\nConditional compilation turns parts of the text on or off. The directives if, ifdef, ifndef, elif, else, and endif check integer expressions and whether names are defined, and the defined operator asks whether a given name exists. That's how you pick code for a platform and compiler, turn on debug printing with the D debug flag at build time, and cut out the obviously unneeded. The construct if zero is handy for temporarily switching off a section, because nested comments don't work in C. The main thing is not to turn the source into a forest of directives: the fewer the branches, the easier it is to check each one.\n\nA macro can take a variable number of arguments: an ellipsis in the parameter list and the name V A underscore ARGS in the body. These are used to build wrappers around printf: a logging macro passes on the format and everything else. Another valuable idiom is the X macro: you write the list of items once, as calls of a macro with parameters, and then substitute different definitions and get, all at once, an enumeration and a table of names that cannot drift apart. That's how large projects maintain error codes, commands, and fields without duplicating the list in several places.\n\nHow do you choose between a macro, a function, and a constant? If the value is a number, use an enumeration or a constant. If it's a computation, use a static inline function in a header. Keep macros for what can't be done any other way: gluing names, stringification, conditional compilation, and necessary macros such as array size, which divides the size of the whole array by the size of one element. You can always check the result by stopping compilation with the capital E flag: you'll see the text the compiler received. And turn on warnings: Wall and Wextra will catch many mistakes before the program even runs.\n\nLet's sum up. The preprocessor is a pass of text substitution before compilation: include copies files, define replaces names, and conditional directives choose pieces of code. Headers contain declarations and are protected by an include guard. Macro parameters and the body itself go in parentheses, side effects are avoided, and multi-statement macros are wrapped in do while zero. Stringification and token pasting make macros more powerful than functions, but they pay for it in readability. In the next chapter we'll turn to input and output: the standard library, formatting, and buffering.
