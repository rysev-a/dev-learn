#CHAPTER 11 | Undefined behavior, debugging and sanitizers
From Assembler to C. Chapter 11. Undefined behavior, debugging and sanitizers. The most dangerous thing in C is not the errors that stop the program immediately, but the errors that keep on working. The standard lists cases for which it promises nothing, and calls them undefined behavior. That does not mean you get something strange. It means the compiler has complete freedom: a program with such an error may work, crash, return garbage, or behave differently in another version of the compiler. Do not confuse this with implementation-defined behavior, which is documented, or with unspecified behavior, where several outcomes are allowed.\n\nThe list of undefined behavior is long, but the main groups are familiar from earlier chapters. Going out of the bounds of an array or buffer. Dereferencing a null or dangling pointer, reading after free, freeing twice. Overflow of a signed integer, division by zero, a shift by the width of the type or more. Reading an uninitialized variable. Violating strict aliasing and alignment. Modifying a string literal. Overlapping regions in mem-copy. Data races between threads. They all have one thing in common: the compiler is not required to check these situations, and it will not, because checking would cost time.\n\nWorse still, the optimizer reasons by contradiction: since a correct program contains no undefined behavior, these cases can simply be ignored. For a signed number it will replace the expression x plus one is greater than x with true, because overflow supposedly never happens. A null pointer check placed after a dereference it will delete as redundant. A loop with a signed counter that, by its logic, should end with an overflow becomes infinite. So an error may show up only in an optimized build, only on a different compiler, or months later. To see what the compiler actually did, look at the assembly listing: the dash S flag together with optimization.\n\nA special case is uninitialized data. A local variable gets whatever was left on the stack by earlier calls; you know this from stack frames in the book on computer architecture. Memory from malloc is not zeroed, and reading such a value is forbidden. Worst of all, the program can work for years, as long as a zero happened to lie in that spot. That is why variables are initialized at the declaration, arrays are filled with zeros or by a loop, and the Wall and Wextra warnings are turned on, since they catch some of these cases. If you need zeros in dynamic memory, use the calloc function.\n\nAnother group is lifetime errors. A function returned a pointer to its own local variable, and after the return the frame is gone. A pointer stays pointing at a freed heap block. A pointer to a variable from a block that has already ended. All these errors are equally treacherous, because the memory still exists and keeps old data for a long time. The defense is the discipline of ownership: for every object you know the owner and the lifetime, and a function returns either a value, or a pointer to the caller's memory, or a pointer to an allocated block with a clear rule for freeing it.\n\nThe first line of defense is the compiler. The Wall, Wextra and Wpedantic flags find a lot, while Wshadow, Wconversion and Wformat are for special classes of errors: shadowed names, loss of precision, wrong formats. The Werror flag turns warnings into errors, and in a project with a clean build any new warning is noticed at once. On top of that people use static analysis: the analyzer built into GCC, clang-tidy and cppcheck. They do not replace tests, but they find errors on paths the tests never reach.\n\nSanitizers are the second line: the code is built with instrumentation, and errors are caught right at run time, with the exact location. AddressSanitizer surrounds every block with forbidden zones and keeps a shadow map of memory; it finds out-of-bounds access on the heap, the stack and global data, reading after free, double free and leaks. The fsanitize equals address flag, together with debug information and preserved frame pointers, gives readable reports with a call stack. The price is roughly a twofold slowdown and higher memory use, which is quite acceptable for tests.\n\nFor undefined behavior there is UBSan, the undefined behavior sanitizer. The fsanitize equals undefined flag inserts checks for signed overflow, shifts, division by zero, null pointers, alignment, out-of-bounds access to arrays of known size, and a non-positive length of a variable length array. By default it prints a message and keeps going, while the fno-sanitize-recover equals all flag stops the program at the first error. MemorySanitizer from clang finds reads of uninitialized memory, and ThreadSanitizer finds data races. Different sanitizers can hardly be combined, so you make separate builds.\n\nThe GDB debugger is what you need when you have to see an error from the inside. The program is compiled with the dash g flag and without optimization, otherwise variables vanish from the code. The break command sets a breakpoint, run starts the program, next and step execute a line without and with entering a function, print shows a value, backtrace shows the call stack, watch follows changes to a variable, x shows memory in the format you need, and finish leaves the function. A crash by signal can be analyzed after the fact, if a core dump was saved.\n\nThe simplest tool is printing and checking. The assert macro from the assert header checks an invariant, and on a violation prints the condition, the file and the line, and ends the program; in a release build the NDEBUG flag turns it off, so there must be no side effects inside the condition. For checks known at compile time there is static assert. Tracing to the error stream, with a macro that inserts the place of the call, as we did in the chapter on the preprocessor, is often faster than a debugger. The main rule: once you find an error, turn it into a test so that it never comes back.\n\nThe Valgrind program runs a ready binary on a virtual processor and monitors every memory access. You do not have to rebuild anything, but execution slows down tens of times. Memcheck finds uninitialized reads, leaks and out-of-bounds access on the heap. It complements the sanitizers well when the sources are hard to rebuild, or when you need an exact leak report with the place of allocation. In most projects people use AddressSanitizer and UBSan first, as the fast tools, and Valgrind as a fallback.\n\nHunting for a bug is a method, not inspiration. First reproduce the problem reliably, then shrink the input to the minimum: cut out pieces for as long as the error remains. If the error appeared between two versions, a binary search through the history finds the guilty commit in a logarithmic number of steps. State a hypothesis, test it with a single experiment, and write down the result. To find inputs that break a program there is fuzzing: a generator feeds random and mutated data and watches for crashes under the sanitizers. Every error found becomes a regression test.\n\nLet us sum up. Undefined behavior means the absence of guarantees, and the optimizer takes advantage of it, so errors show up in the wrong place and at the wrong time. The main groups are bounds, pointers and lifetime, signed arithmetic and shifts, uninitialized data, and aliasing. Defense comes in several layers: warnings and analysis at compile time, AddressSanitizer and UBSan in tests, the debugger and assert when hunting, Valgrind as a fallback, and the habit of turning every error found into a test.
