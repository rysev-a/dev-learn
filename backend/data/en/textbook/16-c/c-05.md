#CHAPTER 5 | Dynamic Memory and Data Structures in C
From Assembler to C. Chapter 5. Dynamic Memory and Data Structures in C. Everything we have built so far lived on the stack: the size is known in advance, and the lifetime equals the lifetime of the frame. For growing data that is not enough. A user might type ten lines or ten million, and you cannot declare an array of the right size ahead of time. For cases like this there is the heap: a region of memory from which a program takes a piece of the size it needs and keeps it for as long as it needs. In Python the interpreter takes care of this, in Rust the ownership system does. In C you do everything by hand: if you took memory, give it back, and give it back exactly once.\n\nFour functions of the standard library make up the whole interface. malloc takes a size in bytes and returns a pointer to an uninitialized block, or NULL if there is no memory. calloc allocates an array and fills it with zeros. realloc changes the size of a block, possibly moving it to a new place, and returns the new address. free releases a block, and for NULL it does nothing. The usual habit is to write the size as the number of elements times sizeof of the dereferenced pointer: then the code does not break when the type changes. The result of malloc must always be checked, and a freed pointer should be set to NULL right away, so that you do not touch it again by mistake.\n\nWhat happens inside? The allocator obtains large areas of memory and carves blocks out of them. Before each block there is a small header with its size, and free blocks are linked into lists by size. A request is served from a suitable free block, and if there is none, the allocator gets one more area. The returned addresses are aligned, usually to sixteen bytes, so that any type fits. Over time the heap becomes fragmented: there are plenty of free bytes, but no piece of the right size. That is why allocating and freeing are not free of cost, and many small requests are better replaced by one large one.\n\nThe classic example is a dynamic array, a vector. The structure holds a pointer to a buffer, a length, and a capacity. When the capacity runs out, the buffer is doubled with realloc and the data is carried over, so appending to the end stays amortized constant time. There is a well-known trap here: if realloc returned NULL and you wrote the result straight into your working pointer, the old block is lost forever, and that is a leak. So the result goes into a temporary variable first and is checked there. This is the same structure we saw in Rust under the name Vec: there the pointer, length, and capacity are hidden, and here you manage them yourself.\n\nThe main rule of manual management: every block must have one owner, who is responsible for freeing it. The language does not help, so ownership is fixed by convention. A function that creates an object is called new or create and returns a pointer; the paired free or destroy releases the object and everything it owns. If a function takes a pointer and only reads it, that is borrowing, and it must not free anything. Document in comments who owns the result, and do not pass ownership implicitly. Violations show up as three errors: a leak, if you forgot to free; a double free, if you freed twice; and use after free, if you kept using the pointer afterwards.\n\nThe simplest dynamic structure is a singly linked list. A node holds a value and a pointer to the next node, and the head of the list is a pointer to the first one. Inserting at the front takes three steps: allocate a node, point it at the old head, and make the new node the head. Traversal follows the chain until NULL. Deletion has to change the pointer of the previous node, and an elegant trick is to keep a pointer to a pointer: it points either at the head or at the next field of a node, and one piece of code handles both situations. Reversing a list takes three pointers: previous, current, and next. Don't forget to free every node when you delete the whole list.\n\nA stack and a queue can be built on an array or on a list. A stack works on the last in, first out principle: the operations push and pop at the top take constant time. A queue serves items in the order they arrive, and a convenient implementation is a ring buffer: an array of fixed capacity and two indices, head and tail, that wrap around modulo the capacity. A counter of elements helps tell an empty queue from a full one. A ring buffer needs no allocation on each operation and sits in memory contiguously, so system code uses it to pass data between parts of a program.\n\nA binary search tree stores a key in each node and two pointers: to the left child, where the keys are smaller, and to the right child, where they are larger. Insertion and search go down from the root, choosing a side at each node, and in a balanced tree they take logarithmic time. Walking from left to right yields the keys in ascending order. The recursive version is short and natural, but the depth of the calls equals the height of the tree, and for a degenerate tree that equals the number of nodes. Deletion has three cases: the node has no children, one child, or two; in the last case you replace the key with the smallest one from the right subtree. The tree must be freed by a traversal, children first, then the node itself.\n\nA hash table finds an entry by key in constant time on average. A hash function turns the key into a number, the remainder of dividing by the array size picks a bucket, and collisions are resolved by chaining: each bucket holds a list of entries. For strings a simple and popular function is FNV-1a: the bytes are mixed in one by one with exclusive or and multiplication by a prime number. When the ratio of entries to buckets exceeds a threshold, say three quarters, the table is rebuilt with twice as many buckets, and all the entries are placed again. This is the counterpart of the dictionary in Python and the HashMap in Rust, except that you have to write every step and take care of freeing.\n\nMemory errors are hard to find because they show up far from their cause. Sanitizers come to the rescue. AddressSanitizer surrounds every block with forbidden zones and reports out-of-bounds accesses and use after free, pointing to the lines where the memory was allocated and freed. The built-in leak detector lists the blocks that were never returned when the program exits. All of this is switched on with a single compiler flag during testing. The habit of running your tests under sanitizers is cheaper than any debugging. It also helps to set a pointer to NULL after freeing it and, where possible, to free memory in the same module where it was allocated.\n\nWhen there are a great many allocations, the general-purpose allocator becomes a bottleneck. Then people write their own. An arena is one large block and a pointer to the free space: allocation moves the pointer, and the whole arena is released in a single operation. A pool hands out blocks of equal size and keeps the free ones in a list: taking and returning a block is a few instructions. Such allocators are faster than general ones, do not fragment the heap, and simplify ownership: all objects of an arena die together. The price is that you have to know the memory usage patterns in advance.\n\nGeneric containers in C are built on a void pointer and an element size. A vector stores bytes and on every operation multiplies the index by the element size, copying data with memcpy. Type safety is lost: the compiler cannot tell a vector of ints from a vector of strings, so people wrap the interface in macros or write a separate set of functions for each type. To compare and process elements you pass function pointers, and we will talk about that in the next chapter. The more generic the code, the more responsibility lies on the programmer: size, alignment, the lifetime of stored pointers, and freeing of the contents are all in your hands.\n\nLet's sum up. The heap is for data whose size and lifetime are not known in advance: malloc, calloc, realloc, and free. You check the result of an allocation, write realloc through a temporary variable, give each block a single owner, and keep creation and destruction functions in pairs. Lists, stacks, queues, trees, and hash tables are built on pointers, and each structure is an agreement about ownership and invariants. Sanitizers find out-of-bounds accesses, double frees, and leaks. For speed you use arenas and pools. In the next chapter we will learn to pass functions around as data and to write generic code.
