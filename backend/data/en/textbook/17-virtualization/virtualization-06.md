#CHAPTER 6 | I/O: Device Emulation, virtio and vhost
Virtualization. Chapter 6. Input and output: device emulation, virtio and vhost. We virtualized the processor and memory in hardware, and they run at almost full speed. Input and output are harder: a guest's disk and network are not hardware, they are an invention of the hypervisor. Everything depends on how that invention is built: throughput, latency and processor load. There are three paths: emulation of a real device, paravirtual devices, and hardware passthrough. This chapter covers the first two, and we will look at passthrough in the next one.\n\nLet's start with emulation. QEMU pretends to be a real network card, for example an Intel e1000, and the guest loads an ordinary driver for it. The driver controls the card by writing and reading its registers, through memory addresses or I/O ports. The hypervisor intercepts every such access, and that is an exit. Sending a single packet takes about a dozen register accesses, that is, a dozen exits. The advantage of emulation is compatibility: drivers exist everywhere. The drawback is speed, which quickly runs into the number of exits.\n\nLet's follow the path of one such access. The guest writes to a register address, a nested page table violation occurs, and KVM returns control to the QEMU process with the reason MMIO. QEMU parses the address, finds the device, imitates its reaction, and calls KVM_RUN again. The result is a long path: from the guest into the kernel, from the kernel into a user process, back into the kernel, and again into the guest. Two context switches and an exit for every register write. For a hot I/O path that is too much.\n\nThe idea of paravirtual devices is simple: if both the guest and the hypervisor know the device is virtual, why pretend to be hardware? The virtio standard describes such devices: network, block device, console, balloon, random number generator. The virtio drivers are built into the Linux kernel, and for Windows there is a separate package. Instead of registers, the device and the driver communicate through shared memory and queues, and they draw each other's attention rarely and deliberately. Almost all I/O in the cloud rests on this principle.\n\nThe heart of virtio is the virtqueue. It consists of three areas in shared memory. The descriptor table describes buffers: address, length and a write flag, as well as a link to the next descriptor, so a single request can be a chain. The available ring is filled by the guest: it puts the numbers of the chain heads there. The used ring is filled by the device: it returns the processed chains. To start, the guest adds a request to the available ring and notifies the device once. When finished, the device puts the result into the used ring and interrupts the guest.\n\nThe main benefit of the queue is batching. The guest can put a hundred buffers into the queue and notify the device just once. In addition, both sides can ask each other not to disturb them: if the device is already busy processing, it sets a flag, and the guest does not ring again; modern versions also have event indexes for this. As a result, thousands of packets cost only a handful of exits. The new packed ring format in virtio 1.1 makes the queue even more compact and friendlier to hardware.\n\nBut even virtio in QEMU remains a user-space process: QEMU reads a packet from the queue and writes it to the tap network interface, which again means several transitions. The solution is called vhost. Queue processing is moved into a thread of the host kernel, which reads the rings directly and writes to the tap device without QEMU, which only sets things up. Notifications turn into signals: a guest write to a special address wakes the thread through an ioeventfd, and the interrupt to the guest arrives through an irqfd, with no exit into QEMU.\n\nThere are further steps. Vhost-user moves the queue handler into a separate user-space process, for example one based on DPDK or SPDK, which poll the queues without interrupts and deliver enormous speed. Shared memory is handed to that process over a socket. And vDPA goes even further: the data path itself is served by hardware, for example a smart network card, while the guest still sees a standard virtio device and uses the standard driver. Device control remains in the software layer.\n\nNow disks and network in more detail. Virtio-blk is the simplest block device, with a single request queue. Virtio-scsi supports many disks and SCSI commands, and QEMU executes requests through asynchronous I/O, for example io_uring, and usually in no-cache mode on the host so as not to duplicate the guest's cache. The network is built on a tap interface and a bridge, and multiple queues let different virtual processors work in parallel without a shared lock: one queue per processor.\n\nLet's sum up. Emulation is good for installation and old guests: drivers exist everywhere, but speed is low because of the exits. Virtio is the default choice: its queues cut the number of exits by orders of magnitude. Vhost moves processing into the kernel, and vhost-user and vDPA give even more speed. But if you need the speed of real hardware with no intermediaries at all, only one path remains: give the device to the guest entirely. In the next chapter we will see how to do that safely and what you lose in the process.
