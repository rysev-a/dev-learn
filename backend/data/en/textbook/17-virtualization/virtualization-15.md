#CHAPTER 15 | Nested virtualization: a hypervisor inside a virtual machine
Virtualization. Chapter 15. Nested virtualization: a hypervisor inside a virtual machine. So far we have run guests directly on the server. But what if you run a hypervisor inside a guest, and then start another virtual machine inside that? It sounds like a matryoshka doll, but this is how build systems in the cloud work, along with developer sandboxes, training labs, and even Windows with its subsystem for Linux. Let's see how it works and what it costs.\n\nLet's start with the names of the levels. The real hypervisor on the hardware is called level zero. The machine it runs, which in turn hosts a hypervisor, is level one. Its own guests are level two. The problem is that hardware support is designed for a single level: the processor has only one hypervisor mode. So the second hypervisor has to look real to its guest, even though in fact the whole illusion is maintained by the bottom one.\n\nOn Intel processors, the solution is this: the level zero hypervisor emulates the virtualization extensions for level one. When a level one guest executes the instructions that enable the mode, launch a machine, or read and write the control structure, the processor triggers an exit into the level zero hypervisor. It keeps three structures at once. The first describes level one itself. The second is what level one believes is the description of its own level two machine. The third is the real one, which level zero uses to actually run level two.\n\nLet's walk through one cycle. The level one guest launches its machine, and that is an exit into level zero. Level zero merges the description prepared by level one with its own requirements and builds the real structure. Then it launches the level two machine. When that machine exits, level zero decides whose exit it is. If it is addressed to level zero itself, it is all over quickly. If it is meant for level one, level zero writes the state into level one's description and enters level one, imitating an exit.\n\nNow it is clear where the cost comes from. A single level two exit that is addressed to level one turns into a chain: an exit into level zero, an entry into level one, and there the hypervisor reads and writes dozens of fields of the structure, and every one of those accesses is also an exit into level zero. In the worst case, one exit costs several dozen. What saves us is the shadow structure: the processor lets level one read and write the permitted fields without an exit, and the cost drops several times over.\n\nMemory tells a similar story. There are now three layers of addresses: the virtual address of level two, the guest physical address of level two, which is also the guest address of level one, and finally the level one address, which level zero turns into the real one. The hardware can only handle one level of nested tables. So the level zero hypervisor builds a table out of two: it combines level one's table for level two with its own table for level one. Table faults are handled by level zero as well.\n\nInput and output cost even more. The disk or network of a level two machine is a device invented by the level one hypervisor, for example a paravirtual one. And the disk and network of level one itself are, in turn, invented by level zero. That makes a double chain, and every link adds copying and exits. Passthrough devices can ease the pain: level zero hands a card to level one, and level one passes it further down, provided there is nested protection for direct memory access.\n\nWhat is supported in practice? KVM can host nested hypervisors on both Intel and AMD processors, and in modern kernels this is usually enabled. Clouds allow nested virtualization only in some places and only for some kinds of machines: some providers enable it with a flag, others offer it only on machines without a hypervisor, and others not at all. Check your provider's documentation. Inside the guest, the check is simple: the processor must show the virtualization features.\n\nWhat are the risks? The trusted base grows, and escapes are now possible at two levels. Side channels between the levels remain, and confidential computing supports nesting only in a limited way so far. Speed drops too: computation runs almost as usual, but frequent exits, input and output, and page table work suffer noticeably. That is why nesting is good for development, testing, and builds, but in production workloads it is best avoided.\n\nLet's sum up. Nested virtualization is needed when you have to run a hypervisor where you have no access to the hardware. It works because level zero emulates the extensions for level one and merges the tables. The main cost is the multiplication of exits, softened by the shadow structure. If you can avoid it, pick machines without a hypervisor, or containers.
