#CHAPTER 1 | Why virtualization: isolation, density, and the Popek and Goldberg conditions
Virtualization. Chapter 1. Why virtualization: isolation, density, and the Popek and Goldberg conditions. This book is about how one physical computer pretends to be several. We'll start with the idea and the history, then go down to the processor and memory, and look at hypervisors, migration, containers, and security. Everything you know from the books on architecture, Unix, and networking will come in handy here: interrupts, paged memory, sockets. In this first chapter we'll answer three questions: why anyone needs this, what a virtual machine monitor has to be able to do, and when it can be built on a processor at all.\n\nLet's start with the problem. It used to be that every application got its own server: that's simpler and safer, because programs don't get in each other's way. But most of the time such a server sits almost idle: the load comes in peaks, and you have to buy for the peak. Often the processor is busy for only a small fraction of the time, while the memory and the power are paid for in full. The second trouble is compatibility. One program needs an old version of a library, another needs a new one, and a third wants a different operating system altogether. So we'd like to split one powerful machine into several isolated ones, each behaving like a separate computer.\n\nThat is exactly what virtualization is. A thin layer appears between the hardware and the operating systems; it divides the processor, memory, and devices into parts and hands each part to its own virtual machine. There are three benefits. Isolation: a crash or a break-in on one machine doesn't take down its neighbors. Density: a dozen machines live on one server instead of one, and the loads of different machines don't add up to the sum of their peaks but to a much smoother curve. Manageability: a virtual machine can be saved as a snapshot, copied, stopped, and even moved to another server without shutting it down.\n\nNow let's settle on the words. The physical computer is called the host. The virtual machines that run on it are called guests. And the program or layer that creates and guards them is called a hypervisor, or a virtual machine monitor. The hypervisor is invisible to the guest: the guest operating system is sure it owns the processor, memory, and disks completely. In reality, every access to the real hardware goes through the hypervisor, and it decides what to allow, what to replace, and what to show the guest as an invented device.\n\nThe idea is very old. In the nineteen-sixties, at an IBM research center, engineers built a system called CP-forty, and then CP-sixty-seven, where each user got their own copy of the computer. Then came VM three-seventy: a monitor that gives every user a virtual machine in which you can run any operating system for the same architecture. IBM mainframes still work this way today. On ordinary computers the technology disappeared for a long time, and came back in the late nineteen-nineties, when there were too many servers and processors had power to spare.\n\nIn nineteen seventy-four, Gerald Popek and Robert Goldberg published a paper that formally described what a virtual machine monitor is. It has to have three properties. The first is equivalence: a program in a guest machine behaves the same as on a real computer, give or take the execution time and the limits on resources. The second is resource control: the monitor fully controls everything handed out to guests, and a guest can't grab anything extra. The third is efficiency: the vast majority of guest instructions run directly on the hardware, without the monitor getting involved.\n\nThe third property raises the main question: how do you tell the instructions that can run directly from the ones that can't? Popek and Goldberg split instructions into classes. Privileged instructions are those that cause a trap in user mode, that is, hand control to the kernel. Sensitive instructions are those that change or read the state of the machine itself: the processor mode, the page tables, the interrupt flag. The theorem says that a monitor can be built in a simple way if every sensitive instruction is also privileged. Then the processor itself stops any dangerous guest instruction and hands it over to the monitor.\n\nHypervisors come in two types. Type one runs right on the hardware and is itself a small operating system: that's how Xen, VMware ESXi, and Hyper-V are built. Type two runs as an ordinary program inside the host operating system: that's how VirtualBox and VMware Workstation work. Between them sits a hybrid, KVM, which turns the Linux kernel itself into a hypervisor: the host system stays an ordinary one, but its kernel gets the right to run guests directly on the processor. For the guest there is no difference; it only matters who controls the hardware and through how many layers.\n\nVirtualization is easy to confuse with neighboring technologies. Emulation decodes and executes every guest instruction in software, as QEMU does in translation mode: the guest can be of a completely different architecture, but the price is speed, several times and even tens of times lower. Virtualization runs guest instructions on a real processor, so the guest has to be of the same architecture. A container doesn't create a new machine at all: it's a set of isolated processes sharing one kernel, and we'll compare them with virtual machines in chapter twelve. The three technologies sit at different points of the trade-off between speed and isolation.\n\nVirtualization is never free, and you should understand the price. Ordinary computation the guest does directly on the processor, with almost no loss. The expensive part is everything that needs the monitor to step in: privileged instructions, access to devices, misses during memory address translation. So the history of virtualization is the history of speeding up exactly these places: first clever software tricks, then hardware support in processors, then paravirtual devices. In the next chapter we'll see why the simple Popek and Goldberg scheme didn't work on the most popular processor, the x86.
