#CHAPTER 4 | Guest memory: shadow page tables, EPT and NPT, and huge pages
Virtualization. Chapter 4. Guest memory: shadow page tables, EPT and NPT, and huge pages. Now let's talk about the most expensive resource in virtualization: memory. The guest system is sure that its physical memory starts at zero and belongs to it alone. In reality the guest has three kinds of addresses: the virtual address inside a program, the guest physical address, which the guest believes is real, and the host physical address, which exists in the hardware. The hypervisor's job is to turn the first address into the third, quickly and safely.\n\nLet's recall how paged memory works, from the book on computer architecture. An address is split into four indexes of nine bits each, one for each of the four levels of tables, and a twelve-bit offset within the page. The root of the tables is held in the CR3 register, and the cache of finished translations is called the TLB. The guest keeps its own tables, and its CR3 register holds a guest physical address. But the processor has to walk through real physical addresses. So one table is not enough: we also need a translation from the guest physical address to the host one.\n\nThe first solution is shadow page tables. For each of the guest's tables, the hypervisor builds a shadow in which the guest's virtual address is translated straight to the host physical address. It's the shadow that it puts into the real CR3 register. To keep the shadow from falling behind, the pages holding the guest's tables are write-protected: any edit the guest makes to its own table causes an exit into the hypervisor, which updates both the original and the shadow. A process switch in the guest, that is, a write to CR3, is intercepted as well and swaps in a different shadow.\n\nShadow tables work, but they're expensive. Every operation that changes the memory mapping, such as creating processes, launching programs, and allocating memory, turns into exits. Workloads that created processes often slowed down several times over. The shadows take up memory and must be exact copies: a mistake in synchronization leads to subtle and dangerous bugs. The complexity of this code in hypervisors was legendary. Before hardware help arrived, memory was the main bottleneck of virtualization on x86.\n\nThe hardware solution is called nested paging. On Intel it's EPT, extended page tables, and on AMD it's NPT, nested page tables, also known as RVI. The idea is simple: the processor has two tables at once. The first is kept by the guest and translates the guest virtual address into a guest physical one. The second is kept by the hypervisor and translates the guest physical address into the host one. The hardware walks both. The guest changes its tables without a single exit, and the hypervisor edits only the nested ones, so each side minds its own business.\n\nBut you pay for the convenience. To translate one address on a TLB miss, the processor does a two-dimensional walk. Each of the four steps of the guest walk produces a guest physical address, which itself has to be translated in four steps through the nested tables, and one more such translation is needed for the final address. In total that's five times five minus one, that is, twenty-four memory accesses instead of four. This is why a translation cache miss is especially expensive in virtualization.\n\nHence the main conclusion: protect the TLB. It holds finished translations from the virtual address straight to the host one, so the two-dimensional walk is needed only on a miss. The entries are tagged with the guest's identifier, VPID on Intel and ASID on AMD, so the cache doesn't have to be flushed when switching between the guest and the hypervisor. The processor also keeps intermediate results of walks in additional caches. All of this softens the price of two-dimensional tables, but doesn't remove it completely.\n\nThe strongest remedy is huge pages. A two-mebibyte page shortens the walk by one level, and a one-gibibyte page by two. If both the guest and the hypervisor have big pages, the walk becomes several times shorter. And most importantly, a single translation cache entry now covers a huge chunk of memory: with fifteen hundred entries, that's about six mebibytes on ordinary pages and about three gibibytes on huge ones. In Linux, the hypervisor gets such pages through transparent huge pages or a dedicated pool.\n\nNested tables give the hypervisor a powerful tool: the nested page fault, called an EPT violation on Intel. When the guest accesses a guest physical address that is missing from the nested table or whose permissions don't match, the processor makes an exit with the reason violation. The hypervisor can allocate a page at the moment of first access, bring it back from swap, make a copy on write, or simply mark it as dirty. An access to a device address also ends in a violation, and the hypervisor emulates the register. Almost everything in the following chapters rests on this mechanism.\n\nLet's sum up. Shadow tables give a fast walk but expensive edits, while nested tables give cheap edits and an expensive cache miss. Modern processors chose nested tables, and in KVM they're enabled by default. The practical advice is this: give guests huge pages, especially for databases, watch the TLB miss rate, and remember that every clever hypervisor trick, whether swapping or deduplication, works through nested page violations. Next we'll see how they are used to save memory.
