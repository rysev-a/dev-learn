#CHAPTER 5 | Saving Memory: Ballooning, KSM and Overcommit
Virtualization. Chapter 5. Saving memory: ballooning, KSM and overcommit. Memory is the scarcest resource on a server, and it is memory that most often limits the number of virtual machines. A simple observation comes to the rescue: guests almost never use everything they were given. If you promise guests more memory than you really have, more machines fit on one server. In this chapter we will look at how to promise with a margin, how to take back memory that a guest considers its own, and how to find duplicates.\n\nPromising more than you have is called overcommit. The total memory of all guests exceeds the physical memory, and as long as they do not ask for everything at once, the system works. A guest usually keeps file caches and pages it has not read for a long time, and it can do without them. In KVM, the guest's memory is ordinary anonymous memory of the QEMU process, so the host kernel can reclaim it just as it does for any program. The risk is clear: if all guests demand their share at the same moment, swapping starts, or the out-of-memory killer starts killing processes.\n\nThe simplest tool is to swap the guest's pages out to disk right at the hypervisor level. But the hypervisor does not see which pages the guest needs. It may swap out exactly the working data, or the file cache pages that the guest kernel itself would have evicted first. Worse, the guest operating system also does swapping, so you get double swapping: a page sits on disk twice, or is read in just to be written somewhere else. This path is fine as a last line of defense, but not as the main one.\n\nIt is smarter to negotiate with the guest itself. That is why ballooning was invented: inside the guest runs a driver called the balloon, for example virtio-balloon. When the hypervisor needs memory, it asks the driver to inflate. The driver requests the needed number of pages from the guest kernel, and the kernel decides what to sacrifice: free pages first, then cache, and only as a last resort does it push data out to swap. The driver passes the numbers of the pages it got to the hypervisor, and the hypervisor takes back the host memory behind them. Deflating works the other way round.\n\nBallooning has its limits. You need a driver in the guest and its cooperation, and the process is not instant: the guest needs time to free the pages. You cannot take more than the guest can give up without harm: every machine has a lower bound. That is why management systems keep two values for each machine, the configured memory and the current memory, and change the second within the limit set by the first. There are also newer techniques: free page hints, where the guest itself reports unused memory without inflating a balloon, and memory allocated in blocks with virtio-mem.\n\nAnother source of savings is duplicates. Ten identical guests keep ten copies of the same kernel and libraries in memory. KSM, kernel same-page merging, looks for such copies. A background thread scans pages that an application has marked as mergeable, and QEMU does this for guest memory. When it finds pages with identical contents, it keeps one physical copy, maps all the others onto it as read-only, and frees the extra pages.\n\nWhat happens if a guest writes to a merged page? The nested page table forbids the write and a violation occurs. The hypervisor makes a copy on write: it allocates a new page, copies the contents, and allows writing only for the owner. The others keep sharing the common copy. It is the same trick processes use with the fork call. The benefit of KSM is noticeable with identical guests, and the price is processor time for scanning: the more memory and the more frequent the checks, the higher the load.\n\nMerging has an unpleasant side. A write to a shared page is noticeably slower than an ordinary write, because a copy is needed. An attacker in one machine can prepare a page with the suspected contents, wait for the merge, and from the write time learn that a neighbor has exactly the same page. This is how secrets leak through KSM. That is why many providers turn off merging between untrusted tenants. One more incompatibility: huge pages get in the way of merging, since only regular pages can be merged, which means large pages have to be split.\n\nHow do you tell that memory is running short? The host shows memory pressure: the pressure stall information for memory says how much time processes spent waiting for memory. Watch swapping on the host and in the guests, the share of used and available memory, and the number of merged pages and inflated balloons. A typical policy is stepwise: while there is enough free memory, do nothing; as the reserve shrinks, inflate balloons on the machines that have slack; and only if that does not help, the host starts swapping.\n\nLet's sum up. Overcommit is cheap but risky. Hypervisor swapping needs no help from the guest, but it is slow and blind. Ballooning is precise and uses the guest's knowledge, but it needs a driver and time. Page merging finds duplicates, but it eats processor time and opens a side channel. A good hypervisor combines all of this and keeps a reserve. In the next chapter we move on to input and output: a guest's disks and network work in a fundamentally different way from memory, and the number of exits turns out to be what matters most.
