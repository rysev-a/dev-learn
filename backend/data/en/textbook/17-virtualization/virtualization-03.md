#CHAPTER 3 | Hardware support: VT-x, AMD-V, VM exit, ARM EL2, and RISC-V H
Virtualization. Chapter 3. Hardware support: VT-x, AMD-V, VM exit, ARM EL2, and RISC-V H. The software tricks from the previous chapter worked, but they were complicated and slow. The processor vendors solved the problem at the root: they added a special mode for the guest. In two thousand five Intel released VT-x, and in two thousand six AMD released AMD-V. Since then the Popek and Goldberg scheme works on x86 again, and the problem of the seventeen instructions is solved without any translation.\n\nThe main idea of VT-x is two modes, called monitor mode and guest mode, or in Intel's words, VMX root and non-root. Each of them has its own four protection rings. The guest kernel runs in ring zero of guest mode and executes privileged instructions as usual without breaking anything, because the real machine doesn't belong to it. The monitor occupies ring zero of monitor mode and controls which events force the guest to hand control back. There's no need to squeeze the rings anymore: the guest got a real privileged mode, but on a leash.\n\nThe leash is kept in a structure called the VMCS, the Virtual Machine Control Structure. It's a page-sized area of memory, and you can reach it only through the special instructions VMREAD and VMWRITE. It has four groups of fields. Guest state: registers, the instruction pointer, tables. Host state: where to return to. Control bits: which events must cause an exit. And exit fields: the reason and details of the last exit. You turn the mode on with the VMXON instruction, start the guest with VMLAUNCH, and after the first exit you continue with VMRESUME.\n\nThe working cycle is visible from the names. On VM entry, the processor loads the guest state from the VMCS and starts executing its instructions, without interfering at all. While the guest does ordinary things, nothing happens. A VM exit happens when the guest executes an instruction or hits an event that is marked as intercepted. The processor itself saves the guest state, records the exit reason, loads the host state, and passes control to the monitor. The monitor figures it out, handles the event, and enters the guest again. The whole switching cycle is done in hardware.\n\nWhat causes an exit? Some events always exit: the processor identification instruction, the VMCALL hypercall, and any attempt to use virtualization itself. Everything else is configurable. You can intercept accesses to I/O ports, the halt instruction, accesses to control registers, such as loading a page table, and reads and writes of special registers. Any external interrupt also pulls the guest out. A good monitor intercepts only what's necessary: every extra bit in the VMCS means extra exits. For example, the guest's accesses to its own page table don't need to be intercepted if memory is virtualized in hardware, and that's the topic of the next chapter.\n\nHow much does an exit cost? An exit and re-entry together take on the order of a thousand cycles, and on some processors several thousand, plus the time of the handling itself in the monitor. For rare events that's nothing, but for hot ones, like hundreds of thousands of network card accesses per second, it becomes a noticeable share of the processor. That's why in production, exits are counted and profiled, and developers fight them: with paravirtual devices, which we'll cover in chapter six, and with hardware interrupt delivery such as APICv, which lets the guest avoid exiting on every interrupt.\n\nAMD does things in a similar way, but with different words. Instead of the VMCS it has the VMCB, the Virtual Machine Control Block, and a single instruction, VMRUN, starts the guest. The exit is called VMEXIT, and the intercept causes are set by bits in the same block. There is one difference: AMD keeps the guest state in an ordinary memory page and uses address space tags, called ASIDs, so that the translation cache doesn't have to be flushed at every switch. Intel added tags too, called VPIDs. For a programmer the two variants are almost the same, and in the Linux kernel a common KVM layer takes care of both.\n\nThe ARM architecture is built differently. The processor has four exception levels: zero for programs, one for the operating system kernel, two for the hypervisor, and three for the secure monitor. These levels existed before virtualization, so no separate guest mode was needed: the guest kernel simply runs at level one, and the hypervisor at level two, more privileged than it. From level one, the hypervisor is called with the HVC instruction. A Linux kernel running as the host would like to live at level two, and the Virtualization Host Extensions, VHE, introduced in ARMv8.1, let it do that and spared it from needless switches.\n\nIn the RISC-V architecture, the H extension, ratified in two thousand twenty-one, gives the hypervisor its own mode. On top of the usual machine, supervisor, and user modes, there's a virtualization bit. The hypervisor runs in hypervisor-extended supervisor mode, and the guest runs in virtual supervisor and virtual user modes. The guest kernel accesses its own registers, for example the page table register, and the processor quietly substitutes virtual copies. If the guest tries to touch the hypervisor's registers, it gets a special exception, a virtual instruction exception. This is how a modern open architecture got virtualization without any workarounds.\n\nLet's see how KVM uses all this. A virtual machine monitor such as QEMU opens the device slash dev slash kvm and asks to create a virtual machine and virtual processors. Each virtual processor is an ordinary Linux thread. It calls KVM_RUN, and the kernel enters the guest. Events that the kernel can handle itself, such as interrupts, halts, and page faults, are handled without returning to user mode. Only device accesses go back to QEMU. We'll go through this loop in detail in chapter eight, and in chapter four we'll start with the most important resource, memory.
