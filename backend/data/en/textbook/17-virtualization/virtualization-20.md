#CHAPTER 20 | Storage: domains, the SPM, and image chains
Virtualization. Chapter 20. Storage: domains, the SPM, and image chains. In oVirt, machine disks live in storage domains. The main kind is the data domain, which holds disk images, templates, and snapshots. One data domain of a data center plays the role of master and keeps the pool's service data. ISO and export domains are deprecated; images are now uploaded straight into a data domain. In addition, every data domain carries special OVF_STORE disks with the descriptions of its machines, from which the configuration can be rebuilt if the engine is lost.\n\nDomains are split into file-based and block-based. File domains are NFS, any POSIX-compliant file system, GlusterFS, and a local directory of a host: the host mounts them, and disks are simply files. Block domains are iSCSI and Fibre Channel: the host sees raw volumes, and the logical volume manager, LVM, carves disks out of them. There is also a third branch, Managed Block Storage: Cinder drivers attach systems such as Ceph. Its features are still limited, so rely on it carefully and check the documentation of your version.\n\nLet us look inside a file domain. The root directory is named by the domain identifier, and inside are two branches. The dom_md folder is the service one: it holds the metadata file with the description of the domain, the ids file for host numbers, the leases, inbox, and outbox files, and in newer versions also xleases for machine leases. The images folder has a directory per disk, and in it the volume files named by identifiers. Next to each volume sit a meta file with its description and a lease file with its lease. Remember the difference: a disk is a directory, and a volume is a file inside it.\n\nA block domain holds the same things, but on LVM. The domain is a volume group, and its name equals the domain identifier. Service data live in the logical volumes metadata, ids, leases, inbox, outbox, and xleases, and the master has one more volume called master. Every disk volume is a separate logical volume named by an identifier. The links between volumes are recorded in tags: a tag with the image identifier, a tag with the parent identifier, and a tag with the slot number in the metadata volume. A shortage of space is cured by adding new devices to the volume group.\n\nNow the main question: who is allowed to change the metadata? In the classic scheme, only one host per data center: the Storage Pool Manager, or SPM. It creates and deletes volumes, extends them, and makes snapshots. Why? The metadata are shared, and a shared file system or volume group cannot resolve write conflicts by itself. One writer means no conflicts. The engine appoints the SPM taking into account the host's priority and storage reachability. But one host is a bottleneck, so more and more operations move to the SDM model, where any host works on a volume after taking a lease on it.\n\nHow do we guarantee that there is one SPM, and that a machine runs in only one place? That is the job of sanlock. Every host gets a number in the domain and regularly renews its lease in the ids area. If a host vanishes and stops renewing, the lease expires after roughly eighty seconds by default. The SPM itself also holds a lease, on the master domain. There are volume leases and machine leases too: while one host owns them, another cannot change the volume or start the same machine. A host that lost contact with storage is rebooted by the watchdog.\n\nNow disk formats. The raw format is simply the bytes of the disk. The qcow2 format, also called COW, keeps tables and supports snapshots. The second axis is allocation: a preallocated disk takes everything at once, a thin one grows as data is written. On a file domain, a thin disk is a sparse file and grows by itself. On a block domain it is harder: it is qcow2 inside a small logical volume, and VDSM watches the fill level. When free space drops below a threshold, the host asks for the volume to be extended by a chunk, in the classic scheme through the inbox and outbox mailboxes. If it is too slow, the machine gets a write error and pauses.\n\nSnapshots and templates turn into volume chains. The base is the very first volume and has no parent. A template is a base on which linked clones are built: every machine has its own thin layer on top of the shared base. When a snapshot is taken, the current leaf is frozen and becomes internal, and a new empty volume becomes the leaf that receives all writes. A read goes from the leaf down the chain to the first volume that has the needed block. That is why a long chain slows reads, and every snapshot adds metadata. A live merge removes the extra link without stopping the machine.\n\nHosts constantly check every domain: they read its metadata and measure the delay, and the results go to the engine. A domain can be active, inactive, in maintenance, locked for the time of an operation, or unknown when there is no data. If one host loses a domain, that host becomes Non Operational. If nobody sees the domain, it goes Inactive, and machines with disks on it are paused. If the master is lost, the engine tries to appoint another domain as master, which is called master reconstruction. And before any works, the domain is put into Maintenance.\n\nDisks can be moved and copied between domains. A cold move copies the whole image, while live storage migration first takes a snapshot, then mirrors the blocks to the new domain, switches the machine over, and deletes the old copy. Thin disks can be compacted: the sparsify operation returns the space the guest has freed. Mind the sizes: a disk has a virtual size and an actual size. The sum of the virtual sizes of thin disks can exceed the domain capacity, which is overcommit. By default a warning arrives at ten percent free space, and at five gigabytes new disks and snapshots cannot be created.
