#CHAPTER 16 | Practice: QEMU/KVM by hand and observability
Virtualization. Chapter 16. Practice: QEMU and KVM by hand, and observability. The theory is over, and it is time to get our hands on a live machine. You will need a Linux host with access to KVM, the QEMU package, and a little patience. Other systems work too: on macOS there is Apple's accelerator, and on Windows there is the Windows Hypervisor Platform. All the commands in this chapter are collected on the slides, and in the text we will go over what each one does and why.\n\nStart by checking readiness. The processor must show the virtualization flags, and the dev kvm device must exist and be accessible to your user, usually through the kvm group. Utilities such as virt-host-validate check everything at once: the processor, kernel modules, control groups, and the IOMMU. If you are inside a virtual machine, you will need to make sure nested virtualization is enabled, otherwise the guest will only run on software translation.\n\nThe first machine comes together quickly. Create a disk in the qcow2 format, take a ready-made cloud image of some distribution, and write a small initial configuration file that sets a user and a key for logging in. Start QEMU with KVM acceleration, a paravirtual network, and a forwarded port for SSH. In half a minute you will have a machine you can log in to, and it will run at nearly the speed of the hardware.\n\nThere are several ways to control a running machine. QEMU has its own monitor, where you can pause the machine, take a snapshot of its state, and return to it. For programs there is the QMP channel, which speaks JSON. A higher level is libvirt with its virsh command: it starts and stops machines, shows information about them, creates snapshots, and changes parameters on the fly. In practice, you will mostly go through libvirt.\n\nNow try image layers. Create a new image on top of a base one and see that it takes only a few kilobytes. Take several snapshots and look at the chain with the image info command. Then commit the upper layers down, and after that flatten the whole chain into a single file. While you are at it, check how read speed changes when reading from deep layers. These experiments reinforce everything you saw in the simulator, and show that the sizes and chains really are what the textbook says.\n\nNow the network. The simplest mode is user-space networking: the machine reaches the outside through a built-in address translator and needs nothing, but incoming connections are possible only through port forwarding. For serious work you create a tap interface and attach it to a bridge, and set up outside access through packet filters. Check that vhost is enabled, and try several queues on the virtual interface: throughput will grow noticeably.\n\nLet's move on to observing the host. The kvm_stat utility shows event counters in real time, including the number of exits by reason. The perf kvm stat command records exits and produces a report: which reasons are the most frequent and what share of time they take. Usually the leaders are processor halts, external interrupts, writes to special registers, and nested page table violations. If port accesses show up at the top, it means that somewhere emulation is used instead of paravirtual devices.\n\nLook from inside the guest as well, and at the level of resources. In the guest's top utility, the st column shows stolen time. The pressure files under proc pressure report how long tasks waited for the processor, memory, or disk. The virsh domstats command prints, for each machine, the balloon size, the number of processors, and disk and network statistics. And numastat with a process option shows whether QEMU's memory sits on the right node. Together these sources give you the full picture.\n\nTypical problems and first checks. Slow network: make sure the device is paravirtual, vhost is enabled, and there are enough queues. Disk latency: the no-cache mode, asynchronous I/O, and discarding blocks. High stolen time: overcommit and processor pinning. The machine will not start: permissions on the KVM device, nested virtualization being enabled, the processor model version. Migration does not converge: the rate at which dirty pages appear. Every "it doesn't work" has a short list of checks.\n\nLet's sum up the book and the chapter. You can now check a host's readiness, start a machine, control it, build images with layers, configure the network, and see what is going on inside: from exits to memory pressure. Next, it is worth reading the KVM and QEMU documentation, the Firecracker source code, and projects built on rust-vmm. The most valuable thing is to break and fix things yourself: virtualization is learned best by hand. Good luck with your experiments.
