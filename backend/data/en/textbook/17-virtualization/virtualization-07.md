#CHAPTER 7 | Device Passthrough: IOMMU, VFIO and SR-IOV
Virtualization. Chapter 7. Device passthrough: IOMMU, VFIO and SR-IOV. Sometimes virtio is not fast enough: a graphics card needs millions of accesses per second, a hundred-gigabit network card needs direct access to its queues, and a storage drive has to be squeezed to the limit. Then the physical device is handed to the guest whole. This is called passthrough. It sounds simple, but along the way you meet three problems: letting the device access memory directly and safely, delivering its interrupts, and fairly dividing one device among several guests.\n\nThe main danger is direct memory access, DMA for short. The device reads and writes main memory by itself, bypassing the processor and the nested page tables. The guest driver tells it the address of a buffer that it believes is physical, but in fact it is a guest physical address, and the device will take it as a host address. Without protection, a guest could make the device write data into the memory of the host or a neighbor. That is a ready-made escape route from the virtual machine, so the processor's nested tables alone are not enough here.\n\nProtection is provided by the IOMMU: Intel calls it VT-d, AMD simply calls it the IOMMU, and on ARM it is the SMMU. It is a block between the device and memory, the equivalent of paging for devices. Its tables translate the address given by the device into a host address and check permissions. Each device is identified by its bus, device and function number and is attached to its own domain. The hypervisor fills the domain's table from the mapping of guest physical addresses to host ones, and now the device sees exactly the memory that the guest sees.\n\nThe second obstacle, interrupts, is handled by interrupt remapping. A device sends an interrupt by writing a special message, and the IOMMU checks it against a table: this device may send only these interrupts, and only to these virtual processors. That way a device in a guest cannot trigger someone else's interrupt. Modern processors can deliver such an interrupt straight to a running guest without an exit, and this is called posted interrupts. Remapping works even without passthrough, as protection against spoofing.\n\nOn Linux, passthrough is organized by the VFIO subsystem. Devices are combined into IOMMU groups: if a bridge does not isolate devices from each other, the IOMMU cannot tell them apart, and they must be handed over together. The procedure is this: unbind the device from its native driver, bind it to the vfio-pci driver, and open the group in QEMU. QEMU creates a container and, with the map command, enters guest memory into the IOMMU tables, pinning the pages so that they do not move while data is being transferred.\n\nPassthrough costs you flexibility. Pinned memory cannot be evicted, ballooned or merged, which means overcommit is impossible for such a machine. The state of a real device is hard to move, so live migration and snapshots are usually unavailable. The device is tied to a specific server and goes to one machine only. In return, the guest gets speed close to that of the hardware and uses the vendor's native drivers, for example for graphics accelerators and network cards with offload.\n\nTo share one device among several guests, SR-IOV was invented: a single physical device presents itself as one physical function and many virtual ones. The physical function is fully featured and is managed by the host. Each virtual function is a lightweight copy with its own queues and registers, and to the system it looks like a separate PCI Express device with its own address. Each such function can be given to its own virtual machine through VFIO. The switching between them is done by the card itself, and the number of functions runs into the tens and hundreds.\n\nThere are also intermediate approaches. Mediated devices split a graphics card in software: the host driver creates virtual graphics accelerators, and the guest gets a share. The newer family called Scalable I/O Virtualization allows far more instances to be created than SR-IOV does. And vDPA, as we discussed, leaves the guest with a standard virtio driver over a hardware data path, which makes migration easier, because the guest does not depend on a specific card.\n\nIn practice, passthrough runs into pitfalls. Devices end up in large IOMMU groups because the platform does not enable isolation. A device must be able to reset itself, otherwise after the guest stops it will not return to a clean state. Pinned memory requires planning, and it matters to keep the device and the memory close to the same processor socket. Sometimes the guest driver behaves strangely when it notices a hypervisor. These problems are solvable, but you need to know them in advance, before promising customers hardware speed.\n\nLet's sum up the section on memory and I/O. Emulation is compatible and slow. Virtio is fast, and supports migration and density. Vhost reduces the load on the host. Passthrough and SR-IOV give hardware speed but tie the machine to a server. vDPA tries to join hardware speed with the freedom of virtio. The choice depends on the task: what matters more to you, speed, or migration and density. In the next section we will put it all together and see how KVM and QEMU turn these ideas into a working hypervisor.
