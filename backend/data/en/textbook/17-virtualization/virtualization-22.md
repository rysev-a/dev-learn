#CHAPTER 22 | The scheduler, migration, and high availability
Virtualization. Chapter 22. The scheduler, migration, and high availability. Let us begin with the question of which host a machine should land on. In oVirt this is the job of the engine's scheduler, and it works in two steps. First come filters: each one throws out hosts that cannot work at all, for example a host without the needed network, without enough memory, or with an unsuitable processor. Then come weights: each module ranks the remaining hosts, the ranks are multiplied by the policy's factors and summed, and the host with the best total wins. A filter says "not allowed", a weight says "better here".\n\nA set of filters, weights, and factors is called a scheduling policy, and it is chosen per cluster. There are five built-in policies. None balances nothing and merely spreads machines at start time. Evenly distributed levels the processor and memory load. Power saving does the opposite: it packs machines onto fewer hosts and frees the rest. VM evenly distributed levels the number of machines per host. Cluster maintenance lets only highly available machines through during work. The load balancer does not run at start time but periodically: it finds an overloaded host and migrates a machine off it, usually one per pass.\n\nThe scheduler counts not what machines have actually eaten, but what has been promised to them. A cluster has memory optimization: no overcommit, one hundred fifty percent for server load, or two hundred for desktop load. A host's scheduling memory is its physical memory multiplied by this factor, minus a reserve, minus the memory of every running and starting machine. If the remainder is too small for a new machine, the memory filter drops the host. The processor is treated more softly: the filter only checks that a machine has no more virtual processors than the host has cores (or threads, if the cluster counts threads as cores), while the weights and the balancer regulate how busy the host is.\n\nNeighbor rules are set by affinity groups. A group joins machines and, if desired, hosts. A positive rule requires keeping machines together, a negative one keeps them apart, for example two database replicas on different hosts. A rule can be hard, called enforcing, or soft. A hard rule works as a filter: if it cannot be met, the machine will not start and will not move. A soft rule is a weight: the scheduler tries but is not obliged. A group can also tie machines to hosts. Finally, affinity labels are just names attached to both machines and hosts; they are a special case of affinity groups that ties a machine to hosts. A label can conflict with a group, and then the machine will not start.\n\nHigh availability is switched on per machine with a checkbox. If a host disappears and the engine has made sure it is off, for example through fencing, the highly available machines are restarted on other hosts in order of priority: high, medium, low. Whoever does not fit has to wait. To avoid depending on fencing, a machine can be given a lease: a service record on a storage domain, held by the running host. While the lease is alive a second copy of the machine cannot start, and once the host has vanished it can be safely started elsewhere. For such machines the only resume behavior after storage loss is to kill and restart.\n\nNow live migration. It works as pre-copy. First the whole guest memory is copied to the destination host while the machine keeps running. QEMU tracks dirty pages: those the guest has changed during the copy. The next pass sends only them, then again only the newly dirtied ones, and so on in a loop. When the remainder can be sent faster than the allowed downtime, the machine is stopped for a moment, the rest is sent, and the machine is started on the destination. But if the guest writes to memory faster than the network carries it away, the remainder does not shrink, and the migration does not converge.\n\nWhat to do when a migration does not converge is decided by the migration policy: it is set per cluster and can be overridden per machine. Legacy is the historical variant: VDSM decides everything with its own timers, and newer versions no longer show it in the interface. Minimal downtime reacts not to time but to QEMU iterations: if the migration stalls, the allowed downtime grows in steps, roughly from a hundred milliseconds to half a second, and then the migration is aborted. Suspend workload if needed allows a very long downtime at the end. Post-copy switches the machine to the destination host and pulls the missing pages on demand: it always converges, but a network break at that moment kills the machine. Auto-converge, which slows the guest down, and stream compression, which sends only the differences of pages that changed again, help too.\n\nNow the plumbing. Migration goes over the migration network: a separate logical network can be set aside for it so that it does not disturb management and machine traffic. The bandwidth is configurable: automatic from the link speeds, the hypervisor default, or manual, and it is shared between parallel migrations. A host runs a limited number of migrations at once (the limit is configurable), and the rest wait in a queue. Newer versions can use several parallel connections for one migration. There are timeouts too: with no progress for roughly one hundred fifty seconds, or if the migration drags on too long, it is cancelled and the machine stays on the old host.\n\nMemory and the processor can be tuned as well. KSM merges identical pages of different guests into one copy; when memory is short, it is switched on by the MOM daemon, which ships together with VDSM. Ballooning works differently: a driver inside the guest, at the host's request, takes free memory and gives it back to the host. For latency-sensitive workloads there is pinning: virtual processors are bound to physical cores, and the guest is cut into virtual NUMA nodes mapped onto the host's nodes. The dedicated policy gives the cores to the machine entirely. Huge pages reduce the load on the translation cache, but memory for them is reserved in advance. Pinned machines are tied to hosts and migrate poorly.\n\nThe last lever is the cluster's resilience policy. It answers the question of what to do with machines when a host becomes non-operational: migrate all of them, migrate only the highly available ones, or migrate none. And so that one machine does not eat a host, there are limits. CPU shares divide core time by weight at the moment of shortage. CPU QoS sets a ceiling in percent. Storage QoS limits throughput and operations per second. Guaranteed memory sets a floor below which the host will not take memory from a machine. Together this turns a shared cluster into a predictable environment where one neighbor does not disturb another.
