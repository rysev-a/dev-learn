Virtualization. Chapter 23. Automation: the REST API, the SDK, Ansible, and templates. When a fleet has dozens of hosts and hundreds of machines, clicking through the portal stops working: it is slow, dull, and a little different every time. The good news is that the oVirt portal itself works through the engine's REST API. Everything the interface can do, a script can do. So automation is built in layers: Ansible and Terraform on top, the Python SDK below them, and plain HTTP requests at the very base.\n\nThe REST model is simple. The root is slash ovirt-engine slash api. Under it are collections: VMs, hosts, disks, templates. A collection holds resources with an identifier, and inside a resource are links to related objects, such as network interfaces. Reading is GET, creating is POST on the collection, changing is PUT on the resource, deleting is DELETE. Actions such as start and stop are a POST to the resource slash the action name. The body format is JSON or XML, chosen by the Accept header, and the Version header with the value 4 pins the API version.\n\nNow the query parameters. The search parameter takes conditions such as name equals web-star and status equals up; you can join them with and and or, and a sortby clause and a page number may follow. The max parameter limits the number of objects, and pages are walked with a page clause inside search. The API is stateless, so if things change between requests, pages can shift. The follow parameter expands links in place and saves dozens of requests. The async parameter chooses whether to wait for the end of an action, and a correlation ID helps you find your call in the engine's log.\n\nAuthentication. The simplest path is basic authentication: a login and password in every request. It is handy for a quick check, but the password travels with every call. It is better to take a token: send a POST to ovirt-engine slash sso slash oauth slash token, giving the grant type password and the scope ovirt-app-api. The reply brings the token and its lifetime. From then on the token travels in the Authorization header with the word Bearer. When it expires, the engine answers 401, and there is no token refresh, so just ask for a new one. Store a token like a password.\n\nThe Python SDK is called ovirt-engine-sdk-python. You create a Connection object with the address, the credentials, and the CA certificate, take the system service, then a collection service such as the VMs one, and call list, add, or the service of one particular machine. The types live in the types module. Many operations are asynchronous, so after a start you wait for the status you need: a loop with a pause that doubles up to a ceiling, and an overall deadline. Errors arrive as an exception of the base class Error. Reads are safe to repeat, but creation only after making sure the object is not there yet. At the end, close the connection.\n\nThe Ansible collection ovirt.ovirt wraps the same API in modules. The ovirt_auth module obtains a token, while ovirt_vm, ovirt_disk, ovirt_host, and others describe the desired state. The modules are idempotent: running again changes nothing if everything is already as described. State present creates the machine and leaves power alone, running also starts it, stopped stops it, absent deletes it. The wait parameter is on by default and waits for the result, and the default timeout is 180 seconds. Besides modules, the collection has roles: hosted engine setup, infrastructure, vm_infra, template images, and disaster recovery.\n\nA template is a frozen sample of a machine: disks, memory, network, and settings. A machine is made from a template as a thin clone, whose disk refers to the template's, or as a full copy. Before turning a Linux machine into a template you seal it: wipe the host keys, the machine ID, and the logs, and for Windows sysprep does this job. An instance type sets only the sizes: CPU and memory. A pool is a group of machines from one template. In an automatic pool, changes are rolled back after shutdown, and a few prestarted machines are already waiting for users. Names are built from a mask with question marks, which numbers replace.\n\nSo that a clone is not a twin of its template, it is configured on first start. On Linux this is cloud-init, on Windows it is sysprep. The engine builds a disk with data: the host name, a user, SSH keys, the network, and an arbitrary script, the so-called user data, in YAML format. Cloud-init remembers the instance, and most of its modules run only on the first boot. In Ansible all this is set with the cloud_init block, and the cloud_init_persist parameter saves the settings in the machine itself, so that it need not be started in run-once mode. Do not put secrets in user data: they stay on the guest's disk.\n\nTerraform can also work with oVirt: there is a community provider that describes machines and disks declaratively and keeps the mapping in a state file. It complements Ansible rather than replacing it, but check the provider's age and quality yourself. Now events. Every action lands in the audit log, which is available at the events path, and the from parameter lets you fetch only the new ones. The engine's notifier service can send mail over SMTP and SNMP traps. The notifier is documented only for mail and SNMP; if you need a webhook, write an external script that polls the events and calls your URL.\n\nFinally, security and reliability. Create a separate user for automation instead of the shared admin, and give it the smallest role at the lowest level of the hierarchy: permissions are inherited downward, from the data center to the cluster and the machine. Tokens are short-lived, and passwords sit in a secret store, not in a repository. The API has no separate rate limiter, but the engine can be overloaded, so limit the concurrency yourself. Retry only what is safe: reads and desired-state operations, with a growing pause and random jitter, and always set a correlation ID so that you can find the trace in the log.
