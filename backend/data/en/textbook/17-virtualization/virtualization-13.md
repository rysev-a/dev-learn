#CHAPTER 13 | MicroVMs and the Cloud: Firecracker, Xen, ESXi and libvirt
Virtualization. Chapter 13. MicroVMs and the cloud: Firecracker, Xen, ESXi and libvirt. The public cloud makes contradictory demands. It needs strong isolation, like virtual machines, fast startup, like containers, and high density, so that it doesn't bankrupt the provider. In this chapter we will see how the big hypervisors, KVM-based clouds and a brand-new class of micro virtual machines cope with that.\n\nLet's start with the classics. Xen is a type one hypervisor with a tiny kernel. Management and drivers are handed over to a privileged machine called Dom0, and all the other guests are called DomU. This split shrinks the trusted part. Guests can run in paravirtual mode, in full virtualization mode, or in a mixed mode. Xen was the foundation of the first big clouds, Amazon's among them, until they moved to their own KVM-based solutions. It is still found in server systems and in embedded solutions.\n\nThe commercial classic is VMware ESXi, a closed type one hypervisor with its own kernel. Its ecosystem provides everything an enterprise needs: centralized management, live migration called vMotion, automatic load balancing, and distributed storage. Microsoft has Hyper-V: a root partition running Windows manages the rest, and the same technology underlies the Azure cloud. All three products are mature and rich in features, but for cloud scale they have to be considerably extended.\n\nModern big clouds are more often built on KVM. In the Nitro system, Amazon kept the hypervisor minimal and moved the network, disks and security onto special cards with their own processors. All that is left for the host is to run guests. Google uses KVM with its own virtual machine monitor. Open private clouds, such as OpenStack, are built from libvirt, QEMU and KVM. The common idea is to move everything you can out of the trusted base and make it thin.\n\nThe next step is micro virtual machines. These are ordinary KVM virtual machines with everything unnecessary cut out: no firmware and no PCI bus, no video adapter and no USB. Only a handful of devices remain: a virtio network device and block device, a socket for talking to the host, a serial port and a reset button. The best-known monitor of this class is Firecracker from Amazon, written in Rust. There are others: Cloud Hypervisor from Intel and crosvm from Google. The goals are a startup of about a hundred milliseconds and memory overhead of a few megabytes.\n\nWhere does the speed come from? A micro machine loads the Linux kernel directly, bypassing firmware and bootloader, and the kernel is built minimal. The system boots in a fraction of a second. Restoring from a snapshot speeds things up even more: the snapshot memory is mapped into the machine lazily, and pages are pulled in on access, as in post-copy. This is how a service runs someone else's function in milliseconds. Serverless services like AWS Lambda are built on this: every function gets its own micro machine.\n\nSecurity of micro machines is well thought out. The small code of a monitor written in Rust reduces a whole class of memory errors, and the set of devices is minimal. Each machine is served by a separate monitor process, launched through a special wrapper called the jailer: it confines the process with control groups and namespaces, locks it into an isolated directory, drops privileges, and turns on a strict system call filter. An escape has to get through several layers of protection in a row: the device, the monitor, the wrapper and the kernel.\n\nHow do we assemble all this into a system? Orchestrators like Kubernetes decide which server each pod runs on. Through the container runtime interface they can run containers in Kata, and on serverless platforms in micro machines. The scheduler takes into account cores, memory, device proximity and placement rules, for example not putting two copies of a service on the same server. For serverless functions the cold start matters: if a function hasn't been called for a long time, its machine has to be created again, and that adds latency.\n\nWhat remains is the cloud's network and storage. Virtual networks are built on software switches such as Open vSwitch and on tunnels that encapsulate guest frames in packets of the physical network: VXLAN or Geneve. Encapsulation eats part of the packet size, so guests are given a smaller maximum transmission unit. Machine disks live in distributed copy-on-write storage, and management layers such as OpenStack and oVirt tie everything together through libvirt.\n\nLet's sum up. Xen, ESXi and Hyper-V are mature general-purpose hypervisors. KVM clouds give openness and scale. Micro machines give fast startup and low overhead with a hard isolation boundary. The choice depends on the task: startup time, density, openness of the code, maturity of management. The last chapter is about what to do when someone does try to break through that boundary: guest escapes, side channels, and protecting memory from the hypervisor itself.
