#CHAPTER 9 | Disks and images: qcow2, snapshots, and copy-on-write
Virtualization. Chapter 9. Disks and images: qcow2, snapshots, and copy-on-write. To the guest, a disk is a device made of blocks. To the hypervisor, it is a file, a logical volume, or an object in network storage. The choice of format decides speed, space, and how cheaply you can make copies and snapshots. In this chapter we'll look at the two main formats, layered images, and snapshots, and at the end we'll see what kind of storage sits underneath all of this in the cloud.\n\nThe simplest format is called raw. It is just the bytes of the disk, one after another: an offset in the guest disk is the same as an offset in the file. There is no metadata and no overhead, and the speed is the same as that of a file or a partition. File systems can store such images as sparse files, which means space is allocated only as data is written. The price of simplicity is that there are no snapshots, and compression and encryption of the image have to be done outside. For maximum speed, raw images are put directly on a logical volume.\n\nThe qcow2 format was invented for QEMU, and it can do almost everything: allocation on demand, snapshots, compression, and encryption. The disk is divided into clusters, sixty-four kibibytes by default. To find a cluster by a guest address, you need two tables: the first points to second-level tables, and the second holds the offsets of clusters in the file. Separate reference counters say how many times each cluster is used. As long as the guest hasn't written anything, the corresponding clusters simply don't exist in the file.\n\nThe main idea of qcow2 is copy-on-write and the backing image. An image can refer to another image, which stays read-only. The new layer stores only the changed clusters. On a read, the cluster is looked up in the top layer first, and if it isn't there, we go down. On a write, the cluster is copied into the top layer, and for a partial write the missing part is read from below first. From a single base image with an operating system you can start hundreds of machines, and each will take up exactly as much space as it has changed.\n\nSnapshots come out naturally. An external snapshot is a new empty layer on top of the current one, and the previous layer becomes the base and is frozen. The operation is instant: nothing is copied. A rollback is simply discarding the top layer. But the chain has a cost: a read from a deep layer passes through all the layers above it, and the longer the chain, the more table lookups. That's why layers are merged from time to time, moving the clusters of the top layer down, or the whole chain is flattened into a single image.\n\nA disk snapshot is not the same as a machine snapshot. At the moment of the snapshot, the guest's disk may be in an intermediate state: some of the data still sits in the guest file system's cache. Such a snapshot is called crash-consistent: after restoring, the system behaves as it would after a sudden power loss. To get a consistent snapshot, the guest agent, on the hypervisor's command, flushes the caches and freezes writes, then the snapshot is taken, and then writes are thawed. A live snapshot additionally saves the memory and the state of the devices.\n\nThe speed of a format depends on its metadata. Cluster tables are cached in memory, and a cache that is too small turns random reads into double reads. You can preallocate the metadata, or the whole file, to remove the cost of growth. The caching mode matters too: most often people choose the mode with no host cache, so that pages aren't stored twice and writes go straight through. There are also modes with a cache and forced syncing, but they are either slower or riskier in a crash. And the discard command returns space to the storage.\n\nThe extra features of qcow2 are not always needed. Cluster compression saves space for images that are read more often than written. Encryption at the image level protects the file on disk, but many clouds encrypt at the storage level, where it is simpler and faster. Note that compressed clusters lose their compression when overwritten. Also, qcow2 is slower than raw on random writes because of the extra metadata work, and for heavily loaded databases people often choose raw.\n\nStorage lies beneath the images. Local files and logical volumes are simple and fast. Copy-on-write file systems can make instant clones of files. In the cloud, images live in network storage: over the NFS and iSCSI protocols, or more often in distributed systems like Ceph, where a machine's disk is a set of objects, and snapshots and clones are done at the storage level. A shared disk is especially important, because with it live migration doesn't copy the disk data, it just hands over control.\n\nLet's sum up. For speed, take raw on a logical volume; for flexibility, qcow2 with layers; and in the cloud, disks live in network storage with instant clones. Watch the length of the layer chain, and don't forget discard and freezing the file system before a snapshot. In the next chapter we'll use all of this to move a running machine to another server without stopping it for long, and we'll find out why dirty pages become the main character of migration.
