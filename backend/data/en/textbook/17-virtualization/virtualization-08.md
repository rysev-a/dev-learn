#CHAPTER 8 | KVM and QEMU: How the Linux Kernel Becomes a Hypervisor
Virtualization. Chapter 8. KVM and QEMU: how the Linux kernel becomes a hypervisor. We have taken the processor, memory and I/O apart piece by piece. Now it is time to assemble them into a working system. On Linux this is done by two components that almost always come as a pair. KVM is a kernel module that appeared in two thousand seven and turns an ordinary kernel into a hypervisor. QEMU is an ordinary program that creates a virtual machine and invents devices for it. Many clouds are built on this pair.\n\nLet's start with the interface. The KVM module creates a device called dev kvm in the system, and support for a specific processor is added by modules for Intel and AMD. QEMU opens this device and, through ioctl calls, asks the kernel to create a virtual machine, then virtual processors, and then tells it which region of its own memory to give to the guest. The guest's memory is ordinary anonymous memory of the QEMU process, and the Linux kernel manages it the same way as the memory of any other program.\n\nEach virtual processor is an ordinary thread of the QEMU process. This is the key idea of KVM: the hypervisor does not need its own scheduler, because Linux itself schedules virtual processors alongside all other threads. That is why all the familiar tools work on the host: top, control groups, core pinning, priorities. For each thread the kernel keeps a shared page describing the last exit, which we already saw when we talked about the KVM run loop.\n\nLet's look at this thread's work once more. It calls KVM run, and the kernel enters the guest and executes it until an exit happens. The kernel handles most exits on the spot: interrupts, processor halts, nested page table faults, reads of special registers. This is the fast path, with not a single switch to a user process. Only when device emulation is needed does the call return to QEMU with a reason, for example an access to a port or to device memory. QEMU sorts it out and calls KVM run again.\n\nTo keep the most frequent events from reaching QEMU, the kernel itself emulates some of the devices. It hosts the local interrupt controller, the I/O interrupt controller and the timers, which means an interrupt can be delivered to the guest without an exit to a user process. The same goal is served by ioeventfd and irqfd, which we discussed in the chapter on I/O. The general principle is this: whatever happens often and is simple is moved closer to the kernel, while what is rare and complex stays in the program.\n\nQEMU is responsible for everything else. It describes the machine model: a set of chips, for example the old and the new chipset variants, the firmware, whether classic BIOS or modern UEFI, disk and network devices, a video adapter, USB controllers. It also accepts management commands through the QMP channel: add a disk on the fly, pause the machine, start a migration. And it has a mode without KVM, in which every guest instruction is translated in software: slow, but it works for any architecture.\n\nThe price of such flexibility is the size of the code. QEMU contains millions of lines of C and hundreds of emulated devices, and it is the main attack surface of the hypervisor, because any bug in a device can become an escape from the guest. That is why it is run as an unprivileged user, its set of system calls is restricted with seccomp, and it is isolated with SELinux or AppArmor rules and control groups. Another path is to do without QEMU altogether, and in the chapter on the cloud we will see projects that do exactly that.\n\nNobody writes a QEMU command line by hand, so there is a management layer: libvirt. It describes machines as documents in XML format, stores networks and storage pools, launches QEMU with the right parameters and watches it through a management channel. It has a daemon, a console command called virsh, and a graphical manager. Libvirt can also work with other hypervisors, and cloud platforms such as OpenStack manage their servers precisely through it.\n\nWhich settings are worth knowing? The processor model for the guest: either "same as the host" for maximum speed, or a generic one for safe migration between different servers. The number of virtual processors and the amount of memory. The chipset and firmware type. Using huge pages for the guest's memory. Paravirtual devices instead of emulated ones, and vhost for the network. Asynchronous I/O for disks without the host's cache. We will go through all these parameters in more detail on the slides and in the practice tasks, and for details, consult the documentation.\n\nLet's sum up. KVM gives speed, because the guest runs on a real processor, and gets scheduling and memory from the Linux kernel. QEMU gives devices, and the price of their variety is a large attack surface. Libvirt gives management at industrial scale. Together they have become the standard of open virtualization. The next question is a practical one: where to keep the machines' disks and how to take snapshots of them. We will talk about that in the next chapter.
