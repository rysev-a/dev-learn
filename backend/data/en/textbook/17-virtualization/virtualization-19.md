#CHAPTER 19 | Hosts: VDSM, lifecycle and fencing
Virtualization. Chapter 19. Hosts: VDSM, lifecycle and fencing. Let us begin with how a host gets into oVirt. The administrator supplies an address and credentials, and the engine logs in to the server over SSH. Then the deployment runs, and it is done by Ansible playbooks. They install the VDSM, libvirt and QEMU packages, set up the management network, and the engine issues the host certificates from its own certificate authority. The progress of the installation is visible in the engine's logs, and if something breaks, the host gets the InstallFailed status.\n\nWhat runs on the host after installation: two daemons. The first, vdsmd, lives under an ordinary user and accepts the engine's commands. The second, supervdsmd, runs as root and does only what needs privileges: network setup, mounting, working with devices. The engine talks to the first daemon over JSON-RPC on top of TLS, on port 54321. The same calls can be made by hand with the vdsm-client utility, and a detailed log lives in /var/log/vdsm, in the file vdsm.log.\n\nHow does the engine learn what is happening on a host? VDSM regularly gathers reports: processor and memory load, the state of network interfaces, the statistics of every running machine. Separately it watches storage: for each storage domain a monitor runs that reads the metadata and checks the lease through sanlock. The engine polls the host and updates the database from this data, and for important events VDSM notifies it on its own. To look deeper, call vdsm-client on the host: ask for the host capabilities, its statistics, or the state of a single machine. This is the first thing to do when troubleshooting.\n\nIn the portal a host always has a status, and each one means something. Installing lasts while the deployment runs; if it fails, the status is InstallFailed. Up means all is well. Connecting says the engine has lost contact and is trying to restore it. NonResponsive is set when there has been no contact for too long. NonOperational is a special case: the host is reachable but unfit for work, for example it lacks a required network, cannot see a storage domain, or its processor does not suit the cluster. And two maintenance statuses: PreparingForMaintenance while machines move away, and Maintenance itself.\n\nHow does the engine decide that a host is gone? It keeps polling the host and waiting for answers. One missed answer means nothing: the host goes to Connecting, and the engine retries. The host becomes a candidate for fencing only when two conditions hold at once: there have been at least two failures in a row, and at least sixty seconds have passed since the first. Sixty seconds is a base: for every machine running on the host the wait grows by half a second, and if the host is the SPM, by another twenty seconds. These are defaults, changed with the engine-config utility. In addition, every operation has its own timeout, which can reach three minutes. So in the worst case, minutes rather than seconds pass between losing contact and the decision.\n\nMaintenance mode exists so that a host can be updated, repaired, or switched off safely. When the administrator turns it on, the engine first empties the host: every running machine is moved to other hosts in the cluster by live migration, following the migration policy. While machines move away, the status is PreparingForMaintenance. Machines pinned to the host cannot migrate, and they are stopped. If a migration fails, the process stays in preparation, and maintenance can be cancelled with the Activate button. If the host was the storage manager, the SPM, that role also passes to another. When no machines are left, the host gets the Maintenance status, disconnects from the storage, and can be touched.\n\nFor the engine to really switch off a hung host, power management is needed. It is configured on the host: you choose a fence agent, a program from the fence-agents package, for example ipmilan for ordinary management controllers, and also agents for iLO, DRAC and APC power strips. You give an address, a login and a password. For a server with two power supplies you can add a second agent. The fencing command is run not by the engine itself but by another host, the proxy. By default the search order is this: first a host of the same cluster, then of the same data center; it can be changed, and hosts of other data centers can be added. The proxy must be in the Up status.\n\nNow the fencing process itself. When a host has become a candidate, the engine tries soft fencing: VDSM is restarted over SSH. If that does not help, the cluster policy comes into play. It has five settings: fencing can be switched off altogether, and it can be skipped in four cases. First, the host has a fresh lease on the storage, meaning it is alive and writing to disk. Second, contact is lost with at least a configured share of the cluster's hosts, so most likely the engine's own network is broken. Third, the Gluster bricks are up. Fourth, switching the host off would break the Gluster quorum. If fencing is allowed, power management follows: switch off, make sure the host is off, and switch on. Our simulator simplifies the order. In the real engine, it first checks that fencing is enabled and the connectivity threshold, then come soft fencing and kdump, then power, and the lease and the Gluster bricks are checked right before the switch-off.\n\nWhy such caution? Only after the host is reliably off can its machines be started elsewhere: otherwise two copies would open one disk and corrupt the data. As soon as the engine knows the host is off, it restarts the highly available machines on other hosts, by priority, and marks the rest as down. If the host holding the SPM role has failed, a new one is chosen. Without power management the administrator presses Confirm host has been rebooted, and the responsibility is theirs. Kdump is a special case: if the integration is enabled, the engine waits for messages from the host and does not switch it off while it writes a kernel dump.\n\nFinally, upgrades. Hosts are upgraded one at a time so that the cluster keeps working throughout. The order is: make sure the other hosts can carry the load; put the host into maintenance, and the machines move away; update the packages or, for oVirt Node, the image; reboot if needed; activate and wait for the Up status; only then take the next one. The portal and an Ansible role for cluster upgrades can do this. If a host must be reinstalled, it is also put into maintenance, the reinstall is started, and the certificates are renewed if needed. This keeps hosts healthy for years without stopping services.
