#CHAPTER 12 | Containers vs. Virtual Machines: Namespaces, Cgroups, gVisor, and Kata
Virtualization. Chapter twelve. Containers versus virtual machines: namespaces, cgroups, gVisor, and Kata. We've spent the whole book building virtual computers. But in the cloud, containers are what usually get run: they start in a fraction of a second and cost almost nothing. How are they different from virtual machines, and why is the security question sharper here? The answer is one word: the kernel. A virtual machine brings its own kernel and sits behind the hypervisor boundary, while a container uses the host's kernel and is fenced off only by the rules of that kernel.\n\nLet's start with the mechanisms. Namespaces make a process see its own version of the world. The process namespace gives its own numbering, where the container's main process has the number one. The mount namespace shows its own file system, the network namespace its own interfaces and routes, and the hostname namespace its own machine name. The user namespace maps user IDs, so the root user inside can be an ordinary user outside. A container is not a separate kernel object, but a set of such namespaces for a group of processes.\n\nThe second mechanism is control groups, or cgroups, which we discussed in the book on Unix. They limit and account for resources: the share of CPU, the amount of memory, disk bandwidth, the number of processes. The second version is hierarchical: a parent's limit applies to its descendants. Going over the memory limit gets the group's processes killed, and going over the CPU quota leads to pauses. Together, namespaces and cgroups produce the familiar illusion: a separate machine with its own network, its own file system, and its own limits.\n\nContainer images are built in layers. Each layer is a set of changed files, and an overlay file system stacks them up and shows them as a single tree. This is the copy-on-write you know from disk images: writing to a file in a lower layer copies it up to the top layer, and deleting a file leaves a marker that hides it. Starting a container doesn't involve booting a kernel or firmware, so it takes milliseconds, and the memory overhead is negligible. That's where the density comes from: thousands of containers fit on one server.\n\nNow the main difference in security. The boundary of a virtual machine runs along a very narrow interface: VM exits, hypercalls, and emulated devices. The boundary of a container runs along system calls, and the Linux kernel has hundreds of them, each a potential bug. A vulnerability in any system call or kernel driver may let a container process break out and gain access to the entire host, because the kernel is shared by everyone. So for untrusted code, for example other people's programs in a public cloud, containers alone are usually not enough protection.\n\nLet's compare the other parameters. A virtual machine can run any operating system, while containers can only run programs for the host's kernel, that is, Linux. A machine starts in seconds, a container in milliseconds. A machine carries a separate kernel and spends memory on it, while a container spends almost nothing. Live migration and snapshots are something machines do well, and for containers it's harder. Virtual machines can be restricted at the hardware level, containers only by kernel rules. Every advantage of one technology is a disadvantage of the other.\n\nContainers can be hardened. The seccomp system call filter forbids all calls except those the program needs, and so shrinks the attack surface. The set of capabilities splits the omnipotence of the root user into small pieces, and the container is left with only the necessary ones. The user namespace makes it possible to run containers without superuser rights on the host, which is called rootless. Security modules such as SELinux and AppArmor forbid unnecessary access to files. But all of these measures work inside the same kernel, and a bug in it remains shared.\n\nThe first way to tighten the boundary is gVisor, a project from Google. It replaces the host kernel, for the application, with its own kernel, written in Go and running in user space. The application makes system calls, this kernel, which is called the Sentry, intercepts them and carries them out itself, and it talks to the real kernel only through a narrow set of calls. This shrinks the attack surface several times over. The price is performance for call-heavy workloads and incomplete compatibility: not all rare system calls are supported.\n\nThe second way is Kata Containers. Each container, or set of containers, is started inside a lightweight virtual machine with a minimal kernel. From the outside it all looks like an ordinary container and is managed with the same tools, while on the inside the boundary is real and hardware-based. To launch, Kata uses lightweight hypervisors, for example Cloud Hypervisor or Firecracker. The price is clear: a separate guest kernel, extra memory, and a start in hundreds of milliseconds instead of tens. In return, untrusted code gets no access to the host kernel.\n\nLet's sum up. Choose by threat model. If the code is your own and trusted, containers give you speed and density. If other people's tenants live on the same server, you need a stronger boundary: a virtual machine, Kata, or at least gVisor. Often these are combined: containers inside virtual machines, one machine per tenant. The easiest way to think about it is the price of the boundary: the harder it is, the more we pay in memory and start time. In the next chapter, we'll look at how the cloud gets a hard boundary at a minimal price.
