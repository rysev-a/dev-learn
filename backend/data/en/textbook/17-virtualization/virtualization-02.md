#CHAPTER 2 | Trap-and-emulate and the x86 problem: binary translation and paravirtualization
Virtualization. Chapter 2. Trap-and-emulate and the x86 problem: binary translation and paravirtualization. In the last chapter we found out that a monitor is simple to build if every sensitive instruction is privileged. Now we'll see how this simple scheme works, then learn why the most widespread processor broke it, and what tricks engineers used to get around the obstacle before hardware support appeared. This is a story about how even an unfortunate architecture can be virtualized, if you don't spare the ingenuity.\n\nThe idea of the scheme is simple: intercept and imitate. The guest operating system is started in an unprivileged mode, even though it is used to running in the most privileged one. While the guest adds numbers and touches its own memory, the processor executes everything itself, with no delay. But as soon as the guest kernel executes a privileged instruction, say, disabling interrupts or loading a new page table, the processor can't carry it out and raises a trap. Control passes to the monitor, which runs in the real privileged mode. The monitor looks at what the guest wanted and carefully imitates the required action.\n\nWhat does this look like on x86? The processor has four protection rings. The operating system kernel lives in ring zero, programs live in ring three, and rings one and two are hardly used by anyone. To run a guest, the monitor takes ring zero, pushes the guest kernel down into ring one, and leaves the guest programs in ring three. This is called ring compression. The guest kernel can now no longer execute a privileged instruction, and every such attempt becomes a trap into the monitor. The hardware catches the offender by itself, and the monitor doesn't have to check each instruction.\n\nWhat exactly does the monitor imitate? For every virtual machine it keeps a virtual processor: a copy of the registers that the guest considers its own. For example, the guest has an interrupt-enable flag. When the guest kernel executes the disable-interrupts instruction, the real flag stays as it was, otherwise the monitor would stop getting control from the timer. The monitor just clears the virtual flag in its records and from then on doesn't deliver interrupts to the guest until the guest enables them again. The guest notices nothing: it sees its own state, which the monitor faithfully maintains.\n\nNow the problem. In the year two thousand, Robin and Irvine analyzed the Pentium instruction set and found seventeen instructions that are sensitive but not privileged. They don't cause a trap in user mode, but behave differently there. The best-known example is the instruction that restores the flags: in the kernel it can change the interrupt flag, but outside ring zero it silently ignores the change and reports no error. Even worse is the instruction that saves the flags: it shows the guest the real state, not the virtual one. The intercept-and-imitate scheme simply doesn't see these instructions.\n\nThe first answer came from VMware in the late nineteen-nineties: binary translation. Before running the guest kernel, the monitor scans its code, block by block, and replaces the dangerous instructions with safe sequences that call into the monitor or work with the virtual state. The result goes into a translation cache, and the next time the block runs it's already prepared. Guest programs in ring three don't need translating: there are no dangerous instructions there. The guest stays unmodified and doesn't even know its code was swapped; the price is a complex monitor and the time spent on the first pass.\n\nThe second answer is paravirtualization, demonstrated in two thousand three by the Xen project. If you can't make the guest ignore virtualization, let it know about it. The guest kernel is rewritten: instead of dangerous instructions it calls the hypervisor with explicit calls known as hypercalls. A hypercall is like a system call, only not from a program into the kernel but from the guest kernel into the hypervisor. This is how the kernel asks, by hand, to switch a page table or set a timer. It's fast and exact, but the operating system has to be modified, and a closed-source system can't be run this way.\n\nLet's compare the three approaches. Trap and emulate is the simplest, but it didn't work on x86. Binary translation runs the guest without a single change, but spends time on scanning and needs a complex translator. Paravirtualization is the fastest, because the guest itself calls the hypervisor in batches and makes no needless traps, but it needs a modified kernel. In practice they were combined: VMware translated the kernel, while Xen paravirtualized Linux. And in two thousand five and six, processors gained hardware support, which we'll talk about in the next chapter, and the dispute quickly became history.\n\nParavirtualization didn't die; it turned into a technique that works alongside hardware support too. A modern Linux kernel can detect that it's running in a guest and replace some operations with hypercalls. The guest can read the time from a shared page instead of an emulated timer, and acknowledge interrupts without exiting to the hypervisor. Paravirtual network and disk devices work the same way: they don't pretend to be hardware but honestly negotiate with the hypervisor through shared queues. Chapter six is devoted to this topic. A hypercall in KVM is executed with the VMCALL instruction.\n\nThe main takeaway of the chapter: the price of a trap is the most important number in virtualization. An ordinary instruction costs a fraction of a cycle. Going into the monitor, imitating, and coming back costs on the order of a thousand cycles or more, because the processor has to save and restore state. If the guest kernel takes a trap on every operation, say, on every page switch, speed drops several times over. That's why all the tricks of this chapter, translation, batched hypercalls, virtual flags, serve one goal: to have as few traps as possible. Next we'll see how the processors themselves achieved this.
