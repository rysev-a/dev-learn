#CHAPTER 18 | The engine and its database
Virtualization. Chapter 18. The engine and its database. The engine is installed with a single command, engine-setup. It asks questions: the server name, where to keep the database, the administrator password, and whether you want the data warehouse for reports, Grafana and, from 4.5.1 on, the bundled Keycloak. The answers can be saved to an answer file, and later the installation runs without questions once you point it at that file. This gives identical engines for testing and for production. The same command upgrades the engine after the packages are updated, and engine-cleanup removes it all. Before an upgrade you always take a backup.\n\nWhat lies in the database. It is an ordinary PostgreSQL with a database named engine. The data of every object is split into three tables: the static part holds what a person configured, the dynamic part holds the current state, and the statistics part holds fast-changing counters. For a machine these are vm_static, vm_dynamic and vm_statistics, for a host vds_static and its siblings, for a storage domain storage_domain_static and storage_domain_dynamic. Separately there are the audit log, jobs and steps, permissions and the engine-config values. You may read these tables, but you should not write to them by hand.\n\nEvery action of the engine is a command, a Java class. First comes the validation phase: are there enough permissions, does the object exist, is its state acceptable. Then execution: writes to the database and calls to hosts. Long work, such as copying a disk, goes to an asynchronous task on the host, and the finishing phase of the command waits for its result. Commands can be nested, and the command coordinator keeps their state in the database, so after an engine restart the work goes on. If something goes wrong, compensation kicks in: the database changes are rolled back from saved snapshots.\n\nWhile a command runs, the engine keeps a record in the jobs table and several steps in the steps table. A job is what the user sees in the tasks tab, for example adding a disk. Steps are its parts: preparation, execution, completion. Each has a status: started, finished, failed or aborted, and the job's status is built from its steps. Do not confuse them with the asynchronous task on the host: that one lives in VDSM and in a separate table. If the portal shows running for hours, look for a stuck task on the host, and stale records are cleaned by a service script.\n\nEverything notable the engine writes to the audit log, the audit_log table. These are the portal events: a machine started, a host lost, space running out. An event has a code and a severity: normal, warning, error or alert. The notification service subscribes to events and sends emails or SNMP traps. Technical details go to files. The engine.log tells what the application did, and every line carries a correlation ID shared by the whole command. The server.log is the journal of WildFly itself: startup and deployment errors. You start diagnosis with events, then go to engine.log.\n\nSettings live on three levels. Global keys are edited with the engine-config command: it lists the keys, reads and writes values, but after a write the engine must be restarted. The values are stored in the vdc_options table, and many keys have variants for different compatibility versions. Settings of a cluster or data center, such as the scheduling policy and the CPU type, are changed in the portal or through REST and take effect at once. There are also settings of a single machine. The rule is simple: what can be configured on an object, configure there, and touch the global keys last.\n\nPermissions are simple. A permission is a triple: subject, role and object. The subject is a user or a group. A role is a set of allowed actions: cluster admin, host admin, user, VM creator, and above them all the super user. The object is any rung of the ladder: the system, a data center, a cluster, a host, a machine. The key property is inheritance downward. A role granted on a cluster applies to the hosts and machines inside it, but not to the neighboring cluster and not to the data center above. So permissions are granted as close as possible to what the person manages, and to groups rather than to people.\n\nThe single sign-on service decides who you are. The built-in internal domain knows the administrator and those created by hand. For people you connect a directory. From version 4.5.1 on, Keycloak is recommended, bundled or external, and the older providers, for example through LDAP, are deprecated. The directory only confirms identity, while permissions are still granted in the engine. Programs obtain a token: they send a login and password to the SSO address, slash oauth, slash token, and then put it into the authorization header as a Bearer. A token has a limited lifetime.\n\nThe engine trusts the hosts and the hosts trust the engine thanks to a certificate authority of their own. Its certificate is created by engine-setup. It signs the web server certificate, the certificate of the engine itself and the host certificates, which are issued when a host is added. Browsers do not know this authority, so its certificate is handed to users, or an external certificate is installed on the web server. Certificates have finite lifetimes, and the engine warns about them in advance through events. A host is re-issued like this: put it into maintenance, run certificate enrollment again, activate it again. The engine certificate is renewed by engine-setup.\n\nBackups are made by engine-backup. It has backup, restore and verify modes and scopes: all, files, db and the reports database. The archive holds the database dump, the settings and the certificate authority files, but not the machine disks or the contents of the storage. A restore is done on a clean machine, and then the hosts are checked. Alongside runs the data warehouse service, DWH: it regularly copies metrics from the engine database into the ovirt_engine_history database and rolls them up into hourly and daily values. On top of that database stands Grafana with ready-made dashboards.
