#CHAPTER 10 | Live migration: pre-copy, post-copy, and dirty pages
Virtualization. Chapter 10. Live migration: pre-copy, post-copy, and dirty pages. Imagine you need to update the kernel on a server that runs hundreds of machines, and you can't disturb anyone. The solution is live migration: a running virtual machine moves to another server, and the service downtime is measured in tens of milliseconds. Migration is needed for maintenance, for balancing the load, and for saving power. It requires shared storage or disk migration, compatible processors, and a fast network between the servers.\n\nFirst, let's work out what gets transferred. The bulk of it is the guest's memory. Besides that, you need to send the state of the virtual processors, the registers and device queues, and, if the disks aren't shared, the contents of the disks. The guest's network connections aren't broken: the addresses stay the same, and after the move an announcement is sent out from the destination so that the switches update their tables. To the guest itself, migration looks like a short hiccup: the clock jumped a little, and packets were delayed slightly.\n\nThe most common algorithm is called pre-copy, that is, copying before the switchover. It works in rounds. In the first round, all the memory is copied to the destination, while the guest keeps running and spoils pages that were already sent. In the second round, only the changed pages are copied, which are called dirty pages. The rounds repeat until the remainder gets so small that it can be sent within the allowed downtime. Then the machine is stopped, the remainder and the processor state are sent, and the machine is started on the destination.\n\nHow does the kernel know which pages have become dirty? The hypervisor marks all pages in the nested page tables as read-only. The very first write to a page causes a fault, the page is marked in a bitmap, and the write is allowed. This is expensive, so Intel processors got a page-modification log: the hardware itself writes the addresses of dirty pages into a buffer of five hundred twelve entries, and an exit happens only when it fills up. QEMU picks up the dirty bitmap through the kernel.\n\nDoes the process converge? It is decided by the ratio of two rates: the rate at which the guest writes to memory, and the network bandwidth. If the guest dirties pages faster than they can be sent, the remainder doesn't shrink, and the rounds go on forever. If it's slower, the remainder shrinks with every round. The downtime is the remainder divided by the bandwidth, plus the transfer of the state. For example, with sixteen gigabytes of memory and ten gigabits per second, which is about one and a quarter gigabytes per second, the first round takes about thirteen seconds.\n\nIf migration doesn't converge, there are several tricks. Auto-converge artificially slows down the guest's virtual processors so that it dirties memory less often. Zero pages are sent as short flags, and pages that change again are sent as a delta through a cache. Parallel transfer threads use the full width of the link. You can allow a longer downtime. Or you can switch to an entirely different algorithm, one that doesn't depend on the guest's write rate.\n\nThis algorithm is called post-copy, that is, copying after the switchover. First, the processor and device state is moved to the destination, and the guest starts there with almost no memory. When it touches a page that isn't on the destination yet, a fault occurs. A special kernel mechanism, userfaultfd, catches it and asks the source for the page. The remaining pages are pushed over in the background. Every page is sent exactly once, so migration always finishes in a predictable time, and the guest's write rate doesn't get in the way.\n\nThe price of post-copy is reliability. While memory is scattered between two servers, the up-to-date state of the machine is stored partly there and partly here. If the network breaks or either server fails, the machine can't be recovered, whereas with pre-copy the original copy stays intact until the very end. On top of that, the guest waits at every missing page, and the delays are noticeable. That's why a hybrid is often used: a few rounds of pre-copy, then the switchover and post-copy for the tail.\n\nWhich machines can't be migrated, or are hard to migrate? Passed-through devices and virtual functions: their state lives in hardware, and general migration for them is still limited. Machines with very large memory and a high write rate. Machines on servers with different processors, if the guest already uses instructions that the destination doesn't have. For that, you set a common processor model. It's best to send migration over a separate encrypted network, limiting the bandwidth so as not to choke the production traffic.\n\nLet's sum up. Pre-copy is the default: it's safe, because the source always has a full copy. Its convergence is determined by the ratio of the guest's write rate to the network bandwidth. For stubborn workloads there are throttling, compression, and post-copy with its risk. Watch three numbers: the downtime, the total time, and the rate at which dirty pages appear. In the next chapter we'll turn to the question of how to distribute processors among machines, so that migration is needed less often.
