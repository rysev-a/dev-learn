#CHAPTER 11 | Resource Scheduling: vCPUs, NUMA, Pinning, and Steal Time
Virtualization. Chapter eleven. Resource scheduling: virtual CPUs, NUMA, pinning, and steal time. We've shared out memory, laid out the disks, and mastered migration. What's left is the processor: the most requested resource, and the least obvious one. If there are more tenants than rooms, somebody inevitably waits. The question is how to organize the waiting so that quiet machines get enough, noisy ones don't bother their neighbors, and latency-sensitive ones get exactly what they were promised.\n\nRecall that a virtual CPU in KVM is just a thread of the host. That means the number of virtual CPUs can exceed the number of physical cores, and this kind of CPU overcommit is perfectly ordinary: for general workloads you see ratios of two, even four to one, while for latency-sensitive ones people try to keep it at one to one. While one guest thread waits for a core, the guest has no idea: from its point of view, time simply stopped, and then jumped forward.\n\nSo that the guest can measure this loss, someone came up with stolen time, or steal time. Through a shared page, the host tells the guest how long the virtual CPU was ready to run but didn't get a physical core. In the top utility, this is the column called st. A small value, a couple of percent, is considered normal, while a consistently high one, say more than five to ten percent, means the host is overloaded or a neighbor is too noisy. It is one of the main health indicators of a virtual environment.\n\nControl groups help distribute processors. A weight lets you split a core proportionally, but it only applies under contention: if the neighbors are quiet, the machine gets more. A quota limits consumption always: only a set share of time in each period, and going over it leads to forced pauses called throttling. You can also restrict the set of cores explicitly. Libvirt lets you configure all of these mechanisms separately for virtual CPUs, emulator threads, and disk I/O threads.\n\nThe strictest approach is pinning: every virtual CPU is bound to its own physical core. The result is predictable: data stays in the cache, neighbors don't push it out, and latency is stable. Cores are usually isolated from the host's own tasks, so that only guests run on them. Don't forget about hyper-threading: the two logical processors of one core share resources and caches, so they aren't handed to different untrusted machines. Pinning is costly: you lose flexibility, and an unused core can't be lent to a neighbor.\n\nModern servers are almost always multi-socket, and each socket has its own memory. This is called NUMA, non-uniform memory access. Accessing the memory of your own node is faster, while remote memory goes through the inter-socket link and usually costs noticeably more latency. For virtualization the conclusion is simple: a machine's virtual CPUs and its memory should sit on the same node, otherwise some accesses will be remote, and that quietly slows down everything running inside.\n\nIf a machine is bigger than one node, it has to be stretched across several. Then the guest is shown a virtual NUMA topology: the guest kernel and applications such as databases learn about the nodes and place data closer to their threads on their own. The host kernel can balance NUMA automatically, moving pages to whoever uses them, but that is constant background work, so for critical machines the nodes are pinned explicitly. And make sure the number of virtual CPUs doesn't exceed the number of cores in a node without need.\n\nEverything must line up in one place. Huge pages are allocated from a specific node, the network card and the graphics card also belong to a node, and it pays to place the machine next to its devices. The QEMU and vhost threads that serve the machine also consume host CPU, and you need to keep them in mind when planning. For disks, dedicated I/O threads are allocated so that heavy operations don't take time away from the virtual CPUs. The balance breaks if you miss even one link of the chain.\n\nThere are also fine-grained latency settings. When a virtual CPU halts, the host can wait a little without going to sleep, so it can react faster if an interrupt arrives almost immediately. This is halt polling: it speeds up wake-up but burns CPU. The host's power-saving mode and dynamic frequency matter too: for services with strict latency, people choose the maximum performance mode and disable deep sleep states. Any such optimization trades latency against energy and density.\n\nLet's sum up. For ordinary workloads, overcommit and cgroup weights are enough, with careful watching of steal time. For critical ones, you need pinning, NUMA, and huge pages together. The metrics are clear: steal time, run queue length, and the number of remote memory accesses.
