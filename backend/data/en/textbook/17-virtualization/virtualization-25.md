#CHAPTER 25 | Operations: upgrades, troubleshooting, and the future of oVirt
Virtualization. Chapter 25. Operations: upgrades, troubleshooting, and the future of oVirt. Let us start with upgrades, because here the order decides everything. First comes a backup of the engine with engine-backup, then the upgrade of the engine itself with engine-setup. Then the hosts, strictly one at a time: a host goes into maintenance mode, its virtual machines move to neighbors, the packages are updated, and the host returns to service. Only when every host is updated do you raise the compatibility version: first the cluster, then the data center. We verify each step in the portal before going further.\n\nWhy this order. The engine must be newer than the hosts or equal to them: an old engine will not understand new hosts, while a new engine can still work with old ones. Versions are not jumped but climbed step by step, as the documentation requires: the database schema migrates one step at a time. The compatibility version is raised at the very end and only upward: while even one old host remains in a cluster, it cannot be raised. A data center is never newer than its clusters, so clusters first, then it. Running machines pick up the new version after a restart.\n\nA separate topic is the operating system under oVirt. CentOS 8 Stream reached its end of life in 2024, and version 4.5.7 no longer supports it. The way out is to move to CentOS Stream 9 or to the rebuilds of Red Hat Enterprise Linux, such as AlmaLinux and their relatives. Release 4.5.7, January 2026, added support for CentOS 10 and AlmaLinux 10. The engine is usually moved to the new system through a backup and a restore on a clean machine, while the hosts are reinstalled one by one.\n\nNow, where to look when something breaks. On the engine the main log is engine.log, in the directory var log ovirt-engine, with the application server log next to it. On the host there are vdsm.log and supervdsm.log, the latter for actions with elevated privileges. Further down the chain: each machine has its own libvirt and QEMU log, there is a separate sanlock log about disk locks, an ovirt-imageio log about image transfers, and the agent and broker logs for the hosted engine. To hand all this to colleagues there is sosreport on a host and the log collector on the engine.\n\nMethod matters more than tools. We go from a symptom to a layer: the portal and engine, VDSM, libvirt, QEMU, storage, network. First we find out who is affected: one machine, one host, or everybody. Then we take the command's correlation id from engine.log and look for the same id in the other logs, and where it is missing we match by time and by machine id. The first error in a chain matters more than the last one: the last one is usually just an echo. And we check the clocks right away, because when time drifts apart the timestamps in the logs begin to lie.\n\nTypical failures. A host is NonResponsive: the heartbeat is gone, so we look at the network, VDSM, and fencing. A host is NonOperational: it lacks a logical network or cannot reach storage. A storage domain is Inactive or Unknown: we check whether the hosts can see it. A machine is stuck in Image Locked or WaitForLaunch: we look for a hung task and an image lock. A migration or a live merge of a snapshot failed: we read the error in VDSM and QEMU. And if the engine vanished on a hosted engine, we look at the high availability score: zero means the host is unfit to run the engine. And we always check clocks and certificates.\n\nIt is better to fail predictably, so we watch capacity. The data warehouse, DWH, copies history into a separate database, and Grafana draws dashboards from it: processor, memory, disks, storage latency. We set thresholds and alerts, but we also watch the trend: if memory use grows by ten gigabytes a week, the date of exhaustion can be calculated. Headroom follows the N plus one rule: when the largest host fails, the cluster must still fit all the machines. And we keep memory overcommit within sensible bounds.\n\nSecurity rests on a few habits. Permissions follow least privilege: a role is granted on the narrowest object, superusers are a handful, and roles go to groups rather than people. All traffic runs over TLS, and certificate lifetimes are monitored. On hosts SELinux stays in enforcing mode and is not switched off for convenience, and for strict requirements FIPS mode is enabled. And above all, timely updates: an unpatched host is worse than any unfortunate setting. Auditing belongs here too: who changed what is visible in the engine's events.\n\nLet us compare oVirt with other platforms, without big promises. Proxmox VE is also KVM with a web interface, easier to install, and it has commercial support. OpenStack is a cloud with self-service and an API, but harder to operate. VMware vSphere is the commercial reference with a mature ecosystem, although its licensing terms have changed. OpenShift Virtualization, based on KubeVirt, runs machines as Kubernetes pods, and that is the path Red Hat chose. For a move there are image converters and migration tools, and some of them can take machines from oVirt.\n\nAnd what comes next. Today oVirt is a community project: Red Hat has stepped back from it, the latest release, 4.5.7, came out in January 2026, and you should not expect many new features. The risks are clear: a small team, slow fixes, no vendor support. The decision to adopt goes by a checklist: who will maintain it, is there enough time for a migration, do the hardware and storage fit. For live installations: move to a supported system and keep an exit plan. For new ones: compare honestly with the alternatives.
