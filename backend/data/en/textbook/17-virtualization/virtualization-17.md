#CHAPTER 17 | oVirt: a virtualization management platform
Virtualization. Chapter 17. oVirt: a virtualization management platform. So far we have taken the bricks one at a time: the hypervisor, memory, disks, the network. But a company does not run one KVM server, it runs hundreds of machines on dozens of hosts. It needs a layer that ties all this together: it keeps the inventory, decides where to start a machine, repairs what has failed, and gives people access by role. oVirt is exactly such a layer, and in the next chapters we will take it apart screw by screw.\n\noVirt has a fairly long history. Its roots go back to Qumranet, the company that built both KVM and a management system around it; Red Hat bought Qumranet in 2008. In 2011 the project was opened under the name oVirt, and Red Hat's commercial version was called Red Hat Virtualization. Later Red Hat concentrated on OpenShift Virtualization and stepped back from the project, but the community carried on: the 4.5 branch lives, and version 4.5.7 came out in January 2026.\n\nThe platform has three parts. The first is the manager, called the engine: a single brain that stores all the configuration and makes all the decisions. The second is the hosts, ordinary servers with KVM on which the machines actually run. The third is storage: shared disks that hold the machine images. The engine does not run virtual machines itself, it only gives orders to hosts. So if the engine is down, machines that are already running keep running, you just cannot manage them for a while.\n\nAll objects in oVirt are arranged in a hierarchy. At the top is the data center: the boundary of shared resources, to which storage and logical networks are attached. Inside a data center live clusters, groups of hosts with compatible processors between which running machines can be moved. And inside a cluster are the hosts themselves. A virtual machine always belongs to a cluster and at any moment runs on one of its hosts. Remember this ladder: data center, cluster, host, machine. Permissions, policies and settings are all attached to one of these levels.\n\nWhat is inside the engine. It is a Java application running on the WildFly application server. It keeps all configuration and state in a PostgreSQL database. Outwardly the engine looks in two ways: a web portal for people and a REST interface at the path ovirt-engine slash api for programs, and the portal itself uses the same interface. Logins are handled by a single sign-on service, and next to it live optional services: a data warehouse for reports and logs. One database and one application also means a single point of failure.\n\nNow the host. Every host runs the VDSM daemon, written in Python. It accepts the engine's commands over an encrypted channel on port 54321 and turns them into libvirt calls. Libvirt, in turn, starts and configures QEMU processes, and QEMU uses KVM. The result is a chain of four links: the engine, VDSM, libvirt, and QEMU with KVM. VDSM also watches the host's storage and network and regularly reports to the engine what is going on.\n\nLet us follow a single command: the administrator clicks Run on a machine. The engine checks the permissions, chooses a host by the scheduler's rules, and records in the database that the machine is starting. It then sends the chosen host's VDSM a command to create the machine, with the description as a structure. VDSM prepares the disks and the network, builds the configuration for libvirt, and calls it. When the QEMU process is up, VDSM reports it upward, and the machine's status in the database changes to running. If any step fails, the failure reaches the engine as a command error.\n\nWhere does the engine itself live? There are two schemes. In the first, standalone, the engine sits on a separate machine, physical or virtual, and manages the fleet from outside. It is simple and clear, but the engine has to be protected separately. In the second, hosted engine or self-hosted, the engine runs as a virtual machine on the very hosts it manages. Special services watch it and restart it on another host if the old one fails. The chicken-and-egg problem is solved neatly: the engine machine lies on shared storage, and any host can bring it up.\n\nHosts come in two kinds. An ordinary host is a standard distribution such as CentOS Stream or AlmaLinux, onto which the engine installs the packages it needs. The second kind is oVirt Node, a ready minimal image with VDSM already installed and nothing extra, updated as a whole image, like firmware. In addition, every data center and cluster has a compatibility version. It determines which features are enabled. A cluster's version can be raised only when all hosts and the engine support it, and you cannot go back.\n\nLet us sum up and draw a map. The engine stores the configuration and makes decisions, VDSM carries out orders on the host, libvirt and QEMU run the machines, and storage holds the disks. Above it all is the ladder of data center, cluster, and host. In the next chapters we will cover in turn: the engine and its database, hosts and fencing, storage, networks, the scheduler and migration, automation through REST and Ansible, and finally backups, disaster recovery, and troubleshooting.
