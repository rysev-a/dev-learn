#CHAPTER 24 | Backups and disaster recovery
Virtualization. Chapter 24. Backups and disaster recovery. An oVirt platform keeps its data in three places, and each of them needs protection. The first is the engine: the PostgreSQL database, the configuration files and the certificates. The second is the content of the virtual machines: the disks and the machine descriptions. The third is the storage domain metadata, which records which disks exist and who owns them. Lose the engine and you lose control; lose the disks and you lose customer data. So protection is built from layers, not from one magic button, and in this chapter we will assemble it step by step.\n\nLet us start with the engine. It has the engine-backup utility with three modes: backup, restore, and verify. The scope is chosen by a parameter: everything, files only, the engine database only, or the data warehouse database only. The output is one archive, and it must be moved off the engine machine at once. The archive is restored onto a clean system running the same or a newer engine version; the tool refuses an older one. If the engine lives as a hosted engine, that is, as a virtual machine on the hosts, restoring goes through a fresh deployment with the archive passed in. The virtual machine disks are not in such an archive.\n\nA snapshot is not a backup. It lies on the same storage as the disk itself: if the domain dies, the disk and all its snapshots die together. After a snapshot, writes go into a new qcow2 layer, the chain of layers grows, reads slow down, and the merge on deletion takes longer. Consistency comes from the guest agent: it freezes the file systems, and the snapshot becomes consistent at the file-system level; consistency for applications also needs freeze hooks inside the guest. Without the agent a snapshot is only crash-consistent, as if the machine's power cord had been pulled. A snapshot with memory also brings back the running state, but it takes a lot of space and time.\n\nA real copy is made with incremental backup. The idea is simple: QEMU tracks which disk blocks changed since the previous backup and stores this in bitmaps inside the disk file itself. The first backup is full, the following ones take only the changed blocks. The moment from which changes are counted is called a checkpoint. The disk must be in qcow2 format, and it is usually marked for incremental backup so that such disks can be tracked; raw disks do not fit, so a snapshot is created for them first. If a bitmap becomes invalid, for example after an unclean shutdown of the machine, the backup fails: the invalid checkpoint is removed, and the chain usually restarts from a full backup.\n\nHere is how a backup goes through the programmatic interface. The client asks the engine to create a backup of the machine; to get an incremental one, it names the checkpoint to count from. The engine returns the identifier of the new checkpoint, and the backup moves through its phases until it is ready. The host opens the disks through NBD: usually a running machine uses QEMU's built-in server, and a stopped one a separate process. The client downloads the data and must finish the backup, otherwise the temporary bitmaps and areas stay hanging. A full backup and a chain of incremental ones are restored in sequence, forward from the last full backup.\n\nThe data is carried by the oVirt imageio service. A client creates an image transfer, and the engine issues a ticket: permission for one specific disk and specific operations, with a limit on idle time. Downloads and uploads go over HTTPS. There are two paths: directly to the daemon on the host, or through a proxy on the engine. Direct is faster but the client must see the hosts; the proxy is better for network isolation but slower. HTTP ranges let you read the disk in pieces in parallel, and the extents query shows which parts of the disk actually hold data and which are empty.\n\nTools vary: commercial products with ready-made integration, or your own scripts on the SDK. Check any scheme against the three-two-one rule: three copies, on two different media, one of them off site. Set the goals. RPO is how much data you are ready to lose, that is, the longest gap between backups. RTO is how long recovery may take. A retention policy such as grandfather-father-son deletes the old, but you must not delete a backup that live increments depend on. And the main rule: a backup that has never been tried in a restore does not count as a backup.\n\nMachines can be moved in different ways. Exporting to OVA puts a machine into a single file on a chosen host, and from that file it can be imported back. The old export domain is deprecated and should not be used. The modern way is importing a data domain: you attach an existing storage domain to another data center, and the engine finds the unregistered machines and templates in it. The machine descriptions live in special service disks called OVF_STORE, which are refreshed periodically, roughly once an hour by default. At registration you can map the clusters, networks and domains of the target site.\n\nDisaster recovery is built on storage replication between sites. In the active-passive scheme the second site waits with its own engine and takes over the replicated domains on failure. In the active-active scheme one cluster is stretched across the sites: the storage is replicated synchronously and writable on both, and the sites need a shared layer-2 network with bounded latency. For the first scheme there is an Ansible role for disaster recovery. Its mapping file lists clusters, domains, networks, roles, affinity groups and direct LUN disks. Validation finds the gaps in advance, and separate commands perform the failover to the secondary site and the failback, with the primary site cleaned before the failback.\n\nThree topics remain. First: moving a disk between storages while the machine runs. The host takes a snapshot, mirrors the data into the new domain, switches over and merges the snapshot; moving a whole domain goes through maintenance mode, detach and attach. Second: importing from VMware. It is done by virt-v2v: it reads the machine, replaces drivers with virtio ones, removes the other hypervisor's tools and writes the disks into oVirt; from the command line that goes through imageio. Third: security. TLS runs between the components, and encryption of data at rest is usually handled on the storage side or inside the guest.
