#CHAPTER 21 | Networks: logical networks, bonds, VLANs and OVN
Virtualization. Chapter 21. Networks: logical networks, bonds, VLANs and OVN. In oVirt a network is first described at the data center level as a logical network: a name, a VLAN tag, an MTU. Then it is attached to a cluster, and there it is marked required or not. Only after that does the administrator bind the network to a NIC or a bond on each host. If a required network is missing on a host or is not working, the engine moves the host to the NonOperational state, and the machines leave it. An optional network does not do that.\n\nOne network is always there: it is called ovirtmgmt, the management network. The engine talks to VDSM over it, and it cannot be removed. A network in a cluster can also have roles. Management. Display: the consoles of virtual machines go over it. Migration: the memory of the machines being moved travels over it. Gluster: the traffic of the distributed storage. And the default route, which is the host's gateway. Roles can be split across different networks, and on a busy platform they usually are, so that migration does not choke management. In a cluster there is exactly one default route.\n\nNetworks are either virtual machine networks or the rest. For a machine network the host builds a Linux bridge named like the network, and the virtual cards plug into it. The rest, for example migration or storage, need no bridge: the address goes straight onto the interface. If a network has a VLAN tag, a sub-interface appears on the host: the NIC name, a dot, the number. The number runs from one to 4094, and the whole interface name in Linux is at most fifteen characters. One NIC may carry only one untagged network; all the others must be tagged.\n\nTo avoid depending on a single cable, NICs are joined into a bond. There are seven modes. Zero: round-robin transmission. One: an active NIC and a standby, and the switch needs nothing. Two, by hash, and three, broadcast: they need static aggregation on the switch ports. Four, 802.3ad, also known as LACP: the switch needs a configured group. Five and six balance by themselves, with no help from the switch. For virtual machine networks, modes zero, five and six are not recommended. Special parameters, such as miimon or the hash policy, are given as a string in the bond's custom options.\n\nThe engine sends all network changes of a host as one operation, setupNetworks. It is atomic: the whole set is applied, additions, removals, edits of bonds and networks, or nothing at all. And there is a guard against suicide. If the connectivity check is on, after applying the changes VDSM waits for the engine to reach the host again, about two minutes by default. If it cannot, the old configuration is restored. So any edit of the management network should be made with the check on, not blindly. Otherwise a typo in a VLAN number cuts the host off from the engine, and you fix it by hand at the console.\n\nThe engine remembers how a network should look, but a host can live its own life: someone edited a file by hand, or the network's MTU was changed. Then the host is marked out of sync, and the engine shows exactly what differs: the VLAN tag, the frame size, the bridge, the quality of service, or the address. The sync button returns the host to the definition. Addressing is set on the host: a static address with a mask and a gateway, DHCP, IPv6, DNS servers. And a network label saves time: the network attaches itself to every host NIC that carries the same label.\n\nA virtual machine connects to a network not directly but through a vNIC profile. The profile lives at the network level and holds the settings: port mirroring, rate limiting, a network filter, passthrough mode, and custom properties. Permissions are granted on the profile, so a user can be let into one specific network. Quality of service comes in two kinds. For machines you set an average rate, a peak rate and a burst. For host networks you set shares, a limit and a committed rate: they divide the capacity of a physical NIC among the networks that sit on it.\n\nThe frame size must match along the whole path. If a network has an MTU of nine thousand and the switch port passes fifteen hundred, small packets flow while large ones silently vanish, and such a fault is hard to notice. MTU is set on the logical network, and the host NIC needs the maximum over its networks. For speed a virtual card can be made passthrough: the machine is given an SR-IOV virtual function, bypassing the bridge. It is fast, but filters, mirroring and rate limits do not work on such a card, and live migration needs a special solution, for example a profile with a failover card.\n\nFor overlay networks oVirt uses OVN. The provider, ovirt-provider-ovn, runs next to the engine and understands Neutron-style commands. The central OVN database stores logical switches and routers. On every host runs ovn-controller: it builds the flow rules and joins the hosts with Geneve tunnels over UDP. Security groups are turned into access lists, and addresses and MACs are handed out by OVN itself. Such a network needs no VLAN on the physical switches, but the tunnel eats part of the MTU, so the logical network usually has a smaller MTU than the physical one.\n\nMigration goes over the management network by default, but the role can be given to a dedicated network: then the memory of the machines being moved does not interfere with management. Migration speed is limited automatically from the NIC speed or set as a number. The faults are typical and repeat. A required network is missing, and the host is NonOperational. LACP was enabled on the host but not on the switch, the link was lost, and a rollback happened. The VLAN is not allowed on the trunk. The MTU does not match. The host is out of sync. First read the VDSM logs on the host and the engine log, then change things.
