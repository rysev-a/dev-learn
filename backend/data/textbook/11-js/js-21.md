#CHAPTER 21 | Сеть: fetch, CORS, WebSocket и Server-Sent Events
Современный Frontend. Глава 21. Сеть в браузере: фетч, корс, веб-сокеты и сервер-сент-ивентс. Почти любое приложение живёт за счёт данных с сервера, поэтому умение работать с сетью — основа фронтенда. В этой главе мы разберём фетч и его объекты, отмену и повторы запросов, политику одного источника и междоменные запросы, кеширование, авторизацию, новые версии протокола, а затем два способа получать данные в реальном времени. В упражнениях мы сами напишем разбор заголовков, повторы с задержкой, проверку корса, кеш с условными запросами, парсер потока событий и клиент веб-сокета.\n\nРаньше для запросов использовали объект иксэйч-ар, с обратными вызовами и неудобным интерфейсом. Современный способ — функция фетч: она возвращает промис с ответом. Вокруг неё живут три объекта: рекуэст, респонс и хедерс. Важная особенность: фетч отклоняет промис только при сетевой ошибке — нет связи, отказ в соединении, запрет корса. Ответ с кодом четыреста четыре или пятьсот — это нормальный ответ, и его успешность нужно проверять самому по полю ок или по статусу.\n\nВ запросе задают метод, заголовки и тело. Тело может быть строкой, джейсоном, формой, блобом или бинарным буфером. Для джейсона не забывайте заголовок тип содержимого и сериализацию тела. Ответ читают одним из методов: джейсон, текст, блоб, массив байтов. Тело можно прочитать только один раз — второй вызов бросит ошибку; если нужны две копии, перед чтением делают клон. Заголовки нечувствительны к регистру, а повторяющиеся значения склеиваются через запятую.\n\nТело ответа — это поток. Метод для чтения потока отдаёт ридер, который выдаёт куски байтов по мере прихода. Так можно показывать прогресс скачивания: сравнивать накопленные байты с длиной из заголовка, декодировать текст порциями через текстовый декодер и обрабатывать строки на лету, не дожидаясь конца. Нужно помнить о границах: кусок может обрезать символ или строку посередине, поэтому остаток накапливают в буфере. А вот прогресс загрузки на сервер фетч до сих пор нормально не умеет — для этого остаётся иксэйч-ар.\n\nСетевые запросы нужно уметь отменять. Для этого создают абортконтроллер и передают его сигнал в запрос; вызов абор рвёт соединение, а промис отклоняется ошибкой с именем эйборт-эрор. Так отменяют устаревшие запросы поиска, уход со страницы или медленный ответ. Для таймаута есть готовый сигнал на заданное число миллисекунд. Повторы делают только для безопасных и идемпотентных запросов, с растущей задержкой и случайным разбросом, чтобы клиенты не бросились на сервер одновременно.\n\nБраузер защищает пользователя политикой одного источника. Источник — это схема, хост и порт; страница с одного источника не может читать ответы с другого. Чтобы сервер разрешил чтение, он отвечает заголовками корса, главный из которых — разрешённый источник. Простые запросы уходят сразу, а для остальных браузер сначала шлёт предварительный запрос методом оптионс и спрашивает, какие методы и заголовки разрешены. Корс защищает чтение ответа, но сам запрос на сервер всё равно доходит. Чтобы запрос нёс куки, клиент ставит режим учётных данных, а сервер обязан вернуть точный источник вместо звёздочки; если ответ зависит от источника, нужен заголовок вэри. Исправить корс на клиенте нельзя — он настраивается только на сервере.\n\nКеширование — самый дешёвый способ ускорить сеть. Заголовок кэш-контрол задаёт срок жизни и правила: максимальный возраст, запрет на кеш, обязательную перепроверку. Когда срок вышел, браузер не обязан скачивать всё заново: он присылает условный запрос с идентификатором версии из заголовка итэг, и сервер отвечает кодом триста четыре без тела, если данные не менялись. Шаблон «отдать устаревшее и обновить в фоне» ускоряет интерфейс. У самого фетча есть режимы кеша, которые тоже можно менять.\n\nАвторизацию в запросах строят двумя способами. Первый — куки с сессией: браузер сам прикладывает их к запросам на тот же сайт, а защиту от подделки запросов дают атрибут сэйм-сайт и токены. Второй — заголовок авторизации с токеном, который приложение хранит и прикладывает само. При ответе четыреста один клиент пробует обновить токен один раз и повторить запрос; при четыреста три доступ запрещён, и повторять бессмысленно. Важно, чтобы параллельные запросы не запускали десяток обновлений токена одновременно.\n\nПротокол тоже развивается. Версия один и одна десятая открывает много соединений и ждёт ответа по очереди. Версия два мультиплексирует много запросов в одном соединении, сжимает заголовки и убирает необходимость склеивать файлы и разносить ресурсы по доменам. Версия три работает поверх протокола куик на основе юдипи и не страдает от потери одного пакета. Для фронтенда выводы такие: используйте сжатие бротли, не злоупотребляйте горячей загрузкой через предзагрузку и доверяйте браузеру приоритеты. Всё это включается на сервере и в сети доставки.\n\nКогда данные нужны мгновенно, подходит веб-сокет. Соединение начинается с обычного запроса с заголовком апгрейд, сервер отвечает кодом сто один, и дальше по тому же каналу идут кадры в обе стороны. У объекта есть события открытия, сообщения, ошибки и закрытия, а у закрытия — код и причина. Канал сам не переподключается, поэтому клиент делает это сам: с экспоненциальной задержкой, пингами для проверки живости и очередью сообщений, накопленных за время обрыва.\n\nДля односторонней рассылки с сервера есть более простое решение: сервер-сент-ивентс. Клиент создаёт объект ивент-сорс, и браузер держит обычное соединение, по которому сервер присылает текстовый поток. Каждое событие — несколько строк с полями дата, ивент и ай-ди, разделённые пустой строкой. Если связь пропала, браузер сам переподключается и сообщает серверу последний полученный идентификатор, чтобы тот досыпал пропущенное. Ограничения: только метод гет и только текст, зато работает через обычный хттп и проходит прокси.\n\nНа практике сетевой слой нужно оформлять аккуратно. Приложение следит за состоянием онлайн и накапливает запросы в очередь на время обрыва. Оптимистичные обновления показывают результат сразу и откатывают его при ошибке. Дубликаты одинаковых запросов объединяют, ответы кешируют с понятным сроком, а ошибки превращают в типизированные результаты и показывают пользователю по-человечески, а не страшным стектрейсом. Именно такую работу выполняют клиентские библиотеки вроде реакт-квери и эс-даблью-ар, и теперь мы понимаем, что внутри них.\n\nПодведём итоги. Фетч возвращает ответ даже при ошибках сервера, тело читается один раз, и его можно получать потоком. Запросы отменяют абортконтроллером, а повторы делают осторожно. Корс настраивает сервер, предварительный запрос проверяет разрешения, а учётные данные требуют точного источника. Кеш и условные запросы экономят трафик, веб-сокет даёт двусторонний канал, а сервер-сент-ивентс — односторонний с автоматическим переподключением. В следующей главе мы поговорим о сервис-воркерах и приложениях, которые работают без сети.
