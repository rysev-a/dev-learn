#SECTION JavaScript в браузере
#CHAPTER 22 | Воркеры, Service Worker и PWA: приложение, которое работает без сети
Современный Frontend. Глава 22. Воркеры, сервис-воркер и пи-даблью-эй. До сих пор весь наш код выполнялся в одном главном потоке страницы и зависел от сети. Воркеры выносят тяжёлую работу в отдельные потоки, а сервис-воркер встаёт между страницей и сетью и позволяет приложению открываться без интернета, получать уведомления и обновляться по правилам. Из всего этого складывается прогрессивное веб-приложение. В этой главе мы разберём обычные воркеры, жизненный цикл сервис-воркера, стратегии кеширования, офлайн, пуши, манифест и установку, а в упражнениях напишем уменьшенные модели каждого механизма.\n\nГлавный поток один: в нём выполняются скрипты страницы, расчёт стилей, раскладка и отрисовка. Если запустить долгое вычисление, интерфейс замирает. Выход — веб-воркер: отдельный поток со своим глобальным объектом, своей очередью событий и без доступа к документу. Воркер создают из отдельного файла, общаются с ним сообщениями через постмесседж, а данные при этом копируются алгоритмом структурного клонирования: он умеет даты, карты, множества и циклические ссылки, но не функции и не элементы страницы.\n\nКопировать большие данные дорого, поэтому есть передача владения: буфер из списка переносимых объектов не копируется, а переезжает в другой поток, и у отправителя становится пустым. Для общения напрямую служит канал сообщений с двумя портами, а общий для вкладок воркер — шаред-воркер. Разделяемую память с атомарными операциями даёт шаред-аррэй-буфер, но она требует изоляции страницы. На практике воркеры оборачивают в удалённые вызовы, как это делает библиотека комлинк, и держат пул потоков, чтобы не создавать их на каждую задачу.\n\nСервис-воркер — особый скрипт, который браузер запускает отдельно от страницы. Он работает как прокси между страницей и сетью: видит все запросы своей области и может ответить на них из кеша, из сети или собственным ответом. У него нет доступа к документу, он живёт недолго и просыпается по событиям. Работает он только по защищённому соединению, исключение — локальный хост для разработки. Областью называют путь, под которым воркер управляет страницами; по умолчанию это папка, где лежит его скрипт.\n\nУ сервис-воркера есть жизненный цикл. После регистрации браузер скачивает скрипт и запускает событие установки, в нём обычно кладут файлы в кеш. Если старая версия ещё управляет вкладками, новая ждёт в состоянии ожидания, пока вкладки не закроются. Затем наступает активация — время убрать старые кеши. Метод пропуска ожидания и захват клиентов ускоряют переход, но могут смешать версии на одной странице. При каждой проверке браузер сравнивает скрипт побайтно и считает изменением любую разницу.\n\nГлавное событие сервис-воркера — перехват запросов. Обработчик получает запрос и вызывает метод ответа с промисом, в который можно положить ответ из кеша или из сети. Если ответ не задан, запрос уйдёт в сеть как обычно. Нельзя забывать про ожидание продления жизни: фоновую работу, например обновление кеша, оборачивают в метод продления, иначе браузер усыпит воркер раньше времени. Запросы нужно различать по методу, адресу и назначению: кешировать стоит только безопасные запросы получения.\n\nКеширование строят по нескольким стратегиям. Сначала кеш, потом сеть — для неизменяемых файлов с хешем в имени. Сначала сеть, потом кеш — для данных, которые должны быть свежими, но желательно показывать хоть что-то без связи. Отдавать устаревшее и обновлять в фоне — для картинок и аватарок. Только кеш и только сеть — крайности. Интерфейс называется кеш-эй-пи-ай: открыть хранилище по имени, положить пару запрос-ответ, найти по запросу с учётом заголовка вэри, удалить. Ответ с ошибкой в кеш не кладут.\n\nКеш нужно версионировать. Имя хранилища включает версию, при активации удаляют все кеши с тем же префиксом и другой версией, иначе диск забьётся. Основные файлы приложения заранее кладут в кеш списком, в котором у каждого файла есть ревизия: при обновлении скачивают только изменившиеся, а исчезнувшие удаляют. Такой список генерирует сборщик, а готовые стратегии, правила маршрутизации и плагины срока жизни записей даёт библиотека воркбокс. Не забудьте про ограничения: число записей и возраст кеша.\n\nЧтобы приложение открывалось без сети, нужна оболочка: минимальные разметка, стили и скрипт, из которых строится интерфейс. Для навигационных запросов воркер отдаёт эту оболочку из кеша, а маршрутизатор страницы сам решает, что показывать; исключения — адреса интерфейса данных и файлы с расширениями. Когда не получилось ничего, воркер выдаёт запасную страницу: для документа — страницу «нет связи», для картинки — заглушку. Если воркер медленно просыпается, помогает предзагрузка навигации: запрос в сеть уходит параллельно запуску воркера.\n\nСтраница и воркер общаются сообщениями. Воркер может написать всем открытым вкладкам: перебрать клиентов и отправить им событие. Так делают уведомление «доступна новая версия»: страница замечает ожидающий воркер, показывает кнопку, по клику отправляет сообщение с просьбой пропустить ожидание и один раз перезагружается, когда сменится управляющий воркер. Для связи между вкладками есть бродкаст-ченнел: сообщение получают все его участники, кроме отправителя. Этим же каналом выбирают главную вкладку, которая держит единственное соединение.\n\nУведомления приходят через пуш: сервер шлёт сообщение службе браузера, а та будит сервис-воркер событием пуш, где показывают уведомление. Подписка создаётся с публичным ключом приложения, а сервер подписывает запросы по схеме вапид. Нужно разрешение пользователя и осторожность: уведомления без причины раздражают. Фоновая синхронизация помогает отправить накопленные запросы, когда появилась связь: очередь хранят в индексед-ди-би и разбирают по событию синхронизации. Периодическая синхронизация и часть возможностей доступны не во всех браузерах.\n\nПрогрессивное веб-приложение состоит из защищённого соединения, сервис-воркера и манифеста. Манифест — файл с названием, адресом запуска, областью, режимом отображения, цветами и значками; нужны значки двух размеров, в том числе маскируемый. Когда условия выполнены, браузер предлагает установку, а событие перед установкой позволяет показать собственную кнопку. Установленное приложение запускается в своём окне, и о нём важно помнить про квоты хранилища: оно оценивается по источнику, а постоянное хранение запрашивают отдельно, иначе данные могут вытеснить.\n\nПодведём итоги. Веб-воркеры выносят вычисления из главного потока и общаются копированием или передачей владения. Сервис-воркер работает как прокси с жизненным циклом: установка, ожидание, активация, а обновление определяется побайтным сравнением. Стратегии кеширования выбирают по виду ресурса, кеши версионируют, а оболочка приложения и запасные страницы дают офлайн. Пуши и фоновая синхронизация расширяют возможности, а манифест превращает сайт в устанавливаемое приложение. В следующей главе мы займёмся производительностью: что измерять и как ускорять.
