#CHAPTER 33 | Компоненты и маршрутизатор
Современный Frontend. Глава 33. Компоненты и маршрутизатор. У нас есть реактивность и виртуальный дом. Теперь нужна архитектура: как разделить интерфейс на части и связать их в приложение. Основной приём — компоненты. Компонент объединяет разметку, поведение и состояние одного кусочка интерфейса: кнопки, формы, карточки, страницы. Данные текут вниз по дереву через свойства, а сообщения о событиях поднимаются вверх через обработчики. Такое однонаправленное движение данных делает поведение предсказуемым: всегда можно понять, откуда пришло значение, и кто его изменил.\n\nСвойства — это входные данные компонента, и он не должен их менять: они принадлежат родителю. Поэтому компонент ведёт себя как функция от свойств. У свойств бывают значения по умолчанию, обязательные поля и проверки типов. Дети и слоты позволяют родителю вложить содержимое внутрь компонента: в карточку — заголовок и тело, в модальное окно — любой текст. Это называется композицией, и она гибче наследования: из небольших независимых компонентов собирают сложные, комбинируя их, а не расширяя иерархии классов.\n\nУ компонента может быть собственное состояние: открыт ли список, что введено в поле. Если состояние нужно только ему, оно остаётся внутри. Если им пользуются несколько компонентов, его поднимают к ближайшему общему предку, а вниз передают значения и функции для изменений. Если таких компонентов слишком много и путь через предков длинный, используют контекст или общее хранилище. Правило простое: держите состояние как можно ближе к месту использования и поднимайте только когда это действительно нужно: лишнее глобальное состояние усложняет проверку и отладку.\n\nУ компонента есть три момента жизни. Монтирование: он впервые появился в дереве, и здесь подписываются на события, запускают таймеры, загружают данные. Обновление: изменились свойства или состояние, и нужно перерисовать часть и, возможно, пересинхронизировать побочные эффекты. Размонтирование: компонент уходит, и необходимо отписаться, остановить таймеры, отменить запросы. Современные фреймворки выражают это эффектами с очисткой: эффект запускается при монтировании и при изменении зависимостей, а возвращаемая им функция вызывается перед следующим запуском и при удалении.\n\nСобытия в интерфейсе всплывают: элемент сообщает о клике, а затем событие поднимается к предкам. Этим пользуются для делегирования: вместо сотни слушателей на строках списка ставят один на контейнере и по цели события определяют, какая строка нажата. Компонент сообщает наверх о своих событиях через вызов функции-обработчика из свойств или собственные события. Родитель решает, что с ними делать. Всплытие можно остановить, а действие по умолчанию — отменить. Событие не должно содержать лишнего: достаточно данных, нужных получателю.\n\nИногда одно и то же значение нужно многим компонентам на разной глубине: тема оформления, язык, текущий пользователь. Передавать его через свойства каждого промежуточного компонента утомительно. Контекст решает проблему: предок предоставляет значение, а любой потомок запрашивает его по ключу и получает ближайшее значение вверх по дереву. Так же устроено внедрение зависимостей: подмена службы в тесте — это просто другой провайдер. Но злоупотреблять не стоит: неявные зависимости усложняют чтение, поэтому в контекст кладут действительно сквозные вещи.\n\nКогда состояние общее для всего приложения, его собирают в хранилище. Хранилище держит единственное значение, меняется оно только отправкой действий: простых объектов с типом. Чистая функция-редьюсер принимает старое состояние и действие и возвращает новое, не изменяя прежнее. Подписчики получают уведомления об изменениях. Такой подход делает историю изменений прозрачной: можно записать все действия и воспроизвести состояние, откатываться по шагам, тестировать редьюсер как обычную функцию. Асинхронность добавляют промежуточными обработчиками: журналом, функциями-санками.\n\nОдностраничное приложение не загружает новую страницу при переходе, но адрес в строке браузера должен меняться: чтобы ссылкой можно было поделиться, а кнопка «назад» работала. За это отвечает маршрутизатор. Он сопоставляет адрес с компонентами и, когда пользователь переходит, обновляет адрес через интерфейс истории браузера: метод пуш-стейт добавляет запись, реплейс-стейт заменяет текущую. На кнопки «назад» и «вперёд» браузер присылает событие поп-стейт, и маршрутизатор показывает соответствующий вид. Вариант с решёткой в адресе работает без настройки сервера, но выглядит хуже.\n\nМаршруты описываются шаблонами: пользователи, двоеточие, ай-ди. Параметры вырезаются из адреса, строка запроса разбирается отдельно. Маршруты вкладываются: общий каркас страницы выбирается по префиксу, а внутри него по остатку пути выбирается конкретная страница, так что результатом сопоставления становится цепочка совпавших маршрутов. Порядок проверки важен: более конкретные шаблоны идут раньше общих. Последним ставят маршрут-ловушку для неизвестных адресов, который показывает страницу «не найдено». Хорошо, когда адреса можно собрать обратно из шаблона и параметров, а не склеивать строки.\n\nКомпонент-ссылка должен оставаться настоящей ссылкой: у неё есть адрес, средний клик и клик с клавишей открывают новую вкладку. Маршрутизатор перехватывает только обычный левый клик без модификаторов по ссылке на тот же сайт и без атрибута цели, а остальное оставляет браузеру. Перед переходом работают охранники: функции, которые могут разрешить его, запретить или перенаправить, например на вход. Охранники бывают асинхронными, а новый переход отменяет незавершённый предыдущий. Для редиректов нужен предел глубины, чтобы цикл не завис.\n\nНе нужно загружать код всех страниц сразу. Маршрут описывается функцией, которая возвращает динамический импорт, и сборщик превращает каждую страницу в отдельный файл. При первом переходе код загружается, пока идёт ожидание, показывается индикатор, а при ошибке — запасной вид. Результат кэшируется, и повторный переход мгновенный. Загрузку можно начать заранее: при наведении курсора на ссылку или когда ссылка появилась в зоне видимости. Баланс прост: основной экран должен открываться быстро, а остальное подгружаться так, чтобы пользователь ожидания не замечал.\n\nСтраница обычно требует данных, и удобно связывать их загрузку с маршрутом: у каждого совпавшего маршрута есть загрузчик, и все они выполняются параллельно, а не друг за другом. Пока данные идут, показывается состояние загрузки; если загрузчик вернул ошибку, она не должна ронять всё приложение. Для этого вокруг частей интерфейса ставят границу ошибок: она ловит исключение при отрисовке дочерних компонентов и показывает запасной вид с возможностью повторить. Не забывайте и о доступности: при переходе обновляйте заголовок страницы и объявляйте её смену для программ экранного чтения.\n\nПодведём итоги. Компонент — единица интерфейса: свойства идут вниз, события вверх. Композиция через детей и слоты гибче наследования. Состояние держат как можно ближе к использованию и поднимают при необходимости, а сквозные значения передают контекстом. Общее хранилище меняется только действиями через чистые редьюсеры. Жизненный цикл выражается эффектами с очисткой. Маршрутизатор связывает адрес с видом через интерфейс истории, сопоставляет шаблоны с параметрами и вложенностью, перехватывает ссылки и выполняет охранники. Страницы грузятся лениво, данные — параллельно. В последней главе соберём проект целиком.
