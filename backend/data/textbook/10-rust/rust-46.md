#CHAPTER 46 | JSON, serde и единый тип ошибки
Изучаем Раст. Глава 46. Джейсон, серде и единый тип ошибки. Наш чат общается с клиентами через джейсон. Чтобы это было надёжно, нужны две вещи. Во-первых, точные типы данных: запрос разбирается в структуру, а всё неверное отсекается на входе. Во-вторых, единый формат ошибок: клиент должен одинаково понимать, что пошло не так, будь то пропавшая комната, занятое имя или сбой базы. В этой главе мы построим оба слоя: типы запросов и ответов, а также одно перечисление ошибок на всё приложение.\n\nСерде — общая библиотека сериализации. Она отделяет структуру данных от формата: структура объявляет, что умеет превращаться и собираться, а формат — джейсон, яммл или двоичный — реализован отдельно. Для структур достаточно двух производных признаков: сериалайз и десериалайз. Дальше серде-джейсон превращает значение в строку и обратно. Разбор строгий: лишнего типа или пропущенного обязательного поля он не простит и вернёт ошибку с позицией. Это основа безопасной границы системы: внутрь попадают только данные ожидаемой формы.\n\nПоведение настраивается атрибутами. Переименование всех полей в верблюжий регистр нужно для клиентов на джаваскрипте. Значение по умолчанию позволяет клиенту не присылать поле. Пропуск пустых значений делает ответ компактнее. Атрибут деный-анноун-филдс запрещает неизвестные поля: так опечатка в имени не пройдёт молча. Алиасы принимают старые имена полей, а флэттен вкладывает поля одной структуры в другую на одном уровне. Атрибуты — часть контракта: меняя их, вы меняете формат, который видят клиенты, поэтому изменения нужно вносить осознанно.\n\nПеречисления в джейсоне можно представить по-разному. По умолчанию вариант записывается как объект с одним ключом — именем варианта. Атрибут таг делает поле-метку внутри объекта: тип равен, например, сообщение, и рядом лежат остальные поля. Такой формат удобен клиентам: они смотрят на поле тип и выбирают обработчик. Вариант без тега пробует все варианты по очереди и годится только для особых случаев. Для событий чата мы используем внутренний тег: сообщение, вход пользователя, выход, и каждое событие несёт свои поля.\n\nХороший приём называется «разбирай, а не проверяй». Вместо того чтобы хранить имя пользователя как строку и всюду проверять длину, заводят отдельный тип, создать который можно только из допустимой строки. Конструктор возвращает результат, и недопустимое значение просто не существует. Через признак трай-фром такой тип подключается к серде: некорректное имя отвергается при разборе тела запроса. Так проверка выполняется один раз на границе, а внутри кода вы работаете с типами, чьи инварианты гарантированы компилятором и конструктором.\n\nЭкстрактор джейсон отказывает тремя способами. Синтаксическая ошибка даёт четыреста. Неверный заголовок типа содержимого даёт четыреста пятнадцать. Данные неверной формы дают четыреста двадцать два. Ответ по умолчанию — просто текст, а клиенту нужен привычный формат. Поэтому пишут обёртку: свой экстрактор, который вызывает стандартный, а при отказе возвращает ошибку приложения. После этого все отказы разбора выглядят как остальные ошибки. Дополнительно он может выполнить валидацию и вернуть список проблемных полей.\n\nЗавести одно перечисление на все ошибки приложения — хорошая практика. В нём варианты по смыслу: не найдено, конфликт, неверные данные со списком полей, не авторизован, запрещено, внутренняя ошибка. Каждый вариант знает свой код статуса и короткий машинный код для клиента. Обработчики возвращают результат с этим типом ошибки и пользуются оператором вопроса. Тип реализует отображение для журнала и стандартный признак ошибки, чтобы подключаться к цепочкам причин. Так сложная логика обработки отказов сводится к одной точке.\n\nЧтобы обработчик мог вернуть ошибку напрямую, для неё реализуют превращение в ответ. Статус берётся по варианту, а тело — одинакового формата: машинный код, человекочитаемое сообщение и необязательный список полей. Важное правило безопасности: для внутренних ошибок клиенту показывают только общее сообщение, а подробности пишут в журнал с идентификатором запроса. Иначе в ответ может утечь текст запроса к базе или путь на диске. Единый формат ещё и упрощает клиенту обработку: один разбор на все случаи.\n\nОператор вопроса автоматически преобразует ошибку через признак фром. Поэтому для каждой внешней ошибки пишут преобразование в ошибку приложения: ошибка базы данных, ошибка разбора, ошибка ввода-вывода. Особый случай — база: отсутствие строки превращается в не найдено, нарушение уникальности — в конфликт, остальное — во внутреннюю ошибку. Код обработчика становится линейным: запросили, получили, вернули, без вложенных проверок. Внешняя библиотека для генерации таких реализаций называется зис-эррор, но их легко написать и вручную.\n\nФормат ошибки — такая же часть контракта, как и формат успешных ответов. Хороший вариант: объект с полем ошибка, а в нём машинный код, сообщение для человека и необязательный массив проблемных полей с именем и причиной. Машинный код стабилен, по нему клиент выбирает поведение, а сообщение можно менять и переводить. Все маршруты возвращают ошибки в одном формате, включая те, что порождает сам каркас: неизвестный путь, неверный метод, слишком большое тело. Для этого настраивают запасной обработчик и обёртки экстракторов.\n\nСтруктуры для обмена с клиентом лучше отделять от внутренних моделей и от строк базы. Запрос на создание комнаты содержит только имя, а модель в базе — ещё идентификатор и время создания. Ответ не должен показывать хеш пароля, даже если он есть в строке. Отдельные структуры позволяют менять базу, не ломая клиентов, и наоборот. Преобразования между ними — простые функции или признак фром. Небольшая избыточность окупается: каждая граница получает точный тип, а случайно утечь лишнему полю становится труднее.\n\nКонтракт со временем меняется, и менять его надо совместимо. Новые поля в ответах добавляют свободно: клиенты их игнорируют. Новые поля в запросах делают необязательными. Переименование проводят через алиас: принимаем старое и новое имена, отдаём новое. Удаление поля сначала объявляют устаревшим. Строгий запрет неизвестных полей хорош для запросов, где опечатка опасна, но вреден в клиентских моделях, которые должны терпеть расширение. Различие между отсутствующим полем и явным нулём важно для частичных обновлений: его выражают двойным оптионом.\n\nПодведём итоги. Серде отделяет данные от формата, атрибуты задают контракт, перечисления с внутренним тегом удобны для событий. Валидацию выполняют один раз на границе, превращая данные в типы с гарантиями. Один тип ошибки приложения превращается в ответ с нужным статусом и единым телом, подробности внутренних ошибок остаются в журнале. Оператор вопроса и реализации фром делают код линейным. Запросы, ответы и внутренние модели разделены. В следующей главе подключим базу данных через эс-кью-эл-экс.
