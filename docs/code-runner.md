# Проверка кода: очередь и воркеры

Проверка решений (python, js, c, rust, sql) — самая тяжёлая и самая опасная часть сервиса: это запуск чужого кода.
Поэтому API **не запускает контейнеры сам**: решение попадает в очередь (`backend/app/exercises/jobs.py`), а выполняет его воркер.

```
браузер ──POST /api/exercises/run──► API (VPS) ──► таблица exec_jobs ◄── claim (долгий опрос, исходящий HTTPS) ── воркер (VM дома)
   ▲                                                                                                                  │
   └──────── GET /api/exercises/run/{id} (queued → running → done) ◄── POST /internal/worker/jobs/{id}/result ◄───────┘
```

## Режимы

| `SAY_RUNNER` | кто выполняет | когда |
|---|---|---|
| `local` (по умолчанию) | потоки внутри API (`local_worker.py`, `SAY_LOCAL_SLOTS`, по умолчанию `light:3,heavy:1`) | разработка, одна машина |
| `remote` | только внешние воркеры (`backend/worker.py`) | прод: API на VPS, Docker на отдельной машине |

В режиме `remote` нужен `SAY_WORKER_TOKEN` (общий секрет API и воркеров); без него `/internal/worker/*` отвечает 404.
Если ни один воркер не отозвался за 30 с, `POST /run` отвечает 503 «проверка временно недоступна» (теория, вопросы и
лаборатории в браузере продолжают работать). Состояние — `GET /api/exercises/runner/status`.

## Что делает очередь

- Полосы: `light` (python, js, sql — секунды) и `heavy` (rust, c — компиляция); у воркера свои слоты на каждую.
- У пользователя не больше одной проверки; в очереди не больше 300 заданий (иначе 503).
- Аренда задания 45 с, воркер продлевает её сердцебиением каждые 10 с; пропал — задание возвращается в очередь (две попытки,
  потом ошибка «сервер проверки не ответил»).
- Одинаковое решение одной версии задачи отдаётся из кэша (`exec_cache`, 7 дней), воркер не нужен.
- Попытку и статус «решено» записывает API по результату, у воркера доступа к базе нет.

## Песочница (`runner.py`)

`--network none`, лимиты памяти/CPU/процессов, `--read-only`, tmpfs, `--cap-drop ALL`, `no-new-privileges`, `ulimit`,
пользователь `nobody` (кроме задач с PostgreSQL: им нужен root и несколько возможностей), потолок вывода 1 МБ, контейнер
получает имя и **останавливается по имени при таймауте** (раньше убивался только клиент docker, а цикл крутился дальше),
при старте воркер удаляет забытые контейнеры `say-run-*`.

## Воркер на домашнем сервере

1. VM (KVM: Proxmox/libvirt) в отдельной сети, лимиты на ядра/память/диск. Файрвол VM: исходящее **только** на VPS:443 (плюс DNS и
   окно обновлений), в домашнюю сеть доступа нет, входящих нет (кроме SSH из админской сети). Раз в сутки или при подозрении — откат к снимку.
2. В VM: Docker, образы `python:3.13-slim`, `rust:1.97-slim`, `node:22-alpine`, `say-rust-crates:1`
   (`docker build -t say-rust-crates:1 backend/docker/rust-crates`), репозиторий и `uv`.
3. Запуск (systemd-юнит с `Restart=always`):

   ```
   SAY_WORKER_TOKEN=… uv run worker.py --server https://say.example.com --name home-1 --light 4 --heavy 2
   ```

   На VPS: `SAY_RUNNER=remote SAY_WORKER_TOKEN=… uv run uvicorn app.main:app`.
4. Усиление изоляции следующим шагом: gVisor (`--runtime=runsc`) внутри VM; метрики очереди и числа контейнеров.

## Что ещё нужно до публичного запуска

Лимиты на регистрацию, вход и `run` по IP, HTTPS и `secure`-cookie, удаление временных пользователей, квоты на черновики, WAL в SQLite
(или переезд на Postgres). Подробнее — обсуждение в истории проекта: открытая регистрация обходит лимит «одна проверка на пользователя».
